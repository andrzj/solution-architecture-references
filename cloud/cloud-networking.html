Cloud Architecture Networking

Cloud Networking

How to design virtual networks, segment workloads, connect hybrid sites, and publish services across AWS VPC, Azure VNet, and Google Cloud VPC—with hub-spoke transit, private connectivity, and DNS for multi-region availability.

⏱ 11 min read

What it is

Cloud networking is how workloads, users, and hybrid data centres meet inside a provider’s virtual network: segmenting tiers with subnets and policy, routing between virtual networks and regions, publishing DNS, and steering traffic through load balancers, private endpoints, and edge caches.

Each hyperscaler names the primitives differently—AWS VPC, Azure virtual network (VNet), Google Cloud VPC—but the design patterns recur. A three-tier subnet layout separates public tiers (internet ingress, NAT egress), private application tiers, and isolated data tiers with no path to the internet. Replicate each tier across multiple availability zones so a single zone loss does not take the service offline.

CIDR planning is fixed-cost to get wrong: virtual network ranges must not overlap on-premises address space (for VPN, ExpressRoute, or Direct Connect), sibling environments, or future hub attachments. Reserve non-overlapping RFC 1918 blocks per environment and region in central IPAM—AWS VPC IPAM, Azure IPAM in Virtual WAN, or a provider-agnostic registry—before the first landing-zone account is vended.

Hub-and-spoke connectivity scales past pairwise peering: AWS Transit Gateway, Azure Virtual WAN, and Google Cloud Network Connectivity Center (with Shared VPC where appropriate) attach many spokes to shared transit, DNS, and egress inspection. Private connectivity to PaaS—AWS PrivateLink, Azure Private Link, Google Private Service Connect—exposes provider-managed APIs on RFC 1918 addresses inside your VPC without public internet paths or full mesh peering.

Why it exists

Cloud breaches often start with overly broad network exposure: databases reachable from the internet, flat VNets where a compromised dev workload can scan production, or hybrid routes that accidentally advertise on-premises ranges into the wrong subscription. Subnet tiering and explicit route tables implement defence in depth—misconfigured security groups alone should not put data on a public path.

Modern estates are multi-network by design: one virtual network per environment, per team account, or per regulated workload. Mesh peering does not scale; transitive hubs centralise route policy, firewall inspection, and shared hybrid attachment. DNS and global load balancing sit above the network layer so users reach healthy regional endpoints without application code knowing which region is active.

When to use

  • Three-tier segmentation for production: public, private, and isolated subnets in every region—cheap insurance on all three clouds.
  • Hub transit when you have more than a handful of virtual networks, a landing zone with a connectivity subscription, or a requirement for centralised egress or inspection (NAT plus firewall in a dedicated hub).
  • Private Link / Private Service Connect / PrivateLink when consumers need your API or a managed service (object storage, key vault, registry) without internet exposure or peering every consumer VPC.
  • Latency-based DNS (Route 53, Azure Traffic Manager performance, Cloud DNS routing policies) when users should hit the nearest healthy region.
  • Failover DNS or global load balancers for active–passive DR where health-checked records or front doors redirect when a region fails.
  • Hybrid connectivity (Site-to-Site VPN, AWS Direct Connect, Azure ExpressRoute, Google Cloud Interconnect) when latency, bandwidth, or compliance requires a private path to on-premises or colocation.

When not to use

  • Full mesh peering among many VPCs or VNets: attachment count and route table complexity grow quadratically; use a hub instead.
  • Edge CDN for east–west API traffic: CloudFront, Azure Front Door, and Cloud CDN terminate user-facing HTTP; service-to-service calls stay on internal load balancers or a mesh.
  • Geolocation DNS for latency: geolocation follows resolver country, not RTT; prefer latency or performance routing unless residency mandates geography.
  • Single-AZ NAT: AWS NAT Gateway, Azure NAT Gateway, and Cloud NAT should be zone-redundant—one NAT in one zone couples all private egress to that zone’s fate.
  • Public endpoints on data tiers even temporarily: remediate with private endpoints and private DNS zones rather than leaving SQL or storage on a public IP.

Typical architecture

Internet-facing load balancers or application gateways sit in public subnets; application tiers in private subnets reach data stores in tiers without a default route to the internet. Spoke virtual networks attach to a hub for hybrid and cross-account traffic; global DNS or a global load balancer fronts multi-region active or standby pairs.

Pros and cons

Pros

  • Tiered subnets implement defence in depth without changing application binaries—routing, not app config, enforces reachability.
  • Hub transit simplifies policy: one place to inspect egress, advertise hybrid routes, and attach new landing-zone spokes.
  • Private service connectivity exposes PaaS and shared APIs on internal IPs—no internet gateway on the consumer side.
  • Managed DNS and global front doors combine health checks with short TTLs for regional failover patterns.
  • Provider edge networks absorb DDoS and cache static content, shrinking origin load and cross-region bandwidth.

Cons

  • CIDR mistakes are painful: expanding or merging overlapping networks often means rebuild, not resize.
  • Hub data processing and cross-AZ transfer fees accumulate on chatty east–west traffic—design aggregates and endpoints deliberately.
  • NAT and hybrid circuits are recurring cost centres; high outbound or on-premises sync traffic needs FinOps visibility early.
  • DNS-based failover is eventually consistent—TTL and health-check intervals bound how fast traffic shifts.
  • Hybrid and multi-cloud networking multiplies route tables, firewalls, and ownership—documentation and automation are mandatory.

Implementation notes

Allocate address space centrally before the first spoke ships. On AWS, enable VPC IPAM organisation-wide; on Azure, plan hub CIDRs in Virtual WAN and document VNet peering versus hub attachment; on Google Cloud, use Shared VPC for shared services and reserve subnet ranges per project in IPAM or a runbook-backed registry. Size spokes with room for additional subnets (often a /16 per environment with /24 slices per tier per zone).

Reduce NAT load: on AWS use gateway endpoints for S3 and DynamoDB and interface endpoints for high-volume control-plane APIs; on Azure prefer service endpoints or private endpoints for storage and SQL; on GCP combine Private Google Access with restricted APIs where applicable. For hybrid, terminate ExpressRoute, Direct Connect, or Interconnect in the hub, propagate only agreed prefixes, and avoid asymmetric routing through split tunnelling unless deliberate.

Publish internal services with provider private-link patterns and private DNS zones (Route 53 private hosted zones, Azure Private DNS, Cloud DNS private zones). For global entry, terminate TLS at a managed front door, set deep health checks on backends, and keep failover records or origin groups in infrastructure as code beside the networking modules.

Plan VPC CIDRs with IPAM headroom—overlapping ranges cannot be peered later without NAT hacks. PrivateLink and private endpoints keep SaaS and PaaS traffic off the public internet; pair with private hosted zones so clients resolve producer names inside the VPC. Centralized NAT simplifies egress filtering but becomes a cost and bandwidth choke point; prefer gateway endpoints and split egress by tier. Where dual-stack is required, assign IPv6 subnets deliberately and document whether security groups or firewall rules differ from IPv4. Hybrid DNS often needs conditional forwarders: on-prem resolves cloud private zones via forwarding links, and cloud resolver rules send corporate suffixes to data-center DNS—test split-horizon before cutover.

Common failure modes

  • Overlapping CIDRs discovered when a new spoke must peer or attach to the hub—only IPAM discipline or a painful rebuild fixes it.
  • Single-AZ NAT or firewall making every private subnet depend on one availability zone for egress.
  • Overly permissive NSGs or security groups left from development (0.0.0.0/0 on admin or database ports)—complement with config rules and periodic access reviews.
  • No flow or diagnostic logs when investigating lateral movement—enable VPC Flow Logs, NSG flow logs, or Firewall Insights with retained storage.
  • Shallow health checks that return 200 while the data tier is down—validate dependencies in the probe path used by DNS or the global load balancer.

Decision checklist

  • Do production virtual networks use three tiers with data stores on subnets (or tiers) without internet default routes?
  • Is every allocated CIDR recorded in IPAM with owner, environment, and region before attachment to a hub?
  • Is NAT or egress inspection zone-redundant on each spoke that needs outbound internet?
  • Are high-volume managed APIs reached via private endpoints or service endpoints instead of NAT hairpins?
  • Are flow logs or equivalent enabled with retention that meets security and compliance needs?
  • For multi-region apps, do DNS or global load balancers use deep health checks and tested failover runbooks?

Example use cases

  • Illustrative scenario — Meridian Commerce fronts static assets and APIs with a global CDN, uses latency-based DNS across three regions, and keeps cache hit rates high enough that most storefront traffic never hits origin compute.
  • Illustrative scenario — An enterprise landing zone attaches many workload subscriptions to Virtual WAN or Transit Gateway in a connectivity account, inspects egress centrally, and exposes shared services through private link so spokes avoid mesh peering.
  • Illustrative scenario — Northwind Logistics runs active–passive regional APIs: health-checked DNS or traffic manager profiles fail over when regional load-balancer targets are unhealthy.
  • Illustrative scenario — A manufacturing firm extends on-premises Active Directory into cloud VNets over ExpressRoute with split DNS so identity traffic stays on the private path while SaaS egress uses centralised NAT in the hub.
