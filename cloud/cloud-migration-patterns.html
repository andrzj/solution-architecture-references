Cloud Architecture Migration

Cloud Migration Patterns

The 6 Rs framework for categorising migration approaches, wave planning, Strangler Fig modernisation, database migration with DMS, and risk mitigation strategies for large-scale cloud migrations.

⏱ 12 min read

What it is

Cloud migration patterns are repeatable ways to move workloads from on-premises or co-lo estates into public cloud (or between clouds): how you classify each application, sequence dependencies, cut over data, and optionally modernize after landing. The widely used 6 Rs portfolio lens—Retire, Retain, Rehost, Replatform, Refactor, and Repurchase—assigns each system a disposition with different cost, risk, and duration.

Rehost moves VMs or containers with minimal change; replatform swaps specific components for managed services without redesigning the whole app; refactor rebuilds for elasticity and operability; repurchase replaces custom software with SaaS; retire decommissions; retain keeps systems on-premises until a later window. Complementary patterns include migration waves (dependency-ordered batches), database replication and cutover for data tier risk, and the Strangler Fig for incremental replacement of a monolith behind a routing façade.

Portfolios rarely refactor everything at once. Typical enterprise mixes skew toward rehost and replatform for datacenter exit, with refactor reserved for strategic systems and a funded backlog for post-migration optimization.

Why it exists

Lease ends, hardware refresh cliffs, and consolidation mandates force exit dates that full re-architecture cannot meet. A classification framework prevents paralysis (“modernize everything”) and prevents silent debt (“lift everything, optimize never”). It gives executives a portfolio view and gives engineers wave plans grounded in dependency discovery.

Data stores drive the highest migration risk: schema compatibility, stored procedures, replication lag, and rollback. Continuous replication with a parallel-run period and explicit validation gates reduces cutover surprises compared with weekend-only dumps. Modernization patterns like Strangler Fig decouple exit deadlines from multi-year rewrite programmes.

When to use

  • Rehost when a fixed exit date dominates and the application can run unchanged on cloud VMs or containers.
  • Replatform when a targeted bottleneck (commercial database, cache, message broker) maps cleanly to a managed equivalent.
  • Refactor when cloud-native elasticity or delivery speed is a stated outcome and capacity exists beyond the exit programme.
  • Repurchase when commodity functions (HR, CRM, email) cost more to operate than a SaaS subscription.
  • Strangler Fig when a monolith must shrink incrementally without big-bang rewrites or shared-state coupling across domains.

When not to use

  • Refactor on the exit critical path: Microservice decomposition belongs in a follow-on programme with its own budget and milestones.
  • Rehost without a modernization backlog: Lift-and-shift without rightsizing, resilience review, or managed-service targets often raises cost.
  • Strangler where extract is simpler: Stateless modules with clean boundaries may migrate wholesale faster than maintaining a long-lived proxy layer.

Typical architecture

Assessment routes each application to an R disposition; database migrations add replication paths; strangler deployments interpose routing between legacy and new services.

Pros and cons

Pros

  • Rehost and automated lift tools accelerate datacenter exit when discovery and waves are disciplined.
  • Log-based database replication supports parallel-run validation before connection cutover.
  • Strangler Fig limits blast radius compared with monolithic big-bang rewrites.
  • Portfolio tagging (6 Rs) aligns executives, finance, and engineering on scope per application.
  • Post-landing optimization (rightsizing, commitments, managed swaps) can follow without blocking exit dates.

Cons

  • Lift-and-shift of oversized VMs often inflates cloud spend until rightsizing runs.
  • Heterogeneous database moves expose manual conversion work for procedures and triggers.
  • Ignoring dependency graphs breaks integrations when callers and callees land in different waves.
  • Long-lived routing proxies for strangler patterns add latency and operational ownership.
  • Dual-running datacenter and cloud during migration raises temporary cost and complexity.

Implementation notes

Start with automated discovery of servers, utilization, and east-west traffic; build waves so no migrated application depends on a system left behind. Pilot waves should be low-risk internal tools to harden runbooks before customer-facing tiers.

For databases, prefer full load plus change-data capture when the engine supports it; hold parallel run until business validation queries match and replication lag stays within agreed bounds. Heterogeneous moves need schema and procedure assessment reports up front so manual rewrite effort is budgeted, not discovered at cutover week.

Document rollback: keep the source environment read/write-capable for a defined soak period, freeze schema changes during cutover windows, and assign an owner to the post-migration optimization backlog (rightsizing, resilience, replatform targets).

Common failure modes

  • Unmapped dependencies: An upstream service migrates before its synchronous downstream partner, causing timeouts or data inconsistencies.
  • Undersized replication: Large tables prolong initial load and CDC catch-up, blowing maintenance windows.
  • Conversion surprise: Assessment percentages applied to hundreds of stored procedures explode into quarters of manual work.
  • Premature decommission: Source systems are powered off before soak validation finishes, removing rollback options.
  • License model mismatch: Bring-your-own-license versus license-included pricing changes TCO on commercial databases.

Decision checklist

  • Has discovery produced a dependency graph used to sequence migration waves?
  • Does every application have a documented 6 R disposition with rationale?
  • For data tiers, is replication strategy, parallel-run duration, and validation checklist defined?
  • Does each wave include rollback steps and a minimum soak period on the source?
  • Is dual-run infrastructure cost included in the programme budget?
  • Is there a named owner and timeline for post-migration optimization work?

Example use cases

  • Illustrative scenario — A datacenter exit classifies hundreds of servers into retire, retain, rehost, and replatform buckets; early waves move internal tooling, final waves take payment paths after runbooks mature, and a backlog tracks refactor candidates after the lease ends.
  • Illustrative scenario — A commercial database moves to a managed open-source engine using schema conversion tooling for DDL, manual rewrite for unsupported procedures, and two weeks of dual-write validation before DNS cutover.
  • Case study — Capital One publicly described a multi-year migration to AWS using portfolio-based waves and strong platform foundations rather than a single big-bang rewrite.
