Cloud Architecture Migration

Cloud Migration Patterns

The 6 Rs framework for categorising migration approaches, wave planning, Strangler Fig modernisation, database migration with DMS, and risk mitigation strategies for large-scale cloud migrations.

⏱ 12 min read

What it is

Cloud migration patterns are repeatable ways to move workloads from on-premises, colocation, or another cloud into a target platform: how you classify each application, sequence dependencies, replicate data, cut over traffic, and optionally modernize after landing. The widely used 6 Rs portfolio lens—popularised in AWS prescriptive guidance and aligned with Gartner’s disposition vocabulary—assigns every system one of Retire (decommission unused software), Retain (stay on-premises for the current programme window), Rehost (lift-and-shift VMs or containers with minimal change), Replatform (lift with targeted managed-service swaps), Refactor (re-architect for cloud-native capabilities), or Repurchase (replace with SaaS). Each R carries a different cost, risk, and duration profile.

In a large portfolio, distributions often cluster around exit speed: many applications land in rehost and replatform buckets for datacenter closure, a smaller share in refactor once funding exists, and retain or retire decisions remove scope from the critical path. Complementary execution patterns include migration waves (dependency-ordered batches), continuous database replication and cutover for data-tier risk, and the Strangler Fig for incrementally replacing a monolith behind a routing façade without a big-bang rewrite.

Rehost is not “finished architecture”; it is a time-boxed disposition. Replatform trades a bounded conversion (commercial database to managed open-source engine, self-hosted cache to managed Redis) for operability gains without redesigning application logic. Refactor is reserved for systems where elasticity, delivery speed, or managed-service fit is a stated business outcome—not every workload on the exit critical path.

Why it exists

Lease ends, hardware end-of-life cliffs, and consolidation mandates create fixed exit dates that full re-architecture cannot meet. Without a classification framework, programmes stall trying to modernize everything at once, or they lift everything and never fund post-migration optimization—both outcomes inflate cost and miss deadlines. The 6 Rs give executives a portfolio view and give engineering wave plans grounded in discovery output rather than optimism.

Database migration remains the highest-risk component for most estates. Schema differences, stored procedures, replication lag, and rollback windows dominate cutover planning. Services such as AWS Database Migration Service (DMS) support full load plus change data capture (CDC) so source and target can run in parallel while applications validate against both sides; AWS Schema Conversion Tool (SCT) estimates how much DDL and procedure logic can convert automatically versus manual rewrite. Understanding replication and conversion depth before wave planning is how teams avoid discovering a multi-quarter procedure rewrite during the final maintenance window.

Modernization patterns like Strangler Fig decouple exit deadlines from multi-year rewrite programmes: traffic routes incrementally to new services while legacy cores remain until domains are fully extracted. That separation lets datacenter exit complete on time while product teams fund refactor waves afterward.

When to use

  • Rehost when a fixed exit date dominates, discovery shows stable dependencies, and the application can run unchanged on cloud VMs, instances, or lift-and-shift tooling (for example AWS Application Migration Service) without touching business logic.
  • Replatform when a specific bottleneck maps cleanly to a managed equivalent—commercial RDBMS to Aurora or RDS, self-hosted Redis to ElastiCache, message broker to a managed queue—without redesigning the whole application.
  • Refactor when cloud-native elasticity, reliability, or development velocity is a funded outcome and capacity exists outside the datacenter exit sprint; tie milestones to product value, not lease dates alone.
  • Repurchase when commodity capabilities (HR, CRM, email) cost more to operate and secure than a vetted SaaS subscription that eliminates custom migration work entirely.
  • Retire when usage analytics, CMDB records, or dependency graphs prove an application no longer serves a business function—removing it shrinks wave scope and cost.
  • Strangler Fig when a monolith must modernize incrementally: route specific routes or domains to new services behind a proxy or gateway while shared legacy modules remain until extraction completes.

When not to use

  • Refactor under exit time pressure: Decomposing a monolith into microservices on the same timeline as datacenter closure is a common failure mode; separate migration from modernization programmes with distinct budgets.
  • Rehost without a post-migration backlog: Lift-and-shift without rightsizing, resilience review, reserved capacity planning, or replatform targets often raises monthly cloud spend versus on-premises for years.
  • Strangler for cleanly bounded modules: Stateless components with narrow interfaces may migrate wholesale faster than maintaining a long-lived routing proxy and dual codepaths.
  • Big-bang database cutover without parallel run: Weekend-only dumps without CDC validation rarely meet RPO expectations for OLTP systems with active writes.

Typical architecture

Assessment routes each application to an R disposition; database migrations add replication paths; strangler deployments interpose routing between legacy and new services.

Pros and cons

Pros

  • Rehost and continuous replication tooling accelerates datacenter exit when discovery, waves, and runbooks are disciplined.
  • CDC-based database migration enables parallel-run validation and low-downtime cutover compared with dump-and-restore weekends.
  • Strangler Fig limits blast radius versus monolithic rewrites while preserving revenue-critical paths on legacy cores during transition.
  • Portfolio tagging on the 6 Rs aligns executives, finance, auditors, and engineering on scope and risk per application.
  • Post-landing optimization—rightsizing, savings plans, managed-service replatforms—can proceed on a backlog without blocking exit dates.

Cons

  • Lift-and-shift of oversized VMs often inflates cloud spend until rightsizing and purchasing models catch up.
  • Heterogeneous database moves expose manual conversion work for procedures, triggers, and incompatible types.
  • Unmapped east-west dependencies break integrations when callers and callees land in different waves or regions.
  • Long-lived strangler proxies add latency, routing complexity, and operational ownership until legacy cores decommission.
  • Dual-running datacenter and cloud estates during migration raises temporary cost, staffing load, and change-control overhead.

Implementation notes

Begin with application and server discovery—utilization, dependency graphs, and data classifications—before assigning Rs or wave numbers. Sequence waves so no migrated workload depends on a system still on-premises unless latency and connectivity are explicitly engineered (for example dedicated links or temporary APIs). Pilot waves should target low-risk internal tools to harden runbooks, rollback steps, and observability baselines before customer-facing tiers move.

For compute-heavy rehost paths, use block-level or agent-based replication where appropriate, validate networking and identity in the target landing zone first, and automate cutover playbooks. For data tiers, prefer full load plus CDC when the engine supports it; monitor replication lag (for example DMS CDCLatencySource and CDCLatencyTarget) and hold parallel run until business validation queries match and lag stays within agreed bounds. Run SCT or equivalent assessment early on heterogeneous moves so manual procedure rewrite effort appears in the plan, not during cutover week.

Strangler implementations route at the edge—API gateway, service mesh ingress, or reverse proxy—so new domains deploy independently while legacy models stay behind an anti-corruption layer. Document rollback explicitly: keep sources read/write-capable through a defined soak period, freeze schema changes during cutover windows, and assign an owner to the post-migration optimization backlog with timeline and KPIs (cost per environment, incident rates, managed-service adoption).

The seven Rs guide wave planning: Retire unused systems; Retain on-prem when cloud TCO fails; Rehost (lift-and-shift); Relocate to cloud VMware or bare metal; Replatform (managed DB, containers); Refactor or Repurchase (SaaS). Choose R per workload from discovery data—not a single R for the estate. Strangler fig routing at the edge splits traffic by capability while the monolith shrinks. Data migration uses bulk load plus CDC when available; hold cutover until replication lag stays inside RPO with representative validation queries. Waves order dependencies: migrate services only after their synchronous downstreams or stub APIs exist in the target landing zone.

Assign each wave an executive sponsor and a numeric success criterion—cost delta, incident rate, or latency—so migration does not stall in permanent hybrid limbo.

Common failure modes

  • Dependency mapping skipped: An upstream service migrates before its synchronous downstream partner; post-cutover latency spikes and partial failures appear—always base wave order on discovered call graphs, not org charts.
  • DMS large-table full load timeout: Very large unpartitioned tables extend initial load and CDC catch-up beyond maintenance windows—pre-split tables, right-size replication instances, and rehearse timing.
  • Stored procedure conversion underestimated: A modest “manual conversion” percentage applied to hundreds of procedures becomes quarters of engineering—quantify procedure count before committing cutover dates.
  • No rollback plan: Source systems decommission before cloud validation completes, leaving no path back when data or integration defects surface—retain sources through a minimum soak with documented promotion and demotion steps.
  • Licensing surprise: Bring-your-own-license versus license-included pricing on commercial databases shifts TCO materially—engage licensing specialists before replatform decisions land in contracts.

Decision checklist

  • Has application discovery and dependency mapping completed before migration waves are named and scheduled?
  • Does every application have a documented 6 R disposition with business and technical rationale?
  • For database workloads, is replication mode (full load, CDC), parallel-run duration, and validation query pack defined and owned?
  • Has heterogeneous conversion assessment quantified manual procedure and trigger work with realistic staffing?
  • Does each wave include rollback steps and a minimum soak period on the source before decommission?
  • Is dual-run infrastructure cost included in the programme budget and finance forecast?
  • Is there a named owner, timeline, and success metrics for post-migration optimization (rightsizing, resilience, replatform)?

Example use cases

  • Illustrative scenario — A datacenter exit classifies hundreds of servers into retire, retain, rehost, and replatform buckets; early waves move internal tooling and batch schedulers, final waves take payment paths after runbooks mature, and a funded backlog tracks refactor candidates after the lease ends.
  • Illustrative scenario — A commercial database moves to a managed open-source engine using schema conversion for DDL, manual rewrite for unsupported procedures, CDC parallel run, and a maintenance-window DNS cutover only after row-count and checksum validation succeed.
  • Illustrative scenario — A legacy monolith routes /api/v2/orders to a new service behind a gateway while inventory and reporting remain on the old stack; one domain migrates per quarter without stopping the exit programme clock.
  • Case study — Capital One publicly described a multi-year migration to AWS using portfolio-based waves and strong platform foundations rather than a single big-bang rewrite.
