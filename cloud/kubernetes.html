Cloud Architecture

Kubernetes Architecture

Control plane, worker nodes, pods, services, and networking model explained.

⏱ 10 min read

What it is

Kubernetes architecture on cloud is the split between a provider-managed control plane (API server, scheduler, controllers, etcd) and a customer-operated data plane (nodes, pods, networking plugins). Hyperscaler offerings — Amazon EKS, Azure AKS, Google GKE — run and patch the control plane; you supply compute (managed node groups, spot pools, or serverless backends such as Fargate or GKE Autopilot) and declare workloads through the standard Kubernetes API.

The portable object model — Pods, Deployments, Services, Ingress — is defined by the CNCF-hosted Kubernetes project. Cloud-specific integration happens through cloud controller managers and workload identity (IRSA on AWS, Workload Identity on GKE, managed identity on AKS) so Services can provision load balancers and PersistentVolumeClaims can attach managed disks without bespoke glue code.

Why it exists

Self-managed Kubernetes requires multi-AZ etcd backups, API server HA, certificate rotation, and upgrade sequencing — work that does not differentiate most products.

Managed control planes let platform teams focus on node strategy, tenancy, and add-ons while keeping manifests portable across regions and vendors.

When to use

  • Multiple containerized services that share one cluster and need uniform deploy, scale, and discovery.
  • Internal platform teams vending namespaces or virtual clusters with guardrails (quotas, network policies, admission).
  • Workloads that benefit from Horizontal Pod Autoscaler, rolling updates, and cloud load balancer integration.

When not to use

  • A single stateless API where serverless containers (Cloud Run, Fargate) or PaaS (App Service) suffice.
  • Teams without bandwidth to own CNI upgrades, ingress controllers, and storage classes after the control plane is managed.
  • Latency-sensitive systems where mesh sidecars and extra hops are unacceptable without careful design.

Typical architecture

Pros and cons

Pros

  • Provider-operated control plane with published SLAs and automated patching.
  • Native hooks to cloud IAM, VPC, load balancers, and block storage.
  • Portable workloads: the same API objects run on every major cloud and on-premises distributions.

Cons

  • Nodes, networking plugins, and ingress remain customer operational scope.
  • Cluster sprawl and unfettered namespaces inflate cost without quotas and labeling.
  • Advanced security (mesh mTLS, policy engines) adds latency and expertise requirements.

Implementation notes

Isolate platform add-ons (ingress, DNS, metrics) on dedicated node pools or taints so application bursts cannot evict critical system pods. Enable audit logging on the managed API endpoint and treat cluster-admin as break-glass only, with day-to-day access via namespace-scoped RBAC or cloud IAM federation.

Align cluster version skew with the Kubernetes version skew policy: upgrade control plane first, then node groups. Pin add-on versions (CNI, CSI, ingress) to tested bundles delivered through GitOps rather than ad hoc helm upgrades.

The control plane comprises the API server (authentication, authorization, admission), etcd (cluster desired state), scheduler, and controller managers. On managed offerings the provider operates and patches etcd and API HA; you still need a clear story for backup, disaster recovery, and maximum object cardinality because heavy watches and large ConfigMaps increase read pressure. Follow the published skew policy: control plane on minor version N, worker nodes on N or N−1, kubectl clients within the supported band. Upgrade the control plane first, then node pools in waves with health gates between waves. Prefer managed EKS, AKS, or GKE when integrated IAM, patching, and support matter; self-managed clusters only when regulation or customization demands it—and then you own etcd quorum, defragmentation, and backup drills. Pod scheduling, probes, and disruption budgets are operational concerns covered in deployment container orchestration, not repeated here.

Common failure modes

  • Control plane API saturation: Mass apply or runaway controllers hit request limits — rate-limit CI and operators; watch apiserver_request_total and 429 responses.
  • Spot or node upgrades without PDBs: Concurrent drains drop below minimum replicas — enforce PodDisruptionBudgets and graceful termination hooks.
  • Over-wide network exposure: Public API endpoints or wide security groups — prefer private endpoints, authorized networks, and zero-trust access.

Decision checklist

  • Is the API endpoint reachable only over private networking or approved CIDRs?
  • Are node pools, CNI, and ingress versions tracked and upgraded on a calendar?
  • Do production Deployments use topology spread or anti-affinity across availability zones?
  • Is workload identity configured instead of long-lived cloud keys in Secrets?

Example use cases

  • Illustrative scenario — A platform team runs EKS with a private API endpoint, Karpenter blending spot and on-demand, IRSA per microservice, and GitOps-promoted manifests across dev and prod accounts.
