Cloud Architecture

Multi-Region Architecture

Active-active and active-passive patterns for geographic redundancy and latency.

⏱ 10 min read

What it is

Multi-region architecture is the pattern to use when global SaaS with users on multiple continents and strict uptime SLAs. Deploys application components across two or more geographic regions of a cloud provider so traffic, data, and operations can survive regional outages and reduce latency for global users. Regions are fully isolated failure domains sharing only global control-plane services (Route 53, Global Accelerator, IAM).

Design choices include active-passive (one region serves production traffic while another waits on standby), active-active (multiple regions serve traffic concurrently), and data-local patterns where compute is regional but authoritative data lives in a single primary region with read replicas elsewhere.

Why it exists

Customers expect services to stay available when an entire region fails. A single-region deployment ties reliability to one power grid, fibre bundle, and operations team mistake.

Latency-sensitive global products cannot place all users far from one data centre; multi-region placement moves compute closer to users without building private POP networks.

When to use

  • Global SaaS with users on multiple continents and strict uptime SLAs.
  • Regulatory requirements to process data in specific countries while still offering a unified product.
  • DR targets below what pilot-light DR in a secondary region can achieve — need always-warm capacity.

When not to use

  • Single-country products with modest uptime requirements — multi-region adds cost and consistency complexity without proportional benefit.
  • Applications with a single-primary database that cannot tolerate cross-region write conflicts without a full redesign.

Typical architecture

Pros and cons

Pros

  • Regional isolation limits blast radius of provider incidents.
  • Latency-based routing improves experience for distant users.
  • Warm standby regions shorten failover versus cold backups.

Cons

  • Cross-region data replication cost and consistency trade-offs.
  • Operational complexity: deployments must succeed in every active region.
  • Debugging distributed systems across regions is harder during incidents.

Implementation notes

Pick a traffic steering model early: Route 53 latency routing, geoproximity, or anycast with Global Accelerator. Document failover triggers (health check thresholds, manual runbook).

Standardise infrastructure per region with Terraform/CDK modules; drift between regions causes failover surprises. Run GameDays that fail over production traffic quarterly.

Common failure modes

  • Split-brain after DNS TTL: Stale DNS caches send traffic to a failed region longer than expected — use low TTLs on health-checked records only during incidents.
  • Schema migration skew: Region B deploys before region A; database migration breaks older code — enforce same-version deployments or backward-compatible migrations.

Decision checklist

  • Is RTO/RPO defined per tier of service with a mapped multi-region pattern?
  • Are health checks end-to-end (not just ALB /) from outside each region?
  • Can the database tier fail over without manual steps in under the target RTO?
  • Is cross-region egress cost modeled for steady-state replication?

Example use cases

  • Streaming platform: Primary in us-east-1, active-active API in eu-west-1 and ap-southeast-1; DynamoDB global tables for session state; 30-second DNS failover tested monthly.
