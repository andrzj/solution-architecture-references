Cloud Architecture Governance

Cloud Landing Zones

A pre-configured, governed cloud environment that provides the baseline multi-account structure, networking topology, security controls, and guardrails teams need to build and operate workloads safely at scale.

⏱ 11 min read

What it is

A cloud landing zone is a pre-configured, governed foundation in a public cloud: multi-account (or multi-subscription) structure, shared networking, identity integration, logging, and guardrails that every new workload inherits before application teams deploy. It answers “where does this service live, who can access it, how is it billed, and what security baseline applies?” with defaults instead of one-off reviews.

Major providers ship reference implementations—AWS Control Tower with Organizations and Service Control Policies (SCPs), the Azure Landing Zone pattern on Management Groups and policy assignments, and Google Cloud security foundations blueprints on folders, organization policies, and Shared VPC. The names differ; the model is the same: a management hierarchy with inherited policies, dedicated shared services (logging, audit, connectivity), and an account vending (or subscription vending) path so teams request environments through automation rather than tickets.

A landing zone is platform scope, not application scope. It does not replace secure coding, data classification, or workload-specific threat models; it ensures that every account starts from the same detective and preventive controls the organisation has already agreed to.

Why it exists

Cloud without a landing zone tends toward two extremes: central IT becomes a gate for every VPC and role (slowing delivery), or teams spin up resources ad hoc (inconsistent security, opaque spend, audit gaps). Automating the repeatable baseline—central audit logs, threat detection enrollment, encryption defaults, network attachment patterns—lets product teams move quickly inside guardrails instead of negotiating the same controls for each project.

Separating environments by account (or subscription) is one of the strongest isolation primitives on hyperscaler platforms. A compromised credential in a sandbox should not reach production data in another account; SCPs and network boundaries encode that separation so it survives turnover and organic growth. Landing zones also give FinOps and security a consistent tagging, billing, and evidence model from the first migrated workload.

When to use

  • The organisation is scaling past a single shared cloud account and needs a repeatable multi-account model with inherited policies.
  • Regulated or certified operations require the same preventive and detective controls on every environment (for example PCI-DSS, HIPAA, FedRAMP, or ISO 27001).
  • Several autonomous product teams need their own accounts but must share hub networking, identity, and central logging.
  • A large migration programme needs target accounts ready before application waves land.
  • Per-team cost allocation, budgets, and chargeback depend on account- or subscription-level boundaries.

When not to use

  • Small single-team footprints: Cross-account IAM, log aggregation, and vending machinery may cost more than one well-governed account with strong role design.
  • Broken vending latency: If automated account creation still takes days, fix the pipeline before adding more policy layers.
  • Over-nested policy trees: Deep organizational unit hierarchies and opaque SCP stacks are hard to reason about during incidents; prefer fewer levels with documented intent.
  • As a substitute for application security: Landing zones enforce infrastructure baseline; workloads still own secrets, encryption choices, and least-privilege access to data.

Typical architecture

Most designs place management, audit, networking, and workload OUs (or folder equivalents) under an organization root, with guardrails applied at OU level and spokes attaching to a shared connectivity hub.

Pros and cons

Pros

  • Every new account inherits an agreed security and logging baseline without a bespoke review cycle.
  • Account boundaries limit credential compromise blast radius between production and non-production.
  • Self-service vending scales team autonomy while keeping policy inheritance intact.
  • Centralized audit logs and cost dimensions are available from the first migrated workload.
  • Assessors see consistent control evidence when guardrails are uniform across the estate.

Cons

  • Initial design of hierarchy, policies, vending, and hub networking requires substantial upfront engineering.
  • Cross-account role assumptions and network paths add operational complexity for application teams.
  • Overly tight guardrails block valid services until policy exceptions are understood and documented.
  • Customization of managed landing-zone products adds ongoing maintenance as provider features evolve.
  • Retrofitting a landing zone onto a mature single-account estate is disruptive and needs careful sequencing.

Implementation notes

Start from the provider’s reference landing zone (for example Control Tower, Azure Enterprise-Scale, or Google security foundations), then extend vending with infrastructure-as-code: Git-requested account creation, mandatory tagging, enrollment in central logging, and hub network attachment. Version SCPs (or policy assignments) in the same repository as the vending pipeline so every change is reviewable.

Adopt hub-and-spoke networking early: a connectivity account hosts shared transit, DNS, and egress inspection; workload VPCs attach as spokes with non-overlapping CIDR blocks reserved in IPAM before the first account ships. Federate human access through a single identity plane (SAML/OIDC into short-lived roles per account) instead of long-lived console users scattered across subscriptions.

Document which guardrails are preventive (SCPs, organization policies) versus detective (config rules, security posture management) and who owns exceptions. Sandbox OUs should be explicitly lower risk so experimentation does not land in production-adjacent accounts.

Common failure modes

  • Slow or manual vending: Ticket-driven account creation negates self-service; target end-to-end automation measured in minutes, not days.
  • SCPs that block security tooling: Root-level denies on services required by remediation lambdas or automation break the controls they were meant to protect; test in sandbox OUs first.
  • Overlapping or exhausted IP plans: Ad-hoc CIDR assignment breaks hub routing and peering; reserve ranges before scaling account count.
  • Shadow accounts: Teams create subscriptions outside the vending path, bypassing logging and guardrails; enforce creation only through the factory where policy allows.
  • No purposeful sandbox: Without a designated experiment OU, developers push risky configs into staging that mirrors production blast radius.

Decision checklist

  • Is the hierarchy organized around security and compliance boundaries rather than the org chart alone?
  • Can a new workload account be provisioned end-to-end through self-service with an audit trail?
  • Are audit logging, configuration recording, and threat detection centralized for every new account by default?
  • Are non-overlapping network ranges allocated for current and projected accounts?
  • Are guardrail policies version-controlled, reviewed, and tested before production OUs inherit them?
  • Do engineers access clouds through federated, time-bounded roles instead of static users?

Example use cases

  • Illustrative scenario — A retail enterprise migrates from one shared cloud account to dozens of team accounts over several waves; vending via pull request enrolls each account in central logging and attaches spokes to a shared transit hub so security reviews findings in one audit account.
  • Illustrative scenario — A card-processing workload lands in a dedicated OU where organization policies restrict regions, block direct internet attachment on data subnets, and require customer-managed encryption keys; continuous compliance rules flag drift.
  • Illustrative scenario — A platform team adopts the provider’s control-tower product, then extends vending so every new product line account inherits the same logging and guardrail stack on day one.

Related patterns

  • Shared Responsibility Model — clarifies provider versus customer security obligations that landing-zone guardrails implement on the customer side.
  • Cloud Networking — hub-and-spoke transit, DNS, and private connectivity that the landing zone networking account owns.
  • Cloud Migration Patterns — migration waves assume target accounts and networks already exist inside the landing zone.
  • FinOps — account structure and mandatory tags enable allocation and budgets across teams.
  • Infrastructure as Code — Terraform or Bicep modules typically drive vending and baseline stacks.
