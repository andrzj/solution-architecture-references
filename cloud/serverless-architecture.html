Serverless Architecture

An execution model where cloud providers dynamically manage infrastructure allocation, billing per invocation rather than per idle hour, eliminating server provisioning and management entirely for the application developer.

⏱ 11 min read

What it is

Serverless architecture on cloud is an execution and integration model where the provider runs and scales compute, and teams pay for invocations, duration, and attached managed services rather than reserved instances. The common face is functions-as-a-service (AWS Lambda, Azure Functions, Google Cloud Functions), triggered by HTTP, queues, object events, or schedules.

A full serverless system composes FaaS with consumption-priced data plane services — API gateways, object storage, message queues, NoSQL stores, and serverless relational tiers (Aurora Serverless, Cosmos serverless). Functions stay stateless; durable state lives in managed stores. Scale-to-zero is the default economic property: no traffic means no compute charge for that function.

Why it exists

Provisioned servers bill around the clock while many workloads are intermittent — webhooks, file transforms, nightly reports.

Offloading patching, scaling, and runtime lifecycle to the provider lets small teams ship event-driven features without operating clusters, as long as workload shape fits platform limits.

When to use

  • Event pipelines: uploads, queue messages, streaming records, or webhooks that fan out to short handlers.
  • HTTP APIs with spiky traffic where idle VMs or pods would dominate cost.
  • Scheduled or low-duty automation replacing cron on always-on instances.
  • Integration glue between managed services with idempotent, stateless steps.

When not to use

  • Jobs longer than platform timeouts (for example 15 minutes on Lambda) or needing persistent in-memory state.
  • Sustained high throughput where provisioned containers are cheaper than per-invocation pricing.
  • Sub-100 ms p99 latency without provisioned concurrency, warm pools, or a non-serverless tier.
  • Heavy connection-oriented database access without a pooler (RDS Proxy, Hyperdrive, etc.).

Typical architecture

Pros and cons

Pros

  • Pay only while code runs; native scale-out and scale-to-zero.
  • No OS or runtime fleet to patch; security and capacity are provider-managed.
  • Tight integration with event sources and managed data services.

Cons

  • Cold starts and invocation overhead affect tail latency.
  • Timeouts, memory, and package limits bound feasible workloads.
  • Debugging is request-scoped; tracing and structured logs are mandatory.

Implementation notes

Initialize expensive clients (SDKs, pool handles) outside the handler so warm containers reuse them. Keep deployment packages small; for Java consider SnapStart; for user-facing paths use provisioned concurrency or minimum instances where the platform supports it.

Front relational databases with a pooler (RDS Proxy, etc.). Set function timeout above downstream p95 but below client deadlines. For queue triggers, size visibility timeout to at least six times function timeout. Use dead-letter queues and idempotent handlers for async paths. Align designs with the AWS Well-Architected Serverless Applications Lens pillars (operational excellence, security, reliability, performance, cost).

Common failure modes

  • Connection storms: Concurrent invocations exhaust database max_connections — pool at the proxy layer.
  • Timeout retry loops: Short timeouts plus aggressive retries amplify downstream load — cap retries and use circuit breakers.
  • Duplicate queue processing: Visibility timeout shorter than handler duration — increase timeout or shorten work units.
  • Payload limits: Large bodies inline instead of claim-check via object storage references.

Decision checklist

  • Is traffic intermittent enough that invocation pricing beats always-on compute?
  • Do all handlers finish within platform time and memory limits?
  • Are cold-start p99 and warm latency measured with production-like artifacts?
  • Are async failures routed to DLQs with replay procedures?

Example use cases

  • Illustrative scenario — object pipeline: Object storage event invokes a resize function; output written to a second bucket; downstream queue triggers indexing.
  • Illustrative scenario — webhook intake: API gateway validates signatures, enqueues events, returns 202; workers process at consumer pace.
