Security Architecture

Authentication Fundamentals

Verifying identity at scale — passwords, MFA, SSO, passwordless, and session management.

⏱ 10 min read

What it is

Authentication answers whether a claimed identity is genuine before any authorisation or business logic runs. Humans prove identity with passwords, MFA, passkeys, or federated login; workloads prove identity with client certificates, signed JWTs from a trusted issuer, or cloud workload identity. The outcome is an authenticated session or token that downstream components can bind to audit logs and access policies.

Modern browser apps almost always delegate human login to an OpenID Connect provider using OAuth 2.0's Authorization Code flow with PKCE, exchanging a one-time code for ID and access tokens. The ID token carries identity claims; the access token authorises API calls—authentication and API access stay related but distinct. NIST SP 800-63 defines Authenticator Assurance Levels (AAL) for how strongly an identity was proven; regulated programmes map MFA requirements to AAL2 or AAL3.

Sessions may be server-side (opaque cookie pointing to Redis) or token-based (short-lived JWT in HttpOnly cookie). Machine-to-machine flows use client credentials or mutual TLS. OWASP's Authentication Cheat Sheet summarises baseline controls: rate limiting, secure credential storage, session expiry, and resistance to credential stuffing.

Why it exists

Weak authentication is the gateway to account takeover, fraud, and data exfiltration. Per-app password databases multiply breach impact; users reuse passwords across sites, feeding credential-stuffing bots. Centralising authentication behind an IdP with MFA, device binding, and anomaly detection shrinks the attack surface. Strong authentication also enables trustworthy authorisation—RBAC and ABAC decisions are meaningless if the principal can be impersonated.

Compliance regimes (PCI DSS for admin access, HIPAA for workforce users, Zero Trust maturity models) expect phishing-resistant factors for privileged roles and documented session timeout policies. Authentication telemetry—failed logins, impossible travel, new device enrollment—feeds SOC workflows and NIST 800-207 risk-adaptive access.

When to use

  • Any system distinguishing users, administrators, or service principals.
  • At every trust boundary facing the internet, partners, or devices.
  • When regulations or customer contracts mandate MFA or federated workforce access.
  • East-west service calls requiring cryptographic peer identity (mTLS, SPIFFE JWT-SVID).

When not to use

  • Truly public read-only content may omit login for anonymous visitors—still protect admin and write paths.
  • Authentication does not replace authorisation; never infer permissions from successful login alone.

Pros and cons

Pros

  • Federated OIDC eliminates duplicated password databases and syncs MFA policy.
  • Passkeys and WebAuthn resist phishing better than passwords alone.
  • Central IdP logging supports investigations and compliance evidence.
  • Short-lived access tokens limit replay windows when stolen.

Cons

  • IdP dependency requires HA design and rehearsed break-glass.
  • Token and session debugging complexity for engineers.
  • Legacy clients may lack PKCE or passkey support—need transitional controls.
  • Overly long sessions undermine MFA benefits for sensitive operations.

Implementation notes

Implement Authorization Code + PKCE for public clients; store client secrets only on confidential backends. Hash passwords with Argon2id or bcrypt where local accounts exist; never store plaintext. Enforce MFA for admin and high-value roles; prefer FIDO2/WebAuthn over SMS when possible per NIST 800-63B. Use HttpOnly, Secure, SameSite cookies for session identifiers; avoid storing bearer tokens in localStorage where XSS can exfiltrate them.

Set idle and absolute session timeouts; rotate session IDs after login to prevent fixation. Validate OIDC tokens on every API request at the gateway: signature, issuer, audience, expiry. Instrument authentication metrics—failure rate, MFA challenges, geo anomalies—and alert on spikes. Require step-up authentication for sensitive actions (wire transfers, credential changes) even within an active session.

Common failure modes

  • Credential stuffing: No rate limits or breached-password checks—pair with MFA and IP throttling.
  • Session fixation: Failing to mint a new session ID post-login.
  • JWT in localStorage: XSS steals tokens—use HttpOnly cookies or memory-plus-refresh patterns.
  • SMS-only MFA/recovery: SIM-swap risk—offer stronger factors.
  • Implicit or resource-owner flows: Deprecated patterns exposing tokens to user agents.

Decision checklist

  • Do browser apps use Authorization Code + PKCE against a trusted OIDC provider?
  • Is MFA enforced for privileged and high-risk accounts?
  • Do sessions define idle and absolute TTL with rotation on privilege change?
  • Are authentication events logged with correlation IDs to SIEM?
  • Is break-glass access documented, monitored, and rare?
  • Are passwords hashed with modern algorithms where local auth exists?

Example use cases

  • Illustrative scenario — Meridian Commerce workforce: Okta OIDC for internal apps; FIDO2 required for production deploy approvals; sessions expire after 12 hours absolute TTL.
  • Consumer mobile: Passkey-first registration with email magic link as recovery only on new devices.
  • Service mesh: SPIFFE-issued JWT SVIDs authenticate gRPC between microservices without shared API keys.
