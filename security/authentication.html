Security Architecture

Authentication Fundamentals

Verifying identity at scale — passwords, MFA, SSO, passwordless, and session management.

⏱ 10 min read

What it is

Example: an employee signs into a SaaS app via corporate OIDC, completes password plus WebAuthn, receives an ID token, and the app binds a short-lived server-side session to that identity.

Why it exists

Authorization depends on trustworthy identity. Weak authentication drives account takeover and compliance failures. Centralized auth with MFA, lockout policies, and credential monitoring reduces risk versus per-app password silos.

When to use

  • Any application that distinguishes users or workloads.
  • At every trust boundary (internet, partner, device).
  • When regulations require MFA or federated workforce access.
  • For machines via mTLS, signed JWTs, or workload identity.

When not to use

  • Anonymous public content with no abuse surface — still protect admin paths.
  • As a substitute for authorization decisions.

Typical architecture

Federated login with MFA and server-side session validation.

Pros and cons

Pros

  • Federation removes duplicate password databases.
  • MFA and WebAuthn defeat most credential stuffing.
  • Central IdP yields unified sign-in audit trails.
  • Short-lived tokens limit replay windows.

Cons

  • IdP outage blocks dependent apps without break-glass.
  • Token/session debugging is harder for engineers.
  • Legacy clients may lack PKCE or passkey support.
  • Long sessions can negate MFA benefits.

Implementation notes

Use OIDC Authorization Code + PKCE; avoid implicit flow. Store sessions server-side or use rotating encrypted cookies marked HttpOnly, Secure, SameSite.

Hash passwords with Argon2id/bcrypt; enforce MFA for admins; instrument login metrics and anomaly alerts.

Common failure modes

  • Credential stuffing: breached password lists; use MFA, rate limits, and breached-password APIs.
  • Session fixation: rotate session identifiers at login.
  • JWT in localStorage: XSS theft; prefer HttpOnly cookies or memory + refresh rotation.
  • SMS-only recovery: SIM-swap risk; prefer safer factors.

Decision checklist

  • Browser apps use Authorization Code + PKCE?
  • MFA enforced for privileged roles?
  • Sessions have idle and absolute TTL with rotation?
  • Auth events logged with correlation IDs?
  • Break-glass accounts documented and rare?
  • Passwords hashed with modern algorithms?

Example use cases

  • Enterprise SSO: Okta OIDC across internal apps with FIDO2 for admins.
  • Consumer mobile: Passkey-first with email fallback for account recovery.
  • Service mesh: SPIFFE JWT SVIDs for east-west calls.
