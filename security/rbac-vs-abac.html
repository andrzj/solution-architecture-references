RBAC vs ABAC

Role-Based vs Attribute-Based Access Control — structured comparison of models and use cases.

⏱ 11 min read

What it is

Role-Based Access Control (RBAC) grants permissions by assigning users to roles, and roles to permissions. Authorisation reduces to “does this user hold a role that includes this permission on this resource type?” NIST SP 800-162 defines standard RBAC models (flat, hierarchical, constrained) used in IAM products and enterprise directories.

Attribute-Based Access Control (ABAC) grants access when a policy expression evaluates attributes of the subject (user, service account), resource (labels, owner, classification), action (read, export), and environment (time, IP, device posture). Decisions are dynamic: the same user may read a record at 10:00 but not export it at 22:00 from an unmanaged device.

Most production systems use a hybrid: RBAC for coarse admin versus member gates, ABAC for data-plane rules tied to sensitivity tags or tenant context.

Why it exists

Flat access control lists do not scale with headcount — every hire requires touching thousands of resources. RBAC compresses grants into roles auditors understand (“only billing_admin may refund”). As regulations and data classification mature, static roles cannot express “same role, different row-level outcome based on label and geography,” which pushes teams toward ABAC or policy engines (OPA, Cedar, cloud IAM condition keys).

Choosing the model deliberately avoids accidental complexity: engineers copying one-off exceptions into role matrices until nobody knows effective permissions.

When to use

  • RBAC when org structure is stable, permissions align to job functions, and auditors expect role certification campaigns.
  • ABAC when decisions need resource labels, time windows, location, device trust, or data sensitivity (healthcare, finance, government).
  • Hybrid when SaaS products expose tenant admin/user roles but must enforce row-level rules on exports, PHI fields, or cross-border reads.
  • ReBAC complements (relationship-based access) for graph-shaped permissions — see Authorization Models when ownership graphs dominate.

When not to use

  • ABAC-only for a tiny team with two roles — policy engines and attribute pipelines cost more than a simple RBAC matrix.
  • RBAC-only when regulators require purpose-of-use, break-glass, or label-based rules that change per record.
  • UI hiding as authorisation — either model still requires server-side enforcement on every API.

Typical architecture

Place a single policy decision point behind the API layer: the request carries authenticated identity; the PEP loads resource metadata and subject attributes, then asks the PDP for allow/deny. Log the decision inputs for auditors.

Pros and cons

Pros

  • RBAC is easy to explain in access reviews and SOC evidence.
  • ABAC expresses fine-grained, context-aware rules without role explosion.
  • Hybrid keeps admin consoles simple while protecting sensitive data paths.
  • Both models map to policy-as-code with versioned tests in CI.

Cons

  • RBAC suffers role explosion and privilege creep without governance.
  • ABAC is harder to reason about without simulators and negative tests.
  • Hybrid without documented boundaries confuses which layer owns a rule.
  • Attribute pipelines (HR, device, labels) become single points of failure.

Implementation notes

Start with a minimal RBAC matrix documented in a permission catalog. Introduce ABAC only where product or compliance repeatedly demands exceptions (“same role, different outcome”). Encode ABAC in OPA/Rego, AWS IAM condition keys, Azure ABAC on storage, or Google IAM Conditions — pick one PDP per surface to avoid divergent logic.

Treat HR and IdP groups as sources of truth for subject attributes; refresh on schedule and on session start for high-risk actions. Define explicit deny semantics when policies conflict. Emergency access (break-glass) should be time-boxed, reason-coded, and monitored.

For multi-tenant SaaS, bind every decision to tenant_id on both subject and resource — RBAC roles must be tenant-scoped, not global superuser unless strictly controlled.

Common failure modes

  • Shadow admin: composite roles or nested groups recreate superuser without review.
  • Attribute drift: stale department or clearance attributes grant outdated access.
  • UI-only authorisation: buttons hidden but APIs return 200 for any authenticated caller.
  • Ambiguous deny defaults: PDP returns allow when policies conflict or attributes are missing.
  • Untested policy edits: Rego/IAM changes deploy without regression tests or shadow mode.

Decision checklist

  • Is there a documented permission catalog with least-privilege roles?
  • Are ABAC policies owned, versioned, and tested in CI?
  • Are subject attributes sourced from authoritative systems (IdP/HR)?
  • Can auditors reproduce a decision from logged inputs and policy version?
  • Is there a process to retire roles and remove stale grants?
  • Are break-glass grants time-boxed and alerted?

Example use cases

  • Illustrative scenario — enterprise SaaS: Tenant RBAC separates admin and member; ABAC blocks bulk export unless user.mfa_recent and resource.tenant matches.
  • Illustrative scenario — hospital EHR: Clinicians hold RBAC roles; ABAC enforces break-the-glass with mandatory reason codes on sensitive charts.
  • Illustrative scenario — data lake: Object tags (classification=confidential) drive ABAC on query engines; IAM roles alone cannot see tagged prefixes.
  • Case study — AWS: IAM roles (RBAC-shaped) combine with resource tags and condition keys (ABAC-shaped) for least-privilege at scale.
