Security Architecture

Supply Chain Security

Securing the software supply chain: SBOM generation, SLSA build provenance, dependency vulnerability scanning, artifact signing with Sigstore/Cosign, and container image integrity.

⏱ 10 min read

What it is

Software supply chain security protects every hop from commit to running artifact: source integrity, dependency hygiene, build pipeline trust, registry policy, and deploy-time verification. A Software Bill of Materials (SBOM) in CycloneDX or SPDX format inventories components for rapid CVE impact analysis. SLSA levels describe build isolation and provenance maturity; Sigstore Cosign signs images with OIDC-bound identities verified at Kubernetes admission.

Software composition analysis (SCA) matches lockfiles and container layers against NVD, OSV, and vendor feeds. Container scanners (Trivy, Grype, Snyk Container) catch OS package CVEs that library-only tools miss. Provenance attestations plus signature verification close the gap between trusting a mutable tag and knowing which commit produced a digest.

NIST SP 800-218 and CISA’s SBOM guidance expect organisations to maintain dependency inventory and respond to newly disclosed CVEs with measurable timelines. SLSA Build levels document how isolated, authenticated pipelines produce non-forgeable provenance—admission controllers can reject artifacts that lack expected attestations.

Why it exists

Applications are mostly third-party code—Log4Shell showed teams unaware of transitive Log4j usage until exploitation began. Pipeline compromise (SolarWinds-style) proves signed binaries can still be malicious if build systems are hijacked. Executive Order 14028 and customer procurement clauses increasingly mandate SBOMs, vulnerability response SLAs, and provenance. Without inventory and signed builds, incident response and customer notifications stall on manual archaeology.

Modern services can be 80–95% dependencies by line count. An SBOM lets you query exposure in minutes when the next Log4j-scale CVE lands. SLSA provenance makes it cryptographically verifiable that an artifact came from an expected pipeline running expected source—detecting build-pipeline tampering before deploy.

OWASP dependency-risk guidance and CIS Control 2 emphasise inventory of software assets—SBOMs are the machine-readable fulfilment of that control for each release artifact.

When to use

  • Any shipped software with dependencies—SBOM and SCA are baseline, not optional.
  • Customer-facing or government distribution where attestations are contractual.
  • Container platforms where image contents differ from declared application lockfiles.
  • Products requiring tamper-evident releases (firmware, agents, on-prem installers).

When not to use

  • SLSA level 3–4 hermetic builds cost more—prioritise for widely consumed artifacts; still generate SBOM at level 1 for internal tools.
  • Do not defer SCA because “we have few dependencies”—transitive graphs explode quickly.
  • Do not treat SBOM export alone as compliance—without gates and verification, inventory does not stop bad deploys.

Typical architecture

SBOM generation, vulnerability gates, and signature verification run in CI before images reach cluster admission.

Pros and cons

Pros

  • SBOM queries answer “are we affected?” within minutes of new CVEs.
  • Signed provenance detects unexpected build origins before deploy.
  • Policy gates block critical CVEs and unsigned images automatically.
  • VEX documents mitigations for non-exploitable findings, reducing noise.
  • CISA and EO 14028 procurement language increasingly expects SPDX or CycloneDX with each deliverable.

Cons

  • SBOM maintenance must track every rebuild and fork—stale BOMs mislead.
  • False positives from SCA without VEX exhaust developer time.
  • Hermetic builders require pipeline redesign and cached artifact strategy.
  • Admission policies can halt deploys when signing infrastructure fails.
  • Keyless Sigstore transparency logs may be unsuitable for some proprietary release models.
  • Dual signing models (keyless plus long-lived keys) add operational complexity during rotation events.

Implementation notes

Generate SBOMs in CI from lockfiles (Syft, CycloneDX plugins) and attach them to releases. Fail builds on critical CVEs with SLA exceptions tracked in GRC. Sign container images with Cosign keyless via GitHub/GitLab OIDC; verify in Kyverno or OPA Gatekeeper policies. Record SLSA provenance with build attestations stored alongside artifacts.

Protect default branches: require code review, block force-push, and enable secret scanning on push. Run SCA on every PR and again at image build—transitive updates can land between merge and release. Store SBOMs immutably with the artifact digest so forensic rollback matches the BOM customers received.

Pin dependency versions in committed lockfiles; pin container bases by digest, not mutable tags, and let Renovate or Dependabot open update PRs. Maintain a central registry allowlist and mirror approved base images internally. Admission policies should deny unsigned images, images from unknown registries, and digests failing CVE severity thresholds unless a signed VEX documents accepted risk.

Practice Log4Shell-style drills: query SBOM, open incidents, and measure time-to-scope. Use EPSS and VEX to triage noise from truly exploitable findings. For SLSA level 2+, run builds on hosted CI with signed provenance; level 3 adds isolated builders and verified source revision tied to the attestation.

Publish SPDX or CycloneDX SBOMs per release and attach VEX documents when you have compensating controls for noisy CVEs. Sign images with Sigstore cosign and verify in admission; in-toto attestations chain build steps to source commits. Block dependency confusion by pinning private registries and scopes; scan package names for typosquats on install. Dependency review in CI should fail merges that introduce critical SCA findings without owner exception.

Store provenance attestations beside release tags so on-call can answer “what commit built this image?” without digging through build logs.

Mirror critical upstream registries internally so builds survive public npm or Docker Hub outages.

Common failure modes

  • SBOM generated once: Stale CycloneDX files mislead incident response when dependencies changed three releases ago.
  • Scan libraries only: A vulnerable openssl in the base image survives while npm dependencies look clean.
  • Sign but never verify: Emergency deploys bypass admission policies; tampered images schedule when someone disables the webhook.
  • Pin tags not digests: Registry tag reuse swaps digest under the same label—Kubernetes pulls unexpected bytecode.
  • No VEX process: Developers mute SCA forever; the next critical CVE hides in suppressed noise.
  • No post-build monitoring: NVD publishes a flaw Tuesday; production still runs Friday's image with no registry rescan alert.
  • Typosquat dependency: A rushed npm install pulls a similarly named package with no review gate on publish.

Decision checklist

  • Does every release artifact ship with an SBOM in a standard format?
  • Do CI gates block critical CVEs without approved exceptions?
  • Are images signed and verified at admission with digest pinning?
  • Is build provenance stored and queryable for forensic rollback?
  • Can you answer customer impact within one hour of a major CVE publication?
  • Is there a documented process for VEX and emergency dependency patches?
  • Are default branches protected with required reviews and no direct pushes?
  • Does registry continuous scanning re-evaluate deployed digests when CVEs publish?

Example use cases

  • Case study — Log4Shell-style response: CycloneDX SBOM query lists affected services; VEX marks non-reachable transitive paths.
  • Illustrative scenario — procurement: Enterprise customers receive SBOM plus SLSA attestations with each quarterly release.
  • Illustrative scenario — Sigstore admission: Kyverno verifies Cosign signatures from CI OIDC; tampered images never schedule.
  • Private registry mirror: Approved base images replicate internally; admission denies pulls from public Docker Hub except the mirror digest.
