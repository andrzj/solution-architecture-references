Security Architecture

Identity and Access Management

IAM architecture: federated identity providers, SAML 2.0, OIDC, SSO, JIT provisioning, SCIM, privileged access management, and service account design.

⏱ 11 min read

What it is

Identity and Access Management (IAM) is the discipline and tooling that governs who and what can access which resources, under which conditions, for how long, and with what audit trail. It unifies authentication (proving identity), authorisation (enforcing permissions), and identity lifecycle (joiner, mover, leaver, and non-human credentials). An Identity Provider (IdP) is the system of record for workforce identities: credentials, MFA policies, groups, and issued tokens that relying applications trust.

Enterprise federation uses SAML 2.0 for browser SSO into many SaaS apps, and OpenID Connect (OIDC) on top of OAuth 2.0 for modern web, mobile, and API access—JSON tokens, JWKS-backed signatures, and standard scopes. SCIM automates provisioning: when HR marks an employee inactive, the IdP propagates deactivation to connected apps within minutes. Privileged Access Management (PAM) layers just-in-time, recorded access for break-glass and production systems. Cloud IAM (AWS IAM, Azure RBAC, GCP IAM) extends the same concepts to infrastructure APIs and workload identities.

IAM is the foundation for NIST 800-207 Zero Trust: policy engines consume identity attributes, group membership, and risk signals to make per-session decisions. Without a authoritative directory and consistent token validation, Zero Trust devolves into network ACL theatre.

Leading enterprise platforms include Okta, Microsoft Entra ID, Google Workspace, and Ping Identity; cloud-native teams pair them with secrets managers and SPIFFE-style workload identity for non-human principals. Governance artefacts—access reviews, segregation-of-duties matrices, and entitlement certification—are as much part of IAM as login screens.

Why it exists

Decentralised passwords per application create credential sprawl, inconsistent MFA, and slow offboarding—a terminated user may retain access in a shadow IT tool for weeks. Breach data repeatedly implicates compromised credentials and excessive privileges. Central IAM shrinks the authentication attack surface to hardened IdP endpoints, enables organisation-wide MFA and conditional access, and produces a single audit stream for access reviews required by SOX, HIPAA, and PCI DSS.

Federation also improves experience: one phishing-resistant login reaches multiple apps via OIDC or SAML, while backend services validate short-lived access tokens rather than storing user passwords. For machines, IAM defines service principals, roles, and federation to Kubernetes service accounts—replacing shared passwords in configuration files.

IAM programmes also reduce help-desk load: password resets concentrate at the IdP, and self-service MFA enrollment flows replace ticket-driven lockouts. When integrated with HR status, access becomes an employment attribute rather than a manual IT task—critical for fast-growing organisations where hiring velocity outpaces manual account creation.

When to use

  • Organisations with more than one application or cloud account needing consistent access policy.
  • Hybrid workforce spanning SaaS, on-premises, and contractor identities.
  • Regulated environments requiring documented access reviews and segregation of duties.
  • Production data paths where privileged access must be just-in-time and recorded.
  • Customer-facing products integrating enterprise SSO (SAML/OIDC) for B2B tenants.
  • Zero Trust programmes that need a single attribute source for policy decision points.
  • Organizations recovering from credential incidents that require centralised MFA and session control.

When not to use

  • Early-stage single-app startups may defer enterprise IdP until a second app appears—still use MFA and secure password storage per OWASP guidance.
  • Customer Identity (CIAM) at millions-of-users scale uses different products (Auth0, Cognito, Firebase) and patterns—do not force workforce SAML onto consumer login without considering social IdPs and self-service recovery.

Typical architecture

Federated IAM flows HR-driven provisioning into an IdP, then distributes SAML, OIDC, and cloud IAM bindings—with MFA and group policy at the centre.

Pros and cons

Successful IAM programmes treat identity as a product: product owners for the IdP, published SLAs for provisioning latency, and developer experience metrics for OIDC integration time. That framing keeps IAM from becoming a purely compliance exercise detached from delivery velocity.

Pros

  • Single pane for access certification and MFA enforcement.
  • SCIM deprovisioning reduces insider and orphaned-account risk.
  • SSO improves UX while concentrating hardening on IdP endpoints.
  • Federation enables B2B "bring your own IdP" without storing customer passwords.
  • PAM reduces standing privilege and records sensitive sessions.

Cons

  • IdP becomes critical dependency—requires HA, monitoring, and break-glass.
  • SAML/OIDC misconfiguration causes subtle authorisation bugs.
  • Legacy apps without SCIM need manual or custom provisioning glue.
  • Enterprise IdP licensing and integration labour are non-trivial costs.

Implementation notes

For OIDC relying parties, always validate ID and access tokens server-side: signature via JWKS, correct iss and aud, clock-skew-tolerant exp/nbf, and optional nonce for implicit-hybrid avoidance. Use Authorization Code + PKCE for browser and mobile public clients per OAuth 2.1 direction; avoid implicit flow. APIs should accept short-lived bearer tokens at the gateway, validating JWTs centrally rather than trusting opaque session cookies from unrelated apps.

Model authorisation with business roles mapped to permissions at runtime; avoid attaching users directly to hundreds of permission flags. Run quarterly access reviews exporting IdP group membership. Automate joiner/mover/leaver from HR via SCIM or event-driven workflows. For infrastructure, prefer workload identity (IAM roles, workload identity federation) over long-lived access keys. Align conditional access with NIST 800-207 signals—device compliance, location, and risk score—from the IdP into PEP decisions.

Document SAML attribute mappings and OIDC claim mappings in version control—silent failures occur when groups claims stop flowing after an IdP upgrade. For B2B federation, issue separate OIDC clients per customer tenant with distinct redirect URI allow-lists to prevent cross-tenant authorization code interception. Apply OWASP ASVS controls for session management on applications that still maintain local sessions after OIDC login: idle timeout, absolute timeout, and re-authentication for sensitive transactions.

Separate workforce IAM from customer CIAM directories—even when the same vendor product hosts both—so a marketing-site breach does not expose employee group mappings. Monitor IdP sign-in logs for impossible travel and impossible token use (refresh from two continents). Test deprovisioning monthly with a synthetic user account to prove SCIM paths still reach every integrated SaaS tool acquired through shadow IT discovery.

Machine identities deserve the same lifecycle discipline as humans: rotate Kubernetes service account tokens, disallow long-lived cloud access keys in CI, and catalogue every non-interactive principal in the same CMDB item as the service it represents. Delegation chains—users obtaining tokens on behalf of services—should be short, logged, and scoped to the minimum API surface required for the calling workflow.

Common failure modes

  • No break-glass: IdP outage locks out all admins—maintain offline break-glass with MFA and quarterly drills.
  • SAML signature issues: Incomplete assertion validation enables XML signature wrapping—follow hardening guides and test with known payloads.
  • Group sprawl: Everyone in all-staff-admin—certifications never trim privilege.
  • Shared service passwords: Rotation is impossible; migrate to OIDC client credentials or cloud IAM roles.
  • HR sync failures: Terminated users active in SaaS—alert on SCIM error queues.
  • Token audience mismatch: APIs accept tokens minted for a different client ID—strict aud validation missing on resource servers.
  • Over-scoped OAuth consent: Third-party integrations request offline_access and broad scopes users approve once—periodic consent review absent.

Decision checklist

  • Is there a central IdP with MFA enforced for all workforce users?
  • Do applications federate via SAML or OIDC instead of local password databases?
  • Is SCIM (or equivalent) provisioning tied to HR status changes?
  • Are production privileges accessed via PAM with JIT and session recording?
  • Are OIDC/OAuth tokens validated completely on every relying party?
  • Is break-glass documented, monitored, and rare?
  • Are group-to-role mappings reviewed at least quarterly with manager attestation?
  • Do conditional access policies enforce device posture for sensitive apps?

Example use cases

  • Illustrative scenario — Northwind Logistics SSO: Okta fronts GitHub, AWS console, and internal tools; hardware MFA required for cloud admin roles; SCIM removes SaaS access within an hour of HR termination.
  • B2B SaaS tenant federation: Each enterprise customer configures SAML with their IdP; JIT provisioning creates tenant-scoped users from assertion attributes—no password ever stored by the vendor.
  • Database PAM: Engineers request four-hour PostgreSQL credentials via a vault; SQL is recorded for SOC 2 evidence.
  • M&A integration: Acquired company users federate through a transitional IdP trust; no password synchronisation—SAML links expire when migration completes.
  • Kubernetes workforce access: OIDC authentication to the cluster API with group claims mapped to RBAC ClusterRoleBindings; break-glass kubeconfig stored offline for control-plane outages.
