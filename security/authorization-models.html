Security Architecture

Authorization Models

RBAC, ABAC, ReBAC, and policy-based authorization — choosing the right access control model.

⏱ 10 min read

What it is

Authorisation decides what an already-authenticated principal may do with which resources. Models differ in how they express and evaluate permission: RBAC binds permissions to roles assigned to users; ABAC evaluates attributes of subject, resource, action, and environment (time, IP, data classification); ReBAC (relationship-based access control) models tuples like user U is editor of document D popularised by Google Zanzibar. Policy-based access control centralises rules in a Policy Decision Point (PDP) queried by enforcement points at APIs, data layers, and service meshes—aligning with NIST ABAC guidance and Zero Trust continuous authorisation.

OAuth 2.0 scopes express coarse API authorisation at token issuance; fine-grained enforcement still happens in services. OWASP API Security highlights Broken Object Level Authorisation—roles that allow read:orders without checking the order belongs to the caller—which RBAC alone rarely prevents without object-level checks.

Why it exists

Authentication proves identity; authorisation limits damage when identity is valid but over-scoped. Breach investigations routinely find admin-equivalent roles on production, shared staging credentials, and APIs that trust client-side role claims. Explicit models make least privilege enforceable, testable in CI, and explainable to auditors. Central PDPs (OPA, Cedar, cloud IAM policy engines) prevent each microservice inventing incompatible rules.

Regulated data often requires attribute policies—only clinicians on active shift assigned to a patient ward may open records. SaaS multi-tenancy needs organisation-scoped roles and ReBAC-style sharing graphs. As systems scale, flat ACL lists collapse; policy-as-code with version control becomes necessary.

When to use

  • Products with multiple personas (admin, operator, customer, partner) and differing data scope.
  • Regulated or high-sensitivity data needing purpose, location, or time-bound access.
  • Microservice estates requiring consistent enforcement at each service boundary.
  • Public or partner APIs where OAuth scopes must map to server-side object checks.

When not to use

  • Single-role internal tools with one operator group—simple RBAC suffices without a graph database.
  • Mixing ad-hoc checks in each service without a policy source of truth—creates drift and OWASP BOLA exposure.

Typical architecture

Services consult a PEP that calls a PDP evaluating roles, attributes, or relationship tuples—default deny unless policy explicitly allows.

Pros and cons

Pros

  • RBAC is easy to communicate to product and compliance stakeholders.
  • ABAC captures contextual least privilege (device posture, data tags).
  • Central PDP ensures consistent decisions across polyglot services.
  • Policy-as-code enables review, testing, and rollback like application code.

Cons

  • ABAC/ReBAC policies grow complex without simulation and debugging tools.
  • PDP latency requires caching with careful invalidation on role changes.
  • RBAC role explosion in large organisations—needs periodic role mining.
  • ReBAC stores need operational maturity (replication, consistency).

Implementation notes

Enforce authorisation in the domain service that owns the data—not only at the API gateway—so internal callers cannot bypass checks. Represent permissions as triples: principal, action, resource (including tenant and object ID). Default deny; explicit allow. For REST, implement object-level checks on every route that accepts an identifier—map to OWASP API Top 10 BOLA test cases in CI.

Store Rego or Cedar policies in Git; run table-driven unit tests on policy packages in CI. Log allow/deny with principal, resource, policy version, and correlation ID—denials feed detection rules. When using OAuth, treat scopes as upper bounds; services still verify the token's subject may access the requested object. Align PDP placement with NIST 800-207: PEPs on the data path, PDPs fed by identity attributes from OIDC claims and resource metadata.

Choose RBAC for stable job functions, ABAC when decisions need attributes (clearance, geo, time), and ReBAC for shareable graphs—Google Zanzibar-style tuples in OpenFGA or SpiceDB model “user U is editor on folder F.” Deploy OPA or Cedar either as a centralized PDP with sidecar PEPs or embedded library calls; centralized suits uniform policy, embedded suits lowest latency inside one service. The RBAC versus ABAC trade-off table lives in RBAC vs ABAC; here focus on where each decision runs and how to stop BOLA by always matching subject to resource ID in the owning service.

Add integration tests that call APIs as user A with user B’s object IDs and expect consistent 403 responses across list, get, and patch routes.

Common failure modes

  • Coarse roles: admin in production for convenience—violates least privilege.
  • Missing object scope: Role permits action without verifying resource ownership—classic BOLA/IDOR.
  • Stale decision cache: Revoked role still allowed until TTL expires—bind cache to token/session lifetime.
  • Dual models: RBAC in app, ABAC at gateway—conflicting outcomes under load.
  • Client-trusted claims: Accepting role flags from JWT without server-side lookup.

Decision checklist

  • Is there a single policy source of truth under version control?
  • Are decisions default-deny with explicit allow rules?
  • Does every mutating and read-by-ID API perform object-level checks?
  • Are policies unit-tested in CI before deploy?
  • Are denials logged and monitored for abuse patterns?
  • Is emergency break-glass access separate, time-limited, and audited?

Example use cases

  • Illustrative scenario — healthcare ward access: ABAC permits nurses to read vitals only for patients assigned to their ward during active shift hours.
  • Illustrative scenario — B2B SaaS: Organisation-scoped RBAC with custom roles per tenant; OAuth access tokens carry org_id enforced on every query.
  • Collaboration product: ReBAC tuples express editor/viewer links on documents; sharing revokes propagate through the graph store.
