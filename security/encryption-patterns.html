Security Architecture

Encryption Patterns

Encryption in distributed systems: AES-256-GCM, envelope encryption, KMS key hierarchy, TLS 1.3, mutual TLS, field-level encryption, key rotation, HSMs, and BYOK.

⏱ 11 min read

What it is

Encryption patterns are repeatable ways to apply cryptography in distributed systems, including at two layers: encryption in transit (protecting data moving between systems over networks using TLS) and encryption at rest (protecting stored data using symmetric encryption of storage volumes, databases, or individual fields). The dominant algorithm for symmetric encryption at rest is AES-256-GCM (Advanced Encryption Standard, 256-bit key, Galois/Counter Mode) — AES provides confidentiality, GCM provides authenticated encryption with associated data (AEAD), ensuring both confidentiality and integrity in a single operation.

For asymmetric operations (key exchange, digital signatures), RSA-4096 and ECDSA/P-256 are standard.

Envelope encryption is the pattern used by all cloud KMS providers: data is encrypted with a Data Encryption Key (DEK) generated per-object or per-record; the DEK itself is then encrypted by a Key Encryption Key (KEK) managed in a KMS (AWS KMS, Azure Key Vault, GCP Cloud KMS). The encrypted DEK is stored alongside the ciphertext. This pattern solves the key management scaling problem: you never need to call the KMS for each data operation (the DEK is cached); you only call the KMS to unwrap the DEK, which limits KMS API calls and cost, while ensuring that rotating or revoking the KEK immediately invalidates all data encrypted under it. Bring Your Own Key (BYOK) is an enterprise pattern where the customer owns and controls the root KEK in a customer-managed KMS or HSM, providing cryptographic isolation from the cloud provider.

Why it exists

Regulators and enterprise customers expect ciphertext at rest and TLS on the wire—NIST SP 800-52 and SP 800-57 articulate minimum postures auditors reference. Physical theft, mis-published buckets, and passive network capture remain common; crypto without key separation is theater. Mature patterns—envelope encryption, mTLS, BYOK—bind confidentiality to KMS policy rather than application discipline alone.

Architects choose patterns based on performance, compliance scope, and operational maturity: platform-default encryption covers broad baselines; field-level envelopes address crown jewels; mutual TLS addresses service identity in Zero Trust estates. Each pattern adds operational surface—rotation runbooks, cert automation, decrypt monitoring—that must be funded alongside the initial implementation.

Disaster-recovery drills should explicitly test whether standby regions can unwrap DEKs with the same CMK policies as primary—failover surprises often stem from IAM or key policy differences rather than missing ciphertext copies.

When to use

  • All sensitive data paths: TLS 1.2+ externally; mutual TLS where Zero Trust demands workload identity.
  • Managed data services with default encryption plus CMKs for regulated tiers.
  • High-value columns (PAN, SSN, PHI) isolated with field-level envelopes and decrypt audit.
  • BYOK or external key custody when contracts require cloud-provider crypto isolation.
  • Backup and disaster-recovery copies that must remain encrypted during transit to secondary regions.
  • Software supply-chain signing where code and artifact integrity depend on HSM-backed private keys.

When not to use

  • Public static assets—skip at-rest encryption that adds cost without threat reduction.
  • Custom primitives—use vetted libraries and platform TLS per OWASP cryptographic storage guidance.

Typical architecture

Write paths generate per-record DEKs, wrap them with KMS, and persist ciphertext bundles; read paths unwrap under IAM audit—diagram unchanged, pattern per NIST envelope recommendations.

Pros and cons

Pros

  • Envelope patterns amortise KMS calls while keeping CMKs in HSM boundaries.
  • Rotation and versioned CMKs limit impact of future key compromise.
  • mTLS proves both ends of a connection—foundational to Zero Trust meshes.
  • Field encryption narrows insider and DBA overexposure on crown-jewel columns.

Cons

  • KMS latency and quotas require caching discipline on hot paths.
  • Botched rotation can orphan ciphertext without tested recovery.
  • BYOK shifts HSM availability burden to the customer.
  • Encrypted columns need companion indexes or tokenisation for lookup.
  • Mesh cert automation is mandatory—expiry outages are opaque and sudden.
  • Operational runbooks must span cloud KMS, on-prem HSM, and application caches—complexity grows with each added pattern.
  • Debugging TLS or mTLS failures often requires packet captures that privacy policies must allow during incidents only.

Implementation notes

Disable weak TLS ciphers; prefer TLS 1.3 where clients allow. Enforce HSTS on browser properties per OWASP TLS cheat sheet. Require verified TLS to databases and object stores; deny unencrypted S3 uploads via policy. For AES-GCM, generate unique 96-bit nonces per operation from a CSPRNG—never reuse with the same key.

Automate internal cert renewal (cert-manager, SPIRE). Document lazy re-wrap procedures when CMKs rotate. Map controls to NIST SP 800-57 key states and SP 800-52 transport requirements in architecture decision records.

When caching plaintext data keys in memory, bound TTL to transaction scope and zero buffers after use. For object storage, prefer SSE-KMS with bucket policies that deny unencrypted uploads and require correct key ARNs. Evaluate hardware security modules or Cloud HSM only when contracts or regulators demand dedicated modules; otherwise managed KMS with tight IAM often suffices. Test decrypt failover across regions before declaring disaster-recovery readiness.

Document cipher choices in threat models: AES-256-GCM for bulk data, RSA-OAEP or ECDH for key transport, and approved curves for signatures. Avoid deprecated algorithms (3DES, RC4, SHA-1 for signatures) in new designs. Reference OWASP cryptographic storage cheat sheet checkpoints during security design reviews.

When bridging on-prem and cloud, agree which party holds CMKs, how dual-control break-glass works, and how revocation propagates to cached DEKs in application clusters. Performance-test encrypt-decrypt paths under peak load before cutover; latency surprises often appear only when KMS throttling or cross-region calls enter the path.

Common failure modes

  • Plaintext DEKs in rows without proper KMS wrap.
  • Clients that skip TLS verification—MITM negates transport crypto.
  • GCM nonce reuse from counters or duplicated IVs.
  • Password-based keys without Argon2/bcrypt/PBKDF2 stretching.
  • Expired mesh certificates from missing automation.

Decision checklist

  • Is TLS 1.2+ with forward secrecy mandatory on sensitive paths?
  • Are CMKs used for regulated at-rest data with rotation enabled?
  • Does application data use envelope encryption—not per-row KMS encrypt?
  • Are crown-jewel fields encrypted independently of volume encryption?
  • Are mesh or internal certs renewed automatically with alerting?
  • Are IV/nonce generation practices reviewed in crypto design reviews?
  • Are DR regions verified to decrypt using the same CMK policies as primary?
  • Do architecture records list approved algorithms and retired legacy ciphers?

Example use cases

  • Clinical SaaS: Diagnosis notes encrypted with per-patient DEKs under a healthcare CMK; volume encryption provides defense-in-depth.
  • Checkout service: Token vault holds PAN; application DB stores only processor tokens meeting PCI scope goals.
  • Mesh-secured microservices: SPIFFE identities with daily cert rotation between payment and ledger services.
  • Cross-region analytics: Encrypted columnar extracts in object storage with per-partition DEKs and centralized CMK in home region for GDPR transfer analysis.
  • Mobile offline cache: SQLCipher or platform secure enclaves with keys derived from device-bound material plus server-issued session secrets.
  • Key escrow for e-discovery: Separate legal-hold CMKs with break-glass procedures distinct from production rotation to satisfy lawful access without weakening everyday controls.
  • Batch ETL: Columnar files encrypted at rest in the lakehouse with per-dataset DEKs and catalog tags indicating classification for downstream jobs.
