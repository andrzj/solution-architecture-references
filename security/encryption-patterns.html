Security Architecture

Encryption Patterns

Encryption in distributed systems: AES-256-GCM, envelope encryption, KMS key hierarchy, TLS 1.3, mutual TLS, field-level encryption, key rotation, HSMs, and BYOK.

⏱ 11 min read

What it is

Encryption patterns extend beyond default volume and TLS settings to address application-specific threats: envelope encryption with per-object data keys, field-level encryption for regulated columns, tokenisation, searchable-encryption trade-offs, and mTLS for cryptographic peer identity on east-west paths. Patterns align with NIST SP 800-57 key hierarchies and cloud KMS APIs—architects decide where ciphertext is created based on who must remain unable to decrypt and which queries must keep working.

Tokenisation replaces PANs or government identifiers with reversible references stored in a vault, shrinking PCI scope compared with local ciphertext. Searchable encryption trades some leakage for indexability via deterministic encryption or blind indexes. mTLS proves both peer identities on east-west RPC paths, supporting Zero Trust meshes where network location is untrusted.

In distributed systems, encryption in transit protects bytes on the wire (TLS); encryption at rest protects volumes, databases, or individual fields. Symmetric work typically uses AES-256-GCM (AEAD confidentiality and integrity). Asymmetric work uses RSA-4096 or ECDSA P-256 for exchange and signatures.

In envelope encryption, a data encryption key (DEK) encrypts each object or record; a key encryption key (KEK) in AWS KMS, Azure Key Vault, or GCP Cloud KMS wraps the DEK. Stored ciphertext includes the wrapped DEK so applications decrypt locally after a single KMS unwrap—limiting API cost—while KEK rotation invalidates wrapped DEKs under retired versions. BYOK places the root KEK in a customer HSM when contracts require proof the cloud operator cannot read tenant data.

Why it exists

Disk and bucket encryption do not stop authorised application users or SQL injection from reading plaintext. Field encryption and tokenisation shrink compliance scope and limit insider blast radius. mTLS binds connections to workload identity—essential for Zero Trust meshes and regulated interconnects. Regulations (GDPR, HIPAA, PCI DSS) and SOC 2 audits expect encryption in transit and at rest plus demonstrable key governance: ciphertext stored with an exposed KEK is effectively plaintext.

Platform defaults (EBS, S3 SSE, managed database TDE) are necessary but insufficient when the threat model includes application compromise or insider abuse. Architects choose where ciphertext is produced—client, service tier, or database extension—based on query needs and who must remain unable to decrypt.

When to use

  • All data in transit—TLS 1.2 minimum, TLS 1.3 preferred, with weak protocol fallbacks disabled.
  • All sensitive data at rest in databases, object stores, block volumes, and backups—provider-managed keys at minimum, customer-managed keys for regulated tiers.
  • PCI PAN, PHI, or national ID fields needing scope reduction or extra confidentiality.
  • Multi-tenant SaaS where per-tenant keys limit cross-tenant decrypt after a bug.
  • Service meshes or gRPC estates requiring cryptographic peer authentication.
  • Backup and analytics pipelines that must not store decryptable PII.
  • Regulated BYOK scenarios where customers control root KEKs in an HSM.

When not to use

  • Do not field-encrypt columns heavily used in ad hoc SQL without deterministic or blind-index strategies.
  • Avoid custom envelope schemes—use KMS wrap/unwrap APIs and audited libraries.
  • Public static assets rarely justify at-rest encryption overhead.
  • Never implement primitives from scratch; use libsodium, Bouncy Castle, or platform TLS stacks.

Typical architecture

Envelope keys wrap per-record DEKs while mesh mTLS and token services anchor trust for sensitive fields.

Pros and cons

Pros

  • Per-tenant keys constrain blast radius of application defects.
  • Tokenisation keeps PAN out of application databases.
  • mTLS ties traffic to workload identity, not IP alone.
  • Envelope patterns scale with object count via cached DEKs.
  • Key rotation supports forward secrecy when old KEK versions are retired promptly.
  • Field-level encryption enforces confidentiality even when database roles are over-permissive.

Cons

  • Key rotation and bulk re-wrap projects are operationally heavy; mistakes can brick ciphertext.
  • Search and sort on encrypted fields need deterministic encryption, blind indexes, or application-side filters.
  • mTLS certificate lifecycle burdens large microservice fleets unless fully automated.
  • BYOK customers own HSM availability and backup procedures.
  • Client-side encryption complicates support and escrow debates.

Implementation notes

Generate a DEK per object or row; wrap with KMS; store ciphertext and wrapped key together. Cache DEKs briefly; never log plaintext keys. For tokenisation, use a vault-style service; format-preserving tokens only when contractually required.

Enforce TLS 1.2 minimum with TLS 1.3 preferred; disable RC4, DES, 3DES, and MD5 suites; prefer ECDHE for forward secrecy so stolen server keys cannot decrypt past sessions. Set HSTS with a one-year max-age and include subdomains where feasible. Require TLS to databases and validate server certificates in clients—sslmode=require on PostgreSQL and require_secure_transport=ON on MySQL are common baselines. For S3, enable default bucket encryption and deny PutObject without server-side encryption headers.

Roll out mesh mTLS with SPIFFE/SPIRE or cloud PKI; rotate certificates faster than expected compromise windows. For AES-GCM, generate a fresh random nonce per encryption—nonce reuse is catastrophic. Store the IV with ciphertext; it is not secret.

Generate one DEK per object or row; wrap with KMS; store ciphertext and wrapped key together; cache DEKs with a short TTL and never log plaintext keys. Document which pattern applies per data class in architecture decision records. For tokenisation, prefer vault-backed services; use format-preserving tokens only when contracts demand them.

Key hierarchy typically flows from an HSM or cloud KMS root to a customer master key (CMK), then to per-record DEKs, then to data. Automatic CMK rotation creates a new key version; lazy re-wrap updates encrypted DEKs over time while retaining old CMK versions to decrypt legacy rows. Per-tenant CMK aliases isolate cryptographic blast radius in multi-tenant SaaS. Never store unwrapped DEKs or CMKs alongside ciphertext in the same table without an additional access control boundary.

Plan hybrid TLS and key agreement with ML-KEM (NIST FIPS 203) alongside classical algorithms during post-quantum migration—capture records now, re-wrap later with quantum-safe DEKs where regulators ask. Platform-wide TLS 1.3 defaults and volume encryption toggles belong in encryption at rest and transit; this article covers application envelope design, mTLS between services, and AEAD nonce discipline (never reuse a GCM nonce under one key).

Record ciphertext format version bytes beside wrapped DEKs so decrypt paths can branch when algorithms or key sizes change during migration programs.

Benchmark envelope encrypt and decrypt latency per record size before choosing row-level versus object-level keys.

Common failure modes

  • Unwrapped DEKs beside data—defeats envelope design.
  • Single CMK for all tenants—one IAM mistake decrypts everyone.
  • Optional mTLS—fallback to plaintext east-west under load.
  • Tokens without vault controls—tokens become secrets themselves.
  • Skipped re-wrap on CMK rotation—orphaned data keys.
  • TLS verify disabled—negates transport encryption entirely.
  • IV reuse in AES-GCM—sequential or repeating nonces break authentication guarantees.
  • Weak key derivation—password-based keys without PBKDF2, bcrypt, or Argon2 succumb to brute force.
  • Expired mTLS certificates—manual rotation causes sudden east-west outages.

Decision checklist

  • Are sensitive fields mapped to encryption or tokenisation patterns with owners?
  • Does KMS enforce least-privilege decrypt per workload?
  • Is all data in transit protected by TLS 1.2+ with forward-secrecy cipher suites?
  • Is all sensitive data at rest encrypted with AES-256 (or equivalent) using KMS-managed keys?
  • Is envelope encryption used so KMS is not invoked on every read and write?
  • Is automatic key rotation configured with tested rollback?
  • Is mTLS required on critical east-west APIs with automated rotation?
  • Are DEKs never logged or cached beyond defined TTL?
  • Is there a tested plan for CMK rotation and bulk re-wrap?
  • Do backups inherit the same field protections as primary stores?

Example use cases

  • Illustrative scenario — per-tenant SaaS: CMK alias per tenant; DEK per customer record; decrypt scoped in middleware.
  • Healthcare application: PHI fields use AES-256-GCM with per-patient DEKs wrapped by a customer-managed CMK; database TDE adds a second layer.
  • Payment processing: PCI requires PAN protection at rest; tokenisation in the app DB with PAN only in a hardened vault.
  • Service mesh: Istio or Linkerd enforces mTLS; SPIRE issues 24-hour SVIDs for workload identity.
