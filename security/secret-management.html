Security Architecture Essential

Secret Management

Centralised management of credentials, API keys, and certificates: dynamic secrets, automatic rotation, secure injection, and eliminating secret sprawl.

⏱ 10 min read

What it is

Secret management centralises the lifecycle of credentials—database passwords, API keys, TLS material, signing keys—outside repositories and long-lived environment variables. A secrets manager (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) exposes an audited API so workloads fetch secrets at runtime using platform identity rather than static configuration checked into Git.

Dynamic secrets mint short-lived credentials per request: Vault provisions a unique database user with a TTL, revokes it on expiry, and never stores a reusable password. Rotation replaces static secrets on a schedule (Lambda rotation in AWS Secrets Manager, Vault engines) so stolen values age out even when leakage is undetected. Injection patterns include Vault Agent sidecars, Kubernetes CSI drivers, and CI OIDC federation so humans rarely handle plaintext credentials.

OWASP Secrets Management and CIS Control 3 emphasise eliminating long-lived secrets from repos and enforcing rotation with audit trails. NIST SP 800-57 defines cryptographic key and secret lifetimes—short TTLs and automated replacement reduce exposure windows when exfiltration happens.

Why it exists

Credential theft remains a dominant breach pattern—Verizon DBIR and cloud IR reports consistently cite stolen keys and passwords. Commits to public repos, CI logs printing connection strings, and shared .env files create multi-year exposure windows because Git history is immutable. Secret managers remove the habit of baking credentials into artifacts and provide queryable audit trails for compliance (PCI Req. 8, SOC 2 CC6.1).

When every service uses unique, revocable credentials tied to workload identity, lateral movement after one compromise becomes harder and incident scope shrinks to lease duration instead of password lifetime. Automated scanners (Gitleaks, truffleHog, GitHub secret scanning) find past leaks, but prevention at the source is the durable fix.

PCI DSS requirement 8 and SOC 2 CC6.1 expect documented credential lifecycle controls—who can read secrets, when they rotate, and what was accessed during an investigation. Central managers answer those questions from API audit logs instead of spreadsheets and shared password vaults.

When to use

  • Any production workload connecting to databases, queues, partner APIs, or cloud control planes.
  • CI/CD that deploys infrastructure or signs artifacts—prefer OIDC to static cloud keys.
  • Microservice estates with dozens of per-service credentials requiring least privilege and rotation evidence.
  • Regulated environments demanding access logging, dual control, and provable rotation cadence.

When not to use

  • Local-only developer sandboxes where a gitignored .env is acceptable; optionally run Vault dev mode for parity.
  • Non-sensitive configuration (feature toggles, timeouts)—use parameter stores or config services without encryption overhead.
  • Replacing a secrets manager with Kubernetes Secrets alone—base64 is not encryption; pair with etcd encryption or external CSI mounts.

Typical architecture

Workloads authenticate with platform identity to Vault or cloud secret stores that lease or rotate credentials at runtime.

Pros and cons

Pros

  • Removes static credentials from source, images, and broad environment variables.
  • Dynamic leases cap blast radius of exfiltrated credentials to minutes or hours.
  • Central audit logs attribute every read to identity, path, and time.
  • Automated rotation reduces operational toil and stale-password risk.
  • Policy-as-code for Vault policies or cloud IAM integrates with SDLC review.

Cons

  • Self-hosted Vault demands HA operations, unseal discipline, and backup testing.
  • Outage of the secrets layer can block credential renewal—design caching and graceful degradation.
  • Legacy targets may lack dynamic engines; migration projects are cross-team.
  • Mis-scoped “read *” policies recreate shared-password anti-patterns at scale.

Implementation notes

Prefer cloud-native managers for static secrets when already on that cloud—native IAM, rotation Lambdas, and CMK integration reduce bespoke ops. On Kubernetes, mount secrets via Secrets Store CSI Driver rather than copying values into cluster Secret objects; enable etcd encryption at rest if Secrets are unavoidable.

Scope Vault policies or cloud IAM to explicit paths and operations per application—avoid read on entire mount points. Use cloud identity auth (AWS IAM, Azure managed identity, GCP service account) or Kubernetes projected tokens instead of embedding long-lived Vault tokens in environment variables. For database dynamic secrets, set TTL to the shortest interval that avoids connection storms; implement lease renewal in the agent or SDK before expiry.

Run organisation-wide secret scanning (GitHub Advanced Security, Gitleaks, truffleHog) on default branches and historic commits when adopting centralized management. Block PR merges when scanners find high-confidence patterns; pair with immediate rotation of any leaked value still in use. For Vault production, use integrated Raft or Consul storage across AZs, automate unseal with cloud KMS, and rehearse seal recovery. Never store the root token alongside application secrets.

CI pipelines should assume cloud roles via OIDC (GitHub Actions, GitLab) instead of static cloud API keys in repository secrets. Log every secret read with principal, path, and timestamp; feed those logs to SIEM rules that flag off-hours bulk reads or new identities accessing production paths.

Vault dynamic secrets mint database or cloud credentials with short TTLs and auditable leases instead of static passwords in config. Solve secret zero by bootstrapping workloads with cloud IAM or SPIFFE identities before they can call the secrets API. External Secrets Operator syncs cluster secrets from Vault or cloud managers so pods never bake long-lived values into images. Rotate shared credentials with dual-active windows—issue credential B, deploy consumers, retire A—so restarts are not synchronized globally. Run gitleaks in CI and enable provider push protection so accidental commits never reach default branch.

Alert when secret lease TTL approaches zero for long-running batch jobs that cannot refresh mid-flight—those workloads need static roles with narrow scope instead of minute leases.

Common failure modes

  • Secrets in Git history: Removing a value from HEAD leaves it in immutable history; rotate the live secret immediately and use BFG or filter-repo when policy allows rewriting history.
  • CI log leakage: Debug flags that dump environment variables expose database passwords to anyone with pipeline read access—mask outputs and forbid secret echo in build scripts.
  • Manual unseal: Vault restarts without auto-unseal stall credential renewal across the fleet during deploy waves.
  • Over-broad policies: A single policy granting read on secret/data/* recreates shared-password blast radius at API scale.
  • No lease renewal: Apps that cache dynamic database users past TTL hit auth failures at peak traffic when leases expire together.
  • Kubernetes Secret as source of truth: Copying values into cluster Secrets without CSI sync leaves stale copies after rotation and often skips audit of who read them.

Decision checklist

  • Are production secrets absent from Git, container images, and shared parameter files?
  • Do workloads authenticate with cloud or Kubernetes identity—never long-lived vault tokens in env?
  • Is rotation automated for static secrets with documented intervals per sensitivity?
  • Are policies scoped to explicit paths and operations per application?
  • Is the secrets platform deployed HA with tested backup and unseal procedures?
  • Does continuous scanning block new leaks in PRs?
  • Are CI and deploy roles using OIDC federation instead of stored cloud keys?
  • Do audit logs for secret reads feed alerting within 24 hours?

Example use cases

  • Illustrative scenario — Kubernetes sidecar: Vault Agent authenticates with projected service account JWT, renders rotating PostgreSQL creds to tmpfs; each pod receives unique DB users.
  • Illustrative scenario — GitHub Actions OIDC: Pipeline assumes AWS role without stored keys, reads deployment secrets from Secrets Manager; credentials expire when the job ends.
  • Illustrative scenario — legacy lift: Monolith still on static DB password; Secrets Manager rotation Lambda updates RDS user monthly while app pulls via SDK at startup.
