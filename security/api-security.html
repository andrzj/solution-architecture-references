Security Architecture

API Security

Securing APIs against the OWASP API Top 10: broken object-level authorisation, excessive data exposure, mass assignment, API key management, rate limiting, and GraphQL-specific mitigations.

⏱ 10 min read

What it is

API security hardens HTTP, GraphQL, and gRPC interfaces against abuse, data leakage, and unauthorised access. Unlike browser applications, APIs are trivial to script: attackers enumerate resource IDs, replay bearer tokens, and flood endpoints without rendering a UI. Sound API design therefore combines authentication (OAuth 2.0 per RFC 9700, mTLS for partners), fine-grained authorisation, schema validation, rate limiting, and security logging.

The OWASP API Security Top 10 catalogues API-specific weaknesses separately from the OWASP Web Application Top 10—important because API defects rarely surface in HTML-centric scans.

Broken Object-Level Authorisation (BOLA / IDOR) is the archetype: an endpoint such as /api/orders/12345 that checks authentication but not ownership lets any signed-in caller read another customer’s orders by incrementing IDs. Broken authentication covers weak API keys and non-expiring tokens. Excessive data exposure returns full domain models while mobile clients display a subset—attackers read all fields. Mass assignment binds request bodies directly into models, enabling fields like isAdmin: true. Misconfiguration leaves debug routes and stack traces visible; injection reaches databases through parameters. GraphQL adds introspection, deeply nested queries that stress databases, and the need for explicit field-level authorisation.

Why it exists

Microservices and mobile clients made APIs the authoritative data plane for web, mobile, IoT, and partner integrations. Verizon’s Data Breach Investigations Report consistently ranks web application attacks—mostly API abuse—among the top breach actions. Traditional DAST tools optimised for HTML forms rarely exercise BOLA, mass assignment, or GraphQL complexity attacks. Predictable REST paths invite automation: without server-side ownership checks, an adversary can walk /api/orders/1 through /api/orders/1000000 in minutes. Shared taxonomies such as the OWASP API Top 10 and NIST SP 800-218 (secure software supply chain practices) give architects and auditors a common vocabulary for reviews and customer questionnaires.

When to use

  • Every API reachable outside a single trusted process—public, partner, mobile backend, or internal microservice behind a mesh.
  • Integrations where clients cannot hold long-lived secrets safely (use OAuth with PKCE or short-lived tokens).
  • GraphQL or admin APIs that need depth limits, complexity budgets, and disabled introspection in live environments.
  • High-value flows—payments, bulk export, privilege changes—where step-up authentication and stricter rate limits apply.

When not to use

  • These are not optional product features: all APIs need baseline controls. Scope varies—a read-only catalogue with no tenant data still needs injection defences and throttling even if BOLA is N/A.
  • Do not treat private network placement or VPN access as authorisation; lateral movement uses the same endpoints.
  • Avoid copying authZ logic into every service without tests—prefer a shared library or policy engine with reviewed defaults.

Typical architecture

Edge gateways validate tokens, enforce OpenAPI schemas, and apply per-identity rate limits before traffic hits domain services that enforce object-level authorisation.

Pros and cons

Pros

  • Consistent gateway policies for authentication, throttling, and request validation reduce duplicated code across services.
  • Ownership checks on every read and write block horizontal privilege escalation—the most common API breach pattern.
  • Explicit response DTOs and allowlisted field binding prevent accidental exposure of hidden columns.
  • Structured audit logs (auth failures, denials, admin mutations) accelerate fraud investigations and incident response.

Cons

  • The gateway becomes a critical path; it must be highly available and degrade gracefully when downstream authorisation services lag.
  • Gateways cannot infer resource ownership—each service still implements tenant and object checks.
  • OAuth scope design that is unclear to integrators causes support burden and misconfigured clients.
  • Generic error responses improve safety but require correlation IDs and server-side detail for engineers debugging production issues.

Implementation notes

Make BOLA prevention a code-review invariant: any query or update by resource identifier must also filter by authenticated user or tenant ID. Automate authorisation tests that prove cross-tenant access is rejected. Keep ownership rules in the service layer—the gateway validates JWT claims but not business semantics.

Return response DTOs instead of ORM entities; serialise with opt-in field lists. Cap page sizes to deter bulk scraping. Send stable, generic errors to clients while logging stack traces and internal identifiers only server-side. Hash API keys at rest, show plaintext once at issuance, prefix with environment (sk_live_), scope narrowly, and expire on a schedule. For sensitive B2B integrations prefer mTLS over static API keys.

Validate every body and query parameter against OpenAPI or JSON Schema; reject unknown fields on privileged routes. Pair edge WAF rules with positive security models for JSON where practical. Instrument authentication failures and authorisation denials with trace IDs shared across services.

Use structured error codes in documentation so support teams can map client-facing messages to internal causes without exposing implementation detail. Track last-used timestamps on API keys for dormant-credential review. For GraphQL, cap mutation complexity lower than queries, persist approved query documents for mobile clients, and expose schema changes through a portal rather than live introspection.

Common failure modes

  • BOLA via predictable IDs: Sequential integers in URLs are easy to scan; opaque IDs reduce noise but never replace ownership checks.
  • User enumeration in errors: Messages like “email not found” confirm account existence—return a single “invalid credentials” response for auth failures.
  • Unthrottled auth routes: Login, reset, and OTP endpoints without rate limits invite credential stuffing.
  • Hidden admin routes: Undocumented /api/admin/* paths protected only by obscurity remain exploitable once discovered.
  • GraphQL introspection left on: Exposes the full schema and speeds targeted exploitation—disable in production and ship SDL via your developer portal instead.

Decision checklist

  • Does every sensitive read or write verify resource ownership on the server?
  • Are access tokens short-lived, scoped, revocable, and documented for rotation?
  • Do request schemas validate input and block unknown privileged fields?
  • Are auth and data-export routes rate-limited with anomaly detection?
  • Do logs record denials without leaking secrets or full PII?
  • Has an API-focused test covered the OWASP API Top 10 within the last year?

Example use cases

  • Illustrative scenario — mobile banking: OAuth with PKCE, per-account object checks, and device binding on high-risk transfers.
  • Financial services API: Banking APIs enforce object-level authorisation on accounts and transactions; access requires a valid JWT plus verified ownership; every call is logged for compliance audit.
  • GraphQL BFF: Backend-for-frontend GraphQL disables introspection in live environments, scores query complexity (mutations capped at 200, queries at 1000), and applies field middleware that checks roles before resolving sensitive fields.
  • Partner API gateway: Partner keys scoped to orders:read and inventory:write, rate limited per hour, hashed at rest, and stored only in the partner’s secrets manager.
