Security Architecture

API Security

Securing APIs against the OWASP API Top 10: broken object-level authorisation, excessive data exposure, mass assignment, API key management, rate limiting, and GraphQL-specific mitigations.

⏱ 10 min read

What it is

API security is the set of controls that ensure only authenticated, authorised callers access the right data through programmatic interfaces — REST, GraphQL, gRPC, and webhooks — with acceptable abuse resistance. It spans transport trust (TLS, mTLS), token validation, object-level authorisation, input validation, rate limiting, and safe error handling. The OWASP API Security Top 10 catalogues the most critical API-specific vulnerabilities, distinct from the OWASP Web Application Top 10.

The leading API vulnerability is Broken Object-Level Authorisation (BOLA / IDOR): an API that accepts a resource identifier (e.g., /api/orders/12345) but fails to verify that the authenticated user owns resource 12345 allows horizontal privilege escalation — any authenticated user can access any other user's data by iterating IDs.

Other critical OWASP API risks include: Broken Authentication (weak API key schemes, missing token expiry), Excessive Data Exposure (returning full data models and relying on the client to filter — a mobile app might show 5 fields but the API returns 50, including sensitive ones), Mass Assignment (blindly binding request body fields to data model objects, allowing a user to set fields like isAdmin: true), Security Misconfiguration (debug endpoints left enabled, verbose error messages revealing stack traces), and Injection (SQL, NoSQL, command injection via API parameters). GraphQL introduces additional surface: introspection exposes the full schema to attackers, deeply nested queries can cause denial of service by triggering deeply recursive database joins, and field-level authorisation must be implemented explicitly as GraphQL does not have built-in field visibility controls.

Why it exists

Every modern channel—web, mobile, partner, and batch—eventually calls the same API surface, which makes that surface the highest-value target for credential stuffing, automated enumeration, and authorisation bypass. Industry breach data and the OWASP API Security Top 10 consistently rank broken access control and unsafe consumption ahead of exotic exploit chains. Dynamic application scanners tuned for HTML forms frequently miss BOLA, mass assignment, and GraphQL depth abuse because those failures require token context and object ownership semantics. NIST access-control guidance (SP 800-53 families AC and SC) expects systems to enforce least privilege at the resource level, not only at the front door.

Predictable URLs and machine-readable JSON responses lower the cost of abuse: a single missing ownership predicate on GET /api/orders/{id} can turn a legitimate session into a fleet-wide data harvest in minutes. API security programmes exist to close that gap with consistent gateway policy, service-layer authorisation, and testable patterns auditors and red teams can verify.

When to use

  • Internet-exposed REST, GraphQL, gRPC, and webhook endpoints—treat OWASP API Top 10 mitigations as non-negotiable baselines.
  • East-west microservice APIs where lateral movement after one compromised pod could reach sensitive aggregates.
  • GraphQL gateways that need query cost limits, depth caps, and production introspection lockdown beyond typical REST controls.
  • B2B integrations where scoped API keys or mTLS must replace long-lived shared secrets in configuration files.

When not to use

  • Security is never optional for APIs; calibrate depth to data classification. Public read-only catalogues may deprioritise BOLA testing but still require injection defences, TLS, and abuse throttling.
  • Do not rely on “security by obscurity” (undocumented admin routes) instead of role checks—discovery tooling finds them quickly.

Typical architecture

Request path: terminate TLS at the edge, validate tokens and quotas at an API gateway, enforce object-level rules in domain services, and emit structured audit events—aligned with OWASP cheat sheets for REST and GraphQL hardening.

Pros and cons

Pros

  • Consistent object-level authorisation shrinks the OWASP API Top 10 “broken object-level authorisation” class of incidents.
  • DTO-first responses and allowlisted binders prevent mass assignment and accidental over-disclosure in mobile payloads.
  • Central rate limits and bot rules absorb credential stuffing and scraping without per-service reinvention.
  • Schema validation at the gateway catches malformed traffic before it reaches fragile parser code paths.

Cons

  • Authorisation logic must be repeated and tested per resource type—one gap equals a headline breach.
  • Aggressive throttling can break bulk integrators unless tiered quotas and partner allowlists exist.
  • GraphQL cost controls need ongoing tuning as schemas evolve and resolvers gain joins.
  • Strong production GraphQL lockdown shifts developer ergonomics toward schema registries and offline explorers.

Implementation notes

Adopt a fail-closed authorisation pattern: persistence access always includes tenant or subject filters derived from validated claims—never trust client-supplied user IDs in the body. Complement manual review with contract tests that attempt cross-tenant reads and writes; map cases to OWASP API scenarios for regression suites. Gateways should verify JWT signature, issuer, audience, and expiry (per RFC 8725 and the OWASP JWT cheat sheet) but cannot substitute for domain ownership rules inside services.

Serialise with explicit projection types; forbid returning raw ORM entities to external callers. Cap page sizes and export endpoints; log high-volume reads for fraud analytics. Return stable, coarse error codes to clients while logging rich detail to a tamper-evident store. Store API keys hashed with scoped IAM-style permissions, rotation schedules, and last-used telemetry; prefer mTLS or OAuth client credentials for high-trust partners under NIST-oriented key-management practices.

Common failure modes

  • Opaque IDs without ownership checks: UUIDs reduce guessing but do not stop BOLA when authorisation is absent.
  • User enumeration via errors: Different responses for “unknown user” vs “bad password” leak account existence—normalise auth failure text.
  • Unthrottled token and OTP flows: Password reset and MFA endpoints become brute-force lanes without per-IP and per-account throttles.
  • Hidden admin routes: Undocumented /internal/admin handlers reached by scanners when RBAC is missing.
  • Production GraphQL maps: Introspection and unbounded nested queries enable schema-driven exploitation and DoS.

Decision checklist

  • Does every mutating and reading path enforce tenant or owner scope server-side?
  • Are request DTOs allowlisted and response shapes explicitly projected?
  • Do gateway policies include per-identity rate limits and anomaly alerts?
  • Are GraphQL depth, cost, and introspection settings verified in production config?
  • Are partner credentials hashed, scoped, expiring, and never logged?
  • Do CI suites include OWASP API–style authorisation negative tests?

Example use cases

  • Illustrative scenario — financial services API: Object-level authorisation on every account and transaction endpoint; access requires valid token plus verified account ownership; all decisions logged for compliance audit.
  • Illustrative scenario — GraphQL BFF: Introspection disabled in production; per-query complexity scoring; per-field authorisation middleware before resolving sensitive fields.
  • Case study — Stripe: Partner APIs use scoped secret keys with rate limits and idempotency keys; documentation emphasises server-side verification of webhooks.
  • Illustrative scenario — partner API gateway: Keys scoped to orders:read / inventory:write, rate limited per key, hashed at rest, issued only into partner secrets managers.
