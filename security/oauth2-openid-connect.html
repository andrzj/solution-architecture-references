Security Architecture

OAuth2 & OpenID Connect

The industry standard delegation and identity protocols — flows, tokens, and common pitfalls.

⏱ 12 min read

What it is

OAuth 2.0 is an authorisation framework: a client obtains limited access to a resource on behalf of a resource owner without ever receiving that owner’s password. The authorization server issues access tokens scoped to specific permissions; resource servers validate those tokens before serving data. OpenID Connect (OIDC) is an identity layer on top of OAuth 2.0 — it standardises how clients learn who authenticated via an ID token (a JWT carrying claims such as sub, iss, and aud) alongside the access token.

Common grant patterns include Authorization Code (with PKCE for public clients such as SPAs and mobile apps), Client Credentials for machine-to-machine calls, and Device Authorization for headless devices. OAuth answers “may this client act on behalf of this user with these scopes?”; OIDC answers “which user signed in, and when?”

Why it exists

Before OAuth, third-party integrations often required users to share passwords — a breach of one site compromised accounts everywhere. Custom single sign-on protocols did not interoperate across vendors. OAuth 2.0 and OIDC are IETF/OpenID Foundation standards supported by every major identity provider, API gateway, and cloud IAM product, which means architects can federate workforce and customer identity once and reuse the same token validation patterns across services.

Mis-implementing these flows still causes high-severity breaches (redirect hijacking, token theft, confused-deputy attacks), so the standards ecosystem now encodes safer defaults: OAuth 2.1 deprecates the implicit flow, mandates PKCE for public clients, and encourages sender-constrained tokens.

When to use

  • User login for web, mobile, and single-page applications where a browser or system web view can complete an interactive authorisation step.
  • Delegated API access — a client calls an API with an access token scoped to what the user consented to, not the user’s full account.
  • Enterprise and B2B federation — OIDC bridges SaaS apps to corporate IdPs; SAML federation upstream can still terminate at an OIDC-capable broker.
  • Partner integrations where partners authenticate users at their IdP and your resource server trusts tokens from a known issuer.

When not to use

  • Pure service-to-service with no user in the loop — prefer client credentials, workload identity, or mTLS rather than inventing a “user” for OAuth.
  • Resource Owner Password Credentials or Implicit flow for new applications — both are deprecated or removed from OAuth 2.1; they expose credentials or tokens to the browser.
  • First-party session replacement where a simple server-side session and HttpOnly cookie suffice and no third-party delegation is required — OAuth adds moving parts without benefit.

Typical architecture

For interactive clients, the Authorization Code flow with PKCE keeps secrets out of the browser: the client proves possession of a one-time verifier when exchanging the code at the token endpoint. Confidential backends (BFF pattern) hold client secrets and perform token exchange server-side.

Pros and cons

Pros

  • Interoperable libraries, conformance suites, and managed IdPs reduce bespoke auth code.
  • PKCE secures public clients without embedding a client secret in mobile or SPA binaries.
  • Scoped access tokens enforce least privilege per API and per client registration.
  • Refresh token rotation and PAR (Pushed Authorization Requests) support high-assurance deployments.

Cons

  • Redirect URI and client registration mistakes are a frequent source of account takeover.
  • JWT validation errors (wrong aud, stale JWKS, accepting none) are common in custom middleware.
  • Enterprise claim mapping (groups, tenant IDs, custom attributes) grows complex across many clients.
  • Large JWT access tokens inflate headers and complicate logging and caching.

Implementation notes

Register exact redirect URI allowlists — no wildcards, no open paths. Use separate client registrations per environment (dev/stage/prod) and per platform (web vs mobile deep link). For SPAs, prefer a backend-for-frontend that performs token exchange; never store refresh tokens in browser storage.

Validate ID tokens on every login: signature against issuer JWKS, iss matches configured authority, aud matches this client ID, exp/iat within clock skew, and nonce if the authorisation request included one. For access tokens, validate audience for this API — an ID token audience is not interchangeable with an API resource indicator.

Enable refresh token rotation with reuse detection; revoke family on suspected theft. Consider DPoP or mTLS-bound tokens when tokens might leak from logs or proxies. Use PAR or JAR for clients that need request integrity on the authorisation endpoint. Propagate logout via OIDC RP-initiated logout or back-channel logout when sessions must end across apps.

OAuth 2.1 and IETF Security BCP RFC 9700 deprecate the implicit flow and resource-owner password credentials for interactive apps—use authorization code with PKCE for browser, mobile, and native clients. After exchange, enforce that each API checks token audience and granted scopes for that resource, not only signature validity. Sender-constrained tokens via DPoP proof keys or mutual TLS certificate binding reduce replay when a bearer token leaks from a proxy log.

Register back-channel logout URIs alongside redirect URIs so session termination propagates to all relying parties after password reset or admin revoke.

Document which scopes each API enforces; scope inflation in consent screens trains users to click approve without reading.

Common failure modes

  • Open redirect on redirect_uri: wildcard or prefix-only matching lets an attacker steal authorization codes on a controlled path.
  • PKCE downgrade: authorization server accepts token exchange without code_verifier for public clients.
  • Using access tokens as session cookies without audience and scope checks on each request.
  • Accepting alg=none or symmetric algorithms when only asymmetric RS256/ES256 from the IdP is intended.
  • Long-lived refresh tokens without rotation, device binding, or revocation on password change.
  • Mixing tenants: one client ID serves multiple customers without iss/tid validation, enabling cross-tenant token replay.

Decision checklist

  • Are interactive clients using Authorization Code + PKCE (not implicit or ROPC)?
  • Are redirect URIs exact-match only, with separate registrations per app surface?
  • Are ID and access tokens validated separately with correct aud for each resource?
  • Is refresh token rotation enabled with reuse detection?
  • Are scopes minimised per client registration and documented for reviewers?
  • Does logout propagate to the IdP when shared sessions must end?

Example use cases

  • Illustrative scenario — multi-tenant B2B SaaS: Each customer’s workforce federates via SAML to a central OIDC broker; the SaaS API trusts access tokens whose tid claim scopes data plane queries.
  • Illustrative scenario — mobile consumer app: System browser completes PKCE login; refresh tokens are device-bound; step-up authentication at the IdP raises acr before high-risk in-app actions.
  • Case study — Google accounts: Google’s identity platform issues OIDC tokens consumed by thousands of third-party “Sign in with Google” clients using standard discovery and JWKS endpoints.
  • Illustrative scenario — operator CLI: Device Authorization Grant displays a user code on a headless VM; the engineer approves on a phone; the CLI polls until it receives scoped tokens.
