Security Architecture

Data Security

Protecting data at rest, in transit, and in use: data classification frameworks, column-level encryption, tokenisation, data masking, PII handling, GDPR/CCPA technical controls, and access auditing.

⏱ 10 min read

What it is

Data security is the set of controls that keep information confidential, intact, and available according to its sensitivity. The foundation is data classification: assigning sensitivity levels to data (Public, Internal, Confidential, Restricted) based on the harm that disclosure would cause, and applying proportionate controls at each level. Encryption at rest protects data stored on disk from physical media theft; encryption in transit (TLS) protects data from network interception; and column-level encryption (also called application-level encryption or field-level encryption) protects specific sensitive fields even within a database to which the application has legitimate read access.

Tokenisation replaces a sensitive value (credit card number, SSN) with a non-sensitive surrogate token that has no mathematical relationship to the original value and can only be de-tokenised by authorised parties with access to the token vault. It differs from encryption in that the token cannot be de-tokenised without the vault, even with the algorithm. Data masking transforms data for lower-trust environments: static masking creates a de-identified copy for development/testing; dynamic masking returns masked values in real-time to unprivileged users. PII (Personally Identifiable Information) handling requires additional controls under GDPR and CCPA: data minimisation (don't collect what you don't need), purpose limitation (don't use data beyond its stated purpose), retention limits (delete data when no longer needed), and the right to erasure (technical ability to delete all data associated with a user).

Why it exists

Data loss incidents drive regulatory fines, churn, and forensic cost—often measured in millions per event. Layered controls ensure stolen backups or SQL-driven dumps return ciphertext or tokens instead of usable PII. Privacy law (GDPR, CCPA) and sector rules (HIPAA, PCI DSS) expect demonstrable technical safeguards aligned with the NIST Privacy Framework and OWASP cryptographic storage guidance.

Classification, encryption, masking, and immutable access logs produce the evidence privacy officers and external auditors request—not merely policy PDFs.

Board and regulator questions increasingly ask for quantitative metrics—percentage of restricted data encrypted, mean time to complete erasure tickets, and counts of unmasked copies in lower environments—so instrumentation should expose those figures without manual spreadsheet audits.

When to use

  • Any datastore holding personal, financial, or health information subject to breach notification.
  • Cardholder environments where PAN must be tokenised or vaulted per PCI DSS.
  • Analytics and AI pipelines that must minimise raw PII retention.
  • Lower-trust environments (dev/stage) fed only by masked or synthetic datasets.
  • Cross-border replication where data residency tags must travel with records and keys stay in-region.
  • Machine-learning feature stores that aggregate attributes requiring minimization and purpose binding.

When not to use

  • Blanket column encryption—reserve field-level crypto for truly sensitive attributes; over-encryption breaks indexing and reporting unless paired with tokenisation or blind indexes.

Typical architecture

Sensitivity tiers from public to restricted drive control depth: token vaults for PAN, envelope encryption for regulated columns, and WORM audit logs for access reviews.

Pros and cons

Pros

  • At-rest encryption and tokenisation shrink exploitable value in leaked dumps.
  • Vaulted PAN patterns materially reduce PCI assessment scope for merchants.
  • Masking and synthesis keep engineers off production PII without halting delivery.
  • Immutable query logs support insider-threat detection and privacy audits.

Cons

  • Field-level ciphertext complicates ad hoc SQL analytics and equality search.
  • Per-field KMS usage increases cost and requires disciplined rotation runbooks.
  • Erasure on append-only streams needs crypto-shredding design up front.
  • Synthetic data may break referential tests unless generators model relationships.
  • Cross-border transfers may require additional legal basis and key residency even when ciphertext looks identical technically.

Implementation notes

Use envelope encryption for column-level fields: per-record DEK, AES-256-GCM on the value, KEK wrap via AWS KMS, Azure Key Vault, or Google Cloud KMS; store encrypted DEK beside ciphertext so rotation re-wraps keys rather than re-encrypting entire tables. Enable default encryption on object storage and managed databases; deny unencrypted uploads with policy where the platform supports it.

For searchable encrypted data, consider deterministic encryption (same plaintext always produces same ciphertext, allowing equality comparison) for low-cardinality fields, or use a blind index (hash of the plaintext, indexed separately) for lookups, understanding that this leaks some information about equality.

For GDPR erasure, design the system from the start to support pseudonymisation: store a stable internal user_id as a foreign key in all data tables rather than PII like email. On erasure, the PII record is deleted or nulled, but the user_id foreign key rows in analytics and audit tables remain intact (now pseudonymous). For event streams and append-only logs, implement crypto-shredding: encrypt user-specific events with a per-user encryption key; when erasure is requested, delete the user's encryption key from KMS — all their encrypted events become unreadable.

Inventory data flows with catalog tools; tag columns in schemas so encryption and masking policies apply automatically in ETL jobs. Coordinate with legal on retention schedules and subprocessors documented in privacy notices. Where OWASP logging guidance applies, scrub identifiers from diagnostic output while preserving correlation IDs for support.

Periodically sample production queries against sensitive tables and compare to access-policy intent—unexpected BI tools or support accounts reading restricted columns indicate control drift. Pair data-loss prevention rules on endpoints and email with database activity monitoring for defense in depth on exfiltration paths.

Common failure modes

  • Encrypted primary store, cleartext exports—nightly dumps to open buckets undo TDE.
  • DEKs beside rows without wrap—single-table compromise reveals keys and ciphertext.
  • PII in traces and access logs—weaker retention on logs leaks more than the database ACL.
  • Retention policies without jobs—infinite hoarding violates purpose limitation.
  • Immutable events without shred plan—erasure requests cannot be implemented post hoc.

Decision checklist

  • Is every dataset tagged with a classification driving control choice?
  • Are backups and replicas encrypted with the same rigor as primaries?
  • Are PAN/SSN/PHI fields tokenised or field-encrypted with KMS audit?
  • Is non-production fed only by masked or generated data?
  • Can erasure requests complete with auditable evidence?
  • Are sensitive-table queries logged to WORM storage?

Example use cases

  • Illustrative scenario — healthcare PHI: Column-level ciphertext for clinical notes with per-patient DEKs wrapped in AWS KMS; PHI access logged to immutable audit storage.
  • Case study — payment tokenisation: Processors such as Stripe store PANs in PCI-scoped vaults; merchants retain only tokens and last-four—pattern that shrinks PCI DSS scope for ecommerce platforms.
  • Illustrative scenario — GDPR erasure: Crypto-shred per-user keys in Cloud KMS plus pseudonymous analytics identifiers; erasure jobs emit completion events for privacy audit trails.
  • Illustrative scenario — multinational CRM: Region-scoped encryption keys with data residency tags enforced in API gateways; dynamic masking for offshore support contractors viewing EU customer records.
