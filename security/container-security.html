Security Architecture

Container Security

Securing containerised workloads: image scanning, hardened container configurations, Kubernetes RBAC, PodSecurity admission, Falco runtime security, and network policy enforcement.

⏱ 11 min read

What it is

Container security operates at four layers. The image layer scans OS packages, prefers minimal bases (Alpine, distroless), and signs artifacts to prove provenance. The runtime layer constrains Linux capabilities—non-root user, read-only root filesystem, dropped caps, seccomp and AppArmor profiles—so a container escape or RCE has limited host impact. The Kubernetes configuration layer governs RBAC, Pod Security admission, and how secrets reach pods. The monitoring layer uses Falco (CNCF) to watch syscalls and flag shells, odd egress, or credential file access indicative of active compromise.

Kubernetes RBAC governs who may call the API—human users and service accounts—and which verbs apply to which resources. Overly broad cluster-admin bindings are a common penetration-test finding. Pod Security admission enforces profiles (privileged, baseline, restricted) at schedule time so workloads cannot run as root, mount host paths, or request privileged mode even when manifests ask for it. The restricted profile is the usual north star for app namespaces; baseline blocks the riskiest settings while teams remediate. Admission controllers (Kyverno, OPA Gatekeeper) close the gap between “scanned in CI” and “running in the cluster” by enforcing registry allowlists, resource limits, and signature verification.

Why it exists

Container adoption outpaced secure defaults: privileged pods, mutable :latest tags, and CI pipelines with cluster-admin remain routine. Supply-chain attacks target registries and poisoned base layers. Because Kubernetes deploys change in seconds, a single misconfiguration can affect every replica. Containers share the host kernel—a kernel bug or privileged mount can expose the node and every pod on it. The Kubernetes API is itself an attack surface: a stolen service-account token with broad RBAC allows deploying privileged workloads or reading secrets cluster-wide.

Industry surveys (for example Datadog’s 2022 cloud report) cited most Kubernetes workloads still running as root and lacking resource limits—both magnify blast radius when an app is exploited. Runtime tools such as Falco catch behaviour that preventive controls miss after an attacker is already inside a pod.

When to use

  • Any production Kubernetes, ECS, or comparable platform processing customer or regulated data.
  • Multi-tenant clusters where contractual isolation between teams or customers is required.
  • Environments that must prove image provenance, signed digests, and enforced runtime constraints.
  • CI/CD pipelines shipping many images daily—admission policy is the last enforcement gate before pods run.
  • All containerised production workloads—scanning, non-root execution, and baseline RBAC are expected defaults.
  • High-assurance estates where Falco plus OPA or Kyverno adds defence in depth beyond standard hardening.

When not to use

  • Do not rely on namespace labels alone; pair them with NetworkPolicy and Pod Security enforcement.
  • Scanning without admission rules still lets vulnerable digests deploy under release pressure.
  • Some daemons (eBPF collectors, node agents) legitimately need elevated privileges—isolate them in dedicated system namespaces with tight RBAC rather than weakening tenant policies globally.

Typical architecture

Hardened images flow through signed CI builds into clusters where admission policy, Pod Security, and runtime monitors enforce the baseline.

Pros and cons

Pros

  • Immutable signed images reduce tampering between CI and the cluster.
  • Pod Security admission blocks dangerous pod specs even when developers commit insecure YAML.
  • NetworkPolicy contains east-west movement after an initial compromise.
  • Runtime detection surfaces attacker behaviour that static analysis cannot see.
  • Non-root containers with read-only filesystems limit malware persistence and privilege escalation after app-layer compromise.
  • Distroless images strip shells and package managers, shrinking attacker tooling inside a compromised container.

Cons

  • Policy sprawl without paved-road templates frustrates application teams.
  • Falco and similar tools need tuning to avoid alert fatigue; custom rules require deep knowledge of normal workload behaviour.
  • Distroless and read-only root filesystems complicate debugging unless you standardise ephemeral debug pods.
  • Least-privilege RBAC for every service account demands upfront analysis of required verbs and resources.
  • Shared clusters make blast-radius analysis harder when noisy neighbours affect SLOs.

Implementation notes

Build from minimal bases; scan in CI with fail-on-critical; sign with Cosign; pin image digests in manifests. Apply restricted Pod Security labels on production namespaces gradually—use warn/audit first, remediate violations, then enforce. Grant cluster-admin only with break-glass logging and time bounds. Pin bases by digest, not floating tags, and block latest in admission policies.

Enable Kubernetes audit logging; restrict kubelet and API server exposure. Route Falco or eBPF alerts to your SIEM. Default-deny NetworkPolicies with documented exceptions. Prefer External Secrets Operator or cloud secret stores over long-lived secrets in etcd unless encryption at rest is enabled and RBAC is tight. Review Cosign and admission policies whenever CI registries or build identities change.

Roll out controls progressively: baseline profile in warn mode cluster-wide, fix workloads, enforce baseline, then move namespaces toward restricted starting with less critical applications. Use pod-security.kubernetes.io/warn and audit alongside enforce to surface remaining violations before blocking schedules.

Avoid treating Kubernetes Secret objects as encrypted storage unless etcd encryption at rest is enabled—they are base64 by default. Prefer External Secrets Operator syncing from Vault or a cloud secrets manager; restrict which service accounts may read each secret via RBAC.

Common failure modes

  • Mutable latest tags—silent drift between environments and unrepeatable rollbacks.
  • cluster-admin for CI—a compromised pipeline owns the fleet.
  • Privileged debug pods left running—become persistent attacker tooling.
  • No resource limits—DoS via noisy neighbours or crypto miners.
  • Scan-only CI—critical CVE images still deploy when deadlines pressure teams.
  • Privileged containers in production: securityContext.privileged: true removes most isolation—equivalent to root on the host.
  • hostPath and docker.sock mounts: Mounting /etc or the Docker socket enables container breakout to the host.
  • Auto-mounted service account tokens: Pods default-mount API tokens; disable with automountServiceAccountToken: false when the workload does not need the Kubernetes API.
  • Cluster-admin CI/CD bindings: Namespace-scoped deploy roles limit damage if the pipeline is compromised.
  • Unscanned ubuntu:latest bases: Popular tags accumulate critical CVEs between refreshes.

Decision checklist

  • Are production images signed and verified at admission?
  • Do namespaces enforce at least baseline Pod Security (restricted where feasible)?
  • Is RBAC least-privilege with periodic access reviews?
  • Are NetworkPolicies default-deny with tested allow lists?
  • Does runtime monitoring alert on shells and suspicious egress?
  • Are cluster-admin actions audited to immutable storage?
  • Do all production pods declare CPU and memory requests and limits?

Example use cases

  • Illustrative scenario — multi-tenant platform: Restricted Pod Security, Kyverno registry allowlists, tenant NetworkPolicies, Falco on shell execution.
  • Kubernetes multi-tenant platform: Restricted profile on tenant namespaces; Kyverno enforces registry allowlists; NetworkPolicies block cross-tenant traffic; Falco alerts on shells in any tenant pod.
  • Financial services hardening: Distroless images, UID 65534, read-only root with tmpfs for /tmp and logs, seccomp RuntimeDefault; CIS scan output supports PCI evidence.
  • Supply-chain signing: CI signs with Cosign via GitHub OIDC; Kyverno rejects unsigned images at admission.
