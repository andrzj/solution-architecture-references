Security Architecture

Container Security

Securing containerised workloads: image scanning, hardened container configurations, Kubernetes RBAC, PodSecurity admission, Falco runtime security, and network policy enforcement.

⏱ 11 min read

What it is

Container security protects images, runtimes, orchestrators, and workloads from build through production. Containers share a host kernel, so compromise of one workload can threaten neighbors without deliberate isolation and least privilege. The practice spans image security (minimal bases, CVE scanning, Cosign/Sigstore signatures and SLSA-style provenance at admission); runtime hardening (non-root, read-only root filesystem, dropped capabilities, seccomp/AppArmor); Kubernetes configuration (RBAC, PodSecurity profiles, secrets handling aligned with the CIS Kubernetes Benchmark); and runtime detection (Falco syscall rules for shells, unexpected egress, credential access).

Kubernetes RBAC (Role-Based Access Control) controls access to the Kubernetes API — which users and service accounts can create, read, update, or delete which Kubernetes resources. Misconfigured RBAC (overly permissive roles, cluster-admin granted broadly) is a primary vector for Kubernetes cluster compromise. PodSecurity admission (the successor to PodSecurityPolicy) enforces a set of pod-level security constraints at admission time, preventing workloads from running as root, mounting host filesystems, or using privileged mode, even if the deployment manifest requests it. The three standard profiles are privileged (no restrictions), baseline (prevents the most dangerous configurations), and restricted (most security, requires non-root, drops capabilities, read-only root filesystem).

Why it exists

Containers collapse isolation assumptions: shared kernels, mutable images, and powerful orchestrator APIs expand blast radius when workloads run as root or hold cluster-admin tokens. A single privileged pod or hostPath mount can pivot to the node and neighbor pods. Industry benchmarks (CIS Kubernetes, OWASP container guidance) exist because default cluster posture is permissive—wide RBAC, automounted service account tokens, and allow-all pod networking. Runtime detections such as Falco close the loop when preventive controls fail.

Supply-chain incidents show that vulnerable base images ship to production faster than patch cycles; signing and admission verification are now baseline expectations for regulated tenants.

Kubernetes control planes expose high-value APIs; compromised credentials there bypass application-layer controls entirely. Namespace isolation, admission controllers (Kyverno, OPA Gatekeeper), and audit logging of API mutations align with CIS and NIST supply-chain guidance for software artifacts. Treat cluster bootstrap and node images as part of the same trust boundary as application containers.

When to use

  • Production container fleets—scan, sign, non-root execution, and least-privilege RBAC are mandatory.
  • Shared Kubernetes platforms serving multiple teams or customers—namespace isolation plus NetworkPolicies.
  • Regulated workloads needing admission policy, provenance checks, and runtime syscall monitoring.
  • CI/CD pipelines that must block critical CVEs before images reach registries.
  • Platform engineering teams operating internal Kubernetes-as-a-service for product squads with different trust levels.
  • Edge or on-prem clusters where air-gapped registries and offline vulnerability feeds are part of the threat model.

When not to use

  • Privileged node agents (CNI, CSI, observability) may require elevated profiles—isolate them in system namespaces with tight RBAC rather than relaxing standards for application tiers.

Typical architecture

Security threads build → deploy → operate: minimal signed images, admission enforcement, hardened pod specs, network policy, and continuous syscall monitoring mapped to CIS and NIST supply-chain practices.

Pros and cons

Pros

  • Non-root, read-only root filesystems deny persistence and local privilege escalation in many exploit chains.
  • PodSecurity admission blocks dangerous specs before they schedule—even when manifests slip through review.
  • Runtime rules catch shell spawns and unexpected egress after preventive controls fail.
  • Minimal signed images shrink the attacker toolkit after initial code execution.

Cons

  • Distroless and restricted profiles complicate break-fix unless debug pods are standardised.
  • Read-only roots force explicit volume design for temp and cache paths.
  • Falco and similar tools need continuous tuning to balance noise versus coverage.
  • Least-privilege RBAC per workload is labor-intensive without automated permission mining.

Implementation notes

Implement container security controls progressively using the Kubernetes PodSecurity standard levels: start by applying baseline (blocks the most dangerous configurations) to all namespaces in warn mode to identify violations without breaking workloads, fix violations, then switch to enforce mode. Then apply restricted incrementally namespace by namespace, starting with least-critical workloads and working toward production. Use the pod-security.kubernetes.io/warn and pod-security.kubernetes.io/audit labels alongside enforce to identify remaining violations.

For Kubernetes secrets management, avoid storing sensitive configuration in Kubernetes Secrets directly unless the cluster has etcd encryption at rest enabled — Kubernetes Secrets are base64 encoded, not encrypted, by default. Use an external secrets operator (ESO) to sync secrets from Vault or AWS Secrets Manager into Kubernetes Secrets, with the source of truth in a properly encrypted secrets manager rather than in etcd. Configure RBAC to restrict which service accounts can read which secrets.

Scan images in CI with Trivy or Grype and block critical CVEs before push. Sign release digests with Cosign via Sigstore OIDC; admission controllers should verify signatures and optionally SLSA provenance attestations. Export CIS Kubernetes Benchmark scan results periodically as audit evidence for regulated workloads.

Define pod security standards per namespace label: start with audit and warn modes, remediate workloads violating restricted profiles, then enforce. Integrate image policy with registry allowlists so only CI-promoted digests can run in production. Pair Falco with SIEM forwarding so container events correlate with cloud audit trails during incident response.

Review Linux capabilities granted to DaemonSets and init containers during change management—capabilities persist across restarts and are easy to overlook in Helm chart upgrades. Align worker node hardening (CIS benchmarks, immutable OS images) with pod-level controls so attackers cannot pivot from a soft node to a strict pod boundary.

Common failure modes

  • Privileged production pods—effectively host root from a single workload spec typo.
  • Dangerous hostPath mounts including Docker socket paths enabling cluster takeover.
  • Automounted API tokens on workloads that never call the Kubernetes API—lateral movement enablers.
  • Cluster-admin CI accounts—pipeline compromise equals full cluster compromise.
  • Floating :latest tags without digest pinning or CVE gates.

Decision checklist

  • Do CI pipelines block critical/high CVEs on promoted images?
  • Are application pods non-root with read-only root filesystems where feasible?
  • Are capabilities dropped by default with explicit adds only?
  • Is PodSecurity restricted or baseline enforced on prod namespaces?
  • Is RBAC namespace-scoped with automount disabled unless required?
  • Does runtime monitoring alert on shell execution and suspicious egress?

Example use cases

  • Illustrative scenario — multi-tenant platform: Restricted PodSecurity, Kyverno registry allowlists, NetworkPolicies, Falco on shell execution.
  • Illustrative scenario — regulated hardening: Distroless, non-root, read-only root FS; CIS benchmark scans as PCI audit evidence.
  • Illustrative scenario — Sigstore admission: Cosign keyless CI signing; Kyverno verifies signatures before scheduling pods.
  • Illustrative scenario — batch analytics: Spark jobs on isolated nodes with read-only mounts, dedicated service accounts, and network policies allowing egress only to encrypted object storage endpoints.
