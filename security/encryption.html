Encryption at Rest & Transit

Baseline cryptographic controls for data at rest and in transit—AES-256, TLS 1.3, and cloud KMS envelope encryption aligned with NIST key-management and TLS guidance.

⏱ 12 min read

What it is

Encryption at rest and in transit pairs symmetric protection for stored bits with TLS for data moving across networks. AES-256 in authenticated modes (GCM) encrypts volumes, object storage, backups, and snapshots. TLS 1.2+ (prefer TLS 1.3 per NIST SP 800-52 Rev. 2) secures client-to-service and service-to-service hops on untrusted paths.

Cloud KMS services (AWS KMS, Azure Key Vault, Google Cloud KMS) hold customer master keys and support envelope encryption—per-object data keys wrapped by CMKs per NIST SP 800-57—so applications never embed long-lived secrets.

Why it exists

Regulations and customer contracts assume stolen disks or captured packets do not immediately reveal plaintext. Volume encryption alone does not stop application-layer leaks, but it closes physical and misconfiguration paths. Cryptography without lifecycle governance—keys in repos, shared passwords, never-rotated CMKs—fails audits. KMS audit logs and TLS configuration evidence prove controls operate in production.

When to use

  • Customer, employee, financial, and health records at rest—including backups and replicas.
  • Any network path crossing tenants, internet, or shared backbone without private trust.
  • Field-level encryption when column sensitivity exceeds blanket volume encryption.

When not to use

  • Public marketing assets where encryption adds cost without measurable risk reduction.
  • Never roll custom crypto—use FIPS-validated libraries and platform TLS stacks.

Typical architecture

Clients terminate TLS at the edge; persisted objects use platform volume encryption with optional field envelopes wrapped by KMS.

Pros and cons

Pros

  • Stolen media and mis-published buckets yield ciphertext.
  • TLS mitigates passive capture on untrusted networks.
  • KMS centralises key rotation and audit.
  • Platform defaults make baseline encryption low-friction.

Cons

  • Encrypted data still readable to authorized app roles—pair with access control.
  • KMS outages block decrypt unless caching designed carefully.
  • TLS misconfiguration (weak ciphers, expired certs) gives false confidence.
  • Field encryption complicates search and reporting.

Implementation notes

Enable default encryption on object and block storage; require TLS on load balancers and service mesh. Use ACM or managed certs with auto-renewal; disable TLS 1.0/1.1. For sensitive columns, envelope-encrypt with data keys per record or tenant; store wrapped keys alongside ciphertext.

Restrict KMS decrypt to workload IAM roles; enable CloudTrail or equivalent for every key use. Test restore from encrypted backups. Document cipher suites and HSTS alongside application releases.

Common failure modes

  • Keys in source control—bypasses all at-rest protection.
  • TLS termination only at edge—plaintext inside VPC after compromise.
  • Unencrypted snapshots—cloned volumes leak data.
  • Shared CMK without IAM discipline—one role decrypts all tenants.
  • Expired certificates—outages push teams to disable TLS temporarily.

Decision checklist

  • Is at-rest encryption enabled for all production datastores and backups?
  • Does TLS 1.2+ cover client and critical east-west paths?
  • Are CMKs scoped with least-privilege IAM and audit logging?
  • Are certificates renewed automatically before expiry?
  • Are sensitive fields envelope-encrypted where required?
  • Was backup restore from encrypted media tested this year?

Example use cases

  • Illustrative scenario — SaaS multi-tenant DB: RDS encryption with CMK; TLS to app tier; SSN column envelope-encrypted per tenant key.
  • Illustrative scenario — object storage: S3 default encryption SSE-KMS; bucket policy denies unencrypted puts.
  • Illustrative scenario — service mesh: mTLS between microservices; edge TLS 1.3 with OCSP stapling.
