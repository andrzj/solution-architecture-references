Security Architecture

Defense in Depth

Layered security controls spanning perimeter, network, host, application, and data layers so that the compromise of any single layer does not result in a full breach.

⏱ 10 min read

What it is

Defense in Depth (DiD) layers independent security controls so that defeating one barrier does not expose the entire system. Each layer addresses a different class of failure: misconfiguration, vulnerability, insider abuse, or stolen credentials. The classical stack runs from perimeter (DDoS scrubbing, WAF, CDN edge filters) through network (VPC segmentation, security groups, east-west firewalls), host or container (hardened images, patching, EDR), application (validation, OWASP-aligned secure coding, dependency scanning), and data (encryption, tokenisation, masking, DLP). Modern programmes add an explicit identity layer—MFA, conditional access, privileged access management—because stolen identity bypasses network rules without touching servers.

DiD assumes assume breach: designers expect at least one layer to fail eventually and invest in detection, response, and containment. NIST's glossary describes defense in depth as complementary safeguards that implement multiple protection mechanisms. In cloud-native estates the layers shift shape—perimeter becomes API gateway and WAF in front of serverless functions—but the principle persists: no single control is the last line of defence.

Why it exists

Perfect security is unattainable. Firewalls leak through rule drift; patches ship late; developers introduce OWASP Top 10 flaws despite training; encryption fails when keys sit beside data. Attackers chain small weaknesses—a SSRF in an internal tool, a overly broad IAM role, an unpatched sidecar—into full compromise. DiD raises the cost of that chain by requiring multiple independent successes. It also multiplies detection chances: malware that evades the perimeter may still trigger EDR behaviour rules or DLP on egress.

Compliance frameworks encode the same idea. PCI DSS expects firewall, access control, vulnerability management, and encryption together—not any one in isolation. HIPAA safeguards map to administrative, technical, and physical controls spanning layers. Architects use DiD vocabulary to explain why buying only a WAF does not satisfy risk reviewers who ask what happens when the WAF is bypassed.

When to use

  • All production systems handling customer or regulated data—DiD is baseline hygiene, not a luxury control.
  • Internet-facing products with diverse threat actors and automated scanning.
  • Environments where a single control failure would be catastrophic (payments, healthcare records, credentials).
  • Organisations mapping controls to MITRE ATT&CK or CIS Critical Security Controls for coverage reporting.

When not to use

  • DiD always applies in principle; the question is depth and cost proportionate to threat. Avoid security theatre—disabled WAF rules, encryption with keys in source code, or logging without alerting are layers on paper only.
  • Do not duplicate the same control type expecting depth—three overlapping antivirus agents on one host add operational pain without independent failure modes.

Typical architecture

Cloud-native DiD stacks thread traffic through edge protection, segmented networks, hardened compute, application controls aligned with OWASP, and encrypted data stores—with identity policies binding each hop.

Pros and cons

Pros

  • Increases attacker effort and time on target, improving odds of detection.
  • Single-layer failures (0-day, misconfiguration) rarely become total data loss events.
  • Multiple telemetry sources feed SIEM correlation for multi-stage attack visibility.
  • Maps cleanly to PCI DSS, HIPAA, ISO 27001, and CIS control families.
  • Reduces insider and credential-theft impact when data and identity layers hold.

Cons

  • Operational overhead grows with agents, policies, and patch windows per layer.
  • Uncorrelated alerts from siloed tools cause fatigue without central analytics.
  • Commercial tooling at every layer is expensive; prioritisation discipline is required.
  • Checkbox deployments—controls present but never tested—create false confidence.

Implementation notes

Prioritise from the data layer outward: classify sensitive fields, encrypt at rest with KMS-managed keys, enforce least-privilege database IAM, then harden applications against OWASP injection and broken access control, then hosts, network, and perimeter. Use a unified posture dashboard (Security Hub, Defender for Cloud, Security Command Center) to see misconfigurations across layers instead of hopping consoles.

Map detections to MITRE ATT&CK techniques and note gaps—if you detect initial access but not lateral movement, invest in network segmentation logging and identity analytics. Pair DiD with threat hunting and red teaming to prove layers work under adversarial simulation, not only in compliance PDFs. Automate patch and image rebuild pipelines so the host layer does not lag months behind CVE disclosure.

Depth is intentional overlap: an exploited web flaw should still meet MFA, least-privilege IAM, segmented networks, and tamper-evident logging before crown-jewel data. Avoid checkbox stacking—two broken layers that share the same blind spot do not double security. Measure coverage with purple-team exercises and control frameworks, then fund the weakest layer in the kill chain you model in threat modeling.

Document which layers are compensating controls versus primary—auditors ask why you still need MFA when the WAF blocks SQLi. Tie each layer to an owner and a health metric so one silent failure does not collapse the whole strategy.

Retest detective controls after major architecture migrations—they often stop shipping logs quietly.

Common failure modes

  • Hard shell, soft centre: Strong perimeter, flat internal network, no app-layer authorisation—one phished VPN session owns the estate.
  • Detection-only WAF: Rules log OWASP signatures but never block—attackers iterate until a bypass succeeds.
  • Stale patch debt: Container base images months behind; host layer negated by known exploits.
  • Over-privileged workload roles: Application compromises become database admin via attached IAM policies.
  • Uncorrelated layer telemetry: Each tool alerts in isolation; multi-hop attacks stay invisible until exfiltration.

Decision checklist

  • Are meaningful controls present at perimeter, network, host, application, data, and identity layers?
  • Does each preventive control enforce (block/quarantine), not only log?
  • Do layer events aggregate in a SIEM with correlation rules?
  • Has coverage been mapped to MITRE ATT&CK with documented gaps?
  • Are assume-breach practices (hunting, tabletop exercises, red team) scheduled?
  • Are controls tested on a cadence—not only at annual audit time?

Example use cases

  • Illustrative scenario — Northwind Commerce checkout: Edge WAF blocks OWASP injection patterns, VPC isolates payment microservices, containers run as non-root with read-only roots, application code uses parameterised queries and server-side price validation, cardholder data never touches application disks (tokenised via PSP).
  • Healthcare SaaS: Network segmentation for PHI tenants, field-level encryption, audit logging at API and database layers, MFA for workforce access per HIPAA technical safeguards.
  • Financial batch platform: PCI scope reduction via segmented CDE, HSM-backed keys, file integrity monitoring on batch hosts, and dual-control PAM for operator access.
