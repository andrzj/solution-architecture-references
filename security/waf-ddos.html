Security Architecture

WAF & DDoS Protection

Defending internet-facing entry points from application-layer attacks and volumetric floods.

⏱ 11 min read

What it is

A Web Application Firewall (WAF) inspects HTTP and HTTPS traffic at the edge and applies rules to block or challenge requests that match known attack signatures (SQL injection, cross-site scripting, path traversal) or custom policies (geo blocks, IP reputation, bot scores). A DDoS protection layer absorbs or scrubs volumetric and protocol floods — typically at CDN anycast scrubbing centers or cloud DDoS services — before traffic reaches your origin.

WAFs address application-layer (L7) abuse: credential stuffing on login, scraping, and crafted API payloads. DDoS services address network/volumetric (L3/L4) floods and large L7 floods that would overwhelm origin capacity even when each request is “valid.” Together they form the outer shell of Defense in Depth; they do not replace authentication, authorisation, or input validation in application code.

Why it exists

Internet-facing endpoints are probed continuously by automated scanners. Origin auto-scaling alone cannot distinguish a flash crowd from a botnet — scaling up during an attack raises cost without guaranteeing availability. Managed WAF rule packs (for example OWASP Core Rule Set) and provider bot intelligence distribute the cost of tracking new CVEs and attack variants across customers, which individual product teams cannot match.

Hiding origin IP addresses behind a CDN and scrubbing center also prevents attackers from bypassing edge controls with direct volumetric floods against a small number of origin addresses.

When to use

  • Any internet-facing website, API, or BFF that accepts unauthenticated or lightly authenticated traffic.
  • High-risk paths — login, password reset, checkout, token endpoints — with stricter rate limits and bot management.
  • Regulated environments (PCI DSS) that expect managed rule sets and documented edge protection.
  • Applications subject to scrape or inventory-harvesting where bot scores and CAPTCHA challenges reduce abuse.

When not to use

  • Pure internal east-west service mesh traffic — enforce mTLS and mesh policy instead of a perimeter WAF.
  • As the only access control — WAF pattern matching cannot understand object-level authorisation or business logic flaws.
  • Replacing secure coding — SQLi rules help, but parameterised queries remain mandatory.

Typical architecture

Terminate TLS at the CDN/WAF, apply managed and custom rules, then forward only sanitised traffic to the origin over a private link or locked-down security group. Origin must not accept traffic except from the edge provider’s IP ranges.

Pros and cons

Pros

  • Managed rule updates track emerging web attack patterns without per-service patches.
  • Edge rate limiting and bot management scale beyond what a single origin can enforce.
  • Geo, ASN, and IP reputation blocks support rapid incident response.
  • Centralised logging gives forensic visibility before traffic hits application pods.

Cons

  • False positives on JSON APIs and mobile clients require tuning and exclusion lists.
  • Extra network hop adds latency unless WAF is integrated with the CDN PoP.
  • Cost grows with request volume and advanced bot features.
  • Complex custom rules are hard to test and may introduce regex denial-of-service risk.

Implementation notes

Deploy OWASP Core Rule Set in count (observe) mode first; review false positives on real API traffic; add targeted exclusions for known-safe JSON fields; then switch matching rules to block. Separate rule groups for HTML apps versus JSON APIs — CRS defaults assume form posts.

Pair WAF rate limits with application-level quotas and authentication. Use bot scores to challenge only suspicious traffic, not every user. For DDoS, document runbooks: who can enable aggressive geo blocks, when to enable “under attack” mode, and how to communicate to customers.

Ensure every public hostname — including marketing subdomains, legacy domains, and API gateways — points through the same edge stack. Monitor certificate transparency and DNS for shadow hostnames that leak the origin.

Layer 3/4 volumetric attacks need upstream scrubbing and anycast absorption; application-layer floods need WAF rate rules, bot scores, and challenge pages tuned to avoid blocking legitimate API clients. Start rules in count or log mode, promote to block with SLA review—false positives on JSON APIs are expensive. Place rate limits at the edge for anonymity, and again at the API gateway keyed by OAuth client or API key so shared IPs cannot bypass quotas. VPC-level security groups and segmentation are in network security.

Rehearse origin failover quarterly: if the CDN or scrubbing contract cannot absorb an attack, you need a documented maintenance page and comms path.

Common failure modes

  • Bypass via alternate hostnames — staging or legacy DNS records expose origin without WAF.
  • Permanent log-only mode — rules never promoted to block after tuning fatigue.
  • Regex denial of service — catastrophic backtracking in custom WAF rules stalls the edge.
  • Origin IP leakage — historical DNS, mail headers, or error pages reveal direct attack targets.
  • Over-broad geo blocks — incident response blocks entire regions including paying customers.
  • WAF as sole SQLi defence — application still vulnerable when rules are disabled or bypassed.

Decision checklist

  • Are all internet-facing hostnames routed through CDN/WAF with no direct origin access?
  • Is OWASP CRS tuned with API-specific exclusions after a count-mode observation period?
  • Are authentication endpoints rate-limited and bot-managed separately from static assets?
  • Is there a documented DDoS playbook with roles and communication templates?
  • Are origin security groups or firewalls limited to edge provider address ranges?
  • Are WAF logs shipped to SIEM with alerts on block-rate anomalies?

Example use cases

  • Illustrative scenario — e-commerce checkout: Bot control on checkout paths; sudden scraper spike triggers managed challenge without throttling legitimate card traffic.
  • Illustrative scenario — public API: Per-API-key rate limits at the edge plus geo allowlist for partner ASNs; CRS tuned to avoid blocking JSON bodies.
  • Case study — AWS Shield Advanced: Large L3/L4 floods mitigated at the network edge while AWS WAF blocks application-layer probes against ALB targets.
  • Illustrative scenario — media publisher: CDN caching absorbs flash crowds; WAF blocks aggressive scrapers while cache hit ratio stays high.
