Security Architecture

Secure SDLC

Embedding security across the software development lifecycle: shift-left practices, SAST/DAST/SCA tooling, security gates in CI/CD, threat modelling in design, security champions, and penetration testing cadence.

⏱ 10 min read

What it is

A secure software development lifecycle (Secure SDLC) embeds security activities in requirements, design, implementation, verification, release, and operations—not only in a final gate. Shift-left runs SAST and SCA on pull requests, models threats before coding, and trains security champions inside product teams. Verification levels in the OWASP ASVS give measurable targets for authentication, session handling, access control, and input validation.

Tooling categories include SAST (static code analysis), DAST (black-box HTTP probing in staging), SCA (dependency and license risk), IaC scanners (Checkov, Terraform Sentinel), and periodic penetration tests that validate what automation missed. Threat modelling during design uses frameworks such as STRIDE on data-flow diagrams so mitigations become requirements before code exists. Secure SDLC ties to supply chain security through SBOM generation and signed release artifacts.

Why it exists

Remediation cost rises sharply the later a flaw is found—industry studies cite order-of-magnitude jumps from design to production. Pre-release-only reviews create schedule pressure to waive findings. Automated PR gates and design-time threat modelling catch SQL injection, leaked secrets, and authorisation gaps when fixes are small diffs. Microsoft's SDL and OWASP SAMM show measurable vulnerability reduction when practices are consistent rather than heroic.

A pen test or security review only at release discovers issues after weeks of sprint work, forcing expensive rework. Shift-left controls surface findings minutes after a PR opens, when a one-line change is enough. NIST cost models illustrate the same curve: design-time fixes are orders of magnitude cheaper than post-release incidents and regulator notification.

When to use

  • All product engineering teams—baseline SAST, SCA, and secrets scanning are universal hygiene.
  • Internet-exposed or regulated data paths need threat modelling, DAST, and annual third-party pen tests.
  • SOC 2, ISO 27001, FedRAMP, and customer security questionnaires expect documented SDLC controls.
  • Platform teams shipping shared libraries or internal frameworks where one defect affects many consumers.

When not to use

  • Maturity scales with risk—toy prototypes may defer DAST until external exposure, but never skip secrets scanning on shared repos.
  • Do not treat “we run a scanner” as SDLC without fixing SLAs, ownership, and design reviews.

Typical architecture

Threat models and scanner gates thread through CI stages before signed artifacts promote toward production.

Pros and cons

Pros

  • Catches vulnerabilities when change cost is lowest.
  • Security champions scale expertise without bottlenecking every PR on AppSec.
  • Pipeline gates produce audit evidence for change-management clauses.
  • Threat models document abuse cases alongside happy-path stories.
  • Combines with SBOM and signing for end-to-end assurance narratives.

Cons

  • False positives from SAST require tuning investment.
  • Tool sprawl without integration creates alert fatigue.
  • DAST against staging can be slow and flaky without stable test data.
  • Champion programmes fail without executive sponsorship and time allocation.

Implementation notes

Anchor releases to OWASP ASVS levels proportional to risk. Start with high-value, low-friction controls: GitHub Advanced Security or Semgrep on PRs, Dependabot or Snyk for CVEs, gitleaks on pre-commit, and a lightweight STRIDE session for net-new features. Block merges on critical findings; time-box medium issues with tracked exceptions.

Integrate IaC scanning in Terraform pipelines; run DAST weekly against staging with realistic auth flows. Schedule annual external pen tests and targeted tests before major releases. For threat modelling, use data-flow diagrams with trust boundaries and record mitigations as tracked requirements. Publish SBOMs per release and wire defect metrics to engineering dashboards so security is visible like reliability SLOs.

Common failure modes

  • Scan without enforce—tools report criticals but merges proceed under deadline pressure.
  • SAST in warn-only mode forever—findings become background noise.
  • No false positive suppression process—developers disable or bypass scanners.
  • Threat models filed once—architecture drifts without updating mitigations.
  • Security review only at release—bottlenecks and pressure to ship known gaps.
  • Champions burned out—volunteers lack bandwidth or recognition.
  • Pen test findings never remediated—reports become compliance theatre.

Decision checklist

  • Do PRs run SAST, SCA, and secrets scans with defined severity SLAs?
  • Are abuse cases and STRIDE notes stored with design docs for new features?
  • Is there a named security champion per squad with allocated time?
  • Does staging receive scheduled DAST with authenticated scenarios?
  • Are pen test findings tracked to closure with regression tests?
  • Does each release publish an SBOM and security attestation where required?

Example use cases

  • Illustrative scenario — fintech squad: CodeQL blocks SQLi patterns; OWASP ZAP runs nightly on staging; annual PCI pen test covers ASVS L2 controls.
  • Illustrative scenario — platform team: Paved-road pipeline enforces Checkov on Terraform and signs container images before any consumer deploys.
  • Illustrative scenario — healthcare SaaS: Threat models reference HIPAA safeguards; champions review every PHI-related epic in design review.
  • Illustrative scenario — payment feature: Mandatory champion review and a two-hour STRIDE session find a missing authorisation check on an amount field before implementation starts.
