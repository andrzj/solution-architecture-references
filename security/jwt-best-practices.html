Security Architecture

JWT Best Practices

Secure JWT issuance, validation, rotation, and anti-patterns to avoid.

⏱ 10 min read

What it is

Example: an API gateway validates a JWT's RS256 signature using the IdP JWKS, checks exp and aud, then forwards trusted claims to upstream services.

Why it exists

JWTs enable stateless verification at the edge, but incorrect validation causes critical vulnerabilities. Documented best practices reduce alg confusion, replay, and scope leakage.

When to use

  • OIDC ID tokens and OAuth access tokens.
  • Short-lived service credentials between trusted issuers.
  • Signed webhooks with embedded metadata.

When not to use

  • Long-term session storage — use server-side sessions instead.
  • Carrying large PII payloads — prefer references.

Typical architecture

Pros and cons

Pros

  • Stateless verification scales horizontally at gateways and mesh proxies.
  • Standard claims (sub, scope, groups) interoperate across polyglot stacks.
  • JWKS rotation and multiple active keys are well supported by major IdPs.
  • Short TTL tokens limit blast radius when leakage occurs.

Cons

  • No built-in revocation — compromised tokens work until expiry unless extra controls exist.
  • Verbose tokens increase latency and may exceed header size limits.
  • Symmetric secrets do not scale across many verifying services.
  • Developers may treat decoded payloads as trusted without verifying signatures.

Implementation notes

Use a maintained JWT library; never implement signature verification by hand. Allowlist algorithms explicitly; reject none and unexpected HS256 on APIs that should only accept asymmetric keys from the IdP. Pin expected iss to the discovery document URL or canonical issuer string; pin aud (or resource-specific audience) to this API resource — tokens minted for another API must fail closed.

Cache JWKS with TTL aligned to Cache-Control from the issuer, but refresh on unknown kid to handle key rotation without downtime. Keep access token lifetime in the low minutes; pair with refresh token rotation and reuse detection at the authorization server. For browsers, avoid storing JWTs in JavaScript-accessible storage; a BFF holds tokens server-side.

When logs need correlation, log jti or a hash prefix — never the full bearer token. If using JWE, remember encryption does not replace signature validation on nested signed JWTs. Prefer opaque access tokens plus introspection when clients cannot be trusted to keep JWTs confidential.

Common failure modes

  • Algorithm confusion: accepting HS256 with the public key mistakenly used as HMAC secret.
  • Skipped audience validation: API accepts tokens intended for a different resource server.
  • Stale JWKS after rotation: validators cache only the old kid and reject valid tokens or, worse, disable verification temporarily.
  • Logging bearer tokens in APM, ingress logs, or error reports.
  • Embedding secrets or PII in claims that traverse browsers or third-party analytics.
  • Treating scopes as authorisation without server-side checks on object ownership.

Decision checklist

  • Are allowed signing algorithms explicitly allowlisted?
  • Are iss, aud, exp, and nbf validated on every request?
  • Does JWKS fetching handle key rotation (unknown kid refresh)?
  • Are access token TTLs under 15 minutes for internet-facing APIs?
  • Are refresh tokens rotated with reuse detection at the authorization server?
  • Are JWTs excluded from URLs, analytics, and client-side persistent storage?

Example use cases

  • Illustrative scenario — API mesh: Envoy JWT filter validates per-route audiences; upstream pods trust only mTLS peer identity and normalised claim headers.
  • Illustrative scenario — internal microservices: SPIFFE JWT-SVIDs with five-minute TTL authenticate east-west calls; SPIRE rotates keys automatically.
  • Case study — Stripe Connect: Partners verify Stripe-signed JWTs on Connect webhooks using published keys and narrow claim semantics.
  • Illustrative scenario — partner webhook: HMAC or JWT with fixed aud and iss; receiver rejects replays via jti idempotency store.
