Security Architecture

Security Headers

HTTP response security headers: Content-Security-Policy, HSTS, X-Frame-Options, CORS configuration, COOP/COEP isolation, and violation reporting endpoints.

⏱ 9 min read

What it is

HTTP security headers are outbound directives that tell browsers how to load, frame, and connect to your application. They form a client-side enforcement layer complementary to server-side validation—when reflected XSS slips through, Content-Security-Policy (CSP) can still block execution. Core headers include HSTS (force HTTPS), X-Content-Type-Options: nosniff (block MIME sniffing), frame-ancestors / X-Frame-Options (clickjacking), and Referrer-Policy (limit URL leakage).

Modern isolation headers—Cross-Origin-Opener-Policy (COOP), Cross-Origin-Embedder-Policy (COEP), and Cross-Origin-Resource-Policy (CORP)—enable cross-origin isolation required for SharedArrayBuffer and mitigate Spectre-class side channels. Permissions-Policy disables sensitive browser APIs (camera, geolocation, payment) your app does not need. Correct CORS configuration remains part of API security: browsers enforce same-origin unless you explicitly and safely delegate.

The OWASP Secure Headers Project publishes recommended values for production baselines. CIS benchmarks for web servers and CDNs call out HSTS, CSP, and framing controls as low-cost hardening that applies even when legacy application code cannot be refactored quickly.

Why it exists

Many attacks exploit browser behaviour—mixed content downgrade, MIME confusion, clickjacked admin clicks, token theft via Referer—not application logic bugs alone. Headers ship defences that apply uniformly across frameworks and legacy pages when set at CDN or reverse proxy layers. OWASP Secure Headers guidance and MDN document baseline sets suitable for production without waiting for every codebase path to be hardened.

CSP can neutralise XSS impact even when an attacker injects script—the browser refuses execution when the source is not allowlisted. HSTS prevents SSL stripping on hostile networks. These controls cost little to deploy centrally but materially reduce well-understood client-side attack classes.

OWASP ASVS verification chapters reference CSP, HSTS, and cookie flags as measurable requirements—headers give auditors artefact-free evidence via automated scans (Mozilla Observatory, securityheaders.com) rather than manual code walkthroughs of every template.

When to use

  • Every browser-facing HTML, API, and static asset response should carry transport and baseline headers.
  • High-value sessions (banking, healthcare, admin consoles) need strict CSP and framing deny policies.
  • Multi-origin SPAs and APIs require deliberate CORS allowlists—not wildcards with credentials.
  • WebAssembly threading or SharedArrayBuffer workloads require COOP+COEP cross-origin isolation.

When not to use

  • Do not enforce strict CSP without a migration plan—use Content-Security-Policy-Report-Only first to collect violations.
  • Avoid HSTS preload until every subdomain serves valid HTTPS—preload is difficult to unwind.
  • Server-to-server API calls ignore CORS; do not add permissive CORS “just in case” on internal-only APIs.

Typical architecture

Edge proxies attach transport and browser policy headers on every response before HTML or API payloads reach clients.

Pros and cons

Pros

  • CSP nonces and hashes neutralise many XSS payloads even after injection.
  • Infrastructure-level header policies cover all routes including third-party plugins.
  • HSTS and upgrade-insecure-requests reduce sslstrip and mixed-content risk.
  • CSP reporting surfaces attempted injections and misconfigured asset hosts.

Cons

  • Strict CSP breaks legacy inline scripts, tag managers, and some CMS patterns.
  • Per-request nonces complicate edge caching unless templates regenerate at origin.
  • CORS mistakes are common—overly broad origins expose APIs to malicious sites.
  • COEP can block third-party widgets lacking CORP headers until vendors cooperate.
  • HSTS preload is a long-term commitment if HTTPS coverage is incomplete.

Implementation notes

Define headers in CDN response policies, ingress controllers, or API gateways so application teams cannot omit them on new endpoints. Roll CSP from report-only to enforce over several sprints; fix violations before blocking. Prefer nonces over unsafe-inline; externalise scripts where possible.

Generate a cryptographically random nonce per HTML response and pass it to templates so inline scripts carry a matching nonce attribute—injected script without that nonce fails CSP. Include base-uri 'self', form-action 'self', and frame-ancestors 'none' (or an explicit allowlist) on high-value apps. Use upgrade-insecure-requests during HTTPS migration.

Stage HSTS with short max-age, validate all subdomains, then increase duration before considering preload list submission. For multi-origin APIs, validate the Origin header against an allowlist and echo the matched origin—never combine Access-Control-Allow-Origin: * with credentials. Restrict Access-Control-Allow-Methods and headers to what the API actually uses.

Pipe CSP violation reports to a collector or SIEM; spike in script-src violations often precedes active XSS probing. Test with securityheaders.com, Mozilla Observatory, or CSP Evaluator before production enforce; add regression tests in CI that curl key routes and assert header presence.

Deploy CSP with per-request nonces and strict-dynamic so trusted bootstrap scripts can load dependencies without endless host allow lists. Submit domains to the HSTS preload list only after max-age and includeSubDomains are stable. Use frame-ancestors instead of legacy X-Frame-Options where browsers permit. Audit CORS: wildcard origins with credentials enabled are toxic. Set cookies with Secure, HttpOnly, and appropriate SameSite; prefer __Host- prefixed session names on apex hosts to block subdomain override attacks.

Roll out CSP in report-only mode on one subdomain first; promote to enforce only after violation volume is near zero for a full release cycle.

Common failure modes

  • CSP with unsafe-inline: Attackers who achieve HTML injection can still run arbitrary script because the browser permits inline execution.
  • Wildcard CORS on authenticated APIs: A malicious site can trigger credentialed fetches and read JSON responses when Allow-Origin echoes attacker-controlled origins incorrectly.
  • HSTS missing on API hostnames: Mobile clients and scripts may hit plain HTTP on first request, enabling sslstrip on captive portals.
  • Framing allowlists too broad: Partner domains that allow embedding your admin UI enable clickjacked transfers or role changes.
  • No monitoring of CSP reports: Probing continues until chargebacks or account takeover alerts surface the issue.
  • Analytics workarounds: Tag managers push teams toward unsafe-inline instead of nonce-based or hosted-script allowlists.
  • Duplicate or conflicting headers: CDN and origin both set CSP with different values—browsers apply unpredictable combinations; standardise on one layer.

Decision checklist

  • Are HSTS, nosniff, frame-ancestors, and Referrer-Policy present on all HTML and API responses?
  • Does enforced CSP avoid unsafe-inline and unsafe-eval except documented exceptions?
  • Is CSP reporting piped to SIEM or a dedicated collector?
  • Is CORS limited to explicit origins without credential leakage patterns?
  • Are headers owned in IaC or CDN policy with CI checks for drift?
  • Was the site scored with an external header analyser after the last major release?
  • Do cookie-backed sessions use Secure, HttpOnly, and appropriate SameSite alongside transport headers?
  • Is COOP/COEP configured only where isolation is required, with CORP on static assets?

Example use cases

  • Illustrative scenario — CDN-hosted SPA: CloudFront response headers policy applies CSP, HSTS, and frame-ancestors to cached static bundles.
  • Illustrative scenario — regulated web app: Server generates per-request script nonces; CSP violations stream to SIEM; domain is HSTS-preloaded.
  • Illustrative scenario — WASM compute: COOP/COEP enabled; subresources carry CORP headers for cross-origin isolation compliance.
  • Banking portal: Strict CSP with nonce-only scripts, frame-ancestors 'none', and short-lived session cookies—Observatory grade A on every release candidate.
