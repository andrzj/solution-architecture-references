IoT & Edge Data Architecture

IoT Data Pipeline

Processing IoT telemetry at scale: high-volume ingestion patterns, time-series database selection, stream processing with Flink and Spark Streaming, hot and cold path architecture, edge pre-aggregation, and anomaly detection.

⏱ 12 min read

What it is

An IoT data pipeline is the end-to-end path from device-generated telemetry through ingestion, stream processing, and durable storage to dashboards, alerts, and batch analytics. Messages usually arrive over MQTT or HTTPS into a managed IoT endpoint, fan out through a rules engine or router into a durable log (Amazon Kinesis, Apache Kafka, Azure Event Hubs), and land in purpose-built time-series databases for operational queries and in columnar object storage for historical SQL.

Most production estates split the hot path (seconds-fresh readings in a TSDB—Timestream, InfluxDB, TimescaleDB, Azure Data Explorer) from the cold path (Parquet in S3 or a data lake queried by Athena, Spark, or BigQuery). Stream processors such as Apache Flink or Kinesis Data Analytics compute rolling averages, joins, and anomaly scores on the hot path while the same events archive cheaply for model training and compliance. Edge gateways often pre-aggregate before cloud ingress; this article focuses on cloud-side continuation after messages reach the platform.

Why it exists

IoT telemetry is time-ordered, high-volume, and queried almost exclusively by device identity plus time range—not by arbitrary relational joins. OLTP databases choke on billion-row fact tables even with partitioning; TSDBs compress tag cardinalities, tier storage by age, and expose downsampling, gap fill, and derivative functions operators need for fleet monitoring.

Without an explicit pipeline, teams bolt HTTP POST handlers onto application servers, lose events during spikes, and cannot replay history after schema changes. A log-backed design decouples fragile devices from analytics cadence, supports dead-letter and quarantine paths, and makes hot versus cold retention a policy choice instead of an accidental full-resolution hoard.

When to use

  • Any IoT system generating continuous sensor telemetry (temperature, pressure, vibration, power, location).
  • Operational monitoring dashboards requiring real-time device status views.
  • Predictive maintenance: anomaly detection on sensor streams to predict equipment failure.
  • Energy management: aggregating power consumption data across large building or vehicle fleets.

When not to use

  • Low-volume hourly readings into one relational database—managed streaming and TSDB ops rarely pay for themselves.
  • Overnight batch exports satisfy all stakeholders and ordering is loose—ELT from object storage may beat operating Kafka and Flink.
  • Early prototypes where IoT rules → S3 plus Athena exploration is enough until ingest rate and alert SLAs are proven.
  • Non-time-series events (sparse configuration or command acks only) without continuous sensor series—simpler queues or document stores may suffice.

Typical architecture

Devices publish to an IoT broker; rules route copies to a stream buffer, TSDB writers, and raw archive. Flink or managed analytics jobs read the log with event-time semantics, emit alerts and aggregates, and checkpoint state so failover does not duplicate financial or safety-critical side effects.

Pros and cons

Pros

  • Time-series databases provide 10–100x better storage efficiency and query performance for telemetry data compared to relational databases.
  • Hot/cold path split allows real-time dashboards and alerts without affecting analytical query performance.
  • Edge pre-aggregation dramatically reduces ingestion costs and bandwidth requirements.
  • Kinesis + Flink provides an elastic, managed streaming backbone that scales to millions of messages per second without infrastructure management.

Cons

  • Multiple stores (TSDB + S3 + DynamoDB) increases architectural complexity and operational surface area.
  • Time-series databases are specialised — team must learn new query languages (InfluxQL, Flux, KQL) in addition to SQL.
  • Edge aggregation loses raw data unless the raw stream is also archived — downsampled data may be insufficient for future diagnostic needs.
  • Flink's exactly-once semantics require careful checkpoint configuration; misconfiguration can lead to duplicates or data loss.

Implementation notes

Partitioning: In TSDBs and lake files, partition by time first (hour or day), then by device cohort or sensor type so dashboards scanning “today” avoid full-table reads. Hive-style prefixes such as s3://bucket/year=2025/month=11/day=16/site=west/ enable partition pruning in Athena and Spark.

Event time and watermarks: Devices buffer readings during outages and may arrive hours late. Processors must key windows on the device timestamp, not broker ingest time. Set Flink watermarks and allowed lateness (or side outputs) to match worst-case backfill; document whether late records update TSDB rows or only the cold archive.

Retention tiers: Define transitions from full resolution → one-minute rollups → hourly aggregates → cold Parquet. Automate downsampling jobs or TSDB policies; operators should not discover petabyte bills from unmetered full-resolution retention.

Ingest economics: Model cost per million messages including stream shards, TSDB write units, and egress from edge. Justify aggregation at the gateway when savings exceed the operational cost of dual raw-plus-aggregate paths.

Common failure modes

  • Relational telemetry tables: Unpartitioned OLTP tables for sensor rows bloat indexes and break range-query SLAs at modest fleet scale.
  • No retention policy: Indefinite full-resolution storage drives cost and slows queries—tiering must be automatic, not a manual cleanup project.
  • Processing-time windows: Kinesis arrival timestamps skew rolling alerts when gateways backfill after connectivity returns.
  • Shard hot spots: Partitioning the stream by device ID without salting can overload one shard when a single high-rate asset dominates.
  • Duplicate alerts: At-least-once ingest plus non-idempotent TSDB upserts or SNS publishes multiply pages on replay.

Decision checklist

  • Is operational telemetry in a TSDB or TS-optimized store, not a generic OLTP table?
  • Are hot path (dashboards, alerts) and cold path (lake, ML) explicitly separated with retention policies?
  • Do stream jobs use event time, watermarks, and documented late-data handling?
  • Are lake partitions and TSDB cardinality bounded (downsampling, tag limits)?
  • Does edge pre-aggregation preserve a raw archive when diagnostics may need it later?
  • Are replay and backfill procedures tested without duplicating customer-visible alerts?

Example use cases

  • Illustrative scenario — FieldOps operates 5,000 machines × 20 vibration sensors at 1 Hz; gateways emit 10-second rollups; Kinesis → Flink flags rolling-average anomalies → SNS opens CMMS work orders; Timestream backs a 60-day operations wall while Parquet on S3 feeds retraining.
  • Illustrative scenario — Northwind Logistics ingests 500k smart-meter intervals per quarter-hour; IoT rules write billing-grade series to Timestream and archive Parquet for demand-forecast features; Athena supports regulatory month-close reporting.
  • Case study — Public AWS and InfluxData documentation describes Timestream and InfluxDB 3 architectures for high-cardinality telemetry; Flink’s event-time model is the reference for late-arriving industrial backfill.
