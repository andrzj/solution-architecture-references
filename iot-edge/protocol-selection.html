IoT & Edge Connectivity

Protocol Selection

Choose MQTT, CoAP, AMQP, or HTTP/WebSocket based on link budget, power, firewall rules, and how gateways bridge legacy plant-floor protocols.

⏱ 12 min read

What it is

IoT protocol selection is the practice of matching a device-to-cloud (or device-to-gateway) transport to link characteristics: bandwidth, latency, power budget, packet loss, firewall traversal, and payload shape. Common choices include MQTT for lightweight publish/subscribe over TCP, CoAP for REST-like UDP exchanges on constrained radios, AMQP for enterprise messaging with rich reliability semantics, and HTTP/WebSocket where HTTPS-only egress or browser-adjacent clients dominate.

Protocol choice is not merely a library import—it fixes topic or URI conventions, quality-of-service behavior, reconnect storms, TLS handshake cost, and how gateways translate between plant-floor buses (Modbus, OPC UA) and cloud ingest. Teams standardize per product line but often operate protocol gateways at the edge when legacy devices cannot change stacks.

Why it exists

A protocol designed for a wired LAN will drain batteries on NB-IoT or LoRaWAN. Oversized JSON over a 512-byte MTU fragments, retries, and amplifies cost on cellular. Conversely, forcing every camera and gateway through bespoke UDP when HTTPS and WebSockets already pass corporate firewalls adds needless integration tax.

Operators need predictable behavior under intermittent connectivity: session persistence, retained messages, at-most-once versus at-least-once delivery, and how the cloud deduplicates duplicate sensor readings. Selecting the wrong default QoS or keep-alive interval shows up months later as broker CPU saturation or billion-row duplicate tables.

When to use

  • Battery-powered sensors on cellular or LPWAN where small headers and configurable MQTT keep-alives preserve power.
  • Fan-in telemetry from thousands of devices to a central broker benefiting from MQTT topic hierarchies and QoS 1 defaults.
  • UDP-capable mesh or 6LoWPAN fabrics where CoAP observe/notify and blockwise transfers fit MTU limits.
  • Integration with existing AMQP or RabbitMQ enterprise buses requiring transactions or complex routing.
  • OTA manifests, REST configuration, or mobile companion apps where HTTPS and occasional WebSocket push are already standardized.
  • Industrial brownfield where an edge gateway translates OPC UA or Modbus to MQTT without retooling every PLC.

When not to use

  • MQTT for large file transfer when resumable HTTP range downloads or dedicated blob protocols are simpler and cheaper.
  • CoAP across the public internet without DTLS and congestion control when TCP-based MQTT over TLS already works on the same radio.
  • HTTP polling for sub-second control loops when persistent MQTT or WebSocket subscriptions cut latency and header overhead.
  • Introducing a second protocol because one team prefers REST while the fleet already speaks MQTT—prefer gateways or a single cloud ingress contract.

Typical architecture

Constrained devices publish over MQTT or CoAP to a field gateway or directly to a managed IoT endpoint. The gateway terminates TLS, enforces topic namespaces, and may aggregate or compress payloads before cloud ingest. Richer edge nodes and mobile clients may use HTTPS for provisioning and WebSockets for command channels. Enterprise integrations consume the same event stream through AMQP bridges from the cloud bus.

Pros and cons

Pros

  • Right-sized protocols reduce bytes per reading and extend battery life on LPWAN.
  • Mature brokers and cloud IoT hubs provide auth, ACLs, and observability per protocol.
  • MQTT topic trees enable fleet-wide subscriptions without per-device coupling.
  • HTTP familiarity lowers onboarding for mobile and web configuration surfaces.
  • Gateways let you phase migrations without forklift firmware upgrades.

Cons

  • Multiple protocols multiply SDKs, certificates, and on-call expertise.
  • MQTT topic mistakes (deep wildcards, tenant leakage) are costly to fix post-fleet.
  • CoAP and UDP stacks need careful DTLS session reuse to avoid handshake storms.
  • AMQP client libraries are heavier than MQTT on small MCUs.
  • Bridging layers add latency and another failure domain at the gateway.

Implementation notes

Model worst-case links (high loss, 2G latency) in CI with network emulators before picking QoS defaults. Document a versioned payload schema with a schemaVersion field in every message body.

Prefer MQTT QoS 1 for telemetry unless you have idempotent processing and can afford QoS 0 loss. Reserve QoS 2 for rare control planes—its four-step handshake does not scale on massive fan-in.

Size payloads to radio MTU: binary encodings (Protobuf, CBOR) often beat JSON above a few hundred bytes. Split large diagnostics across chunked topics or HTTPS side channels.

Align keep-alive and session expiry with carrier NAT timeouts; stagger reconnect with jitter after outages to avoid broker thundering herds.

Run a capability matrix workshop with firmware, cloud, and ops: who owns topic design, cert rotation, and gateway firmware updates.

Common failure modes

  • QoS 2 everywhere saturating broker CPU while applications still lack idempotent writes.
  • Oversized JSON blobs exceeding link MTU and silently dropping on UDP paths.
  • Implicit last-will misuse marking thousands of devices offline on brief DNS blips.
  • Topic wildcards granting tenants visibility into neighbor devices' command topics.
  • Unbounded retained messages on dynamic topics filling broker storage.
  • Protocol gateways without backpressure buffering indefinitely when cloud ingest lags.

Decision checklist

  • Are payload size, interval, and QoS modeled against link budget and carrier cost?
  • Is TLS mandatory on every protocol path (including CoAP DTLS)?
  • Is there a single documented topic or URI namespace with tenant isolation rules?
  • Do reconnect and keep-alive settings include jitter after fleet-wide events?
  • Can the stack be tested under simulated packet loss and high latency?
  • Is there a gateway fallback plan for legacy devices that cannot adopt the primary protocol?
  • Are schema versions and compatibility rules enforced at ingest?

Example use cases

  • Illustrative scenario — A smart-building vendor uses CoAP on a BLE mesh for room sensors, aggregates at a floor gateway, and publishes MQTT with QoS 1 to a cloud BACnet analytics pipeline.
  • Illustrative scenario — Agricultural soil probes on NB-IoT send 40-byte CBOR readings over MQTT every six hours; configuration uses HTTPS because operators already have a mobile web console.
  • Case study — The OASIS MQTT specification defines QoS levels and session semantics widely implemented by HiveMQ, EMQX, and managed cloud IoT services.
