IoT & Edge

Device Identity

X.509 certificates, TPM-based attestation, and device authentication patterns.

⏱ 10 min read

What it is

Device identity is the pattern to use when large fleets of edge gateways or sensors. Establishes cryptographic proof that a physical device is genuine and authorized before it connects to cloud services. Patterns include X.509 client certificates, TPM-backed key storage, AWS IoT/X.509 JITR/JITP, and Azure DPS enrollment groups.

Identity is distinct from user identity — a device may act on behalf of many users or autonomously.

Why it exists

Shared passwords or API keys baked into firmware are extracted and cloned at scale.

Regulators and customers expect device authentication comparable to service mTLS.

When to use

  • Large fleets of edge gateways or sensors.
  • Zero-touch provisioning at factory or install time.
  • High-assurance industrial or medical devices with TPM.

When not to use

  • Prototype kits where security is deferred — must upgrade before production fleet.

Typical architecture

Pros and cons

Pros

  • Revocable per-device credentials.
  • Tamper-resistant keys in secure element.

Cons

  • Certificate lifecycle management at scale.
  • Factory process complexity.

Implementation notes

Use unique certs per device, never shared fleet keys. Automate rotation before expiry with staged rollout.

Bind identity to hardware root where available; document clone detection responses.

Common failure modes

  • Shared bootstrap cert: One leak compromises entire product line.
  • No revocation plan: Stolen device stays trusted.

Decision checklist

  • Is there a cert expiry monitoring and rotation runbook?
  • Are private keys non-exportable from secure storage?

Example use cases

  • Smart meter fleet: TPM keys; DPS enrollment; cert rotation via OTA channel.
