Deployment & Delivery

GitOps

GitOps keeps Kubernetes desired state in Git and reconciles clusters from that repository via Flux or Argo CD, using a pull-based model that limits CI cluster access and corrects drift automatically.

⏱ 10 min read

What it is

GitOps is an operational model for Kubernetes (and similar platforms) in which the desired cluster state is declared in Git, reviewed like application code, and continuously reconciled by controllers running inside the cluster. CI builds and tests application artifacts; a separate configuration repository (or directory) records which versions and manifests should run in each environment. OpenGitOps formalizes this as four principles: declarative configuration, versioned and immutable desired state, automated application of approved changes, and continuous reconciliation with alerting on divergence (OpenGitOps).

Flux and Argo CD are the common reconcilers. Both watch Git (or OCI artifacts), render manifests with Kustomize or Helm, and apply them to the API server. Flux composes CNCF controllers (source, kustomize, helm) and pairs with Flagger for progressive delivery; Argo CD adds a multi-application UI, health aggregation, and multi-cluster patterns documented in the Argo CD and Flux guides.

GitOps favors a pull delivery path: the cluster agent fetches desired state and applies it, rather than a CI job holding cluster-admin credentials to run kubectl apply. That narrows who can mutate production and supports self-healing when live resources drift from Git—subject to reconcile interval and sync policy.

Why it exists

Imperative kubectl and ad hoc Helm runs from laptops or CI leave clusters in unknown states: emergency edits, orphaned resources, and no single answer to what is running where. GitOps makes Git the contract for cluster configuration—pull requests review manifest diffs, merges trigger sync, and history supports revert-based rollback. It aligns with Kubernetes’ declarative API: you specify desired resources; controllers converge actual state, as described in the Kubernetes objects model.

Separating image build (application repo) from deployment intent (fleet or platform repo) also clarifies ownership: developers ship artifacts; platform or SRE teams govern how those artifacts land per environment—similar in spirit to Google’s production change discipline in the Site Reliability Engineering books.

When to use

  • Use GitOps when Kubernetes workloads should be auditable, reproducible, and recoverable from version control rather than from shell history.
  • Use it when multiple clusters or tenants need the same promotion pattern with environment-specific overlays in one fleet repository.
  • Use it when security policy prefers not granting CI systems long-lived cluster credentials for direct apply.
  • Use it when drift correction and prune behavior must keep live resources aligned with declared manifests.

When not to use

  • Do not expect Flux or Argo CD alone to provision cloud accounts, VPCs, or clusters—that belongs in infrastructure as code tooling.
  • Do not adopt GitOps without a secrets strategy; plaintext Secret manifests in Git are unsafe and permanent in history.
  • Do not rely on GitOps latency for emergencies that cannot wait for reconcile and sync policy; document break-glass that still updates Git afterward.

Typical architecture

CI publishes container images and opens a change in the fleet repository (image tag or Helm values); the GitOps controller detects the commit, syncs manifests into the target namespace or cluster, and reports health until the rollout completes.

Pros and cons

Pros

  • Every intentional cluster change maps to a Git commit and review record, which supports audits and post-incident timelines.
  • Automated sync and self-heal reduce silent drift from manual kubectl edits.
  • The pull model limits which systems hold cluster credentials, which shrinks exposure if CI is compromised.
  • Fleet repositories make promotion between environments a deliberate, diffable operation.

Cons

  • Reconcile intervals introduce delay between merge and live state, which complicates urgent intervention unless break-glass is defined.
  • Secrets require operators such as External Secrets or Sealed Secrets, which add moving parts beyond plain manifests.
  • Self-heal can undo temporary debugging changes unless operators patch Git or pause sync knowingly.
  • Multi-cluster GitOps still needs RBAC, tenancy, and repository structure discipline to avoid blast-radius mistakes.

Implementation notes

Keep application source and deployment manifests in separate repositories (or clearly separated roots). After CI pushes an image, automation or a pull request updates the fleet repo; Flux image automation or Argo CD Image Updater can open those commits when policy allows.

Enable prune so deletions in Git remove orphaned objects. Configure automated sync and self-heal where policy permits, and scope projects or Kustomizations so one team cannot sync another’s namespace accidentally. Manage the GitOps installation itself from Git so bootstrap drift is visible.

For secrets, store ExternalSecret (or SealedSecret) manifests in Git and source values from Vault, cloud secret managers, or similar—see secret management. Document break-glass: how to pause sync, apply a hotfix, and backport to Git within the change window your organization accepts.

Common failure modes

  • Secrets in Git: Plaintext Secret data in history cannot be unpublished; use external secret sync from the start.
  • Prune disabled: Removed manifests leave zombie resources that confuse capacity and security reviews.
  • CI still applies directly: Parallel imperative deploys fight the reconciler and recreate drift.
  • Untrained operators: Manual scale or image override during incidents is reverted on the next sync, which looks like “mysterious” rollbacks.
  • Monolithic fleet repo: Unscoped sync permissions let one application change affect unrelated namespaces.

Decision checklist

  • Is deployment configuration versioned separately from application build logic?
  • Are secret values sourced from a managed backend rather than committed to Git?
  • Does sync policy include prune for resources removed from manifests?
  • Is drift correction (self-heal) enabled where it matches operational policy?
  • Is there a documented break-glass flow that still records intent in Git afterward?
  • Is the GitOps controller’s own installation bootstrapped and upgraded from Git?

Example use cases

  • Illustrative scenario — A compliance review asks who changed production RBAC last month; reviewers use Git history and merged pull requests on the fleet repository instead of reconstructing kubectl sessions.
  • Illustrative scenario — After cluster loss, engineers attach a new control plane, install the GitOps agent, and reconcile workloads from the same fleet branch used before the incident.
  • Illustrative scenario — Staging and production image tags advance through separate pull requests in the fleet repo so promotion stays visible and reversible.
  • Case study — Weaveworks coined and operationalized GitOps on Kubernetes; the What is GitOps? article and OpenGitOps principles remain common reference points alongside vendor docs for Flux and Argo CD.

Related patterns

  • CI/CD Pipelines — Build, test, and publish artifacts that GitOps manifests reference.
  • Infrastructure as Code — Provisions clusters and cloud foundations GitOps does not own.
  • Progressive Delivery — Canary and analysis hooks often pair with Flagger or Argo Rollouts.
  • Secret Management — Supplies secret values Git manifests reference but do not contain.
