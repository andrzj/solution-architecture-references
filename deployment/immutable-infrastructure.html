Deployment & Delivery

Immutable Infrastructure

Treat servers and containers as disposable: ship versioned artifacts, roll forward by replacing instances, and forbid in-place mutation so every environment reproduces from known-good builds.

⏱ 11 min read

What it is

Immutable infrastructure means production instances are never patched, tuned, or configured live. When behavior must change, the pipeline builds a new artifact—container image by digest, VM image, or launch template version—and the orchestrator replaces running instances with ones created from that artifact. Old instances are terminated, not “fixed.”

On Kubernetes, immutability is natural: a Deployment rollout creates new Pods from an updated image spec; kubelet does not mutate container filesystems in place. On VM fleets, autoscaling groups or instance refresh swap nodes when the AMI or cloud-init bundle version changes. Packer and image pipelines bake OS hardening and agents into golden images so bootstrapping is identical every time.

Immutability pairs with declarative desired state (GitOps, IaC): what runs in production is whatever version control and CI promoted—not whatever an operator typed over SSH last Tuesday.

Why it exists

Mutable servers become snowflakes: manual sysctl tweaks, one-off package installs, and emergency hotfixes diverge from documentation. Drift hides missing security patches, breaks autoscaling symmetry, and makes incidents non-reproducible (“works on node 7”). Replacing whole instances from signed artifacts gives auditors a clear bill of materials, makes rollback a redeploy of the previous digest, and forces teams to encode changes in pipelines instead of tribal shell history.

When to use

  • Container platforms and cloud VM fleets where orchestrators can roll replacements safely.
  • Regulated environments that require provenance, image signing, and SBOM attachments per release.
  • GitOps or IaC-driven estates where controllers reconcile declared versions continuously.
  • Security programs that patch by rebuilding base images and redeploying—not apt-get on production.

When not to use

  • Stateful pets without automation: Databases or legacy VMs that cannot be recreated from automation still need migration paths before immutability applies to compute.
  • No reliable build pipeline: If CI cannot produce artifacts in minutes, hotfixes stall; fix delivery before forbidding SSH.
  • Edge or air-gapped nodes: Slow artifact distribution may force staged mutability until sync mechanisms mature.
  • Break-glass only culture: Immutability fails if leaders routinely reward manual prod edits without post-incident codification.

Typical architecture

The loop is always the same: merge triggers build, build produces a pinned artifact, deploy controller swaps instances, telemetry validates, then old revisions drain. Data layers stay outside immutable compute where possible.

Pros and cons

Pros

  • Stops configuration drift; prod matches the artifact CI tested.
  • Rollback is redeploying a prior digest or launch template version.
  • Patch cadence maps to image rebuilds with scannable, signable outputs.
  • Aligns with declarative IaC and GitOps reconciliation loops.

Cons

  • Stateful data and migrations need separate, carefully orchestrated processes.
  • Pipeline outages block all change—including urgent security fixes.
  • Rebuild times and image storage costs grow with fleet size and layer churn.
  • Requires cultural enforcement: SSH edits must be exceptional and audited.

Implementation notes

Pin images by digest or immutable tags in manifests—not floating :latest. Keep environment-specific config in ConfigMaps, Secrets, or external parameter stores injected at deploy time; do not bake per-environment URLs into images unless unavoidable.

Run golden-image pipelines (Packer, cloud image builders) on a schedule and on CVE signals; promote only scanned artifacts. For Kubernetes, prefer RollingUpdate or GitOps sync with health checks and PDBs. For VMs, use launch template versions with instance refresh or blue/green ASG swaps.

Disable routine SSH; use break-glass with session recording when absolutely necessary, then capture the fix in IaC and rebuild. Store desired state in Git; let Flux or Argo CD correct manual kubectl drift.

Packer (or cloud-native image builders) produces a golden AMI or machine image per release train: OS hardening, agents, and baseline packages are applied once in CI, then instances launch from that artifact. The pets-versus-cattle trade-off is operational—pets are repaired by hand, cattle are replaced wholesale. Immutable discipline fails when operators SSH to “just fix” disk fullness or sysctl drift; the next rollout destroys those edits. Detect drift with scheduled IaC plans and replace instances from a fresh image rather than converging live servers.

Common failure modes

  • Mutable hotfix: Operator patches a live node; next rollout wipes the fix and repeats the incident.
  • Floating tags: :latest or unpinned AMIs make “what is running?” unanswerable during audits.
  • Config in image: Twelve-factor violations force per-env image matrices instead of one portable artifact.
  • Data on cattle: Treating databases like disposable pods without backup/restore automation causes data loss on replace.
  • Skipped health gates: Fast replace without probes routes traffic to half-booted instances.

Decision checklist

  • Are all production artifacts versioned, scanned, and optionally signed?
  • Is SSH or console edit banned except audited break-glass?
  • Does IaC or GitOps describe the only approved desired state?
  • Is rollback defined as redeploying a known prior artifact?
  • Are secrets and config injected at runtime, not baked into images?
  • Is stateful data managed outside immutable compute with tested backups?

Example use cases

  • Illustrative scenario — Northwind Logistics promotes container digests via GitOps; any manual kubectl set image is reverted within minutes by Flux.
  • Illustrative scenario — Meridian Commerce refreshes an EC2 ASG weekly from a new Packer AMI; instances never receive in-place yum updates in production.
  • Case study — Netflix’s immutable AMI and container practices and Google’s Borg/Cell models popularized replace-over-repair at hyperscale—useful references for artifact promotion discipline.
