Deployment & Delivery

Database Migrations

Database migrations evolve shared schemas without outage by pairing Fowler’s evolutionary database design with expand/contract steps and N/N+1 application compatibility.

⏱ 10 min read

What it is

Database migrations are the controlled sequence of schema and data changes that keep a shared database compatible with continuously deploying applications. Martin Fowler’s Evolutionary Database Design treats the database as an integrated part of delivery: every migration must coexist with at least two application versions during rolling deploys, and destructive change is decomposed into reversible steps.

The dominant pattern is expand / contract (also called parallel change): expand adds new structures without breaking old code (nullable columns, new tables, indexes built concurrently); application changes dual-write or backfill; contract removes obsolete columns or tables only after all running code stops reading them. Renaming in place is avoided—add the new name, migrate data, drop the old name in a later deploy.

Tooling—Flyway, Liquibase, Sqitch, gh-ost, or database-native online DDL—implements the physical steps, but the architectural constraint is N/N+1 compatibility: version N of the app must run against schema S; version N+1 must run against S; only after N is gone may S contract.

Why it exists

Blocking DDL on large tables—full table rewrites, exclusive locks—can halt production traffic for minutes or hours. Coupling “deploy app” with “migrate database” in one atomic step forces big-bang releases and makes application rollback unsafe when schema has moved forward. Evolutionary migrations align schema velocity with microservice and trunk-based cadences: small, reviewable steps each safe on their own.

Shared databases amplify the problem: one service’s migration can break a neighbor still on last week’s binary unless contracts and expand phases are coordinated.

When to use

  • Continuous delivery against relational or strongly schema’d stores with rolling or blue-green application deploys.
  • Large tables where naive ALTER would lock writers or rebuild for hours.
  • Multi-region databases where replicas must apply compatible steps without diverging drift.
  • Zero-downtime column type changes, index additions, or table splits that cannot freeze traffic.
  • Organizations requiring auditable, versioned migration history per environment.

When not to use

  • Disposable development databases where wipe-and-reseed is cheaper than multi-step expand.
  • Greenfield services with no production readers—simple forward migrations suffice until traffic exists.
  • Destructive changes without verified backups and a forward repair plan—rollback is not undo.
  • Skipping expand because “we will deploy app and schema together Friday”—that recreates outage risk.

Typical architecture

Migrations run in CI/CD as reviewed artifacts; expand deploys precede or accompany application dual-write; backfill jobs run idempotently; contract deploys lag after traffic is fully on the new path.

Pros and cons

Pros

  • Avoids long exclusive locks by using online DDL tools and additive schema steps.
  • Enables application rollback to N while schema remains in expand phase.
  • Matches rolling deploy reality—old and new binaries coexist for a window.
  • Produces reviewable migration history and repeatable environment promotion.

Cons

  • More deploy steps and coordination between DBA, service, and batch owners.
  • Temporary dual-write complexity and risk of inconsistent rows if backfill fails silently.
  • Sharding and multi-region topologies multiply ordering constraints.
  • Contract phase is easy to defer—legacy columns linger as permanent debt.

Implementation notes

Author migrations in the same repo as the service when possible; run them in CI against representative data volumes. Prefer PostgreSQL CREATE INDEX CONCURRENTLY, MySQL gh-ost/pt-osc, or vendor online DDL for large tables. Backfills should be idempotent, throttled, and monitored for replication lag on followers.

Document the minimum application version required for each schema revision. Block contract migrations in automation until metrics show zero pods on N. Pair with feature flags when logical migration spans weeks—toggle read path after backfill completeness checks pass.

Expand–contract in order: add the new column or table as nullable or unused; ship code that dual-writes old and new fields; run a throttled backfill keyed on primary key ranges with replication-lag guards; switch reads to the new field behind a flag; remove reads from the old path; drop the old column in a later release. gh-ost applies MySQL changes on a shadow table with binlog-driven cutover; pt-online-schema-change uses triggers on the live table. Both need lock_wait_timeout set so a blocked DDL fails fast instead of stalling writers. Dual writes must be transactional where possible: if only one column updates, reconciliation jobs repair skew before contract.

Common failure modes

  • Big-bang DDL in peak: Table rewrite locks checkout for the duration.
  • Deploy N+1 before expand: New code expects column that does not exist; crash loop.
  • Non-idempotent backfill: Job rerun duplicates or corrupts data.
  • Early contract: Dropped column still referenced by a forgotten batch job.
  • Regional drift: Migration applied in primary region only; replicas serve inconsistent schema.

Decision checklist

  • Is there a written expand/contract plan with deploy ordering?
  • Can application versions N and N+1 both run against the current schema?
  • Are backfill jobs idempotent with lag and duration alerts?
  • Is contract gated on zero traffic from old application versions?
  • Was a backup or restore drill completed before destructive contract steps?
  • Do migration timeouts and lock timeouts match table size and maintenance windows?

Example use cases

  • Illustrative scenario — Meridian Commerce adds tax_jurisdiction_code nullable, dual-writes from checkout v2, backfills overnight, switches reads behind a flag, then drops legacy tax_region after canary completes.
  • Illustrative scenario — Northwind Logistics uses gh-ost to add an index on a billion-row shipments table without blocking dispatch writers during rolling app deploys.
  • Case study — Fowler and Sadalage’s Evolutionary Database Design article is the reference for parallel change and continuous schema integration with application delivery.
