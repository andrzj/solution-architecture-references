Deployment & Delivery

Database Migrations

Safe schema evolution strategies for zero-downtime database changes.

⏱ 10 min read

What it is

Example: add nullable column, dual-write, backfill job, switch reads, remove old column — each step deployable independently.

Why it exists

Blocking DDL on large tables causes outages. Migration patterns align application deploys with schema changes safely across replicas.

When to use

  • Continuous delivery with shared databases.
  • Large tables where locks are unacceptable.
  • Multi-region databases with lag.

When not to use

  • Empty dev databases — simple migrations suffice.
  • Skipping backups before destructive steps.

Typical architecture

Pros and cons

Pros

  • Avoids long table locks.
  • Supports rollback at each step.
  • Compatible with rolling deploys.
  • Reduces failed Friday deploys.

Cons

  • More deploy steps to coordinate.
  • Temporary data inconsistency if mis-ordered.
  • Tooling needed for backfills.
  • Complex with sharded databases.

Implementation notes

Never rename in place — add new, migrate, drop old. Run migrations in CI with review; prefer backward-compatible app deploys.

Monitor replication lag during backfills; throttle jobs.

Common failure modes

  • Non-backward-compatible deploy mid-migration.
  • Full table rewrite on prod peak.
  • Missing rollback for data backfill.
  • Drift between regions.

Decision checklist

  • Expand/contract plan written?
  • App supports N and N+1 schema?
  • Backfill idempotent?
  • Replication lag monitored?
  • Backup before contract?
  • Migration timeouts configured?

Example use cases

  • Postgres: Concurrent index creation.
  • MySQL: gh-ost for online ALTER.
  • NoSQL: Lazy migration on read.
