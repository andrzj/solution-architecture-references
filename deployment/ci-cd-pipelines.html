Deployment & Delivery Essential

CI/CD Pipelines

CI/CD pipelines automate build, test, and promotion from commit to production; the pattern covers stage design, trunk-based flow, artifact promotion, and DORA metrics for delivery performance.

⏱ 10 min read

What it is

A CI/CD pipeline is an automated path from source commit to running software: continuous integration merges changes to a shared trunk with automated build and test, and continuous delivery (or deployment) promotes the same validated artifact through gated stages until it reaches production. Jez Humble and David Farley describe this as a deployment pipeline—each change is proven in increasingly production-like steps rather than validated only at a big-bang release (Continuous Delivery; Martin Fowler’s deployment pipeline essay).

Continuous integration integrates work frequently on the main branch so integration defects surface while they are small. Continuous delivery means every successful pipeline run produces a release candidate that could go live on demand. Continuous deployment goes further by automatically releasing every candidate that passes policy—appropriate only when observability, rollback, and blast-radius controls match production risk.

Typical stages run in order: source trigger (push or pull request), build and package (including container images), fast unit tests and static analysis, slower integration or end-to-end tests, publish to an artifact registry, deploy to a pre-production environment, then promote to production—often with a progressive strategy such as rolling, blue-green, or canary deployment. Fast stages should fail first so developers get signal while context is fresh; expensive tests run only after cheap gates pass.

Trunk-based development pairs well with CI/CD: developers integrate to main in short-lived branches (or directly), keep the trunk deployable, and hide incomplete work behind feature flags instead of long-lived release branches. DORA’s research associates trunk-based flow with stronger software delivery performance among the teams they study (DORA).

Why it exists

Manual releases concentrate risk, depend on individual runbooks, and hide whether production matches what was tested. A pipeline turns release steps into repeatable automation: the same commands run for every change, artifacts are immutable, and quality gates block promotion when tests or policy checks fail. That structure supports the four DORA software delivery metrics—deployment frequency, lead time for changes, change failure rate, and time to restore service—which teams use to compare capability and improvement over time.

Pipelines also shorten feedback. When build or test failure returns to the author quickly, fixes stay inexpensive; when validation waits until a quarterly release, defects compound. Continuous Delivery treats the pipeline as the primary mechanism for both quality assurance and release governance.

When to use

  • Use a pipeline for any software that ships to users or other systems, because automated integration and promotion reduce variance compared with ad hoc deploy scripts.
  • Prioritize pipeline investment when releases are slow, error-prone, or blocked on a single operator—automation and auditable gates typically return capacity quickly.
  • Model staging and production promotion explicitly when regulation or change management requires evidence of tests and approvals between environments.
  • Run security and compliance checks (static analysis, dependency scanning, container image scanning) inside the pipeline so risky changes fail before they reach shared environments.

When not to use

  • Do not enable fully automated production deployment until monitoring, rollback, and incident response can absorb frequent releases; continuous delivery with a manual production gate is a deliberate interim state.
  • Do not treat the pipeline as the only quality layer—local pre-commit checks and review still matter, especially for changes pipelines cannot cheaply exercise.
  • Do not copy another team’s stage graph blindly; pipeline depth should match test pyramids, coupling, and blast radius rather than a generic checklist.

Typical architecture

A change enters from version control, flows through build and test jobs (often in GitHub Actions, GitLab CI, or a similar runner), passes security scans, produces a versioned artifact, and deploys through environment-specific jobs with optional human approval before production.

Pros and cons

Pros

  • Automation makes every release follow the same steps, which reduces operator variance and creates an audit trail in pipeline logs.
  • Early automated tests return failures to the author while the change is still familiar, which lowers the cost of repair compared with late integration.
  • Trunk-based flow plus feature flags lets teams ship code continuously while controlling when users see new behavior.
  • Immutable artifacts promoted by digest tie what was tested to what runs in production.

Cons

  • Pipelines require ongoing ownership; flaky tests, outdated actions, and drifting runners erode trust if nobody maintains them.
  • Slow or over-serialized stages encourage merging before results finish, which defeats the purpose of gating.
  • Continuous deployment without strong observability and rollback can amplify production incidents.
  • Shared pipeline templates that ignore service boundaries can run irrelevant work or miss service-specific risks.

Implementation notes

Treat pipeline duration as a product metric: parallelize independent jobs (lint, unit tests, static analysis), cache dependencies and build layers, and scope expensive integration or E2E suites to affected components when the repository structure allows. Fowler’s pipeline guidance favors a thin fast stage that most commits pass quickly, with deeper validation afterward.

Promote one artifact end to end—container image by digest, not a rebuild per environment. Pair build pipelines with environment management so staging mirrors production configuration even when scale differs.

Quarantine flaky tests rather than weakening required checks; track quarantined cases until fixed. Store credentials in the platform’s secret store, scope production deploy permissions narrowly, and wire security scanners into pull-request workflows so findings block merge when policy requires it.

Typical stages run commit → compile/unit test → package (container image or tarball) → integration and security gates → sign and attest → publish to registry → promote the same digest through environments. Rebuilding at deploy time breaks the guarantee that production runs what integration tested. Attach an SBOM (CycloneDX or SPDX) to the artifact for vulnerability response. SLSA provenance describes how the artifact was built; signing with Sigstore cosign (or similar) lets admission controllers verify signature and policy before a pod starts. Trunk-based development keeps main always releasable: short-lived branches merge frequently and incomplete work hides behind flags instead of long release branches.

The four DORA metrics measure different facets of delivery. Deployment frequency is how often you deploy to production. Lead time for changes is commit-to-production latency. Change failure rate is the fraction of changes that cause failure in production. Time to restore service is how long it takes to recover when failure happens. Improving one without the others can mislead—for example, deploying constantly with poor quality raises failure rate.

Common failure modes

  • Slow feedback: Long-running pipelines train contributors to merge without waiting for red builds, which lets defects reach main.
  • Normalized failures: Teams that habitually rerun or ignore flaky stages lose confidence in green status and skip real regressions.
  • Environment mismatch: Staging that diverges from production in configuration, dependencies, or integrations produces passing tests that do not predict production behavior.
  • Rebuild per stage: Producing a fresh artifact after tests invalidates the guarantee that production runs what was validated.
  • Missing rollback path: Fast deploy without rehearsed rollback or forward fix leaves operators improvising under incident pressure.

Decision checklist

  • Does the pull-request pipeline usually finish quickly enough that authors wait for results before merging?
  • Is the same immutable artifact promoted from build through staging into production?
  • Are secrets and tokens stored in a managed secret store rather than committed to the repository?
  • Are DORA metrics (or equivalent delivery indicators) visible to the team for trend review?
  • Is there an explicit process to detect, quarantine, and fix flaky automated tests?
  • Do required security scans run on every change that can reach shared or production environments?

Example use cases

  • Illustrative scenario — A team replaces quarterly manual releases with trunk merges, an automated pipeline, and feature flags; smaller batches and consistent gates reduce release-week incidents.
  • Illustrative scenario — Mandatory SAST and dependency scanning on pull requests blocks high-severity findings before merge, and engineers adopt local checks to shorten feedback.
  • Illustrative scenario — Pipeline YAML in the service repository documents build, test, and deploy steps for onboarding instead of oral handoffs alone.
  • Case study — DORA’s published research links team practices such as trunk-based development and automated delivery to higher software delivery performance; see DORA capabilities and the deployment pipeline pattern for foundational design.

Related patterns

  • GitOps — Kubernetes delivery driven by Git-declared desired state and in-cluster reconcilers.
  • Feature Flags — Separates deploying code from enabling features for users.
  • Canary Releases — Limits production blast radius during the final pipeline stage.
  • Environment Management — Defines how artifacts move across dev, staging, and production.
