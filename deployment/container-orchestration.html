Deployment & Delivery

Container Orchestration

Kubernetes as the dominant container orchestrator: control plane and node agents, workload controllers for stateless and stateful apps, autoscaling with HPA, VPA, and KEDA, and disruption budgets that keep upgrades safe.

⏱ 12 min read

What it is

Container orchestration is the automated placement, lifecycle, networking, and scaling of containerized workloads across a pool of machines. Kubernetes is the de facto implementation: you declare desired state (images, replica counts, resources, probes) in API objects; controllers continuously reconcile cluster state toward that declaration.

Architecture splits into a control plane (cluster brain) and a data plane (workers that run pods). The control plane exposes the API server (the only supported entry for changes), persists state in etcd, assigns pods via the scheduler, and runs controllers (Deployment, StatefulSet, and dozens more) that enforce desired versus actual state. Cloud controller manager bridges to provider APIs for load balancers, disks, and node lifecycle where the cluster runs on EKS, GKE, or AKS.

Each worker runs kubelet (pod execution), kube-proxy or equivalent datapath (Service connectivity), and a CRI runtime (containerd, CRI-O). Application teams usually interact through workload APIs rather than raw Pods:

  • Deployment — stateless apps; rolling updates; arbitrary replica count.
  • StatefulSet — stable network identity, ordered rollout, persistent volumes per replica (Kafka, etcd, some databases).
  • DaemonSet — one pod per node (agents, CNI, log collectors).
  • Job / CronJob — batch and scheduled tasks.
  • HorizontalPodAutoscaler (HPA), VerticalPodAutoscaler (VPA), and KEDA — scale replica count or recommend/adjust resource requests from metrics or external events (queues, schedules).
  • PodDisruptionBudget (PDB) — limits voluntary evictions during drains and upgrades.

Why it exists

At scale, “run Docker on N VMs” collapses under scheduling fairness, bin packing, failure recovery, secret distribution, service discovery, certificate rotation, and coordinated rollouts. Ad hoc scripts become snowflake automation that no new hire can safely change. Kubernetes standardizes those problems behind a portable API and a large ecosystem (Ingress, CSI storage, GitOps, policy engines), so the same manifest patterns work across clouds and on-premises with provider-specific tuning at the edges.

When to use

  • Many containerized services sharing one platform for deploy, scale, network policy, and observability hooks.
  • Load that varies by time or queue depth, where HPA or KEDA can right-size replicas automatically.
  • Organisations standardizing on portable manifests across EKS, GKE, AKS, or CNCF-certified distributions.
  • Platform teams offering namespaces, quotas, and guardrails to product squads without hand-rolling fleet scripts.

When not to use

  • Single small app: Managed runtimes (Cloud Run, App Service, Lambda containers) often beat operating a control plane for one binary.
  • No platform capacity: Kubernetes rewards teams that can own upgrades, etcd backup, CNI debugging, and incident response.
  • Hard real-time on bare metal: Extra scheduling and CNI hops may be unacceptable without careful tuning; sometimes VMs or dedicated hosts win.
  • Stateful databases as default: Running primary databases on StatefulSets is possible but often loses to managed RDS, Cloud SQL, or Atlas unless there is a strong cost or compliance driver.

Pros and cons

Pros

  • Self-healing replaces crashed containers and reschedules after node loss without custom watchdog scripts.
  • Workload APIs encode rollout, scaling, and affinity policy once; controllers enforce it continuously.
  • Portable YAML across managed Kubernetes offerings simplifies migration and multi-cloud strategies.
  • Rich extension points (admission webhooks, CNI, CSI, Gateway API) let platforms enforce security and cost guardrails centrally.

Cons

  • Operational surface area is large: upgrades, etcd, networking, and storage failures require trained on-call engineers.
  • Mis-set requests and limits cause silent performance loss (throttling, OOMKilled) or wasted capacity.
  • StatefulSets reduce but do not remove database operational burden compared to managed data services.
  • Default networking and DNS abstractions hide complexity until cross-namespace or multi-cluster debugging is needed.

Implementation notes

Set requests for scheduling and limits for cap behavior on every container. Memory limits should reflect real headroom; CPU limits often throttle bursty Java or Go services—many teams set CPU requests without limits for latency-sensitive tiers. Run VPA in recommendation mode before auto-mutating production pods.

Configure livenessProbe, readinessProbe, and startupProbe so rollouts only receive traffic when dependencies are warm. Pair Deployments with topologySpreadConstraints or pod anti-affinity so replicas survive zone loss. Use preStop hooks and adequate terminationGracePeriodSeconds so load balancers drain connections before SIGKILL.

Ship PDBs for every production Deployment and StatefulSet. During node drains, cluster autoscaler scale-downs, or control-plane-adjacent maintenance, PDBs cap simultaneous evictions. For critical tiers, align minAvailable with SLO error budgets. Namespace-scoped ResourceQuota and LimitRange prevent one team from starving the fleet.

Common failure modes

  • BestEffort scheduling: Pods without requests land on busy nodes and become noisy neighbors under load.
  • Probe lies: Readiness succeeds before migrations finish or caches warm; Ingress sends traffic to failing instances.
  • Single-zone stacking: Missing spread constraints concentrate replicas in one AZ; one outage drops the service entirely.
  • Surge without PDB: Aggressive maxUnavailable or absent PDB allows drains to take all replicas offline.
  • StatefulSet storage mismatch: Wrong storage class or non-expanding volumes block ordered recovery after disk fill.

Decision checklist

  • Are requests, limits, and probes defined for every container in production?
  • Do PDBs and spread rules match the service availability target?
  • Is autoscaling (HPA or KEDA) wired to metrics that reflect real demand, not just CPU?
  • Are StatefulSet data tiers backed by tested backup, restore, and failover runbooks—or migrated to managed databases?
  • Can the platform restore etcd and recover workloads within RTO/RPO targets?
  • Are admission policies blocking privileged pods, hostPath mounts, and unscoped cluster-admin bindings?

Example use cases

  • Illustrative scenario — Northwind Logistics runs order ingestion on a Deployment with KEDA tied to queue depth; overnight scale-to-zero cuts compute cost while morning spikes add replicas in minutes.
  • Illustrative scenario — Meridian Commerce upgrades an EKS node group one node at a time; PDBs hold checkout at ≥60% capacity and error rates stay flat through a full AMI refresh.
  • Case study — Spotify and Adidas have publicly described large-scale Kubernetes fleets for service portability and fleet efficiency; both illustrate platform investment paying off at high pod counts.

Related patterns

  • GitOps — Reconcile desired Deployments and controllers from Git with drift detection, per the Kubernetes declarative model.
  • Service Mesh — Sidecar-based traffic policy, mTLS, and telemetry atop the pod graph the orchestrator schedules.
  • Rolling Deployments — Native Deployment rollout semantics (maxSurge, probes, PDBs) the control plane executes.
  • Blue-Green Deployment — Second ReplicaSet or slot labels plus Service selector flips on the same cluster.
  • Canary Releases — Progressive weights often implemented with Rollouts CRDs plus mesh or ingress integration.
  • Infrastructure as Code — Cluster and node-pool lifecycle that precedes workload placement.
