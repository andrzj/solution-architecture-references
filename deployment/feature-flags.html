Deployment & Delivery

Feature Flags

Feature flags decouple deployment from release using Fowler’s toggle taxonomy—release, experiment, ops, and permission toggles—with lifecycle discipline and safe evaluation.

⏱ 10 min read

What it is

Feature flags (feature toggles) are runtime switches that choose which code path or capability is active for a request, user cohort, or environment—without redeploying application binaries. Martin Fowler’s Feature Toggles article groups toggles into four complementary types, each with different lifetime and ownership expectations.

Release toggles hide incomplete work on trunk so teams can integrate continuously while keeping features dark in production. Experiment toggles route traffic across variants for A/B tests and multivariate experiments. Ops toggles act as circuit breakers or kill switches for risky integrations—payment processors, new storage backends, or model inference paths—so operators can mitigate without waiting for a deploy pipeline. Permission toggles expose capabilities by entitlement (tier, role, region) at runtime; they resemble product configuration but should not replace server-side authorization for sensitive data.

A flag evaluation supplies a flag key, an evaluation context (user ID, attributes, environment), and a safe default when the control plane is unreachable. Rules implement boolean on/off, percentage rollout via stable hashing (same user stays in the same bucket as percentage increases), attribute predicates, and allowlists. Platforms such as LaunchDarkly, Unleash, and Flagsmith stream configuration to in-process SDK caches so hot-path evaluation stays sub-millisecond; the critical design constraint is that per-request evaluation must not synchronously call a remote API.

Why it exists

Traditional release trains bundle many changes behind a single production deploy: code must be “done,” risk is concentrated, and rollback reverts everything together. Feature flags invert the coupling—code ships on an engineering cadence while product and operations decide when behavior becomes visible. That separation enables trunk-based development, dark launches, and incremental exposure with observability between steps.

Fowler also emphasizes toggle lifecycle: release toggles should be short-lived and removed once a feature is fully on; ops toggles may persist longer but need owners; experiment toggles tie to experiment conclusions. Without lifecycle discipline, flags become permanent configuration forks and compound testing cost.

When to use

  • Trunk-based delivery where incomplete features must land in main but stay invisible until ready.
  • Gradual exposure—1% → 10% → 100%—with monitoring and business metrics between steps.
  • Kill switches for third-party or high-blast-radius dependencies that must be disable-able in seconds.
  • Entitlement or regional rollout where attributes in the evaluation context gate behavior.
  • Coordinated migrations (dual-write periods) where application logic must flip between old and new paths under operator control.

When not to use

  • Long-lived product configuration that rarely changes—model it as configuration or entitlements in the domain layer, not ephemeral release toggles.
  • Security-sensitive access control where client-side or easily spoofed evaluation would bypass payment or privacy rules.
  • Replacing infrastructure-level traffic management when the goal is version-level routing—use canary releases or a service mesh instead.
  • Teams unwilling to schedule toggle removal; accumulating flags is worse than infrequent batched releases.

Typical architecture

Applications embed a flag SDK that maintains a local rules snapshot. Operators change targeting in a dashboard; changes stream to servers; each request evaluates flags in-process with deterministic defaults on failure.

Pros and cons

Pros

  • Decouples deploy cadence from customer-visible release, shrinking batch size and coordination overhead.
  • Instant mitigation via ops toggles—seconds to disable a path versus minutes for artifact rollback.
  • Supports experiments and cohort rollouts without maintaining long-lived feature branches.
  • Enables dark launches and soak time with production traffic before full exposure.

Cons

  • Flag debt multiplies code paths and test matrices; Fowler warns that stale release toggles become liabilities.
  • Control-plane or SDK misconfiguration can strand users on defaults—or unexpectedly enable new behavior.
  • Client-side flags are not a trust boundary; server-side checks remain mandatory for authorization.
  • Observability must tag flag state; otherwise incidents during rollouts are impossible to diagnose.

Implementation notes

Register every toggle with an owner, type (release/experiment/ops/permission), creation date, and removal criteria—for example, “100% for 14 days with no SLO regression, then delete flag and dead code.” Schedule removal in the same sprint that completes rollout. Prefer static configuration for ops toggles that rarely change, but keep the evaluation API uniform so applications do not branch on ad hoc environment variables.

Always pass a safe default to variation calls: on outage, behavior should match the last stable path. Use consistent percentage hashing so increasing rollout does not reshuffle existing users. Emit flag key and resolved value into traces or structured logs (never PII in flag names). For mobile or thick clients, treat flags as hints only—enforce entitlements on the server.

Permission toggles differ from release toggles: they gate entitlements that must be enforced on the server even when the flag SDK is unavailable. Flag debt is the accumulation of toggles past their removal date—treat cleanup as a release task, not backlog trivia. OpenFeature standardizes the evaluation API across vendors so you can swap providers without rewriting call sites. Latency-sensitive services should evaluate from an in-process cache fed by streaming or periodic sync; blocking HTTP on every request couples availability to the flag vendor’s SLA.

Common failure modes

  • Stale release toggles: Hundreds of permanent if (flag) branches; engineers fear deletion because ownership was never recorded.
  • Network evaluation on hot paths: Per-request HTTP to the flag vendor; latency and availability become coupled to product traffic.
  • Flags as authorization: Premium APIs gated only by a client-readable flag; trivial to bypass.
  • Inconsistent hashing: Changing rollout strategy resets cohorts, breaking experiments and user trust.
  • Missing observability: Rollout succeeds in the dashboard but incidents cannot be tied to flag state in metrics.

Decision checklist

  • Is each toggle classified with Fowler’s type and a documented removal or review date?
  • Does evaluation use an in-process cache with streaming updates—not remote calls per request?
  • Are defaults defined so outage reverts to stable behavior?
  • Is there a scheduled cleanup task after full rollout?
  • Are sensitive capabilities enforced server-side independently of flag state?
  • Do traces or logs include flag keys and resolved values for rollouts in flight?

Example use cases

  • Illustrative scenario — Meridian Commerce ships a redesigned checkout behind a release toggle; traffic moves 5% → 25% → 100% over two weeks while error-rate dashboards gate each step; the toggle and branch are removed once conversion holds steady.
  • Illustrative scenario — Northwind Logistics enables a new carrier-rate provider under an ops toggle; when the provider times out during peak season, operations disable the toggle in the control plane while PostgreSQL remains authoritative—no redeploy required.
  • Case study — Fowler’s Feature Toggles remains the reference taxonomy for release versus experiment versus ops toggles and toggle lifecycle hygiene in continuous delivery.

Related patterns

  • Progressive Delivery — Combines flags with traffic-shaped deploys and metric gates.
  • Canary Releases — Infrastructure-level percentage routing between binary versions.
  • Rollback Strategies — Flag-off is often the fastest mitigation layer.
  • CI/CD Pipelines — Trunk-based pipelines assume flags for incomplete features.
