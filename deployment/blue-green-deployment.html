Deployment & Delivery

Blue-Green Deployment

Two identical environments with instant traffic switching, database migration challenges, rollback in seconds, and DNS vs load balancer switching strategies for zero-downtime deployments.

⏱ 9 min read

What it is

Blue-green deployment keeps two production-identical environments—conventionally “blue” (live) and “green” (idle)—and moves user traffic from one to the other in a single switch once the new version is validated. Martin Fowler’s Blue-Green Deployment bliki frames the core idea: deploy to the idle side, test it, then flip the router; rollback is the same flip in reverse. The pattern cleanly separates deployment (getting binaries running) from release (exposing users to them).

The deployment process: (1) new version is deployed to the idle environment; (2) smoke tests and validation run against the idle environment; (3) the load balancer or DNS record is updated to route traffic to the new environment; (4) the old environment is kept live for a period to enable instant rollback;

(5) after a stability window, the old environment is decommissioned or repurposed for the next release cycle.

The traffic switch can be performed at different layers. Load balancer switching is the most common: the load balancer's target group is changed from blue to green. This is near-instantaneous (under a second) and provides immediate rollback capability by reverting the target group assignment. DNS switching updates the DNS record to point to the new environment's IP or load balancer.

DNS is slower due to TTL propagation (even with TTL set to 30-60 seconds, some clients cache longer) but works for environments without a shared load balancer. Kubernetes Service switching changes the Service selector labels to route to the new Deployment's pods — the cleanest approach in Kubernetes where both deployments coexist in the cluster and traffic switch is a label selector update.

Blue-green is distinct from rolling deployments (incrementally replacing pods one at a time) and canary releases (routing a small percentage to the new version). Blue-green performs a complete, simultaneous switch of all traffic — it is binary, not gradual. This means if the new version has a problem, all users are affected rather than a subset. The compensation is that rollback is trivially fast — reverting to blue takes the same time as the original switch, typically under a second.

Why it exists

Traditional release flows often coupled “build finished” with “users see it now,” so rollback meant rebuilding artifacts under pressure while outages clocked up. Blue-green makes deployment (warm the idle stack) and release (move the router) two explicit steps—an idea Fowler formalized in Blue-Green Deployment. High-performing teams in the DORA research associate faster recovery with practices that keep the prior version reachable; a rehearsed router flip is one of the shortest paths back when a promotion goes wrong.

Production-identical idle capacity also supports soak and smoke validation against real dependencies before any customer request hits the new build—closer to the “verify in prod-like conditions” discipline described in canarying releases material, but with a binary cutover instead of percentage ramps.

When to use

  • When SLAs forbid sustained mixed-version fleets—authorization, checkout, or ledger paths where old and new binaries must not share live traffic concurrently.
  • When schema work follows expand-contract (or parallel-change) and you need the new code on idle capacity before cutover, as in Fowler’s Parallel Change write-up.
  • When rollback must be operator-simple: revert service selector, ALB target group, or DNS weight—not re-run a long rolling undo under incident stress.
  • When Kubernetes promotion is automated—e.g. Argo Rollouts activeService / previewService with pre-promotion analysis per the blue-green feature docs.

When not to use

  • When doubling compute for the cutover window is unbudgeted—stateless, low-risk services often fit native rolling updates instead.
  • When you need production metric gates across small traffic slices before full exposure—progressive delivery or canary releases reduce all-at-once blast radius.
  • When the change is not safe on two full stacks at once (destructive migrations, incompatible RPC contracts)—fix compatibility or sequencing before any duplicate environment strategy helps.

Typical architecture

Two full replica sets (or environments) sit behind one routing surface; only the active selector or target group receives user traffic until operators flip the switch.

Pros and cons

Pros

  • Cutover at the router is near-instant for load balancers and many ingress patterns—users avoid maintenance-window downtime when validation succeeds on idle capacity first.
  • Rollback symmetry: the same control-plane change that promoted green can demote it; the prior stack stays warm during the stability window.
  • Idle stack testing uses production networking, secrets, and data-plane dependencies—closer to reality than staging-only sign-off.
  • Clear runbooks: operators document one promotion path (deploy green → verify → flip) instead of interpreting partial rollout health across heterogeneous pod ages.

Cons

  • Capacity and cost spike while both stacks run at production scale—unacceptable for GPU-heavy or large replica counts without autoscaling headroom.
  • Data plane discipline: expand-contract migrations and dual-read/write phases span multiple releases; rushing contract steps removes rollback safety.
  • Binary exposure: unlike metric-stepped canaries, a missed defect in pre-switch checks affects the full traffic share at once.
  • State and sticky routing: in-memory sessions, pod-local caches, or affinity rules can make “identical environments” behave differently after the flip.

Implementation notes

Treat database evolution as a release prerequisite, not a same-day toggle. Apply expand steps while blue still serves traffic; ship green code that tolerates both old and new schema; run contract steps only after green is stable—matching Fowler’s parallel-change sequencing. Destructive DDL before cutover effectively forfeits instant rollback.

On Kubernetes, label two Deployments (or ReplicaSets) and point the Service selector at the live slot; promotion is a selector patch, as sketched in the Service model. Prefer controllers that encode the lifecycle: Argo Rollouts blue-green sets auto-promotion timers, optional AnalysisTemplate hooks, and scale-down policy; AWS CodeDeploy and ALB target groups follow the same mental model off-cluster.

Before flipping, run synthetic traffic against green (auth, health, critical RPC paths), warm connection pools, and confirm observability dashboards distinguish blue versus green series so post-cutover regressions are obvious within minutes—not after a full incident bridge.

Session stickiness changes cutover behavior. When a load balancer pins users to a backend by cookie or source IP, flipping the router does not move in-flight sessions until their affinity expires. Plan either short-lived stickiness during promotion, dual-stack serving during the stickiness TTL, or acceptance that some users complete on blue while new sessions land on green. WebSockets and long polling need explicit drain: stop accepting new connections on blue, wait longer than the longest expected connection lifetime, then shift weight.

Argo Rollouts can run AnalysisTemplate jobs against the preview (green) Service before automatic promotion, querying Prometheus for error rate and latency versus the active service. Configure scaleDownDelaySeconds so blue stays warm while you still need a one-click revert.

Both colors must run against a schema that tolerates either application revision: expand new columns before cutover, avoid contract steps until blue is retired, and ensure message formats remain backward compatible for async consumers still attached to the draining stack. In-flight HTTP requests on blue should complete via drain hooks on the old target group or Ingress backend before weights move to one hundred percent on green.

Common failure modes

  • Promoting ahead of migration expand: Green binaries expect columns or topics that production schema lacks; 5xx spike until rollback—sometimes with partial writes that complicate data repair.
  • Cold green after flip: Autoscaler lag, empty caches, and JIT warm-up produce latency cliffs even when functional tests passed on a lightly loaded idle stack.
  • Config drift between slots: Green receives different feature flags, secrets, or ConfigMap revisions than blue; the cutover surfaces environment skew mistaken for code defects.
  • DNS-led cutover with long TTL: Clients cache old targets; operations believes rollback succeeded while a tail of users remains on green—or the reverse during revert.
  • Premature blue teardown: Reclaiming idle capacity before the stability window ends removes the fast revert target when slow-burn bugs appear.

Decision checklist

  • Is full duplicate production capacity affordable for the soak window, including burst headroom?
  • Are migrations sequenced expand → dual-compatible apps → contract, with rollback tested on paper?
  • Are sessions, carts, and idempotency keys externalized so slot changes do not log users out or duplicate work?
  • Do pre-switch tests exercise green under realistic auth, quotas, and downstream rate limits?
  • Is promotion automated (GitOps, rollout controller, or IaC) with audit history for who flipped what and when?
  • Does observability tag telemetry by slot/version so dashboards compare error rate and latency across blue and green?
  • Is there a timed hold on blue after cutover before scale-down, aligned with error-budget policy?

Example use cases

  • Illustrative scenario — Payment processing with a strict zero-downtime SLA: new code runs on green, a ten-minute automated transaction suite passes, the load balancer target group flips in under a second, blue stays warm for thirty minutes, and a post-switch metric spike triggers an immediate flip back.
  • Illustrative scenario — A regulated workload must complete cutover inside a thirty-second maintenance window; green is pre-deployed and validated before the window opens so the only live action is the router change.
  • Case study — Teams on AWS often pair CodeDeploy or ALB target groups with blue-green; Argo Rollouts automates the same pattern in-cluster via activeService / previewService and pre-promotion analysis (Argo Rollouts blue-green).

Related patterns

  • Canary Releases — Step traffic by percentage when observability can gate each increment instead of a single full cutover.
  • Rolling Deployments — In-place pod replacement when dual stacks are costly and versions stay compatible during overlap.
  • Release Strategies — Pick blue-green versus rolling versus canary from change risk, traffic volume, and rollback time budget.
  • Rollback Strategies — Pair router revert with data and config rollback plans when schema or flags moved with the release.
  • Database Migrations — Expand-contract sequencing that makes blue-green rollback technically feasible.
  • Progressive Delivery — Controllers (Argo Rollouts, Flagger) that implement blue-green and canary behind one operational model.
