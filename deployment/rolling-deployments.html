Rolling Deployments

Incrementally replace application instances while keeping capacity online: the default Kubernetes Deployment strategy, its tuning knobs, and the backward-compatibility constraints that make or break a roll.

⏱ 10 min read

What it is

A rolling deployment replaces running instances with a new version in small waves rather than stopping the entire fleet at once. The orchestrator starts new pods, waits until they pass health checks, removes old pods, and repeats until every replica runs the target version. On Kubernetes, strategy.type: RollingUpdate is the default on Deployment objects; maxSurge caps how many extra pods may exist during the roll, and maxUnavailable caps how many pods may be down—together they bound capacity and blast radius during the update.

A typical zero-downtime configuration sets maxUnavailable: 0 and maxSurge: 25%: the cluster may temporarily run up to 125% of desired replicas while old pods drain. The Service endpoints controller adds new pods only after readinessProbe success and removes terminating pods after graceful shutdown. Unlike blue-green, there is no separate idle environment—old and new versions coexist for the duration of the rollout, which demands backward compatibility across the overlap window.

Why it exists

Big-bang restarts drop serving capacity to zero and force maintenance windows. Rolling updates keep a minimum healthy replica count online while newer code warms up, which matches how stateless horizontally scaled services are usually operated. The pattern is cheap in infrastructure (no second full environment), familiar to platform teams, and built into every major orchestrator—not only Kubernetes but also ECS rolling task replacement, Azure App Service deployment slots in rolling mode, and similar VM-scale-set patterns.

The trade-off is deliberate: rolling is the right default for routine, backward-compatible changes, but it does not provide instant full rollback or fine-grained traffic percentages. Teams that outgrow naked rolling—needing metric-gated promotion or instant switchback—layer canary or blue-green on top via Argo Rollouts or external load balancers.

When to use

  • Stateless services behind a load balancer or Kubernetes Service where extra replicas can absorb surge during replacement.
  • Changes that remain backward compatible for at least one release (API schema, message formats, database reads/writes) while two binary versions run together.
  • Routine application and configuration deploys where downtime is unacceptable but deployment risk is moderate and covered by pre-production tests.
  • Platforms where rolling is the default and operational runbooks already assume mixed-version windows (standard Kubernetes, many PaaS offerings).

When not to use

  • Breaking API or schema changes without dual-write or expand-contract migrations—mixed versions will corrupt data or fail requests; prefer blue-green with a hard cutover.
  • Stateful single-replica workloads where maxUnavailable: 0 cannot be satisfied without doubling capacity elsewhere.
  • Releases that require instant, complete rollback of all traffic in seconds—rolling back a Deployment is another roll forward to the previous revision, which takes as long as the original rollout.
  • High-risk changes where only a small percentage of traffic should see the new build first—use canary or Argo Rollouts instead of uncontrolled pod mixing.

Typical architecture

Each wave creates new pods, gates on readiness, deregisters old pods from the Service, and honors termination grace so in-flight requests complete.

Pros and cons

Pros

  • No planned outage window when maxUnavailable is tuned to preserve capacity.
  • First-class support in Kubernetes and most cloud runtimes—no extra controllers required for the baseline pattern.
  • Infrastructure cost stays at one replica set; unlike blue-green, you do not pay for a full duplicate environment during release.
  • Works naturally with horizontal pod autoscaling: new pods join the Service as they become ready.
  • kubectl rollout undo (or CI rollback to a prior manifest revision) reverts to the last known-good ReplicaSet without rebuilding images.

Cons

  • Two application versions run concurrently for minutes—schema, APIs, and feature flags must tolerate the overlap.
  • Large fleets roll slowly; a 500-replica service with conservative surge settings may take tens of minutes to complete.
  • Long-lived connections (WebSockets, SSE, gRPC streams) may survive on old pods until termination grace expires, complicating drain.
  • Error attribution is muddy during the roll unless metrics and traces carry version labels—you cannot isolate “canary” traffic without mesh or header routing.
  • Rollback is “roll forward” to the previous revision, not an instantaneous traffic switch like blue-green.

Implementation notes

Readiness probes must reflect real dependencies (database connectivity, cache reachability, feature-flag SDK init)—a probe that only checks /healthz on the process will admit pods before they can serve traffic. Pair preStop hooks with a sleep long enough for the load balancer or kube-proxy to stop sending new connections before SIGTERM handling begins; AWS ALB and many ingress controllers need several seconds of deregistration delay.

Set progressDeadlineSeconds so a stuck rollout fails visibly instead of leaving a permanent mix of versions. Define a PodDisruptionBudget so voluntary evictions (node upgrades, cluster autoscaler) cannot drain more replicas than the rollout math allows. During the roll, tag Prometheus metrics and traces with pod template hash or image tag so dashboards can compare error rates between old and new ReplicaSets.

Argo Rollouts can still use rolling semantics for low-risk changes while delegating high-risk releases to canary or blue-green strategies on the same Rollout resource—pick strategy per pipeline stage rather than per cluster.

The rolling math is bounded by replica count. With desired replicas of twenty, maxSurge: 25% allows five extra pods (ceil), and maxUnavailable: 0 forbids dropping below twenty ready endpoints—so the controller must create new pods before terminating old ones. With maxUnavailable: 1 and no surge, the fleet may briefly serve nineteen pods during each wave. Set minReadySeconds so a pod that flaps ready once must stay ready for that many seconds before counting toward availability; combined with realistic readiness probes, this stops a crashing new revision from advancing the rollout. PodDisruptionBudgets limit voluntary evictions during node drains; without a PDB, cluster maintenance can remove more pods than rolling math assumes and breach SLO during an unrelated upgrade.

Common failure modes

  • Premature readiness: Pods join Service endpoints before caches warm or connection pools fill; a traffic spike right after the wave starts causes elevated 5xx until JVM/CLR JIT or app caches catch up.
  • PDB omitted during node drain: A cluster upgrade evicts too many pods at once; availability drops below SLO even though the Deployment spec looked correct.
  • Insufficient termination grace: terminationGracePeriodSeconds too short for in-flight requests; clients see reset connections mid-roll.
  • Breaking change under rolling: New pods write a schema the old pods cannot read (or vice versa); errors appear only on the overlap window and are blamed on “flaky deploys.”
  • Progress deadline too generous: One bad replica blocks the entire rollout for hours with half old and half new versions—operators lack a clear failure signal.

Decision checklist

  • Does readiness verify downstream dependencies, not just process listen?
  • Is a PodDisruptionBudget defined for this Deployment?
  • Does preStop allow load-balancer deregistration before shutdown?
  • Will old and new versions remain compatible for the full expected rollout duration?
  • Is progressDeadlineSeconds set and alerting wired on stalled rollouts?
  • Are metrics and traces labeled by version or ReplicaSet during the roll?
  • Is kubectl rollout undo (or CI rollback) tested on a non-production cluster?

Example use cases

  • Illustrative scenario — A horizontally scaled REST API with 50 replicas deploys a backward-compatible bugfix weekly; maxUnavailable: 0, maxSurge: 25% completes in about ten minutes with no user-visible downtime.
  • Illustrative scenario — Background workers consume from a queue; the team pauses autoscaling during roll, drains in-flight jobs via graceful shutdown, and resumes—rolling remains safe because work is idempotent.
  • Case study — Kubernetes’ own documentation and countless production clusters use Deployment rolling updates as the default path; teams graduate to Argo Rollouts when they need automated analysis beyond native ReplicaSet replacement (Deployment strategies).
