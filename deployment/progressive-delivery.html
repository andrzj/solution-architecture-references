Deployment & Delivery

Progressive Delivery

Progressive delivery unifies continuous deployment with controlled exposure—traffic shaping, SLI gates, feature flags, and fast rollback when error budgets burn.

⏱ 10 min read

What it is

Progressive delivery is a delivery discipline that combines continuous deployment with deliberate, measurable exposure of change to production users. Coined in the GitOps and cloud-native community (notably James Governor and Weaveworks), it extends “ship often” with “expose slowly”: new versions, features, or configuration reach only a slice of traffic or users until service-level indicators (SLIs) and business metrics confirm safety.

The practice layers three mechanisms: deployment controls (canary, blue-green, or rolling updates that run multiple versions concurrently), application controls (feature flags that gate behavior inside a single binary), and verification (automated analysis against baseline metrics, error budgets, and custom promotion templates). Progressive delivery is the umbrella; canary releases and percentage rollouts are common implementations—not synonyms for the whole discipline.

Mature teams treat promotion as a closed loop: deploy → observe → expand or abort. Tools such as Argo Rollouts, Flagger, Spinnaker, and cloud deployment APIs encode steps, pauses, and analysis hooks so humans are not the bottleneck on every incremental weight increase.

Why it exists

Staging environments approximate production but rarely reproduce long-tail traffic mixes, partner failures, or data skew at scale. Big-bang deploys convert residual uncertainty into an all-users incident. Progressive delivery accepts that some defects surface only under real load, and constrains blast radius while generating statistical signal: if 2% of requests exhibit elevated 5xx rates, only that slice is affected while automation or operators halt promotion.

It also aligns delivery with SLOs and error budgets: rapid deploy velocity is sustainable only when failed promotions automatically stop burning budget. Feature flags add a second throttle—behavior can be disabled even when the new container image is already everywhere.

When to use

  • Customer-facing services with measurable SLIs and enough traffic for canary analysis within minutes.
  • High-impact flows—checkout, authentication, payments—where partial exposure is preferable to full cutover.
  • Organizations practicing continuous deployment that need guardrails beyond “hope staging caught it.”
  • Experiments and phased product launches that combine infrastructure canaries with in-app flag targeting.
  • Platform teams standardizing promotion templates (error rate, latency, saturation) across many microservices.

When not to use

  • Very low-traffic services where a canary slice never gathers statistically meaningful samples in an acceptable window.
  • Breaking schema or API changes that cannot run old and new versions side by side—plan expand/contract migrations first.
  • Teams without version-tagged metrics; promotion decisions become guesswork.
  • Batch or offline jobs where “traffic percentage” is meaningless—use staged inputs or shadow processing instead.

Typical architecture

A progressive delivery controller orchestrates replica sets or routes, queries observability backends, and either increases weight or triggers rollback. Feature flags provide parallel mitigations at the logic layer.

Pros and cons

Pros

  • Limits customer impact while still exercising production realism on every change.
  • Automates promotion against objective gates, reducing release-day heroics.
  • Combines infra-level and app-level controls for defense in depth.
  • Feeds post-incident learning: failed analyses produce artifacts (queries, thresholds) for the next rollout.

Cons

  • Requires mature telemetry—metrics by version, trace tags, and dashboards per rollout.
  • Longer wall-clock time from commit to full exposure; not every stakeholder accepts gradualism.
  • False positives from noisy metrics can abort healthy releases; tuning baselines is ongoing work.
  • Dual-version operation complicates debugging and doubles resource use during promotion.

Implementation notes

Define AnalysisTemplates (Argo Rollouts) or equivalent metric queries before the first production canary. Compare canary to stable baseline, not absolute thresholds alone—diurnal traffic shifts otherwise cause spurious aborts. Tag metrics and traces with version, rollout_id, or deployment labels so dashboards isolate the slice.

Pair every progressive deploy of risky logic with an ops feature flag default-off. Wire manual abort buttons in the control plane and runbooks that state order of operations: flag off first (instant), then traffic shift, then scale-down. Document minimum observation windows per step; “promote because CI passed” defeats the purpose.

Traffic splitting at the mesh layer routes by percentage without resizing fleets: Istio VirtualService weights, Linkerd traffic splits, and ingress controllers integrated with Flagger adjust share independently of pod counts. Session stickiness at the load balancer can starve the canary slice of representative traffic—either shorten affinity during rollout or analyze by route rather than by user cohort. Keep database schema compatible across stable and candidate revisions so partial traffic does not hit code paths that assume a contract migration already completed.

Common failure modes

  • Unrepresentative canary: Single replica on quiet nodes misses GC or cache effects visible only at fleet scale.
  • Metric lag: Promotion interval shorter than observability scrape or aggregation delay.
  • Session stickiness: Users never hit the canary slice, producing false confidence.
  • Flag/binary mismatch: New code at 100% traffic while flag still routes most users to legacy logic—analysis interprets the wrong variant.
  • No manual abort: Automation-only paths without an incident commander's kill switch.

Decision checklist

  • Are promotion and abort criteria defined per service with baseline-relative SLI queries?
  • Can metrics and traces filter by deployment version or rollout step?
  • Is there a feature-flag kill switch for the same change set?
  • Are minimum pause durations documented and enforced in the controller?
  • Does the runbook specify flag-off versus traffic-shift order?
  • Is there a post-rollout review when analysis aborts or barely passes?

Example use cases

  • Illustrative scenario — RideRelay’s booking API uses Argo Rollouts: 5% weight for ten minutes, automated Prometheus error-rate comparison against stable, then 25% and 50% with latency gates before full promotion.
  • Illustrative scenario — FieldOps ships a mobile-backend change with LaunchDarkly at 10% of enterprise tenants while Kubernetes runs a 20% infrastructure canary—either layer can halt exposure independently.
  • Case study — The Google SRE workbook’s canarying releases chapter describes metric-driven promotion and rollback patterns that underpin modern progressive delivery controllers.
