Infrastructure as Code

Infrastructure as Code defines cloud resources in versioned modules and environment stacks, with plan/apply workflows, remote state, policy scans, and drift detection aligned to the deployment pipeline.

⏱ 11 min read

What it is

Infrastructure as Code (IaC) is the practice of defining networks, compute, data stores, IAM, and platform resources in version-controlled files so environments can be planned, reviewed, applied, and reproduced consistently. Declarative tools describe desired end state; the engine computes a diff and converges the cloud control plane toward that state. Martin Fowler’s infrastructure as code essay frames this as treating infrastructure with the same discipline as application software.

Terraform (and the open-source OpenTofu fork) uses HCL, providers for many APIs, and a state file that maps configuration addresses to real resource IDs so plan can show intended changes (Terraform docs). Pulumi expresses infrastructure in general-purpose languages. AWS CloudFormation, Azure Bicep, and similar cloud-native stacks integrate tightly with their vendor APIs. Tools such as Ansible often orchestrate imperative steps and fit configuration management more than long-lived cloud resource lifecycle.

IaC underpins environment management: the same modules with different variables or workspaces yield dev, staging, and production stacks without hand-building consoles.

Why it exists

Console-driven infrastructure becomes tribal knowledge: dependencies stay undocumented, disaster recovery means archaeology, and staging diverges from production in ways tests cannot see. IaC makes the specification executable—pull requests show plan output, merges trigger controlled apply, and state (held remotely with locking) coordinates team changes. That pairs naturally with deployment pipelines that treat infrastructure changes as gated promotions, as Humble and Farley describe for automating environment creation in Continuous Delivery.

When to use

  • Use IaC for shared cloud or platform resources that must survive staff turnover and audits.
  • Use module composition when many environments should differ only in sizing, region, or policy variables.
  • Use plan-in-PR workflows when infrastructure changes need the same review rigor as application code.
  • Use policy scanners in CI when misconfiguration must be blocked before apply.

When not to use

  • Do not skip IaC for production paths just because a throwaway experiment is faster in the console—promote patterns into code before they become dependencies.
  • Do not treat IaC as a substitute for application deploy mechanics on Kubernetes; cluster provisioning and workload GitOps solve different layers.
  • Do not store long-lived secrets in plain state or committed files; integrate with a secrets backend instead.

Typical architecture

Reusable modules encapsulate VPCs, clusters, and data services; environment directories compose those modules, remote backends store state with locking, and CI runs fmt, validate, policy checks, and plan before approved apply.

Pros and cons

Pros

  • Infrastructure intent lives in Git with authors and messages, which supports audits and onboarding.
  • Shared modules make staging and production structurally alike even when capacity differs.
  • Plan output surfaces create, update, and destroy actions before any change hits the cloud API.
  • Scheduled or post-incident plans can detect console drift against declared configuration.

Cons

  • State is a dependency: corruption, lock failures, or manual state edits can block or misdirect applies.
  • Brownfield import from consoles is laborious and error-prone for large estates.
  • Provider gaps or lag behind new cloud features sometimes force workarounds.
  • Large monolithic states lengthen plans and widen blast radius of a single mistake.

Implementation notes

Store state remotely with encryption and cooperative locking (for example S3 with DynamoDB on AWS, GCS with locking on GCP, or HCP Terraform). Treat state as sensitive because it may embed credentials in outputs. Partition state by environment and domain so one team’s apply does not plan unrelated resources.

Run terraform fmt, validate, and policy tools such as Checkov on pull requests; post plan artifacts for reviewer sign-off. Use drift detection jobs that fail or alert when plan shows unexpected delta. For generated secrets, write them to a vault or cloud secret manager rather than leaving them only in state.

Tools like Terragrunt can DRY backend configuration across many folders. Combine IaC apply for clusters with GitOps for workloads so each layer has a clear owner.

Common failure modes

  • Concurrent apply without locking: Parallel applies corrupt state and produce unpredictable diffs.
  • Console hotfix not backported: Urgent manual edits disappear on the next apply and look like tool bugs.
  • Monolithic workspace: One giant root module couples unrelated systems and slows every plan.
  • Secrets in state only: Rotation and least-privilege become harder when credentials never leave Terraform state.
  • Ignored plan warnings: Destructive changes merge because reviewers skim large plans.

Decision checklist

  • Is state remote, encrypted, and protected by locking for every production workspace?
  • Is state split so blast radius matches team or system boundaries?
  • Do pull requests include human-readable plan output before merge to apply branches?
  • Does CI run static IaC security policy on changed files?
  • Is there scheduled or event-driven drift detection on critical workspaces?
  • Are generated credentials forwarded to secret management instead of living only in state?

Example use cases

  • Illustrative scenario — A platform team provisions a feature sandbox by applying a parameterized stack and destroys it after merge, avoiding long-lived manual sandboxes.
  • Illustrative scenario — Compliance asks for encryption defaults on object storage; reviewers point to module defaults and CI policy scan results rather than spot-checking consoles.
  • Illustrative scenario — A secondary region stack defined in the same modules as primary is reapplied during failover exercises so DR infrastructure matches current code.
  • Case study — Fowler’s IaC writing and HashiCorp’s Terraform tutorials document the plan/apply model; Google’s eliminating toil chapter motivates automating manual provisioning.

Related patterns

  • GitOps — Declares Kubernetes workloads after IaC provisions the cluster.
  • Environment Management — Uses IaC overlays to keep environments aligned.
  • CI/CD Pipelines — Gates infrastructure plan and apply like application releases.
  • Secret Management — Holds values IaC must not commit or expose casually.
