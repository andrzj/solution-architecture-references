Data Lakehouse

An architecture that combines the low-cost storage and flexibility of a data lake with the reliability, governance, and performance of a data warehouse using open table formats.

⏱ 10 min read

What it is

A data lakehouse is an architecture that keeps cheap object storage as the system of record while adding warehouse-like table semantics on top: ACID commits, schema evolution, snapshot history, and SQL access through engines such as Spark, Trino, or managed SQL warehouses. Instead of maintaining a separate copy in a proprietary warehouse for every curated dataset, teams register open tables—usually Parquet data files plus a format-specific metadata layer—and let multiple consumers query the same physical data.

The enabling formats are Delta Lake (transaction log alongside Parquet), Apache Iceberg (catalog-neutral table spec with broad engine support), and Apache Hudi (incremental upserts and CDC-friendly layouts). Choice depends on your query engines, upsert patterns, and catalog strategy—not on a single vendor default.

Why it exists

Classic lake-plus-warehouse stacks duplicate data, run brittle copy pipelines between tiers, and drift when loads fail silently. Lakehouses collapse curated analytics onto governed lake tables so batch, streaming, BI, and ML share one lineage. The pattern does not remove the need for dimensional modeling or semantic layers; it removes an extra physical hop when open formats and compute are mature enough to meet latency and governance goals.

When to use

  • When a greenfield platform should avoid maintaining parallel lake copy jobs and warehouse reloads for the same curated entities.
  • When ML feature pipelines and BI dashboards must read identical table versions without export-and-reload gymnastics.
  • When retention economics favor keeping analytical history on object storage with format-level governance.
  • When audit, reproducibility, or erasure workflows need snapshot history and row-level delete semantics on lake tables.
  • When multi-engine access (Spark batch, Flink streaming, Trino SQL, external warehouse readers) must share one table definition.

When not to use

  • Do not add lakehouse machinery when a managed warehouse already satisfies latency, security, and cost targets with less toil.
  • Do not self-host lakehouse infrastructure without platform skills for Spark/Flink operations, cataloging, and table maintenance.
  • Do not distribute metadata and clusters for datasets that fit comfortably on a single well-tuned analytical database or embedded OLAP tool.
  • Do not promise sub-second executive BI on cold object storage without benchmarking tail latency against dedicated warehouse compute.

Typical architecture

CDC, bulk load, and streaming writers land data into Iceberg, Delta, or Hudi tables on object storage. A shared catalog registers schemas. SQL engines and notebooks serve BI and ML; maintenance jobs compact files and expire snapshots so planners stay fast.

Pros and cons

Pros

  • One physical copy on object storage serves batch, streaming, BI, and ML consumers when formats and catalogs are shared.
  • ACID table semantics make concurrent writers and readers safe compared with raw prefix writes.
  • Snapshot history supports reproducible experiments, audits, and rollback analysis.
  • Open specifications let organizations swap or combine query engines without re-exporting data.
  • Unified pipelines reduce bespoke “copy to warehouse” jobs for every new mart.

Cons

  • Platform teams must operate catalogs, clusters, and format-specific maintenance—not just SQL schemas.
  • Compaction and snapshot expiration are ongoing duties; neglected tables accrue metadata debt quickly.
  • Interactive BI tail latency may trail dedicated warehouse caches unless you invest in managed SQL layers.
  • Cross-engine authorization (row filters, column masks) is less uniform than a single-vendor warehouse RBAC model.
  • Behavior differs by format and runtime—Delta on one vendor’s stack is not identical to Iceberg on another without integration testing.

Implementation notes

Anchor on one catalog (Glue, Hive metastore, Nessie, Unity, or equivalent) visible to every engine you plan to support. Pick Iceberg when multi-engine neutrality matters, Delta when Databricks is the control plane, Hudi when CDC upserts dominate. Document that choice in platform ADRs so new teams do not fork formats per project.

Automate maintenance: compact small files, rewrite manifests when planners slow, and expire snapshots according to legal retention—not “forever by default.” Test schema evolution against downstream readers before promoting breaking changes. Align with Iceberg, Delta, and Hudi documentation for procedure names and concurrency semantics on your chosen runtime.

Common failure modes

  • Snapshot accumulation: Historical snapshots are retained without expiration; planning time grows because metadata scans dominate execution.
  • Small files at scale: Streaming micro-batches create huge file counts; interactive queries slow even when data volume is modest.
  • Concurrent write conflicts: Optimistic commits fail under contention; jobs without retry logic leave partitions stale.
  • Catalog inconsistency: Lifecycle rules delete objects behind the table format’s back; metadata points at missing files and queries fail.
  • Schema evolution breakage: Hardcoded client schemas miss new required columns added by producers.

Decision checklist

  • Is the table format chosen for engine portability, upsert patterns, and catalog integration—not habit?
  • Are compaction and snapshot jobs scheduled, owned, and alerted?
  • Does every engine use the same catalog registration for a given table?
  • Are schema changes tested against BI, ML, and streaming consumers before merge?
  • Are row and column policies enforced consistently at the catalog or engine boundary?
  • Have representative BI queries been benchmarked against latency SLAs?

Example use cases

  • Illustrative scenario — An e-commerce team lands bronze Delta or Iceberg tables, promotes curated gold models with dbt-Spark, and serves SQL BI from a managed warehouse endpoint on the same storage without a nightly copy job.
  • Illustrative scenario — Flink writes CDC into Hudi or Iceberg while Spark batch jobs read the same table for reconciliation; Trino supplies ad hoc SQL without exporting to a separate database.
  • Illustrative scenario — A multi-team organization standardizes on Iceberg metadata so Athena, Snowflake external tables, and local DuckDB development all target one canonical table path.
  • Case study — The CIDR 2021 lakehouse paper (Lakehouse: A New Generation of Open Platforms) articulated how open formats and unified compute could subsume parts of the traditional two-tier lake and warehouse split; subsequent vendor and Apache ecosystem work on Iceberg, Delta, and Hudi operationalizes that model.

Related patterns

  • Data Lake — Raw and zoned storage that lakehouses govern with table formats.
  • Data Warehouse — Still relevant when managed SQL and RBAC outweigh open-format operations.
  • ETL vs ELT — Lakehouses favor in-place transformation on landed tables.
