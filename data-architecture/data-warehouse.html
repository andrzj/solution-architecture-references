Data Architecture Essential

Data Warehouse

A centralized analytical store optimized for read-heavy reporting workloads using dimensional modeling, columnar storage, and separated compute and storage.

⏱ 11 min read

What it is

A data warehouse is a centralized analytical datastore optimized for read-heavy reporting: large scans, joins across history, and repeatable aggregations that would contend with live transactions on an OLTP database. Data is modeled for business questions—facts and dimensions, conformed keys, and governed metrics—rather than for single-row updates. Cloud warehouses separate storage from elastic compute so many concurrent analysts can query shared history without resizing operational databases.

Modeling traditions include Ralph Kimball’s dimensional modeling (star and snowflake schemas tuned for BI tools) and Bill Inmon’s enterprise warehouse (normalized hub from which subject-area marts derive). Contemporary stacks usually blend both: raw staging replicas, a transformation layer (often dbt) that builds tested models, and presentation marts or a semantic layer where “revenue” means one definition everywhere.

Facts record measurable events at explicit grain (one line per order line, one row per daily active user); dimensions describe who, what, where, and when. Conformed dimensions—shared customer or product keys—let finance and marketing dashboards join without rebuilding incompatible surrogates. Slowly changing dimensions capture history when attribute changes matter for reporting: overwrite for corrections, effective-dated rows for audit trails, or limited prior-value columns when only the last change is legally relevant.

Why it exists

Row-oriented OLTP engines excel at concurrent short transactions but force aggregation queries to touch many columns stored with each record. Columnar warehouse layouts store each attribute contiguously so a query summing one measure reads only that column and benefits from encodings tuned for repeated values, as Martin Kleppmann describes in Designing Data-Intensive Applications. Heavy reporting on the production primary still competes for the same buffer pool and I/O as checkout and billing, which is why mature architectures land operational changes in a dedicated OLAP tier fed by ELT or streaming loads.

Warehouses also centralize policy: row-level security, masking, and retention windows apply once instead of per replica. Analysts iterate on SQL without ship cycles in application code, while engineers keep OLTP schemas normalized for write integrity. That separation is less about technology fashion than about protecting transactional SLAs while still answering questions that require scanning years of history.

When to use

  • When BI, finance, and operations need governed metrics across large historical datasets that would slow or destabilize OLTP if run in place.
  • When CRM, ERP, product, and marketing sources must conformed into one vocabulary for cross-functional reporting.
  • When regulators or auditors require reproducible numbers, lineage, and point-in-time snapshots of reported figures.
  • When self-service tools generate SQL against star schemas and benefit from a documented semantic layer or metrics catalog.
  • When feature engineering and batch ML training need warehouse-scale scans with SQL ergonomics and role-based access.

When not to use

  • Do not rely on a batch-loaded warehouse alone when dashboards require sub-minute freshness without an explicit streaming or CDC path.
  • Do not use a warehouse as the system of record for high-frequency row updates; OLTP or event-sourced write models remain authoritative.
  • Do not store raw unstructured blobs or wildly evolving JSON as the only copy; pair with a data lake or lakehouse landing zone.
  • Do not provision a warehouse when bounded reporting on a read replica or embedded OLAP already meets SLAs with less operational surface.

Typical architecture

Connectors replicate operational and SaaS sources into staging. SQL transformations (often Git-managed dbt projects) build dimensions and facts. BI tools and semantic layers query marts while pipelines monitor freshness and test keys and relationships.

Pros and cons

Pros

  • Columnar layouts, compression, and MPP execution align with aggregation-heavy SQL and large fan-in joins across conformed dimensions.
  • Isolates analytics from OLTP so reporting does not steal buffer cache or I/O bandwidth from transactional paths during month-end crunches.
  • A well-governed model can publish one definition of core metrics across BI tools, notebooks, and reverse-ETL APIs.
  • Elastic cloud warehouses scale compute for bursts without resizing operational databases or provisioning oversized read replicas.
  • Mature ingestion, transformation (dbt), and BI integrations reduce bespoke glue code and make schema drift visible in pull requests.
  • Time-travel or snapshot semantics on some engines simplify regulatory reproduction of reported numbers without mining application logs.

Cons

  • Batch or micro-batch loads introduce staleness that must be negotiated with dashboard SLAs and executive meeting cadences.
  • Schema and contract changes require coordinated migrations across facts, dimensions, and downstream dashboards tied to the same conformed keys.
  • Scan-heavy queries without partition discipline inflate cost in consumption-priced engines where billed bytes dominate the budget.
  • Unstructured and highly volatile semi-structured sources still need lake or lakehouse landing before relational models can enforce grain and types.
  • Source quality problems propagate unless tests, alerts, and ownership exist on every mart that finance treats as authoritative.
  • Privileged analyst access concentrates sensitive attributes in one place, raising governance work compared with fragmented OLTP silos.

Implementation notes

Manage transformations as software: versioned SQL in dbt (or equivalent), with sources, staging, intermediate, and mart layers. Test uniqueness, not-null, and relationships before promoting models that power executive metrics. Document grain on every fact table so join errors are obvious during review.

Choose slowly changing dimension types deliberately—Type 1 overwrites, Type 2 preserves history with effective dates, Type 3 keeps limited prior values. Match partitioning and clustering (or sort keys) to filters BI actually runs; missing partition predicates on time-series facts is a recurring cost and latency trap. Pair warehouse access with column masking or tokenization where PII appears, and surface freshness in the catalog next to each mart.

Stage ingestion should land raw replicas with lineage timestamps; transforms never mutate staging in place without auditable jobs. For incremental facts, watermark on change timestamps or CDC sequence numbers and document late-arriving rows—returns and chargebacks routinely violate naive “event time equals ingest time” assumptions. Snowflake-style transient tables, BigQuery partition expiration, and explicit archival to cold storage keep storage bills predictable without deleting compliance windows.

Common failure modes

  • Metric inconsistency: Competing SQL snippets or dashboard-specific calculations define revenue differently; executives lose trust in every chart.
  • Data quality propagation: Nullable keys from a source slip through untested joins and silently drop rows from reported totals.
  • SCD Type 2 explosion: High-churn dimensions grow unbounded; analysts forget effective-date filters and scans balloon.
  • Unbounded scans: Ad hoc queries omit date filters on partitioned facts and bill entire history every run.
  • Stale data without alerting: A failed nightly job leaves dashboards on yesterday’s slice until a human notices during a decision meeting.
  • Grain mismatch joins: Summing fact lines already at daily grain against hourly events double-counts activity and inflates conversion metrics.
  • Surrogate key churn: Rebuilding dimensions without preserving natural keys breaks longitudinal cohort analysis across mart reloads.

Decision checklist

  • Is the modeling approach (Kimball, Inmon, Data Vault, or hybrid) chosen and written down with naming standards?
  • Do dbt or equivalent tests guard keys, relationships, and business rules on every production mart?
  • Is freshness monitored with paging when loads miss their SLA window?
  • Do large tables use partitioning and clustering aligned with common filters?
  • Is there a single semantic layer or metrics project for headline KPIs?
  • Is sensitive data masked or restricted with column-level security tied to identity?

Example use cases

  • Illustrative scenario — An e-commerce company loads Shopify and CRM replicas into staging, builds a star schema of orders and customers in dbt, and serves executive revenue and attribution dashboards from governed marts.
  • Illustrative scenario — A bank partitions ledger facts by booking date, materializes regulatory aggregates, and runs dbt tests that block publish when duplicate transaction keys appear.
  • Illustrative scenario — A SaaS vendor exports product events nightly into the warehouse, models cohort retention facts, and gives product managers SQL access with row filters by tenant.
  • Case study — Kimball Group’s dimensional techniques remain the reference for star-schema design; teams pairing those ideas with dbt’s software-engineering workflow cite faster iteration without sacrificing testability on warehouse SQL.
