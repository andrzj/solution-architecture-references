Data Architecture

Data Contracts

Formal, versioned agreements between data producers and consumers — specifying schema, semantics, SLAs, and ownership to prevent silent breaking changes and enable trustworthy data pipelines.

⏱ 9 min read

What it is

A data contract is a versioned agreement between whoever produces a dataset or event stream and the teams that consume it. Beyond column types, it states semantics (what a field means), quality thresholds, freshness SLAs, ownership, and how incompatible changes get announced—so downstream jobs fail loudly instead of silently ingesting wrong-shaped data.

Serial forms usually live in Apache Avro, Protocol Buffers, or JSON Schema, registered in a schema registry that rejects publishes violating a chosen compatibility mode. The open Data Contract Specification layers YAML metadata—SLAs, quality rules, lineage hooks—on top of schema-only checks. Registries such as Confluent Schema Registry and AWS Glue Schema Registry automate enforcement at produce time.

In Zhamak Dehghani’s Data Mesh writing, each domain-oriented data product exposes a contract as its public interface under data as a product and federated computational governance. Consumers discover products through the catalog but rely on contracts to know how those products will behave over time—see Dehghani’s monolith-to-mesh essay and Fowler’s principles synthesis.

Structural compatibility—what a registry can prove—is only half the story. BACKWARD readers tolerate new schema versions when they deserialize historical payloads; FORWARD writers must not drop fields old consumers still expect; FULL locks both directions and suits tightly coupled analytics; NONE is an emergency escape hatch that should expire with an audit trail. Semantic drift—redefining “amount” as post-tax while the column name stays unchanged—passes green registry checks until business rules or model features fail in production.

Why it exists

Implicit assumptions about shared tables and topics fail once dozens of pipelines fork the same landing zone. A renamed column, narrowed type, or shifted timezone silently poisons dashboards and models because batch jobs do not throw on extra NULLs. Contracts move compatibility left: registries block incompatible schema versions, CI runs assertion suites on warehouse tables, and human notice periods give consumers time to adapt.

They also clarify accountability. When ownership, semantics, and escalation paths sit beside the schema, platform teams spend less time arbitrating Slack threads about “whose bug” broke revenue reporting. Mesh-aligned organizations treat the contract artifact as the durable interface while implementation details remain inside the domain.

Poor contracts externalize breakage: optional fields appear without notice, timezone shifts change daily aggregates, and nullable key columns silently widen until dashboards disagree with finance closes. Explicit SLAs, notice periods, and versioned semantics turn those surprises into scheduled migrations consumers can plan for.

When to use

  • When Kafka or similar brokers connect producers and consumers in different teams and schema drift would otherwise surface only in consumer lag or garbage payloads.
  • When a mesh or product-oriented data platform needs stable interfaces between domain-owned datasets and enterprise consumers.
  • When ML feature stores or regulatory reports depend on columns whose meaning and null rates must not change without review.
  • When warehouse tables feed multiple dbt projects, BI semantic layers, or partner exports that cannot coordinate informally on every deploy.
  • When audit or privacy programs require documented lineage tied to explicit field definitions and change policies.
  • When partner or regulator exports need frozen column semantics and published retention windows, not informal “ask the producer” agreements.
  • When multiple consumer teams deserialize the same topic or landing table and cannot attend every producer stand-up to learn about additive changes.

When not to use

  • Do not mandate contracts on exploratory sandboxes, personal scratch tables, or one-off notebooks where churn is the point.
  • Do not equate registry compatibility with semantic safety—a backward-compatible optional field can still break a model that inferred categories from absence.
  • Do not default every subject to FULL compatibility unless the organization accepts severely constrained evolution; BACKWARD suits most stream consumers reading historical data.
  • Do not deploy tooling without producer commitment—contracts maintained only by central governance become stale within a quarter.

Typical architecture

Producers own the contract repository entry, register schemas, embed schema identifiers in serialized messages, and publish quality metrics. Consumers pin reader schemas or dbt tests to contract versions; CI blocks merges that violate assertions. Mesh deployments link contract metadata to catalog entries so discovery shows freshness and owner alongside structure.

Breaking evolution paths favor multi-step releases: add a renamed column alongside the legacy field, dual-write during a notice window, migrate consumers under registry compatibility checks, then deprecate the old subject version. Warehouse contracts mirror the pattern—dbt exposures reference stable model contracts while silver-to-gold promotions run Great Expectations or Soda suites tied to the same YAML thresholds product managers cite in SLAs.

Pros and cons

Pros

  • Stops incompatible schema publishes at the broker or CI boundary instead of hours later in silent metric drift.
  • Documents owner, semantics, and escalation paths beside machine-readable schema.
  • Lets consumers evolve independently when compatibility rules and notice windows are respected.
  • Connects automated dbt, Great Expectations, or Soda checks to the same thresholds product managers reference.
  • Supplies audit evidence for regulated fields when paired with catalog lineage and classification.
  • Makes additive stream evolution routine when BACKWARD mode and field defaults are understood by every producing service.

Cons

  • Imposes ongoing producer workload—contracts decay without owners and version discipline.
  • Restricts quick hacks: renames and type changes need multi-step migrations with aliases or dual writes.
  • Semantic gaps remain; prose definitions still require human review for business-breaking shifts.
  • Registry, contract repo, and CI integration carry platform cost before benefits compound.
  • Emergency bypasses (compatibility NONE) tend to linger unless governance audits configuration.
  • Cross-team negotiation overhead rises when every nullable addition still needs semantic review beyond registry green lights.

Implementation notes

On Kafka, use registry-aware serializers for every producer; default subjects to BACKWARD unless readers truly never read history. Document when to choose FORWARD or FULL per Confluent’s compatibility types. Store contract YAML in Git beside infrastructure so SLAs and semantics version with schema.

For warehouse tables, encode quality as executable tests—dbt not_null, unique, relationships, or Great Expectations suites—and fail deploy pipelines on regression. Publish semantic definitions in the business glossary and link them from contract YAML so “revenue” cannot mean pre-tax in one subject and post-tax in another without a version bump. Align the open Data Contract Specification fields (owner, quality, service-level) with what you already expose in Datadog or Monte Carlo.

Instrument freshness monitors on the same thresholds contracts promise: if YAML says five-minute lag, dashboards and paging rules must reference the same metric IDs consumers read in the catalog. Reject raw JSON producers that bypass registration; shadow traffic in staging should exercise reader schemas against canary payloads before promotion.

Pair technical gates with process: breaking changes require consumer acknowledgement, semantic release notes, and catalog updates. In mesh topologies, treat the contract as the data product’s API; Dehghani’s platform principle expects domains to publish these interfaces without a central modeling committee.

Common failure modes

  • Registry bypass: Raw JSON producers skip registration; compatibility checks never run until consumers deserialize garbage.
  • Permanent NONE mode: A “temporary” loosening of compatibility survives post-incident and accumulates unreviewed schema drift.
  • Semantic break behind green CI: Adding a nullable enum value passes Avro checks but invalidates downstream business rules.
  • Rename via edit instead of migration: Changing Avro field names in place fails registry rules; teams need add-alias-deprecate patterns.
  • SLA without telemetry: Freshness promises in YAML lack monitors, so stale data reaches executives before anyone pages.
  • Dual schema truth: Producers maintain Avro in the registry while warehouse DDL diverges manually, so stream and table contracts disagree on required fields.

Decision checklist

  • Is a schema registry the mandatory path for every production topic serializer?
  • Does each high-value dataset have an owner, semantic glossary, and documented compatibility mode?
  • Are warehouse quality rules tied to CI so contract violations block release?
  • Do producers notify consumers before backward-compatible additions that still alter semantics?
  • Does the catalog surface contract version, freshness SLO, and last assertion status?
  • Are emergency registry overrides time-boxed and audited?

Example use cases

  • Illustrative scenario — Payments emits payment.completed with Avro registered BACKWARD; fraud adds optional risk_score without forcing a coordinated consumer deploy.
  • Illustrative scenario — A feature table’s dbt tests enforce null-free keys; an upstream bug fails CI before corrupted rows reach the online model.
  • Illustrative scenario — Orders domain publishes a mesh data product with contract YAML listing 14-day notice; analytics schedules migration when line_items JSON shape changes.
  • Illustrative scenario — A platform bot comments on pull requests that touch owned dbt models, linking the contract diff and listing consumer teams that acknowledged the prior semantic version.
  • Case study — Large-scale schema discipline narratives include Uber’s Schemaless series and Confluent’s registry guides; Dehghani’s mesh essays motivate treating contracts as product interfaces.
