Data Architecture Storage

Data Lake

A centralized repository storing raw data in any format at any scale with schema-on-read semantics, organized in zones with open table formats to provide ACID transactions and governance.

⏱ 10 min read

What it is

A data lake is a centralized repository that stores raw, semi-structured, and structured data in native formats at scale, usually on object storage, and interprets schema at read time rather than at ingest (schema-on-read). Teams land events, files, database extracts, and model outputs in one durable tier so exploration, archival, and downstream modeling can proceed without forcing every source into a single warehouse schema first.

Mature lakes layer open table formats—Delta Lake, Apache Iceberg, and Apache Hudi—over columnar files such as Parquet. Those formats add transaction logs, schema evolution, snapshot history, and safer concurrent writes than ad hoc file drops alone. Organizing data into zones (for example bronze raw, silver cleaned, gold curated in a medallion layout) keeps provenance clear and supports governance without abandoning cheap scale-out storage.

Why it exists

Warehouses and OLTP systems expect schemas and contracts before load. Product and data science teams often need months of raw clickstream, logs, sensor readings, and JSON exports to discover what to model. A lake absorbs that heterogeneity immediately while ELT, feature engineering, and warehouse loading catch up in parallel.

Object storage decouples capacity from database licensing and fits long retention of immutable history. Without catalogs, lineage, and quality gates, the same flexibility produces a data swamp—hence table formats, zone policies, and catalog integration as standard practice. The lakehouse pattern extends these ideas by running warehouse-style SQL and ACID semantics directly on lake storage.

When to use

  • When you must retain raw event logs, clickstream, IoT readings, or semi-structured payloads whose shape is still evolving at ingest time.
  • When the lake is the landing zone that preserves source fidelity before warehouse or lakehouse transformations run.
  • When ML and experimentation need full historical extracts and feature engineers work in Spark, notebooks, or SQL engines over the same files BI will eventually govern.
  • When compliance or science requires long archival of immutable raw data that is queried infrequently compared with curated marts.
  • When one storage tier must hold tables, documents, and large binary assets without forcing everything through a single relational schema.

When not to use

  • Do not treat an unmodeled lake as the sole BI platform; governed metrics and dimensional models still live in a warehouse or curated gold zone unless a lakehouse path is explicitly designed.
  • Do not skip catalog, ownership, and quality standards when access control and trust are non-negotiable.
  • Do not use object storage as an OLTP system of record; per-object latency and consistency models suit analytics and batch, not interactive row updates.
  • Do not add lake infrastructure when every workload is already well served by a warehouse and sources are stable, structured, and contract-bound.

Typical architecture

Sources land in a bronze zone; silver applies validation and conformed schemas; gold exposes business-ready datasets for BI, ML, or warehouse load. Open table formats sit between raw files and query engines so compaction, partitioning, and ACID commits are explicit operations rather than tribal conventions.

Pros and cons

Pros

  • Ingest-first flexibility accepts diverse formats and defers modeling until consumption patterns are clear.
  • Object storage plus open file formats typically cost less per retained terabyte than keeping all history in warehouse-native storage.
  • Capacity grows with usage instead of upfront database sizing.
  • Compute and storage separate so Spark, Trino, Flink, and warehouse external tables can share one canonical copy of data.
  • Iceberg, Delta, and Hudi reduce lock-in because multiple engines read the same table metadata and Parquet payloads.

Cons

  • Without catalogs, lineage, and stewards, lakes become swamps where trust erodes faster than data accumulates.
  • Interactive BI latency usually trails purpose-built warehouses until partitioning, compaction, and caching are disciplined.
  • Fine-grained column security and row filters are harder to enforce consistently across engines than in a single warehouse RBAC model.
  • Operating distributed compute, compaction jobs, and format-specific maintenance requires platform skills beyond SQL-only teams.
  • Raw file writes without table formats risk partial outputs and conflicting writers corrupting downstream reads.

Implementation notes

Adopt medallion zones or an equivalent quality ladder: bronze keeps immutable landing copies, silver enforces contracts and deduplication, gold publishes curated datasets for BI and ML. Document promotion rules so consumers know which zone is authoritative for which metric.

Pick a table format deliberately. Iceberg emphasizes multi-engine catalogs and hidden partitioning; Delta integrates tightly with Databricks workflows; Hudi optimizes upserts and incremental pipelines. See the official guides for write semantics, compaction, and snapshot retention in Iceberg, Delta Lake, and Hudi.

Schedule compaction and monitor file counts and average object size; streaming micro-batches often create small files that dominate metadata overhead. Register tables in a shared catalog, wire data contracts at silver promotion, and classify PII before wide internal access. For erasure requests, combine row-level deletes supported by the format with snapshot expiration policies documented with legal retention limits.

Common failure modes

  • Data swamp: Datasets accumulate without owners, descriptions, or quality checks, so every project rediscovers the same tables via Slack instead of the catalog.
  • Small file problem: High-frequency writers emit tiny objects; planners spend disproportionate time listing metadata before reading data.
  • Concurrent writer corruption: Jobs write to the same prefix without transactional table semantics and clobber each other's outputs.
  • Uncontrolled PII ingestion: Production replicas land in bronze without classification; notebook exports leak sensitive columns because access was file-granular only.
  • Schema drift: Hardcoded schemas in jobs ignore new JSON fields that the catalog already documents, silently dropping business-critical attributes.

Decision checklist

  • Are new datasets written through Iceberg, Delta, or Hudi rather than unmanaged object prefixes?
  • Are bronze, silver, and gold (or equivalent) quality standards documented and enforced in CI?
  • Does every production table have a catalog entry, owner, and freshness expectation?
  • Is PII classified at or before silver, with access policies tied to classification?
  • Are compaction and snapshot maintenance jobs scheduled and alerted on failure?
  • Do automated checks cover row counts, null rates, and contract violations on promotion?

Example use cases

  • Illustrative scenario — A video platform lands raw clickstream JSON in bronze, converts to partitioned Parquet in silver with schema tests, and exposes session aggregates in gold for recommendation features and BI.
  • Illustrative scenario — An industrial operator streams sensor Avro captures into a lake, normalizes readings in silver Delta tables, and serves operational dashboards from gold while ML retrains on the same history.
  • Illustrative scenario — A regulated enterprise retains immutable log and audit bronze copies for years on cold storage tiers and uses Iceberg time travel during investigations to reproduce table state at a past timestamp.
  • Case study — Netflix’s open sourcing of Apache Iceberg and Uber’s Apache Hudi popularized table formats that brought warehouse-style reliability to object storage; Databricks’s Delta Lake followed a similar path for Spark-centric estates.

Related patterns

  • Data Warehouse — Curated dimensional models and semantic layers often consume gold-zone lake outputs.
  • Data Lakehouse — Runs governed SQL and ACID semantics directly on lake storage.
  • Data Cataloging — Discovery and lineage that keep lakes governable instead of opaque.
