Vector Databases

Storage and approximate nearest-neighbor (ANN) search over high-dimensional embedding vectors — the retrieval backbone for RAG, semantic search, recommendation systems, and similarity matching in AI applications.

⏱ 10 min read

What it is

A vector database (or vector index inside another store) persists embeddings—fixed-length float vectors from ML models—and answers approximate nearest neighbor (ANN) queries: given a query vector, which stored vectors are closest under cosine, dot product, or L2 distance?

Purpose-built systems include Pinecone, Weaviate, Qdrant, and Milvus; embedded options include pgvector on PostgreSQL, Redis vector search, Elasticsearch dense_vector, and MongoDB Atlas Vector Search when documents and vectors should co-locate. Indexes are dominated by HNSW (graph-based, high recall, RAM-heavy) and IVF (inverted lists with probes).

Kleppmann’s secondary-index discussion in Designing Data-Intensive Applications applies: ANN structures are maintenance-heavy, approximate, and must be validated on domain queries—not benchmark slogans.

Managed offerings—Pinecone, Azure AI Search, Google Vertex AI Vector Search—trade control for operations when teams lack capacity to babysit shards. Open-source Milvus and Qdrant suit Kubernetes-native estates that want filtering and horizontal scale in-house. Weaviate emphasizes multi-modal schemas and GraphQL APIs; co-located stores such as Elasticsearch dense_vector or OpenSearch k-NN matter when lexical and vector retrieval must share one cluster.

HNSW graphs deliver high recall with millisecond queries but consume RAM for edge lists and tolerate slow rebuilds after large ingest. IVF clusters vectors into inverted lists probed at query time—cheaper builds and smaller memory at the cost of tuning list counts and probe depth. Product selection is less about brand than about whether your SLA tolerates approximate ranking and how often the corpus re-embeds.

Why it exists

Keyword search fails when vocabulary diverges from user intent; embeddings map text, images, or audio into spaces where semantic nearness is geometric nearness. Exact k-NN over millions of 1k–3k dimensional vectors is CPU-prohibitive for interactive SLAs.

ANN indexes trade guaranteed optimality for throughput and latency, exposing knobs (ef_search, probes, quantization) that teams must tune against labeled evaluation sets. RAG architectures ground LLM outputs by retrieving chunks from this layer; without it, prompts hallucinate or omit policy-sensitive context.

Keyword systems still win for error codes, SKUs, and statutory phrases where exact tokens carry legal weight. Vectors complement those engines: a query about “comfortable walking footwear” should surface hiking boots and insoles even when the catalog copy never repeats the user’s adjectives. Hybrid pipelines—BM25 shortlist plus vector rerank, or the reverse—remain the pragmatic default in commerce and support tooling because neither signal alone survives production tail queries.

Embedding model upgrades are breaking changes for the index—plan reindex windows and dual-read periods like schema migrations. Store model name and dimension on every vector metadata field for forensic comparison when ranking quality regresses after a silent model swap.

When to use

  • RAG and enterprise search where natural-language questions must retrieve policy, runbooks, or product docs by meaning.
  • Recommendations based on embedding similarity of items, sessions, or multi-modal assets.
  • Deduplication and near-duplicate detection for media, code, or support tickets.
  • Anomaly cues when “far from all neighbors” signals novelty—paired with human review.
  • Hybrid retrieval stacks combining BM25 filters with vector ranking for SKU-heavy catalogs.
  • Multi-modal search when images, audio, and text share one embedding index for similarity—common in catalog and media libraries.
  • Internal copilots that must cite runbooks, contracts, or policy PDFs with tenant-scoped metadata filters on every query.

When not to use

  • Exact identifier lookup (order ID, error code)—use btree or inverted indexes.
  • Tiny corpora where pgvector brute force or small HNSW on Postgres suffices.
  • Compliance-only search without recall evaluation—ANN false negatives are silent failures.
  • Teams unable to operate embedding refresh pipelines when source documents change.
  • Problems solved well by graph traversals or SQL joins alone—vectors add cost without lift.

Typical architecture

Content lands in object storage or CMS; a pipeline chunks text, calls an embedding API or local model, and upserts vectors with metadata (tenant, ACL, version). Query paths embed the question, run top-K ANN with metadata filters, optionally rerank, then pass chunks to an LLM or UI. Pros and cons

Pros

  • Captures intent and synonymy that keyword indexes miss—essential for conversational interfaces.
  • ANN indexes deliver interactive latency at million-plus scale when tuned.
  • Metadata-filtered vector search supports tenant isolation and ACL-aware retrieval.
  • Model upgrades are localized to re-embedding jobs; storage layout can remain stable.
  • Colocated pgvector reduces moving parts for moderate corpora already on PostgreSQL.
  • Quantization and product-native sharding paths help when single-node RAM ceilings approach millions of high-dimensional vectors.

Cons

  • ANN recall gaps are invisible without labeled eval harnesses.
  • HNSW RAM footprint scales superlinearly—capacity planning is non-optional.
  • Chunking and embedding version choices dominate RAG quality more than index brand.
  • Re-embedding entire corpora on model changes is a scheduled migration, not a toggle.
  • Distance metric mismatches silently degrade ranking until indexes are rebuilt.

Implementation notes

Pick distance ops to match model training: pgvector index opclasses (vector_cosine_ops, etc.) must align with embedder docs. Tune HNSW m, ef_construction, and session hnsw.ef_search against a held-out query set; log recall@k and nDCG in CI for retrieval changes.

Chunk with overlap sized to model context—headings-aware splits beat naive fixed token windows for policy docs. Store content hash and embedding model version on each row to trigger partial re-embed jobs. Cache query embeddings when models are deterministic.

Ship hybrid retrieval (vector + BM25 via Elasticsearch/Postgres FTS) with reciprocal rank fusion for SKU- and error-code-heavy domains. For MongoDB workloads, define Atlas vector index definitions alongside document validators so metadata filters stay consistent.

On pgvector, raising HNSW m and ef_construction improves recall at build time while session hnsw.ef_search controls exploration during queries—benchmark both on held-out questions rather than defaulting to tutorial values. IVF indexes benefit when lists scales roughly with the square root of row count and probes targets ten to twenty percent of lists for latency-sensitive paths.

Production RAG should log retrieval IDs, similarity scores, and embedding model version per answer so incident review can distinguish chunking bugs from index regressions. Pair offline nDCG or recall@k suites with canary queries that include rare acronyms and multilingual phrases your tokenizer might otherwise bury.

Index trade-offs: HNSW and IVF families differ in recall/latency/memory—tune from measured query sets, not vendor defaults. Embedding model changes require reindex or dual-write periods; version vectors in metadata so retrieval does not mix incompatible spaces.

Governance: DAMA-style lineage applies to source documents and chunk policies; PII in embedded text needs classification at ingest. Archiving corpora to Iceberg/Delta tables can hold raw text while vectors live in the specialist index—document authoritative deletion paths for erasure requests.

Hybrid retrieval: BM25 plus vector fusion improves recall when keywords matter (SKUs, regulations); pure semantic search misses exact tokens. Rerankers add latency—budget end-to-end p95 in the serving path, not only index query time.

Filters: metadata pre-filtering (tenant, doc type) shrinks ANN search space; enforce ACL filters before k-NN, not after, to avoid leaking neighbours across tenants.

Chunking strategy is part of the model—identical embeddings on overlapping windows inflate storage without retrieval gain; measure recall on held-out Q&A sets when changing chunk size.

Canary queries after index rebuilds should include non-English and rare-token cases when the product serves multilingual users.

Index build jobs should run on replicas when the primary serves live queries—full rebuilds contending with ANN search inflate tail latency.

Access control on vector collections must mirror source document ACLs—embedding search without metadata filters is a lateral movement path.

Common failure modes

  • Stale vectors after edit: CMS updates without re-embed jobs cause RAG citations to reference withdrawn policy.
  • No offline eval: Demo queries look fine; production long-tail queries miss 30%+ relevant docs.
  • Micro-chunks: Sentence-level splits retrieve irrelevant snippets lacking definitional context.
  • RAM cliff: High m HNSW on tens of millions of vectors without horizontal sharding collapses nodes.
  • Metric mismatch: Euclidean index on cosine-normalized embeddings ranks plausible neighbors incorrectly.
  • Filter leakage: Tenant or ACL metadata applied only at the application layer lets cross-tenant chunks appear in ANN results before post-filtering drops them.

Decision checklist

  • Is there a labeled query set representing production traffic for recall measurement?
  • Does embedding model choice, dimensionality, and distance metric appear in architecture docs?
  • Are chunking rules versioned and tested against token limits of downstream LLMs?
  • Is re-embedding scoped by content hash when sources change?
  • For pgvector: is ANN sufficient at projected N, or is a dedicated shard required?
  • Are ACL metadata fields enforced on both ingest and query filters?
  • Is memory headroom modeled as raw vector bytes plus index overhead before the first production reindex?

Example use cases

  • Illustrative scenario — Internal IT embeds runbooks in pgvector, retrieves top chunks per incident description, and requires the LLM to cite chunk IDs in responses.
  • Illustrative scenario — A retailer hybrid-searches SKU tokens with BM25 and merges with description embeddings for natural-language browse.
  • Case study — Streaming platforms publicly describe embedding similarity for discovery—illustrative of ANN at catalog scale with metadata filters.
  • Illustrative scenario — A forty-thousand-document policy library chunks at eight-hundred-token windows, embeds with a small commercial model, and requires support answers to list chunk IDs so auditors can replay citations.
  • Illustrative scenario — An engineering org embeds functions with a code-oriented model to flag semantic duplicates in pull requests before human review escalates license or provenance risk.
