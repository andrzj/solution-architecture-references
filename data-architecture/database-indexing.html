Database Indexing

Matching PostgreSQL index access methods to query predicates—B-tree, GIN, GiST, BRIN, covering and partial indexes—and validating plans with EXPLAIN ANALYZE instead of guessing.

⏱ 10 min read

What it is

Database indexing maintains auxiliary access paths—B-tree nodes, inverted lists, block summaries—so the engine can find rows by key or predicate without scanning every page in the heap. Each index adds storage and must be updated on writes; in exchange, selective reads drop from sequential scans over the full table to bounded tree or bitmap walks.

This article centers on PostgreSQL, where the planner chooses sequential scan, index scan, bitmap index scan, or index-only scan from statistics and cost estimates. The indexes and index types chapters map access methods to predicates: B-tree for equality, range, and sort; GIN for arrays, jsonb, and full-text; GiST for geometry and ranges; BRIN for very large, physically ordered tables. Partial indexes, INCLUDE covering columns, and expression indexes extend the same model.

At scale the gap is stark: a million-row heap may still satisfy occasional admin queries with a sequential scan, but the same filter on a hundred-million-row ledger without an index can pin disks for tens of seconds. B-tree remains the default access method—balanced pages that support equality, inequalities, IN, prefix LIKE, and ORDER BY when key order matches sort order. Hash indexes target equality only and rarely beat a well-maintained B-tree in PostgreSQL; treat them as a niche unless benchmarks prove otherwise. GIN builds inverted lists per composite element (array entries, JSON keys, lexemes), which powers containment and full-text operators that B-trees cannot represent. GiST handles geometry, range overlap, and nearest-neighbor predicates where ordering is approximate or multidimensional. BRIN stores per-block min/max summaries and shines when insert order correlates with filter columns on append-mostly facts.

Why it exists

Heap tables are fast for bulk maintenance and simple full-table analytics, but OLTP paths that filter on a handful of columns pay linear cost in table size. Without indexes, a selective lookup on a billion-row ledger still reads the entire relation; foreign-key checks and cascades devolve into the same pattern. Indexes localize I/O to the matching row set and give the optimizer an alternative when estimated selectivity crosses its threshold.

The hard part is not creating indexes but choosing the few that match real query shapes. Misaligned indexes waste disk, slow every mutation, and may never appear in plans if predicates wrap columns in functions or statistics lie. Sound practice pairs schema design with EXPLAIN evidence rather than indexing every column by convention.

When to use

  • When production queries filter, join, or sort on columns that return a small fraction of rows and EXPLAIN shows recurrent sequential scans on large relations.
  • When foreign keys and referential integrity require fast lookups on child columns during parent updates and deletes.
  • When a hot read path can be satisfied with an index-only scan via INCLUDE or a tight composite key aligned to WHERE and ORDER BY.
  • When JSON containment, array membership, or full-text operators appear in predicates and need GIN (or GiST for nearest-neighbor or range overlap).
  • When append-only time-ordered tables are huge and range queries align with physical insert order, making BRIN a compact alternative to B-tree.
  • When staging or batch tables will graduate to production traffic and you want indexes in place before the first customer query after cutover.
  • When uniqueness or exclusion constraints (for example duplicate prevention on natural keys) require a backing index the planner can exploit for lookups.
  • When GiST-backed PostGIS or range types appear in geographic or scheduling predicates that B-tree cannot index meaningfully.

When not to use

  • Do not index ultra-low-cardinality columns used alone in predicates that return large fractions of the table—the planner may correctly ignore the index.
  • Do not add indexes “just in case”; each one amplifies write latency and vacuum work on churny tables.
  • Do not assume presence implies usage—verify plans after deploy and drop indexes with persistently zero idx_scan in pg_stat_user_indexes.
  • Do not duplicate redundant indexes on the same leading columns; PostgreSQL maintains both without prioritizing either.
  • Do not index volatile computed columns that change every row touch unless the expression is truly stable and documented with IMMUTABLE discipline.
  • Do not create GIN on wide JSON documents before profiling which keys filters use—blanket GIN on large payloads slows writes without helping dominated predicates.
  • Do not rely on multicolumn statistics alone to rescue a fundamentally misordered composite index; redesign the key or split access paths instead.

Typical architecture

Start from workload capture: log or sample top queries, group predicates and sort keys, then map each pattern to the smallest index family that can serve it. Stage changes on replicas with EXPLAIN (ANALYZE, BUFFERS), roll out with CREATE INDEX CONCURRENTLY where tables stay writable, and feed index usage back into capacity planning.

Pros and cons

Pros

  • Turns selective reads from scans proportional to heap size into tree walks or bitmap combinations bounded by matching row counts, which keeps p99 latency flat as tables grow.
  • Covering and index-only scans remove heap fetches when the visibility map marks pages all-visible, shaving microseconds per row on hot OLTP paths that repeatedly fetch the same narrow projection.
  • Partial indexes shrink working set and maintenance cost when business logic concentrates on a stable subset of rows such as open tickets, active subscriptions, or unprocessed events.
  • BRIN delivers enormous space savings on monotonic time-series compared with B-tree while preserving acceptable range performance when queries honor correlation with physical insert order.
  • GIN unlocks containment, membership, and full-text operators that would otherwise force full-table scans on document-like columns or wide array fields.
  • Unique indexes double as integrity enforcement and fast conflict detection on natural or business keys during concurrent upserts and batch loads.

Cons

  • Every index participates in write amplification; over-indexed OLTP tables show up as lock contention, buffer churn, and elevated autovacuum cost during update-heavy windows.
  • B-tree and GIN structures bloat after heavy updates; without VACUUM and occasional REINDEX CONCURRENTLY, scans read dead pages and inflate I/O despite nominally healthy index definitions.
  • The planner may still choose sequential scan for wide result sets, correlated subqueries, or bad cardinality estimates after migration or bulk load.
  • GIN builds are slow and writes are heavier than B-tree; bulk ingest into GIN-heavy tables needs staging strategies, deferred index creation, or maintenance_work_mem tuning.
  • Composite indexes honor left-prefix rules; secondary-column-only filters need separate indexes, expression keys, or redesigned queries that lead with the indexed prefix.
  • Index maintenance windows on large tables may require hours of CREATE INDEX CONCURRENTLY and still block if operators underestimate disk headroom during builds.

Implementation notes

Instrument with EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) on statements that matter for SLOs. Compare estimated versus actual row counts; sustained divergence triggers ANALYZE or targeted statistics extensions. Read the official guidance on index-only scans and partial indexes before defaulting to full-table B-trees.

Build production indexes with CREATE INDEX CONCURRENTLY and track progress via pg_stat_progress_create_index. Order composite keys: equality columns first, then range, then sort columns mirroring the query. Expression indexes (for example LOWER(email)) belong in the migration that introduces wrapped predicates—not as retroactive band-aids.

Review pg_stat_user_indexes quarterly; drop duplicates and zero-scan indexes. For jsonb and FTS, pick operator classes deliberately—GIN and BRIN docs list tradeoffs between build time, query operators, and index size.

Treat index design as a living contract with application queries: capture top statements from pg_stat_statements, tag them with expected plans, and regression-test EXPLAIN output in CI when migrations add predicates. When loads spike, temporarily raise maintenance_work_mem for index builds and validate autovacuum keeps pace so HOT updates do not collapse into full index tuple churn. For partitioning, align local indexes on each child with partition pruning predicates—global indexes on the parent are not the PostgreSQL model, so cross-partition sorts may need redesigned keys or federation.

Hash indexes aside, prefer proving necessity with benchmarks on production-sized clones. Document each production index in schema metadata: owning team, query class served, expected selectivity band, and last verification date from EXPLAIN evidence so future migrations do not accidentally drop silent performance anchors.

Common failure modes

  • Immutable function on indexed column: Wrapping a column in LOWER() or casting mismatched types prevents btree use until a matching expression index exists.
  • Leading wildcard LIKE: Prefix searches can use B-tree with the right operator class; substring patterns need trigram GIN or a search engine.
  • Unindexed foreign key: Parent deletes scan entire child tables, producing surprise wait events under concurrency.
  • Stale statistics after bulk load: Plans flip to sequential scan until ANALYZE catches up, masking otherwise valid indexes.
  • Redundant index sprawl: Multiple overlapping composites inflate storage and slow vacuum without improving plans.
  • OR predicates across columns: Disjunctive filters often defeat a single composite; bitmap OR combinations help when each branch has its own index, otherwise redesign with UNION or partial indexes per branch.
  • Implicit type coercion: Comparing a text column to integer literals may block index use until casts align with indexed expression definitions.
  • Long idle transactions: Open snapshots prevent vacuum from reclaiming dead tuples, bloating indexes even when application traffic is quiet.
  • Monitoring blind spots: Teams watch CPU but not index bloat until sequential scans reappear weeks after a mis-tuned autovacuum threshold change.

Decision checklist

  • Are foreign-key columns indexed on the referencing (child) side?
  • Do composite indexes match equality-then-range column order for the top queries?
  • Are JSONB, array, and full-text filters backed by appropriate GIN operator classes?
  • Has EXPLAIN ANALYZE confirmed index use for each performance-critical statement?
  • Are unused or duplicate indexes identified via pg_stat_user_indexes and removed on a schedule?
  • Are new production indexes created concurrently with a rollback plan if build fails?
  • Does each critical index have an owner and documented query class in schema metadata or runbooks?
  • After bulk loads, is ANALYZE scheduled before traffic returns so plans reflect new row counts?
  • Are partition-local indexes created on every child before attaching partitions to avoid sequential scans on new ranges?

Example use cases

  • Illustrative scenario — An order API paginates by created_at per user_id; a covering B-tree on (user_id, created_at DESC) INCLUDE (total, status) enables index-only scans for heavy shoppers.
  • Illustrative scenario — A compliance team scans last-quarter events from a multi-terabyte append-only log; BRIN on recorded_at keeps index size negligible while skipping unrelated heap ranges.
  • Illustrative scenario — Inbox queries touch only unread rows; a partial index matching WHERE read = false tracks the active slice instead of the full notifications heap.
  • Case study — Practitioners commonly pair PostgreSQL’s B-tree documentation with Markus Winand’s Use The Index, Luke when onboarding teams to systematic index reviews.
  • Illustrative scenario — A tenant-aware SaaS routes every OLTP read through WHERE tenant_id = $1; a composite on (tenant_id, external_id) plus a partial unique index on active rows removes both full-table scans and duplicate integration keys.
  • Illustrative scenario — Search over product SKUs with fuzzy substring needs pg_trgm GIN on normalized text columns; exact-match catalog lookups stay on B-tree while exploratory admin search uses the trigram path.
