Time-Series Databases

Databases purpose-built for time-stamped sequential data — sensor readings, metrics, financial ticks — with native support for retention policies, continuous aggregates, downsampling, and cardinality-aware indexing.

⏱ 9 min read

What it is

A time-series database (TSDB) optimizes for measurements stamped with time: values (fields) plus identifying dimensions (tags or labels). Workloads are dominated by sequential append, time-windowed aggregation, and downsampling—not by arbitrary many-to-many joins across business entities.

Kleppmann’s Designing Data-Intensive Applications explains why columnar, partitioned, and log-structured layouts win when reads scan ordered time ranges and writes arrive in bursts. Engines differ by protocol and ops model: Prometheus pull metrics with PromQL; InfluxDB line protocol ingest; TimescaleDB hypertables on PostgreSQL for SQL joins; VictoriaMetrics/Thanos for long-term Prometheus storage; Timestream managed; Cassandra-style partition+time clustering for DIY telemetry at extreme ingest.

Cardinality—the number of distinct series—is the hidden schema. Prometheus naming guides and Influx schema docs treat labels/tags as part of the physical model; mis-labeled dimensions explode memory and index size faster than raw point volume.

Beyond the headline vendors, OpenTSDB remains relevant on HBase estates, QuestDB markets columnar SQL ingest for finance tick workloads, and Amazon Timestream appeals when teams want serverless scaling without operating another cluster. Selection often hinges on whether operators already live in PromQL, SQL, or a proprietary DSL—and whether long-horizon retention is a day-one requirement or a retrofit after the first compliance audit.

Why it exists

Relational row stores treat each insert as index maintenance across multiple B-trees; million-points-per-second telemetry turns compaction and WAL pressure into operational incidents. Ad hoc GROUP BY time_bucket over billions of rows without chunking, compression, and retention policies yields unpredictable dashboard latency.

TSDBs encode lifecycle as product features: roll raw data to coarser resolutions, drop chunks past legal retention, compress cold segments, and answer “last hour” vs “last year” with different physical paths. That separation matches Fowler’s polyglot persistence story—metrics are not orders—and keeps OLTP schemas free of append-only noise.

Columnar and log-structured layouts exploit temporal locality: successive timestamps for the same series compress with delta and gorilla-style encodings, and chunk boundaries make eviction predictable. Dashboards that scan only the last hour touch hot chunks on fast media while year-over-year trends read hour-resolution rollups that would require painful ad hoc resampling in a general-purpose row store.

When to use

  • Service and infrastructure observability: histograms, counters, gauges scraped on intervals.
  • Industrial IoT and fleet telemetry with clear tag sets and range queries per device or site.
  • Market ticks and operational “event timelines” queried primarily by timestamp windows.
  • Product analytics where session metrics are pre-aggregated per minute/hour bucket—not row-level user CRUD.
  • Environments that require automated retention and tiered precision without bespoke cron DELETE jobs.

When not to use

  • Authoritative business entities (users, contracts, inventory)—keep them relational; emit metrics separately.
  • Prometheus as multi-year archive without remote write/read—plan Thanos, Cortex, or VictoriaMetrics up front.
  • High-cardinality dimensions as labels (user ID, request ID, trace ID) in Prometheus or Influx tags.
  • Heavy cross-domain joins on every dashboard tile—TimescaleDB can join hypertables to SQL tables, but do not overload the metrics cluster with BI.
  • Strong cross-record ACID workflows—TSDBs favor idempotent writes and eventual consistency on rollups.

Typical architecture

Agents and services expose metrics endpoints or push gateways; scrapers or collectors batch writes into the TSDB. Recording rules, continuous aggregates, or stream processors maintain coarser series; Grafana or alert managers read hot windows. Cold tiers may land in object storage via Thanos/Cortex sidecars. Pros and cons

Pros

  • Ingest paths favor sequential I/O and batching—suitable for fleet-wide telemetry without rewriting OLTP schemas.
  • Chunk-level compression and encoding exploit temporal locality—often an order-of-magnitude space savings vs naive relational storage.
  • Built-in rollups and retention encode SLO vs cost tradeoffs explicitly in the datastore.
  • Query languages expose rates, histograms, and windows tuned for operators—not ad hoc SQL gymnastics.
  • Timescale and SQL hybrids allow guarded joins to registry tables when enrichment is occasional, not per-scrape.

Cons

  • Data model rigidity: tags define identity; retroactive label changes effectively create new series.
  • Cardinality mistakes are painful to unwind—relabeling history is hard once indexes balloon.
  • Late or out-of-order points may be dropped or expensive depending on engine tuning.
  • Another cluster to secure, upgrade, and restore—with different HA patterns than PostgreSQL alone.
  • PromQL/Flux learning curve and fewer transactional semantics than mature OLTP engines.

Implementation notes

Design Prometheus labels before code merge: follow metric and label naming guidance—bounded labels like service, env, region; never unbounded user_id on hot paths. Use recording rules to pre-aggregate expensive queries.

Influx ingest should prefer line protocol batches on /api/v2/write; separate high-cardinality identifiers into fields if they must be stored, not tags, per Influx schema design documentation.

On TimescaleDB, set chunk intervals to match query windows, enable compression with segment-by columns that match filters, and schedule continuous aggregate refresh policies in infrastructure-as-code. For DIY Cassandra telemetry, pair time bucketing in the partition key with Cassandra’s time-ordered clustering guidance to avoid wide partitions.

Influx line protocol batches are far more efficient than per-point JSON posts. A single measurement line carries tag sets, field key-value pairs, and optional epoch timestamps—for example cpu_usage,host=web-01,env=prod usage_percent=72.4,load_avg=2.1. Ship thousands of points per HTTP write and monitor unique tag combinations per measurement; practical guidance from Influx schema documentation treats six-digit tag cardinality as a red flag worthy of architecture review.

For Timescale compression, segmenting by host or region before ordering by descending time routinely yields order-of-magnitude space reductions on numeric telemetry. Chain continuous aggregates so a one-minute view feeds an hourly view, each with explicit refresh policies and lag alerts on the job that keeps dashboards honest about freshness.

Common failure modes

  • Label explosion: Shipping per-tenant IDs as Prometheus labels during a feature flag experiment OOMs scrapers overnight.
  • Retention amnesia: Teams discover year-over-year trends are impossible because remote write was never configured.
  • Tag/field inversion: Storing floats as tags or IDs as tags in Influx multiplies series count without analytics benefit.
  • Stale rollups: Continuous aggregates without refresh policies silently age; alerts fire on old p95 values.
  • Backfill storms: Buffer flushes after outages write hours of out-of-order points, triggering rejections or compaction stalls.

Decision checklist

  • Is every metric’s cardinality estimated with labels counted as schema columns?
  • Are retention tiers defined (raw, 5m, 1h) with owners and legal hold exceptions documented?
  • For Prometheus, is long-term storage architected before production—not after the first audit request?
  • Do dashboards query rollups for wide windows and raw series only for narrow incidents?
  • If using TimescaleDB, are compression lag and continuous aggregate freshness on-call monitors?
  • Are alerts defined on recording rules resilient to scrape gaps and label changes?

Example use cases

  • Case study — The Prometheus ecosystem became the default Kubernetes metrics spine: short local retention, remote write to durable backends, Grafana for visualization.
  • Illustrative scenario — A factory floor streams vibration and temperature via Influx line protocol, retains 30-day high resolution, and pages maintenance when rolling variance crosses thresholds.
  • Illustrative scenario — An SRE team stores latency histograms in Timescale, maintains five-minute continuous aggregates, and joins service names from PostgreSQL only for executive dashboards.
  • Illustrative scenario — A Kubernetes estate runs Prometheus with fifteen-day local retention, remote-writes to VictoriaMetrics for twelve months of downsampling, and uses Grafana recording rules so control-plane SLO dashboards query five-minute aggregates instead of raw thirty-second scrapes.
