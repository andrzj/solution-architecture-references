Data Architecture Specialized Databases

Graph Databases

Native storage and traversal of nodes, edges, and properties — where the data model is a network of entities and their relationships, and traversal performance doesn't degrade with join depth.

⏱ 9 min read

What it is

A graph database persists data as nodes (entities), relationships (typed, directed edges), and properties on both. Queries are expressed as pattern matching over paths—who follows whom, which accounts share a device, how permissions inherit—rather than as repeated join clauses over junction tables.

Label–property graphs (Neo4j, Neptune with Gremlin) dominate operational microservices; RDF triple stores answer SPARQL for semantic web and ontology workloads. The performance story is index-free adjacency: storing pointers from each node to its incident edges makes each hop roughly O(1) in the local neighborhood, which Kleppmann contrasts with relational join planning in Designing Data-Intensive Applications. That matters when SLA-bound features need three to six hops across millions of vertices, not when you occasionally draw an ER diagram with many lines.

Cypher (documented in the Neo4j Cypher manual) makes paths legible: MATCH (u:User {id: $id})-[:PURCHASED]->(p)<-[:PURCHASED]-(peer) RETURN peer, count(p). Treat the graph as a specialized read/traversal engine alongside relational OLTP, per Fowler’s polyglot persistence, not as a drop-in replacement for every foreign key.

Why it exists

Relational schemas represent graphs indirectly: entities in tables, edges as join tables or foreign keys evaluated at query time. Each additional hop multiplies intermediate rowsets and planner work; deep recursive SQL on dense networks often misses latency budgets even with good indexes. Fraud, identity resolution, and social features ask relational questions that are graph-native in shape.

Graph stores invert the cost model: you pay operational complexity and narrower analytics primitives, but bounded traversals stay predictable as total graph size grows. Neo4j’s own graph modeling guidance and Kleppmann’s model comparison both emphasize measuring path queries on realistic degree distributions—not assuming “we have relationships” is sufficient justification.

When to use

  • Multi-hop recommendations or similarity over explicit links (co-purchase, co-view, shared interests).
  • Risk and compliance graph analytics: shared identifiers, circular ownership, shell-company structures within N hops.
  • Authorization models where roles, groups, and resources form inheritance DAGs queried on every request.
  • Operational knowledge graphs where entities are discovered incrementally and linked without rigid upfront schemas.
  • Master data or lineage scenarios when impact analysis is “what downstream nodes depend on this edge?” more often than “sum revenue by month.”

When not to use

  • Primary financial OLTP with strong cross-entity transactions—keep money and inventory in relational stores; project edges asynchronously if needed.
  • Flat reporting and warehouse aggregates—export events to columnar OLAP rather than scanning all nodes in-graph.
  • Shallow trees with depth caps (org charts, BOMs)—PostgreSQL recursive CTEs or ltree may suffice without new ops surface.
  • Catalog browsing with attribute filters only—document or relational indexes win when relationships are not in the query path.
  • Teams without capacity to govern label/property conventions—unconstrained graph schemas become unqueryable swamps.

Typical architecture

Command paths validate business rules in relational or document stores, then upsert nodes and edges into the graph for traversal-heavy reads. Change feeds (Kafka, CDC) keep search indices, warehouses, and feature caches aligned with graph writes—mirroring microservices.io guidance to keep integration event-driven rather than dual-writing every store synchronously. The diagram is a minimal property-graph motif; production topologies add read replicas, GDS batch jobs, and cached traversal results.

Pros and cons

Pros

  • Path queries stay localized—latency depends on hop count and local degree, not on global table cardinality.
  • Relationship properties (weights, timestamps, trust scores) are queryable without rebuilding junction tables.
  • Cypher/Gremlin/SPARQL align code with whiteboard diagrams, easing reviews with risk and product teams.
  • Graph Data Science libraries ship centrality, community detection, and path algorithms without bespoke Spark jobs for moderate scale.
  • Schema evolution can be incremental—new labels and edge types land without wide ALTER TABLE migrations on monolithic schemas.

Cons

  • Global aggregates and BI-style slicing belong in warehouses, not in traversal engines.
  • Write scaling is hard: edges bind partitions; many deployments run single-leader write paths.
  • Another datastore means backups, upgrades, on-call runbooks, and data residency review.
  • Supernodes and dense cliques break naive patterns; modeling and caching discipline are mandatory.
  • Smaller ORM and migration ecosystems—teams own query review, profiling, and regression tests.

Implementation notes

Index every anchor property used to start traversals—typically external IDs, emails, or account numbers. In Neo4j, CREATE INDEX FOR (u:User) ON (u.id) plus PROFILE on hot Cypher in CI catches plan regressions. Cap variable-length patterns (*1..4) and require selective predicates early in the match.

Model supernodes explicitly: fan-out edges through intermediate “bucket” nodes, precompute ranked neighbors, or serve celebrity adjacency from a cache. For Neptune, pick Gremlin for property graphs and SPARQL for RDF ontologies; use reader endpoints for recommendation read traffic and keep Gremlin/Cypher workloads within documented memory limits.

Synchronize graph projections from an authoritative relational source or event log—avoid dual manual updates. Pair with vector indexes on Neo4j when hybrid semantic+structural retrieval is required (see Neo4j embeddings documentation). Document retention: GDPR deletes may require node/edge tombstoning strategies that relational cascades do not provide automatically.

Common failure modes

  • Unanchored MATCH: Queries without selective start predicates devolve into label scans—acceptable in dev, catastrophic in production.
  • Unbounded variable paths: -[*]- patterns on social graphs explore the entire component and OOM the heap.
  • Graph-as-warehouse: Revenue rollups and cohort metrics run in Cypher stall engineering until moved to OLAP.
  • Supernode blindness: Influencer or hub nodes with millions of edges dominate latency; no ranking or sampling strategy exists.
  • Stale dual writes: Edge updates in the graph without matching OLTP commits produce irreversible fraud false positives.

Decision checklist

  • Do production SLIs include multi-hop queries that fail SQL budgets on realistic data volumes?
  • Is there a single source of truth for entity identity before graph projection?
  • Are traversal entry points indexed and covered by automated plan checks?
  • Is maximum hop depth documented per use case, with abuse limits for user-supplied patterns?
  • Are supernodes identified in degree histograms with mitigation designs approved?
  • Do analytics and compliance reads route to warehouse exports instead of the graph cluster?

Example use cases

  • Case study — Professional networks built “people you may know” on two-hop connection signals—archetypal graph workload where join depth dominated SQL cost at scale.
  • Illustrative scenario — A bank links accounts, merchants, and devices; investigators run bounded traversals from alert nodes to surface shared hardware within three hops.
  • Illustrative scenario — A SaaS platform stores RBAC as a graph; permission checks become reachability queries with cached results for hot principals.
