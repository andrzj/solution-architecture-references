OLTP vs OLAP

The fundamental distinction between transaction-optimized and analytics-optimized database designs — row vs columnar storage, write vs read optimization, and HTAP databases that bridge both worlds.

⏱ 9 min read

What it is

OLTP (online transactional processing) is the class of database workloads dominated by short, concurrent reads and writes—placing an order, updating inventory, or recording a payment—with row-oriented storage and ACID guarantees on individual records. OLAP (online analytical processing) is the class dominated by scans and aggregations over large historical datasets—revenue by region, funnel conversion, or inventory aging—typically on columnar storage and denormalized dimensional models. As Martin Kleppmann explains in Designing Data-Intensive Applications, the access patterns differ enough that one physical layout is usually optimized for one side and costly for the other.

OLTP engines (PostgreSQL, MySQL, SQL Server, and similar row stores) favor B-tree indexes, normalized schemas, and predictable point operations. OLAP engines (warehouse and columnar systems such as BigQuery, Snowflake, Redshift, ClickHouse, and DuckDB) favor reading only the columns a query needs, compression on homogeneous column values, and batch-friendly ingestion. Running heavy reporting directly on the OLTP primary still competes for the same I/O and buffer cache as live transactions, which is why mature architectures copy or stream operational data into an analytical tier.

HTAP (hybrid transactional/analytical processing) systems maintain both row-oriented and columnar representations of the same dataset—often via an integrated columnar replica—so some analytics can run on fresher operational data without a separate batch pipeline, at the cost of more moving parts and infrastructure. HTAP is a deliberate compromise, not a default; separated OLTP plus data warehouse or lakehouse tiers remain the common pattern.

Why it exists

Row stores lay out all columns of each record together, which makes fetching or updating one business entity efficient but forces aggregation queries to read many columns that the query never uses. Column stores lay out each column contiguously, so a query that sums one measure can read only that column and benefit from encodings tuned for repeated values. That layout trade-off is why analytical queries that feel trivial in a warehouse can time out or throttle a busy OLTP database.

Writes tell the same story in reverse: updating a single row in a row store touches a compact record, while updating one row in a columnar layout may require rewriting multiple column files. OLTP and OLAP therefore evolved as separate specializations; unifying them without accepting compromise usually means HTAP complexity, read replicas with guardrails, or change-data-capture into a purpose-built analytical engine.

Financial close and regulatory reporting still tolerate batch latency many product teams reject for operational tiles—match engine choice to stated freshness, not to vendor HTAP marketing. Kleppmann’s derived-data narrative applies: analytical stores are rebuilt from operational truth, not alternate sources of record.

When to use

  • Use an OLTP database when the workload is user-facing transactions with high concurrency, many small writes, and primary-key lookups that must stay fast and consistent.
  • Use an OLAP store or warehouse when the workload is reporting, BI, or data science queries that scan wide history and aggregate across dimensions.
  • Use a columnar OLAP engine tuned for events or metrics when you need near-real-time dashboards over high-volume append-only streams, not when you need frequent row-level updates.
  • Consider HTAP when freshness requirements rule out batch ETL but you can fund the extra storage, replication, and operational surface of a dual-layout system.
  • Use embedded OLAP (for example DuckDB on local files) for analyst exploration and CI-sized benchmarks before committing to a managed warehouse.

When not to use

  • Do not run ad hoc analytical scans on the production OLTP primary without strict resource limits, because they contend with live traffic for locks, memory, and disk.
  • Do not use a cloud warehouse as the system of record for interactive OLTP, because per-insert latency and cost models assume batch loads and analytical reads.
  • Do not adopt HTAP solely to skip pipeline design, because dual layouts still need governance, capacity planning, and clear query routing rules.
  • Do not assume a row-store read replica replaces a columnar warehouse for heavy aggregation, because the on-disk layout and optimizer assumptions remain OLTP-oriented.

Typical architecture

Operational data stays in OLTP; pipelines or streams propagate changes into columnar OLAP or warehouse tables. Analysts and BI tools query the analytical tier so production transaction latency stays protected.

Pros and cons

Pros

  • Separating OLTP and OLAP lets each tier use storage and indexing matched to its workload, which improves both transaction latency and analytical throughput.
  • Columnar OLAP achieves strong aggregation performance and compression because scans touch few columns and encodings exploit repeated values.
  • Isolating analytics off the OLTP primary protects checkout, billing, and other write paths from ad hoc report queries.
  • Cloud warehouses decouple storage from compute so analytical capacity can scale without resizing the operational database.
  • Partitioning and clustering on the OLAP side reduce scanned data for time-bounded queries when filters align with table design.

Cons

  • Two tiers mean pipelines, schema contracts, and monitoring for replication lag or failed loads.
  • OLAP systems are poor at high-frequency single-row updates and fine-grained locking compared with OLTP engines.
  • Batch or micro-batch ingestion introduces staleness that HTAP or streaming partial views must address explicitly.
  • HTAP and dual-engine estates increase operational surface area compared with a single well-sized PostgreSQL instance.
  • Misrouted queries—OLAP on OLTP or point lookups on warehouses—produce cost and latency surprises without guardrails.

Implementation notes

On the OLTP side, treat the primary as a transaction system: index foreign keys, cap long-running sessions, and route BI to a replica, warehouse, or dedicated role with statement_timeout on PostgreSQL (see client connection settings). PostgreSQL window functions and CTEs can serve moderate in-database reporting on bounded datasets—measure before provisioning a warehouse.

For analytical freshness without HTAP, use change-data capture into Kafka or the warehouse loader (Debezium and similar) so fact tables update on a schedule or stream that matches dashboard SLAs. In columnar OLAP engines, align sort keys and partitions with the filters BI actually runs; omitting partition predicates on partitioned tables is a frequent source of runaway scan cost in BigQuery and analogous systems.

When evaluating HTAP, document which queries route to the row store versus the columnar replica, how replication lag is measured, and who owns failure of the analytics path. CQRS at the application layer often pairs naturally with OLTP/OLAP separation at the storage layer.

Workload isolation: DDIA contrasts OLTP row stores with columnar scan engines—mixing heavy analytics on primary OLTP without guardrails starves checkout latency. Debezium CDC to columnar files or warehouse landing zones is the common compromise; snapshot and streaming modes define recovery after connector failure.

When HTAP is justified: low-concurrency operational dashboards on fresh data may use vendor HTAP replicas—document maximum concurrent analysts and forbid ad hoc cross joins that bypass resource queues.

Resource governance: warehouse engines use workload management or slots; OLTP killed by analyst SQL needs routing rules or read replicas, not hope. Postgres read replicas serve reporting only when queries tolerate replication lag displayed in BI headers.

Schema shape: columnar engines favour narrow fact tables and late-binding dimensions; wide OLTP rows map poorly—normalize or flatten in the landing zone before claiming lakehouse performance.

Batch ETL windows remain valid for small orgs—CDC streaming is operational complexity you adopt when freshness SLAs beat nightly suffices.

BI tools should display replication lag on dashboards sourced from replicas so analysts interpret partial data knowingly.

Capacity reviews should separate OLTP connection pool headroom from warehouse slot usage—bursting either layer during month-end is a planning failure, not an surprise.

Query routing middleware needs audit logs when analysts are redirected from OLTP to replicas—forensics use them after accidental heavy scans.

Common failure modes

  • Analytical queries on production OLTP: A long aggregation on the primary acquires broad locks or saturates I/O, which slows application transactions and triggers timeouts.
  • Warehouse for tiny datasets: Moving a small reference dataset to a managed warehouse can make interactive exploration slower than local columnar tools on Parquet without adding governance value.
  • HTAP without routing rules: Mixed workloads hit the wrong engine, so columnar replicas lag or row stores absorb scans they were not sized for.
  • OLAP as system of record: High-frequency point lookups against a warehouse behave like full scans and inflate cost because the engine expects batch analytics, not keyed OLTP access.
  • Unbounded partition scans: Dashboards omit date filters on partitioned tables, so every query reads the full history and bills accordingly.

Decision checklist

  • Is the dominant workload transactional (many small writes) or analytical (large scans and aggregates)?
  • What freshness do dashboards and models require, and does batch ETL, streaming CDC, or HTAP meet that SLA?
  • Have production OLTP metrics shown analytical contention that justifies separation?
  • For modest analytical scope, have you tried bounded queries on PostgreSQL or embedded OLAP before a managed warehouse?
  • If HTAP is in scope, are storage duplication, query routing, and on-call ownership documented?
  • Do analytical query reviews enforce partition and time filters on large tables?

Example use cases

  • Illustrative scenario — An e-commerce checkout API stays on PostgreSQL for orders and inventory; CDC streams order facts nightly into a warehouse star schema where finance runs regional revenue reports without touching the primary.
  • Illustrative scenario — A product analytics team ingests append-only events from Kafka into ClickHouse for sub-minute active-user dashboards while user settings remain in a relational OLTP store.
  • Case study — Amazon’s early retail architecture popularized separating operational order processing from analytics warehousing; Kleppmann discusses similar batch-and-stream trade-offs in Designing Data-Intensive Applications (OLTP vs. analytics and derived data).
