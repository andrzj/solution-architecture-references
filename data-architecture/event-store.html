Event Store

An append-only log as the authoritative source of truth — persisting every domain event that changes an aggregate's state, enabling event replay, temporal queries, multiple read projections, and complete audit history.

⏱ 12 min read

What it is

An event store is an append-only persistence layer that records every domain event affecting an entity’s lifecycle instead of overwriting current state in place. Where a CRUD row might hold only the latest account balance, the store holds an ordered stream such as AccountOpened, MoneyDeposited, and MoneyWithdrawn; present state is derived by replaying those events from the start of the stream or from a stored snapshot.

It is the storage backbone of event sourcing, which Martin Fowler describes as persisting state changes as a sequence of events rather than as mutable rows (Event Sourcing). Events are grouped into streams (often one per aggregate instance), each carrying an immutable sequence number. Projections consume streams to build query-optimized read models; snapshots cache aggregate state so replay does not always begin at event zero.

Implementations range from purpose-built databases such as EventStoreDB to append-only tables in PostgreSQL, partitioned logs in Kafka used with disciplined retention, or key-ordered stores in DynamoDB. The interface matters more than the brand: atomic appends per stream, optimistic concurrency on expected version, and subscriptions for catch-up or live projection processing.

Why it exists

Mutable tables discard history by default, yet audits, disputes, and post-incident analysis need to know how state evolved. Event stores make change the primary artifact: compliance can trace balance adjustments, engineers can reproduce pre-bug state by replay, and new read models can bootstrap from historical events without backfilling from opaque nightly dumps. Paired with CQRS, the write side stays event-centric while read sides optimize for each query pattern, as summarized on microservices.io.

When to use

  • When regulations or contracts require tamper-evident, chronological evidence of how business state changed.
  • When you must answer “what did we know at time T?” by replaying to a timestamp or version.
  • When the domain is naturally workflow- or transaction-centric (orders, payments, policies, collaborative documents).
  • When you anticipate new read models and want to rebuild them from the canonical event log instead of one-off migrations.
  • When CQRS separates command processing from queries and the write model is event-sourced.

When not to use

  • Do not event-source simple CRUD settings or catalogs where history adds little value and consistency can live in a relational row.
  • Do not adopt without training: aggregate boundaries and event granularity are expensive to fix after production traffic appends immutably.
  • Do not query the store like a reporting database; business questions go through projections, materialized views, or warehouse exports.
  • Do not ignore erasure law: plan crypto-shredding, retention, or legal holds before writing irrecoverable PII into immutable streams.

Typical architecture

Command handlers load an aggregate by replaying its stream (or snapshot plus tail), enforce invariants, append new events with expected-version checks, and publish to subscribers. Projectors maintain SQL, search, or cache read models asynchronously; UI reads those models and tolerates brief eventual consistency unless you add synchronous read-your-writes paths.

Pros and cons

Pros

  • Append-only streams provide a durable audit trail without bolting change-data capture onto CRUD tables after the fact.
  • Replay enables temporal reasoning and deterministic reproduction of past aggregate state.
  • Multiple projections can subscribe to the same streams, enabling new views without rewriting the write model.
  • Stored domain events can feed integration when outbox or log-based publishing is designed carefully.
  • Debugging benefits from replaying the exact event sequence that preceded a failure.

Cons

  • Event sourcing, snapshots, and upcasting demand sustained design discipline and on-call familiarity.
  • Business queries depend on projection health; lag or bugs in projectors surface as “data loss” to users.
  • Schema evolution requires versioned events and upcasters before deploying breaking changes.
  • Long-lived aggregates need snapshot policies or replay cost dominates command latency.
  • Immutability complicates privacy erasure unless encryption and key destruction are planned up front.

Implementation notes

Use optimistic concurrency on append: pass the stream version observed at load time; reject conflicting writes so callers reload and retry. EventStoreDB exposes this as expectedRevision; relational implementations use unique constraints on (stream_id, sequence).

Version events explicitly (OrderCreated_v2 metadata) and implement upcasters that translate older payloads during replay. Prefer additive evolution and new event types over mutating semantics of historical types. Schedule snapshot creation for hot aggregates and document retention for snapshots separately from events.

Connect projectors with idempotent handlers and monitor lag. For cross-service integration, pair the store with outbox or log publishing patterns described in Kleppmann’s treatment of logs and derived data in Designing Data-Intensive Applications.

Common failure modes

  • Aggregate too large / stream too long: Commands replay unbounded history because snapshots are missing or misconfigured.
  • Projection lag causing stale reads: Users read query models before projectors catch up and file defects against eventual consistency.
  • Upcaster not implemented for schema change: Deployments deserialize legacy events with new code and crash mid-replay.
  • Forgotten snapshot cleanup: Snapshot storage grows without lifecycle rules while events remain the legal source of truth.
  • Accidental event store mutation: Manual edits to stored events break audit guarantees and invalidate projections.

Decision checklist

  • Are audit, temporal, or multi-projection requirements real—not hypothetical convenience?
  • Does the team have a learning path for aggregates, CQRS, and projection operations before production cutover?
  • Is expected-version checking mandatory on every append?
  • Are upcasting rules defined and tested before the first incompatible event change ships?
  • Is there a snapshot cadence for long-lived aggregates?
  • Is erasure or retention for PII in events documented with legal review?

Example use cases

  • Illustrative scenario — A ledger records credits and debits as events; balance is a fold over the stream; auditors replay any account to the end of a reporting period.
  • Illustrative scenario — An order service appends lifecycle events; customer support projections show the exact sequence that led to a failed shipment.
  • Illustrative scenario — A collaborative editor stores operations as events and rebuilds document revisions by replay for conflict diagnosis.
  • Case study — Fowler’s Event Sourcing essay and the microservices.io pattern page remain the common references for when to persist events as the system of record; Kleppmann’s log-oriented discussion in DDIA connects the idea to stream processing and derived views.

Related patterns

  • Event Sourcing — Pattern the event store implements on the write path.
  • CQRS — Separates command-side events from query-side projections.
  • Event Streaming — Integrates persisted events with brokers for cross-service consumers.
