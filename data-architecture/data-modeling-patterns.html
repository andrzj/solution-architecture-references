Data Architecture

Data Modeling Patterns

Structural patterns for organizing data across relational, document, key-value, wide-column, and graph models — including hierarchical, polymorphic, and hybrid JSONB patterns that bridge model boundaries.

⏱ 11 min read

What it is

Data modeling patterns name recurring ways to map domain concepts onto physical storage: how you represent trees, sparse attributes, time-ordered events, or polymorphic entities when a single normalized table is awkward. The choice is not cosmetic—it fixes which queries stay index-friendly and which paths pay join or scan penalties at scale.

Kleppmann’s Designing Data-Intensive Applications frames the trade space across relational rows, documents, wide partitions, and graphs; Fowler’s polyglot persistence explains why production stacks often mix engines rather than stretch one model to every bounded context. In practice you still pick a pattern per access path: adjacency lists versus nested sets for hierarchies, EAV or JSONB for variable attributes, Cassandra-style partition keys for entity-scoped timelines, and MongoDB’s embed-versus-reference guidance for document shape.

Relational databases remain the default OLTP backbone; patterns such as adjacency list, nested set, materialized path (ltree), EAV, JSONB hybrid, and single/class table inheritance let you stay in SQL while matching domain geometry. When a pattern fights the engine—unbounded recursion, fan-out updates, or partition hotspots—it is a signal to adopt a different store or denormalize deliberately, aligned with database per service boundaries.

Why it exists

Schemas encode assumptions about read and write shape. A catalog modeled as fifty nullable columns wastes space and indexing budget; EAV without pivot discipline turns filters into self-join nightmares. Trees stored only as parent_id make subtree reads expensive until you add nested sets, paths, or a graph sidecar. Telemetry stuffed into generic relational tables hits B-tree write amplification long before business logic does.

Patterns exist so teams can name these mismatches early and pick structures whose hot paths are first-class in the storage engine—GIN containment on JSONB, range scans on nested-set boundaries, partition-local time ordering in Cassandra—rather than reimplementing traversal and compression in application code. Fowler’s data-model guidance and Kleppmann’s comparison of storage engines both stress that there is no universal winner, only fit to measured access patterns.

When to use

  • Adjacency list when hierarchies change often (reorgs, moved categories) and queries focus on direct parent/child or shallow depth; PostgreSQL recursive CTEs or ltree extend this when subtree reads matter.
  • Nested set or materialized path when read-heavy subtree queries dominate and reparenting is rare—or use ltree as a compromise with path-prefix reads and localized updates.
  • JSONB hybrid when a stable core of columns needs indexes and constraints, while extension attributes vary by tenant or category; pair with GIN and explicit validation in app or JSON Schema checks.
  • EAV only for genuinely user-defined attribute dictionaries with extreme sparsity; plan pivot views or search indexes if filters must stay SQL-friendly.
  • Wide-column time ordering when ingest is append-mostly per entity and queries are “latest N” or “range for device X,” following Cassandra’s query-first modeling rules.
  • Document embedding when MongoDB’s one-to-few pattern holds: children are always read with the parent and seldom updated independently.
  • Single Table Inheritance (STI) when subtypes share most columns and row volume stays moderate; use discriminators and partial indexes rather than nullable swamps without discipline.
  • Class Table Inheritance (CTI) when each subtype has many dedicated columns and you want typed child tables with joins only when specialization is queried.
  • Graph sidecar when many-to-many relationships dominate reads and a relational join path exceeds latency budgets for recommendation or authorization traversals.

When not to use

  • Avoid EAV when attribute names and types are known at design time—typed columns, CTI, or JSONB with a schema contract preserve integrity and simpler EXPLAIN plans.
  • Avoid nested sets on volatile trees; each move renumbers large subtrees and contends under concurrent edits.
  • Avoid deep MongoDB embeds when shared sub-documents update often (addresses, product copy)—fan-out writes across parents violate DRY and consistency windows.
  • Avoid using document arrays as the only edge representation for many-to-many graphs unless you accept bidirectional denormalization and sync logic.
  • Avoid Cassandra partitions that grow without time bucketing; Kleppmann’s discussion of partition size and compaction applies directly to “one partition per device forever” designs.

Typical architecture

Bounded contexts usually land on different shapes: relational core for money and identity, document or JSONB facet for catalogs, wide-column or TSDB for telemetry, graph for recommendations, vector index for semantic recall. Services own their schema per microservices.io database-per-service guidance; integration happens through APIs and events, not shared mutable tables. Pros and cons

Pros

  • Explicit pattern choice documents which queries are cheap, reducing “surprise slow reports” after data volume grows and keeping data-path assumptions visible in architecture reviews.
  • JSONB hybrid preserves migration-free extension fields while keeping fiscal and identity columns strongly typed and indexable in PostgreSQL for auditors and reconciliation jobs.
  • Materialized paths and nested sets turn subtree membership into range or prefix predicates—friendly to covering indexes, read replicas, and cache keys derived from path prefixes.
  • Query-first Cassandra keys align with DDIA’s emphasis on partitioning by known access paths, yielding predictable ingest throughput on commodity clusters without surprise hotspot shards.
  • MongoDB embedding matches Fowler’s aggregate-root thinking for entity-local reads without cross-shard joins on every page view, which lowers latency for product-detail experiences.
  • Polymorphic modeling with clear ADR rationale lets teams evolve bounded contexts without forcing every service into identical relational templates.

Cons

  • EAV and polymorphic tables push integrity and reporting complexity into views, ETL, or search indexes—not into the declarative schema where CHECK constraints would live.
  • Nested sets and some path models penalize frequent structural edits; operational org charts may thrash under concurrent moves unless moves batch during maintenance windows.
  • Hybrid polyglot stacks multiply backup, versioning, and transactional boundaries—exactly the cost Fowler warns about under polyglot persistence when every feature needs another datastore skill on call.
  • Cassandra and similar stores forbid ad hoc analytics on the hot path; new questions often mean new tables, batch exports, or warehouse pipelines instead of exploratory SQL.
  • JSONB and document payloads need contract tests or catalog metadata; without them, producers ship incompatible shapes silently until downstream consumers fail in production.
  • Over-embedding in documents creates oversized working sets and BSON size pressure when regulatory exports require per-field redaction at rest.

Implementation notes

Start hierarchy work with adjacency list + constraints (CHECK (parent_id <> id), optional closure detection in migrations). Add ltree when prefix subtree reads appear in SLIs; refresh paths in the same transaction as parent_id updates. Reserve nested sets for read-mostly taxonomies with measured recursive-CTE pain.

For polymorphic products or multi-type entities, document the choice among STI, CTI, and JSONB in an ADR; CTI fits fixed per-type columns, JSONB fits tenant-specific facets with GIN on containment keys you actually filter. In MongoDB, follow the manual’s one-to-few versus one-to-many guidance: reference when children have independent lifecycles or high cardinality.

Cassandra tables should be designed from stated queries, not ER diagrams—define partition width targets (for example monthly buckets per device) before production ingest. Pair JSONB producers with data contracts or JSON Schema validation at the write boundary so analytics and search consumers do not parse ambiguous blobs.

Common failure modes

  • EAV as default catalog: Faceted filters devolve into multi-way self-joins; teams bolt on Elasticsearch instead of admitting typed or JSONB facets were the right fit.
  • Cycle-blind trees: Bugs or imports create loops; recursive SQL hits depth limits or spins until cancelled—add cycle detection or materialized path invariants in tests.
  • Hot Cassandra partitions: Single-key partitions absorb unbounded history; compaction debt and read latency spike on noisy neighbors.
  • Unindexed JSONB filters: Containment predicates without jsonb_path_ops GIN behave like sequential scans at million-row scale.
  • Historical orders with live product embeds: Denormalized product text inside order documents forces impossible fan-out when marketing updates copy—snapshot product fields at purchase time instead.
  • STI without partial indexes: Sparsely populated subtype columns inflate table width and confuse vacuum; partial indexes per discriminator restore scan selectivity.
  • Graph without uniqueness on edge keys: Duplicate relationship rows make traversal idempotent checks expensive and break merge logic in authorization graphs.

Decision checklist

  • Have you listed the top five queries and writes per aggregate and matched each to a pattern (not merely a database brand)?
  • For trees: what is the ratio of subtree reads to reparents, and is depth bounded in production data?
  • For variable attributes: are names/types stable (columns/CTI), configurable per tenant (JSONB + contracts), or unbounded sparse (EAV with search backing)?
  • For documents: does MongoDB’s cardinality guidance classify the relationship as embed, reference, or subset pattern?
  • For Cassandra: does every query include partition key equality, and are buckets sized for retention and compaction?
  • Are JSONB/GIN or GiST indexes aligned to real predicates in EXPLAIN, not hypothetical filters?

Example use cases

  • Illustrative scenario — A marketplace stores SKU, price, and inventory in relational tables, pushes category facets into JSONB with GIN, and publishes change events so search indexes stay eventually consistent with the OLTP source.
  • Illustrative scenario — A content hierarchy uses adjacency for edits and ltree for menu rendering; nightly jobs verify path consistency against parent_id before cache warming.
  • Case study — Operators at Netflix-scale have published Cassandra models that shard viewing events by profile and time bucket—useful reference when modeling high-volume per-user timelines without relational bloat.
  • Illustrative scenario — A healthcare platform stores immutable clinical facts relationally, models flexible provider-defined forms in JSONB with schema registry validation, and mirrors relationship queries into a graph for care-team routing.
  • Illustrative scenario — A ticketing product uses adjacency for workflow state, materialized path for SLA rollups, and exports dimensional snapshots nightly because nested-set reparents are rare after initial import.
