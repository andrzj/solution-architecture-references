Data Architecture Microservices

Database Per Service

Each microservice owns its private, dedicated database — no other service can access it directly. This pattern enables independent deployment, polyglot persistence, and fault isolation at the cost of cross-service query complexity.

⏱ 10 min read

What it is

Database per service is a microservices data pattern where each service has exclusive ownership of its persistence: no other service may read or write that database directly, and cross-service data needs are satisfied through the owning service’s API or through replicated read models fed by events. Chris Richardson documents the pattern on microservices.io as the data counterpart to service encapsulation—schema and storage technology become private implementation details.

“Database” can mean a dedicated server, a separate schema on shared infrastructure, or table sets isolated by credentials; stronger isolation reduces noisy-neighbor risk and credential blast radius. If an order workflow needs a customer display name, the order service calls the customer service—it does not issue SQL against the customer schema.

The pattern does not eliminate the need for cross-cutting analytics; it routes them through warehouses, CDC streams, or CQRS read models instead of shared mutable tables.

Physical separation can be gradual: teams often start with schema-per-service on one cluster, then split noisy tenants onto dedicated instances once ownership and SLO arguments are clear. The architectural rule—no cross-schema writes from foreign services—matters more than how many VPCs host the disks.

Why it exists

A single shared database is the fastest path to a distributed monolith: teams couple through foreign keys and ad hoc joins, schema migrations require release trains, and one expensive report query slows every consumer. Giving each service its own store makes the persistence boundary match the deployment boundary, which is what independent teams and polyglot persistence require in practice.

The trade-off is intentional: you lose cross-database ACID transactions and single-query reporting, and you gain autonomy, clearer ownership, and the ability to scale or replace one service’s store without destabilizing neighbors.

Sam Newman’s Building Microservices frames the pattern as non-negotiable once services claim independent lifecycles: shared persistence reintroduces the same deployment coupling microservices were meant to escape, even when teams rename schemas instead of tables.

When to use

  • Apply the pattern when services must ship on independent cadences and cannot wait for coordinated schema migrations across a shared database.
  • Apply it when separate teams own separate services and need schema freedom without cross-team migration approvals for every column change.
  • Apply it when scalability profiles diverge—one service may shard while another stays on a single-instance relational store.
  • Apply it as a foundation for polyglot persistence so each service can choose row, document, or event storage without veto from a central DBA schema.
  • Apply it when fault isolation matters: an outage in one service’s database should not halt unrelated services that do not depend on that data.

When not to use

  • Do not split databases inside a monolith that deploys as one unit, because you incur distributed-data complexity without gaining independent deployment.
  • Do not carve databases before bounded contexts are stable, because mistaken service cuts are expensive to untangle once data is physically split.
  • Do not adopt many database instances without platform capacity for backup, monitoring, and incident response per store.
  • Do not weaken the rule because reporting is hard—the answer is a warehouse or read model, not shared write access to peer schemas.

Typical architecture

Services hold private datastores; peers interact only via APIs or async messages. Reporting and joins happen in derived stores populated from domain events or CDC, not by crossing service boundaries with SQL.

Pros and cons

Pros

  • Schema migrations stay local to the owning team, which supports continuous delivery without organization-wide migration windows.
  • Each service can adopt storage technology suited to its domain without forcing a single global standard.
  • Database failures and maintenance windows affect only consumers of that service’s API, not every tenant of a shared schema.
  • Capacity planning can target hot services independently instead of oversizing one shared instance for the noisiest neighbor.
  • Public APIs and versioned events become the stable contract instead of shared table layouts.

Cons

  • Cross-service screens and reports need API composition, batch fetches, or materialized views—not one SQL join across schemas.
  • Multi-service business processes require sagas and compensations rather than a single cross-database transaction.
  • Duplicated reference data must be synchronized via events, with clear rules for staleness and conflict.
  • Operating many databases multiplies backup, patching, and credential management work.
  • Foreign keys cannot span service databases; referential integrity becomes an application and process concern.

Implementation notes

For analytics, emit domain events from each service’s private database—often via the transactional outbox—and load a warehouse or lakehouse with denormalized facts. That path preserves ownership while giving BI a queryable cross-domain layer.

For interactive reads that join multiple services, prefer a dedicated read model or BFF that subscribes to events and materializes one query-friendly document, or expose batch APIs (for example “customers by ids”) to avoid chatty per-row HTTP calls. CQRS separates this read-optimized store from each service’s write model.

For multi-step business flows—place order, reserve stock, capture payment—use the saga pattern with explicit compensating commands and user-visible intermediate states (pending versus confirmed). Register event schemas so consumers detect incompatible changes before production deploys.

Instrument ownership at the connection layer: application credentials should reach only one service’s schema, secrets managers should tag which deployment owns each DSN, and CI should fail builds that import another team’s repository layer. Platform teams can offer managed Postgres or document clusters per tenant, but the encapsulation rule stays at the service API, not at “we promise not to query your tables.”

For customer-facing aggregates that stitch peer data, publish SLIs on fan-out latency and partial failure rates. A BFF that hydrates twenty microservices per page is a symptom that a read model or cached projection is missing—not permission to open SQL ports between databases.

Common failure modes

  • Shared database creep: Teams grant “read-only” SQL access across service databases for convenience, which restores coupling and hidden dependencies.
  • Missing saga compensation: A downstream step fails after an upstream reservation, leaving inventory or payments in a stuck partial state.
  • Chatty API composition: List endpoints trigger one remote call per row instead of batch or denormalized reads, which overloads peer services and inflates latency.
  • Breaking event contracts: Producers change payload shapes without versioning; consumers stop updating read models silently.
  • Orphan references: An entity is removed in one service while another still stores its identifier, because cross-service deletes are not orchestrated.

Decision checklist

  • Are bounded contexts and service APIs stable enough to justify physical data separation?
  • Is there an approved path for cross-service reporting (warehouse, lake, or CQRS read store)?
  • Does every multi-service workflow document compensating actions for partial failure?
  • Do composite APIs use batching, caching, or read models to avoid per-item peer calls?
  • Are domain events versioned and checked in a registry or contract test pipeline?
  • Can platform teams operate backup restore and paging for each database instance in scope?

Example use cases

  • E-commerce microservices: Order, inventory, catalog, payment, and notification services each hold a private store—PostgreSQL for money paths, document storage for flexible catalogs, Redis beside inventory for reservations. Teams ship schema changes on their own cadence; analytics land in Redshift fed by order-placed and payment-captured events.
  • Multi-tenant SaaS: Tenant administration, billing, identity, and usage metering run as separate deployables with isolated databases. JWT claims carry tenant identifiers into APIs; usage counters append to ClickHouse while authoritative tenant rows stay in PostgreSQL.
  • Travel booking: Availability counters live in a low-latency cache backed by relational source rows; reservations and pricing own normalized schemas; reviews use a document model. A booking saga coordinates availability, reservation, and payment with compensating releases when card authorization fails.
  • Reference material — Chris Richardson’s database per service and saga pages remain the standard pattern write-ups for splitting monolith data stores.

Related patterns

  • Polyglot Persistence — Independent databases per service enable different engines per domain.
  • Saga Pattern — Coordinates multi-service writes without distributed two-phase commit.
  • CQRS — Materializes cross-service read models from events while writes stay private per service.
  • Transactional Outbox — Publishes integration events atomically with local database commits.
