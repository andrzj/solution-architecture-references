Anti-Patterns

Shared Database

Multiple services directly accessing the same database, creating hidden coupling.

⏱ 10 min read

What it is

The Shared Database anti-pattern appears when two or more services or applications read and write the same database schema as if it were a shared integration layer. On paper the system is split into services. In practice, teams still coordinate through tables, views, and stored procedures that everyone owns and nobody owns at once.

Microsoft and others document this as integration through the database: the DB becomes the message bus, the contract repository, and the coupling point. It is one of the fastest ways to build a distributed monolith.

Why it exists

Teams reach for a shared database for understandable reasons. A single schema is easy to query with SQL joins. Reporting wants one source of truth. Migrations from a legacy monolith often leave one database in place while code is split into deployable units. Short deadlines make “we will fix boundaries later” tempting.

The pain shows up later. Schema changes require cross-team agreement. One service’s migration can break another at runtime. Performance tuning becomes political: indexes that help one consumer hurt another. Independence—the main reason to adopt services—never arrives.

When you see it

  • Multiple repositories deploy separately but connect to the same production database or schema.
  • Services bypass APIs and read “foreign” tables owned by another team.
  • Database triggers or batch jobs synchronize state that should be owned by a single boundary.
  • Release notes routinely say “deploy Service A and B together because of schema change X.”
  • ORM models for another team’s tables are copied or linked through a shared library.

When it is (briefly) acceptable

  • During a time-boxed strangler migration: one database only while you carve out true service-owned stores.
  • For read-only replicas or analytics sandboxes that never write back to the operational schema.
  • Inside a modular monolith where one team owns the entire database and deployment unit.

Even then, treat shared access as debt with a written exit plan—not as the target architecture.

Typical architecture

Each “service” talks to the same logical database. Cross-domain rules leak into SQL, and deployment independence is an illusion.

Pros and cons

Why teams keep it

  • Fast to ship early: familiar SQL, existing DBAs, one backup strategy.
  • Ad-hoc reporting with joins across domains.
  • No need to design events or APIs for every read path yet.

Long-term costs

  • Cannot evolve schemas independently; every change is a multi-team release.
  • Blast radius of bad queries or locks spans the whole platform.
  • Ownership blur: nobody can enforce invariants at the service boundary.
  • Scaling write load on one domain stresses everyone on the same instance.

Implementation notes

Remediate in small steps. Give each bounded context its own database (or schema with hard network isolation). Replace cross-table reads with APIs or replicated read models. Use change-data capture or domain events to publish facts other contexts need—do not grant them write access.

Where you must share data temporarily, use explicit views or replication consumers with contracts, not ad hoc table access. Track progress with architecture decision records so “temporary” does not become permanent.

Common failure modes

  • Schema lock-in: fear of breaking consumers freezes migrations until emergency firefights.
  • Silent cross-writes: two services update the same row without a single transactional owner.
  • Reporting-driven OLTP abuse: heavy analytics queries run on the operational database.
  • Shared ORM package: domain entities ship as a library, recreating compile-time monolith coupling.

Decision checklist

  • Does each production service have credentials that can reach only its own schema?
  • Can any service deploy a schema change without another team’s code going live the same day?
  • Are cross-context reads served by APIs or materialized views—not direct table access?
  • Is there a dated plan to retire shared-database access left from the monolith?

Example use cases

  • Retail split: Order and catalog services shared Postgres; a catalog price column rename broke checkout until both apps rolled back together.
  • Healthcare SaaS: Scheduling and billing services read the same patient table; a privacy column addition violated billing’s assumptions and halted claims for a week.

Related patterns

  • Distributed Monolith — the usual outcome of shared data plus synchronous calls.
  • Database per Service — the target pattern for service-owned data.
  • Modular Monolith — when one team truly owns one database.
