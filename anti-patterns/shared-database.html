Anti-Patterns

Shared Database

Multiple microservices reading and writing the same database—recreating monolith coupling with higher operational cost.

⏱ 10 min read

What it is

The shared database anti-pattern lets multiple services read and write the same tables as if they were one application. Deployments look separate; persistence is not. Martin Fowler’s Integration Database describes the same idea: the RDBMS becomes the integration bus.

Order, payment, inventory, and reporting services may each have their own repo and CI pipeline, yet they still mutate the same orders and line-item tables inside one OLTP schema. A partner integration that gains write access to freight columns on those rows adds another migration consumer without adding a bounded context boundary.

Chris Richardson’s database per service pattern states the inverse: each service owns data it alone writes. Shared-database coupling is what remains when a microservices migration stops at the connection string.

Why it exists

Shared tables feel faster than duplicating data or standing up change-data capture. A split from a modular monolith often leaves the original Postgres or SQL Server instance in place; JOINs and foreign keys still look cheaper than domain events on a roadmap.

Integration pressure reinforces the shortcut. When a shipment or marketplace partner needs freight metadata on order rows, granting JDBC write access beats defining OrderPlaced events and a separate shipment aggregate—until schema contention becomes the release bottleneck.

Shared NuGet, npm, or internal ORM packages that map the whole enterprise schema make the problem worse: every service compiles against the same entity graph, so version bumps force coordinated releases even when runtime behavior should be independent.

How it manifests

  • Payment and inventory services both UPDATE orders.payment_status and orders.fulfillment_state without a single write owner.
  • A nullable column for payment capture requires coordinated deploys of order, shipment batch jobs, and a partner label worker that reads the same table.
  • Reporting or ad-hoc BI runs heavy SQL against primary OLTP tables, pinning locks during checkout peaks.
  • Schema change advisory boards gate routine ALTERs because any migration can break a peer service’s queries or ORM mappings.
  • Teams file cross-repo release tickets before merging schema-dependent features because no service owns the database alone.
  • Horizontal scale adds pods that increase lock contention on shared hot rows rather than isolating workloads per context.

How to recognize it early

  • Deployment choreography: Payment cannot ship alone when order still expects a new column on a shared table—that is a shared-database signal, not healthy service independence.
  • Cross-service SQL: Inventory joins orders in views or stored procedures instead of consuming events or APIs, which means persistence is shared rather than contracted.
  • Read replica without writers: An analytics replica with no application writers is a reporting pattern, not this anti-pattern.
  • Monolith with one owner: A modular monolith with one team owning one schema is a valid choice, not shared-database coupling across deployables.
  • Warehouse-fed reads: Operational teams reading a curated mart fed by CDC integrate at the warehouse layer, not via shared OLTP access.

Typical manifestation

Services stay independent only above the JDBC or ODBC connection string; below that line, one schema serializes change.

Consequences and remediation

Consequences

  • Release trains: Peak-season deploy windows require order, payment, inventory, and partner label services in one coordinated train because migrations must align.
  • OLTP contention: Long-running reporting or reconciliation queries stall checkout writes on the shared primary.
  • Scale limits: No team can shard, archive, or retention-policy orders independently when rows are multi-writer.
  • Incident blast radius: A bad migration or lock storm on shared tables takes down every service on that schema, not one bounded context.

Remediation strategies

  • Database per service: Order owns order rows; payment owns captures in its own store—see database per service.
  • CDC and events: Change data capture and domain events feed reporting and partner read models without shared writes.
  • Strangler extraction: Peel writers off orders slice by slice with anti-corruption layers at each new boundary.
  • Freeze new writers: Stop granting JDBC write access to integration partners until an event contract exists.

Implementation notes

Remediation usually starts by freezing new cross-table writers, then moving the highest-churn context—often payment—off direct orders updates behind PaymentCaptured or equivalent events. Partner label services should stop mutating order rows and instead consume the same stream to build a shipment aggregate they own.

Dual-write periods need a field-level source-of-truth matrix: which service wins when capture status disagrees, how long reconciliation runs, and when the legacy column becomes read-only. CDC contract tests catch schema drift before BI and operational dashboards break.

Intentional duplication is part of the exit. Order may keep denormalized shipping addresses fed by user-profile events so fulfillment does not join across databases at request time. Simon Brown’s C4 views help executives fund schema splits when containers and data stores are drawn separately.

Detect coupled migrations, cross-team ALTER tickets, and BI queries that break when one service deploys. Incentives: one DBA team, fast joins in SQL, and fear of eventual consistency. Remediate with views as interim contracts, CDC plus outbox to split writers, strangler reads, then schema deletion behind feature flags. A single-team product on one database with read replicas for reporting is a sane trade-off; five services mutating the same tables is not. Pair with distributed monolith signals when repos split but schemas did not. Treat cross-service views as versioned contracts with consumers in the same review queue as APIs. Drop views only after all writers moved.

Run migration rehearsal on staging clones owned by one service before granting cross-team ALTER privileges in production.

Escalation patterns

  • Dual-write limbo: Payment and order both write capture status during migration—incidents when states disagree and support cannot tell which store is canonical.
  • BI exception: Finance adds a read-only JDBC user that becomes a shadow writer via ad-hoc “fix” scripts during month-end.
  • Partner shortcut: A label service writes freight fields on order rows instead of owning shipment data, permanently enlarging the shared schema.
  • Schema coupling spiral: Teams postpone nullable-column migrations because consumers disagree on semantics, so the shared schema stops evolving.

Diagnostic checklist

  • Does every OLTP table have exactly one owning write service?
  • Can payment ship without inventory migrating the same schema in the same window?
  • Are cross-context reads served from events, APIs, or marts—not shared primary tables?
  • Can reporting run without holding locks on checkout-critical tables during peaks?
  • Do integration partners consume events instead of gaining new writers on the core schema?
  • Is there an exit plan with dual-write boundaries documented before the next major ALTER?

Example use cases

  • Meridian Commerce and Northwind Logistics on one shared orders table: Payment added capture_reference as NULLable; Northwind’s nightly label batch expected NOT NULL legacy columns; order, payment, and label services had to deploy in a single maintenance window. The remediation assigned order ownership of orders, moved captures to payment’s store with events, and fed reporting and Northwind via CDC into separate databases—aligned with database per service.
