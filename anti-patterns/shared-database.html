Anti-Patterns

Shared Database

Multiple microservices reading and writing the same database—recreating monolith coupling with higher operational cost.

⏱ 10 min read

What it is

The shared database anti-pattern lets multiple services read and write the same tables as if they were one application. Deployments look separate; persistence is not. Martin Fowler’s Integration Database describes the same idea: the RDBMS becomes the integration bus.

At Meridian Commerce, Order, Payment, Inventory, and Reporting still share meridian_core.orders and related line-item tables. When Northwind Logistics onboarded merchant shipments, its label service gained write access to the same schema for freight metadata — four teams, one migration queue.

Why it exists

Shared tables feel faster than duplicating data or standing up CDC. Meridian’s split from a modular monolith left the Postgres instance in place; JOINs and foreign keys still look cheaper than events on a roadmap. Northwind’s integration added another writer instead of subscribing to OrderPlaced.

Shared NuGet/npm ORM packages that map the whole enterprise schema make the problem worse: every service “owns” the same entity graph.

How it manifests

  • Meridian Payment and Inventory both UPDATE orders.payment_status and orders.fulfillment_state without a single write owner.
  • A nullable column for Payment capture requires coordinated deploys of Order, Shipment batch jobs, and Northwind’s label worker.
  • Reporting runs heavy SQL against primary OLTP tables, pinning locks during checkout peaks.
  • Schema CAB meetings gate routine ALTERs because any change can break a peer service’s queries.

How to recognize it early

  • Meridian’s analytics replica is read-only with no application writers — that is a reporting pattern, not shared-database coupling.
  • A modular monolith with one team owning one schema is a valid modular-monolith choice, not this anti-pattern.
  • Northwind FieldOps reading a curated mart fed by CDC is integration done at the warehouse layer, not shared OLTP access.

Typical manifestation

Meridian and Northwind services stay independent only above the JDBC connection string.

Consequences and remediation

Consequences

  • Meridian’s Black Friday deploy window requires Payment, Order, Inventory, and Northwind label services in one train.
  • A long-running reporting query stalls checkout writes on the shared primary.
  • Neither team can shard or archive orders independently.

Remediation

  • Database per service — Order owns order rows; Payment owns captures in its own store.
  • CDC and domain events feed Reporting and Northwind read models without shared writes.
  • Strangler extraction on orders with anti-corruption layers at each new boundary.

Implementation notes

Meridian froze new cross-table writers first, then moved Payment off direct orders updates behind PaymentCaptured events. Northwind stopped mutating Meridian tables and consumes the same stream to build its shipment aggregate. Dual-write periods need a field-level source of truth matrix; CDC contract tests catch schema drift before BI and FieldOps break.

Escalation patterns

  • Dual-write limbo: Payment and Order both write capture status during migration — incidents when states disagree.
  • BI exception: Finance adds a read-only JDBC user that becomes a shadow writer via ad-hoc “fix” scripts.
  • Northwind shortcut: Label service writes freight fields on Meridian’s rows instead of owning shipment data.

Diagnostic checklist

  • Does every Meridian/Northwind table have exactly one owning write service?
  • Can Payment ship without Inventory migrating the same schema?
  • Are cross-context reads served from events, APIs, or marts — not shared primary tables?

Example use cases

Meridian and Northwind on one shared orders table:

  • Anti-pattern: Payment adds capture_reference NULLable; Northwind’s nightly label batch expects NOT NULL legacy columns; three services deploy in a single maintenance window.
  • Fix: Order owns orders; Payment stores captures separately and publishes events; Reporting and Northwind subscribe via CDC into their own databases — per database per service.
