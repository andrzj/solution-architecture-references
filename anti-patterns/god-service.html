Anti-Patterns

God Service

A microservice that absorbs unrelated responsibilities—becoming a distributed monolith in a single deployable unit.

⏱ 10 min read

What it is

A god service is a deployable that owns more business capabilities than one team can evolve on its own schedule. It usually began as the “service that already has the database,” then absorbed every adjacent feature until identity, billing, dispatch rules, and reporting share one schema and one release train. At the service level it is the same hub pattern as a god object, but with network fan-in and fan-out across the whole logistics platform.

A common pattern is a DispatchService microservice that still hosts driver roster CRUD, route optimization calls, SLA timers, partner webhooks, fuel surcharge tables, mobile sync, and finance export hooks left over from an earlier monolith split. Consoles, mobile apps, and batch jobs all call it, so incident response, scaling, and security reviews route through one bottleneck.

Why it emerges

Teams often decompose by deployable artifact, not by bounded context. “Dispatch” was the label on the repository that already talked to the shipments schema, so every logistics feature landed on DispatchService instead of new services with their own data and runbooks.

Organizational gravity reinforces the pattern. Standing up the first dispatch service is painful enough that product teams prefer new endpoints on the existing API over arguing for a notification or billing service with separate on-call. Martin Fowler’s microservices writing stresses that service boundaries should follow business capability; entity convenience wins when deadlines are tight.

Without scope freezes, the platform team became the default owner for cross-cutting requirements. Each endpoint was locally rational; the global shape is a monolith with HTTP headers.

How it manifests

  • DispatchService exposes REST and gRPC endpoints for roster management, routing, SLA evaluation, billing hooks, and reporting feeds, and new capabilities still land there by default.
  • Most production incidents start in or propagate through the hub service because dispatcher screens and mobile sync share its call graph.
  • Schema migrations on shared dispatch tables require sign-off from finance and partner integrations because multiple capabilities write the same rows.
  • Autoscaling cannot separate CPU-heavy route recalculation from lightweight mobile poll endpoints because they share one deployment and thread pool configuration.
  • Weekly release trains wait on DispatchService even when the only change is an unrelated mobile notification tweak bundled in the same artifact.

How to recognize it early

  • Track public endpoint growth and client import counts on the hub service; steady increases each quarter signal scope creep before on-call pain spikes.
  • When finance, mobile, and partner teams all open pull requests in the same service repository each sprint, ownership boundaries are already wrong.
  • A thin BFF that aggregates reads is acceptable; DispatchService instead owns authoritative writes for roster, SLA, and billing adjacency, which marks a god service rather than a facade.

Consequences and remediation

Consequences

  • DispatchService outages degrade dispatcher consoles, driver mobile apps, and finance exports simultaneously because those journeys share one deployment and datastore.
  • Conway’s Law runs in reverse: one service serializes finance, mobile, and partner squads that should ship on independent calendars.
  • Security and performance reviews must treat the entire logistics surface on every change because authorization and export paths live beside sub-second mobile reads.

Remediation strategies

  • Freeze new domain logic in the hub service and route greenfield partner APIs to new repositories aligned to bounded contexts.
  • Extraction uses strangler routing at the API gateway plus database per service so roster, SLA, and billing tables gain single write owners.
  • Cross-context reads move to domain events—RouteAssigned, SlaBreached—instead of shared-table joins from other services.
  • Team topologies pair each new service with one on-call rotation so organizational boundaries match deployable boundaries.

Detailed analysis

Remediation starts with change-history clustering on the hub service: endpoints that co-change for the same business reason become extraction units. Introduce narrow client SDKs so mobile and finance depend on small interfaces while implementations peel out behind those ports.

Splitting only the HTTP layer while keeping one shared OLTP schema recreates a distributed monolith; Chris Richardson’s microservices patterns treat separate persistence per service as non-negotiable for independence.

Progress shows up as release independence: roster deploys without finance export coordination, and route optimization scales out without resizing mobile poll tiers. Simon Brown’s C4 containers help narrate target services to leadership before data migration funding arrives.

Detection: one deployment blocks unrelated teams, oversized API surface, and on-call pages that require experts in billing and routing alike. Organizations fund “one platform team” without context boundaries. Safe sequence: event-storm contexts, carve read models, extract writers behind ACLs, split databases last. Monolith-style modules inside one repo with clear package boundaries are a valid interim state. In-process god types are god object problems before they become HTTP facades. Count distinct business owners who must sign off on each production deploy as a leading indicator. Shrinking that list is the goal of each extraction milestone and the metric executives should track quarterly.

Split on-call rotations before splitting databases so operational boundaries match the architecture you advertise to leadership, auditors, and customers.

Escalation patterns

  • Shared library rebound: “Extracted” services import DispatchService’s domain NuGet package, which preserves compile-time coupling and forces lockstep releases.
  • Partial strangler: A new notification microservice reads events but SLA writes still mutate shared tables, which produces dual-write and ordering bugs during hub failures.
  • Ossified interface: So many clients embed the sprawling OpenAPI document that breaking changes stall, and teams add optional fields forever instead of carving new services.

Diagnostic checklist

  • Can you describe the hub service’s responsibility in one sentence without joining unrelated capabilities?
  • Does one team own production deploys without a multi-squad release committee?
  • Can mobile driver sync fail degraded while finance batch export continues from a separate service?
  • Does each table have a single write owner that is not “whoever hits DispatchService first”?

Real-world examples

  • Illustrative scenario — Northwind DispatchService: A fuel-surcharge adjustment required a schema change on tables shared with SLA evaluation; finance and mobile squads had to coordinate a single deploy window, and a delayed rollout left drivers seeing stale ETAs while billing already applied the new rate until SLA evaluation was split into its own service with event-sourced breach records.

Related anti-patterns

  • God Object — code-level equivalent.
  • Distributed Monolith — often co-occurs with a god service at the hub.
  • Shared Database — typical persistence coupling behind god services.
