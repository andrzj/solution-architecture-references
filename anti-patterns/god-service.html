Anti-Patterns

God Service

A microservice that absorbs unrelated responsibilities—becoming a distributed monolith in a single deployable unit.

⏱ 10 min read

What it is

A god service is a microservice that owns far more domain logic, data, and integrations than one team can release independently. It often started small and grew because new features kept landing in “the service that already has the database.” The API surface spans unrelated capabilities—identity, billing, search, reporting—while one schema and one deployment schedule control them all.

At the service level this mirrors the god object anti-pattern in code: extremely high fan-in coupling (most features call it) and high fan-out coupling (it touches every datastore and legacy system). Incident response, scaling, and security reviews all route through this single bottleneck.

Why it emerges

God services appear when decomposition follows technical convenience instead of domain boundaries. Shared entities (“User”, “Order”, “Account”) become gravitational centers—every adjacent feature is added to the same service because the entity already lives there. Organizational pressure reinforces this: routing work through the owning team is easier than standing up a new service, runbook, and on-call rotation.

Without explicit scope governance, platform or “core” teams absorb requirements from product teams. Each addition is locally rational; the global structure becomes an unbounded monolith with network latency.

How it manifests

  • One service exposes dozens of REST or gRPC endpoints across unrelated business capabilities.
  • Most production incidents either start in or propagate through this service’s call graph.
  • Schema migrations require sign-off from multiple product teams because they share tables.
  • Autoscaling cannot match workload shape—CPU-heavy batch jobs share pools with latency-sensitive reads.
  • Release trains block on this service even when changes are unrelated to other teams’ work.

How to recognize it early

  • Track public endpoint count and afferent coupling (who imports this client). Sustained growth each quarter signals scope creep.
  • If more than two teams regularly open PRs against the same service repo, ownership boundaries are wrong.
  • A legitimate BFF that aggregates reads is thin and mostly stateless—if the service owns authoritative writes for many domains, it is a god service.

Consequences and remediation

Consequences

  • System-wide blast radius for failures, deployments, and performance regressions.
  • Team autonomy collapses—Conway’s Law in reverse: one service serializes many teams.
  • Testing and security reviews scale with the entire product surface area.

Remediation strategies

  • Freeze new domain logic in the god service; route features to new bounded-context services.
  • Extract one context at a time using strangler routing and database-per-service.
  • Publish domain events for cross-context reads; eliminate shared-table writes.
  • Align service boundaries with bounded contexts and team topologies.

Detailed analysis

Remediation starts with change-history analysis: which endpoints co-change for the same business reasons? Those clusters are extraction candidates. Introduce facades so consumers depend on narrow interfaces while you peel off implementations. Never split only the HTTP layer while retaining one database—that recreates a distributed monolith.

Measure progress by release independence: can Checkout deploy Friday without Billing coordinating? Can Search scale on object storage without touching transactional tables? Each “yes” indicates a successful extraction.

Escalation patterns

  • Shared library rebound: Extracted services import the god service’s domain package, preserving build-time coupling.
  • Partial strangler: New UI calls a new service while writes still hit the monolithic schema—dual-write bugs follow.
  • Ossified interface: So many consumers depend on the sprawling API that breaking changes become impossible; innovation slows.

Diagnostic checklist

  • Can you describe this service’s responsibility in one sentence without “and”?
  • Does exactly one team own production changes without multi-team release committees?
  • Can the service fail without taking down unrelated customer journeys?
  • Are datastore writes exclusive to this context (no cross-service table access)?

Real-world examples

  • SaaS “AccountService”: Owned SSO, billing, entitlements, audit, and notifications—P0 incidents in email delivery blocked login for all customers until contexts were split.
  • Retail “OrderService”: Absorbed cart, payments, tax, shipping labels, and loyalty points; extracted Checkout and Fulfillment over 18 months with event-driven inventory reservations.

Related anti-patterns

  • God Object — code-level equivalent.
  • Distributed Monolith — often co-occurs with a god service at the hub.
  • Shared Database — typical persistence coupling behind god services.
