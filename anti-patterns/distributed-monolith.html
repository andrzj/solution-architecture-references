Distributed Monolith

Last updated: January 2025

What it is

A distributed monolith is a microservices layout that keeps monolith coupling but adds network hops. Sam Newman popularized the term for teams that split deployables without splitting data or release independence. Services look separate in Kubernetes; in practice they share schemas, libraries, and synchronous call chains that must all succeed before a customer journey completes.

At Meridian Commerce, the running example is a faux microservices estate carved from the modular monolith: Order, Payment, Inventory, Notification, and Fraud services each have their own repo and CI badge, yet they still read and write meridian_core on a shared Postgres instance and call one another in long synchronous chains during checkout. Martin Fowler’s Microservice Premium essay warns that you pay distributed operations cost without autonomy when boundaries are drawn this way.

Why it emerges

Meridian’s migration followed entity labels from the old monolith—one service per noun—rather than bounded contexts. Checkout still needs inventory, payments, and fraud in one request, so the split moved method calls to HTTP without moving data ownership.

Shared database access was the seductive shortcut. Chris Richardson’s database per service pattern explains why shared OLTP breaks independence; Meridian kept one schema to avoid migration cost and duplicated ORM models in a shared npm package so every service compiled against the same entity graph.

Delivery pressure added synchronous coupling: a quick REST call beat standing up events and read models for launch milestones. Each shortcut was locally defensible; collectively Meridian runs a monolith with Grafana dashboards per pod.

How it manifests

  • Meridian’s Order, Payment, and Inventory services deploy in a negotiated order each week because shared migrations and client stubs must align.
  • Multiple services issue INSERT and UPDATE against the same orders and inventory_reservations tables inside meridian_core.
  • Storefront checkout blocks on a synchronous fan-out across Order, Inventory, Payment, Fraud, and Notification before the HTTP response returns.
  • A shared @meridian/domain package ships entity classes and pricing rules to every service, so version bumps force coordinated releases.
  • When FraudService slows during a sale, thread pools fill on OrderService and the gateway returns errors for unrelated browse traffic because there is no bulkheading on the sync graph.
  • Teams file cross-repo release tickets before merging schema-dependent features because no service owns the database alone.

How to recognize it early

  • Deployment choreography: Meridian cannot ship PaymentService alone when OrderService still expects a new column on a shared table, which is a distributed monolith signal.
  • Cross-service database queries: InventoryService still joins orders in SQL views rather than consuming events, which means services share persistence instead of contracts.
  • Thick shared libraries: Business rules live in the shared domain package, so a pricing tweak rebuilds every consumer service.
  • No independent scalability: Scaling Inventory pods during a flash sale also increases lock contention on shared tables that Payment and Order hit, so horizontal scale does not isolate workloads.

Consequences and remediation

Consequences

  • Maximum operational overhead: Meridian pays for service meshes, per-service CI, and distributed tracing while still running coordinated release trains like the old monolith.
  • Compounded fragility: Checkout latency is the sum of synchronous RPCs, and a slow FraudService stall blocks order placement even when inventory and payment tiers are healthy.
  • Development velocity collapses: Product squads wait on schema CAB approvals and cross-service contract bumps, so feature lead time resembles the pre-split monolith.
  • Debugging complexity: A failed checkout trace spans five services and still ends in one shared database transaction log, which is harder to read than a single stack trace.

Remediation strategies

  • Database per service: Meridian assigns each context its own schema or instance and migrates writers first, using CDC or domain events to replicate read-only copies.
  • Introduce async messaging: Post-checkout steps—email, analytics, loyalty—subscribe to OrderPlaced instead of blocking the HTTP response path.
  • Re-draw service boundaries: Event storming and bounded-context workshops re-anchor services on capabilities such as “capture payment” rather than on shared tables.
  • Strangle with a façade: Fowler’s strangler fig routes new checkout experiments behind a façade while legacy sync paths shrink slice by slice.

Detailed analysis

Coupling that was once cheap in-process is now brittle over the network. Meridian’s OrderService and InventoryService both mutate orders rows; adding marketplace seller metadata requires a migration every consumer acknowledges before deploy, which is the monolith dependency graph with extra steps.

Synchronous checkout orchestration keeps threads waiting on FraudService during flash events; circuit breakers limit pain but do not restore independence—the cure is choreography plus idempotent consumers.

Intentional duplication is part of the exit: OrderService keeps denormalized shipping addresses fed by UserService events so fulfillment does not join across databases at request time.

Simon Brown’s C4 views help Meridian executives see containers and data stores separately so funding targets schema splits, not another round of “microservices training.”

Escalation patterns

  • Schema coupling spiral: Meridian postpones nullable-column migrations because Payment and Inventory services disagree on semantics, so the shared schema stops evolving.
  • Shared library versioning hell: Teams pin different versions of @meridian/domain, and production drifts until someone forces a big-bang upgrade weekend.
  • Deployment window compression: Coordination cost pushes Meridian back to monthly “train” releases that batch unrelated service changes.
  • Observability bankruptcy: Traces exist but on-call defaults to widening timeouts because root-cause analysis across sync graphs takes too long during incidents.

Diagnostic checklist

  • Can Meridian deploy PaymentService on its own while OrderService remains on last week’s build without breaking checkout?
  • Does each service own a schema that other services never write to directly?
  • Can FraudService fail entirely while browse and cart APIs stay available?
  • Do non-query steps use events instead of chained HTTP for happy-path checkout?
  • Are shared libraries limited to technical cross-cutting code rather than pricing and inventory rules?
  • Can one squad ship a feature entirely inside its bounded context without opening PRs in three other repositories?

Real-world examples

  • Meridian faux microservices: A nullable payment-capture column migration required Order, Payment, and Inventory to deploy the same evening; Inventory’s batch reconciler failed on the new default, checkout returned 503s until all three rolled back, and leadership paused extraction until database-per-service funding landed for payment capture first.
