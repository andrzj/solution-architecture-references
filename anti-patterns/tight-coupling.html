Anti-Patterns

Tight Coupling

Design where a change in one module forces coordinated changes in many others—across compile time, deploy time, or runtime.

⏱ 10 min read

What it is

Tight coupling means a change in one module forces coordinated changes in others — at compile time, deploy time, or runtime. Shared types, synchronous call chains, and hidden contracts replace published boundaries. The symptom is not “two services talk”; it is that neither can evolve alone.

A billing deployable that imports a catalog ORM package and uses catalog’s Product entity in invoice line generation looks independent in Kubernetes, but catalog’s schema version and package release dictate billing’s train.

Tight coupling is the compile-time and data-plane sibling of distributed monolith behavior: separate repos with monolith dependencies.

Why it exists

Billing teams often need SKU descriptions and tax codes quickly; importing the catalog ORM is faster than defining an integration contract, anti-corruption layer, or event stream.

The shared package duplicates the monolith’s entity graph across repositories. Every consumer compiles against the same types, so renaming a column in catalog becomes billing’s problem without an API version bump anyone discussed.

Without governance on published APIs and events, every shortcut becomes a permanent edge in the dependency graph. Code review that celebrates “reuse” without boundary review accelerates the entanglement.

How it manifests

  • Billing pins catalog-orm@2.3; catalog bumps to 2.4 and billing must ship the same week.
  • Invoice PDFs break when catalog renames a column billing’s ORM mapped directly.
  • Integration tests start Postgres, catalog API, and billing—no isolated billing unit suite.
  • Downstream dispatch or finance teams wait on billing because a catalog refactor blocked invoice deploy.
  • Pull requests in one service require simultaneous changes in two others to keep builds green.
  • Runtime failures in catalog take billing offline even when rating data for recurring invoices is unchanged.

How to recognize it early

  • Generated clients vs shared entities: Versioned OpenAPI clients generated per release signal loose coupling; shared JARs with domain entities signal tight coupling.
  • Monolith boundaries: Explicit module boundaries inside one modular monolith, with no cross-repo ORM imports, are intentional in-process coupling—not this anti-pattern at service scope.
  • Deploy independence: If release notes routinely list paired service versions, coupling has become operational habit.
  • Test pyramid inversion: Teams skip unit tests because wiring half the estate is the only way to exercise billing logic.

Typical manifestation

One service’s dependency graph tugs peers whenever shared libraries or schemas change—any tug moves multiple deployables.

Consequences and remediation

Consequences

  • Shared release windows: Catalog and billing share a single production deploy train for schema-aligned changes.
  • Regression tax: Minor catalog refactors require full regression of invoice PDFs, EDI exports, and batch jobs.
  • Failure propagation: Catalog outages take billing offline even when invoice data is static for recurring lanes.
  • Velocity collapse: Feature work in billing queues behind catalog refactors unrelated to invoice rules.

Remediation strategies

  • Events over ORM: Publish RateCardPublished / SkuSnapshot instead of sharing database packages.
  • Anti-corruption layer: Map catalog API responses into billing-owned invoice line DTOs.
  • Contract tests: Consumer-driven contract tests on catalog’s HTTP API lock JSON shapes.
  • Freeze imports: Measure cross-repo PRs touching shared ORM packages and stop new consumers.

Implementation notes

Remediation starts by measuring cross-repo pull requests touching shared ORM artifacts and freezing new imports. Billing’s anti-corruption layer maps catalog HTTP responses into BillableLineItem (or equivalent) types billing owns outright.

Prioritize the hot path: recurring lane invoices that need stable SKU snapshots before ad-hoc catalog lookups. Strangle remaining ORM reads behind cached snapshots with explicit TTL and version fields so renames surface as contract test failures, not production PDF gaps.

Synchronous calls that remain should use timeouts, bulkheads, and circuit breakers so catalog blips do not empty billing’s thread pools—but resilience patterns do not replace published boundaries.

Diagnose temporal coupling (must call now), location coupling (hard-coded hosts), schema coupling (shared DTOs), and implementation coupling (shared libraries) via dependency graphs and connascence metrics. Deadline pressure and shared backlogs discourage stable contracts. Decouple with versioned events, asynchronous handoffs, and anti-corruption layers in that order. Tight collaboration inside one bounded context is acceptable; hidden coupling across contexts is not. When services deploy separately yet fail together, see distributed monolith. Map coupling types explicitly in incident postmortems so fixes target contracts, not only retries. Prefer events on the critical path only after idempotency, ordering, replay, and monitoring are proven.

Version integration contracts in CI and block consumer deploys when provider events or schema changes break compatibility checks in staging first.

Escalation patterns

  • DTO mirroring: Billing copies catalog’s entire Product graph; every catalog field becomes billing’s problem.
  • Shared migrations: One Flyway script alters tables both teams thought they owned.
  • Version pin deadlock: Services pin different ORM versions; production drifts until a forced big-bang upgrade weekend.
  • ACL bypass: Engineers add “just one” direct ORM read for a demo; the exception becomes the pattern.

Diagnostic checklist

  • Can catalog rename a SKU attribute without a billing release?
  • Does billing depend on catalog’s database package or on versioned APIs and events?
  • Are cross-service calls bounded with timeouts and bulkheads?
  • Do contract tests fail when catalog changes response shape without a negotiated version bump?
  • Can billing unit tests run without starting catalog’s database or API?
  • Is there an inventory of shared libraries with owners and deprecation dates?

Example use cases

  • Northwind Logistics billing and catalog: Billing imported catalog ORM; a hazmat flag rename broke invoice line rendering until both repos deployed. Billing then consumed SkuSnapshot events and called catalog’s OpenAPI for ad-hoc lookups; contract tests locked the JSON schema—aligned with loosely coupled components.
