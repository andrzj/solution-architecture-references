Anti-Patterns

Chatty Services

Fine-grained RPC chatter between services where one user request fans out into dozens of synchronous calls.

⏱ 10 min read

What it is

Chatty services is the pattern to use when p95 user latency tracks the sum of downstream service latencies. Exchange many small synchronous messages to complete a single business operation. A client request triggers a long chain—or wide fan-out—of HTTP/gRPC calls, each adding network RTT, serialization cost, and failure probability. What was a few in-process method calls in a monolith becomes tens of network hops with multiplicative tail latency.

Why it exists

Chatty interactions often begin when services are decomposed along entity lines rather than use cases. Each micro-step becomes its own endpoint. Without caching, batch APIs, or denormalized read models, aggregating a screen requires N+1 service calls. Teams optimize local code clarity at the expense of global call graphs.

How it manifests

  • P95 user latency tracks the sum of downstream service latencies.
  • Distributed traces for one request show 15+ synchronous spans.
  • Timeouts cascade because each hop retries independently.
  • Client teams request a single “bulk” or “aggregate” API to stop calling you five times.

How to recognize it early

  • A bounded internal pipeline with strict size limits and circuit breakers may be acceptable for batch jobs—not for user-facing paths.

Typical manifestation

Fan-out multiplies tail latency; partial failures become full user-visible errors.

Consequences and remediation

Consequences

  • Tail latency explosion and retry storms.
  • Low composite availability across chains.
  • Operational cost of tracing and debugging.

Remediation

  • Aggregate/batch endpoints at bounded contexts.
  • Materialized read models and caching.
  • Async choreography for non-query steps.

Implementation notes

Introduce a BFF or GraphQL layer for read aggregation. Co-locate hot read paths behind a single query service. Enforce budgets: max downstream calls per request via service mesh or gateway policies. Replace chatty fine-grained CRUD with task-based APIs (`PlaceOrder` vs five preparatory calls).

Escalation patterns

  • Cache stampede: Caching each chatty call without request coalescing amplifies load on the hottest microservice.
  • Retry multiplication: Default client retries on every hop turn transient blips into outages.

Diagnostic checklist

  • Is there a documented max fan-out per customer-facing endpoint?
  • Can the use case be completed with one or two synchronous calls?
  • Are non-critical steps moved to async events?

Example use cases

  • Product detail page: 22 synchronous calls for reviews, ratings, inventory, pricing, and promos; consolidated into one catalog query service cut P95 latency 60%.
