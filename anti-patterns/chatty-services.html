Anti-Patterns

Chatty Services

Fine-grained RPC chatter between services where one user request fans out into dozens of synchronous calls.

⏱ 10 min read

What it is

Chatty services exchange many fine-grained synchronous RPCs for one user action. Each hop adds RTT, serialization, and failure surface; tail latency stacks. Sam Newman’s microservice trade-offs note that fine-grained decomposition without aggregate APIs often recreates in-process chatter over the network.

At Meridian Commerce, the mobile checkout BFF loads cart review by calling Pricing, Inventory, Tax, Promotions, Loyalty, Address validation, and Payment vault services sequentially — one shopper tap, fourteen synchronous spans before “Place order” is enabled.

Why it exists

Meridian decomposed by entity (“one microservice per noun”) instead of by use case. Each team shipped crisp CRUD APIs; nobody owned the checkout screen. Composing the UI in the BFF without batch endpoints or a read model felt fastest for each squad.

Without caching, materialized views, or task-based APIs, every new badge on the cart adds another RPC.

How it manifests

  • Meridian checkout P95 tracks the sum of downstream latencies, not the slowest single call.
  • Traces for GET /cart/review show 15+ sync gRPC/HTTP spans before submission.
  • Inventory blips retry independently on each hop, multiplying load on an already hot service.
  • Mobile clients beg for one “cart snapshot” API because the BFF fans out per line item.

How to recognize it early

  • Meridian’s nightly catalog export may chain many internal calls with strict batch limits — acceptable for batch, not for checkout.
  • OpenTelemetry dashboards where span count per route grows every sprint without new user features.

Typical manifestation

Meridian checkout fan-out multiplies tail latency; one downstream timeout fails the whole cart.

Consequences and remediation

Consequences

  • Meridian mobile checkout misses latency SLOs during promos when Pricing and Promotions both slow down.
  • Composite availability is the product of many dependencies — one flaky downstream service drags checkout below its availability target.
  • On-call chases many service owners for a single failed trace.

Remediation

  • GET /cart/snapshot and bulk SKU APIs at Catalog/Pricing boundaries.
  • Materialized checkout read model updated from domain events.
  • Task API PlaceOrder with async choreography for email and loyalty accrual.

Implementation notes

Meridian capped fan-out at the API gateway (max eight downstream sync calls per shopper route) and added a checkout query service behind the BFF. Non-critical steps — loyalty accrual, recommendation nudges — moved to post-commit events. Parallel fan-out with bounded concurrency replaced strictly sequential gRPC where bulk APIs were not yet available.

Escalation patterns

  • Per-call caching: Twelve Redis keys per cart without coalescing stampede Pricing on cache expiry.
  • Retry multiplication: Default gRPC retries on every hop turn a blip into an Inventory outage — tune per cascading failure guidance.

Diagnostic checklist

  • Does Meridian document max fan-out per customer-facing checkout route?
  • Can review-and-submit complete with one or two synchronous calls?
  • Are marketing and loyalty side effects async after order commit?

Example use cases

Meridian mobile checkout:

  • Anti-pattern: Cart review fans out to twelve services; checkout latency exceeds the mobile SLO and abandonment spikes during flash sales.
  • Fix: Checkout query service serves one snapshot; PlaceOrder orchestrates capture synchronously and publishes events for the rest — staging traces show materially lower tail latency on cart review.
