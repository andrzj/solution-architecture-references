Event Notification

A lightweight broadcast of "something happened" — the minimal notification that prompts subscribers to act, contrasted with event-carried state transfer, and aligned to the CloudEvents specification.

⏱ 10 min read

What it is

Event notification is an event-driven integration style in which a producer publishes a compact message meaning “something happened,” and interested consumers react without receiving a full copy of the producer’s entity state in the event itself. Martin Fowler’s essay What Do You Mean by Event-Driven? contrasts this notification style with event-carried state transfer (ECST), where the event payload carries enough fields for consumers to update their own views without calling back.

Notification events typically carry identifiers, types, and timestamps—enough to route and correlate—while the owning service remains the system of record. Consumers that need detail call the producer’s query API (or another sanctioned read path) after they receive the notification. That preserves encapsulation: the producer can refactor internal models while keeping the public notification contract stable.

The CNCF CloudEvents specification standardizes the cross-platform envelope (id, source, type, subject, time, optional data). AsyncAPI documents channel contracts for discovery; schema registries (for example Confluent Schema Registry on Kafka, or cloud event schema catalogs) enforce evolution rules on serialized payloads.

Why it exists

Broadcasting “fat” events forces every publisher to freeze a public projection of its entire domain model. Notification events shrink that commitment to “this entity changed” plus stable identifiers, which makes refactors inside the producer safer and keeps broker storage and fan-out bandwidth lower than shipping full aggregates on every change.

When consumers must reflect authoritative state, a follow-up read from the producer (or a cached replica fed by the same source) avoids embedding stale snapshots in messages that may be processed minutes or hours later. The trade-off is extra read traffic and a runtime dependency on the producer’s query availability—acceptable when change volume is moderate and the producer’s API is engineered for consumer fetch patterns.

Choose notifications when encapsulation and schema stability matter more than offline autonomy. Choose event-carried state transfer when consumers must progress during producer outages or when fetch storms would overwhelm read APIs. Hybrid designs emit thin notifications for most subscribers and full payloads on dedicated changelog topics for analytics—do not force one style globally.

When to use

  • You need many subscribers to learn that a domain fact occurred, but each subscriber only needs a subset of fields and can obtain them via API or a local cache after the signal arrives.
  • The producer must remain the single writer and authoritative reader for its aggregate, and you want events to announce changes without duplicating the full aggregate graph on the bus.
  • Cache or CDN invalidation should be key-oriented: subscribers evict or refresh entries named by IDs in the notification rather than merging partial state from the event stream.
  • Event volume or fan-out is high relative to payload size, so minimizing serialized bytes reduces broker cost and consumer CPU.
  • You already standardize envelopes on CloudEvents and govern type strings and optional dataschema URLs through AsyncAPI and a registry.

When not to use

  • Downstream consumers cannot tolerate a follow-up read when the producer is degraded, rate-limited, or geographically distant—ECST or a materialized read model fed by a durable log may be safer.
  • Every notification would trigger a full-entity fetch and the entity is large or slow to load, so bandwidth and API load dominate compared with shipping a curated projection once in the event.
  • Regulators or auditors require a point-in-time snapshot at the moment the business event occurred; notification-only messages cannot reconstruct that view without separate event sourcing or archival.
  • Consumers need historical replay of what the entity looked like when the event was emitted; use event-carried state, event sourcing, or a retained streaming log instead.

Typical architecture

After a successful local transaction, the producer publishes a skinny domain notification to a topic (Kafka, SNS, Google Pub/Sub, RabbitMQ fanout, or EventBridge). Subscribers deserialize the CloudEvents envelope, decide whether they care based on type and optional filters, and either act on identifiers alone or invoke the producer’s read API before applying side effects. Schema compatibility checks and documented AsyncAPI channels keep producers and consumers aligned as versions evolve.

Pros and cons

Pros

  • Small payloads reduce broker storage, network fan-out, and deserialization cost compared with shipping full aggregates on every change.
  • The producer retains clear data ownership, so consumers read current state from the authoritative API instead of trusting embedded snapshots.
  • Internal domain refactors can proceed while the notification contract (identifiers and type) stays stable.
  • CloudEvents and AsyncAPI give portable metadata across Knative, EventBridge, Event Grid, Eventarc, and self-hosted brokers.
  • Pub/sub channels naturally broadcast the same notification to many independent reactions without producer awareness of subscribers.

Cons

  • High fan-out plus per-consumer fetches multiplies read load on the producer unless you add shared caches or selective ECST.
  • Notification processing stalls or degrades when the producer query API is unavailable unless consumers queue work and retry with backpressure.
  • Replaying old notifications cannot by itself answer “what did the entity look like then” without event-carried state or an event log.
  • End-to-end latency includes publish time plus at least one read round trip when consumers need more than IDs.

Implementation notes

Minimal data: Include stable identifiers, the business event name, and optional correlation fields. Keep rapidly mutating attributes on the read API or a downstream projection, not in every notification.

CloudEvents: Populate required attributes per the CloudEvents core specification. Use reverse-DNS type strings, set subject to the entity reference, and point dataschema at versioned JSON Schema or Avro in the registry when consumers validate payloads.

Governance: Register each type in AsyncAPI with owning team, compatibility mode, and example payloads. Enforce BACKWARD or FULL compatibility in the schema registry before production publishes.

Fetch path: Wrap producer reads with timeouts, circuit breakers, and bulkhead limits. Consider a short-lived read-through cache keyed by entity ID when many subscribers fetch the same object after one notification.

Reliable publish: Pair domain writes with the transactional outbox pattern so notifications are not lost when the broker is temporarily unavailable.

Notification versus carried state: Martin Fowler’s event-driven taxonomy separates event notification (pointer to fetch state) from event-carried state transfer (payload already sufficient). Notifications shrink Kafka bandwidth and publisher coupling but multiply read load on the producer API—size gateways and caches for fan-out fetch, or graduate hot paths to richer events when fetch storms dominate.

Envelope size targets: keep notifications under a few kilobytes—identifiers, type, correlation, optional changed-field list. Large binaries belong in claim check with a fetch URL in data. MQTT and AMQP brokers also punish multi-megabyte frames; notifications should not be dump trucks.

Detection: alert on producer API QPS correlated with notification publish rate—slope above 1:1 per subscriber signals missing cache or ECST where notifications suffice. Schema registry rejections should block deploy; runtime deserialization errors without registry blocks indicate shadow producers.

Versioning: notification contracts should evolve by adding optional fields, not renaming types—subscribers that only need ids tolerate small envelope changes. Breaking type renames require dual-publish periods or consumer feature flags because many subscribers filter on type alone.

Payload discipline: notifications carry identifiers and scalar deltas, not full aggregate snapshots—subscribers that need rich state issue a follow-up query or subscribe to a separate projection stream. Oversized notification payloads force every subscriber to deserialize megabytes for events they may ignore, defeating the pattern’s purpose. CloudEvents dataschema and AsyncAPI documents make “thin envelope” contracts reviewable in CI before deploy.

Common failure modes

  • Fetch storms after fan-out: Many subscribers each pull the full entity on every notification and overwhelm the producer API; mitigate with ECST for hot paths, coalesced reads, or edge caches.
  • Silent schema drift: Two teams emit the same type with incompatible JSON; consumers fail intermittently until registry enforcement and AsyncAPI reviews catch the divergence.
  • Treating current state as delta: A consumer fetches after a later update and misses intermediate transitions; design for idempotent application of latest state or consume a richer event stream when sequence matters.
  • Publishing before commit: A notification leaves the broker while the database transaction rolls back, causing phantom downstream work; commit and outbox in one transaction first.

Decision checklist

  • Can every subscriber tolerate a read dependency on the producer (or a replica fed from the same source) under expected outage windows?
  • Are notifications wrapped in CloudEvents (or an equivalent standard envelope) with unique id values for deduplication?
  • Are event types and payloads registered in AsyncAPI with schema compatibility enforced in CI?
  • Is there a documented breaking-change policy (new type or major schema version, dual publishing during migration)?
  • Are follow-up fetches protected with circuit breakers and backoff so broker lag does not amplify into API outages?
  • Is producer read capacity sized for notification fan-out at peak, including cache hit ratios where applicable?

Example use cases

  • Illustrative scenario — A catalogue service publishes com.example.product.updated with only productId in data; edge caches evict that key and lazy-load fresh attributes on the next shopper request.
  • Illustrative scenario — After payment capture, the payments boundary emits a skinny payment.completed notification; fulfilment loads order lines via the orders API using the payment’s correlation identifiers before reserving stock.
  • Illustrative scenario — A platform team documents all domain notifications in AsyncAPI and blocks deploys when a producer’s schema fails registry compatibility checks against existing consumers.
  • Illustrative scenario — An architecture review chooses notification events for catalogue changes but event-carried state for infrequent bulk catalog exports because downstream warehouses cannot afford N parallel fetches during a full refresh.

Related patterns

  • Command Pattern — successful commands often conclude by emitting a domain notification that downstream systems observe.
  • Publish/Subscribe — fan-out transport for notifications to many subscribers.
  • Webhooks — HTTP push variant of event notification to external partners.
  • Event Streaming — when notifications must be replayed from a durable log rather than ephemeral signals alone.
  • Event-Driven Architecture — system-level style combining notifications, choreography, and projections.
