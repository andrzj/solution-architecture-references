Transactional Outbox Pattern

The transactional outbox pattern atomically updates application data and records outbound messages in one database transaction, then uses a separate message relay—polling or CDC—to publish to a broker without two-phase commit.

⏱ 12 min read

What it is

The transactional outbox pattern lets a service update persistent domain state and record an outbound message in one local database transaction. Instead of calling the message broker inside or immediately after the transaction—which cannot be made atomic across DB and broker—the application inserts a row into an outbox table alongside business writes. A separate message relay reads those rows and publishes them to Kafka, RabbitMQ, SQS, or similar infrastructure.

Chris Richardson documents this on microservices.io as the standard answer to “atomically update the database and send messages” without distributed two-phase commit (2PC). The sender, database (business data plus outbox), and relay are the three moving parts; the broker sits downstream of the relay.

If the transaction commits, the message is guaranteed to reach the broker eventually (at-least-once via the relay). If the transaction rolls back, no outbox row exists and nothing is published. Publication lag is typically milliseconds to seconds depending on polling interval or CDC latency—not synchronous with the client response.

Why it exists

Microservices routinely hit the dual-write problem: “update the aggregate, then publish an event.” Publish-before-commit risks phantom events; commit-then-publish risks lost events if the process crashes or the broker is down. XA/2PC across database and broker is rarely viable—many stacks do not support it, and coupling every service to both stores is undesirable.

Richardson’s formulation adds an ordering constraint: events for the same aggregate should reach consumers in the order the application emitted them, even across multiple application instances. Persisting messages in the outbox inside the transaction gives the database a durable, ordered queue the relay can drain without the application holding an open transaction across the network.

The outbox is not a magic exactly-once pipe: relay retries duplicate broker messages; consumers still need inbox or idempotency. The guarantee is narrower and still valuable—no committed business state without an eventual publish intent recorded, and no publish intent without committed state. Monitoring unpublished row count is as important as monitoring broker lag because a silent relay pause looks like healthy Kafka while workflows freeze.

When to use

  • Database update plus domain event publication — persist aggregate state and enqueue the matching domain event in one logical unit of work.
  • Saga or process-manager steps — each step that mutates local state and must notify the next participant.
  • Regulated or revenue-critical flows — silent message loss after a successful commit is unacceptable.
  • Broker or network instability — the service commits locally; the relay catches up when the broker recovers.
  • No distributed transaction between DB and broker — the practical alternative to 2PC in polyglot microservices.

When not to use

  • Hard synchronous publish requirement — callers cannot tolerate relay lag before downstream systems see the event.
  • No transactional store for the outbox — without local ACID (or an equivalent multi-document transaction), you cannot co-locate business data and outbox rows reliably.
  • Broker is the only source of truth — if you never persist domain state in a database, an outbox table has nothing to join.
  • Extreme write rates without operational discipline — the outbox grows until pruned or partitioned; neglecting retention planning becomes a production incident.

Typical architecture

Within one transaction, the application updates domain tables and inserts into outbox (event type, aggregate id, payload, optional metadata). The message relay either polls unpublished rows or tails the database log via CDC. After successful publish, the relay marks the row published (polling) or relies on downstream idempotency (some CDC setups); unpublished backlog and relay health are monitored. Published rows are pruned or partitioned away on a schedule.

Pros and cons

Pros

  • Local atomicity — business state and intended message commit or roll back together; no split-brain between DB and broker on the write path.
  • Publish iff commit — Richardson’s guarantee: messages are sent only when the transaction commits, and commit implies eventual publish.
  • Broker decoupling — application throughput does not block on broker availability; the relay retries.
  • Per-aggregate ordering — relay can key messages by aggregate id so one partition preserves sequence for that entity.
  • Technology flexibility — relay adapters can target different brokers without changing domain code.

Cons

  • Extra moving parts — relay deployment, monitoring, and failure handling are mandatory, not optional.
  • Eventual publication latency — downstream sees events after relay lag, not inside the request transaction.
  • Polling cost — naive SELECT … WHERE published = false loops add read load unless replaced by CDC.
  • At-least-once from the relay — duplicate publishes after relay crashes; consumers need idempotency (inbox pattern).
  • Developer foot-gun — domain code must always write the outbox row; forgetting it reintroduces dual-write risk.

Implementation notes

Outbox row shape: Typical columns: surrogate id, aggregate_type, aggregate_id (broker partition key), event_type or topic name, serialized payload, created_at, and for polling relays published / published_at. Index (published, created_at) for poll queries. Keep payloads versioned; avoid leaking unstable internal schema.

Polling relay: A worker claims batches of unpublished rows, publishes, then updates published in the same database or via idempotent publish semantics. Use modest batch sizes, backoff on broker errors, and leader election so only one active relay mutates state. Poll intervals in the hundreds of milliseconds are a common starting point—tune against DB load and latency SLOs.

CDC relay (Debezium): Debezium connectors read PostgreSQL WAL, MySQL binlog, or similar and emit change events without polling the outbox table. The Outbox Event Router single message transform maps outbox table columns to Kafka topic, key, and payload per Debezium’s documented router configuration—often the lowest-latency option when you already run CDC. See also the Debezium reference for connector tuning and delivery semantics.

Ordering: Richardson notes messages should leave the broker in application send order for a given aggregate. Use a stable aggregate_id as the message key (Kafka partition key, SQS message group id in FIFO, etc.).

Retention and pruning: Delete or partition away published rows after a retention window. Unbounded tables slow inserts and polls. Time-based partitioning plus partition drops scales better than row-by-row deletes at high volume.

Observability: Metric unpublished outbox depth, relay error rate, publish lag (time from created_at to broker ack), and broker consumer lag. Alert when unpublished count grows monotonically.

Consumer side: Treat relay delivery as at-least-once. Pair with the inbox pattern or Richardson’s idempotent consumer so duplicate events do not duplicate business effects.

Envelope standards: map outbox rows to CloudEvents in the relay adapter so id, type, source, and time propagate for tracing and idempotent consumers. Debezium’s outbox router SMT can embed CloudEvent headers directly from column mappings.

Latency expectations: polling relays often add hundreds of milliseconds to seconds of publication lag; CDC paths commonly reach sub-second when connector lag is healthy. SLO dashboards should chart now() - created_at for unpublished rows at p95, not only relay process uptime.

Common mistake: updating business tables and publishing to Kafka in the same request thread without outbox—Kafka ack after DB commit still fails if the process crashes between the two, or if the broker rejects the record. The outbox row must commit in the same transaction as the domain write; publish always happens later.

Relay lag SLOs: measure time from outbox insert to broker publish (p95 relay latency); multi-second medians often mean polling too slowly or relay competing for DB connections with OLTP traffic. CDC-based relays (Debezium) shift load to the replication log but introduce schema-migration coordination—poll-based relays are simpler but add write amplification on the outbox table. Cap relay batch size so one slow broker partition does not block unrelated events; shard relays by aggregate type when outbox tables exceed tens of millions of rows.

Common failure modes

  • Outbox write omitted in application code — domain state commits without a matching outbox row; downstream never learns of the change. Code review and integration tests should assert outbox inserts on every publish path.
  • Stalled or missing relay — unpublished rows accumulate; user-facing APIs look correct while async workflows freeze. Alert on depth and relay heartbeat.
  • Relay publishes before mark-published (polling) — crash between broker ack and DB update causes duplicate delivery; consumers must deduplicate.
  • Wrong partition key — events for one aggregate interleave across partitions; consumers see reordering. Fix keying in the relay adapter.
  • Unpruned outbox table — index bloat and slower transactions on the hot path. Automate retention from the first production deploy.
  • CDC misconfiguration — connector lag, schema drift, or router SMT mis-mapping produces wrong topics or dropped fields. Validate with contract tests against sample outbox rows.

Decision checklist

  • Does every code path that should emit an event insert an outbox row in the same transaction as the domain write?
  • Is the message relay highly available (or single-leader with fast failover) and monitored?
  • Polling vs CDC: is the chosen relay mode sized for expected throughput and latency?
  • Is aggregate_id used consistently as the broker message key for ordering?
  • Are unpublished outbox rows counted and alerted on?
  • Is there a retention or partition strategy for published rows?
  • Are downstream consumers idempotent (inbox or equivalent) for at-least-once relay delivery?

Example use cases

  • Illustrative scenario — Meridian Commerce order service commits an order row and an order.confirmed outbox entry in one transaction; a Debezium relay publishes to Kafka; inventory consumes and reserves stock without Meridian ever dual-writing to Kafka in the request thread.
  • Illustrative scenario — Northwind Logistics payment service records settlement and enqueues payment.captured via outbox; when the broker was down overnight, the relay drains the backlog at morning cutover so fulfilment does not ship on unpaid orders.
  • Illustrative scenario — A saga orchestrator at FieldOps completes each local step in a workflow table and outbox-inserts the next command; relay lag is acceptable because human operators see consistent internal state even when async participants catch up minutes later.
