Inbox Pattern

The inbox pattern records processed message identifiers in the same database transaction as the business side effect so at-least-once brokers can redeliver without applying duplicate work.

⏱ 10 min read

What it is

The inbox pattern (closely related to the idempotent consumer) makes message handling safe under at-least-once delivery. Before applying a business side effect, the consumer records the message’s unique identifier in an inbox or processed_messages table inside the same database transaction as the domain update. A primary-key or unique constraint on that identifier ensures a redelivered message cannot commit its side effect twice—the duplicate insert fails and the handler skips work while still acknowledging the broker.

Chris Richardson describes the same idea on microservices.io: persist processed message IDs (optionally scoped by consumer) so duplicate invocations produce the same outcome as a single invocation. The database transaction is the serialization point, which matters when several consumer instances might process the same redelivery concurrently.

Paired with the transactional outbox pattern on the producer, inbox deduplication yields effectively exactly-once processing across the pipeline: at-least-once transport on both legs, with idempotent consumers at the edge of each service’s database.

Why it exists

Brokers and relays deliberately favor durability over suppressing duplicates. Visibility timeouts, consumer crashes after publish but before ack, and outbox relay retries all produce the same logical event more than once. Hand-writing idempotent logic into every handler (ledger entries, stock decrements, “send email” actions) is error-prone.

The inbox externalizes deduplication: one table, one constraint, one transactional ordering rule (record message id, then mutate domain state, then commit). Richardson’s idempotent consumer pattern is the reference formulation; the inbox name emphasizes the mirror image of the producer’s outbox table.

When to use

  • Non-idempotent side effects — payments, notifications, inventory movements, downstream outbox inserts.
  • At-least-once brokers and relays — SQS, RabbitMQ, Kafka consumers without end-to-end transactions, transactional outbox relays.
  • Horizontally scaled consumers — competing consumers where redelivery races are possible.
  • Saga participants — orchestrators may retry steps; participants must tolerate duplicate commands.
  • End-to-end pipelines with transactional outbox producers — absorb duplicate events from the relay.

When not to use

  • Naturally idempotent handlers — e.g. “set status to SHIPPED” when already SHIPPED; extra writes buy little.
  • No co-located transactional store — without a DB transaction tying dedupe to side effects, a separate dedupe cache (Redis SET NX) reduces duplicates but does not match inbox atomicity.
  • Kafka EOS already enforced end-to-end — transactional read-process-write within Kafka may suffice for some topologies; inbox remains valuable across polyglot services and external side effects.
  • Unstable message identifiers — if the broker does not provide a stable id across redeliveries, the inbox cannot detect duplicates.

Typical architecture

The consumer opens a database transaction, inserts the message id into the inbox (or detects conflict), applies domain mutations if insert succeeded, optionally writes its own outbox row, commits, and only then acks the broker message. On duplicate delivery, the insert conflicts, the transaction rolls back or short-circuits, and the consumer acks without mutating domain tables.

Pros and cons

Pros

  • Mechanical idempotency — separates deduplication from domain rules; any handler can be made safe.
  • Transactional safety — inbox insert and business write commit or abort together; concurrent consumers rely on the DB constraint, not app-level locks.
  • Broker-agnostic — works with any at-least-once transport and with outbox relay duplicates.
  • Composable pipeline — producer outbox + consumer inbox is a well-documented microservices pairing.

Cons

  • Requires a transactional database at the consumer — not a fit for pure stateless workers with no local state store.
  • Extra write per message — inbox insert adds latency and storage cost on the hot path.
  • Retention discipline — pruning too aggressively re-opens duplicate processing; retaining forever bloats indexes.
  • Depends on stable message ids — producer must embed or broker must expose durable identifiers.

Implementation notes

Table design: Richardson’s PROCESSED_MESSAGES table uses a composite primary key such as (subscriber_id, message_id). A minimal inbox: message_id (PK or part of composite PK), processed_at, optional consumer_name when multiple handlers share one database.

Choosing message ids: Prefer immutable application-level event ids (e.g. outbox row id, CloudEvents id) over transport-specific tokens that change on redelivery. SQS MessageId is stable for the life of that message copy; Kafka consumers often use topic-partition-offset or the business event id in the payload. Do not use RabbitMQ delivery tags as inbox keys.

Transaction ordering: Insert inbox row first; on success run domain logic in the same transaction; commit; then ack the broker. On unique violation, roll back side effects and ack—the message is already applied. Never ack before commit.

Pruning and retention: Retain inbox rows at least as long as the broker may redeliver (SQS up to 14 days; Kafka per topic retention). Partition by month on processed_at for cheap drops. Document the retention policy relative to compliance needs—some audits require longer dedupe history than the broker’s retention.

Competing consumers: Two instances racing on the same redelivery resolve via the unique constraint—one wins, one treats as duplicate. Load-test this path; some ORMs hide constraint violations poorly.

With transactional outbox producers: Propagate the outbox event id in the message envelope so consumers dedupe on the same id the relay may resend. See Richardson’s transactional outbox for producer-side guarantees and Debezium’s Outbox Event Router when events arrive via CDC.

Common failure modes

  • Ack-before-commit — broker drops the message while the DB transaction fails; work is lost. Ack only after commit.
  • Side effect outside the transaction — calling an external API before commit cannot be rolled back on duplicate detection; move external calls after commit or use outbox on the consumer too.
  • Unstable or reused message ids — duplicates slip through or legitimate distinct events collide. Mint ids at publish time and document the scheme.
  • Pruning shorter than broker retention — an old redelivery looks “new” and double-charges or double-ships. Align TTL with max redelivery horizon.
  • Missing composite key — two different consumer types in one database conflict on the same id space; scope keys by consumer or subscriber id.
  • Treating inbox as audit log — using the inbox for analytics without retention planning causes unbounded growth unrelated to dedupe needs.

Decision checklist

  • Are inbox insert and business mutation in one database transaction?
  • Is broker acknowledgment strictly after successful commit?
  • Is the dedupe key stable across redeliveries and documented for producers?
  • Does retention cover the broker’s maximum redelivery window?
  • Is there automated pruning or partition rotation for the inbox table?
  • Have concurrent consumer races been tested against the unique constraint?
  • If producers use transactional outbox, does the event id flow into the consumer inbox key?

Example use cases

  • Illustrative scenario — RideRelay billing consumer charges a card on trip.completed; inbox keyed on event id prevents a second charge when SQS redelivers after a timeout.
  • Illustrative scenario — Meridian Commerce notification worker sends welcome email on user.registered; duplicate outbox relay publishes only trigger one inbox row and one email.
  • Illustrative scenario — Northwind Logistics warehouse service decrements stock on order.confirmed; three competing consumers share one inbox table so relay duplicates and consumer races both resolve safely.
