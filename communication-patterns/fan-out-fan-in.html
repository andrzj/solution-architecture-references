Fan-Out / Fan-In

The scatter-gather pattern for parallel work distribution and result aggregation — fan out to N workers simultaneously, then fan in to combine results within a budget, handling partial results and timeouts.

⏱ 11 min read

What it is

Fan-out / fan-in (EIP Scatter-Gather, also called broadcast–aggregate) is a pattern where a coordinator dispatches the same logical request to multiple independent workers in parallel, then merges their responses—fully or partially—before returning a single outcome to the caller. EIP describes the fan-out as a broadcast and the fan-in as an aggregator that collects correlated replies.

Synchronous implementations issue parallel HTTP or gRPC calls (or language-level tasks) and block until a deadline. Asynchronous implementations publish work to queues or topics—often with correlation identifiers on each branch—and collect replies on a dedicated reply channel, which suits long-running or decoupled workflows on Kafka, RabbitMQ, or NATS.

End-to-end latency approaches the slowest branch (plus aggregation overhead) instead of the sum of serial calls, which is why BFF layers, quote engines, and search federators rely on the pattern.

Why it exists

Real operations often need independent inputs from several systems: carrier pricing, fraud scores, inventory checks, or regional search indexes. Serial calls compound latency and let one straggler block the entire user journey. Fan-out/fan-in runs those dependencies concurrently and gives the aggregator explicit control over deadlines, partial results, and failure semantics.

The same structure appears at different scales—from in-process parallel maps to AWS Step Functions Parallel states, Kubernetes indexed Jobs, and map–reduce stages—whenever work can be partitioned and results reduced.

When to use

  • Multi-provider quotes: You must request prices, risk scores, or availability from several vendors under one user-facing deadline.
  • Parallel enrichment: A composite API gathers geolocation, credit, fraud, and preference data from separate services before responding.
  • Page or API aggregation: A BFF or gateway loads product, stock, pricing, and recommendations concurrently for one screen or payload.
  • Embarrassingly parallel batch work: You shard a dataset, process shards independently, and merge statistics or indexes in a reduce step.

When not to use

  • Strict pipelines: When step B needs A’s output, fan-out adds complexity without latency benefit; use a sequential workflow instead.
  • Unbounded parallelism: Fanning out to hundreds of simultaneous tasks can exhaust connections or memory; use a bounded pool with a work queue.
  • All-or-nothing outcomes: When every branch must succeed (for example multi-party settlement), partial-result policies and compensating actions must be designed explicitly.

Typical architecture

A coordinator issues N parallel invocations, each tagged with a shared correlation identifier. Results arrive on callbacks, futures, or reply messages. An aggregator accumulates them until all required branches finish or a global deadline expires, then merges, sorts, or filters into one response.

Pros and cons

Pros

  • User-visible latency tracks the slowest branch rather than the sum of serial call times.
  • Partial-result policies let slow or failed workers degrade gracefully when the business allows it.
  • New data sources join as additional parallel branches without rewriting the entire caller.
  • Each worker remains independently deployable, scalable, and owned by a separate team.

Cons

  • Aggregators must manage deadlines, correlation state, partial merges, and error taxonomy.
  • Peak resource use multiplies with branch count—connections, memory, and thread pools all spike together.
  • Stragglers consume the full deadline budget, so tail latency still dominates perceived speed.
  • Missing or wrong correlation identifiers mis-attribute replies and corrupt merged responses.

Implementation notes

Define one global deadline for the scatter-gather operation and propagate it on each branch (gRPC deadlines, HTTP Context, or workflow timer). Treat branches that miss the deadline as timed out according to your partial-result policy rather than giving each call its own unrelated timeout.

Document minimum viable responses: quote comparison may need any two carriers; four-engine fraud checks may require all four passes. Encode quorum rules in configuration, not magic constants.

For async fan-out, publish branch tasks with a shared correlation ID and collect replies on a dedicated topic or inbox (RabbitMQ reply-to, Kafka reply topic, NATS request–reply). CloudEvents subject and extension attributes can carry correlation metadata for interoperable envelopes.

In AWS Step Functions, Parallel state runs fixed branches; Map state fan-outs over an array when N is data-driven. For large N, stage work through a queue and aggregate incrementally instead of spawning unbounded inline branches.

Common failure modes

  • Aggregator memory leak: Missing deadline enforcement leaves correlation state allocated when a branch never replies.
  • Unbounded fan-out: The coordinator spawns one task per list element without a cap, exhausting threads or sockets.
  • Silent partial failure: A required branch errors but the aggregator still returns success without critical fields.
  • Reply mismatch: Workers omit correlation identifiers, so results attach to the wrong parent operation.

Decision checklist

  • Are all branches independent with no hidden data dependencies between them?
  • Is there a single operation-level deadline propagated to every branch?
  • Is the partial-result or quorum policy written down and tested?
  • Is fan-out bounded when N is driven by user-supplied lists or catalog size?
  • Does every branch response carry the same correlation identifier as the parent request?
  • Is aggregator state evicted via TTL, completion callback, or explicit delete after timeout?

Example use cases

  • Illustrative scenario — RideRelay fans a pricing BFF out to multiple carrier APIs under a deadline, fans in the lowest fares, and marks slow or failed branches unavailable.
  • Illustrative scenario — Meridian Commerce loads catalogue, inventory, price, and recommendations in parallel on a product detail BFF and merges partial failures before returning the page.
  • Illustrative scenario — Northwind Logistics fans an upload intake out to virus scan, thumbnail, metadata, and CDN promotion workers and marks a shipment complete only when required branches succeed.

Related patterns

  • Competing Consumers — many identical workers share one queue; scatter-gather targets distinct branches.
  • Request-Response — synchronous invocation primitive for each fan-out leg.
  • Correlation IDs — tie branch replies back to the originating request.
