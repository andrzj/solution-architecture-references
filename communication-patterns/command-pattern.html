Command Pattern

Intent-driven imperative messages that instruct a service to perform an action — distinct from events, routed to a single handler, validated before dispatch, and central to the CQRS write side.

⏱ 11 min read

What it is

Command messaging packages an imperative request—“perform this action with this data”—as a typed message routed to exactly one logical handler. In Gregor Hohpe and Bobby Woolf’s catalog, a Command Message contrasts with an event notification: events describe facts that already happened; commands express desired mutations that may be accepted or rejected.

Commands are point-to-point: one command type maps to one owning service or aggregate handler. That ownership boundary is how microservices keep write consistency without multiple writers applying the same instruction. On the CQRS write path (see CQRS and saga orchestration on microservices.io), APIs and sagas emit commands; handlers enforce invariants and emit domain events when state changes commit.

Whether the command travels in-process on a mediator bus or asynchronously through RabbitMQ, Amazon SQS, or Kafka keyed topics, the envelope carries identity metadata (command id, correlation id, issuer, timestamp) so operators can trace, deduplicate, and audit write intent separately from resulting events.

Why it exists

Generic REST bodies hide intent: the same POST shape might create, amend, or cancel depending on undocumented conventions. Named command types make write operations explicit in logs, metrics, and message traces, and they give you a single place to enforce authorization, validation, and idempotency before domain logic runs.

Async command dispatch also decouples client-facing latency from handler duration: the edge acknowledges receipt (or enqueues) while workers process at sustainable throughput, which is how order, payment, and fulfilment boundaries survive traffic spikes without holding HTTP connections open across slow downstream checks.

When to use

  • State changes belong to one aggregate or service boundary and you need a clear single handler responsible for acceptance or rejection.
  • The write path uses CQRS, event sourcing, or DDD aggregates where commands are the only supported mutation entry point.
  • Orchestrated sagas or process managers issue instructions to remote participants and need structured failure reasons rather than opaque HTTP errors.
  • You must audit who requested each change, independent of the events that later appear on the bus.
  • Clients can enqueue work and poll or subscribe for outcomes when synchronous confirmation is unnecessary or impossible.

When not to use

  • The operation is a read-only query; use the read model, a cache, or a dedicated query API instead of overloading command infrastructure.
  • Multiple independent services must react to the same fact; publish an event and let each subscriber decide, rather than fanning one command to many handlers.
  • The domain is trivial CRUD with no invariant rules and no audit requirements—the command envelope may be ceremony without payoff.
  • You need broadcast discovery semantics; commands are the wrong message shape for pub/sub fan-out.

Typical architecture

An API edge or saga step validates wire format, builds a command envelope, and dispatches through a command bus or dedicated queue keyed by aggregate id where ordering matters. The handler loads the aggregate, checks authorization, runs business rules, persists, and either rejects with a typed reason or commits and publishes resulting events via outbox or broker. Reply paths (synchronous HTTP response, callback topic, or polling status resource) communicate acceptance or rejection back to the initiator when required.

Pros and cons

Pros

  • Write intent is explicit in type names, metrics, and traces instead of being buried in anonymous JSON bodies.
  • Single-handler ownership aligns with bounded contexts and prevents competing writers on the same aggregate.
  • Command logs support compliance, dispute resolution, and replay analysis separate from emitted events.
  • The same shape works synchronously at the API and asynchronously on a broker without changing domain rules.
  • Structured business rejection distinguishes expected “no” answers from infrastructure faults that should retry.

Cons

  • Commands, handlers, buses, and registration add boilerplate when the domain is simple CRUD.
  • Asynchronous commands need a deliberate reply strategy when callers must learn rejection reasons.
  • Teams new to messaging confuse commands with events and may broadcast commands or emit commands instead of events.
  • Framework conventions differ across MediatR, Axon, NServiceBus, and custom buses, complicating polyglot estates.

Implementation notes

Envelope: Include commandId, correlationId, issuedAt, issuedBy, and a stable commandType string. Handlers deduplicate on commandId so broker redelivery does not repeat side effects.

Two-stage validation: Reject malformed messages before they hit the queue. Evaluate business rules inside the handler against current aggregate state; return typed rejection codes instead of throwing for expected violations.

Failure taxonomy: Map technical failures (timeout, serialization error) to retry and dead-letter policies; map business rejections to non-retry responses so poison loops do not form.

Routing: Use typed destinations—dedicated queues, routing keys, or Kafka topics per command—and consult message routing patterns when a gateway fans in many command types.

Outcomes: Successful handlers persist and publish events through the transactional outbox so commands and downstream notifications stay consistent.

Common failure modes

  • Multiple handlers for one command type: Split brain writes and partial updates when more than one consumer executes the same instruction.
  • Missing idempotency key: Retries duplicate financial or inventory effects because the handler cannot recognize a replayed commandId.
  • Business rejection on the retry path: Expected rule violations thrown as exceptions cause brokers to retry forever.
  • Stale commands: Long queue delays let superseded instructions apply to aggregates that already moved on; handlers must validate version or sequence.

Decision checklist

  • Is there exactly one registered handler per command type in each environment?
  • Does every command carry commandId and correlationId for idempotency and tracing?
  • Is wire-level validation separated from aggregate business rules?
  • Do handlers return structured rejections without triggering infinite broker retry?
  • For async flows, can the initiator learn the outcome (callback, reply queue, or status API)?
  • Are resulting domain events published reliably after successful commits?

Example use cases

  • Illustrative scenario — A checkout API maps POST /orders to a PlaceOrder command; the order aggregate rejects when credit check fails and emits OrderPlaced only after a successful commit.
  • Illustrative scenario — A ledger service accepts TransferFunds commands on a FIFO queue keyed by account id so mutations for one account stay ordered while different accounts parallelize.
  • Illustrative scenario — A trip-booking saga issues ReserveSeat and CapturePayment commands to remote services and issues compensating commands when a downstream step rejects.
  • Case study — Chris Richardson’s saga pattern material on microservices.io centers on command/event exchanges between participants in long-running transactions.

Related patterns

  • Event Notification — handlers emit facts after commands succeed.
  • CQRS — commands feed the write model; queries use separate read paths.
  • Saga Pattern — coordinates multi-service commands and compensations.
  • Message Routing — delivers commands to the correct queue or handler.
  • Message Queues — async transport for command messages.
