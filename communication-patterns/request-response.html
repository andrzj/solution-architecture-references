Request-Response

Synchronous request-response: the caller waits for a direct reply over HTTP or gRPC, with timeouts, pooling, safe retries, and circuit breaking as first-class design concerns.

⏱ 10 min read

What it is

Request-response is a synchronous communication pattern in which a caller sends a message and blocks until the callee returns a reply or the call fails with a timeout or error. The pattern appears everywhere HTTP exposes request/response semantics, in gRPC unary RPCs on HTTP/2, and in analogous RPC layers over WebSockets or TCP.

Its defining property is temporal coupling: both peers must be available and reachable for the duration of the exchange. That coupling is a trade-off — simplicity and immediate feedback on one side, fragility under partial outages and long chains on the other. Enterprise Integration Patterns describes the same idea as a pair of Request-Reply channels (request channel plus reply channel); microservices.io treats synchronous RPC as the default integration style when you need an answer before proceeding.

HTTP/1.1 typically reuses connections via keep-alive; HTTP/2 multiplexes many streams on one connection. gRPC adds typed contracts (Protocol Buffers), binary framing, and optional streaming modes while keeping unary RPC as the common request-response shape.

Despite async messaging adoption, synchronous request-response remains the default for user-visible reads and quick queries: the programming model is a question followed by an immediate answer, which maps cleanly to await, futures, and familiar HTTP client libraries.

Why it exists

Many operations are inherently interrogative: current price, permission to proceed, or whether a record exists. Async alternatives force the caller to manage correlation identifiers, out-of-band delivery, and completion detection, which buys little when the downstream answer is fast and the caller cannot continue without it.

Request-response maps cleanly to language primitives (await, futures, blocking I/O), which keeps application code readable. On the web it also aligns with cacheable HTTP semantics, so CDNs and reverse proxies can serve read responses without hitting the origin when policy allows.

Async alternatives add correlation IDs, completion channels, and timeout watches that pay off when work is slow or fan-out is wide; for sub-100 ms lookups where the caller cannot proceed without the payload, sync calls usually win on simplicity.

When to use

  • User-facing reads where a browser or mobile client must render before the interaction can continue.
  • Simple queries whose downstream latency fits inside the caller’s end-to-end budget (profile lookup, SKU resolution, inventory check).
  • Authentication and authorisation gates that must return allow/deny before request handling proceeds.
  • Validation that must complete before committing state (address verification, eligibility checks).
  • Operational and admin APIs where an operator expects an immediate success or error (health checks, configuration reads, one-shot triggers).
  • Early-stage systems where the operational cost of brokers and async pipelines outweighs their benefits.

When not to use

  • Workflows that run longer than client or gateway timeouts permit; prefer async jobs with polling or callbacks.
  • Composite pages or APIs that would serialize many downstream calls; parallel fan-out or materialized read models reduce tail latency.
  • Fire-and-forget side effects where the caller does not need the outcome.
  • High-volume write ingestion where a durable queue absorbs burst traffic better than a thread per in-flight HTTP request.
  • Critical paths that span regions or data centers, because round-trip latency accumulates on every synchronous hop.

Typical architecture

A client (browser, mobile app, or upstream microservice) terminates TLS at an API gateway or service mesh ingress, then invokes an edge or BFF service over HTTP/2 or gRPC. Connection pooling amortizes handshake cost across requests; the edge service may call additional services synchronously, forming a dependency chain.

Each hop should consume only part of the end-to-end deadline, and outbound calls should be wrapped with circuit breakers so a failing dependency fails fast instead of tying up worker threads.

Pros and cons

Pros

  • Caller code reads like a local function call, which keeps control flow easy to reason about.
  • Errors and validation failures return immediately to the caller without extra correlation plumbing.
  • HTTP caching headers can serve read-heavy traffic from intermediates when responses are cacheable.
  • Load balancers, API gateways, service meshes, and APM tools have first-class support for HTTP and gRPC.
  • W3C Trace Context headers propagate naturally in request metadata for end-to-end tracing.

Cons

  • Caller and callee must be healthy at the same moment, which increases blast radius during outages.
  • A slow or stalled downstream blocks the caller’s worker until timeout, which can trigger cascading overload.
  • Deep synchronous chains multiply tail latency because each hop consumes part of the same deadline.
  • High concurrency ties up threads or connections for the full duration of each in-flight call.
  • Aggressive client retries can amplify load on a dependency that is already failing.

Implementation notes

Set separate connect and request/read timeouts on every outbound client, sized from the caller’s latency budget rather than library defaults. In gRPC, propagate absolute deadlines through context so child calls inherit the remaining time instead of starting a fresh timeout per hop (gRPC deadlines guide).

Pool HTTP connections per upstream host; HTTP/2 multiplexing reduces connection count but pools still matter for TLS and failover. Size pools from expected concurrency and typical call duration (Little’s Law: in-flight ≈ arrival rate × latency).

Retry only idempotent operations or those protected by server-side deduplication. HTTP GET/HEAD are safe to retry on transport errors; PUT and DELETE are idempotent by definition; POST usually requires an Idempotency-Key or equivalent token so duplicate submits collapse to one effect. Use exponential backoff with jitter on transient failures (timeouts, connection resets, 503, 429) as described in the AWS Builders’ Library.

Wrap fragile dependencies with circuit breakers that open after sustained failure and probe in half-open state before fully closing again. Document AsyncAPI or OpenAPI contracts for public edges so clients know which status codes are retryable.

Size connect timeouts aggressively (often 100–200 ms) so unreachable hosts fail fast, then bound the full call with a read or request timeout derived from the caller’s SLO. For chained calls, subtract each hop’s budget from the parent deadline rather than giving every leg an unrelated fixed limit.

When failure rates cross a rolling threshold (for example more than half of calls failing within a short window), open the circuit so callers fail immediately instead of saturating thread pools; after a sleep interval, allow trial traffic in half-open state before closing the circuit again.

Common failure modes

  • Timeout creep upstream masks a slow dependency until connection pools or thread pools exhaust.
  • Synchronized client retries after a shared outage create a thundering herd against a recovering service.
  • Per-hop fixed timeouts ignore the parent deadline, so deep chains accept work they cannot finish in time.
  • Undersized connection pools queue healthy requests behind slow ones and inflate perceived latency.
  • Retries on non-idempotent POSTs without deduplication keys cause duplicate side effects (for example double charges).
  • Circuit breaker thresholds tuned to deployment noise trip open during normal rollouts and amplify perceived outages.

Decision checklist

  • Does the caller truly need the reply before continuing, or would async handoff suffice?
  • Does measured downstream latency fit inside the caller’s end-to-end budget?
  • Are connect and read/request timeouts configured on every outbound client?
  • Are retries limited to safe/idempotent operations or backed by idempotency keys?
  • Is each fragile dependency protected by a circuit breaker or equivalent bulkhead?
  • Is the connection pool sized for peak concurrent in-flight calls?
  • Are traceparent (and optional tracestate) headers forwarded on internal calls?

Example use cases

  • Illustrative scenario — A storefront BFF loads product detail and stock level with two parallel gRPC calls, then returns one JSON payload to the browser in a single synchronous page request.
  • Illustrative scenario — An API gateway validates access tokens via a synchronous introspection call and caches allow/deny decisions per token to avoid repeating the round trip on every request.
  • Illustrative scenario — A latency-sensitive pricing screen issues unary gRPC calls over a warm HTTP/2 connection pool so each quote refresh stays inside a strict single-digit millisecond budget.
  • Case study — Stripe documents idempotency keys for payment APIs so clients can retry POSTs safely after transport failures without double-settling charges.

Related patterns

  • Publish/Subscribe decouples producers and consumers when immediacy is not required.
  • Fan-Out / Fan-In parallelizes multiple synchronous dependencies within one latency budget.
  • Correlation IDs tie log and trace lines together across a call chain.
  • Reliability patterns include circuit breaking and bulkheads tailored to synchronous call graphs.
