Event Streaming

Event streaming treats business activity as a durable, partitioned, replayable log—so many consumers read, resume, and reprocess the same events independently.

⏱ 14 min read

What it is

Event streaming treats business activity as an immutable, ordered log that any consumer can read at any offset, at any time, while data remains within the retention window. Producers append records to partitions within a topic; partitions spread across brokers for parallelism and replicate for fault tolerance. A consumer group is a logical subscriber—each partition is assigned to exactly one group member at a time, giving both fan-out (multiple groups read the same topic independently) and parallelism (partitions inside a group process concurrently). Every consumer tracks a monotonic offset per partition so it can resume after restarts, catch up from lag, or deliberately replay from an earlier point.

Unlike classic queues that delete messages after acknowledgment, streams retain data for hours, days, or indefinitely under log compaction. That makes the log both a message bus and a short- to medium-term event store—supporting replay, new consumer bootstrap, and audit without a separate archival pipeline for every downstream team.

Apache Kafka is the reference implementation, but the model generalizes to Redpanda, Amazon MSK, Confluent Cloud, and Pulsar-style segmented logs. The distinguishing idea is durable ordered logs as the integration backbone—not transient handoff buffers.

Why it exists

Task queues optimize for “process once and forget,” which is ideal for background jobs but weak when new services must bootstrap from history, analytics needs the same facts as operations, or compliance requires a tamper-evident trail. A retained log lets every downstream system catch up and re-read without rewiring producers.

Kafka emerged at LinkedIn to unify activity tracking, operational metrics, and pipeline ingestion on one durable bus; microservices.io and event-driven architectures now treat the stream as the integration contract rather than a transient handoff buffer.

When to use

  • Event sourcing or CQRS where derived read models are rebuilt by replaying the log from offset zero or a known checkpoint.
  • Multiple independent consumers—search indexing, cache warming, analytics, ML feature pipelines—over the same fact stream without custom fan-out plumbing.
  • Audit and compliance paths that require retained, ordered, tamper-evident evidence of financial or user activity events.
  • Real-time stream processing—rolling aggregates, anomaly detection, stream-table joins—via Kafka Streams, Flink, Spark Structured Streaming, or managed equivalents.
  • Geo-replication when disaster recovery or regional processing needs a copy of the log (MirrorMaker 2, cluster linking, or vendor replication).

When not to use

  • Simple task queues where messages should disappear after one worker succeeds—SQS or RabbitMQ carry less operational overhead than a three-broker Kafka footprint.
  • Very small scale without replay needs: minimum production replication and offset management may be disproportionate for low-volume cron-style work.
  • Request-response semantics—streaming is strictly one-way pub/sub; RPC-over-Kafka is an anti-pattern unless you accept complexity and latency trade-offs.
  • Exactly-once business guarantees without investing in idempotent producers, transactional APIs, and consumer isolation—default paths are at-least-once and duplicates are possible on retry.
  • Ad hoc random access at warehouse scale—the log is not a queryable OLAP engine; projections or lakehouse loads still sit downstream.

Typical architecture

Producers append to topic partitions, usually choosing partition via message key hash so related events co-locate for per-key ordering. Each partition replicates to N brokers (replication factor 3 is common); leaders serve writes while followers catch up. Consumer groups commit offsets to the internal __consumer_offsets topic (or an external store in exotic setups), so each group maintains an independent cursor per partition.

Stream processors consume input topics, maintain state (RocksDB in Kafka Streams, keyed state in Flink), and emit derived topics—implementing the stream-table duality Confluent describes: changelog topics back materialized views that processors query as tables while the bus remains the source of ordered events.

Pros and cons

Pros

  • Consumers can reset offsets to replay history for new services, fixes, or regulatory requests.
  • Sequential disk writes and batching yield high throughput on commodity hardware when tuned properly.
  • Separate consumer groups read the same topic without custom fan-out wiring.
  • Retention policies keep the log as both transport and short- to medium-term archive.
  • Log compaction retains the latest record per key on changelog topics, bounding storage for entity state.

Cons

  • Cluster operations—broker upgrades, partition movement, ACLs, and quota tuning—need platform skills.
  • Partition counts are painful to shrink; expanding partitions rebalances keys and can disturb ordering assumptions.
  • Consumer group rebalance pauses processing when members churn unless cooperative protocols and static membership are used.
  • End-to-end exactly-once needs idempotent producers, transactions, and careful consumer configuration.
  • Kafka is optimized for append and sequential read, not ad hoc random queries at warehouse scale.

Implementation notes

Partition count: Choose initial partition count generously—you cannot shrink partitions later, and increasing them triggers reassignment and may disturb per-key ordering assumptions. Target roughly one partition per consumer instance at peak load with headroom; common starting points are 12, 24, or 48 for domain topics. See Kafka concepts for how keys map to partitions.

Log compaction: Enable cleanup.policy=compact on changelog topics keyed by entity ID. Compaction retains the latest record per key in the background, bounding disk for entity state while tombstone records (null values) delete keys. Mix compact+delete policies when you need both state snapshots and time-bounded raw history.

Exactly-once semantics: Producers need enable.idempotence=true to deduplicate retries; multi-topic atomic writes need transactional APIs (initTransactions, beginTransaction, commitTransaction). Consumers that must not read uncommitted transactional data set isolation.level=read_committed. Test failure injection—misconfiguration often silently falls back to at-least-once (delivery semantics).

Kafka Streams versus Flink: Kafka Streams embeds topologies in JVM services—no separate cluster, ideal for enrichment, filtering, and modest aggregations. Flink adds a dedicated cluster, event-time watermarks, large stateful joins across many streams, and operational tooling for massive state—at the cost of another platform to run.

Consumer lag: Track consumer_lag (end offset minus committed offset) per partition per group. Alert when lag growth exceeds thresholds relative to produce rate and retention—lag crossing retention means permanent data loss for that group. Use Burrow, Cruise Control, or vendor control planes; correlate lag spikes with deploys and rebalance events.

Schema governance: Deploy a schema registry with BACKWARD (or stricter) compatibility so producers cannot ship breaking layouts that crash deserializers on older consumers.

Common failure modes

  • Rebalance storms: Rapid membership changes during rolling deploys stall all consumers—mitigate with static membership (group.instance.id) and cooperative incremental rebalancing protocols.
  • Under-replicated partitions: Followers lagging leaders risk data loss if the leader fails before catch-up—monitor UnderReplicatedPartitions and alert on any sustained count above zero.
  • Retention expiry before catch-up: Consumers that fall behind retention permanently lose unread segments—extend retention or add compact+delete policies on critical topics and page on lag versus retention overlap.
  • Schema evolution breaks consumers: Required fields added without compatible schemas crash deserializers—enforce registry rules and contract tests in CI.
  • Hot partitions: Low-cardinality keys (for example a constant "global" key) funnel all traffic through one partition and cap throughput—choose keys with enough cardinality for load spread while preserving needed ordering.

Decision checklist

  • Do any consumers need to read from arbitrary historical positions?
  • Will multiple independent groups consume the same topic?
  • Does the message key balance shards while preserving per-entity ordering?
  • Are schemas governed with compatibility rules and contract tests?
  • Is lag monitored per group and partition with retention-aware alerts?
  • Are replication factor and min.insync.replicas set for the durability tier you promise?
  • If exactly-once is required, are producer and consumer EOS settings tested under failure injection?

Example use cases

  • Illustrative scenario — Domain services append order lifecycle events to a shared topic while read models rebuild projections by replaying from the earliest retained offset after a bug fix.
  • Illustrative scenario — A fraud team runs a Kafka Streams or Flink topology joining live transaction events with account risk tables, emitting alerts within tens of milliseconds of suspicious patterns.
  • Case study — LinkedIn and Uber have publicly described Kafka-backed pipelines for activity feeds, metrics, and stream processing at organizational scale.
  • Case study — Debezium change-data-capture connectors write database mutations to Kafka; Flink or Spark jobs transform and load them into warehouses for sub-minute analytics freshness.

Related patterns

  • Competing Consumers explains parallelism inside one consumer group across partitions.
  • Event Sourcing uses the stream as the system of record.
