Event Streaming

Event streaming treats business activity as a durable, partitioned, replayable log—so many consumers read, resume, and reprocess the same events independently.

⏱ 14 min read

What it is

Event streaming is a communication and persistence pattern where producers append records to an ordered, partitioned log and consumers read forward at their own pace, retaining a cursor (offset) per partition. Unlike classic queues that delete messages after acknowledgment, streams retain data for a policy-defined period or under log compaction, which enables replay, audit, and late-arriving consumers.

Apache Kafka is the reference implementation: topics split into partitions spread across brokers; consumer groups assign each partition to one member for parallelism while separate groups each receive the full stream. The model generalizes to managed offerings and other log brokers, but the core idea—durable ordered logs as the integration backbone—is what distinguishes streaming from point-to-point queuing.

Why it exists

Task queues optimize for “process once and forget,” which is ideal for background jobs but weak when new services must bootstrap from history, analytics needs the same facts as operations, or compliance requires a tamper-evident trail. A retained log lets every downstream system catch up and re-read without rewiring producers.

Kafka emerged at LinkedIn to unify activity tracking, operational metrics, and pipeline ingestion on one durable bus; microservices.io and event-driven architectures now treat the stream as the integration contract rather than a transient handoff buffer.

When to use

  • Event sourcing or CQRS where derived read models are rebuilt by replaying the log.
  • Multiple independent consumers (search, cache warming, analytics, ML features) over the same fact stream.
  • Audit and compliance paths that require retained, ordered evidence of what happened.
  • Continuous processing—aggregations, joins, windows—via Kafka Streams, Flink, or similar engines.
  • Geo-replication of topics when disaster recovery or regional processing needs a copy of the log.

When not to use

  • Simple job queues where messages should disappear after one worker succeeds; SQS or RabbitMQ are lighter operationally.
  • Very low volume without replay needs, where a multi-broker cluster is disproportionate cost.
  • Request-response interactions; streaming is one-way unless you layer request-reply patterns on top.
  • Exactly-once end-to-end processing without investing in idempotent producers, transactions, and consumer design—defaults are at-least-once.

Typical architecture

Producers append to topic partitions, usually choosing partition via message key hash so related events co-locate for ordering. Brokers replicate partitions for fault tolerance; consumer groups commit offsets to track progress independently per group.

Stream processors consume input topics, maintain state (RocksDB in Kafka Streams, keyed state in Flink), and emit derived topics—implementing the stream-table duality described in Kafka’s documentation (changelog topics back materialized views).

Pros and cons

Pros

  • Consumers can reset offsets to replay history for new services, fixes, or regulatory requests.
  • Sequential disk writes and batching yield high throughput on commodity hardware when tuned properly.
  • Separate consumer groups read the same topic without custom fan-out wiring.
  • Retention policies keep the log as both transport and short- to medium-term archive.
  • Log compaction retains the latest record per key on changelog topics, bounding storage for entity state.

Cons

  • Cluster operations—broker upgrades, partition movement, ACLs, and quota tuning—need platform skills.
  • Partition counts are painful to shrink; expanding partitions rebalances keys and can disturb ordering assumptions.
  • Consumer group rebalance pauses processing when members churn unless cooperative protocols and static membership are used.
  • End-to-end exactly-once needs idempotent producers, transactions, and careful consumer configuration.
  • Kafka is optimized for append and sequential read, not ad hoc random queries at warehouse scale.

Implementation notes

Plan partition count up front for peak consumer parallelism; increasing partitions later requires reassignment and may change per-key ordering guarantees (Kafka concepts).

Use cleanup.policy=compact on changelog topics that mirror table state; tombstone records (null value) remove keys during compaction (log compaction).

For stronger delivery guarantees, enable idempotent producers and transactional writes where needed; consumers that must skip open transactions set isolation.level=read_committed (delivery semantics).

Pick Kafka Streams for library-embedded topology on existing JVM services; choose Flink when you need a dedicated cluster, event-time watermarks, and large stateful joins across many streams.

Monitor consumer lag (end offset minus committed offset) per partition and alert before retention would delete unread data.

Common failure modes

  • Rapid membership changes trigger rebalance storms that stall all consumers in the group.
  • Under-replicated partitions during broker failure increase risk of lost data if leaders fail before catching up.
  • Consumers fall behind retention and permanently lose messages they never read.
  • Breaking schema changes crash consumers that still deserialize older layouts.
  • Low-cardinality message keys create hot partitions that limit end-to-end throughput.

Decision checklist

  • Do any consumers need to read from arbitrary historical positions?
  • Will multiple independent groups consume the same topic?
  • Does the message key balance shards while preserving per-entity ordering?
  • Are schemas governed with compatibility rules and contract tests?
  • Is lag monitored per group and partition with retention-aware alerts?
  • Are replication factor and min.insync.replicas set for the durability tier you promise?
  • If exactly-once is required, are producer and consumer EOS settings tested under failure injection?

Example use cases

  • Illustrative scenario — Domain services append order lifecycle events to a shared topic while read models rebuild projections by replaying from the earliest retained offset.
  • Case study — Uber and LinkedIn publicly describe Kafka-backed pipelines for log aggregation, metrics, and stream processing at organizational scale.
  • Case study — Debezium documents change-data-capture connectors that write database changes to Kafka for downstream Flink or warehouse loaders.

Related patterns

  • Publish/Subscribe covers lighter broadcast semantics without long retention.
  • Transactional Outbox reliably publishes to Kafka after database commits.
  • Competing Consumers explains parallelism inside one consumer group across partitions.
  • Event Sourcing uses the stream as the system of record.
