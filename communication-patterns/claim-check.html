Claim Check Pattern

Store large message payloads in external storage (S3, Azure Blob, GCS) and pass only a lightweight reference token through the message broker — eliminating payload size limits and reducing broker memory and bandwidth costs.

⏱ 9 min read

What it is

The Claim Check pattern (EIP Store in Library, also called reference-based messaging) stores bulky message bodies in external object storage and sends only a lightweight claim check—URL, object key, or pre-signed token—through the broker. Consumers redeem the check with a GET against S3, Azure Blob, GCS, or similar, then process bytes locally while the broker carries kilobyte-scale routing metadata.

The luggage analogy still fits: drop the bag at the counter (blob store), carry the ticket through the trip (queue or topic), and collect the bag at the destination (consumer fetch). Kafka, RabbitMQ, SQS, and NATS all benefit when default message size limits or memory pressure would otherwise block large binaries.

Why it exists

Brokers enforce practical size ceilings—SQS 256 KB per message, Kafka often 1 MB by default, RabbitMQ tolerates larger frames but punishes multi-megabyte bodies with memory and replication cost. Embedding PDFs, imagery, or model artifacts inline fails outright or harms neighbors on shared clusters.

Object storage is cheap at scale and built for large sequential reads. Claim check keeps the messaging tier responsible for routing and backpressure while bulk bytes live where throughput and retention policies belong.

When to use

  • Oversized payloads: Bodies would exceed broker limits or noticeably inflate broker RAM and replication bandwidth.
  • Binary artifacts: Images, PDFs, media, and serialized model outputs are awkward to base64 inside JSON events.
  • Shared large objects: Pub/sub fan-out references one stored object from many small messages instead of duplicating bytes per subscriber.
  • Retention and audit: The object store becomes the durable archive; the message carries routing, correlation, and content-type metadata only.

When not to use

  • Tiny messages: Sub–10 KB payloads pay an extra round trip without meaningful broker savings.
  • Sub-millisecond paths: An additional object-store GET per message adds latency incompatible with tight realtime SLAs.
  • Unreliable object lifecycle: If TTL or deletion races are unmanaged, consumers fetch missing objects and fail repeatedly.

Typical architecture

The producer writes the payload to object storage, builds a compact message with storage reference, checksum, content type, and correlation identifiers, and publishes to the broker. The consumer retrieves the object, validates optional hashes, processes, acknowledges the broker message, then deletes or leaves the object per lifecycle policy.

Pros and cons

Pros

  • Brokers carry small control messages while payloads scale to object-store sizes.
  • Broker memory, replication, and network usage stay predictable under large artifacts.
  • One stored object can back many subscriber messages in fan-out topologies.
  • Object versioning and lifecycle rules provide durable audit and replay surfaces.

Cons

  • Every consumer pays an extra object-store GET before processing begins.
  • The pipeline now depends on storage availability, IAM, and lifecycle automation.
  • Orphaned or expired objects break redelivery unless TTL and delete rules align with ACK semantics.
  • Leaked pre-signed URLs or loose bucket policies expose data if references are intercepted.

Implementation notes

Choose between object keys plus IAM for in-account consumers and pre-signed URLs for cross-account or third-party fetchers. Pre-signed expiry must exceed worst-case queue lag plus processing time—often ten times p99 processing duration.

Include metadata in the broker message: content type, size, checksum, correlation ID, and optional CloudEvents attributes so observability does not require opening the blob. Kafka users may instead use the large-record path only when cluster policy allows; claim check remains the portable default across SQS, RabbitMQ, and NATS.

Configure lifecycle rules on prefixes or tags, and delete objects only after successful broker ACK (or rely on TTL with DLQ handling for expired references). Pair upload plus publish with the transactional outbox to avoid orphaned blobs when the producer crashes between PUT and publish.

Encrypt at rest (SSE-KMS or SSE-S3), deny public ACLs, and validate hashes after GET when tamper detection matters.

Common failure modes

  • Expired pre-signed URL: Slow consumers hit HTTP 403 when URL lifetime is shorter than end-to-end latency.
  • Premature delete: A consumer deletes the object before ACK, so redelivery cannot fetch the body again.
  • Storage outage: S3 or Blob errors fail processing unless fetch retries with backoff and DLQ escalation.
  • Orphan PUT: Payload lands in storage but no message publishes, leaving unreachable objects until garbage collection runs.

Decision checklist

  • Does payload size exceed broker limits or stress cluster memory (typically above ~64 KB)?
  • Is server-side encryption enabled on the payload bucket or container?
  • Are buckets private with least-privilege IAM or short-lived pre-signed access?
  • Do lifecycle rules cap retention and cost for unprocessed objects?
  • Does deletion happen only after successful message acknowledgment?
  • Are object keys or URLs logged with correlation IDs at publish, fetch, and delete?
  • If pre-signed URLs are used, does TTL cover queue backlog plus p99 processing time?

Example use cases

  • Northwind Logistics — customs documents: Multi-megabyte PDFs land in S3; SQS carries claim checks; OCR and search consumers fetch the same object key independently.
  • FieldOps — inspection media: Upload workers store photos in GCS, publish Kafka messages with references, and transcode services write new keys for derivatives.
  • Meridian Commerce — cross-account feeds: Account A stores partner catalog dumps, embeds pre-signed URLs in SNS notifications, and Account B workers fetch without permanent bucket credentials.

Related patterns

  • Message Queues — channels that carry claim-check tokens instead of raw bytes.
  • Competing Consumers — parallel workers that each redeem the same reference safely when processing is idempotent.
  • Transactional Outbox Pattern — atomic publish of claim-check messages with database commits.
