Claim Check Pattern

Store large message payloads in external storage (S3, Azure Blob, GCS) and pass only a lightweight reference token through the message broker — eliminating payload size limits and reducing broker memory and bandwidth costs.

⏱ 9 min read

What it is

The Claim Check pattern (EIP Store in Library, also called reference-based messaging) stores bulky message bodies in external object storage and sends only a lightweight claim check—URL, object key, or pre-signed token—through the broker. Consumers redeem the check with a GET against S3, Azure Blob, GCS, or similar, then process bytes locally while the broker carries kilobyte-scale routing metadata.

The luggage analogy still fits: drop the bag at the counter (blob store), carry the ticket through the trip (queue or topic), and collect the bag at the destination (consumer fetch). Kafka, RabbitMQ, SQS, and NATS all benefit when default message size limits or memory pressure would otherwise block large binaries. The pattern is EIP Store in Library—reference in flight, payload at rest.

Why it exists

Brokers enforce practical size ceilings—SQS caps bodies at 256 KB, Kafka often defaults to 1 MB per record, and RabbitMQ tolerates larger frames but punishes multi-megabyte bodies with memory pressure and slow replication on shared clusters. Scanned documents, imagery, audio, large JSON reports, and serialised model artifacts either fail publish outright or degrade every tenant on the cluster when inlined.

Object storage is cheap at scale and built for large sequential reads. Claim check keeps the messaging tier responsible for routing, ordering, and backpressure while bulk bytes live where throughput, encryption, and lifecycle policies belong—without forcing operators to raise broker heap or max-message-size knobs for a handful of fat payloads.

In event-carried pipelines, claim check also decouples fan-out cost from payload size: ten subscribers each pulling a 50 MB inline message multiply egress through the broker; one stored object and ten pointer messages keep replication and billing predictable. The trade-off is operational coupling to object-store availability and permission models—monitor GET error rates alongside queue depth because a full broker with empty objects is still a failed pipeline.

When to use

  • Oversized payloads: Bodies would exceed broker limits or stress cluster memory and replication bandwidth—typically anything consistently above ~64 KB on managed queues or low single-digit megabytes on self-hosted brokers.
  • Binary artifacts: Images, PDFs, media, and serialized model outputs are awkward to base64 inside JSON events and explode message size without delivering queryable structure in the broker.
  • Shared large objects: Pub/sub fan-out references one stored object from many small messages instead of duplicating bytes per subscriber—a single customs PDF can back OCR, search, and archival consumers independently.
  • Retention and audit: The object store becomes the durable archive; the message carries routing, correlation, content-type, and checksum metadata so compliance teams can list objects by prefix while operators replay routing decisions from broker logs.

When not to use

  • Tiny messages: Sub–10 KB payloads pay an extra round trip, another failure domain, and IAM wiring without meaningful broker savings.
  • Ultra-low-latency paths: An additional object-store GET per message adds tens of milliseconds—unacceptable when the pipeline targets sub-millisecond control loops or synchronous user responses.
  • Unreliable object lifecycle: If TTL, compaction, or deletion races are unmanaged, consumers fetch missing objects and fail repeatedly; the claim check is only as dependable as the backing store and your delete-after-ACK discipline.

Typical architecture

The producer writes the payload to object storage, builds a compact message with storage reference, checksum, content type, and correlation identifiers, and publishes to the broker. The consumer retrieves the object, validates optional hashes, processes, acknowledges the broker message, then deletes or leaves the object per lifecycle policy.

Pros and cons

Pros

  • Removes practical broker size limits—payloads can grow to object-store scale without retuning cluster max-message settings.
  • Broker memory, replication, and network usage stay predictable because only kilobyte-scale envelopes traverse the bus.
  • One stored object can back many subscriber messages in fan-out topologies, amortising storage and upload cost.
  • Object versioning, encryption, and lifecycle rules provide a natural audit trail independent of broker retention.

Cons

  • Every consumer pays an extra object-store GET before processing begins, adding latency and egress cost.
  • The pipeline now depends on storage availability, IAM, and lifecycle automation—another on-call surface.
  • Reference lifecycle management is error-prone: premature deletes break redelivery; delayed deletes inflate storage bills.
  • Intercepted references widen the security surface unless buckets are private, encryption is mandatory, and pre-signed TTLs are tight.

Implementation notes

Pre-signed URLs versus object keys: In-account consumers with stable IAM roles should carry bucket/key references and fetch with instance credentials—simpler rotation and no clock skew on URL expiry. Cross-account or third-party workers often need pre-signed URLs minted at publish time; set TTL to at least ten times worst-case queue lag plus p99 processing so slow consumers never see HTTP 403 on fetch. Document which pattern each queue uses so security reviews do not mix permanent bucket access with short-lived URLs on the same topic.

Broker envelope: Include content type, byte size, checksum (SHA-256 or ETag), correlation ID, optional jobId, and CloudEvents attributes in the small message so metrics and traces do not require opening the blob. Kafka clusters may enable large records for in-cluster consumers, but claim check remains the portable default across SQS, RabbitMQ, Service Bus, and NATS when payloads leave the messaging estate.

Lifecycle and TTL: Tag or prefix objects by pipeline stage and configure lifecycle rules (for example delete after seven days on jobs/). If consumers are healthy, processing finishes well inside the window; if a consumer is down longer than retention, treat broken references as DLQ cases with explicit alerting. Never delete objects during processing—delete only after successful broker ACK unless a compensating workflow guarantees idempotent re-fetch.

Atomic publish: Pair PUT plus enqueue with the transactional outbox or an idempotent two-phase worker so a crash between storage write and broker publish does not leave orphaned blobs. Schedule periodic orphan sweeps on untagged prefixes as a safety net.

Security and integrity: Encrypt at rest (SSE-KMS or SSE-S3), block public ACLs, and validate checksums after GET when tamper detection matters. Treat claim-check messages as sensitive when URLs encode guessable object keys.

Observability: Log storage key or URL hash, correlation ID, and outcome at publish, fetch, process, and delete so incident response can stitch broker traces to object-store access logs without pulling payload bytes into log pipelines.

Thresholds: brokers commonly cap near 256 KB–1 MB per message (SQS 256 KB, RabbitMQ configurable, MQTT often far smaller)—claim-check becomes mandatory, not optional, above those sizes. Even when Kafka large records are enabled, cross-team portability usually favors object storage plus reference messages.

Integrity failures: compare checksum after download before ACK; mismatch should nack to DLQ because the object may be truncated or swapped. For regulated payloads, prefer SSE-KMS with bucket policies that deny non-consumer principals.

Multi-consumer delete authority: when several competing consumers process the same claim check, only one should delete the object—or use reference counting and lifecycle rules—otherwise a fast consumer can delete while a slow peer still needs the bytes. For pub/sub fan-out with one blob, delete only after the last subscriber ACKs or rely on TTL expiration instead of eager delete. Emit metrics on claim fetch latency and 403 rate so object-store permission regressions surface before broker lag alarms.

Common failure modes

  • Expired pre-signed URL: Slow consumers hit HTTP 403 when URL lifetime is shorter than end-to-end latency—set TTL to at least 10× maximum expected processing time and monitor age-at-fetch metrics.
  • Premature delete: A consumer deletes the object before ACK, so redelivery cannot fetch the body again; delete only after ACK or use versioned buckets when reprocessing is required.
  • Storage outage: S3 or Blob errors fail processing unless fetch retries with exponential backoff, circuit breaking, and DLQ escalation after a bounded attempt count.
  • Orphan PUT: Payload lands in storage but no message publishes, leaving unreachable objects until garbage collection runs—use outbox publish or compensating sweeps on stale prefixes.
  • Partial fan-out failure: One subscriber deletes a shared object while others are still processing; coordinate delete authority or refcount objects when multiple consumer groups redeem the same check.

Decision checklist

  • Does payload size exceed broker limits or stress cluster memory (typically above ~64 KB)?
  • Is server-side encryption enabled on the payload bucket or container?
  • Are buckets private with least-privilege IAM or short-lived pre-signed access?
  • Do lifecycle rules cap retention and cost for unprocessed objects?
  • Does deletion happen only after successful message acknowledgment?
  • Are object keys or URLs logged with correlation IDs at publish, fetch, and delete?
  • If pre-signed URLs are used, does TTL cover queue backlog plus p99 processing time?

Example use cases

  • Illustrative scenario — Northwind Logistics stores multi-megabyte customs PDFs in object storage while SQS carries claim checks so OCR, search, and archival consumers fetch the same object key independently without tripling broker bandwidth.
  • Illustrative scenario — FieldOps upload workers store raw inspection video in object storage, publish claim checks to Kafka, and transcoding workers produce derivative keys while correlation IDs tie upload logs to transcode completion.
  • Illustrative scenario — Meridian Commerce stores partner catalog dumps in one account, embeds pre-signed URLs in SNS notifications, and workers in another account fetch without permanent cross-account bucket credentials.
  • Case study — Microsoft’s Azure Architecture Center documents claim-check combinations of Blob Storage plus Service Bus for large-payload integration—a common pattern for document and media handoffs in hybrid estates.

Related patterns

  • Message Queues — channels that carry claim-check tokens instead of raw bytes.
  • Competing Consumers — parallel workers that each redeem the same reference safely when processing is idempotent.
  • Transactional Outbox Pattern — atomic publish of claim-check messages with database commits.
