Correlation IDs

Generate a unique identifier at the system entry point and propagate it through every synchronous call and asynchronous message, enabling end-to-end request tracing across distributed services and log correlation in production.

⏱ 10 min read

What it is

A correlation identifier—typically a UUID v4 generated at the system entry point—is a unique token that marks one logical business operation across every hop: HTTP calls, queue messages, scheduled jobs, and batch stages. When something fails anywhere in the chain, operators filter logs and traces by that single value to reconstruct the sequence across services, queues, and databases. Enterprise Integration Patterns names this the Correlation Identifier pattern for matching request–reply and scatter-gather pairs in messaging systems.

It complements, but is not identical to, distributed trace IDs carried in W3C traceparent or OpenTelemetry spans. Traces excel at latency trees and dependency graphs; correlation IDs excel at durable log search, audit trails, and async chains where sampling or instrumentation gaps would otherwise break APM continuity. Many teams carry both: correlation ID for operations grep and support lookup, trace ID for APM flame graphs.

CloudEvents extensions and broker headers (Kafka, RabbitMQ, NATS, Amazon SQS message attributes) provide standard places to propagate the same identifier on event envelopes without overloading business payloads or coupling logs to domain field names.

Why it exists

A single multi-step workflow may traverse many services, each writing its own logs. Without a shared key, incident response devolves into timestamp guessing, stitching entity IDs that only some teams index, and manual copy-paste across dashboards. One correlation value in structured logs makes the path reconstructable in seconds—a Kibana or Logs Insights query on correlationId returns every line that participated in the operation.

Async boundaries amplify the problem: a message published minutes or days after the originating HTTP request must still tie back to that request for support and compliance. Correlation identifiers bridge synchronous and asynchronous worlds when traces are incomplete, sampling drops spans, or batch workers lack OpenTelemetry SDKs.

W3C Trace Context’s traceparent solves a related problem for APM—parent/child spans inside one trace tree—while business correlation IDs often outlive a single trace when workflows pause overnight. Mature platforms set correlation at the edge, propagate traceparent for latency analysis, and store correlation in CloudEvents extensions so both log search and Jaeger align on failures.

When to use

  • Multi-service call graphs: Any architecture with more than one deployable unit benefits from request-scoped identifiers in logs.
  • Async and event-driven flows: Publishers embed the ID in message metadata so consumers log under the same key as the API that enqueued work.
  • Long-running processes: Identifiers started at user action time should appear in fulfilment, billing, and notification logs days later.
  • Fan-out / fan-in: Aggregators match branch replies to a parent operation using a single shared correlation value.
  • Support and audit: Internal error surfaces and tooling expose the ID to agents without showing it in end-user UI—support can paste one value into a log explorer instead of reconstructing timestamps.

When not to use

  • Omitting in distributed systems: Even two-service estates benefit from request-scoped IDs; skipping them saves nothing meaningful and permanently complicates incident response.
  • Authorization: Correlation IDs are not secrets and must never gate access to data or APIs—anyone who sees them may legitimately use them for log lookup.
  • Replacing trace strategy: Log correlation alone does not substitute for latency SLO analysis—keep OpenTelemetry or vendor APM where dependency timing matters.
  • Derived from PII: Do not encode emails or account numbers as IDs; use opaque UUIDs to avoid coupling, collision risk, and accidental PII export in log pipelines.

Typical architecture

The edge (API gateway, load balancer, or first service) generates an identifier if the client did not supply one, injects it as an HTTP header, and binds it to the logging context. Each downstream service forwards the same value on outbound HTTP calls and on message metadata. Structured logs emit the field at top level; search platforms index it for cross-service queries.

Pros and cons

Pros

  • Incident and support investigations collapse to one indexed log query instead of manual stitching.
  • The pattern works on polyglot stacks with only logging middleware, not full tracing SDKs.
  • Async consumers can log under the same key as the HTTP request that published the message.
  • Storage and CPU overhead of carrying a UUID is negligible compared to request work.

Cons

  • One service that drops or rewrites the identifier breaks downstream correlation permanently.
  • Inconsistent header names (X-Correlation-ID, X-Request-ID, bespoke keys) cause silent propagation gaps.
  • Logs alone do not expose span timing—pair correlation IDs with tracing for latency SLO work.

Implementation notes

Generating IDs: At the API gateway, load balancer, or first service that owns the user action, read an incoming correlation header if the client or upstream already supplied one; otherwise mint a UUID v4 (crypto.randomUUID(), uuid4(), UUID.randomUUID()). Never derive IDs from order numbers or emails—opaque UUIDs avoid collisions and prevent PII coupling across log retention policies.

HTTP propagation: Standardise one header org-wide—commonly X-Correlation-ID or X-Request-ID—and publish the name in platform runbooks. Middleware should bind the value to framework context (MDC, AsyncLocalStorage, OpenTelemetry baggage) before the first log line. Outbound HTTP clients and service meshes must forward the same value automatically; manual header wiring in application code is a common propagation gap.

Async envelopes: On publish, place the correlation ID in message metadata (Kafka headers, RabbitMQ headers, NATS headers, SQS message attributes, CloudEvents extensions), not inside domain payload fields consumers must deserialize. Add causationId for the immediate parent command or HTTP request so operators can distinguish “same long-running workflow” from “this specific step caused the next message.”

Correlation ID versus trace ID: A correlation ID often spans days-long business workflows; a trace ID typically spans one synchronous request tree under sampling rules managed by APM. Carry both when possible: grep logs by correlation ID, analyse latency by trace ID. When OpenTelemetry is universal, also propagate W3C traceparent (00-<trace-id>-<span-id>-<flags>) for interoperable span parenting across instrumented services.

Scatter-gather: Issue one parent correlation value at fan-out and require every branch reply to echo it; aggregators key in-memory state on that value with a TTL matching the operation deadline and reject late replies that would attach to the wrong parent.

Structured logging policy: Enforce JSON logs with correlationId as a mandatory top-level field via linters, shared logging libraries, or CI checks on sample log lines—plaintext logs without the field make centralized search useless.

Support surfacing: Return correlation IDs in internal admin tools, support dashboards, and BFF error payloads for staff—not in customer-facing error copy where the token confuses users without helping them self-serve.

Cross-protocol hops: the same correlation value should survive HTTP → Kafka → webhook → batch job. Map HTTP headers to CloudEvents extensions at publish boundaries; never regenerate at each bus hand-off unless the prior hop failed to provide one.

Cardinality: high-cardinality correlation values in metrics explode cost—use logs and traces for IDs, keep metrics aggregated by service and route. Sampling policies must still retain error spans for failed correlation paths.

W3C Trace Context interplay: propagate traceparent on every synchronous hop even when logs use a separate business correlation ID—OpenTelemetry exporters link spans when both are present; dropping traceparent at a gateway breaks parent/child timing while logs still grep cleanly. For async publishes, copy correlation into CloudEvents extension attributes (for example correlationid) so event consumers without HTTP ingress still emit the same key in structured logs.

Contract testing: integration tests should assert outbound HTTP stubs received the expected correlation header and that message fixtures include metadata headers on publish. Regression tests that only assert HTTP 200 miss silent propagation loss—the dominant production failure mode. Gate releases on a shared platform library version where middleware injects and forwards identifiers rather than leaving each team to wire headers manually.

Retention alignment: log retention must exceed worst-case workflow duration; correlation search that stops at seven days cannot debug a billing reconciliation that completes on day ten. Document maximum workflow latency when setting index TTL and legal hold policies so support tooling does not expire evidence before investigations finish.

Common failure modes

  • Dropped header: Middleware misses propagation on one service, orphaning all downstream logs—fix with framework-level interceptors and contract tests that fail builds when outbound clients omit the header.
  • Regenerated per hop: Each service mints a new ID instead of forwarding the incoming value; every hop becomes an island—read incoming headers first and generate only when absent.
  • Header name fragmentation: Teams use X-Correlation-ID, X-Request-ID, and bespoke keys at boundaries; platform standards and gateway normalisation prevent silent drops at hand-offs.
  • Unstructured logs: Plaintext logs omit the field, so centralized search cannot filter—enforce structured JSON with correlation ID as a top-level key.
  • User-visible leakage: IDs in customer-facing errors confuse users without helping them; route IDs to internal tooling and support panels instead.

Decision checklist

  • Does every external entry point (gateway, event source, batch trigger) generate or accept a correlation identifier?
  • Is the header name standardized and published for all teams, with gateway normalisation for legacy aliases?
  • Do inbound middleware bind the ID before the first log statement in every service?
  • Do outbound HTTP clients, gRPC metadata, and message publishers forward the same value without manual per-call code?
  • Are logs structured JSON with correlation ID at the top level—not nested under context keys search products ignore?
  • Are causation identifiers used on async chains where cause-and-effect debugging matters?
  • When OpenTelemetry is deployed, does traceparent propagate alongside the business correlation ID?
  • Are IDs exposed to support tooling but omitted from end-user error copy?

Example use cases

  • Illustrative scenario — Support at Meridian Commerce pulls the correlation ID from a payment error panel, searches twelve service indices in under two minutes, and finds a tax adapter HTTP 503 that was never retried.
  • Illustrative scenario — Northwind Logistics sends a delayed tracking email that shares the checkout correlation ID so warehouse, carrier, and notification logs days later still align for audit.
  • Illustrative scenario — RideRelay logs four carrier quote branches under one parent correlation value so ops reconstruct scatter-gather timing from logs alone when APM sampling dropped spans.
  • Case study — W3C Trace Context and OpenTelemetry baggage document interoperable propagation headers that many organisations pair with business correlation IDs for grep-friendly operations alongside standard traces.
