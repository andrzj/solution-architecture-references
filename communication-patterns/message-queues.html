Message Queues

Message queues buffer work between producers and consumers: point-to-point delivery, competing workers, visibility timeouts, dead-letter queues, and at-least-once handling.

⏱ 11 min read

What it is

Message queues implement the Enterprise Integration Patterns Point-to-Point Channel: producers send messages into a durable channel and the messaging system delivers each message to one consumer instance among a competing group. The producer does not address a specific worker; the broker routes, buffers, and re-delivers until processing succeeds or the message is moved to a dead-letter path.

Consumers typically lease a message (Amazon SQS visibility timeout, RabbitMQ consumer acknowledgments), process it, then acknowledge so the broker can delete or commit the offset. If the worker dies before ack, the message becomes available again, which yields at-least-once semantics and requires idempotent handlers.

Queues contrast with pub/sub topics, where every subscription receives a copy. Production systems often combine both—SNS fan-out into per-team SQS queues is a common pattern for broadcast plus isolated worker pools.

Why it exists

Synchronous calls force producers to wait for downstream capacity and availability. A queue inserts buffering and temporal decoupling: spikes land in the queue while consumers drain at a sustainable rate, which protects fragile or expensive workers (rendering, enrichment, third-party API calls) from overload.

Queues also define a clear ownership boundary between teams: the contract is the queue name and message schema, not a live HTTP endpoint that must be up when the producer fires.

When to use

  • Background tasks where the user or API caller should not block on completion (email, reports, media processing).
  • Smoothing traffic so producers can burst while consumers respect downstream rate limits.
  • Work that must survive consumer crashes because the broker retains messages until acknowledged.
  • Horizontal scaling via competing consumers on the same queue without duplicate processing of the same message.
  • Cross-team integration where deploy schedules differ and neither side should hold open HTTP connections.

When not to use

  • Every independent service needs its own copy of the same event; use pub/sub or streaming instead.
  • Strict global ordering across all messages is required without sacrificing parallelism; consider a single-partition stream or FIFO grouping with known throughput limits.
  • Latency budgets are tighter than broker round-trip and serialization overhead allow.
  • Consumers must replay historical events from a retained log; queues delete after ack rather than serving as an audit trail.

Typical architecture

The producer enqueues a message; the broker persists it. One consumer receives the message and the broker hides it from peers for the visibility timeout (or holds an unacked delivery in AMQP). Successful processing ends with an acknowledgment that removes the message from the active queue.

Failed or timed-out processing returns the message for retry; after repeated failures the broker routes it to a dead-letter queue for inspection, as configured in Amazon SQS redrive policies or RabbitMQ dead-letter exchanges.

Pros and cons

Pros

  • Messages persist across producer and consumer restarts when the broker is configured for durability.
  • Queues absorb bursts and let consumers process at a steady, defensible rate.
  • Adding consumers increases drain rate without changing producer code.
  • Visibility timeouts and dead-letter queues provide a path for poison messages instead of silent loss.
  • Teams can deploy producers and consumers on independent schedules behind a stable queue contract.

Cons

  • At-least-once delivery makes duplicate processing possible unless handlers are idempotent.
  • Acknowledged messages are removed, so queues are poor primary stores for replay or compliance archives.
  • Strict FIFO or exactly-once semantics often reduce throughput compared with standard queues.
  • Queue depth, age of oldest message, and DLQ volume become mandatory operational metrics.
  • An extra broker hop adds latency unsuitable for user-facing synchronous paths.

Implementation notes

Size Amazon SQS visibility timeout longer than worst-case handler duration; use ChangeMessageVisibility for long jobs (SQS visibility timeout). In RabbitMQ, ack after successful work with manual acknowledgment (consumer acknowledgments).

Configure a dead-letter queue on every workload queue and alert when DLQ depth is non-zero. Include correlation IDs and source timestamps in payloads to support triage.

Scale consumers from queue depth or oldest-message age (KEDA, AWS Application Auto Scaling). Cap producer ingress when depth exceeds policy so back pressure propagates upstream.

When payloads exceed broker limits (for example the maximum message size documented for SQS), store the body in object storage and pass a reference using the Claim Check pattern.

Document queue contracts in AsyncAPI or internal schema registries so version changes do not break consumers silently.

Common failure modes

  • Poison messages retry until they reach the DLQ while operators never page on DLQ depth.
  • Visibility timeout shorter than processing time causes duplicate work on healthy consumers.
  • One priority class monopolizes a shared pool and starves other message types.
  • Missing DLQ configuration drops failed messages after max receives with no audit trail.
  • Runaway queue depth when consumers stop or fall behind without autoscaling or producer throttling.

Decision checklist

  • Should exactly one worker process each message?
  • Are consumers idempotent for duplicate deliveries?
  • Is visibility timeout or ack timeout aligned with worst-case processing time?
  • Is a DLQ wired with monitoring and a documented replay procedure?
  • Does autoscaling react to queue depth or message age?
  • If FIFO ordering is required, are throughput limits documented and tested?
  • Are oversized payloads handled via claim check rather than inline bodies?

Example use cases

  • Illustrative scenario — Checkout enqueues fulfillment jobs so warehouse workers pick and pack without holding the HTTP checkout response open.
  • Illustrative scenario — A notification queue buffers outbound email API calls while workers retry provider rate limits in the background.
  • Case study — Amazon documents SQS decoupling of microservices with standard and FIFO queues, visibility timeout, and dead-letter queues as core reliability primitives.

Related patterns

  • Publish/Subscribe broadcasts events when every subscriber needs a copy.
  • Competing Consumers describes scaling patterns for shared queue consumption.
  • Claim Check stores large payloads externally and passes references on the queue.
  • Transactional Outbox atomically writes domain state and outbox rows before a relay publishes to the queue.
