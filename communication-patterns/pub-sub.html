Publish/Subscribe (Pub/Sub)

Publish/subscribe decouples producers from consumers: one publish to a topic can fan out to many independent subscribers without the publisher knowing who listens.

⏱ 12 min read

What it is

When a single domain fact must trigger several independent reactions—update a projection, notify a user, stream metrics, and run risk checks—pub/sub lets the producer emit once to a topic while each subscriber group consumes on its own schedule without the publisher tracking recipients.

Publish/subscribe (pub/sub) is an asynchronous messaging pattern in which publishers send messages to a named channel (often called a topic) without addressing individual receivers, and the messaging infrastructure delivers a copy to every active subscription. Producers and consumers are decoupled in space (no direct network address), time (subscribers may be offline while messages are retained), and cardinality (new subscribers can be added without changing the publisher).

The pattern contrasts with point-to-point queues: a queued message is processed by exactly one competing consumer, whereas a published message is replicated to each subscriber group. Many production designs combine both — for example Amazon SNS fanning out to multiple Amazon SQS queues — so you get broadcast semantics at the topic and load-balanced workers behind each queue.

Why it exists

Microservices and event-driven systems need to broadcast state changes without wiring N point-to-point integrations every time a new consumer appears. Before brokers, producers often called each downstream over HTTP; every new listener meant producer changes, and a stalled callee could block the caller. Pub/sub inserts a broker between publishers and subscribers so producers emit facts once and infrastructure handles fan-out, buffering, and (when configured) persistence.

That indirection supports independent deployment: teams subscribe to contracts (topic names and event schemas) instead of callee endpoints. Temporal decoupling follows when subscriptions are durable and the broker retains messages — subscribers catch up after maintenance or deploys instead of forcing synchronous availability.

Pub/sub is not free consistency: each subscription advances its own cursor, so lag differs per consumer group. Operators treat maximum lag per group as a product SLO, not a broker afterthought. Ephemeral pub/sub (in-memory Redis, NATS core without JetStream) is appropriate for soft-real-time signals where missed messages are acceptable; durable logs belong in Kafka, Pulsar, or JetStream when downstream recovery matters.

When to use

  • One domain event must trigger several independent reactions (inventory, notifications, analytics, risk) without the producer enumerating recipients.
  • Teams want stable producer APIs while consumers evolve on their own release cadence.
  • Feeds must reach many subscribers (activity streams, market data, device telemetry) with infrastructure-mediated fan-out.
  • Pipeline stages chain through topics so each stage subscribes to upstream output without direct HTTP coupling.
  • Cache or read-model invalidation must reach every edge layer from a single change notification.

When not to use

  • The caller needs a reply before continuing; use synchronous RPC or a dedicated request-reply messaging pattern.
  • Exactly one worker should handle each unit of work; a point-to-point queue with competing consumers is simpler.
  • Latency budgets are tight enough that broker serialization and delivery latency dominate the path.
  • Global total ordering across all events is mandatory, because most brokers only guarantee order within a partition or subscription shard.

Typical architecture

Publishers append or send messages to a logical topic. The broker may shard the topic into partitions for scale (Kafka partition leaders, Google Pub/Sub topics with ordering keys). Each consumer group tracks its own read position; pull-based clients poll (Kafka, Google Pub/Sub pull), while push-based systems deliver to HTTP endpoints or sockets (Amazon SNS, NATS, or ephemeral Redis pub/sub).

Server-side subscription filters (SNS filter policies, Google Pub/Sub filters) drop events that do not match attributes, which reduces wasted delivery and processing on subscribers.

Pros and cons

Pros

  • New subscribers can be added without changing publisher code or redeploying producers.
  • One publish can reach many independent consumer groups with infrastructure-mediated fan-out.
  • Durable subscriptions let consumers restart or scale while the broker retains unprocessed messages.
  • Pull-based consumption lets each group read at its own pace while the broker absorbs bursts.
  • Retained topics support replay for new consumers, backfills, and corrective reprocessing.

Cons

  • There is no in-band reply channel, so request-response needs a separate pattern or reply topic.
  • Ordering guarantees are usually scoped to a partition or ordering key, not the entire topic.
  • At-least-once delivery is common, so handlers must be idempotent or deduplicate on business keys.
  • Independent evolution of publishers and subscribers makes schema governance and compatibility rules essential.
  • Operating topics, retention, partitions, and consumer lag requires ongoing platform attention.

Implementation notes

Prefer CloudEvents or agreed AsyncAPI schemas for event envelopes so subscribers can rely on stable attributes (type, source, id, time) regardless of broker (CloudEvents specification).

Use topics when multiple services need the same event; use queues when competing workers should share load. SNS-to-SQS fan-out is a common cloud pattern for broadcast plus per-team worker pools.

Choose partition or ordering keys that spread load while grouping events that must stay ordered (for example all lifecycle events for one aggregate ID). Avoid low-cardinality keys that create hot shards.

Distinguish durable subscriptions (Kafka consumer groups, Google Pub/Sub with ack deadlines) from ephemeral channels (Redis pub/sub, NATS core) where disconnected clients miss messages. Match durability to business impact.

Apply server-side filters on metadata attributes where the broker supports them, and enforce consumer idempotency with stored processed-event IDs or natural keys.

Push versus pull: Pull consumers (Kafka consumer groups, Google Pub/Sub pull) set their own pace, which makes backpressure explicit. Push targets (SNS HTTP endpoints, Redis pub/sub, WebSocket bridges) shrink delivery latency but can flood a slow handler unless you add rate limits and overflow handling. Favor pull for heavy processing pipelines; favor push for low-volume alerts where milliseconds matter.

Partition keys: Hash on an aggregate identifier (for example aggregate_id) when events for one entity must stay ordered, but avoid keys with only a handful of values that collapse traffic onto one shard.

AMQP topic exchanges: in RabbitMQ, publishers send to a topic exchange with routing keys such as billing.invoice.created; subscribers bind queues with patterns (billing.*, *.created). Each matching queue receives its own copy—classic pub/sub over a broker without Kafka partitions. Wildcard rules differ from MQTT topic filters; document binding tables when multiple teams share one exchange.

MQTT for devices: MQTT 3.1.1 and 5.0 (OASIS specs) target pub/sub over lossy networks: brokers fan out topic subscriptions to many clients with QoS 0/1/2 delivery grades. QoS 2 is expensive; most telemetry uses QoS 0 with application-level idempotency. MQTT is poor for durable audit logs compared with Kafka—use it when battery-powered clients need lightweight publish, not when warehouse analytics needs replay.

Detection metrics: alert per consumer group on lag (Kafka offset lag, Pub/Sub oldest-unacked-age, SNS CloudWatch NumberOfNotificationsFailed). Schema registry incompatibility should fail CI before deploy—runtime deserialization errors spike consumer error rates without growing lag if poison messages retry forever.

Common failure modes

  • Consumer lag grows until message retention expires and data is lost before slow subscribers catch up.
  • A skewed partition key concentrates traffic on one shard and bottlenecks throughput.
  • Duplicate deliveries cause repeated side effects when consumers lack idempotency or deduplication.
  • Incompatible schema changes break deserialization in downstream services after a producer deploy.
  • Orphaned subscriptions on decommissioned services accumulate backlog and trigger misleading lag alerts.

Decision checklist

  • Do more than one downstream systems need a copy of the same event?
  • Is the subscription durable with retention that matches worst-case consumer downtime?
  • Are handlers idempotent under at-least-once delivery?
  • Is event structure versioned with compatibility rules (schema registry or contract tests)?
  • Does the partition or ordering key balance load while preserving required ordering?
  • Is consumer lag monitored per group with actionable alerts?
  • Are unused subscriptions and retention policies reviewed on a schedule?

Example use cases

  • Illustrative scenario — A checkout service publishes order.placed once while inventory, billing, notification, and analytics each subscribe and process at independent rates.
  • Illustrative scenario — A market-data feed publishes ticks to a partitioned topic keyed by symbol; trading algorithms and dashboards each maintain separate consumer groups with their own offset cursors.
  • Illustrative scenario — Device telemetry lands on a durable topic with per-tenant subscriptions; a stream processor acks slowly while a real-time dashboard subscription tolerates gaps on an ephemeral channel.
  • Case study — LinkedIn’s original Kafka deployment used durable logs to fan activity and metrics events to many internal pipelines without point-to-point coupling.
  • Case study — Google Cloud Pub/Sub documents multi-subscriber delivery with independent ack deadlines and scaling pull workers for high-volume telemetry.

Related patterns

  • Message Queues handle point-to-point work distribution when only one consumer should process each message.
  • Event Streaming extends pub/sub with long-retained, replayable logs suited to analytics and event sourcing.
  • Competing Consumers scale worker pools behind a subscription or queue.
  • Event Notification uses minimal envelopes when consumers fetch detail over synchronous APIs.
