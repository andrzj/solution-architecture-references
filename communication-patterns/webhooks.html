Webhooks

Outbound HTTP callbacks that push event notifications to external systems — covering payload signing, retry policies, at-least-once delivery, consumer idempotency, and webhook management platforms.

⏱ 10 min read

What it is

Webhooks are provider-initiated HTTP callbacks: when an event occurs in a SaaS or platform system, the provider sends an HTTP request (usually POST with a JSON body) to a subscriber URL that the consumer registered in advance. The pattern is push-based event notification over the public internet—no shared message broker, only HTTPS reachability and a contract for payload shape and delivery semantics.

Subscribers acknowledge delivery by returning an HTTP success status within the provider’s documented timeout; otherwise the provider typically retries with backoff until a maximum attempt window, yielding at-least-once delivery. Producers document event types, signing rules, and replay APIs; consumers verify authenticity, deduplicate by event identifier, and defer heavy work off the request thread.

Major platforms (payments, source control, commerce, communications) treat webhooks as the default integration surface for partners who cannot join an internal Kafka or AMQP fabric. Managed ingress products (for example Svix, Hookdeck) sit in front of consumer endpoints to absorb retries, fan-out, and observability when you operate a multi-tenant webhook API yourself.

Why it exists

Polling an upstream API on a fixed schedule wastes quota when nothing changed and adds latency bounded by the poll interval. Webhooks invert control flow so integrators react soon after the provider commits the business event, while the provider scales fan-out by enqueueing HTTP delivery work rather than serving repeated “any updates?” queries.

For platform vendors, webhooks lower the cost of bespoke per-customer integrations: subscribers bring their own HTTPS endpoint and shared secret (or OAuth), and the vendor ships one delivery pipeline. That aligns with how external developers expect to wire CRM, fulfilment, analytics, and custom automation without VPNs into the vendor’s private cloud.

Unlike broker consumers, webhook subscribers control neither retry timing nor ingress capacity—a viral customer can DDoS their own endpoint through legitimate provider retries. Providers should offer per-endpoint rate limits and backoff; subscribers should always ACK fast and process async. Treat webhook delivery as at-least-once HTTP: identical event_id fields must dedupe across days-long retry windows.

When to use

  • You integrate two organizations over the public internet and the downstream party can host a TLS-terminated HTTPS endpoint.
  • Event volume is moderate, payloads are kilobyte-scale JSON documents, and near-real-time reaction matters more than streaming throughput.
  • You expose a product API where customers or partners register their own callback URLs for lifecycle events (signup, billing, shipment).
  • Your provider documents signed payloads and retry behavior, and you can make consumer processing idempotent.
  • Partners expect HTTP POST callbacks with documented signature headers rather than broker credentials on their side.

When not to use

  • Sustained high event rates would open an HTTP connection storm; prefer a durable log, queue, or stream the consumer reads with controlled parallelism.
  • Both endpoints live inside the same VPC or service mesh and can use a broker or RPC with mTLS without traversing the public internet.
  • The subscriber cannot expose a stable public URL or must stay on-premises without a relay; consider polling, SFTP drops, or a managed webhook gateway they operate.
  • You require strict global ordering across all events; webhooks across independent HTTP deliveries do not give you broker-style ordering guarantees.

Typical architecture

During onboarding the subscriber registers an endpoint URL and receives a signing secret (or asymmetric key material). The provider persists subscriptions, enqueues delivery jobs when events fire, signs the raw body (commonly HMAC-SHA256 per vendor docs), and POSTs to the URL. The edge handler verifies signatures with constant-time comparison, returns success quickly, and hands the payload to an internal queue for business logic. Failed deliveries land in a retry scheduler with exponential backoff until success or explicit abandonment, at which point operations dashboards should alarm.

Pros and cons

Pros

  • Integrators need only HTTPS and JSON parsing—no VPN, broker credentials, or cloud-specific SDKs on the subscriber side.
  • Delivery is push-based, so reaction time tracks provider event latency instead of a poll cadence.
  • Platform vendors can standardize one outbound pipeline for many customer endpoints.
  • Reference implementations from major SaaS vendors document signing, idempotency, and retry expectations the industry copies.
  • Managed receivers can buffer spikes and shield fragile customer endpoints from retry storms.

Cons

  • At-least-once delivery and HTTP retries require idempotent consumers and durable deduplication stores.
  • Subscribers must be reachable on the public internet or via a relay, which complicates local development and locked-down enterprises.
  • Ordering between unrelated events is not guaranteed, and a retried older event may arrive after a newer one.
  • Operating webhook infrastructure at scale means subscription CRUD, secret rotation, per-tenant rate limits, and delivery analytics.
  • The HTTP handler must stay within provider timeouts; slow work belongs on an internal queue.

Implementation notes

Verification: Recompute the signature over the raw request body bytes using the vendor’s documented algorithm and headers—common patterns are HMAC-SHA256 over the raw body with a shared secret carried in a dedicated header. Compare digests in constant time and reject replays when the vendor supplies signed timestamps or nonces.

Ack-then-process: Return an HTTP success response after validation and persistence to your ingress queue, not after downstream side effects complete. Match your internal SLA to the provider’s documented acknowledgement window.

Idempotency: Key on the provider’s stable event identifier (or a composite of type plus id). Use the inbox pattern or idempotent consumer guidance from microservices.io so retries do not duplicate financial or fulfilment effects.

As a provider: Document event catalogs (AsyncAPI or OpenAPI webhooks where appropriate), sign outbound bodies, expose delivery logs, and offer CLI or dashboard tools to replay test events. Rate-limit per endpoint to protect both your workers and customer infrastructure.

Secrets: Rotate signing secrets with overlapping validity, audit who can read them, and never log raw payloads containing PCI or PII in clear text.

HTTP contract: webhooks are ordinary HTTP requests—RFC 9110 status codes govern retry semantics. Return 2xx only after the event is durably queued; use 4xx for permanent rejection (bad signature) so providers stop retrying poison payloads; use 5xx or timeouts sparingly because they trigger exponential backoff storms. Many providers abandon after 24–72 hours of failures—export metrics on abandoned deliveries if you operate the provider side.

Provider-side pacing: cap concurrent deliveries per subscriber URL (often tens to low hundreds). Queue dispatch workers and respect HTTP client timeouts (commonly 5–30 s). Offer signed replay APIs so subscribers backfill after outages without polling every object.

Common failure modes

  • Unsigned or weakly verified endpoints: Any client that can reach the URL can forge events unless signature checks are mandatory.
  • Heavy work on the request thread: Timeouts trigger retries that duplicate side effects when the first attempt actually succeeded downstream.
  • Environment cross-wiring: Production providers deliver to staging URLs (or vice versa) because subscription metadata lacks environment guards.
  • Retry exhaustion without visibility: The provider gives up after max attempts while the consumer never knew a gap existed—monitor provider dashboards and dead-letter queues.
  • Assumed ordering: Business logic expects event B always follows event A, but network retries violate that; design for out-of-order tolerance or sequence numbers.

Decision checklist

  • Does every handler verify signatures (or mTLS) before parsing JSON?
  • Does the HTTP layer acknowledge quickly and hand off to durable internal processing?
  • Are event IDs deduplicated for at least as long as the provider may retry?
  • Can signing secrets rotate without a hard cutover outage?
  • Are failed deliveries visible in metrics, logs, and paging when abandonment occurs?
  • If you are the provider: is there per-subscriber rate limiting, retry policy documentation, and a support path for replay?

Example use cases

  • Illustrative scenario — An e-commerce integrator receives a payment-succeeded webhook, validates the signature, enqueues the payload, and marks the order paid idempotently before triggering fulfilment workers.
  • Illustrative scenario — A CI service registers repository push webhooks; the ingress layer ACKs immediately while a build queue schedules compile jobs keyed by commit SHA.
  • Illustrative scenario — A B2B SaaS vendor exposes customer-configurable URLs for subscription lifecycle events and routes each tenant’s traffic through a managed receiver for retry and trace headers.
  • Case study — Stripe’s webhook guide is widely cited for signed payloads, idempotent handlers, and treating delivery as at-least-once.

Related patterns

  • Event Notification — semantic intent; webhooks are the HTTP push binding for external subscribers.
  • Inbox Pattern — database-backed deduplication for webhook retries.
  • Publish/Subscribe — internal broker fan-out when both sides share infrastructure.
  • Correlation IDs — trace webhook-triggered work across services.
