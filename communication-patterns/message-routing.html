Message Routing

Directing messages to the correct handler based on content, headers, or dynamic routing tables — covering content-based routing, topic-per-event-type, routing slip, process manager, and dead-letter routing.

⏱ 11 min read

What it is

Message routing is the set of patterns that decide which downstream channel or handler receives each message without hard-wiring every producer to every consumer address. Enterprise Integration Patterns (EIP) documents core routers such as the Content-Based Router, Message Router, Routing Slip, and Process Manager.

Routing can live in the broker (Kafka topic names, RabbitMQ exchanges and routing keys, Amazon SNS filter policies, Google Pub/Sub filters), in an integration framework (Apache Camel, Spring Integration), or in a dedicated stateless router consumer that republishes to downstream topics. The goal is the same: subscribers receive only the traffic they understand, and unmatched messages land on explicit dead-letter paths instead of disappearing.

Routing pairs naturally with command versus event semantics: commands route point-to-point to one handler queue; events route to topics where many subscriptions apply their own filters.

Why it exists

If every consumer subscribed to a firehose and filtered locally, CPU and deserialization cost would scale with the product of publishers and uninterested consumers. If every producer embedded destination addresses, adding a subscriber would require redeploying producers. Routing intermediaries keep address knowledge out of domain services so teams can add consumers or split queues by changing broker configuration or router rules.

Operational concerns—region, tenant, priority, compliance tier—also belong in routing metadata (headers or attributes) so the same business event can fan out to the correct isolated pipelines without duplicating publisher code per geography.

When to use

  • One inbound stream carries many event or command types and each downstream service should see only its subset.
  • Sequential pipelines (validate, enrich, archive) need explicit next-hop instructions via routing slip or topic chaining.
  • Multi-tenant or multi-region deployments require header-driven steering to the correct queue or cluster.
  • You must guarantee a dead-letter path for poison or unroutable messages instead of silent drop.
  • Sagas or process managers choose the next participant based on persisted workflow state.

When not to use

  • Every subscriber legitimately needs every message—use pub/sub without selective routers.
  • Routing rule tables grow so large they encode business policy that belongs in domain services; refactor boundaries or event taxonomy first.
  • Broker-native routing already matches your predicates and you would duplicate it in custom code without added expressiveness.
  • You require global ordering across all message types on one router instance—that bottleneck fights horizontal scale.

Typical architecture

Producers publish to an ingress topic or exchange with typed headers (event type, region, tenant, priority). A content-based router—broker filter, Camel choice flow, or lightweight republisher—evaluates predicates and forwards to dedicated queues. Routing-slip messages embed an ordered list of steps; each worker completes its step and advances the pointer. Stateful process managers read workflow ids from messages, load state, and emit the next command or event to the appropriate destination. Every branch includes a default route to a dead-letter queue monitored by alerts.

Pros and cons

Pros

  • Producers stay stable when new consumers appear because addressing moves to routers or broker bindings.
  • Consumers avoid deserializing irrelevant traffic, which saves CPU and keeps failure domains smaller.
  • Routing slips express linear pipelines without a heavyweight orchestration engine for simple sequences.
  • Topic-per-type conventions make contracts grepable in AsyncAPI and infrastructure repos.

Cons

  • Central routers become failure magnets when misconfigured; changes need review and canary testing.
  • Payload-based rules couple routers to serialization formats and slow hot paths.
  • Routing slips version with workflow shape; new steps require coordinated envelope and consumer updates.
  • Process managers introduce state stores and recovery logic alongside messaging ops.

Implementation notes

Prefer broker features: Use SNS subscription filter policies, RabbitMQ topic exchanges, Kafka topic boundaries, and SQS dead-letter redrive policies before building bespoke routers. Document binding names beside AsyncAPI channels.

Header-first predicates: Route on message attributes (type, tenant, region) rather than parsing large JSON bodies at the edge unless necessary.

Stateless republishers: Custom routers should only read, decide, and forward—no business side effects—so you can scale them horizontally behind competing consumers.

Dead letters: Configure DLQs on every queue, monitor depth, and document replay versus discard. AWS, RabbitMQ, and Google Pub/Sub each document DLQ wiring patterns in their broker guides.

Integration frameworks: Apache Camel’s Choice and Routing Slip EIPs implement EIP semantics with mandatory otherwise branches to catch unmatched messages.

Common failure modes

  • No default route: Unmatched messages disappear; always forward unknown predicates to a DLQ or alert topic.
  • Typoed routing keys: Producers publish to mistyped topic names with no subscribers; validate names in CI against a catalog.
  • Routing slip loops: A step forwards back to itself; cap step counts and validate slips at ingress.
  • Hot router instance: A single-threaded router saturates before workers do; shard routers or push rules into the broker.
  • Filter drift: SNS or Pub/Sub filters desync from producer attributes after deploy; contract tests should publish sample messages per environment.

Decision checklist

  • Can broker-native bindings express the routing rules without a custom service?
  • Does every decision branch include a catch-all path to a monitored DLQ?
  • Are topic, queue, and routing key names validated in CI or registry checks?
  • Is router logic stateless (or is state explicitly owned by a process manager store)?
  • For routing slips, is there a maximum step count and schema version?
  • Can traces or correlation ids follow messages across each routing hop?

Example use cases

  • Illustrative scenario — An order event bus carries multiple type values; SNS filter policies fan order.shipped to logistics queues while analytics queues subscribe only to financial events.
  • Illustrative scenario — A document ingestion routing slip lists normalize, virus-scan, and archive queues; each worker advances the slip after success.
  • Illustrative scenario — A notification router reads channel preference headers and forwards the same request event to email, SMS, or push workers without the publisher knowing which channels apply.
  • Case study — Enterprise Integration Patterns (Hohpe and Woolf) codified content-based routing and routing slips as integration vocabulary still mirrored in Camel and Spring Integration today.
