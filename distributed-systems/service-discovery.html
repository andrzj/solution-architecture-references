Distributed Systems Infrastructure

Service Discovery

Mapping logical names to healthy instances — client-side and server-side discovery, Consul and Kubernetes DNS, health checks, and mesh control planes.

⏱ 13 min read

What it is

Service discovery maintains a live directory from service name (and optional metadata) to network locations of healthy instances. Producers register on startup; the registry deregisters on graceful shutdown or failed health checks; consumers resolve names before opening connections.

Patterns fall into client-side discovery (the caller queries Eureka/Consul, caches endpoints, load-balances in-process—Netflix Ribbon style) and server-side discovery (the caller hits a stable virtual IP or DNS name; a load balancer or kube-proxy chooses the backend). Kubernetes Service objects plus CoreDNS are the canonical managed-platform version; Consul couples DNS, HTTP, and Connect sidecars with Serf gossip for failure awareness.

Checkout pods might scale on Kubernetes while warehouse jobs on another orchestrator register into a shared Consul catalog—clients resolve logical service names to healthy endpoints regardless of which control plane launched the instance.

Why it exists

Microservice and container schedulers recycle IP addresses continuously. Static config files and manual load-balancer edits cannot keep pace with rolling deploys, autoscaling, and multi-version canaries. Discovery automates that mapping and ties it to health so traffic does not land on processes still starting or already drained.

Kleppmann’s network and unbundling themes in DDIA apply: discovery is infrastructure that lets application code speak in service names while the platform tracks where instances actually run.

When to use

  • Use platform-native discovery (Kubernetes Services, ECS Service Discovery, Cloud Map) when the scheduler already owns lifecycle events.
  • Use Consul or Eureka when workloads span VMs and containers and you need a shared registry with rich health checks.
  • Use mesh xDS (Istio, Linkerd) when you want discovery, mTLS, and retries without per-language client libraries.
  • Use DNS-based discovery for polyglot clients that cannot embed SDKs but understand SRV/A records.

When not to use

  • Do not add a registry when a single HAProxy and three static backends suffice—operational surface should match churn.
  • Do not point serverless callers at instance IPs; use provider function URLs or API gateways instead.
  • Do not treat DNS alone as instant discovery—TTL and JVM caching introduce stale routes unless tuned.

Typical architecture

Registration flows through health-checked catalog entries; resolution returns ready endpoints only. Headless Kubernetes services expose individual Pod DNS for StatefulSets (Cassandra, Kafka) while ClusterIP fronts stateless HTTP.

Pros and cons

Pros

  • Automates endpoint churn during deploys and autoscaling—no ticket-driven LB edits.
  • Health-gated catalogs keep cold-start pods and draining nodes off the hot path.
  • Metadata (version, AZ, weight) enables canary and zone-aware routing.
  • Mesh control planes reuse the same catalog for mTLS identities and retries.

Cons

  • Client-side libraries multiply per language and must handle cache staleness.
  • Registry outages block registration and can strand new pods without cached fallbacks.
  • DNS TTL and aggressive JVM caching lengthen incident tails after scale-in.
  • Split views during partitions—clients must tolerate brief inconsistency or use quorum reads on metadata.

Implementation notes

Consul: Agents register local services; servers replicate catalog via Raft; Serf propagates node health. DNS (.service.consul) offers L4-friendly discovery; Connect injects Envoy for L7 policies. Tag prepared queries for nearest healthy payment instance.

Kubernetes: Endpoints/EndpointSlice objects track ready Pods; kube-proxy or CNI datapaths program rules. Use readinessProbe before marking ready; preStop sleeps while Endpoint removal propagates. Headless services expose per-Pod A records for stateful workloads while ClusterIP fronts stateless HTTP.

Eureka pattern: Registry replicates in AP style; clients refresh on a schedule and apply client-side load balancing—acceptable when brief staleness is tolerated and the registry avoids strong global consistency costs.

Graceful deploy: Register only after dependencies connect; deregister before SIGKILL; align terminationGracePeriodSeconds with longest in-flight checkout RPC.

Common failure modes

  • Thundering herd on cold cache: registry flap causes every client to refresh simultaneously—rate-limit lookups and use watch/long-poll APIs.
  • Liveness-only probes: JVM up but not accepting traffic—route payment failures until readiness fails.
  • Stale DNS in Java: InetAddress caching keeps dead Pod IPs—set networkaddress.cache.ttl consciously or bypass DNS with mesh xDS.
  • Cross-DC catalog drift: WAN federated Consul sees different health—prefer local prepared queries for latency-sensitive checkout.

Decision checklist

  • Does the scheduler already expose discovery, or do hybrid VMs need Consul/etcd?
  • Client-side or server-side resolution—and who owns retries/timeouts?
  • Do readiness checks prove dependency readiness (DB, cache), not just port open?
  • Is the registry HA with monitored Raft quorum or etcd health?
  • Does graceful shutdown wait for endpoint removal before process exit?

Example use cases

  • Illustrative scenario — RideRelay checkout on Kubernetes: Payment Deployment scales; EndpointSlices update; checkout sidecar resolves ClusterIP; Istio xDS pushes new endpoints with mTLS before old Pods terminate.
  • Case study — Netflix Eureka + Ribbon (client-side) at scale—with cache refresh trade-offs.
  • Case study — HashiCorp Consul on Nomad with HTTP/TCP health checks for warehouse services.
  • AWS Cloud Map + App Mesh for ECS tasks discovering upstream gRPC hosts.

Related patterns

  • Gossip Protocols — Serf membership accelerates Consul failure detection.
  • Distributed Coordination — shared etcd/Consul clusters often back both discovery and locks.
  • Service Mesh — discovery feeds Envoy/Linkerd data planes.
