Distributed Systems Time & Order

Clock Synchronization

Why nodes cannot agree on “now” — NTP drift, leap smearing, logical clocks from Lamport, hybrid logical clocks, and when TrueTime buys real external consistency.

⏱ 13 min read

What it is

Clock synchronization in distributed systems is the problem of deciding what time an event happened when every machine keeps its own oscillator, NTP skews, and VMs pause for live migration. Leslie Lamport showed in “Time, Clocks, and the Ordering of Events in a Distributed System” that what matters for correctness is usually the partial order of events (the happens-before relation), not agreement on universal time.

Martin Kleppmann’s treatment of “unreliable clocks” in Designing Data-Intensive Applications (Chapter 8) separates three layers operators confuse: synchronizing physical clocks (NTP, PTP, GPS), logical timestamps (Lamport, vector clocks) for causal ordering without trusting hardware, and hybrid schemes (HLC, TrueTime) that bind logical order to wall time when you need TTLs, retention, or “as-of” analytics.

A checkout platform might stamp cart updates with NTP time and apply last-write-wins (LWW). After a leap-second adjustment or a VM time step, two app servers can disagree on which discount edit is newer even though both timestamps look valid—logical or hybrid clocks exist to prevent that class of silent reordering.

Why it exists

Correctness often depends on ordering: snapshot reads need a transaction timestamp, lease expiry assumes time moves forward, and audit trails should not show effect before cause. Network latency between causally related events can be microseconds; clock error on commodity servers is commonly milliseconds and can spike to hundreds of milliseconds during hypervisor migration or misconfigured NTP.

Logical clocks trade synchronized “now” for a consistent story about which messages definitely arrived before which local work. That is enough for many pipelines (tracing, replication metadata) but not enough to detect concurrent writes—that is where vector clocks extend the model. Hybrid clocks bridge to wall time so operators can set expirations and human-readable times without abandoning causal guarantees on the hot path.

When to use

  • Use Lamport or hybrid logical clocks when event ordering across nodes must respect message causality, not just “later timestamp wins.”
  • Use NTP or PTP plus monitoring when you only need approximate alignment for logs, metrics, or SLA dashboards—not for distributed correctness.
  • Use TrueTime-style uncertainty intervals or explicit commit_wait when a database must offer external consistency tied to real time across regions.
  • Use hybrid logical clocks (as in CockroachDB) when transactions need serializable ordering and you still want timestamps that resemble UTC for backups and TTL.

When not to use

  • Do not use wall-clock LWW for conflict resolution when skew can exceed inter-write latency—Kleppmann’s clock discussion is explicit about lost updates in Cassandra-style LWW.
  • Do not attach logical clocks to every log line if you only need rough correlation; standard UTC timestamps plus trace IDs are simpler.
  • Do not assume NTP alone secures distributed locks or lease TTLs; pair short leases with fencing tokens or consensus-backed epochs.

Typical architecture

The sequence below is Lamport’s algorithm: each local event bumps counter L; sends carry L; receives set L = max(L, T) + 1. If event a happens-before b, then L(a) < L(b), but the converse is false—concurrent events get arbitrary order, which is why LWW on Lamport values alone is unsafe for conflict detection.

Pros and cons

Pros

  • Lamport clocks are small (one integer), easy to piggyback on messages, and sufficient for many tracing and replication metadata paths.
  • HLC timestamps stay near UTC—operators can reason about retention and user-visible “modified at” while preserving happens-before on commits.
  • Logical ordering does not require GPS, atomic clocks, or cross-datacenter time sync for causal correctness.
  • TrueTime’s interval API makes clock uncertainty explicit instead of pretending synchrony.

Cons

  • Lamport time does not detect concurrency—two unrelated writes can receive increasing counters without either happening-before the other.
  • NTP and chrony can step clocks backward; leases, LWW, and session expiry built on naive wall time fail quietly.
  • TrueTime-class infrastructure is expensive and rare outside hyperscale operators.
  • HLC and logical schemes still require disciplined use—application code that sorts by client wall clock bypasses the guarantees.

Implementation notes

Physical sync: Run chrony or ntpd on every node, alert on large offset, and prefer slew over step when possible. PTP helps in dedicated racks but does not replace logical ordering for database transactions. Kleppmann recommends treating synchronized clocks as a best-effort signal, not a correctness primitive.

Lamport in practice: Increment before local work; attach timestamp to RPC headers; on receive, advance as in the diagram. Distributed tracers often store both physical time (for human dashboards) and logical order (for causal links).

Hybrid logical clocks: Pair physical time with a logical counter that advances when physical time would violate causality—CockroachDB’s transaction timestamps follow this pattern for serializable isolation without per-transaction global coordination.

TrueTime: Spanner exposes TT.now() as an uncertainty window; commits wait until TT.after(s) ensures no later commit can receive an earlier timestamp—buying external consistency at the cost of bounded commit latency.

Common failure modes

  • NTP step / leap smear mismatch: one rack steps while another smears—LWW picks the wrong cart line for hours until operators notice revenue drift.
  • GC pause vs lease TTL: a coordinator’s JVM stalls; its lock expires on the server while the process still believes it holds leadership—pair TTL locks with fencing tokens.
  • Client-supplied timestamps: allowing writers to set writetime invites stale “future” timestamps that permanently win LWW.
  • Log merge illusions: aggregating stderr from many pods by timestamp alone shows payment capture before authorization when causality crossed hosts.

Decision checklist

  • Is correctness tied to wall-clock order? If yes, document worst-case skew and justify LWW or migrate to logical/versioned resolution.
  • Are lease and TTL durations at least an order of magnitude above measured skew plus GC pause tails?
  • Do databases use server-assigned timestamps (HLC/TrueTime) rather than client clocks for commit order?
  • Is chrony offset exported to metrics with paging on step events?
  • Do you need to detect concurrent writes (vector clocks) or only enforce a partial order (Lamport/HLC)?

Example use cases

  • Illustrative scenario — FleetCart cart LWW: Two regions apply promo codes during an NTP glitch; Cassandra LWW keeps the discount tied to the higher timestamp, dropping the other edit—migrating conflict policy or using version vectors is the DDIA-aligned fix.
  • Case study — CockroachDB serializable transactions with HLC—causal commits without Spanner-class hardware.
  • Case study — Google Spanner external consistency via TrueTime commit_wait.
  • Jaeger and Zipkin correlate spans using trace IDs plus per-span ordering that respects parent/child causality.
