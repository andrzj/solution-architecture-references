Distributed Locking

Mutual exclusion across processes and hosts—why TTL locks are not enough for correctness, the Redis Redlock debate, consensus-backed locks, and fencing tokens per DDIA.

⏱ 13 min read

What it is

A distributed lock is a mutual-exclusion primitive that only one client in a cluster may hold at a time, usually implemented as a key in Redis, a sequential ephemeral znode in ZooKeeper, or a lease record in etcd. Unlike an in-process mutex, lock ownership is inferred over the network: acquirers compete with timeouts, retries, and (hopefully) explicit release. Kleppmann’s distributed locking essay and DDIA (Ch. 8–9) stress that a lock is only safe when both the lock service and the guarded resource cooperate—especially via monotonic fencing tokens that block writes from clients whose lease expired while they were paused.

Why it exists

Applications need cross-host exclusion for leader election, deduplicated cron, serializing access to legacy APIs, or guarding non-transactional side effects. A local synchronized block cannot see peers. Distributed locks approximate a critical section, but wall-clock TTLs, GC pauses, and partitions break the analogy to local mutexes: two holders can be active concurrently unless the system design acknowledges asynchronous failure detection.

When to use

  • Efficiency locks: duplicate work is wasteful but idempotent (metrics rollups, cache warming)—a simple Redis lease may suffice.
  • The guarded resource is external and lacks compare-and-set, transactions, or versioning.
  • Consensus-backed coordination (etcd, ZooKeeper) is already on the critical path for other cluster metadata.
  • You implement fencing at the storage or API layer and treat the lock service as a token issuer, not the sole safety barrier.

When not to use

  • The database or object store supports conditional writes, unique constraints, or serialisable transactions—prefer optimistic concurrency (DDIA’s default recommendation).
  • You need a correctness lock over mutable shared state but cannot enforce fencing tokens downstream—Redlock/TTL-only designs remain unsafe under pause and clock skew.
  • Many clients fight for one lock name; queueing or sharding work removes the choke point.
  • You are tempted to implement Paxos/Raft yourself just for locking—use an existing consensus service instead.

Typical architecture

The safe pattern treats the lock service as a token issuer, not the sole arbiter of exclusivity. A client acquires a unique value or monotonic token, performs work, and attaches that token to writes against the guarded resource. If the client outlives its TTL, a rival acquires a higher token; storage rejects the stale writer even when its local lock handle still looks valid—Kleppmann’s fencing story applied to Redis, etcd, or Chubby-style backends.

Pros and cons

Pros

  • Expresses cross-host exclusion without pushing every service through one database transaction coordinator.
  • Single-node Redis SET NX PX is fast for cron deduplication and cache warmers where overlap wastes work but does not corrupt state.
  • Consensus leases (etcd, ZooKeeper sessions) inherit linearisable grant/revoke semantics suitable for metadata and small critical sections.
  • TTL expiry bounds how long a crashed holder blocks peers without manual operator intervention.

Cons

  • TTL locks remain unsafe for mutable shared resources unless fencing tokens are enforced at the storage layer.
  • Redlock and multi-master Redis variants do not create linearisable locks under pause and clock skew—only probabilistic exclusion.
  • Hot lock names become coordination choke points; retries amplify latency across the fleet.
  • Mis-released locks (wrong token in Lua delete) or missing extend logic are a common source of silent double execution.

Implementation notes

Classify the lock. DDIA and Kleppmann distinguish efficiency locks (occasional overlap is tolerable) from correctness locks (overlap corrupts data). Only the latter demands consensus or fencing.

Redis single-node: acquire with SET key unique-token NX PX ttl; release with a Lua script that deletes only when GET key == unique-token. Extend TTL with the same token check if critical sections can overrun. Without fencing, treat this as best-effort exclusion.

Redlock (multi-master Redis) attempts quorum acquisition across independent nodes. Kleppmann showed overlapping holders remain possible when processes pause longer than TTL or clocks step. Salvador Valverde’s responses and follow-on Jepsen tests of Redis clients reinforce: Redlock does not create a linearisable lock, only a probabilistic one. Use it when wasting work is acceptable, not when protecting financial balances or inventory.

Consensus locks (ZooKeeper, etcd): locks inherit Raft/ZAB safety—sessions, ephemeral nodes, or lease records tie ownership to cluster-visible state. Latency is higher than Redis; correctness for metadata and small critical sections is the payoff. etcd’s concurrency API combines lease TTL with transactional compare—closer to the “lock as token issuer” model.

Fencing tokens: the lock service returns an ever-increasing number (Chubby-style). Every write to the guarded resource carries the token; storage rejects stale tokens even if the client still holds an expired Redis key. This is the pattern DDIA documents for making lease-based leadership safe on shared disks or databases.

Testing: Jepsen’s histories simulate clock skew, process pause, and partition between lock clients and servers—use them as acceptance criteria before trusting a new lock integration.

Common failure modes

  • Pause vs TTL: STW GC or long I/O freeze exceeds lease duration; a second acquirer proceeds while the first still runs critical code.
  • Extend-after-expiry: heartbeat renews a lock the server already granted to someone else because extend did not check token ownership atomically.
  • Fencing bypass: storage accepts writes without comparing tokens—dual holders corrupt rows despite a “correct” lock service.
  • Partitioned lock client: holder cannot renew but continues locally; rivals win on the server and both sides mutate external APIs.
  • Thundering herd on unlock: hundreds of clients spin on the same key after expiry, saturating Redis or etcd.
  • Orphan lock after crash: TTL too long blocks progress; TTL too short causes churn—neither extreme is free.

Decision checklist

  • Could a unique constraint, conditional update, or serialisable transaction replace the lock entirely?
  • If you must lock, is the guard an efficiency or correctness problem—and does the backend match?
  • Does every downstream writer validate monotonic fencing tokens on mutate?
  • Is TTL sized above p99 critical-section time plus GC and clock-skew headroom—and is extend implemented safely?
  • Are acquire, extend, and release implemented with compare-and-delete scripts, not naive DEL?
  • Do metrics track hold time, wait time, failed acquires, and token rejections at storage?

Example use cases

  • Illustrative scenario — A Redis lease ensures only one app replica sends hourly email digests; occasional duplicate sends are acceptable.
  • Case study — Google Chubby (described in the Chubby paper and DDIA) issues lock handles with fencing tokens consumed by Bigtable and other services.
  • Case study — Kubernetes Lease API provides etcd-backed leader election for controllers—consensus locking rather than cache TTL.
  • Illustrative scenario — Payment capture uses a database unique constraint on idempotency keys instead of a distributed lock, following Kleppmann’s preference for conditional writes where possible.

Related patterns

  • Leader Election — long-lived leadership is often “who holds the coordination lock with the highest epoch.”
  • Split Brain Problem — the outcome when locks or leases fail to exclude a second active writer.
  • Clock Synchronization — TTL locks inherit wall-clock assumptions Kleppmann warns about.
  • Consensus Algorithms — safest locks sit on the same Raft log that elects leaders.
  • Distributed Coordination — session, lease, and election APIs from etcd and Consul.
