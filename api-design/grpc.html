gRPC

gRPC RPC over HTTP/2 and Protobuf—unary and streaming call types, codegen, deadlines, health checks, and edge patterns per grpc.io documentation.

⏱ 14 min read

What it is

gRPC is a high-performance remote procedure call (RPC) framework: you define a service and messages in a .proto file, run the Protocol Buffers compiler to generate typed stubs, and exchange binary Protobuf payloads over HTTP/2 (multiplexed streams, header compression, flow control). The gRPC core concepts describe four call patterns—unary, server streaming, client streaming, and bidirectional streaming—on one connection.

From the caller’s perspective, a remote method looks like a local function; the framework handles serialization, metadata headers, status codes, deadlines, and optional TLS or mutual TLS. gRPC is a CNCF project widely used for internal microservice meshes, streaming pipelines, and mobile backends where JSON overhead is measurable.

// user_service.proto (proto3)
syntax = "proto3";
package users.v1;

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
  rpc ListUsers(ListUsersRequest) returns (stream User);
}

message GetUserRequest { string user_id = 1; }
message User {
  string id = 1;
  string name = 2;
}

Why it exists

REST over JSON is universal but pays parsing cost and lacks a first-class IDL across languages. Large organizations needed contract-first RPC with compact wire formats and generated clients—capabilities earlier internal stacks provided privately. gRPC standardizes that: one .proto drives servers and clients in Go, Java, Python, and others, with HTTP/2 allowing many concurrent RPCs per TCP connection without head-of-line blocking at the application layer.

It deliberately targets trusted networks and platform teams who can operate HTTP/2-aware proxies, health probes, and schema registries—not arbitrary browser clients without an adapter.

When to use

  • Low-latency, high-throughput service-to-service calls inside a VPC or mesh.
  • Polyglot microservices sharing one versioned .proto contract.
  • Streaming telemetry, chat, or bulk uploads (client/server/bidi streams).
  • Mobile or edge clients where smaller payloads matter on metered links.
  • Organizations enforcing deadlines, metadata propagation, and interceptors uniformly.

When not to use

  • Public HTTP APIs for unknown clients—OpenAPI/REST remains the default interchange.
  • Browser-only integrations without gRPC-Web, Connect, or a transcoding gateway.
  • Infrastructure that terminates HTTP/1.1 only and cannot route HTTP/2 RPC streams fairly.
  • Debug-by-curl workflows without grpcurl or reflection in non-production environments.

Typical architecture

Clients invoke generated stubs; sidecars or L7 proxies balance per-stream RPCs; servers implement the generated interface and optional grpc.health.v1 checks.

Pros and cons

Pros

  • Compact Protobuf payloads and fast parse/serialize versus JSON.
  • HTTP/2 multiplexing reduces connection count under bursty workloads.
  • Generated stubs enforce types and method names at compile time.
  • Deadlines, cancellation, and metadata are first-class across call chains.
  • Interceptors centralize auth, logging, and tracing on client and server.
  • Standard health and reflection (dev) protocols integrate with Kubernetes tooling.

Cons

  • Not browser-native without gRPC-Web or Connect.
  • Binary on the wire needs tooling to inspect.
  • L4 load balancers mis-route long-lived HTTP/2 connections.
  • Proto evolution rules are strict—never reuse field numbers.
  • Operational stack must understand HTTP/2, mTLS, and schema CI (e.g. buf).

Implementation notes

Protobuf evolution

In proto3, reserve removed field numbers and names. Prefer optional or explicit presence where needed. Never change the wire type of an existing number. Lint and breaking-change checks in CI (Buf breaking rules) catch unsafe edits before deploy.

Deadlines and status codes

Always attach a deadline to client contexts; propagate it on outbound calls. Map UNAVAILABLE and DEADLINE_EXCEEDED to retry policies; treat INVALID_ARGUMENT as non-retryable. See gRPC error handling.

Interceptors and metadata

Use unary/stream interceptors for JWT validation, OpenTelemetry propagation, and request logging. Put auth tokens and trace IDs in metadata, not message bodies.

Browser and gateway paths

gRPC-Web proxies translate browser-safe framing to native gRPC. Connect speaks gRPC-compatible RPC over HTTP/1.1 or HTTP/2 without trailers browsers cannot read. API gateways can transcode JSON/REST to gRPC for external consumers.

Health and reflection

Implement grpc.health.v1.Health per gRPC health checking and point Kubernetes probes at grpc-health-probe. Enable server reflection only outside production so tools like grpcurl can discover services.

Common failure modes

  • Missing deadlines — slow callees pile up blocked threads or goroutines.
  • L4 stickiness — new pods see no traffic until connections recycle.
  • Field number reuse — silent corruption between mixed client versions.
  • Retry storms — retrying non-idempotent RPCs on UNAVAILABLE.
  • Streaming without backpressure — fast producers OOM slow consumers.

Decision checklist

  • Are deadlines set and propagated on every RPC?
  • Does load balancing understand HTTP/2 streams (L7 or client-side)?
  • Are proto files linted and breaking-checked in CI?
  • Is the health service registered and wired to orchestrator probes?
  • Are interceptors handling auth, tracing, and metrics consistently?
  • Is browser traffic using gRPC-Web, Connect, or REST transcoding?
  • Is reflection disabled in production?
  • Are retry policies idempotent and status-aware?

Example use cases

  • Illustrative scenario — An order service calls inventory and payment over gRPC with 150 ms deadlines; an Envoy sidecar terminates mTLS and spreads streams across replicas.
  • Illustrative scenario — Northwind Logistics dispatch agents use client-streaming RPC to upload GPS batches; the ingest service acks aggregates with a single response per window.
  • Case study — Google Cloud and open-source stacks expose many data-plane APIs (e.g. Bigtable, Spanner client libraries) over gRPC for typed, multiplexed access.
  • Case study — Model-serving platforms (TensorFlow Serving, NVIDIA Triton) commonly accept prediction RPCs with tensor Protobuf messages for low overhead.
