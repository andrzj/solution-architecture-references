API Design Essential

REST API Design

Principles and conventions for designing RESTful HTTP APIs that are consistent, evolvable, and easy for clients to consume — covering resource naming, HTTP semantics, status codes, versioning, and pagination.

⏱ 14 min read

What it is

REST API design is the practice of exposing domain resources over HTTP using a uniform interface: nouns in URIs, semantics in methods and status codes, and state carried in representations (usually JSON) rather than on the server between requests. The approach comes from Roy Fielding’s REST architectural style for distributed hypermedia; production APIs often implement a pragmatic subset—resource-oriented URLs and standard verbs—without full hypermedia navigation.

REST’s defining constraints include client–server separation, statelessness, cacheability, a uniform interface, layered intermediaries, and optional code-on-demand. Teams apply them by modeling collections and items (/orders, /orders/{id}), honoring method safety and idempotency, returning meaningful status codes, and supporting conditional requests with validators such as ETag.

Day-to-day design work spans naming and URI shape, pagination and sparse field selection, consistent error bodies, versioning when contracts change, and documenting the surface in OpenAPI so consumers can integrate without reading server code.

Why it exists

Early web services leaned on SOAP envelopes or RPC-style query parameters that did not align with how HTTP caches, proxies, and browsers already behaved. REST reused that infrastructure and gave integrators a shared mental model: resources are addressable, methods express intent, and representations are negotiable.

A uniform interface shortens onboarding for new consumers. Someone who has integrated one well-designed HTTP API can usually infer that listing a collection uses GET on a plural path and that removing an item uses DELETE on the item URI—reducing bespoke client logic compared with opaque RPC names.

When to use

  • You expose a public or partner API where consumers expect conventional HTTP semantics and tooling.
  • Browser, mobile, or CDN clients benefit from standard caching headers and conditional GET behavior.
  • The domain is naturally resource-oriented—accounts, orders, assets—with CRUD-style lifecycles.
  • You need the broadest language and runtime interoperability via any HTTP client library.
  • You plan to publish an OpenAPI contract for documentation, mocks, and generated SDKs.

When not to use

  • Low-latency streaming. WebSockets or Server-Sent Events fit push and live feeds better than polling collections.
  • Dense internal RPC. gRPC and binary payloads reduce overhead when both ends are under your control.
  • Arbitrary client-shaped queries. GraphQL or dedicated query endpoints reduce over-fetching when UIs need many optional field combinations.
  • Fire-and-forget workflows. Message queues and event buses decouple producers from consumers without synchronous HTTP chains.

Typical architecture

Clients call a gateway or edge that authenticates and routes to stateless services; responses carry resource representations and cache validators so intermediaries and clients can avoid redundant downloads.

Pros and cons

Pros

  • HTTP caches, CDNs, and reverse proxies understand GET safety and cache headers without custom plugins.
  • Every mainstream language ships an HTTP stack, so client integration stays portable.
  • Stateless handlers simplify horizontal scale because any instance can serve any request.
  • Method and status semantics are widely documented in RFCs and platform style guides.
  • OpenAPI provides a single contract for docs, mocks, SDK generation, and contract tests.
  • Predictable URI and verb conventions lower cognitive load for new integrators.

Cons

  • Fixed resource shapes often over- or under-fetch compared with client-specific queries.
  • Filtering, sorting, and inclusion rules become ad hoc conventions unless you standardize them.
  • Breaking evolution requires explicit versioning and migration discipline.
  • Deep object graphs can force chatty N+1 HTTP sequences without batch or embed strategies.
  • JSON text payloads are larger than compact binary RPC encodings.
  • Legacy HTTP/1.1 deployments still exist; HTTP/2 and HTTP/3 reduce but do not eliminate coupling to transport choices.

Implementation notes

Resource naming

Use plural nouns for collections (/orders, /users). Avoid verbs in paths (/getOrder signals RPC, not resources). Prefer lowercase paths, hyphens for multi-word segments (/line-items), and shallow hierarchies that reflect real containment—typically at most two levels of nesting.

Status codes

Status codes are part of the contract; middleware, monitors, and clients route retries and UX from them. Align common outcomes with these defaults:

  • 200 OK indicates a successful read or update that returns a body.
  • 201 Created follows a successful create; include a Location header for the new resource.
  • 204 No Content marks success with no body, typical for DELETE or some PATCH operations.
  • 400 Bad Request signals malformed syntax; return a structured problem body.
  • 401 Unauthorized means authentication failed or is missing.
  • 403 Forbidden means the caller is authenticated but not permitted.
  • 404 Not Found means the targeted resource does not exist (or is not visible to the caller).
  • 409 Conflict covers version collisions, duplicates, or state conflicts.
  • 422 Unprocessable Entity means well-formed input that fails domain validation.
  • 429 Too Many Requests signals rate limiting; include retry guidance when possible.

Versioning strategies

URL path versioning (/v1/orders) is visible, easy to route at gateways, and simple to test. Reserve it for incompatible major changes. Accept header versioning (Accept: application/vnd.example.v2+json) keeps paths stable but is harder to exercise in a browser address bar. Query parameter versioning is easy to add but clutters URLs and may interact badly with caches—use sparingly. See API Versioning for sunset and migration patterns.

Pagination

Offset/limit is straightforward but unstable when rows are inserted or deleted during traversal. Cursor-based pagination encodes position in an opaque token so pages stay consistent under churn. Expose continuation via a next field or Link header per RFC 8288. Prefer cursors for large or frequently mutating collections.

Partial responses

A fields (or sparse fieldset) parameter lets clients request subsets: GET /users/42?fields=id,name,email. Document allowed fields in OpenAPI so generators and validators stay aligned.

Conditional requests

Emit an ETag (or Last-Modified) on cacheable GET responses. Clients send If-None-Match to receive 304 Not Modified when nothing changed. For writes, require If-Match against the current ETag and return 412 Precondition Failed when the resource moved underneath the client.

Error bodies

Standardize errors on RFC 9457 Problem Details so clients parse type, title, status, and optional field-level extensions consistently:

{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "The 'email' field must be a valid address.",
  "instance": "/orders/attempt-7e2a",
  "errors": [
    { "field": "email", "message": "Invalid format" }
  ]
}

Common failure modes

  • Verb tunneling via POST. Paths such as POST /users/42/delete hide DELETE semantics from caches and intermediaries.
  • Success status on failures. Returning 200 with {"success": false} breaks monitors, retries, and client libraries that trust HTTP status.
  • Mixed naming styles. Alternating userId, user_id, and UserID forces bespoke mapping in every SDK.
  • Unpaginated collections. Dumping full tables balloons memory on servers and clients as data grows.
  • Retry-sensitive POST. Creating resources without idempotency keys duplicates rows when clients retry after timeouts.
  • Silent contract breaks. Removing or retyping response fields without a new version strand consumers on old builds.
  • Chatty composition. Screens that require many sequential GETs punish high-latency mobile networks unless you offer aggregates or embeds.

Decision checklist

  • Do collection paths use plural nouns and avoid verb segments?
  • Are GET requests safe and PUT/DELETE (and designed PATCH) idempotent?
  • Does each outcome map to an appropriate status code—not only 200 and 500?
  • Do errors return RFC 9457 (or equivalent) bodies with actionable field detail?
  • Is there a documented versioning and sunset path for breaking changes?
  • Are large lists paginated with stable cursors where data changes during reads?
  • Do cacheable GET responses include ETag or Last-Modified validators?
  • Is the OpenAPI description the contract of record and checked in CI?
  • Do create and payment-style POST operations accept idempotency keys?
  • Can clients trim large resources via a documented sparse field parameter?

Example use cases

  • E-commerce platform — GET /v1/products?category=shoes&sort=-price&cursor=eyJpZCI6MTAwfQ returns a stable, sorted page of products with a cursor for the next page.
  • Payment API — POST /v1/payments with an Idempotency-Key: uuid header ensures a network retry does not charge a customer twice.
  • User management service — PATCH /v1/users/42 with a JSON Merge Patch body updates only the supplied fields; If-Match prevents concurrent overwrites.
  • Content delivery API — ETags on GET /v1/articles/slug let CDN edges and browser caches serve stale content and only revalidate when the article changes.
