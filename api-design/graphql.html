GraphQL

GraphQL query language, schema, resolvers, and operations (query, mutation, subscription)—with batching, federation, persisted queries, and production guardrails aligned to graphql.org.

⏱ 16 min read

What it is

GraphQL is a query language for APIs and a runtime that executes those queries against a type system. Clients send a single request—usually POST /graphql with a JSON body containing query and optional variables—and the server returns JSON shaped like the query tree. The public contract is the schema, typically written in Schema Definition Language (SDL): object types, fields, arguments, and the three root operation kinds defined in the GraphQL specification: Query (reads), Mutation (writes), and Subscription (push updates, usually over WebSockets).

Unlike REST, where each URL returns a fixed representation, GraphQL lets the caller name exactly which fields to resolve—including nested objects—so one round trip can assemble a screen-sized graph. The server walks the query tree and invokes a resolver per field to fetch data from databases, other services, or caches.

# Schema (SDL) — illustrative fragment
type User {
  id: ID!
  name: String!
  orders(first: Int, after: String): OrderConnection!
}

type Query {
  user(id: ID!): User
}

type Mutation {
  createOrder(input: CreateOrderInput!): Order!
}

type Subscription {
  orderStatusChanged(orderId: ID!): Order!
}

Why it exists

Mobile and web clients often need different field sets from the same domain model. Classic REST tends to over-fetch (fixed JSON blobs with unused fields) or under-fetch (many sequential calls to stitch a view). GraphQL inverts the coupling: the schema stays stable while product teams change queries when UIs evolve, without requesting a new endpoint for every layout tweak.

The trade-off is operational: resolver trees can hide N+1 database access, caching is harder than cacheable GET URLs, and expressive queries need depth and cost guards. Teams adopt GraphQL when client flexibility and a typed contract matter more than leaning on HTTP caching conventions.

Subscriptions push server-initiated events over WebSockets or similar transports; they share the same schema types as queries but require connection-scoped auth, heartbeat handling, and backpressure when subscribers lag. Many teams keep writes on mutations and reserve subscriptions for narrow notification surfaces rather than full graph replication.

The GraphQL specification separates transport from query execution—HTTP POST remains the default for queries and mutations, while gateways may front subgraphs with federation routers. Teams evaluating GraphQL should budget schema governance and perf tooling as first-class platform work, not as an afterthought once mobile screens ship.

When to use

  • Several client surfaces (web, mobile, partners) with different data shapes over the same backend.
  • Aggregation layers (BFFs, experience APIs) that compose multiple services into one typed graph.
  • Developer-facing APIs where introspection and schema-first tooling improve integration speed.
  • Dashboards or detail views that need nested, related entities in a single request.

CRUD resources with stable shapes and many cache-friendly GET clients are often simpler in REST with OpenAPI than maintaining a graph layer solely for field selection.

When not to use

  • Simple CRUD with one client type—schema and resolver machinery may outweigh benefit.
  • Heavy binary or multipart upload/download—REST or gRPC usually fit better.
  • Internal high-throughput RPC where binary codecs and streaming matter (gRPC).
  • Edge/CDN HTTP caching as the primary performance strategy without persisted queries or GET support.
  • Teams unwilling to invest in query limits, DataLoader-style batching, and schema governance.

Typical architecture

The gateway or client posts a document; the engine validates against the schema, executes resolvers depth-first, and batches relationship loads where batching helpers are wired.

Pros and cons

Pros

  • Clients request precise field sets—less over-fetching and fewer chatty round trips.
  • Strong schema is documentation, validation, and codegen input in one artifact.
  • Introspection enables GraphiQL, IDE plugins, and client generation when policy allows.
  • Additive schema changes are the default; deprecations give consumers a migration path.
  • Federation (e.g. Apollo Router, Cosmo) scales ownership across service teams.

Cons

  • Naive resolvers cause N+1 I/O; batching (DataLoader) must be deliberate.
  • POST-heavy traffic resists generic HTTP caching without persisted queries or field-level cache hints.
  • Arbitrary query depth can stress backends—depth, cost, and timeout limits are required.
  • Errors may return HTTP 200 with an errors array and partial data—monitoring must account for that.
  • Schema design mistakes are expensive to unwind across many clients.

Implementation notes

Resolvers and execution

Resolvers receive (parent, args, context, info) and return a value or Promise for each field. Keep them thin: authorize in middleware or root fields, fetch in repositories, and avoid business rules duplicated across sibling fields. The execution engine runs resolvers in an order consistent with the query shape—plan for parallel sibling fields where your runtime supports it.

N+1 and DataLoader

Listing 100 parents each resolving a child collection can become 101 database round trips. DataLoader collects keys per tick (or per request frame) and issues one batched query, then maps rows back to resolvers. Instantiate loaders per request so cached batches never leak across users.

Persisted queries and transport

Automatic Persisted Queries send a hash instead of the full document after registration—smaller bodies, optional GET for reads, and production allowlists. Pair with variables validated against input types in SDL.

Federation vs manual stitching

Manual stitching merged schemas at a gateway with hand-written delegation. Federation marks entities with @key in subgraphs; the router builds query plans across services. Prefer federation when many teams own slices of one product graph.

Operational runbooks should include query-plan regression tests after subgraph deploys: a new resolver latency spike often appears only when a specific fragment fans out across three services at once.

Caching and security

Strategies: persisted GET queries at the CDN, server-side response cache keyed by operation + variables, and client normalized stores (Apollo Client, Relay). Disable or restrict introspection in production; enforce authentication on sensitive root fields; cap query depth and estimated cost. See GraphQL security notes.

Schema registry and governance

Large organisations treat the schema as a published contract: lint rules in CI, breaking-change detection on pull requests, and optional registry approval before subgraphs deploy. Federation routers add composition checks—conflicting types or missing @key fields fail fast in the pipeline instead of at runtime when the first client query spans services.

Query cost and depth limits

The GraphQL specification does not cap query cost—servers must enforce depth (often 10–15), field count, and complexity scores before execution. Persisted queries (APQ) shrink attack surface and CDN cache keys. Reject introspection or throttle it in production; attackers use introspection to craft expensive trees. Document maximum first connection sizes (50–100) consistent with database page limits. Federation adds N+1 risk across subgraphs—DataLoader batching and subgraph query plans should appear in load tests, not only happy-path UI queries.

Errors and observability

Return partial data with errors arrays per spec rules; log resolver-level failures with correlation IDs without leaking internal paths in extensions. Track p95 resolution time per root field—one hot field dominating latency usually means a missing DataLoader or an unindexed subgraph resolver.

Mutations should return affected entity ids and expected state clients need for cache updates—under-fetching mutation payloads forces extra round trips that defeat GraphQL’s purpose. Subscription transports (WebSocket or SSE) need separate auth and idle timeouts documented beside query endpoints.

Federation trace metrics expose which subgraph dominates latency; alert when a single subgraph’s error rate correlates with composed query failures.

Common failure modes

  • Unbatched relations — list screens trigger one query per row.
  • Unbounded queries — deeply nested fragments exhaust CPU or database pools.
  • Breaking removals — deleting fields without @deprecated breaks shipping clients.
  • Error leakage — stack traces in extensions expose internals.
  • God Query type — hundreds of root fields with no domain grouping or federation boundaries.
  • Shared DataLoader singletons — cross-request cache bleed and wrong authorization context.

Decision checklist

  • Is batching in place for every list→detail relationship?
  • Are depth, cost, and timeout limits configured and tested?
  • Is introspection limited in production?
  • Are persisted queries (or equivalent allowlists) used for external clients?
  • Is there a deprecation policy before field removal?
  • Do alerts treat GraphQL errors separately from HTTP status?
  • For multi-team graphs, is federation (or a clear monolith boundary) documented?
  • Are loaders and auth context scoped per request?

Example use cases

  • Case study — GitHub’s GraphQL API v4 lets integrators fetch repository, issue, and label fields in one operation instead of chaining REST resources.
  • Case study — Shopify Storefront API serves storefronts with nested product, variant, and inventory fields in a single query over checkout-scale traffic.
  • Illustrative scenario — Meridian Commerce runs a mobile checkout BFF whose GraphQL Cart type resolves pricing, inventory, and promotions from three microservices; product can add a field to the query without new REST endpoints.
  • Illustrative scenario — A platform team operates a federated supergraph: payments, orders, and catalog each publish a subgraph while a router enforces auth and query cost limits at the edge.
