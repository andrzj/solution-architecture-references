API Design

HATEOAS

Hypermedia as the Engine of Application State — the highest level of REST maturity, where API responses include links to valid next actions, decoupling clients from hardcoded URL templates and enabling server-driven navigation through the _links object, HAL, JSON:API, and Siren formats.

⏱ 11 min read

What it is

HATEOAS (Hypermedia as the Engine of Application State) is a REST constraint: the server tells the client which transitions are available by embedding links (and sometimes action metadata) in representations, so the client starts from a known entry point and discovers URLs at runtime instead of hard-coding paths from documentation.

Practical APIs express affordances via _links, JSON:API links, or Siren actions. Each response advertises related resources and permitted next steps—such as paginate, cancel, or approve—so navigation reflects current server state.

In Richardson’s Maturity Model, hypermedia-driven discovery is Level 3, above resource-oriented HTTP verbs (Level 1) and consistent URI modeling (Level 2).

Why it exists

When clients assemble URLs from static templates, any path or relationship rename breaks them. Hypermedia shifts URI knowledge to the server: responses carry the current href for collections, items, and state-specific actions. The API can deprecate paths, gate actions by state, and omit invalid transitions without every consumer redeploying.

Link relation types from RFC 8288 give integrators a vocabulary independent of URL shape—clients discover next without knowing whether the server paginates with query parameters or path segments. That decoupling is the practical win most teams adopt even when they skip full state-machine payloads on every resource.

When to use

  • Public APIs with independently deployed clients that cannot upgrade in lockstep with the server.
  • Generic automation or explorer clients that crawl from a single entry URL without bespoke routing tables.
  • Workflow APIs where valid actions depend on state and you want the representation to advertise only permitted transitions.
  • Long-horizon partner integrations where URI stability is negotiated through links rather than static SDK paths.

SDK-first partner programs with semver-guaranteed OpenAPI paths rarely earn ROI from full hypermedia discovery on every resource representation.

When not to use

  • Co-deployed internal services where you control every client release and OpenAPI already documents stable paths.
  • Mobile or SPA clients generated from OpenAPI that call fixed operation IDs instead of traversing links dynamically.
  • Latency- or payload-sensitive APIs where extra link metadata and follow-up GETs measurably hurt SLAs.

Typical architecture

The client loads an entry resource, follows typed links to collections and items, and invokes actions only when the server includes the corresponding link for the current state.

Hypermedia formats

HAL (Hypertext Application Language)

GET /orders/42
{
  "id": "42",
  "status": "confirmed",
  "total": 149.99,
  "_links": {
    "self":    { "href": "/orders/42" },
    "cancel":  { "href": "/orders/42/cancellations", "method": "POST" },
    "invoice": { "href": "/orders/42/invoice" },
    "customer":{ "href": "/customers/7" }
  },
  "_embedded": {
    "items": [
      {
        "productId": "sku-101",
        "quantity": 2,
        "_links": {
          "product": { "href": "/products/sku-101" }
        }
      }
    ]
  }
}

HAL (application/hal+json) adds _links (navigation) and _embedded (pre-fetched related resources) to a plain JSON object. It's the most widely adopted HATEOAS format.

JSON:API

GET /articles/1
{
  "data": {
    "type": "articles",
    "id": "1",
    "attributes": { "title": "Building APIs", "body": "..." },
    "relationships": {
      "author": {
        "links": { "related": "/articles/1/author" },
        "data": { "type": "people", "id": "9" }
      }
    },
    "links": { "self": "/articles/1" }
  },
  "included": [
    { "type": "people", "id": "9", "attributes": { "name": "Jane" } }
  ]
}

JSON:API (application/vnd.api+json) is more opinionated: it standardises resource structure, relationships, compound documents (included), filtering, sorting, and pagination query parameters. Good for document-oriented APIs with rich relationships.

Siren

{
  "class": ["order"],
  "properties": { "id": "42", "status": "confirmed" },
  "entities": [
    {
      "rel": ["items"],
      "href": "/orders/42/items"
    }
  ],
  "actions": [
    {
      "name": "cancel-order",
      "href": "/orders/42/cancellations",
      "method": "POST",
      "fields": [{ "name": "reason", "type": "text" }]
    }
  ],
  "links": [
    { "rel": ["self"], "href": "/orders/42" }
  ]
}

Siren adds actions — structured form-like descriptions of non-safe transitions including the method, fields, and encoding type. More expressive than HAL for APIs with complex write operations.

Pros and cons

Pros

  • Servers can rename or relocate resources when clients follow server-issued hrefs.
  • State-gated links expose only valid actions, reducing duplicate workflow logic in UIs.
  • Entry-point discovery lets generic tools explore capabilities without a static route map.
  • Pagination and related resources can be advertised without encoding URL templates in clients.

Cons

  • Most OpenAPI-generated clients ignore links and call predetermined paths.
  • Link objects add bytes to every response and can multiply on large list endpoints.
  • Correct link generation requires centralized knowledge of base URLs, states, and transitions.
  • Competing formats (HAL, JSON:API, Siren) fragment tooling and learning curves.
  • GraphQL introspection and static contracts solve discoverability for many teams without hypermedia.

Implementation notes

Practical minimum: always include self links

At minimum, return a self link (or JSON:API equivalent) on every resource so clients never guess canonical URLs from bare identifiers.

State-conditional links

Emit action links only when the transition is valid—for example, omit cancel when an order is no longer cancellable. Document the state machine alongside link relation names so integrators know which links appear in which states.

Link relations

Prefer IANA-registered relation names (self, next, prev, collection, item). For domain-specific relations, use URIs as registered in RFC 8288.

Pagination with Link header

Collections can expose next and prev in the HTTP Link header so pagination stays out of the JSON body. The pattern is common on large public Git APIs:

Link: <https://api.github.com/repos/octocat/hello-world/commits?page=2>; rel="next",
      <https://api.github.com/repos/octocat/hello-world/commits?page=34>; rel="last"

Why most REST APIs skip HATEOAS

Many widely used HTTP APIs document stable paths in OpenAPI and ship typed SDKs instead of expecting runtime link traversal. That trade accepts tighter URI coupling in exchange for simpler clients and smaller payloads. Teams still borrow hypermedia ideas—self links, state-gated actions, Link pagination—without adopting a full Level 3 media type everywhere.

Richardson maturity and Fielding constraints

The Richardson Maturity Model ranks APIs from Level 0 (single URI RPC) through Level 3 (hypermedia controls). Fielding’s dissertation describes REST as constraints—statelessness, uniform interface, cacheability—not as mandatory HAL payloads. Most production “REST” APIs sit at Level 2 (HTTP verbs + resources) and add selective Level 3 affordances where mobile clients benefit from state-gated actions. Choosing HAL, JSON:API, or Siren commits teams to one link object shape; mixing formats across resources breaks generic clients.

When not to invest in full HATEOAS

Public B2B APIs with generated SDKs and stable OpenAPI rarely justify navigation discovery—the integrator never executes runtime link following. Invest hypermedia effort where the server owns workflow rules that change frequently (approvals, provisioning) and clients must not hard-code transition URLs. For pagination alone, RFC 8288 Link headers often suffice without embedding _links on every row.

Hypermedia clients should resolve href through the same gateway base URL configuration as OpenAPI servers—hard-coded host overrides in link generation break when environments move behind new domains.

Version custom link relation types in developer docs; renaming rel values is as breaking as renaming JSON fields for hypermedia consumers.

Common failure modes

  • Broken relative links. Relative hrefs fail when gateways rewrite base paths unless the server emits absolute URLs from configuration.
  • Stale affordances. Action links that outlive valid state produce 409 responses and erode trust in hypermedia.
  • Ignored links. Investment in rich _links blocks yields little when every consumer uses hard-coded OpenAPI operations.
  • List payload bloat. Repeating full link sets on every row in large collections inflates bandwidth and parse cost.

Decision checklist

  • Does every resource representation include at least a canonical self link?
  • Are action links generated only when the server state machine allows the transition?
  • Is one hypermedia profile (HAL, JSON:API, Siren) chosen and applied consistently?
  • Are standard and custom link relation types documented for integrators?
  • Do paginated collections advertise next and prev in the body, Link header, or both?

Example use cases

  • Illustrative scenario — Northwind partner TMS: Third-party clients follow _links in JSON responses so URL layout can change without republishing static integration guides.
  • Illustrative scenario — Meridian order workflow: An order resource exposes only valid transitions (approve, reject, cancel) in its link relation set based on current state.
  • Case study — PayPal REST hypermedia: PayPal’s REST design documents discoverable HATEOAS links for follow-on calls instead of hard-coded URLs in client code.
