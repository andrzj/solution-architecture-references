API Design Essential

API Gateway

The edge entry point for APIs — TLS, JWT and scope enforcement, routing, rate limits, and how gateways complement service meshes and BFFs.

⏱ 14 min read

What it is

An API gateway is the controlled entry point for north-south API traffic. It terminates TLS, authenticates callers, enforces coarse authorization and rate limits, routes requests to upstream services, and injects observability context—without exposing internal hostnames, ports, or topology to clients.

Gateways implement a cross-cutting pipeline (authn/authz, throttling, WAF, protocol translation, request/response transformation) described in microservices literature and cloud reference architectures. They complement service meshes (east-west mTLS and policy) and optional BFFs (client-specific aggregation behind the gateway).

Implementations range from self-managed Kong or Envoy Gateway to managed AWS API Gateway, Azure API Management, and Kubernetes Gateway API resources—same pattern, different operational models.

Gateways also terminate long-lived connections—WebSockets, server-sent events, and gRPC streams—where naive reverse proxies buffer incorrectly or drop HTTP/2 flow-control signals. Choosing an L7 implementation that understands streaming semantics prevents subtle production failures that unit tests on JSON REST never catch.

Why it exists

Without a gateway, every service would duplicate JWT validation, quota enforcement, TLS configuration, and trace header propagation—leading to inconsistent security and painful audits. A gateway gives platform teams one place to apply organisation-wide policy while product teams focus on domain code.

Clients need a stable external URL and contract even when services split, merge, or move behind gRPC. The gateway abstracts churn and can translate protocols (HTTP/JSON at the edge, gRPC inside) or route API versions to different upstream clusters.

Security operations teams also gain a choke point for bot scoring, geo policy, and emergency kill switches—without redeploying every microservice when a partner key is compromised or a route must be quarantined during an investigation.

When to use

  • Multiple backend services exposed as one product API surface.
  • Partner, mobile, or public APIs requiring centralized OAuth scope enforcement and rate tiers.
  • Canary, blue/green, or percentage-based routing to new service versions.
  • TLS termination, WAF, and DDoS protection at the perimeter.
  • REST or HTTP front-ends to internal gRPC, WebSocket, or queue-driven workers.

When not to use

  • Single monolith with no external consumers—gateway hop adds latency without benefit.
  • Pure internal service-to-service traffic—use mesh sidecars instead of an edge gateway.
  • When the team lacks automation for gateway config—manual UI drift becomes outages.

Typical architecture

Internet clients hit a highly available gateway cluster; the pipeline validates bearer tokens, applies quotas, routes by path, and forwards trusted identity to stateless upstreams. Mesh handles service-to-service identity inside the cluster.

Pros and cons

Pros

  • Uniform OAuth/JWT validation and rate limits across all routes.
  • Stable public API while internal topology evolves.
  • Central TLS and certificate management.
  • Traffic management for canaries and incident isolation.
  • Frees domain services from perimeter concerns.

Cons

  • HA gateways are mandatory—otherwise a single chokepoint outage drops all APIs.
  • Extra latency hop and plugin CPU cost per request.
  • Risk of “fat gateway” anti-pattern with business logic in plugins.
  • Managed gateways can create vendor lock-in for policies and analytics.
  • Config sprawl without GitOps, declarative sync, or review workflows.

Implementation notes

Authentication patterns at the edge

Validate JWTs against issuer JWKS (RFC 6750 bearer). Enforce exp, iss, aud, and required scopes before routing. Options: pass-through (forward bearer token), token exchange (RFC 8693) to mint a downstream token, or terminate and inject trusted headers (X-User-Id) that backends accept only from the gateway network path. Never forward unverified claims.

Authorization boundary

Gateway enforces route-level scopes and optional role presence; services enforce ownership and field rules (see API Authorization). Document the split in platform runbooks.

Rate limiting and resilience

Apply per-consumer and per-route quotas (see API Rate Limiting). Configure upstream timeouts, retry limits (only for idempotent routes), and circuit breakers per route. Return RFC 9457 problem details on gateway-generated errors.

Request transformation and protocol bridging

Gateways can rewrite paths, inject standard headers, strip dangerous query parameters, and map external JSON to internal gRPC via transcoding filters. Keep transformations declarative and reviewed like routing rules—opaque Lua that encodes business rules becomes undeployed debt. Validate transformed bodies against the upstream OpenAPI contract in CI where possible.

Gateway deployment patterns

  • Central edge cluster — Kong/Envoy behind global load balancer; good for multi-region public APIs.
  • Managed serverless — AWS API Gateway + Lambda or HTTP integrations; minimal ops, AWS-centric auth (IAM, Cognito).
  • Kubernetes Gateway API — portable HTTPRoute, GatewayClass; pairs with Envoy Gateway or Istio ingress.
  • Two-layer — CDN/WAF edge + in-cluster ingress gateway for defence in depth.

Mesh and BFF coexistence

Use the gateway for external clients; mesh for internal mTLS and L7 policy between services. Place BFFs behind the gateway when mobile and web need different aggregates—the gateway still handles auth and quotas; BFFs stay thin orchestrators.

Observability at the edge

Gateway access logs are often the only complete record of north-south traffic: client IP, route, consumer identity, latency, and upstream status. Propagate W3C traceparent on every hop and avoid stripping client-supplied correlation IDs unless they fail validation. Per-route RED metrics (rate, errors, duration) on the gateway surface SLOs that domain services alone cannot compute, because they never see failed auth or throttled requests.

Common failure modes

  • Unverified JWT pass-through — backends trust forged bearer tokens.
  • Business logic in plugins — untested Lua/Wasm becomes a hidden monolith.
  • Single gateway instance — no autoscaling or health-checked pool.
  • UI-only admin protection — privileged routes reachable through the gateway without scope checks.
  • Config not in Git — drifts across environments; rollback is manual.

Decision checklist

  • Is the gateway deployed in HA with health-checked load balancing?
  • Is configuration declarative (Terraform, Kong deck, Gateway API YAML) and reviewed in PRs?
  • Does the edge verify JWT signatures and scopes before upstream routing?
  • Are rate limits keyed on authenticated identity, not only IP?
  • Are trace/correlation IDs injected on every request?
  • Are upstream timeouts and circuit breakers set per route?
  • Is business logic absent from gateway plugins?
  • Is the split with service-mesh east-west policy documented?

Example use cases

  • Illustrative scenario — Meridian Commerce runs Kong on Kubernetes: OAuth2 plugin validates JWTs from its OIDC provider, enforces catalog:read on product routes, and rate-limits by client_id before traffic reaches the catalog microservice.
  • Illustrative scenario — RideRelay places an Envoy Gateway in front of mobile and driver BFFs; the gateway terminates TLS and attaches trace headers while BFFs aggregate trip and payment APIs.
  • Case study — Netflix’s Zuul (historical) and later edge proxies centralised auth and routing for device APIs—pattern now common across Envoy-based edges.
  • Case study — Kubernetes Gateway API standardises ingress routing (HTTPRoute, reference grants) so teams swap controller implementations without rewriting route definitions.

Related patterns

  • Backend for Frontend (BFF) — client-specific APIs behind the gateway.
  • API Authentication — token validation at the perimeter.
  • API Rate Limiting — quotas enforced in the gateway pipeline.
  • API Versioning — path-based routing to versioned upstreams.
