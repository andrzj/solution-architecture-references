API Design

API Filtering and Sorting

REST collection filtering and sorting conventions—allowlists, operator notations, sparse fieldsets, security, and OpenAPI documentation.

⏱ 11 min read

What it is

API filtering and sorting are conventions for narrowing and ordering collection responses over HTTP—typically query parameters on GET /resources. Clients express predicates (status equals, created after, amount between bounds) and sort keys without bespoke “search” endpoints for every screen. Unlike pagination, there is no single global standard; teams pick a notation (simple equality, bracket operators, FIQL, or POSTed DSL) and document it in OpenAPI.

The server maps allowed parameters to indexed database predicates, applies authorization scope regardless of what the client sends, and returns a stable sort order—usually with a unique tie-breaker field when paging cursor results.

Why it exists

Returning full tables does not scale and wastes bandwidth. Admins, mobile clients, and integrations need predictable ways to ask for “confirmed orders since Tuesday, newest first.” Shared conventions reduce integration time, keep caches meaningful (GET stays idempotent), and let DBAs index known filter combinations.

When to use

  • Collection endpoints that can grow large and expose tabular UIs or exports.
  • Operational dashboards filtering by status, tenant, or date range.
  • Mobile list views combining sparse fieldsets with sort and filter.

When not to use

  • Full-text relevance search—use a search index or dedicated search API.
  • Arbitrary boolean trees across dozens of fields—prefer POST /search with a validated DSL.
  • GraphQL APIs where arguments and connections express filters in the query language.

Typical architecture

Query strings pass through an allowlisted mapper; authorized scope is injected; SQL/ORM uses indexes for WHERE and ORDER BY.

Pros and cons

Pros

  • Declarative URLs—bookmarkable, cacheable GET semantics when safe.
  • Integrators learn one pattern across resources.
  • OpenAPI can describe enums, operators, and examples per field.
  • Works with CDNs and intermediaries that only cache GET.

Cons

  • Competing notations—pick one and stay consistent.
  • Complex AND/OR logic clutters URLs or hits length limits (~2 KB).
  • Every popular filter/sort pair pressures index design.
  • Easy to implement unsafely if strings reach SQL directly.

Implementation notes

Filtering notations, sorting, sparse fieldsets, security, and OpenAPI examples follow.

Filtering approaches

Simple equality

GET /orders?status=confirmed
GET /orders?customerId=42&status=pending

Map parameters to columns with an explicit allowlist; reject unknown keys with 400.

LHS bracket notation

GET /orders?total[gte]=100&total[lte]=500
GET /orders?status[in]=pending,confirmed

Operators live in brackets: eq, ne, gt, gte, lt, lte, in, like. Common in JSON:API-inspired APIs.

RHS colon notation

GET /orders?filter=total:gte:100,total:lte:500
GET /orders?total=gte:100

Compact for gateways; document delimiter rules carefully.

FIQL

GET /orders?q=status==confirmed;total=gt=100

Structured AND (;) / OR (,); needs a dedicated parser.

POST search body

When filters exceed URL limits, use POST /orders/search with a JSON DSL (see Elasticsearch Query DSL as a reference). Do not use GET bodies.

Sorting

GET /orders?sort=createdAt          # ascending
GET /orders?sort=-createdAt         # descending (leading minus)
GET /orders?sort=-createdAt,id      # multi-key, id tie-breaker

Allowlist sortable fields; index composite keys matching default sort + id.

Sparse fieldsets

GET /orders/42?fields=id,status,total,customer.name

Project columns in application code or ORM selects—never concatenate unvalidated field names into SQL. GraphQL makes selection structural; REST uses opt-in fields parameters (Google partial response pattern).

Security

  • Allowlist filter and sort fields; unknown parameters → 400.
  • Bind operators to types (no like on UUID columns).
  • Enforce tenant/customer scope server-side, ignoring client-supplied scope tricks.
  • Cap condition count and nesting depth to prevent expensive plans.

OpenAPI documentation

parameters:
  - name: status
    in: query
    schema:
      type: array
      items:
        enum: [pending, confirmed, shipped]
  - name: sort
    in: query
    description: Prefix with - for descending. Example sort=-createdAt,id
    schema:
      type: string

Query cost guardrails

Cap simultaneous filter predicates (commonly eight to sixteen), maximum sort keys (two or three), and default limit well below database page sizes. Reject queries that exceed caps with 400 and RFC 9457 problem details rather than running expensive plans—many teams add server-side statement timeouts (1–5 s on OLTP list routes) aligned with gateway upstream timeouts. Log slow-query fingerprints by normalized parameter pattern so DBAs add composite indexes on hot status + created_at sorts rather than chasing ad hoc integrator strings.

Standards positioning

OData and FIQL offer portable filter grammars when partners expect them; most custom REST APIs instead document bracket or colon notation in OpenAPI and mirror Google AIP list filter patterns (filter query strings with documented operators). Microsoft’s guidelines recommend explicit $filter-style parameters only when the product commits to OData semantics end to end—half-implemented OData frustrates clients more than a small, documented allowlist. When filters approach URL length limits (~2 KB), shift to POST …/search with a JSON body validated against the same OpenAPI schema extensions you would use for query params.

Failure detection

Rising p95 latency on collection GETs with flat traffic often means a new filter combination missed an index. Sudden growth in 400 responses after deploy may indicate tightened allowlists without changelog notice. Compare explain plans in staging for top ten documented filter examples before major releases—silent full-table scans are the dominant failure mode behind “API got slow” tickets.

Document default sort orders in OpenAPI descriptions so integrators do not rely on undefined ordering—unstable sorts break cursor pagination that encodes the last seen sort key.

Common failure modes

  • SQL injection — dynamic sort/filter strings concatenated into queries.
  • Missing indexes — hot filters scan entire tables.
  • Silent ignores — typos in parameter names return unfiltered data.
  • Client-only scoping — trusting customerId query params without auth checks.

Decision checklist

  • Are filter and sort fields explicitly allowlisted?
  • Do indexes cover top filter + sort combinations?
  • Is one notation used consistently and documented in OpenAPI?
  • Are invalid parameters rejected with clear errors?
  • Is authorization scope applied independent of query strings?
  • Do complex queries use POST search instead of oversized GET URLs?

Example use cases

  • Illustrative scenario — Operations uses GET /orders?status=shipped&sort=-createdAt on a dashboard backed by a composite index on (status, created_at, id).
  • Illustrative scenario — Meridian Commerce mobile catalog calls GET /products?fields=id,name,price&sort=-popularity to keep list payloads under a size budget.
  • Illustrative scenario — A partner integration posts to POST /orders/search when filter JSON exceeds URL limits during month-end reconciliation.
