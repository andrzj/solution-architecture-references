API Design

API Versioning

Strategies and conventions for evolving APIs without breaking existing consumers — covering URL path versioning, header versioning, semantic versioning for APIs, deprecation lifecycle, the Sunset header, and the distinction between breaking and non-breaking changes.

⏱ 12 min read

What it is

API versioning is how you evolve an HTTP API’s contract without stranding existing clients. Published endpoints promise specific paths, fields, and behaviors; versioning introduces parallel contracts—or explicit negotiation—so old integrations keep working while new ones adopt improved shapes.

Common mechanisms differ in visibility and routing:

  • URL path versioning embeds major revisions in the path, for example /v1/orders and /v2/orders.
  • Header versioning selects representation via Accept vendor media types or custom headers such as API-Version.
  • Query parameter versioning adds a version flag to the query string, for example ?version=2.
  • Date-based pinning fixes each consumer to an API behavior snapshot identified by a calendar date header.

Versioning is a product commitment: each supported variant needs security patches, documentation, test matrices, and on-call playbooks. Treat concurrent versions like concurrent deployments—capacity planning must include traffic to legacy paths until sunset metrics hit zero.

Why it exists

Shipping a breaking change to an unversioned API forces every client to update immediately—unrealistic for mobile installs, partner batch jobs, and third-party plugins. Versioning keeps prior behaviors available while you publish migration guidance and sunset timelines.

Effective practice balances producer velocity with consumer stability: prefer additive, backward-compatible changes; reserve new major versions for true incompatibilities; and communicate deprecation with machine-readable headers.

Contract tests and OpenAPI diff tools catch accidental breaking edits before release, but they cannot judge semantic shifts—when a field’s meaning changes while the type stays the same. Human changelog review and pilot consumers on release candidates remain essential for high-stakes platforms.

When to use

  • External or partner APIs where you cannot redeploy every consumer when the server changes.
  • Shared internal platforms consumed by many teams on independent release trains.
  • Long-lived product APIs whose models and authorization rules will evolve over years.

When not to use

  • In-process or monolith calls deployed atomically with the callee—version the module, not the wire format.
  • Short experiments explicitly marked unstable with a published end date before the design settles.

Typical architecture

Gateways route version selectors to the correct handler or adapter; deprecated routes return Deprecation, Sunset, and Link headers until they respond with 410 Gone.

Pros and cons

Pros

  • Path versions are obvious in logs, easy to route at gateways, and simple to test with curl.
  • Header negotiation keeps URLs stable while still allowing multiple representations.
  • Date pinning gives each integrator a frozen behavior snapshot that audits cleanly for regulated domains.
  • SemVer-style labeling clarifies whether a release is compatible or requires migration work.

Cons

  • Every active version duplicates handlers, tests, docs, and operational monitoring surface.
  • Header-only versions are easy to omit in ad hoc tests and invisible in browser trials.
  • Query versioning complicates caching and may be stripped by intermediaries.
  • Without enforced sunsets, old versions linger and compound security and support debt.
  • Consumer migration often takes longer than teams plan, extending parallel-version cost.

Implementation notes

Breaking vs non-breaking changes

Publish a written compatibility policy so reviewers classify diffs consistently.

Breaking changes (typically require a new major version or date):

  • Removing or renaming fields, endpoints, or parameters.
  • Changing a field’s type or documented meaning.
  • Introducing required request fields that old clients do not send.
  • Tightening authentication or authorization requirements.
  • Changing status codes or error envelopes that clients branch on.

Usually non-breaking when clients practice tolerant reading:

  • Adding optional response fields or optional request parameters.
  • Adding new routes or resource types without altering existing ones.
  • Adding enum values when clients treat unknown values as opaque.

Semantic versioning for APIs

Map release labels to MAJOR.MINOR.PATCH: incompatible contract changes bump MAJOR and usually map to a new path prefix; MINOR adds compatible capability; PATCH fixes behavior without breaking documented contracts. Many public HTTP APIs expose only MAJOR in the URL and record MINOR additions in changelogs.

Date-based versioning (Stripe model)

With date pinning, each account stores an API version date; the server applies forward and reverse transforms between that snapshot and the internal canonical model. The approach preserves integrator expectations across years but demands a maintained matrix of transforms for every breaking change.

Sunset header (RFC 8594)

Return Sunset on deprecated routes so automation knows the retirement instant. Combine with Deprecation (see RFC 9745) and a Link relation to migration docs. After the sunset time, respond with 410 Gone instead of silent failures.

Versioning at the gateway

Route /v1/* and /v2/* to distinct upstream clusters or adapters during migration. Feature flags inside one codebase can serve multiple behaviors when operational cost of separate deployments is too high—document which header or path selects each behavior.

Migration telemetry

Instrument middleware to tag each request with resolved API version and consumer identity. Dashboards should show week-over-week traffic share per version, error-rate divergence between versions, and top partners still on deprecated paths. Automated emails or developer-portal banners triggered at thresholds (for example 90 days before sunset) reduce surprise hard cutovers.

Common failure modes

  • Unversioned launch. Shipping /orders without a version prefix makes later segmentation a breaking announcement to every consumer.
  • Perpetual deprecation. Old versions stay up because nobody tracks remaining traffic or enforces sunset dates.
  • False compatibility. Strict client parsers treat new required response fields or renamed properties as hard failures.
  • Version explosion. Per-endpoint version numbers confuse partners and dilute testing coverage.
  • Migration vacuum. Releasing v2 without a diff guide and timelines stalls adoption and extends dual-operation cost.

Decision checklist

  • Is the versioning mechanism chosen and documented before the first public release?
  • Does the team share a written definition of breaking versus additive change?
  • Do deprecated routes emit Sunset, Deprecation, and migration Link headers?
  • Is there a published migration guide for every new major version or date bump?
  • Are dashboards or logs tracking traffic to deprecated versions?
  • Is there a policy cap on concurrent supported versions (for example current plus one previous)?
  • Are additive changes recorded in a changelog without forcing a version bump?
  • Does CI detect breaking OpenAPI or schema diffs before merge?

Example use cases

  • Case study — Stripe: Stripe uses date-based API versions so each account pins behaviour to the version active at integration time and can upgrade explicitly when ready.
  • Case study — GitHub REST: GitHub documents numbered major versions in the URL path (/v3/) and communicates breaking changes through release notes and sunset policies.
  • Illustrative scenario — Northwind data platform: /v1/ serves the stable contract while /v2/ runs in parallel; Sunset and Deprecation headers announce retirement before v1 is removed.

Related patterns

  • REST API Design — resource layout and compatibility discipline shape how you expose major versions.
  • OpenAPI Specification — publish a separate spec artifact per supported major version or pinned date.
  • Contract Testing — consumer tests in CI fail builds when producers ship incompatible JSON shapes.
  • API Gateway — path-based rules send /v1 and /v2 traffic to different upstream pools.
