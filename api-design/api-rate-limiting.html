API Design Scalability

API Rate Limiting

Quotas and fairness at the API edge — algorithms, standard headers, 429 with Retry-After, per-consumer limits, and gateway-backed counter stores.

⏱ 13 min read

What it is

API rate limiting caps how many requests a client may send in a time window, protecting upstream capacity, enforcing commercial tiers, and slowing abuse. Counters are keyed by identity (API key, OAuth client_id, user sub, or IP for unauthenticated routes) and evaluated before expensive work runs.

When a client exceeds quota, APIs return 429 Too Many Requests (RFC 6585) with Retry-After and machine-readable quota headers (IETF RateLimit fields, draft-ietf-httpapi-ratelimit-headers). Enforcement typically lives at the API gateway or a shared middleware tier backed by Redis or an edge counter store.

Why it exists

A single buggy retry loop or aggressive scraper can exhaust connection pools and CPU for all tenants. Rate limits convert unbounded demand into predictable load, support fair sharing on multi-tenant platforms, and complement authentication on login and token endpoints against credential stuffing.

When to use

  • Public or partner APIs with published quotas and billing tiers.
  • Authentication, password reset, and OTP endpoints.
  • Expensive operations—search, bulk export, report generation—with tighter per-route caps.
  • Multi-tenant SaaS where one tenant must not saturate shared pools.

When not to use

  • Trusted internal mesh RPC with mutual TLS and backpressure elsewhere—prefer queue admission or client-side throttling.
  • Per-IP limits as the only key on carrier-grade NAT without authenticated identity.
  • Latency-critical paths where a remote counter lookup per request is prohibitive without local token-bucket caching at the edge.

Typical architecture

The gateway increments distributed counters per consumer and route; under quota requests reach backends, over quota the gateway short-circuits with 429 and standard headers.

Pros and cons

Pros

  • Protects shared infrastructure from noisy neighbours.
  • Maps cleanly to product tiers and partner contracts.
  • Reduces brute-force and scraping effectiveness.
  • Token-bucket policies allow short bursts without raising sustained limits.

Cons

  • Distributed counters add latency and a coordination dependency.
  • Naïve fixed windows allow 2× bursts at boundaries.
  • IP-based limits punish shared NAT users.
  • Undocumented limits frustrate integrators; headers and docs are essential.

Implementation notes

Algorithms

Fixed window — simple counter per window; suffers boundary bursts (200 requests in two seconds straddling midnight). Sliding window log — accurate timestamp sets; memory-heavy. Sliding window counter — blends two fixed windows; production default at many CDNs. Token bucket — refills tokens at a rate with burst capacity; friendly for bursty clients (AWS API Gateway style). Leaky bucket — smooths output rate to backends; useful for protecting databases from thundering herds.

Response headers and 429 bodies

HTTP/1.1 200 OK
RateLimit-Limit: 100
RateLimit-Remaining: 47
RateLimit-Reset: 1714000060
RateLimit-Policy: 100;w=60

HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/rate-limited",
  "title": "Too Many Requests",
  "status": 429,
  "detail": "Quota of 100 requests per minute exceeded.",
  "retryAfter": 30
}

Emit quota headers on successful responses too so clients self-throttle. Support both IETF RateLimit-* and legacy X-RateLimit-* during migration. Use RFC 9457 problem details for 429 bodies.

Limit dimensions

Combine per consumer (OAuth client or API key), per route (expensive endpoints), per tier (metadata on the key), optional global ceiling, and per IP only where authentication is absent.

OpenAPI and client behaviour

Document 429 responses, Retry-After, and rate headers in OpenAPI. Clients should honour Retry-After, implement exponential backoff with jitter when absent, and pre-throttle using RateLimit-Remaining.

Fail open vs fail closed

When the counter store is unavailable, decide explicitly: fail open risks abuse; fail closed risks outage. Many teams fail open on read paths with aggressive monitoring, fail closed on auth endpoints.

Common failure modes

  • Boundary burst on fixed windows—migrate to sliding or token bucket.
  • Redis SPOF without HA or defined degradation policy.
  • 429 without Retry-After — clients retry immediately and amplify load.
  • Global limit only — one bad API key affects all tenants.
  • Headers only on 429 — integrators cannot predict exhaustion.

Decision checklist

  • Are quota headers returned on 2xx responses?
  • Does every 429 include Retry-After or explicit reset time?
  • Are expensive routes limited separately from cheap list endpoints?
  • Is the algorithm documented (sliding window vs token bucket)?
  • Is counter-store failure behaviour defined and tested?
  • Are limits published in the developer portal and OpenAPI?
  • Are auth endpoints rate-limited independently?
  • Are limits keyed on authenticated identity where possible?

Example use cases

  • Illustrative scenario — Northwind Logistics enforces 1,000 requests/minute per partner API key with token-bucket burst 100 at Kong; shipping webhooks get a separate 50/minute cap.
  • Illustrative scenario — FieldOps rate-limits mobile sync to 30 requests/minute per device certificate identity to protect rural base stations from upload storms.
  • Case study — GitHub REST API documents primary and secondary rate limits, exposes X-RateLimit-* headers, and returns 403/429 with retry guidance.
  • Case study — Stripe publishes rate limits per API key and advises exponential backoff on 429 responses.

Related patterns

  • API Gateway — central enforcement point for quotas.
  • API Authentication — stable identity for limit keys.
  • OpenAPI Specification — document limits and 429 responses.
