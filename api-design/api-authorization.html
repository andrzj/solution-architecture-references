API Design Security

API Authorization

What authenticated callers may do — OAuth 2.0 scopes at the gateway, RBAC and resource ownership in services, OPA policies, and ReBAC tuple stores.

⏱ 14 min read

What it is

API authorization decides whether an authenticated principal may perform an action on a specific resource. Authentication establishes identity; authorization enforces policy—roles, scopes, attributes, or relationships—on each request.

Production APIs combine layers: OAuth 2.0 scopes on access tokens for coarse, consent-backed API permissions; RBAC from identity claims for job functions; ABAC when decisions need resource metadata, time, or environment; and ReBAC when access follows sharing graphs (document co-owners, group inheritance). Policy engines such as Open Policy Agent (OPA) externalise Rego policies so services stay thin.

A billing API might require scope invoices:read at the gateway, then check that the caller’s organisation owns invoice inv_123 inside the service—scope alone cannot express object-level ownership.

In zero-trust designs, authorization is evaluated at a Policy Enforcement Point (your API handler or sidecar) that asks a Policy Decision Point (OPA, identity provider, or ReBAC engine) for an allow or deny. Deny-by-default is the safe baseline; broad grants require explicit approval, ticketing, and time-bounded elevation where regulations demand it.

Why it exists

Authenticated callers are not automatically trusted for every operation. Without authorization, any valid token could read or mutate any row. Least privilege requires evaluating policy on every call, preferably in code paths that understand domain invariants.

Hardcoded if (role == "admin") checks sprawl across services and diverge under pressure. Central policy (scopes at the edge, OPA or ReBAC stores for fine grain) keeps decisions auditable, versioned, and testable—especially when the same API serves partners, staff, and end users with different rules.

Regulators and enterprise buyers increasingly expect evidence that access was checked at request time—not inferred from network location. Structured authorization logs (subject, resource, action, outcome, policy version) support SOC audits and incident replay without scraping application stderr.

Attribute-based policies express rules on resource labels, time windows, and request context—useful for data residency and “owner may edit, others read” models. Relationship-based stores model inheritance (folder contains documents) without copying role lists into every service. Neither replaces authentication: a forged token with valid signature still fails if authorization denies the action on the targeted resource id.

When to use

  • OAuth scopes — partner and public APIs where users consent to capability bundles (orders:write, profile:read).
  • RBAC — staff admin surfaces with stable role taxonomies (viewer, editor, admin).
  • ABAC / OPA — healthcare, finance, or multi-tenant rules involving classification, department, contract tier, or request context.
  • ReBAC — collaborative products where folders, teams, and inherited shares define access.
  • Resource-based checks — any API returning or mutating instances by ID (orders, patient records, documents).

Authorization belongs in the request path for every mutating and sensitive read operation—caching “admin” in a session cookie without re-checking on each API call is not a substitute for policy evaluation at the resource server.

When not to use

  • Do not rely on gateway scope checks alone when object ownership lives only in the domain database.
  • Do not adopt full ABAC when a small RBAC matrix suffices—policy complexity has operational cost.
  • Do not encode every permission as a JWT claim if roles change frequently and token TTL is long—short TTL, introspection, or server-side role lookup may be required.

Typical architecture

North-south traffic hits a gateway that enforces OAuth scopes and optional JWT claim presence; services enforce resource ownership, field filtering, and OPA or ReBAC policies where domain context is required.

Pros and cons

Pros

  • OAuth scopes give partners a consent-aligned, documentable permission surface in OpenAPI security schemes.
  • RBAC is easy to explain to auditors and product owners.
  • OPA decouples policy from microservice code; policies ship as bundles with tests.
  • ReBAC models sharing without hundreds of bespoke roles.
  • Layered checks align with zero trust: never trust the network, always re-verify policy.

Cons

  • RBAC suffers role explosion when permissions are fine-grained.
  • ABAC policies can interact in surprising ways without rigorous testing.
  • OPA and ReBAC add latency and infrastructure unless embedded as sidecars with warm caches.
  • JWT role claims lag identity-provider updates for the token’s lifetime.
  • Splitting gateway vs service responsibility confuses teams unless documented clearly.

Implementation notes

Scopes, roles, and permissions

Scopes label what an access token may attempt—typically API-wide and user-consented (RFC 6749 §3.3). Roles reflect job functions; map roles to permissions in the identity provider or locally. Permissions are atomic (invoice.void). Document required scopes per operation in OpenAPI; gateway plugins reject missing scopes before traffic reaches services.

Resource-level and function-level checks

Prevent BOLA/IDOR (OWASP API1) by validating the principal’s relationship to each resource instance—owner, tenant, or explicit grant. Prevent broken function level authorization (API5) by protecting admin routes server-side, not only in the UI. Return 404 when hiding existence is safer than 403.

OPA and ABAC

Send a JSON input document (subject, resource, action, environment) to OPA; evaluate Rego policies; cache allow decisions with tight TTL for read-heavy paths. Version policies in Git; run opa test in CI. Use ABAC when attributes like data classification or geography matter more than static roles.

ReBAC and OpenFGA

Model tuples (object, relation, subject) and evaluate checks via graph traversal (Google Zanzibar). Open-source engines (OpenFGA, SpiceDB, Ory Keto) offer gRPC check APIs. Prefer ReBAC when permissions derive from membership, sharing links, and inheritance—not from a flat role list.

Response shaping

Authorisation includes which fields a caller may see. Filter sensitive attributes in the domain layer based on roles; express separate response schemas in OpenAPI where feasible.

Authorization testing and observability

Table-driven tests should cover allow, deny, and edge tuples for each route—especially horizontal privilege attempts with another tenant’s identifier. In staging, replay production-shaped tokens against policy bundles before rollout. Emit metrics on deny rates by route and policy version so sudden spikes reveal misconfiguration or credential abuse before support queues fill up.

Policy engines and latency

Centralised authorisation (OPA, OpenFGA, Cedar) should answer in single-digit milliseconds at p99—budget more than one round trip per HTTP request. Cache decisions by subject–resource–action with TTL only when stale denials are acceptable; never cache denials as allows. Fine-grained ReBAC graphs (Zanzibar-style) scale reads with consistent indexing; document max relation depth and batch-check APIs for list endpoints that must filter rows by permission.

Scopes versus resources

OAuth scopes from RFC 6749 express coarse capability; object-level checks still validate that the token’s tenant matches the resource identifier in the path—OWASP API1/API5 failures happen when scope alone gates access. Return 403 for failed authorisation and 404 when existence must be hidden; document the policy for integrators.

Decision logs for denied requests (subject, action, resource, policy version) support audit without logging full tokens. Policy bundles should be immutable versioned artifacts deployed like application binaries—runtime policy edits without version bumps make incidents unreproducible.

List endpoints must apply authorisation before SQL LIMIT—fetching rows then filtering in memory leaks existence via timing and response sizes.

Common failure modes

  • Scope-only security — token with orders:read can read every order ID; missing tenant filter.
  • Wildcard scopes — issuing admin:* or *:write for convenience.
  • Trusting client-supplied tenant headers without binding to token claims.
  • Stale admin in JWT — demoted admin retains access until token expiry.
  • Policy only in the gateway — cannot see database ownership or field-level rules.

Decision checklist

  • Does every mutating endpoint verify object-level access, not only scope?
  • Are admin and internal routes protected independently of the SPA?
  • Are OAuth scopes narrow and listed per route in OpenAPI?
  • Is there a documented split: gateway scopes vs service ownership checks?
  • Are OPA/ReBAC policies tested in CI?
  • Are sensitive response fields filtered by role?
  • Is token TTL compatible with how fast roles must take effect?
  • Do collection queries automatically scope to the caller’s tenant or user?

Example use cases

  • Illustrative scenario — Meridian Commerce requires scope catalog:read at Kong, then filters product rows with WHERE merchant_id = :principal_merchant in the catalog service.
  • Illustrative scenario — Northwind Logistics stores driver–depot relationships in OpenFGA; a driver may see only shipments for depots where driver relation holds.
  • Case study — Google Zanzibar powers consistent sharing checks across Drive-style products using global tuple storage and Zookie consistency tokens.
  • Case study — Stripe documents restricted API keys with explicit resource and permission lists—scope-like granularity without full OAuth for merchant automation.
