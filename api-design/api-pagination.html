API Design

API Pagination

Splitting unbounded collections into safe pages — offset/limit trade-offs, cursor and keyset stability, Google AIP-158 opaque page tokens, total_size estimates, RFC 8288 Link navigation, Relay connections, and documenting list contracts in OpenAPI.

⏱ 14 min read

What it is

Pagination splits a large collection into pages so clients retrieve a bounded number of items per request. Without it, GET /shipments might return millions of rows — blowing memory budgets, saturating networks, and triggering gateway timeouts.

Every list design answers four questions: stability (do concurrent inserts or deletes duplicate or skip rows?), performance (does the database work grow with page depth?), navigability (sequential only, or jump to page N?), and contract clarity (how does the client know whether another page exists?). Strategies range from simple offset/limit to cursor or keyset pagination and opaque page tokens as prescribed by Google AIP-158.

REST APIs typically expose page_size and page_token (or cursor) query parameters; GraphQL uses the Relay connection specification with first/after; some HTTP APIs surface navigation links via RFC 8288 Link headers instead of embedding tokens in the JSON body.

Why it exists

Collections grow without bound. Pagination caps response size, keeps latency predictable, and lets clients stream through data incrementally. Google’s API Improvement Proposals treat pagination as a day-one requirement: adding it later is a backwards-incompatible behaviour change — clients that assumed unbounded lists silently stop seeing new rows when a default page size appears.

When to use

  • Every collection endpoint whose row count is not hard-capped.
  • Infinite-scroll and mobile “load more” flows — cursor or keyset pagination.
  • Public APIs aligned with AIP-style list methods (page_size, page_token, empty token at end-of-collection).
  • Admin grids on moderately sized tables where offset paging is acceptable and “page N of M” navigation matters.

When not to use

  • Small, bounded enumerations (status codes, config flags with < 100 values).
  • Event streams consumed sequentially (Kafka, Kinesis, SSE) — use offsets or cursors native to the broker, not HTTP list paging.
  • Random access to arbitrary deep pages on billion-row tables — pair search or export APIs with cursor pagination instead of deep OFFSET.

Typical architecture

Offset scans and discards leading rows; keyset pagination seeks on a composite index using the decoded cursor.

Pros and cons

Pros

  • Cursor/keyset paging stays O(log N) at any depth — index seek, not row discard.
  • Stable ordering under concurrent writes — no duplicate or skipped items across pages.
  • Opaque page tokens (AIP-158) let you change storage strategy without breaking clients.
  • Natural fit for infinite scroll and synchronisation jobs that walk forward only.
  • Offset/limit is simple, bookmarkable, and supports “page N of M” admin UIs on small tables.

Cons

  • Deep offset pagination degrades linearly — OFFSET 1000000 scans a million rows.
  • Offset pages shift when rows insert or delete during traversal — duplicates and gaps appear.
  • Cursors cannot jump to arbitrary page numbers without walking from the start.
  • Precise COUNT(*) on filtered large tables is expensive and immediately stale.
  • Base64-encoding a JSON cursor is not sufficient obfuscation — AIP requires true opacity.

Implementation notes

Offset and limit

GET /orders?offset=0&limit=20   → rows 1–20
GET /orders?offset=20&limit=20  → rows 21–40

Response:
{
  "data": [...],
  "pagination": { "offset": 20, "limit": 20, "total": 1842 }
}

SQL:
  SELECT * FROM orders ORDER BY created_at DESC
  LIMIT 20 OFFSET 40;   -- scans 60 rows to return 20

Use only when the table stays small, sort order is stable for the session, or the UX needs direct page numbers. Enforce a maximum limit server-side.

Cursor and keyset pagination

GET /orders?limit=20
→ { "data": [...], "pagination": { "nextCursor": "…", "hasMore": true } }

GET /orders?limit=20&cursor=…

SQL (composite keyset):
  SELECT * FROM orders
  WHERE (created_at, id) < (:last_created_at, :last_id)
  ORDER BY created_at DESC, id DESC
  LIMIT 20;

The cursor encodes the last seen position (opaque to clients). Always add a unique tie-breaker column (usually id) when the primary sort key is not unique. Match the sort order with a composite index on (created_at, id).

Google AIP-158 page tokens (REST mapping)

AIP-158 defines the canonical list contract. Map it to REST query parameters as follows:

  • page_size — optional; choose a documented default when omitted or zero; coerce values above the API maximum; reject negative values with 400 INVALID_ARGUMENT.
  • page_token — opaque, URL-safe string from the previous response; clients must repeat all other list parameters unchanged or the API rejects the request.
  • next_page_token — empty string (or omitted) is the only signal for end-of-collection; never infer “last page” from a short result set alone.
  • total_size — optional estimate; document if approximate.
  • skip — optional count of individual resources to skip (not pages); may return 200 with an empty page and a continuation token when the backend cannot honour skip synchronously.
GET /v1/orders?page_size=50&page_token=CiQKMDIwMjQtMDQtMTU…
→ {
    "orders": [ ... ],
    "next_page_token": "CiQKMDIwMjQtMDQtMTY…"
  }

GET /v1/orders?page_size=50&page_token=
→ last page; next_page_token absent or ""

Tokens must be opaque — serialised protobuf or signed blobs, not decodable offsets clients can manipulate. Page tokens carry pagination position only; authorisation still applies on every request.

Total counts

Avoid mandatory SELECT COUNT(*) on hot list paths. Prefer hasMore or an empty next_page_token. When UX needs “N results”, return total_size as an estimate from statistics, cache counts asynchronously, or document staleness explicitly.

RFC 8288 Link header

HTTP/1.1 200 OK
Link: <https://api.example.com/orders?cursor=abc>; rel="next",
      <https://api.example.com/orders>; rel="first"
X-Total-Count: 1842

Hypermedia clients (GitHub, JSON:API adapters) can navigate without parsing the body. Standard rel values: next, prev, first, last.

GraphQL Relay connections

query {
  orders(first: 20, after: "cursor-abc") {
    edges { cursor node { id status total } }
    pageInfo {
      hasNextPage hasPreviousPage startCursor endCursor
    }
  }
}

Relay standardises forward (first/after) and backward (last/before) paging. Most GraphQL servers implement the connection specification natively.

OpenAPI documentation

Document page_size maximum, default, and coercion behaviour; describe page_token opacity; state that filter and sort parameters must be identical across pages. Reference shared pagination schemas in components/schemas for consistency across list operations.

Common failure modes

  • Adding pagination late — breaking change for clients that assumed full collections (AIP-158 backwards-compatibility warning).
  • Deep offset — list timeouts as tables grow.
  • Duplicate or skipped rows — offset pages while rows mutate underneath the client.
  • Missing tie-breaker — non-unique sort keys yield unstable page boundaries.
  • Transparent cursors — clients depend on internal offset encoding; you cannot evolve storage.
  • Expensive COUNT(*) — total count computed on every list request.

Decision checklist

  • Is pagination designed into list endpoints from day one?
  • Is page_size (or limit) capped and documented with a safe default?
  • Do cursor/page tokens remain opaque and URL-safe?
  • Is there a composite index matching the keyset sort columns?
  • Does end-of-collection use empty next_page_token / hasMore: false, not inferred from result length?
  • Are total counts optional, approximate, or off the hot path?
  • Must clients repeat filters and sort params unchanged when advancing tokens?

Example use cases

  • Northwind Logistics shipment API — GET /v1/shipments?page_size=100 with opaque page_token; mobile drivers page forward only; no total count on the list path.
  • Meridian Commerce admin orders — offset/limit on a 5,000-row filtered view with cached total for “page 3 of 40”.
  • Partner webhook backlog — keyset on (created_at, id) so a synchronisation worker resumes after restarts without gaps.
  • GraphQL storefront — Relay first: 24 product connection for infinite-scroll category pages.
