API Design

Backend for Frontend (BFF)

A pattern that creates a dedicated backend service per user interface type — one BFF for mobile, one for web, one for third-party — enabling each UI team to own the aggregation, transformation, and response shaping logic tailored to their client's exact needs.

⏱ 11 min read

What it is

The Backend for Frontend (BFF) pattern gives each major client experience its own backend service that shapes data and protocols for that UI. Instead of one generic API for web, mobile, and partners, a BFF sits behind the gateway (or alongside it), calls domain microservices, aggregates results, applies presentation rules, and returns a response tuned to one client class.

Sam Newman popularized the term in microservice literature: the team that ships the frontend also owns the BFF, so screen changes do not depend on every domain team publishing new endpoints. The BFF is an integration and adaptation layer—not a home for core business invariants.

BFFs typically speak HTTP/JSON (or GraphQL) to clients and gRPC or REST to internal services. They may hold short-lived session state—device tokens, checkout ids, feature-flag snapshots—but durable business state still belongs in domain databases owned downstream. Treat the BFF as a presentation-tier service with its own SLO, not as a throwaway proxy.

Why it exists

A single REST surface forces compromises. Mobile needs small payloads and stable list cards; web dashboards need wide joins; partners need bulk exports and different auth. One API team becomes a bottleneck, and every client pays for fields others require. BFFs move composition next to the consumer, keep domain services focused on nouns and rules, and let product teams iterate vertically.

The cost is more deployable services, duplicated integration code if unmanaged, and frontend squads maintaining server runtimes—trade-offs that pay off when client divergence is real, not cosmetic.

When the BFF pattern lands well, release cadence for a mobile screen decouples from ledger or inventory services: the experience team ships a new card layout by changing resolver or handler code without waiting for a platform-wide API version bump.

The pattern trades extra network hop and operational surface for team autonomy. A “general-purpose” BFF that serves web, mobile, and partners in one deploy reintroduces the god-service coupling the pattern was meant to remove—split by client type or persona and keep shared domain logic in core services, not in the experience layer.

When to use

  • Distinct client types with different payload, latency, or auth requirements.
  • Screens that fan out to multiple domain services and need one tailored response.
  • Product teams organized to own experience end-to-end (UI + BFF).
  • Per-channel optimizations: image sizing, caching TTL, offline bundles, partner scopes.

When not to use

  • One client channel with stable needs—a shared API or modular monolith may suffice.
  • Mobile and web that consume identical resources—parameterized REST beats two BFFs.
  • Teams without capacity to run, test, and on-call backend services.
  • Using BFFs only to bypass domain design—fix bounded contexts first.

Typical architecture

North-south traffic hits the gateway; each BFF fans in to domain services in parallel; optional GraphQL layer can serve multiple clients from one schema.

Pros and cons

Pros

  • Client-specific performance and UX without polluting core domain APIs.
  • Product teams unblock themselves for screen-driven changes.
  • Domain services stay narrower and more reusable across channels.
  • Independent scale and deploy cadence per channel.
  • Channel quirks (push registration, TV navigation) stay out of core services.

Cons

  • Proliferation—each new device class can spawn another service.
  • Duplicated fan-out, retry, and auth code without shared libraries.
  • Frontend teams inherit backend operational duties.
  • Risk of re-implementing domain rules in the BFF.
  • More integration tests and contract surfaces to maintain.

Implementation notes

What belongs in the BFF

Aggregate for one view, map DTOs to UI models, apply channel caching, orchestrate auth handshakes (device login, partner consent). Keep pricing, inventory invariants, and ledger rules in domain services.

Version BFF routes independently from domain APIs: prefix mobile paths (/mobile/v3/home) so old app binaries keep working while domain services move on internal contracts. Deprecation headers on BFF responses give app stores time to force upgrades without freezing backend evolution.

Parallel fan-out and resilience

Call downstream services concurrently with a parent timeout; fail partial screens gracefully or return degraded data with explicit flags. Use circuit breakers and bulkheads so one slow dependency does not freeze every endpoint.

When one downstream dependency is optional for a screen—recommendations beside order history, for example—return partial JSON with explicit degraded: true flags instead of failing the entire response. Mobile clients can hide empty sections; web clients can show skeleton placeholders. Document which fields are best-effort so QA scripts assert the right behaviour.

Shared libraries and contracts

Extract generated clients, retry policies, and auth validators into versioned packages or an internal SDK. Pair with contract tests so service response changes are caught before production BFF deploys.

GraphQL as a unified BFF

One GraphQL server can serve web and mobile with different queries; resolvers perform the same aggregation REST BFFs would. Federation splits ownership when domains grow. See GraphQL for execution and safety controls.

Controlling proliferation

Merge similar clients (iOS + Android → mobile BFF). Require a written justification for new BFFs. Cap count via architecture review. Prefer experience APIs for shared read models before cloning services.

Error translation and caching

Map downstream 5xx and validation errors into stable, client-friendly envelopes—mobile apps often cache error copy and retry rules. Set cache headers on read-heavy BFF responses when data is safe to memoise (public catalog tiles) but never cache personalised account payloads without explicit TTL and cache-key discipline tied to the authenticated principal.

Team topology

Conway’s law applies: if mobile, web, and partner squads sit in different groups, three BFFs often emerge naturally. Platform engineering can supply golden-path templates (observability, auth, generated clients) so each squad does not reinvent mTLS, retries, and structured logging. Rotation or paired on-call between frontend and BFF owners prevents “throw over the wall” incidents when screens fail only in production fan-out paths.

Security boundary

BFFs see tokens and PII—treat them as tier-one services: patch cadence, secret storage, and dependency scanning match core APIs. Avoid logging full bearer tokens or raw payment payloads even when debugging screen issues; correlation ids and hashed user identifiers suffice for triage.

Fan-out and timeout math

A screen aggregating five downstream HTTP calls in parallel inherits the slowest dependency unless you use partial responses—parent timeout should be roughly max(child deadline) plus aggregator overhead (50–100 ms), not the sum of children. Circuit-break per dependency so one failing catalog service does not blank the entire homepage. BFFs are not generic API gateways: keep one BFF per experience (mobile, web, partner) so channel-specific shaping does not accumulate conflicting requirements in a single codebase.

Auth at the edge of the experience

BFFs often hold session cookies and exchange them for service tokens—follow OAuth BCPs and never forward end-user refresh tokens to untrusted browser storage. Downstream calls should use client-credentials or token exchange with least-privilege scopes rather than replaying the user’s full access token when narrower delegation suffices.

Response shaping for mobile may strip fields the web BFF still needs—duplicate DTO mappers per channel avoid one lowest-common-denominator schema. Cache short-lived BFF responses at the CDN only when they do not embed user-specific data without Vary: Cookie.

GraphQL at the BFF is valid for some teams but concentrates N+1 risk—if the BFF exposes GraphQL, apply the same depth and cost limits as a public GraphQL origin.

Common failure modes

  • Pass-through BFF — no aggregation; adds latency only.
  • Domain logic creep — discounts and eligibility encoded only in the BFF.
  • Sequential fan-out — latency sums across six synchronous calls.
  • Untested downstream drift — silent breakage when services change JSON.
  • Duplicate BFFs — separate iOS/Android services with identical handlers.

Decision checklist

  • Is client divergence substantial enough to justify another service?
  • Does the owning team operate backends (CI, on-call, security patches)?
  • Are downstream calls parallelized with a bounded timeout?
  • Is domain logic forbidden in the BFF by explicit standards?
  • Are consumer-driven contracts tested per dependency?
  • Is there a shared client/retry library across BFFs?
  • Was GraphQL or a shared experience API evaluated before adding a BFF?
  • Is there a governance rule against unbounded BFF growth?

Example use cases

  • Illustrative scenario — A streaming product’s TV BFF returns lean rows and deep-link tiles while the web BFF returns full cast lists and social metadata from the same catalog service.
  • Illustrative scenario — Meridian Commerce exposes OAuth-scoped bulk order export on the partner BFF while the mobile BFF returns three recent orders and avatar thumbnails sized for list views.
  • Illustrative scenario — RideRelay runs separate driver and rider BFFs so location-heavy polling stays off the passenger app’s battery-sensitive code paths.
