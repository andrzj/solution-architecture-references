API Design

OpenAPI Specification

A machine-readable, language-agnostic standard for describing RESTful APIs — OpenAPI 3.1 document structure, JSON Schema alignment, tooling ecosystem (Swagger UI, Redoc, code generators), API-first design workflow, and contract testing with Schemathesis and Dredd.

⏱ 13 min read

What it is

The OpenAPI Specification (OAS; formerly Swagger) is a vendor-neutral, machine-readable format—YAML or JSON—for describing HTTP APIs. A single document states paths and operations, parameters, request and response schemas, security schemes, and metadata so humans and tools share one contract. OpenAPI 3.1 aligns its schema objects with JSON Schema Draft 2020-12, removing the partial-schema friction common in OAS 3.0.

The OpenAPI Initiative (Linux Foundation) maintains the standard. Ecosystem tools render interactive docs, run mock servers, generate typed clients, and fuzz implementations against the documented shapes—making the spec the hub of API-first delivery.

Why it exists

Implementation-only APIs force consumers to read code or chase wiki pages that drift from production. A formal OpenAPI description lets documentation, mocks, SDKs, and contract tests derive from the same artifact, so teams can negotiate changes in review before code merges and detect incompatible edits in continuous integration.

The specification describes HTTP request and response shapes; it does not guarantee behaviour ordering, side effects, or idempotency semantics—those belong in operation descriptions and linked architecture notes. Treating OpenAPI as the sole contract without narrative for workflows (multi-step creates, async operations) leaves integrators guessing about retries and polling.

When to use

  • Multiple internal or external teams consume the same HTTP surface and need a durable contract.
  • You practice API-first design and want clients to integrate against mocks before backends ship.
  • CI should lint style rules (Spectral) and exercise staging APIs with contract tests (Schemathesis, Dredd).
  • Platform engineering standardizes error models, auth, and pagination across many services.

Ephemeral internal debug endpoints used only by operators need not block on OpenAPI authoring if they are excluded from published artifacts and never ship to partners.

When not to use

  • gRPC-only internal traffic where Protobuf and a schema registry already define the contract.
  • Primary async or event interfaces where AsyncAPI describes channels and payloads more naturally.
  • Ephemeral scripts or micro-endpoints where maintaining a spec costs more than the API’s lifespan.

Typical architecture

Authors maintain the OpenAPI document in version control; pipelines lint it, serve mocks and SDKs from it, and validate running services against it before publishing reference docs.

Document structure

openapi: "3.1.0"
info:
  title: Orders API
  version: "2.1.0"
  description: Manage customer orders.
  contact:
    name: Platform Team
    email: platform@example.com

servers:
  - url: https://api.example.com/v2
    description: Production
  - url: https://api.staging.example.com/v2
    description: Staging

security:
  - bearerAuth: []          # Default security for all paths

paths:
  /orders:
    get:
      operationId: listOrders
      summary: List orders for the authenticated user
      tags: [Orders]
      parameters:
        - name: status
          in: query
          schema:
            type: string
            enum: [pending, confirmed, shipped, delivered]
        - name: limit
          in: query
          schema:
            type: integer
            minimum: 1
            maximum: 100
            default: 20
      responses:
        "200":
          description: Paginated list of orders
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/OrderPage"
        "401":
          $ref: "#/components/responses/Unauthorized"

  /orders/{orderId}:
    get:
      operationId: getOrder
      tags: [Orders]
      parameters:
        - name: orderId
          in: path
          required: true
          schema:
            type: string
            format: uuid
      responses:
        "200":
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Order"
        "404":
          $ref: "#/components/responses/NotFound"

components:
  schemas:
    Order:
      type: object
      required: [id, status, total, createdAt]
      properties:
        id:
          type: string
          format: uuid
          readOnly: true
        status:
          type: string
          enum: [pending, confirmed, shipped, delivered, cancelled]
        total:
          type: number
          format: decimal
          minimum: 0
        createdAt:
          type: string
          format: date-time
          readOnly: true
        items:
          type: array
          items:
            $ref: "#/components/schemas/OrderItem"
    OrderPage:
      type: object
      required: [data, pagination]
      properties:
        data:
          type: array
          items:
            $ref: "#/components/schemas/Order"
        pagination:
          $ref: "#/components/schemas/Pagination"
    Pagination:
      type: object
      properties:
        nextCursor:
          type: string
          nullable: true
        hasMore:
          type: boolean

  responses:
    Unauthorized:
      description: Authentication is required
      content:
        application/problem+json:
          schema:
            $ref: "#/components/schemas/ProblemDetails"
    NotFound:
      description: Resource not found
      content:
        application/problem+json:
          schema:
            $ref: "#/components/schemas/ProblemDetails"

  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

API-first design workflow

In API-first delivery the OpenAPI document leads implementation:

  1. Design. Authors edit the spec in Swagger Editor or Stoplight and review changes in pull requests.
  2. Mock. A mock server (Prism, WireMock) serves examples so client teams can build in parallel.
  3. Implement. Services implement operations to satisfy the contract—optionally starting from generated stubs.
  4. Validate. Contract tests on staging assert live responses match documented status codes and schemas.
  5. Publish. CI lints with Spectral; portals (Swagger UI, Redoc) render the same artifact customers read.

Tooling ecosystem

  • Swagger UI and Redoc render interactive reference docs; Swagger UI supports try-it-out flows, Redoc favors readable long-form layouts.
  • Prism mocks responses from examples and can validate proxied traffic against the schema.
  • OpenAPI Generator and Kiota emit typed clients and server stubs across many languages from one spec.
  • Spectral enforces organization style rules (naming, security, required metadata) in CI.
  • Schemathesis generates property-based cases from the spec to find schema violations and server errors.
  • Dredd replays documented transactions against a running server and fails builds on mismatched bodies or codes.

Pros and cons

Pros

  • One artifact feeds documentation portals, mocks, SDKs, and automated contract checks.
  • Mocks unblock client development while server teams implement behind the same contract.
  • Generated clients keep types aligned with documented schemas when regeneration is part of CI.
  • Linters encode design standards so reviews focus on semantics, not formatting drift.
  • OAS 3.1’s JSON Schema alignment reduces custom keywords and conversion glue.

Cons

  • Code-first annotation dumps often produce noisy specs missing descriptions and realistic examples.
  • Monolithic files become unreviewable without $ref splits and bundling in the pipeline.
  • The spec models structure, not runtime policy—rate limits, ordering, and side effects still need prose or extensions.
  • Generated SDKs rarely include production-grade retries, auth refresh, or pagination helpers without hand tuning.
  • Webhooks and streaming patterns remain awkward; event-first APIs may need AsyncAPI alongside or instead of OAS.

Implementation notes

Prefer $ref decomposition

Place reusable models under components/schemas and reference them with $ref. Split paths and schemas into multiple files (for example paths/orders.yaml, schemas/order.yaml) and bundle for publication with Redocly or Swagger CLI so pull requests stay reviewable.

Write example objects

Give every schema at least one representative example; mocks and doc portals render from them. Store shared narratives in components/examples and reference them from multiple operations so partners see consistent payloads.

Schemathesis contract testing

Point Schemathesis at the spec and a staging base URL in CI. It varies parameters and bodies, asserts documented status codes and schemas, and flags unexpected 5xx responses—surfacing null handling gaps and enum omissions that hand-written tests often miss.

Documenting security requirements

Declare schemes in components/securitySchemes, set a default security requirement, and override per operation for public routes. Document OAuth2 scopes on each protected operation so gateways and client generators enforce the same expectations.

OpenAPI 3.1 and JSON Schema alignment

The OpenAPI 3.1 specification aligns schema objects with JSON Schema draft 2020-12, reducing custom nullable and oneOf workarounds from 3.0. Migration checklists include revising type arrays, webhook objects (first-class in 3.1), and summary fields on paths. Pin the spec version in repository metadata so Spectral rulesets and generators pick consistent parsers—mixed 3.0/3.1 files in one repo confuse CI.

CI gates and detection

Run Spectral with an organisation ruleset on every pull request: require operationIds, problem-details response schemas for 4xx, security on non-public routes, and pagination parameters on list operations. Fail builds when bundling introduces duplicate operationIds or broken $ref paths. Track “spec drift” by comparing code-first exports nightly against the canonical hand-written artifact—drift percentage rising above zero for more than a sprint usually means engineers patched handlers without updating the contract.

Publish the bundled spec artifact as a versioned release asset (same semver as API product) so partners pin documentation downloads. Include info.version that tracks product version, not Git commit—confusing the two breaks support triage.

Webhook and streaming operations often need complementary AsyncAPI documents when OAS request/response modeling is awkward; cross-link both from the developer portal.

Common failure modes

  • Spec drift. Code-first exports lag deployments or omit query parameters that exist only in handlers.
  • Monolithic documents. Thousand-line inline schemas discourage review and encourage silent duplication.
  • Happy-path-only responses. Undocumented 4xx/5xx bodies leave clients guessing how to handle failures.
  • Empty examples. Schemas without examples produce useless mocks and vague partner documentation.

Decision checklist

  • Is the OpenAPI document authored and reviewed before implementation (API-first), not scraped afterward?
  • Does every operation expose a unique, stable operationId for generators?
  • Are shared types centralized in components/schemas with $ref rather than copy-paste?
  • Does each schema include at least one realistic example?
  • Does CI run Spectral (or equivalent) against every spec change?
  • Do Schemathesis or Dredd tests gate merges against a staging deployment?
  • Are security schemes and per-route scopes documented and enforced at the gateway?
  • Are error responses typed as application/problem+json per RFC 9457?

Example use cases

  • Illustrative scenario — Northwind platform team: A canonical Orders API spec in git lets product squads generate typed clients in Java, TypeScript, and Go from the same OpenAPI bundle.
  • Illustrative scenario — Meridian storefront: Frontend developers call a Prism mock from the spec while the checkout service implements against the same contract in parallel.
  • Illustrative scenario — Contract gate in CI: Schemathesis runs against staging and blocks deploy when responses violate documented status codes or schemas.
  • Case study — Stripe OpenAPI: Stripe publishes a machine-readable OpenAPI description alongside human docs so integrators can codegen clients and validate shapes.
