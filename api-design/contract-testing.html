API Design Testing

Contract Testing

Verifying API compatibility without integrated environments — Pact consumer tests, provider verification, provider states, broker-backed can-i-deploy gates, message pacts, bi-directional OpenAPI checks, Schemathesis and Dredd, and limits versus integration tests.

⏱ 15 min read

What it is

Contract testing verifies that a provider (API or message producer) satisfies the expectations of its consumers without running the full system together. A contract captures the minimal requests a consumer sends and the minimal responses (or messages) it needs — not the provider’s entire behaviour.

The dominant HTTP pattern is consumer-driven contract testing (CDCT) with Pact: consumers write unit tests against a Pact mock server; successful runs emit a pact file (a collection of interactions); the provider replays those interactions in CI and confirms real responses satisfy the contract’s matchers. A Pact Broker stores contracts and verification results and powers can-i-deploy deployment gates.

Complementary approaches include provider-driven testing against OpenAPI (Schemathesis, Dredd) and bi-directional verification (consumer Pact plus provider OpenAPI compared in PactFlow) when not every team uses the same framework.

Why it exists

Microservices deploy independently. End-to-end integration suites need every service running, couple release cadences, and flake on shared infrastructure. Contract tests shift the question from “did the whole stack pass in staging?” to “does this build still satisfy what production consumers actually use?” — in seconds, per service, in isolation.

When to use

  • Multiple consumers depend on a provider API or event schema.
  • CI/CD needs a pre-production gate before promoting a provider version.
  • Teams want breaking-change detection without maintaining a full integration environment.
  • OpenAPI is the source of truth and you need automated verification on staging.

When not to use

  • Monoliths where consumer and provider ship in one artifact and share one test suite.
  • Interfaces still in flux with no stable consumers — contracts churn faster than the code.
  • Organisations unwilling to operate a broker, provider states, or matcher discipline.

Typical architecture

Consumer CI publishes pacts; provider CI verifies against the broker; can-i-deploy gates promotion.

Pros and cons

Pros

  • Fast feedback — consumer tests hit a local mock; provider verification runs against one service.
  • Contracts document used surface area, not the full API — smaller, more relevant specs.
  • Broker + can-i-deploy answers “safe to deploy this version given production consumers?”
  • Matchers keep contracts data-independent — verification does not depend on literal test values.
  • Message Pact extends the same model to async events (Kafka, SNS, queues).

Cons

  • Setup cost — broker, provider states, CI wiring, and team education.
  • Contracts cover declared interactions only — untested endpoints can still break in production.
  • Pact is not a substitute for functional or load testing of provider business logic.
  • Provider states for complex domains require disciplined test data management.
  • Both sides must agree on workflow; bi-directional or OpenAPI paths add tooling overlap.

Implementation notes

How Pact interactions work

Each interaction is independent (Pact docs): one expected request, one minimal expected response. Precondition data is expressed via provider states (e.g. "order 42 exists"), not by chaining interactions in a single test. Split “create order” and “get order 42” into separate interactions with appropriate states.

Consumer flow: register the interaction with the Pact DSL → exercise consumer code against the mock → mock validates the outgoing request → consumer asserts it handled the response → Pact writes the pact file.

Consumer tests and matchers

await provider.addInteraction({
  state: 'order 42 exists',
  uponReceiving: 'a request for order 42',
  withRequest: {
    method: 'GET',
    path: '/orders/42',
    headers: { Authorization: like('Bearer token') }
  },
  willRespondWith: {
    status: 200,
    headers: { 'Content-Type': 'application/json' },
    body: {
      id: like('42'),
      status: term({ generate: 'confirmed',
        matcher: 'pending|confirmed|shipped|delivered' }),
      total: like(149.99),
      createdAt: iso8601DateTime()
    }
  }
});

Use like, eachLike, term, and format matchers — not literal values — so contracts stay stable when valid data changes. Pact verification succeeds when the provider response contains at least the described structure (superset matching).

Provider verification

return new Verifier({
  provider: 'orders-api',
  providerBaseUrl: 'http://localhost:3000',
  pactBrokerUrl: 'https://pact-broker.example.com',
  consumerVersionSelectors: [{ mainBranch: true }, { deployedOrReleased: true }],
  providerStatesHandler: async (state) => {
    if (state === 'order 42 exists') {
      await db.seed({ id: '42', status: 'confirmed', total: 149.99 });
    }
  }
}).verifyProvider();

The verifier fetches pacts from the broker, sets up each provider state, replays requests against the running provider, and publishes pass/fail. Run verification on every provider build that might deploy.

Pact Broker and can-i-deploy

The broker is the system of record for contract versions and verification results. Tag environments (production, staging) and consumer/provider application versions.

pact-broker can-i-deploy \
  --pacticipant orders-api \
  --version 2.3.0 \
  --to-environment production

Integrate can-i-deploy into deployment pipelines so incompatible provider builds fail before rollout. Pact Broker documentation covers webhooks, pending pacts, and WIP pacts.

Bi-directional contract testing

PactFlow can compare a consumer’s Pact file to a provider’s OpenAPI document without live replay — useful when the provider team publishes OpenAPI but consumers use Pact. The OpenAPI spec must be a structural superset of what consumers require.

OpenAPI-based contract testing

Schemathesis generates property-based cases from the schema and checks responses on a live deployment — strong for undocumented fields, wrong status codes, and 5xx on valid input. Dredd exercises documented examples transaction-by-transaction — strong for “do our documented examples work?” Use both where OpenAPI is authoritative and Pact is not adopted on the consumer side.

Message Pact

For async integrations, Pact tests the message payload, not the queue technology. Split protocol adapters (SNS handler, Kafka consumer wrapper) from domain handlers; test the port that receives the decoded payload. See Pact — Message Pact.

What contracts are not

Contract tests focus on message shape, not full provider behaviour. Do not encode business workflows or exhaustive functional coverage in Pact — that leads to brittle suites. Keep integration or E2E tests thin for critical user journeys; let contracts guard the API boundary.

Common failure modes

  • Literal-value contracts — interactions assert fixed IDs or amounts instead of matchers.
  • Chained interactions — one test assumes another interaction ran; violates Pact independence.
  • Missing provider states — verification cannot seed data the interaction describes.
  • Stale broker versions — abandoned consumer versions block provider deploys; use pending/WIP pact features.
  • Contracts as functional tests — over-specifying provider logic causes constant verification noise.
  • No can-i-deploy — contracts run in CI but never gate releases.

Decision checklist

  • Do consumer tests use matchers for every volatile field?
  • Is each interaction independent with explicit provider states?
  • Does provider CI verify against broker contracts on every merge?
  • Is can-i-deploy required before production promotion?
  • Are consumer versions tagged and traceable to git SHAs?
  • For OpenAPI-only providers, does Schemathesis or Dredd run on staging?
  • Are message contracts tested at the domain handler, not the wire adapter?

Example use cases

  • Northwind Logistics portal — storefront service publishes Pact contracts for the tracking API; the tracking service verifies in CI; can-i-deploy blocks Friday releases when mobile app v3.2 is still on production.
  • Meridian Commerce catalogue — provider-driven Schemathesis nightly against staging OpenAPI catches schema drift before partner integrations notice.
  • FieldOps device events — Message Pact between telemetry producer and alert consumer; handlers tested without standing up SNS in unit tests.
  • PactFlow bi-directional — consumer team on Pact, provider team on OpenAPI; compatibility checked on every consumer pact publish.
