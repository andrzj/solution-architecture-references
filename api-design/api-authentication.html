API Design Security

API Authentication

How APIs establish caller identity — OAuth 2.0 and OIDC flows, bearer JWT validation against JWKS, token introspection, API keys, and mTLS for machine-to-machine trust.

⏱ 16 min read

What it is

API authentication is how a resource server decides which principal—human user, OAuth client, service account, or device—is calling before it runs business logic. It answers “who is this?” and is distinct from authorisation (“what may they do?”).

For HTTP APIs the dominant standards are OAuth 2.0 (delegated access and machine clients, RFC 6749), OpenID Connect (identity layer on OAuth 2.0 for login and id_token claims), JWT access tokens (RFC 9068) carried per RFC 6750, and mTLS or API keys where OAuth is unnecessary. Resource servers either validate JWTs locally via JWKS (RFC 7517) or call token introspection (RFC 7662).

A partner-facing REST API might accept only Authorization: Bearer JWTs whose iss and aud match the platform authorisation server; internal gRPC might require mutual TLS with SPIFFE identities instead of shared secrets in headers.

Why it exists

HTTP does not carry sessions unless you add them. Sending passwords on every request exposes credentials, prevents scoped delegation to third-party apps, and offers no practical revocation path. OAuth 2.0 separates the authorisation server (issues tokens) from resource servers (consume tokens), so partners get least-privilege, time-bounded credentials without sharing user passwords.

OpenID Connect adds a standard login outcome: an id_token (JWT) with subject and profile claims for the client, while access tokens gate API calls. That split keeps authentication policy centralised and lets dozens of microservices validate the same token format.

Machine-to-machine flows lean on client-credentials grants with narrow scopes; user-delegated flows use authorisation code with PKCE for public clients. Document which token formats each route accepts—mixing opaque introspection and local JWT validation on the same route without clarity doubles latency and complicates revocation. Auth endpoints themselves warrant stricter rate limits and anomaly detection than business APIs because they are the blast radius for credential stuffing.

When to use

  • Authorization Code + PKCE (RFC 7636) — browser SPAs and native apps where the user consents to delegated access; mandatory for public clients per OAuth 2.0 Security BCP.
  • Client credentials — service-to-service calls with no interactive user; client authenticates with secret or mTLS at the token endpoint.
  • Device authorization (RFC 8628) — TVs, printers, and CLIs that cannot host a secure redirect.
  • JWT bearer validation — high-volume APIs where cryptographic verification plus claim checks scale better than per-request introspection.
  • Token introspection — opaque tokens, immediate revocation requirements, or mixed token types from one authorisation server.
  • API keys — simple server-side automation when OAuth client registration is heavy; never in browser code.
  • mTLS — zero-trust service mesh or partner APIs where certificate SAN encodes workload identity.

When not to use

  • Implicit flow — removed from OAuth 2.0 Security BCP; tokens in URL fragments leak via history and referrer. Use Authorization Code + PKCE.
  • Resource Owner Password Credentials — legacy only; trains users to type passwords into third-party apps. Prefer OIDC login redirects.
  • Long-lived JWTs without refresh rotation — stolen bearer tokens remain valid until exp; pair short access tokens with refresh-token rotation per RFC 9700 (OAuth 2.0 Security BCP).
  • API keys in front-end bundles — any user can extract them; use an OAuth public client and PKCE instead.

Typical architecture

Public clients complete OIDC/OAuth at the authorisation server, receive access (and often refresh) tokens, and call resource APIs with Authorization: Bearer. The resource server validates JWTs via cached JWKS or calls introspection when tokens are opaque.

Pros and cons

Pros

  • OAuth 2.0 and OIDC are interoperable across vendors; metadata discovery (RFC 8414) reduces custom wiring.
  • JWT validation scales horizontally—no auth server lookup per request once JWKS is cached.
  • PKCE closes authorisation-code interception for public clients without embedding client secrets.
  • Scoped access tokens enforce least privilege at the credential layer.
  • mTLS binds identity to workload certificates, independent of bearer-token theft on the wire inside the mesh.

Cons

  • JWTs are not revocable by default until expiry unless you add deny lists, short TTLs, or introspection.
  • OAuth/OIDC surface area spans many RFCs—misconfigured redirect URIs, weak client auth, and algorithm confusion remain common.
  • API keys lack built-in scoping or rotation standards; operational discipline must compensate.
  • Introspection adds latency and couples availability to the authorisation server.
  • JWKS cache staleness can trust a rotated-but-still-cached signing key unless you handle kid misses correctly.

Implementation notes

OAuth 2.0 grants and OIDC

Use Authorization Code + PKCE for interactive clients. Register exact redirect URIs; reject open redirects. For SPAs, store refresh tokens in HTTP-only cookies where possible rather than localStorage to reduce XSS impact. Request openid scope when you need an id_token; validate nonce on the ID token per OpenID Connect Core. Machine clients use client credentials with confidential client authentication (secret, private-key JWT, or mTLS).

Access tokens and JWT validation

Treat access tokens as credentials, not session cookies. For JWT access tokens, allow-list signing algorithms (reject none and unexpected alg). Validate iss, aud (or resource per RFC 8707), exp, and nbf. Use scope or structured authorization_details (RFC 9396) for coarse API permissions. Fetch JWKS on startup; on signature failure with unknown kid, refresh JWKS once before failing closed.

Bearer usage and introspection

Send tokens only in the Authorization header (RFC 6750), not query strings (logged everywhere). Use introspection when tokens are opaque, when you must honour central revocation within seconds, or for step-up on high-value operations. Cache introspection results briefly with TTL bounded by token exp.

Refresh tokens and rotation

Issue short access tokens (minutes) and longer refresh tokens bound to the client. Rotate refresh tokens on each use and detect reuse (invalidate token family). Pair with sender-constrained tokens (DPoP or mTLS sender-constrained access tokens) when theft of bearer tokens is a primary threat.

API keys and mTLS

Hash API keys at rest; expose only a prefix for support lookup. Attribute every call to a consumer ID for rate limits and audit. For mTLS, map certificate SAN (SPIFFE URI, DNS) to service principals; automate rotation via the mesh or cert-manager.

Token lifetimes and OAuth 2.1 practice

RFC 6749 and RFC 6750 define bearer usage; RFC 7519 JWTs often carry access tokens but are not mandatory. OAuth 2.1 consolidates BCPs: public clients use PKCE (RFC 7636), implicit and password grants are removed from recommended profiles. Typical access-token TTLs run five to sixty minutes; refresh tokens rotate on use with reuse detection. Validate issuer, audience, and exp with clock skew of thirty to sixty seconds. Prefer token introspection (RFC 7662) for opaque tokens at resource servers when local JWT validation is insufficient.

Detection

Spikes in 401 without matching traffic growth suggest clock skew, wrong audience, or mass key rotation without client updates. Monitor introspection latency—central auth becoming a synchronous dependency on every request needs caching with tight TTL and breach revocation paths.

Document which flows are supported (authorisation code + PKCE for public clients, client credentials for service accounts) and explicitly ban implicit and resource-owner-password in new integrations. Rotate signing keys with overlapping JWKS keys (kid in header) so validators pull new keys without hard downtime.

Brute-force detection on token and login endpoints belongs beside rate limiting—authentication failures per IP and per username should feed separate counters with lower thresholds than general API quota.

Common failure modes

  • Algorithm confusion — accepting HS256 with a public key or none; enforce algorithm allow-lists and key type matching.
  • Skipped aud validation — tokens minted for another API are accepted; bind audience to your resource identifier.
  • Tokens in logs — access tokens in query strings, error pages, or APM traces; scrub and use header-only bearer transport.
  • Implicit or password grant in new systems — bypasses modern BCP controls.
  • No refresh rotation — stolen refresh tokens grant indefinite access.
  • Gateway forwards unverified JWTs — backends must not trust claims the edge did not validate.

Decision checklist

  • Is PKCE required for all public OAuth clients?
  • Does the authorisation server publish RFC 8414 metadata and a JWKS endpoint?
  • Are JWT access tokens validated for iss, aud, exp, signature, and allowed algorithms?
  • Are access token TTLs short with refresh rotation and reuse detection?
  • Is introspection or deny-listing defined for immediate revocation on sensitive operations?
  • Are API keys hashed, scoped, and never shipped in client-side code?
  • For M2M, is client credentials or mTLS used instead of shared API keys on the internet?
  • Are tokens excluded from logs, metrics labels, and support ticket attachments?

Example use cases

  • Illustrative scenario — Meridian Commerce ships a React storefront that uses Authorization Code + PKCE against its OIDC provider; 15-minute JWT access tokens stay in memory, refresh tokens rotate in HTTP-only cookies, and the order API validates aud against https://api.meridian.example.
  • Illustrative scenario — Northwind Logistics issues API keys only to server-side EDI partners; keys are SHA-256 hashed in the identity store and mapped to tier metadata consumed by the gateway rate limiter.
  • Case study — GitHub’s REST API accepts personal access tokens and OAuth tokens as bearer credentials, documents required scopes, and rate-limits by authenticated identity rather than IP alone.
  • Case study — Google’s device authorization flow (RFC 8628) powers CLI and TV login: the user approves on a second device while the constrained client polls the token endpoint.

Related patterns

  • API Authorization — scopes and roles decide permitted actions after identity is established.
  • API Gateway — terminates TLS, validates JWTs, and forwards trusted identity headers.
  • API Rate Limiting — quotas keyed on authenticated client or user ID.
