Autocomplete & Suggestions

Implementing fast, typo-tolerant search-as-you-type using edge n-gram tokenizers, completion suggesters, and prefix queries.

⏱ 9 min read

What it is

Autocomplete (query suggestion or type-ahead) returns ranked term or phrase completions while the user types a prefix, usually within tens of milliseconds per keystroke. Unlike full result pages scored with BM25 over entire documents, autocomplete optimises prefix lookup: Lucene exposes completion posting formats, edge n-gram token filters, and dedicated search_as_you_type field types so OpenSearch and Elasticsearch can traverse suggestion graphs faster than re-running heavyweight multi_match queries on every character.

Suggestion quality still depends on the same analyzers and vocabulary as full-text search; autocomplete is not a substitute for tuning BM25 on the final query.

Implementations split between index-time expansion (edge n-grams, completion suggester FSTs built at ingest) and query-time prefix or fuzzy queries against conventional indices. IIR discusses efficient lexical access for interactive IR; autocomplete applies that idea to partial inputs. Mature stacks often blend a fast suggester path with a fuzzy fallback so typos still resolve without sacrificing median latency.

Why it exists

Search abandonment rises when users cannot guess catalog spelling, product naming, or internal jargon. Autocomplete reduces keystrokes, surfaces vocabulary the index already knows, and steers queries away from zero-hit dead ends. It also bridges vocabulary mismatch: colloquial terms can align with canonical titles shown as suggestions before the user commits a BM25 query.

Latency budgets for type-ahead are stricter than full search—often sub-100ms end-to-end including network. Running complete BM25 retrieval per character would saturate CPU; Lucene's completion postings and finite-state transducers (documented in Lucene's suggest module) trade additional index bytes for microsecond prefix traversal that general-purpose databases do not replicate cleanly.

Elasticsearch and OpenSearch also integrate suggesters alongside full-text APIs so one cluster serves both experiences, sharing security roles and index lifecycle policies. From an architecture standpoint, autocomplete is a specialized retrieval profile on the same corpus rather than a separate siloed system—only the field mappings and query templates differ.

When to use

  • Primary search boxes on web or mobile where users expect immediate feedback while typing.
  • Catalogues with finite suggestion vocabularies (titles, brands, places) worth pre-indexing for prefix match.
  • Address, SKU, or ticket lookup flows where partial identifiers must resolve quickly.
  • Enterprise portals surfacing document titles or past queries to accelerate navigation.
  • Voice-to-text search boxes that emit partial transcripts and benefit from rapid lexical alignment.
  • Marketplaces promoting high-margin or high-stock suggestions with explicit completion weights.

When not to use

  • Suggestion sources include sensitive personal data without strict per-user authorization on the suggest endpoint.
  • Catalog churn is so high that rebuilding completion structures lags reality unless you accept query-time prefix costs.
  • Total entity count is modest enough for an in-process trie in the application tier.
  • Shell or IDE tab completion semantics apply—different UX and security constraints.

Typical architecture

Keystrokes hit a debounced API, optional Redis, then Lucene completion or n-gram fields fed by the same ingest pipeline as full-text indexes.

Pros and cons

Pros

  • Lowers abandonment and guides users toward productive full-text queries.
  • Completion FSTs and edge n-grams deliver sub-millisecond Lucene lookups at high QPS.
  • Fuzzy suggest parameters recover single-edit typos on the happy path.
  • Context and weight fields personalise suggestions without rewriting BM25 mappings.
  • Short TTL edge caches absorb duplicate prefix traffic cheaply.

Cons

  • Edge n-grams multiply token counts and disk footprint for autocomplete fields.
  • Large completion indices consume heap on data nodes if weights and contexts proliferate.
  • Query-time prefix and fuzzy clauses on high-cardinality fields stress CPUs under viral load.
  • Mid-token completion needs n-grams, not edge n-grams, with steeper storage cost.
  • Ranking suggestions by revenue versus popularity adds cross-team policy complexity.

Implementation notes

Choose among search_as_you_type (balanced defaults with bool_prefix queries), custom edge n-gram analyzers on a dedicated field, or the completion suggester for curated weighted lists. OpenSearch and Elasticsearch document trade-offs: completion fields reload FST structures on segment merge; edge n-grams inflate postings but keep suggest logic closer to standard search APIs.

Use lightweight analyzers on suggest fields—avoid aggressive stemmers that destroy prefix boundaries. Debounce client calls (~200ms), cap suggestion count (5–10), and cache responses keyed by prefix plus locale in Redis. Refresh completion weights from aggregated query logs in batch jobs rather than per write. For security, never mix tenant-private strings into a global completion index.

Instrument suggestion impressions separately from full search: log prefix length, selected suggestion rank, and whether the subsequent BM25 query zero-hit. Pair phrase suggesters on popular bigrams with term suggesters on titles when users paste multi-word fragments. For multilingual catalogs, scope analyzers per locale field and avoid mixing dictionaries in one completion index. Load-test autocomplete paths independently—sustained 200 RPS on three-character prefixes exhausts data nodes faster than headline search benchmarks suggest.

When exposing recent-queries autocomplete, hash or tokenize user identifiers in log pipelines so suggestion mining stays GDPR-aware while still capturing popular prefixes per segment.

Completion suggesters build weighted finite-state transducers suited to curated head terms; edge n-grams and search_as_you_type fields keep logic closer to standard BM25 APIs but inflate postings. Budget p95 latency under roughly 100 ms end-to-end: debounce client requests near 200 ms, cancel in-flight calls on the next keystroke, and edge-cache hot prefixes. Blend popularity from query logs with optional personalization when the API is authenticated. Typo tolerance via fuzzy or limited Levenshtein edit distance helps fat-fingered SKUs; prefix tries at CDN or API gateway can absorb flash traffic for two- and three-character prefixes without hammering data nodes.

Separate autocomplete mappings from main search fields so stemmers never mangle codes users type from packaging labels. Rebuild completion contexts after bulk catalog deletes—FST-backed fields can surface retired SKUs until segments merge. Load-test suggest endpoints at twice expected holiday QPS because keystroke storms multiply request rate by average query length. Return suggestion rank and source field in API responses so product analytics can tune weights without replaying raw traffic.

Common failure modes

  • Heap pressure from massive completion contexts causes data-node OOM during merges.
  • PII enumeration when user-generated text is indexed into shared suggesters without ACL filters.
  • Missing debounce multiplies QPS by average query length during traffic spikes.
  • Stale suggestions after deletes because completion FSTs lag document removal until reindex.
  • Stemmed autocomplete fields break predictable prefix matching for product codes.
  • Cross-region cache pollution when a shared Redis key ignores locale-specific suggestion lists.

Decision checklist

  • Is the suggest strategy (n-gram, completion, search_as_you_type) chosen from cardinality and latency targets?
  • Are suggest endpoints authenticated and scoped the same as full search?
  • Does the client debounce and cancel in-flight requests on rapid typing?
  • Is there a Redis or CDN cache with safe TTL for hot prefixes?
  • Are popularity weights refreshed on a schedule aligned with catalog updates?
  • Does rebuild or reindex cover completion fields when SKUs retire?

Example use cases

  • Illustrative scenario — Northwind Commerce: Type-ahead on product titles uses search_as_you_type with weights from weekly query logs; selecting a suggestion issues the same BM25 query users would type manually.
  • Illustrative scenario — FieldOps Logistics: Drivers complete street names via edge n-grams on normalized address fields with 150ms debounce and regional cache keys.
  • Case study — Lucene CompletionPostingsFormat: Lucene documents FST-backed completion postings used by Elasticsearch completion suggesters.
