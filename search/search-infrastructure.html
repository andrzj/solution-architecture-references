Search Infrastructure

Designing production-grade Elasticsearch clusters: shard strategy, Index Lifecycle Management, hot-warm-cold tiers, index aliases, and capacity planning.

⏱ 11 min read

What it is

Search infrastructure is how you run retrieval in production—cluster topology, shards, aliases, snapshots, and capacity for lexical plus vector fields on Elasticsearch, OpenSearch, Vespa, or hosted Algolia.

Index Lifecycle Management (ILM) is the Elasticsearch feature that automates the movement of indexes through storage tiers as they age and their query rate decreases. A time-series index (e.g., logs or events) starts on hot nodes (fast NVMe SSDs, high CPU) for real-time indexing and search, transitions to warm nodes (larger, cheaper SSDs) after 7 days for less-frequent queries, moves to cold nodes (bulk HDD or object-storage-backed) after 30 days, and is eventually deleted or snapshotted to S3. This tiered architecture can reduce search infrastructure costs by 60–80% compared to keeping all data on hot hardware.

Why it exists

Production search fuses database durability, Lucene heap, and ranking CPU—operationally heavier than many distributed systems because it combines the challenges of a database (durable storage, index consistency), a cache (heap-resident data structures), and a compute system (aggregation and ranking pipelines). Misjudging shard count is one of the most common mistakes: too few shards limits parallelism; too many shards wastes heap (each shard has a JVM overhead of ~1.5KB of heap per segment per node). The Elasticsearch guidance of targeting 10–50GB per shard, not exceeding 20 shards per GB of heap, and keeping total shard count below ~1,000 per node gives concrete sizing boundaries.

Index aliases are the operational mechanism that enables zero-downtime reindexing and schema migrations. An alias is a stable logical name that points to one or more physical indexes. When you need to change a field mapping (which requires a full reindex in Elasticsearch), you build the new index in the background, then atomically swap the alias from the old index to the new — applications see no interruption. Without alias-based indirection, any mapping change requires taking the search feature offline during reindex, which can take hours for large indexes.

When to use

  • Customer-facing Elasticsearch or OpenSearch clusters where red/yellow shard states directly hit revenue or SLO dashboards.
  • Log and event indexes whose volume justifies hot-warm-cold ILM on Lucene segments plus object-store cold tiers.
  • Catalogs that evolve mappings, analyzers, or HNSW fields and need alias swaps instead of hard-coded index names.
  • SaaS search with uneven tenant sizes where coordinators and shard routing isolate noisy neighbours.
  • High-ingest telemetry where dedicated ingest or data tiers keep bulk Lucene merges from contending with query threads.

When not to use

  • Fully managed clouds: Elastic Cloud, OpenSearch Service, and similar hosts absorb master quorum and tiering—follow their playbooks instead of hand-rolling topology.
  • Single-node sandboxes: A lone dev Elasticsearch node for an internal widget rarely warrants ILM, fleet masters, or frozen tiers.
  • Alternate search SaaS: Algolia, Vespa Cloud, or Meilisearch ship their own capacity models; this pattern maps to self-managed Lucene fleets.
  • Throwaway prototypes: Defer shard math until product owners commit to production search traffic.

Typical architecture

Dedicated master-eligible nodes hold cluster state; data nodes host Lucene shards (and optional OpenSearch k-NN / Vespa-style vector segments); coordinating nodes front scatter-gather while ILM rolls indices across hot, warm, and cold hardware.

Pros and cons

Pros

  • Hot/warm/cold ILM tiering typically reduces time-series storage spend by large margins versus keeping all data on hot nodes.
  • Dedicated master nodes eliminate cluster instability from master elections during data node overload.
  • Index aliases enable zero-downtime schema migrations and reindexing.
  • ILM automates operational toil (rollover, merge, tier migration, deletion) that would otherwise require manual cron jobs.
  • Coordinator nodes absorb scatter-gather overhead, improving data node search throughput.

Cons

  • Cluster topology planning is complex and mistakes (wrong shard count) are expensive to undo.
  • Hot-warm-cold migration can spike latency for queries that touch warm or cold tiers.
  • ILM policies need careful testing; a misconfigured delete phase can purge data prematurely.
  • Elasticsearch's JVM heap requirements mean vertical scaling is bounded — large clusters require many moderately-sized nodes rather than a few large nodes.
  • Cross-cluster replication (for geo-distribution or DR) adds significant configuration and operational complexity.

Implementation notes

For shard sizing, aim for roughly 10–50GB per shard as a practical rule of thumb, and 1 primary shard per 2 CPU cores on hot nodes for write-heavy workloads. Use the _cat/shards API to audit current shard sizes. For a 500GB product index queried but rarely updated, 10 primary shards × 1 replica = 20 total shards is reasonable on a 3-node cluster. Set index.refresh_interval: 30s on hot write-heavy indexes (logs) to reduce indexing pressure; the default 1s refresh is only needed for near-real-time search use cases.

Enable _source: false on fields not needed in response (computed fields, large blobs) to reduce storage footprint.

When OpenSearch k-NN or FAISS graphs sit beside Lucene, budget vector RAM explicitly. For JVM heap sizing, follow the Elasticsearch recommendation: set JVM heap to no more than 50% of available RAM, and cap at 30–31GB to stay below the JVM compressed ordinary object pointer threshold. Above 32GB, pointer compression is disabled, which wastes memory and can crash the node under segment cache pressure. Monitor heap usage per node in Kibana's Stack Monitoring; sustained heap above 75% indicates the node is under-provisioned. Snapshot to S3/GCS regularly — Elasticsearch snapshots are incremental and cheap, and they are your only defence against accidental index deletion or hardware failure.

Index from a source of truth through CDC, outbox, or bulk reindex jobs; replicas add read throughput and HA but double storage. Tune refresh_interval for near-real-time versus indexing cost—one second is not mandatory for catalog search. Zero-downtime mapping changes use write aliases, dual-index reindex, and atomic alias swap; segment merges continue in the background and spike I/O after large bulks. ILM hot-warm-cold tiers move time-series or aging catalogs to cheaper media. Elasticsearch and OpenSearch share Lucene semantics; Solr fits JVM-centric teams; Typesense and Meilisearch target simpler hosted UX; Vespa excels at hybrid tensor ranking at scale—match the engine to ops skills and query mix, not logo familiarity alone.

Isolate master-eligible nodes from heavy indexing roles. Run restore drills from object-storage snapshots quarterly. Track coordinating-node heap separately when fan-out queries multiply shard requests per user click. Size ingest nodes for bulk throughput separately from search-heavy data nodes when CDC lag spikes during catalog replatforms.

Common failure modes

  • Micro-shard sprawl: Dozens of tiny primaries per gigabyte inflate Lucene segment metadata and JVM overhead on every data node.
  • Master on overloaded data: Mixing master-eligible and heavy indexing roles risks election loss and cluster-wide red status during bulk merges.
  • ILM blocked by yellow health: Unassigned replicas stall rollover; watch ilm/explain, not only cluster green lights.
  • Index names in application config: Skipping aliases forces downtime when remapping dense_vector or analyzer changes—swap aliases atomically instead.
  • Heap plus vector RAM pressure: Lucene caches and HNSW graphs competing for the same host drive GC storms and p99 query spikes past seconds.

Decision checklist

  • Do three dedicated master nodes (or managed equivalent) isolate cluster state from indexing load?
  • Does each primary shard target ~10–50GB with room for HNSW or geo_shape growth?
  • Do applications read and write only through aliases wired in CI/CD?
  • Does every time-series index have ILM rollover, warm migration, freeze/snapshot, and delete tested in staging?
  • Is JVM heap ≤50% of RAM, ≤31GB, with vector indexes sized off-heap where OpenSearch/Vespa allow?
  • Are automated snapshots to object storage scheduled and restore drills documented?
  • Do coordinating nodes (or ingest pipelines) absorb fan-out so data nodes stay search-focused?

Example use cases

  • Illustrative scenario — ELK logs: Daily ILM rollover: hot NVMe week, warm SSD month, cold snapshot quarter, delete.
  • Illustrative scenario — product catalog: Three-shard index behind an alias; monthly zero-downtime reindex on mapping changes.
  • Illustrative scenario — multi-tenant SaaS: Per-tenant indexes with ILM; coordinators isolate scatter-gather from heavy tenants.
