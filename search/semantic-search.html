Semantic Search

Using dense vector embeddings and approximate nearest-neighbour indexes to retrieve documents by meaning rather than keyword overlap.

⏱ 11 min read

What it is

Semantic search retrieves by meaning: queries and documents map to dense vectors, and cosine similarity surfaces paraphrases—e.g. “myocardial infarction” for “heart attack treatment”—without hand-built synonym lists.

Fetching top-k matches is approximate nearest neighbour (ANN) search: approximate the closest vectors instead of exhaustively comparing every document in the index.

Production ANN is dominated by HNSW (Hierarchical Navigable Small World; see Malkov and Yashunin), a graph enabling fast approximate neighbours. OpenSearch k-NN, Elasticsearch (from v8.0), Vespa tensors, pgvector, Pinecone, Weaviate, Qdrant, Milvus, and in-process FAISS all expose HNSW-class indexes. The critical distinction in architecture is between bi-encoders — models that encode query and document independently and compare vectors — and cross-encoders — models that take a (query, document) pair and score relevance jointly. Bi-encoders scale to millions of documents (pre-encode offline); cross-encoders are slower but more accurate, used only for re-ranking a small candidate set.

Why it exists

Lexical BM25 and inverted indexes hit vocabulary mismatch: a document about "myocardial infarction" will not match a query for "heart attack" unless synonyms are manually configured. Semantic search solves this because both phrases map to nearby points in the embedding space trained on vast text corpora. This makes it invaluable for long-tail queries, paraphrastic retrieval, cross-lingual search (multilingual embedding models), and conversational AI pipelines such as RAG (Retrieval-Augmented Generation).

LLMs supplied embedding models and the RAG retrieval step. Vector stores and ANN layers—HNSW in OpenSearch k-NN or Vespa, or FAISS in custom serving—handle millions of chunks, refresh vectors as content changes, and target sub-100ms latency under load. Managed neural search from Algolia and peers packaged the same pattern for SaaS operators.

When to use

  • Natural-language Q&A over wikis and policies when titles rarely contain the words users type.
  • RAG assistants that must retrieve authoritative chunks before an LLM answers from your private corpus.
  • Recommendations and “more like this” when relatedness is meaning, not shared SKU tokens.
  • Cross-lingual help desks with multilingual embedding models backing Elasticsearch, OpenSearch, or Vespa kNN.
  • Long-tail specialist vocabulary where Lucene synonym files and BM25 boosts cannot keep pace.
  • Code and doc search that maps plain-English intent to snippets without exact identifier overlap.

When not to use

  • Exact-token compliance: Part numbers, docket IDs, and statutory citations still need Lucene keyword recall—or hybrid fusion.
  • Seconds-fresh news: Embedding batches lag Lucene refresh; BM25 ingest wins for breaking headlines.
  • Micro corpora: Below ~1k chunks, in-memory cosine on a laptop beats standing up HNSW on cluster RAM.
  • Tight spend caps: GPU embedding, HNSW RAM, and Vespa tensor hosting deserve ROI proof against BM25-only baselines first.

Typical architecture

Offline bi-encoders write vectors into HNSW indexes—Elasticsearch dense_vector, OpenSearch k-NN, Vespa tensors, or external FAISS—while queries embed with the same model revision and ANN-fetch candidates before optional cross-encoder rerank.

Pros and cons

Pros

  • Covers vocabulary mismatch and paraphrastic queries that BM25 alone often misses.
  • Enables cross-lingual retrieval with multilingual embedding models (e.g., multilingual-e5).
  • Core enabler for RAG and LLM-grounded question answering over private documents.
  • HNSW delivers sub-10ms ANN latency even over tens of millions of vectors.
  • Embeddings are reusable across tasks — one embedding index can serve search, recommendations, and clustering.

Cons

  • Embedding generation cost: re-encoding millions of documents takes hours of GPU/API time and must be repeated when the model is updated.
  • Hallucination of relevance: embeddings can rank thematically related but factually wrong documents highly, especially with generic models.
  • Exact keyword matching is worse than BM25 — a product code "XK-9021" may not match semantically.
  • HNSW index is memory-resident; at 1536 dimensions × 4 bytes × 10M vectors = ~58GB RAM required.
  • Model selection and versioning complexity: changing the embedding model invalidates the entire index.

Implementation notes

Choose your embedding model based on the trade-off between quality and cost. Open-source bi-encoders from the sentence-transformers library (e.g., all-MiniLM-L6-v2 at 384 dims, or e5-large-v2 at 1024 dims) run on CPU or GPU in-process and avoid per-call API costs. OpenAI's text-embedding-3-small (1536 dims) and text-embedding-3-large (3072 dims) offer strong quality at ~$0.02/1M tokens but require chunked batching for large corpora. Match the model used at index time exactly at query time — even a minor version change produces incompatible embeddings that silently degrade recall.

Whether graphs live in OpenSearch k-NN, Vespa, or a FAISS service, HNSW tuning hinges on m (number of edges per node, typically 16–64) and ef_construction (search depth during index build, typically 100–400). Higher values improve recall but increase memory and build time. At query time, ef_search controls the recall-vs-latency trade-off. A recall@10 of 0.95 at ef_search=100 is typical for well-tuned HNSW.

Implement a two-stage retrieval pipeline: retrieve top-100 candidates with ANN (fast), then re-rank with a cross-encoder (accurate) to produce the final top-10. This hybrid approach achieves near cross-encoder accuracy at bi-encoder speed.

Pick embedding models for domain language: general bi-encoders are cheap baselines; fine-tuned or asymmetric query/document towers (e.g., E5-style instruct prefixes) improve recall when queries are short and documents are long. Chunk policies must match the use case—paragraph-scale for support articles, sentence windows for catalogs—and re-embed the corpus when the model changes because vectors are not portable across spaces. ANN search trades recall for speed via ef_search; raise it when judgment lists show misses, or run exact kNN on small filtered sets. Multilingual embeddings collapse locales only when product accepts cross-lingual bleed. For BM25-plus-vector orchestration see hybrid search; for HNSW, IVF, and engine trade-offs when vectors outgrow co-located k-NN, see vector databases.

Version embedding model identifiers in index mappings and reject queries that omit the same version at the gateway. Monitor embedding drift by sampling cosine distance distributions on weekly ingests. Pre-filter tenants and ACL metadata before ANN so k-NN never scans another customer's vectors.

Common failure modes

  • Encoder version skew: Different model versions at index and query time use incompatible embedding spaces and silently ruin recall.
  • Chunking strategy mismatch: Chunks that are too short (single sentence) lose context; chunks that are too long (full document) dilute the signal of specific passages.
  • Memory underprovisioning: HNSW indexes must fit entirely in RAM; an index that exceeds available memory causes severe latency spikes due to disk swapping.
  • Embedding drift: As the document corpus grows, the distribution of new documents may shift away from the original embedding space, degrading recall for new-topic queries.
  • No pre-filtering: Running ANN across a multi-tenant index without filtering by tenant returns results from all tenants, leaking data; always apply metadata pre-filters before ANN.

Decision checklist

  • Is the bi-encoder model ID pinned identically for bulk index and online query paths?
  • Do chunk size and overlap match median document structure (tables, headings, tickets)?
  • Does HNSW RAM planning cover dimensions × doc count on every data node hosting vectors?
  • Can you re-embed and alias-swap without dual-writing incompatible embedding spaces?
  • Do metadata filters (tenant, ACL) run before kNN to prevent cross-tenant ANN leakage?
  • Should hybrid Lucene + vector fusion cover SKU-heavy queries your embedding model misses?
  • Have recall@K and nDCG@K on a labeled set gated production cutover?

Example use cases

  • Illustrative scenario — internal documentation RAG: Natural-language employee questions retrieve policy and API chunks for LLM grounding without title keyword overlap.
  • Illustrative scenario — ticket deduplication: Incoming tickets embed against resolved tickets; ANN surfaces similar closures to agents automatically.
  • Illustrative scenario — paper discovery: Researchers describe a gap in prose; the system returns the most semantically relevant papers from a multi-million corpus.

Related patterns

  • Hybrid Search — Fuses HNSW cosine ranks with Lucene BM25 when queries mix paraphrase and exact tokens.
  • Full-Text Search — Inverted-index baseline semantic stacks still lean on for identifiers and freshness.
  • Vector Databases — Dedicated ANN stores when vectors outgrow co-located Elasticsearch or OpenSearch k-NN.
