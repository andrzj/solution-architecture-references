Search & Retrieval Essential

Full-Text Search

How inverted indexes, BM25 scoring, and analyzer pipelines power fast, relevant document retrieval at scale.

⏱ 10 min read

What it is

Full-text search is ranked keyword retrieval over analysed text fields using an inverted index. Each token maps to posting lists of documents (and often positions), so conjunctive queries resolve by list intersection instead of full table scans. Elasticsearch, OpenSearch, and Apache Solr embed Apache Lucene: analyzers normalise text at index and query time, segments store the inverted structure on disk, and a similarity scores matches before the coordinator returns a top-K page.

BM25 (Okapi BM25) is the default Lucene similarity in these engines. Manning, Raghavan, and Schütze's Introduction to Information Retrieval describes BM25 as a probabilistic model that dampens raw term frequency, rewards rare terms through inverse document frequency, and penalises length so boilerplate does not dominate. Elasticsearch and OpenSearch expose k1 and b on BM25Similarity; tuning them is the first structured lever before field boosts, function scores, or learning-to-rank.

Why it exists

Transactional stores optimise keyed access and constrained predicates. Ad-hoc LIKE scans, application-side substring filters, and unindexed JSON blobs fail once catalogues and knowledge bases grow and users type natural language with synonyms, stemming variants, and multi-token phrases. The inverted index amortises tokenisation at ingest: posting lists make arbitrary token lookups cheap at query time, which is the access pattern interactive search requires.

Lucene's analyzer chain—character filters, tokenizer, token filters—runs in paired index and search configurations so stored terms align with query terms. That enables stemming, stop-word removal, synonym graphs, and Unicode normalization that are painful to reproduce in generic SQL. IIR treats this lexical stage as the foundation of modern IR; vector and semantic layers may stack above it, but BM25 over analysed text remains the workhorse for document findability in commerce, support, and observability stacks.

When to use

  • Free-text search spans multiple fields—title, body, tags—and relevance should reflect term overlap, rarity, and field importance rather than a single surrogate key.
  • Corpus size and query concurrency exceed what acceptable full scans on the system of record can sustain.
  • Highlighting, phrase queries, and fuzzy or synonym expansion are product requirements alongside ranking.
  • You already operate Elasticsearch or OpenSearch for logs and want a second index for application content with the same operational toolchain.
  • Discovery workflows combine lexical retrieval with structured filters in one query DSL without pushing ranking into application memory.
  • Relevance feedback and A/B tests need a stable BM25 baseline you can measure before layering learning-to-rank or hybrid retrieval.

When not to use

  • Every access path is an exact match on primary keys, barcodes, or enums where a database index is simpler and authoritative.
  • The indexed set is tiny and internal, so cluster operations outweigh sub-second gains over indexed SQL.
  • Ranking is purely temporal—feeds sorted by timestamp—without lexical scoring requirements.
  • Users describe intent without vocabulary overlap with indexed text; add semantic search or hybrid search rather than expecting BM25 alone to infer meaning.

Typical architecture

Pros and cons

Pros

  • Mature Lucene runtimes deliver millisecond-scale retrieval over millions of segments with horizontal sharding.
  • Rich analysis and query types—multi_match, match_phrase, per-field boosts—cover most catalog and portal patterns.
  • Built-in highlighting, suggesters, and aggregations let one cluster serve search, facets, and autocomplete.
  • BM25 parameters and similarity overrides are well documented and map directly to IR textbook intuition.
  • Replica shards scale read throughput independently from write-heavy primaries.

Cons

  • A search tier duplicates data and requires CDC, outbox, or batch sync to stay consistent with the source of truth.
  • Near-real-time refresh intervals create a visible lag between commits and searchable documents.
  • BM25 is lexical; paraphrases and cross-language intent need additional retrieval stages.
  • Deep pagination with large from values is expensive; search_after or scroll APIs are required for export workloads.
  • Poor mappings—unbounded keyword fields, dynamic object explosions—can destabilise cluster heap.

Implementation notes

Define explicit index mappings before production traffic. Use language analyzers such as the built-in english analyzer for prose fields and keyword or standard with minimal filters for SKUs and codes. Pair text fields with keyword sub-fields when you need both retrieval and sorting or aggregations, following Elasticsearch and OpenSearch multi-field guidance.

Keep index-time and search-time analyzers symmetric unless you deliberately configure search_analyzer; asymmetric analysis is the most common cause of zero-hit queries despite visible term overlap in the UI. Size shards for tens of gigabytes per primary, use index lifecycle management for time-series corpora, and route heavy reindex work off peak hours.

For ranking, start with multi_match and explicit boosts on title-like fields, then validate with click logs or a judgment list. Turnbull and Berryman's Relevant Search recommends measuring before tuning boosts blindly. Use function_score or decay functions only after BM25 and field weights are stable.

Lexical search is an inverted index: each analyzed term maps to posting lists of document IDs (and positions when phrases matter). The analysis chain—tokenizer, lowercase filter, optional stemming versus lemmatization, stop words, and synonym graphs—must be deliberate. Apply synonyms at index time for expansion breadth, or at query time when you need symmetrical recall; mixing both without documentation creates ghost hits. BM25 scores term frequency with saturation: parameters k1 (term frequency curve, often ~1.2) and b (field-length normalization, often ~0.75) control how aggressively long fields get discounted. Phrase and proximity queries consult positions in the postings list; edge and n-gram analyzers power partial SKU match at the cost of index size. Multilingual catalogs need per-locale analyzers or ICU tokenization—do not stem product codes on the same field as prose. Deeper tuning with judgment lists, LTR, and interleaving belongs in search relevance tuning.

Validate analyzers with the analyze API on representative SKUs and prose before launch. Store index and search analyzers in versioned index templates so reindex jobs do not silently change token streams. For phrase-heavy use cases (legal clauses, error messages), keep positions indexed and prefer match_phrase with modest slop over sloppy AND queries that explode recall.

Common failure modes

  • Analyzer mismatch between index and query pipelines stem-or-normalize tokens differently, yielding empty result sets for obvious matches.
  • Dynamic mapping sprawl on nested JSON creates thousands of fields and trips the cluster mapping limit.
  • Shard skew from routing keys concentrates hot sellers on one shard, inflating tail latency for BM25 collection.
  • Unsafe deep paging with high from values forces each shard to materialize and discard enormous hit lists.
  • Unmonitored sync lag lets the index drift silently after connector failures or poisoned bulk batches.

Decision checklist

  • Are analyzers and multi-fields defined per logical attribute before the first production index?
  • Does the ingest path guarantee at-least-once delivery with idempotent document IDs?
  • Have you benchmarked p95 query latency at expected QPS with representative bulk sizes?
  • Is there a judgment list or CTR dashboard to validate mapping or boost changes?
  • Are ILM or rollover policies defined for growing indices?
  • Is pagination for exports implemented with search_after instead of offset paging?

Example use cases

  • Illustrative scenario — Northwind Commerce: A marketplace indexes product title, brand, and description with synonym rules for regional spellings; BM25 with title boost 4× and a sales-rank function_score powers the storefront query bar.
  • Illustrative scenario — Meridian Support: Ticket bodies and chat transcripts share an English analyzer; engineers phrase-search error codes in Kibana-compatible indices while agents filter by tenant keyword fields.
  • Case study — Elasticsearch documentation: Elastic documents full-text query types, BM25 similarity settings, and search_after as the supported pattern for deep paging at scale.

Related patterns

  • Faceted Search — Structured aggregations narrow BM25 hit sets without separate analytics queries.
  • Semantic Search — Dense vectors handle paraphrase where lexical overlap fails.
  • Hybrid Search — Combines BM25 and vector scores with tunable fusion weights.
  • Search Infrastructure — Sizing, sharding, and ILM for production Lucene clusters.
