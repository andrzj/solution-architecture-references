Geospatial Search

Querying and aggregating geospatial data using geo_point and geo_shape types, distance queries, bounding boxes, geo grid aggregations, PostGIS, and H3 hierarchical indexing.

⏱ 10 min read

What it is

Geospatial search centers on proximity search ("find all restaurants within 5km of my location") and containment search ("find all orders shipped to addresses within the New York metro boundary polygon"). Elasticsearch supports both through the geo_point type (a single latitude/longitude coordinate) and the geo_shape type (GeoJSON geometries: points, linestrings, polygons, multi-polygons).

Common geo filters include geo_distance (circle/radius filter), geo_bounding_box (rectangular filter), geo_polygon (arbitrary polygon filter), and geo_shape (spatial relationship queries: intersects, contains, disjoint).

At the aggregation layer, geo grid aggregations bucket documents into geographic grid cells: geohash_grid (variable-precision string encoding), geotile_grid (map tile coordinates at zoom level), and hex_grid (H3 hexagonal cells). These aggregations are used to build heatmaps and density visualisations on maps without transferring millions of individual coordinates to the client. For complex spatial operations (topology, routing, network analysis), PostGIS — the PostgreSQL spatial extension — provides a full SQL-based geospatial engine with support for hundreds of ST_ functions.

Why it exists

Standard B-tree indexes on a single axis cannot answer geographic proximity efficiently because space is two-dimensional: a range query on latitude alone is meaningless without also constraining longitude. Geospatial indexes use space-partitioning data structures (R-trees in PostGIS, geohash Trie in Elasticsearch, BKD tree/Lucene PointValues in Elasticsearch 5+) that partition 2D space into indexed regions, enabling fast range lookups in both dimensions simultaneously. Without specialised geo indexing, a query like "find 1,000 nearest restaurants" would require computing the Haversine distance from the user's location to every restaurant in the database — O(n) rather than O(log n).

The proliferation of mobile devices created enormous demand for location-aware features: ride-hailing, food delivery, real estate, and local search all depend on sub-second geospatial queries over millions of points. Hierarchical spatial indexes like Google's S2 (spherical geometry cells) and Uber's H3 (hexagonal hierarchical index) were developed to serve this need at internet scale, providing cells at configurable resolutions from country-level (level 0) to meter-level (level 15) that can be used as pre-computed index keys in any standard key-value or columnar store.

When to use

  • Radius and “nearest K” proximity: pharmacies, chargers, or colleagues within a few kilometres of a live GPS fix.
  • Polygon containment: users, assets, or orders inside a service area, census tract, or regulatory boundary.
  • Map heatmaps and density tiles when you must aggregate millions of points without shipping raw coordinates to the browser.
  • Geofences that fire workflows when trackers cross geo_shape boundaries stored in Elasticsearch or OpenSearch.
  • Spatial joins between delivery stops and zone polygons, often alongside Lucene text ranking on the same cluster.

When not to use

  • Tiny point sets: Below roughly 10k points, an in-app Haversine sort or SQL distance column beats standing up BKD-backed geo indexes.
  • Non-geographic 2D spaces: Game or chart coordinates are not WGS84; use numeric range filters instead of Haversine geo types.
  • Turn-by-turn routing: Shortest-path and traffic-aware routes belong in OSRM, Valhalla, or graph stores—not in Lucene proximity queries alone.
  • Indoor sub-metre precision: Smartphone GPS and geo_point fields suffice outdoors; BLE/UWB indoor stacks need different ingestion and indexes.

Typical architecture

Production stacks usually pair geo_point or geo_shape mappings on Elasticsearch or OpenSearch—indexed via Lucene BKD trees—with optional H3 pre-keys when QPS exceeds what pure geo_distance filters tolerate. Vespa and other engines expose similar spatial predicates if you already colocate ranking there.

Pros and cons

Pros

  • BKD-backed geo_point queries in Elasticsearch and OpenSearch deliver millisecond proximity search over tens of millions of points.
  • Geo grid aggregations enable real-time map density visualisation without transferring raw coordinates to the client.
  • H3 indexing transforms geospatial proximity queries into standard equality/membership lookups, enabling use with any key-value store.
  • PostGIS provides a full suite of spatial operations (topology, projections, routing adjacency) beyond proximity search.
  • Geo_shape queries support complex polygon intersections needed for geofencing and coverage area analysis.

Cons

  • Geo_shape indexes are significantly larger than geo_point indexes due to shape tessellation overhead.
  • PostGIS spatial index performance degrades with very high-cardinality polygon sets; requires careful VACUUM and ANALYZE scheduling.
  • H3 cell approximation introduces boundary errors: proximity based on cell membership is not exactly equal to true radius-based proximity.
  • Aggregation precision vs. performance trade-off: high-resolution geo grid aggregations over large datasets can be slow.
  • Antimeridian and polar edge cases trip up naive implementations; always test with coordinates near ±180° longitude.

Implementation notes

For distance-ranked “near me” results, use OpenSearch or Elasticsearch geo_distance filters combined with a _geo_distance sort. This returns results sorted by ascending distance from the query point. For "find nearest K" queries, use size: k — Elasticsearch collects the K nearest documents using a priority queue without scanning all documents outside the filter radius. Always set a maximum radius to bound the filter cardinality; an unbounded distance filter degenerates to a full scan.

For filtering by arbitrary polygons (service areas, delivery zones), store polygon boundaries as geo_shape in a separate index and use a geo_shape query with relation: intersects.

When building applications that need to serve both proximity queries and map visualisations at scale, consider pre-indexing H3 cell IDs at multiple resolutions alongside the raw coordinates. At resolution 8 (≈460m diameter hexagons), a 5km radius covering approximately 70 H3 cells can be queried with a simple terms filter, which is faster than a geo_distance computation at very high QPS. Uber, Airbnb, and other location-heavy platforms adopted H3 precisely for this reason: it turns a continuous 2D problem into a discrete set membership problem that scales horizontally. Libraries exist for all major languages to compute H3 cell IDs from lat/lon.

Common failure modes

  • Lon/lat inversion: GeoJSON expects [longitude, latitude]; Elasticsearch and OpenSearch geo_point objects use {lat, lon}. Swapping axes silently warps distance sorts.
  • Oversized geo_shape footprints: Coastlines or cadastral parcels with huge vertex counts balloon Lucene postings; Douglas–Peucker simplify before bulk index.
  • Radius filters without caps: An unscoped geo_distance clause on a busy index becomes a full segment scan and trips query timeouts.
  • Geo grid precision runaway: geotile_grid or hex grids at extreme zoom over hundred-million-point indexes allocate more buckets than the coordinating node can hold.
  • Dateline-spanning polygons: Shapes crossing ±180° need splitting; a single ring otherwise “wraps” the long way and misclassifies containment.

Decision checklist

  • Are points on geo_point and regions on geo_shape with CRS WGS84 (EPSG:4326) explicit in mappings?
  • Do ingest pipelines and client SDKs agree on axis order for GeoJSON vs Elasticsearch object form?
  • Does every proximity query ship a maximum distance or bounding box to bound BKD traversal?
  • Are polygons simplified to the display or business precision you actually enforce?
  • Have you regression-tested fixtures east and west of the antimeridian?
  • At extreme QPS, are H3 (or S2) cell arrays indexed for membership filters instead of per-query Haversine?

Example use cases

  • Illustrative scenario — local search: Two-kilometre geo_distance plus text on name and cuisine, sorted by distance then rating.
  • Illustrative scenario — delivery geofence: GPS crossing a stored polygon triggers order state updates.
  • Illustrative scenario — dispatch heatmap: H3 hex aggregations refresh open-request density on a control dashboard every few seconds.

Related patterns

  • Full-Text Search — Lucene BM25 on names and categories stacked with geo_distance for “near me” ranking.
  • Faceted Search — geohash_grid, geotiles, and H3 buckets are spatial analogues to term facets.
  • Search Infrastructure — Shard sizing and heap plans must account for bulky geo_shape segments on Elasticsearch or OpenSearch clusters.
