Architecture Principles

Foundational design principles that guide architectural decisions — separation of concerns, loose coupling, high cohesion, and the SOLID principles applied at the system level.

⏱ 8 min read

What it is

Architecture principles are short, durable rules of thumb that steer design when requirements conflict.

They differ from patterns (named solutions) and standards (mandatory formats). Principles answer “what do we optimize for?” — for example loose coupling over shared databases.

a logistics operator publishes eight principles in docs/architecture-principles.md. When the routing team wants a synchronous chain through dispatch and billing, reviewers cite principle P3 (“depend on published contracts, not peer internals”) instead of debating personalities.

Principles apply at two levels: code (SOLID inside a service) and system (how A logistics operator’s Catalog, Routing, and Billing services interact). System-level principles are often implicit; writing them down stops each team from inventing incompatible rules.

Principles sit above patterns in the decision stack: patterns name repeatable shapes (event sourcing, API gateway), while principles decide which shapes fit your risk profile. Teams can know every microservices tactic and still ship a tightly coupled monolith when nothing anchors trade-offs as latency, cost, and operability collide.

Why it exists

Without shared principles, every team picks local winners. A logistics operator’s Catalog team favors fast iteration; Billing favors audit trails. The result is shared tables, mystery timeouts, and designs nobody can defend in review.

Documented principles survive re-orgs. A new hire can read why Routing exposes OpenAPI events instead of sharing Billing’s ORM models.

Principles also scale review: staff architects set the guardrails once; teams apply them and record exceptions in ADRs when they must break a rule.

Written principles also depersonalize conflict. When Catalog wants shared Postgres and Billing wants private ledgers, reviewers compare the proposal to P4 instead of debating motives. Exceptions stay legitimate when captured in ADRs with scope and expiry, not as silent one-off hacks.

When to use

  • Publish principles when a logistics operator stands up or merges engineering groups that must ship from one shared platform.
  • Use them when you onboard engineers in batches and need the same vocabulary in design reviews.
  • Use them when reviews keep reopening the same arguments, such as sync versus async or shared databases versus APIs.
  • Use them when you run formal architecture review and need pass-or-fail criteria beyond personal taste.
  • Use them when a dispute needs a depersonalized anchor — for example, “does this violate P5?” instead of “whose idea was worse?”

When not to use

  • Do not treat principles as laws with no documented exceptions, because dogma hides real trade-offs.
  • Do not publish dozens of principles nobody can recall; a logistics operator caps the list at eight and revisits it yearly.
  • Do not force separation of concerns on a proven hot path when profiling shows the coupling is required.
  • Do not confuse a principle with a standard — “prefer stateless services” is a principle, while “errors use RFC 7807” is a standard.

Pros and cons

Pros

  • One mental model for Catalog, Routing, and Billing — less reinventing per sprint.
  • Decisions scale without a single architect in every meeting.
  • Reviews shorten when proposals cite principle IDs and planned exceptions.
  • Consistent cohesion/coupling lowers the cost of changing one capability.
  • Onboarding has a readable “why” beyond tribal knowledge.

Cons

  • Stale or vague principles become wallpaper (“simplicity”) and get ignored.
  • Dogmatic application blocks valid shortcuts — exceptions need ADRs.
  • System-wide DRY can couple services through shared domain libraries.
  • Living documents need owners and periodic edits after strategy shifts.

Implementation notes

SOLID at A logistics operator’s service edge: SRP — Catalog owns SKUs and search; Routing owns assignment rules; Billing owns invoices. OCP — Billing adds invoice line types via new fields/events, not by breaking v1 clients. DIP — Routing calls Billing’s published OpenAPI and event schemas, not shared JDBC into Billing’s database.

Cohesion and coupling: Keep “changes together, lives together” inside a service. Avoid convenience bundles (e.g., Catalog code that calculates tax). Coupling shows up as shared Postgres schemas, fat client libraries with domain rules, and long synchronous chains — name each in design docs and justify or remove.

Design for failure: Every cross-service call gets timeouts, bounded retries, and circuit breakers where cascading failure is plausible. Emit metrics and structured errors by default so ops can see Routing starving when Billing is down.

Interfaces at boundaries: ISP and LSP show up in published contracts—Routing depends on Billing’s OpenAPI and event schemas, not on JDBC table layouts. Narrow integration surfaces make substitutions (mock billing, regional variants) possible without forking domain code.

YAGNI: a logistics operator delayed a generic “rules engine” until three distinct routing policies existed. Until then, explicit code in Routing stayed clearer than speculative plugins.

Common failure modes

  • Principle overload: A wiki page of dozens of slogans; a logistics operator resets to eight with named owners.
  • DRY across services: A shared company-domain JAR used by Catalog and Billing — one breaking release blocks both.
  • SRP over-splitting: Micro-functions that obscure the routing workflow new hires must learn.
  • OCP theater: Abstract factories for one billing rule that changes yearly.
  • Missing rationale: “Async only” with no note that a logistics operator chose events for analytics replay, not for every read path.

Decision checklist

  • Are A logistics operator’s principles numbered, versioned in git, and each tied to a one-sentence rationale?
  • Does this service boundary map to one business capability and one primary reason to change?
  • Are shared databases, domain libraries, and sync call chains listed with explicit trade-offs?
  • Do cross-team integrations use published contracts (OpenAPI, events), not private types?
  • Is every feature tied to a current business requirement, not a hypothetical future product?
  • Does each remote integration define timeout, retry, and breaker behavior?
  • Was a principle exception documented in an ADR when the team had to break a rule?
  • Can a new hire explain the Routing/Billing split using a named principle?
