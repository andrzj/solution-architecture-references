Idempotency

An operation that produces the same result whether applied once or many times — the essential property for safe retries in distributed systems.

⏱ 7 min read

What it is

An idempotent operation leaves the system in the same state whether you run it once or many times with the same intent. Set balance to $5 twice—you still have $5. Increment twice—you added two, which is not idempotent.

Networks drop responses, clients retry, and brokers redeliver messages. Without idempotency, a harmless retry becomes a double charge, duplicate row, or second email. Design for safe retries and duplicates become wasted work, not corruption.

Why it exists

Delivery guarantees cluster around at-most-once (may lose), at-least-once (may duplicate), and exactly-once (hard and expensive). Most production pipelines choose at-least-once because it is resilient; idempotent handlers turn "processed twice" into "same outcome as once."

HTTP already encodes this split: GET, PUT, and DELETE are defined as idempotent; POST is not. Browsers and proxies may retry safe methods; POST needs keys or dedupe because side effects are expected.

When to use

  • Payments, refunds, transfers—anything that moves money or inventory.
  • APIs that create, charge, notify, or start workflows and may see client retries.
  • Queue and stream consumers on at-least-once brokers.
  • Webhook endpoints—the sender will retry on non-2xx responses.
  • Saga or choreography steps that can rerun after timeouts.

When not to use

  • Side-effecting operations should default to idempotent unless duplicates are explicitly harmless.
  • Reads need no extra machinery—they are idempotent by nature.
  • When you truly need end-to-end exactly-once semantics, pair idempotency with transactional outbox or broker features—not keys alone.

Typical architecture

The usual pattern is an idempotency key: the client sends a stable id (often a UUID) per logical action. The server looks up the key—if seen, return the stored response; if not, run the work, persist key plus outcome, then respond. The sequence diagram shows that flow.

Pros and cons

Pros

  • Retries after timeouts do not duplicate side effects.
  • At-least-once messaging stays simple and reliable.
  • Many flows avoid two-phase commit when steps can safely rerun.
  • Blips and pod restarts recover with automatic retry instead of manual repair.

Cons

  • Shared key store plus TTL management adds operational surface area.
  • Keys expire—retries outside the window may run twice (payments often use 24h).
  • Physical or external effects (email sent, printer fired) cannot be un-done by dedupe alone.
  • Per-pod memory caches break idempotency behind load balancers.

Implementation notes

Idempotency key storage: All instances must share one store—Redis, DynamoDB, or a relational table—not process memory. Commit the key and the business outcome in one transaction when possible so you never charge without recording the key, or record the key without finishing the work. For external calls (payment gateways), outbox or similar patterns keep local state durable before you confirm upstream.

Database-level idempotency: PostgreSQL INSERT ... ON CONFLICT (idempotency_key) DO NOTHING, SQLite INSERT OR IGNORE, and MySQL INSERT IGNORE make create paths safe. Updates like UPDATE orders SET status='paid' WHERE order_id=? AND status='pending' are naturally idempotent—the second run updates zero rows. Version columns add optimistic locking when you need stricter guards.

Idempotent message consumers: Persist processed message ids (or business ids) and check before side effects. Kafka offsets help inside the consumer group, but HTTP calls, emails, and DB writes still need application-level dedupe.

Common failure modes

  • Deduped API, duplicate email: Key stops double charge but code still sends mail on every entry path.
  • Key reuse with different payload: Same key, different amount—server must reject mismatched replays.
  • TTL too short: Offline mobile client retries after expiry and pays twice.
  • Local key cache: Retry hits another pod with an empty map—work runs again.

Decision checklist

  • Does this path have side effects that must not double on retry?
  • Can clients send a stable idempotency key per logical operation?
  • Is the key store shared by every replica of the service?
  • Are key insert and side effect committed together when the datastore allows?
  • Does TTL cover realistic client retry horizons?
  • Are downstream calls, emails, and events guarded the same way?
  • For consumers, is dedupe persisted by message id, not only in RAM?

Example use cases

  • Stripe charges with Idempotency-Key—timeout plus retry returns the original charge, not a second one.
  • Order API with ON CONFLICT (idempotency_key) DO NOTHING—mobile retries do not spawn duplicate orders.
  • SQS handler writing message ids to DynamoDB—second delivery is acknowledged and skipped.
  • Kubernetes controllers reconciling desired vs actual state—loops rerun safely until the cluster matches spec.

Related patterns

  • Eventual Consistency — at-least-once delivery in eventually consistent systems is the primary driver for needing idempotent consumers.
  • Backward Compatibility — idempotency keys and retry behavior are part of the API contract and must be considered during API evolution.
