Idempotency

An operation that produces the same result whether applied once or many times — the essential property for safe retries in distributed systems.

⏱ 7 min read

What it is

An idempotent operation leaves the system in the same state whether you run it once or many times with the same intent. Set balance to $5 twice—you still have $5. Increment twice—you added two, which is not idempotent.

Networks drop responses, clients retry, and brokers redeliver messages. Without idempotency, a harmless retry becomes a double charge, duplicate row, or second email. Design for safe retries and duplicates become wasted work, not corruption.

Idempotency keys bind one logical intent to one outcome: repeating the same key must return the same response body, while reusing a key with different parameters should fail fast instead of masking a client bug.

Why it exists

Delivery guarantees cluster around at-most-once (may lose), at-least-once (may duplicate), and exactly-once (hard and expensive). Most production pipelines choose at-least-once because it is resilient; idempotent handlers turn "processed twice" into "same outcome as once."

HTTP already encodes this split: GET, PUT, and DELETE are defined as idempotent; POST is not. Browsers and proxies may retry safe methods; POST needs keys or dedupe because side effects are expected.

Sagas retry timed-out steps; compensation handlers must tolerate duplicate delivery the same way forward steps do. Stable keys derived from sagaId and step name keep choreography safe when the orchestrator cannot tell success from a lost ACK.

When to use

  • Design for idempotency on payments, refunds, transfers, and anything else that moves money or inventory.
  • Design for it on APIs that create, charge, notify, or start workflows and may see client retries.
  • Design for it on queue and stream consumers that use at-least-once brokers.
  • Design for it on webhook endpoints, because senders retry on non-2xx responses.
  • Design for it on saga or choreography steps that can rerun after timeouts.
  • Design for it on mobile offline outboxes that drain queued POSTs when connectivity returns.
  • Design for it on admin replay tools that re-drive failed jobs from an operations console.

When not to use

  • Side-effecting operations should default to idempotent design unless duplicates are explicitly harmless.
  • Reads need no extra idempotency machinery, because they are idempotent by nature.
  • When you truly need end-to-end exactly-once semantics, pair idempotency keys with a transactional outbox or broker features — keys alone are not enough.
  • When an operation is intentionally append-only (audit events, immutable ledger entries), use a unique business key per append instead of recycling keys.

Typical architecture

The usual pattern is an idempotency key: the client sends a stable id (often a UUID) per logical action. The server looks up the key—if seen, return the stored response; if not, run the work, persist key plus outcome, then respond. The sequence diagram shows that flow.

Gateways and BFFs should forward keys unchanged to domain services; stripping headers breaks dedupe when the edge times out but the origin already committed work. Document required headers in OpenAPI and enforce them in contract tests the same way you enforce auth scopes.

Rate-limit idempotency table growth: archive completed keys after TTL to cold storage for dispute investigations, but keep hot indexes bounded so lookup latency stays flat as traffic grows.

Pros and cons

Pros

  • Retries after timeouts do not duplicate side effects.
  • At-least-once messaging stays simple and reliable.
  • Many flows avoid two-phase commit when steps can safely rerun.
  • Blips and pod restarts recover with automatic retry instead of manual repair.
  • Saga steps can rerun without manual reconciliation when keys are deterministic.
  • Clients gain freedom to backoff aggressively once keys are mandatory on mutating APIs.

Cons

  • Shared key store plus TTL management adds operational surface area.
  • Keys expire—retries outside the window may run twice (payments often use 24h).
  • Physical or external effects (email sent, printer fired) cannot be un-done by dedupe alone.
  • Per-pod memory caches break idempotency behind load balancers.
  • Payload fingerprinting and saga key schemes complicate API governance.
  • Cached replay bodies must stay compatible as response schemas evolve.

Implementation notes

Idempotency key storage: Every replica must read the same store—Redis conditional sets, DynamoDB attribute_not_exists, or a relational unique index—not a pod-local map. Persist key, response code, and serialized body together with the business write when the database allows one transaction. Return identical HTTP semantics on replay so mobile clients treat timeouts as safe.

Key design: Accept Idempotency-Key on POST (and other unsafe verbs your style guide lists). Clients mint one UUID per user gesture; sagas use {sagaId}:{step}. Store a hash of normalized request fields—duplicate keys with different amounts must answer 409 Conflict, not the prior payment id.

Database-level idempotency: PostgreSQL INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING id tells you insert vs duplicate in one round trip. Conditional updates such as UPDATE orders SET status='paid' WHERE order_id=? AND status='pending' noop on the second attempt. Version columns add optimistic guards when multiple writers share a row.

Outbox and gateways: Commit local state and an outbox event before calling Stripe or another processor with the same idempotency key the API accepted. Workers that crash after the provider succeeds but before the ACK can still finish by reading the stored outcome.

Idempotent message consumers: Insert message_id or a business natural key before side effects. Kafka offsets are not enough when the handler sends email or calls HTTP—saga compensations should record (sagaId, step) completion before telling the orchestrator the undo succeeded.

Testing: Property tests that fire the same keyed request N times in parallel should always yield one row and identical responses. Chaos tests that kill the pod after the provider succeeds but before the HTTP response should still leave the client able to retry safely.

API standards: Publish idempotency header requirements in your organization’s OpenAPI ruleset—Spectral or equivalent linters can fail CI when mutating routes omit documented key support on payment and provisioning paths.

Runbooks: When support replays a failed payment, operators should reuse the customer’s original idempotency key in the internal tool rather than minting a new one—document that procedure beside DLQ replay steps so night shifts do not accidentally double-capture during manual recovery.

In-flight state: Store three states per key—processing (first writer holds the lock), completed (return cached body), failed (optional, so retries do not hammer a known-bad request). Concurrent POSTs with the same key should get 409 or 202 while the first attempt runs, not spawn duplicate side effects. Stripe’s pattern is the de facto reference for payment APIs.

Message brokers: Kafka’s idempotent producer (PID + sequence) dedupes within a producer session; consumers still need business-key dedupe for cross-session retries. The IETF Idempotency-Key header draft standardizes HTTP usage beyond individual vendors.

Operations: Monitor idempotency store size, key age distribution, and replay rate (same key, multiple GETs of cached outcome). Alert when TTL is shorter than the 99th percentile client retry window.

Common failure modes

  • Guarded API, leaky side effects: Payment dedupes but confirmation email fires on every code path.
  • Key collision across intents: Same key with a new amount replays the old capture unless payload hashes are enforced.
  • Expired key window: An offline client retries after TTL and creates a second charge.
  • Sharded memory store: Load balancer lands the retry on a pod that never saw the first attempt.
  • Racing first requests: Parallel POSTs with one key both pass lookup—only a unique constraint or conditional write should win.
  • External success, local gap: Provider captures funds but the service dies before the idempotency row commits—reconcile by provider id before responding.
  • Saga step keyed by transport only: Orchestrator retries generate fresh HTTP ids and bypass dedupe unless business keys are stable.
  • Non-idempotent undo: releaseHold invoked twice drives inventory negative.

Decision checklist

  • Does this path have side effects that must not double on retry?
  • Can clients send a stable idempotency key per logical operation?
  • Do saga forward and compensation steps share deterministic key rules?
  • Is the key store shared by every replica of the service?
  • Are key insert and side effect committed together when the datastore allows?
  • Does the API reject same-key requests whose payload fingerprint differs?
  • Does TTL cover offline client and orchestrator retry horizons?
  • Are emails, webhooks, outbox events, and provider calls deduped equally?
  • For consumers, is dedupe persisted by message or business key, not RAM only?
  • Do tests cover parallel duplicates and post-crash replay?

Example use cases

  • Illustrative scenario — Meridian Commerce’s Payment API requires an Idempotency-Key on POST /payments — a mobile timeout and retry returns the original payment_id, not a second capture.
  • Illustrative scenario — Meridian’s Order service uses INSERT ... ON CONFLICT (idempotency_key) DO NOTHING so flaky checkout clients do not spawn duplicate orders when the response is lost.
  • Illustrative scenario — Fulfillment’s OrderPlaced consumer records processed event ids in DynamoDB — at-least-once Kafka delivery acknowledges duplicates without creating a second pick task.
  • Illustrative scenario — Meridian’s payment-processor webhook handler stores delivery ids — the processor’s retries on non-2xx responses replay the same outcome instead of posting ledger entries twice.
  • Illustrative scenario — Checkout saga at Meridian keys {sagaId}:capture and {sagaId}:release — orchestrator timeouts replay compensation without double-releasing stock.
  • Illustrative scenario — Meridian’s finance batch replayer passes the same Idempotency-Key when operators re-submit a stuck payout file—ledger postings dedupe even though the browser session is new.
