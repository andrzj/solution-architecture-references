Bounded Contexts

Explicit boundaries within which a domain model applies and terms have consistent meaning — the cornerstone of modular system design.

⏱ 7 min read

What it is

A bounded context is an explicit boundary where a domain model and its ubiquitous language (shared terms between devs and domain experts) stay consistent.

Outside that boundary, the same word may mean something else — and that is normal, not a modeling bug.

At Meridian Commerce, “Customer” in the Catalog context is a buyer browsing SKUs. In Order, it is a party placing a checkout. In Payment, it is a bill-to account with a vaulted card. One noun, three models — forcing a single enterprise Customer table is how monoliths accumulate accidental complexity.

Each Meridian context owns its data and vocabulary. Contexts integrate through declared relationships (context maps), not through shared entity graphs.

Why it exists

Teams assume shared words imply shared meaning. That assumption breaks when sales, fulfillment, and finance scale separately.

A canonical “one true model” for Customer, Product, and Order becomes a merge conflict factory: every field change ripples to unrelated teams.

Bounded contexts make differences explicit. Meridian’s Payment team can evolve PCI-related fields without forcing Catalog to accept billing concepts. Integration is deliberate — ACL, events, published APIs — instead of implicit table joins.

When to use

  • Yes: multiple capabilities reuse nouns with different rules (Meridian Catalog vs Order vs Payment).
  • Yes: drawing microservice boundaries — contexts come from domain cohesion, not org chart alone.
  • Yes: peeling apart a monolith — event storming often reveals natural seams between contexts.
  • Yes: several teams share a repo but need clear write ownership.
  • Yes: deciding which service publishes OrderPlaced vs which only consumes it.

When not to use

  • No: a small single-domain CRUD app with one team — context ceremony adds friction.
  • No: one context per database table — contexts track capabilities, not schemas.
  • No: insisting one microservice per context — one context can be a modular monolith or several services later.

Pros and cons

Pros

  • Meridian stops arguing over a single mega-Product entity — Catalog and Inventory model what each capability needs.
  • Contexts deploy independently when data and language stay inside the boundary.
  • Team ownership maps cleanly when Conway’s Law aligns with context lines.
  • Integrations are visible on the context map instead of hidden in shared SQL.
  • New subdomains add new contexts instead of stretching the old model.

Cons

  • Wrong boundaries are costly — discovery workshops are cheaper than constant cross-team rework.
  • Cross-context reporting needs read models or events, not one join across three databases.
  • Duplicated facts (SKU attributes in Catalog and pick lists in Fulfillment) are intentional, not DRY failures.
  • Misaligned teams fight the map if leadership ignores Conway’s Law.

Implementation notes

Finding boundaries: Meridian ran event storming on checkout-to-delivery. Clusters around “merchandising,” “stock reservation,” “payment capture,” and “warehouse pick” became context candidates. Red flags: two teams edit the same noun, different change cadences, or recurring ownership fights.

Anti-Corruption Layer: Order integrates with a legacy card processor. Meridian’s Payment ACL maps processor tokens into Payment’s PaymentIntent aggregate — Order never imports processor DTOs.

Contexts vs microservices: Fulfillment and Inventory might live in one modular monolith until ops needs independent scaling. Do not split one invariant across services that need distributed two-phase commit — keep the transaction inside one context.

Published language: OrderPlaced is the contract from Order to Fulfillment. Schema versioning and backward compatibility rules apply at that edge.

Common failure modes

  • Shared tables: Order and Payment both write orders.payment_status — contexts collapse into coupling.
  • Entity-sized contexts: “AddressContext” because there is an Address table — too small to own a language.
  • No ACL: Fulfillment imports Catalog ORM entities directly; Catalog refactors break the warehouse.
  • Map spray: Twenty contexts before the first production flow ships — boundaries guess wrong.
  • Paper language: Slide says “bounded context” but docs and code still use one generic DTO everywhere.

Decision checklist

  • Did Meridian run event storming or structured interviews before cutting services?
  • Does each context publish a glossary developers and domain experts share?
  • Does each context own its store with no cross-context table writes?
  • Is every cross-context edge labeled on the context map (ACL, customer/supplier, shared kernel)?
  • Do team ownership lines match context lines closely enough to reduce handoffs?
  • Do legacy or SaaS integrations enter through an ACL module?
  • Can any business invariant be enforced without a distributed transaction across contexts?

Example use cases

Meridian Commerce uses one map end to end:

  • Contexts: Catalog, Inventory, Order, Payment, Fulfillment — each team, datastore, and glossary.
  • Shared kernel: Catalog and Inventory share a guarded Product ID format, nothing else.
  • ACL: Payment wraps the external processor; Order only sees Meridian payment commands.
  • Event handoff: Order publishes OrderPlaced; Fulfillment subscribes and builds its own pick aggregate — no shared Order ORM.
