Bounded Contexts

Explicit boundaries within which a domain model applies and terms have consistent meaning — the cornerstone of modular system design.

⏱ 7 min read

What it is

A bounded context is an explicit boundary where a domain model and its ubiquitous language (shared terms between devs and domain experts) stay consistent.

Outside that boundary, the same word may mean something else — and that is normal, not a modeling bug.

At an e-commerce retailer, “Customer” in the Catalog context is a buyer browsing SKUs. In Order, it is a party placing a checkout. In Payment, it is a bill-to account with a vaulted card. One noun, three models — forcing a single enterprise Customer table is how monoliths accumulate accidental complexity.

Each context owns its data and vocabulary. Contexts integrate through declared relationships (context maps), not through shared entity graphs.

In sales, “Customer” may be a prospect with pipeline stage and discount eligibility; in support, the same person is an account with open tickets and SLA tier. Folding both into one enterprise entity forces nullable columns and approval wars over whose definition wins.

Why it exists

Teams assume shared words imply shared meaning. That assumption breaks when sales, fulfillment, and finance scale separately.

A canonical “one true model” for Customer, Product, and Order becomes a merge conflict factory: every field change ripples to unrelated teams.

Bounded contexts make differences explicit. A Payment team can evolve PCI-related fields without forcing Catalog to accept billing concepts. Integration is deliberate — ACL, events, published APIs — instead of implicit table joins.

Large systems fail when everyone assumes shared nouns imply shared semantics. Contexts turn that ambiguity into an integration problem with named edges, owners, and translation rules instead of a silent model merge.

When to use

  • Define bounded contexts when multiple capabilities reuse nouns with different rules—for example Catalog versus Order versus Payment in e-commerce.
  • Define them when you draw microservice boundaries, because contexts come from domain cohesion, not the org chart alone.
  • Define them when you peel apart a monolith and event storming reveals natural seams.
  • Define them when several teams share a repository but need clear write ownership per capability.
  • Define them when you decide which service publishes OrderPlaced and which services only consume it.

When not to use

  • Skip heavy context mapping for a small single-domain CRUD app owned by one team, because the ceremony adds friction without payoff.
  • Do not create one context per database table, because contexts track capabilities, not schemas.
  • Do not insist on one microservice per context, because one context can live in a modular monolith or split into services later.

Maps are living documents: refresh them when teams reorganize, when a SaaS vendor replaces a legacy module, or when a new regulated subdomain (tax, export control) needs its own language. The goal is not prettier boxes—it is visible translation cost every time data crosses a boundary.

Pros and cons

Pros

  • Teams stop arguing over a single mega-Product entity — Catalog and Inventory model what each capability needs.
  • Contexts deploy independently when data and language stay inside the boundary.
  • Team ownership maps cleanly when Conway’s Law aligns with context lines.
  • Integrations are visible on the context map instead of hidden in shared SQL.
  • New subdomains add new contexts instead of stretching the old model.

Cons

  • Wrong boundaries are costly — discovery workshops are cheaper than constant cross-team rework.
  • Cross-context reporting needs read models or events, not one join across three databases.
  • Duplicated facts (SKU attributes in Catalog and pick lists in Fulfillment) are intentional, not DRY failures.
  • Misaligned teams fight the map if leadership ignores Conway’s Law.

Implementation notes

Finding boundaries: Event storming on checkout-to-delivery often surfaces clusters around “merchandising,” “stock reservation,” “payment capture,” and “warehouse pick” as context candidates. Red flags: two teams edit the same noun, different change cadences, or recurring ownership fights.

Anti-Corruption Layer: Order integrates with a legacy card processor. Payment’s ACL maps processor tokens into its PaymentIntent aggregate — Order never imports processor DTOs.

Contexts vs microservices: Fulfillment and Inventory might live in one modular monolith until ops needs independent scaling. Do not split one invariant across services that need distributed two-phase commit — keep the transaction inside one context.

Published language: OrderPlaced is the contract from Order to Fulfillment. Schema versioning and backward compatibility rules apply at that edge.

Context map patterns: Label each edge—customer/supplier when downstream influences upstream APIs, conformist when you must accept a vendor model wholesale, open host service when many consumers share one published API. Shared kernel is reserved for a tiny, jointly governed slice (product ID format), not a dumping ground for convenience fields.

Common failure modes

  • Shared tables: Order and Payment both write orders.payment_status — contexts collapse into coupling.
  • Entity-sized contexts: “AddressContext” because there is an Address table — too small to own a language.
  • No ACL: Fulfillment imports Catalog ORM entities directly; Catalog refactors break the warehouse.
  • Map spray: Twenty contexts before the first production flow ships — boundaries guess wrong.
  • Paper language: Slide says “bounded context” but docs and code still use one generic DTO everywhere.
  • Unlabeled map edges: Teams integrate through ad hoc REST without documenting conformist vs ACL posture—refactors on the upstream side break unknown downstream assumptions.

Decision checklist

  • Did you run event storming or structured interviews before cutting services?
  • Does each context publish a glossary developers and domain experts share?
  • Does each context own its store with no cross-context table writes?
  • Is every cross-context edge labeled on the context map (ACL, customer/supplier, shared kernel)?
  • Do team ownership lines match context lines closely enough to reduce handoffs?
  • Do legacy or SaaS integrations enter through an ACL module?
  • Can any business invariant be enforced without a distributed transaction across contexts?
  • Is cross-context reporting fed by events or read models instead of live joins across foreign schemas?
