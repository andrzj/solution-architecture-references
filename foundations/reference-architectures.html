Reference Architectures

Pre-validated blueprints for common system topologies — accelerating design, enabling governance, and providing proven starting points.

⏱ 6 min read

What it is

A reference architecture (RA) is a validated blueprint for a recurring system shape — web portals, event pipelines, data planes — that teams adapt instead of debating every cross-cutting choice from zero.

Northwind Logistics maintains an internal RA called ra-product-service: container image baseline, Postgres + Redis, standard GitHub Actions pipeline, OpenTelemetry hooks, and approved AWS accounts. When the dispatch group launched shipment-tracking, they forked that RA and swapped the domain module — they did not redesign TLS, secrets, or deploy gates.

RAs also arrive from outside the company: AWS Well-Architected, the Azure Architecture Center, and industry models such as HL7 FHIR for healthcare interoperability.

Why it exists

Every greenfield service once rediscovered the same incident lessons — missing health checks, weak IAM boundaries, no standard dashboards. Northwind’s platform team folded those lessons into ra-product-service so new teams inherit guardrails instead of outages.

RAs compress onboarding. Telling a contractor “FieldOps portal follows our three-tier web RA” communicates tiers, approved edge services, and data-zone rules faster than a week of whiteboards.

When to use

  • Start from an RA when Northwind’s new workload matches a known class — customer-facing web portal, Kafka-backed integration, or the standard product microservice.
  • Adopt organization-wide RAs when several teams must share compliance, observability, and deployment patterns without a central architect in every review.
  • Lean on a cloud provider’s RA when Northwind onboards a new region or account and needs environment-specific guidance for edge, identity, and networking.
  • Use a target-state RA during legacy migration so FieldOps and dispatch teams share a concrete picture of where the monolith is heading.
  • Reach for an RA when a squad lacks depth in a domain (for example ML serving) and needs a vetted starting topology while they learn.

When not to use

  • Do not force the product RA on a real-time control system with safety timing requirements the RA never contemplated — reject or amend it in an ADR with evidence.
  • Do not treat vendor RAs as neutral; they promote that vendor’s managed services, which may or may not fit Northwind’s cost and portability constraints.
  • Do not skip quality-attribute work because a diagram looks complete; the RA is a starting point, not proof the SLOs are met.

Pros and cons

Pros

  • Northwind’s dispatch team stood up shipment-tracking in weeks because networking and CI were pre-approved in the RA fork.
  • Security and SRE sign off faster when every fork includes the same WAF, IAM boundary, and dashboard pack.
  • Executives audit compliance against a finite catalog of approved RAs instead of one-off diagrams.
  • Contractors and acquisitions learn Northwind’s vocabulary once — “three-tier web RA” — and reuse it across portals.
  • Vendor RAs such as Well-Architected track new service guidance; platform teams port relevant deltas into internal docs.

Cons

  • Dogmatic RA mandates blocked a low-latency telemetry experiment that needed edge compute the RA did not list.
  • AWS-centric RAs nudged teams toward managed services even when a simpler self-managed option was cheaper.
  • Internal RAs rot when nobody owns updates; Northwind once shipped a template still referencing a retired CI runner.
  • Teams that fork without reading the RA cannot justify deviations when PCI auditors ask why a database sits in a public subnet.

Implementation notes

Well-Architected reviews: Northwind runs a lightweight Well-Architected pass before production for every RA fork — operations, security, reliability, performance, cost, and sustainability pillars — and files gaps as ADRs or backlog items.

C4 as drawing RA: Context, Container, Component, and Code levels are mandatory in architecture packs so reviewers compare diagrams instead of fighting notation.

Deviation path: Teams propose RA changes through the architecture guild; approved deviations become ADRs and, when repeated, merge back into ra-product-service or the web RA repo.

Fork checklist: Identity integration, secrets, observability, backup, and runbook stubs ship with every fork — dispatch cannot disable them without an explicit exception.

Common failure modes

  • Blank fork: A team copies the repo but strips “unused” Terraform modules and loses the private subnet layout the RA encoded.
  • Stale RA: FieldOps still points new hires at a portal RA that lists an end-of-life Node LTS.
  • Universal microservices RA: Northwind applied the event-driven RA to a five-user internal tool; ops cost dwarfed value.
  • Silent drift: Shipment-tracking added a public S3 bucket without an ADR; the estate no longer matches the compliance map.
  • RA without QAs: Teams treat the diagram as approval while checkout-scale load was never part of the RA’s assumptions.

Decision checklist

  • Does this workload match the problem class the RA was written for (web portal vs stream processor vs batch)?
  • Have we written down the QA assumptions baked into the RA and confirmed they match this product?
  • Did we review vendor-specific bias and evaluate at least one portable alternative for critical components?
  • Is the RA version pinned in the repo, and was it updated or reviewed recently enough for this launch?
  • Is there a published process to request RA deviations with architecture guild approval?
  • Does every approved deviation have an ADR that explains risk accepted?
  • Is a named owner responsible for merging lessons from forks back into the canonical RA?

Example use cases

  • Northwind shipment-tracking: Forked ra-product-service, kept Postgres/Redis/CI defaults, added domain modules and dispatch Kafka consumers.
  • Northwind FieldOps portal: Follows the three-tier web RA mapped to CloudFront → ALB → Fargate → Aurora; mobile clients share the same API tier.
  • Northwind cloud governance: Platform runs Well-Architected reviews on each new account workload before granting production traffic.
