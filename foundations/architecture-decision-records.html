Architecture Decision Records (ADRs)

Lightweight records that capture the context, decision, and consequences of significant architectural choices — making decisions explicit and searchable.

⏱ 5 min read

What it is

An Architecture Decision Record (ADR) is a short, durable note that captures why the team made a significant design choice.

Each ADR states the context (constraints and forces), the decision (what you chose), and the consequences (trade-offs you accepted).

At Northwind Logistics, the platform team keeps ADRs as numbered Markdown files in docs/decisions/ next to the services they govern. When a new engineer asks why dispatch events go through Kafka instead of direct HTTP calls, ADR-0002 explains the coupling and replay requirements that existed when that call was made.

The decision ages; the context is what future readers need. ADRs preserve that context in git, where people already search for answers.

Why it exists

Architecture choices outlive the people who made them. Staff turnover, shifting product goals, and forgotten incident postmortems erase the reasoning behind “weird” design.

Without ADRs, Northwind’s dispatch team might rip out Kafka and reintroduce the same ordering bugs the original design avoided.

Writing an ADR before acceptance also forces the team to name alternatives and honest downsides. That short writing step often surfaces weak rationale before code locks the choice in.

When to use

  • Write an ADR when undoing the choice would take meaningful engineering effort, such as a multi-service migration or data movement.
  • Write an ADR when Northwind selects infrastructure other teams will inherit, including the database, broker, cloud region, or auth model.
  • Write an ADR when you draw or move service boundaries, event contracts, or data ownership lines.
  • Write an ADR when you deliberately break an architecture principle or org standard so the exception stays visible.
  • Write an ADR when you pick a simpler or domain-specific pattern over a popular default and need that rationale in git.

When not to use

  • Skip an ADR for local implementation choices that do not change structure or quality attributes, such as naming or private algorithms.
  • Skip an ADR for decisions you can reverse in a single pull request without consumer impact.
  • Do not replace feature design documents with ADRs; they complement specs, they do not substitute for them.
  • Do not write post-hoc ADRs to justify code already in production; they read as rationalization, not discovery.

Typical architecture

Northwind stores ADRs under docs/decisions/ as NNNN-short-title.md. Once accepted, a file is not edited; a later choice creates a new ADR that marks the old one Superseded. That chain shows how dispatch messaging evolved without losing history.

Pros and cons

Pros

  • Low ceremony: one to two pages, not a hundred-page architecture volume.
  • Versioned with code — blame, search, and PR review work the same as for application changes.
  • Keeps the “why” when Northwind revisits Kafka, Postgres, or gRPC years later.
  • Architects explain once; consuming teams read the record instead of scheduling another meeting.
  • Structured sections make gaps in thinking visible before merge.

Cons

  • Only valuable if written while the debate is live — late ADRs lack options and rejected alternatives.
  • Uncurated folders become noise; deprecated ADRs need explicit status updates.
  • Teams can treat ADRs as rubber stamps after the fact.
  • Political and budget context may stay tacit unless you deliberately include it.

Implementation notes

Start with Nygard, grow into MADR: Northwind’s first ADRs use Context, Decision, and Consequences. When disagreements repeat, they add MADR’s “considered options” table. Default template: Title, Status, Context, Decision, Consequences — add sections only when pain proves you need them.

Status workflow: Proposed ADR-0004 (gRPC for internal APIs) collects comments in a PR. Accepted ADR-0002 binds the org until replaced. Deprecated marks dead systems (legacy monolith decommissioned). Superseded links ADR-0005 to ADR-0001 when Aurora replaces plain Postgres — never delete the old file.

Tooling: adr-tools handles numbering and supersede links. log4brains helps when dozens of ADRs need a browseable index. A README table in docs/decisions/ is enough for a small platform team.

Reversibility test: If undoing the choice means coordinated migrations across Northwind’s dispatch, billing, and mobile clients, write the ADR before the first production deploy. Team disagreement on the same topic is also a hard trigger — the ADR becomes the resolution artifact.

Common failure modes

  • Post-hoc rationalization: Northwind ships Kafka, then writes ADR-0002 to defend it — readers see no rejected options.
  • Stale accepted status: ADR-0001 still says Postgres is primary after Aurora cutover because nobody marked it Superseded.
  • Context-free decisions: “We use Kafka” with no note on peak load, ordering, or ops skills on call.
  • ADR only for megaprojects: Medium choices (shared library vs copy-paste) repeat the same debates.
  • Wiki exile: ADRs live in Confluence, drift from repos, and stop getting updated.

Decision checklist

  • Would reversing this choice require coordinated work across multiple Northwind services or clients?
  • Does the ADR state constraints (latency, compliance, team skills) that existed at decision time?
  • Are at least two real options documented, including “do nothing for now”?
  • Are negative consequences listed, not only benefits?
  • Is the file under docs/decisions/ in the same repo as the affected code?
  • Is status one of Proposed, Accepted, Deprecated, or Superseded?
  • Did another engineer review before Accepted?
  • If this replaces an earlier ADR, does it cite the superseded number?

Example use cases

Northwind’s story runs through one decision chain:

  • ADR-0001 (Accepted): Postgres as the dispatch service’s system of record — context: relational invariants, small ops team.
  • ADR-0002 (Accepted): Kafka for LoadAssigned and LoadDelivered events — context: multiple consumers, replay for analytics.
  • ADR-0004 (Proposed): gRPC between dispatch and routing — open for comment while REST still runs in production.
  • ADR-0005 (Supersedes 0001): Aurora Serverless after sustained growth — links back so auditors see deliberate migration, not drift.
