Foundations Consistency

Eventual Consistency

Replicas will converge to the same state given enough time without new updates — the consistency model behind most large-scale distributed systems.

⏱ 7 min read

What it is

Eventual consistency means replicas may disagree for a while, but if writes stop, every copy converges to the same state. It does not say how long convergence takes, and any single read might lag the latest write. Different clients can see different values at the same moment.

Amazon's Dynamo paper made the trade-off mainstream: accept writes locally, replicate in the background, and live with brief divergence instead of waiting for global agreement on every request. That pattern powers carts, caches, and global scale when stale beats unavailable.

Convergence is guaranteed only after writes quiesce—there is no bound on how long replicas may disagree while replication is active. CRDT merges and well-chosen session guarantees narrow the practical window without turning the store into a globally linearizable system.

Why it exists

Strong consistency needs coordination—read paths must confirm they have the newest write, which adds cross-replica round trips, fails when peers are down, and gets expensive across regions. At web scale, paying that cost on every read is often worse than tolerating temporary mismatch.

Eventual consistency lets each replica serve independently while anti-entropy or gossip catches up later. DNS is the familiar example: a record change can take hours to spread, yet resolvers answer instantly from local state billions of times per day.

Bounded contexts in microservices amplify the pattern: Order, Inventory, and Fulfillment each hold authoritative local state and learn about foreign changes through events—downstream readers should assume lag unless an API explicitly offers a linearizable read model.

When to use

  • Choose eventual consistency when profiles or preferences can show an old avatar for a short time without harm.
  • Choose it for social counters and rankings where approximate totals are acceptable.
  • Choose it for shopping carts and session blobs where availability matters more than perfect contents.
  • Choose it for metrics and analytics that are approximate by nature.
  • Choose it for CDN and edge caches that are intentionally TTL-stale.
  • Choose it for telemetry streams where each reading is a time-stamped fact, not an authoritative balance.
  • Choose CRDT-backed collaborative fields when multiple writers edit the same logical document from different regions.
  • Choose it for read models rebuilt from an event log where consumers explicitly track offsets and versions.

When not to use

  • Do not use eventual consistency for balances, payments, or ledger lines where stale reads cause real money errors.
  • Do not use it for inventory with oversell risk when two nodes might both think one unit remains.
  • Do not use it for permissions or authorization where a revoked grant must disappear quickly.
  • Do not use it for workflows where two readers could make conflicting irreversible decisions on divergent data.
  • Do not use it when regulators require provable read-after-write freshness without client session aids.

Typical architecture

Pros and cons

Pros

  • Local reads and writes without quorum waits—latency stays low at scale.
  • Replicas keep serving through partitions and partial outages.
  • Throughput grows with replica count instead of hitting a coordination ceiling.
  • Multi-region deployments can favor local writes with async cross-region catch-up.
  • CRDT-backed fields converge without a dedicated merge coordinator.
  • Session tokens can give one user a tighter view without paying global quorum on every read.

Cons

  • Users can see different answers at once—confusing or dangerous depending on data.
  • Concurrent writes need merge rules (LWW, vector clocks, CRDTs, or app logic).
  • No bound on staleness—"eventual" can stretch to seconds under load.
  • Developers must label which operations are safe on possibly stale reads.
  • Event-driven boundaries stack replica lag on top of consumer delay.
  • Incident analysis needs version metadata, not only wall-clock timestamps.

Implementation notes

Last-write-wins (LWW): Tag each mutation with a timestamp; the highest tag wins on merge. Cassandra and DynamoDB default here. Clock skew can discard a legitimate update while still returning success to the writer—hybrid logical clocks (HLCs) couple physical time with per-node counters to reduce but not eliminate that risk. Reserve LWW for low-contention fields where losers can be reconstructed from an audit log.

Vector clocks: Attach a per-replica counter vector to each version so the store can flag concurrent siblings instead of picking a silent winner. Application code merges siblings, shows both values, or branches like Riak. Expect larger payloads and explicit merge code in the service layer.

CRDTs: Pick types whose merge is commutative and associative—G-Counter for grow-only counts, PN-Counter when increments and decrements must compose, OR-Set for add/remove membership without lost elements. State-based CRDTs ship snapshots; op-based CRDTs replicate operations. Use them for collaborative lists, distributed presence, and any counter LWW would flatten to one winner.

Repair paths: Gossip with Merkle trees finds divergent ranges; read repair fixes hot keys on the query path. Size replication throughput for peak write rate so repair keeps pace—otherwise dashboards showing "millisecond eventual" lie during traffic spikes.

Session guarantees: Sticky routing, local-quorum reads after local writes, or client-held min-read timestamps implement read-your-writes and monotonic reads for one session. Document which REST endpoints require session tokens versus which accept arbitrary replica lag.

Observability: Export per-replica lag histograms, repair queue depth, and sibling-conflict counters so SLOs reference measured staleness instead of marketing copy. Alert when convergence p99 exceeds the threshold product committed to in ADRs.

API contracts: Mark read endpoints that may return stale bodies with explicit version or asOf fields so clients do not infer linearizable inventory from eventually consistent browse responses.

Staleness budgets: Product should sign maximum staleness per entity type—catalog browse might allow 30s, cart contents 0s (session stickiness), inventory hold 0s (conditional write). SRE dashboards compare measured replica lag p99 against those budgets, not against generic “eventual” marketing.

CALM insight: The CALM theorem (Hellerstein and Alvaro) separates programs that need coordination for correctness from those that converge without it—use it when arguing whether a workflow can be AP with CRDTs or must stay CP. See Keeping CALM: When Distributed Consistency is Easy for formal criteria.

Convergence guarantees: Eventual consistency promises that if updates stop, all replicas share the same value—but says nothing about bound while writes continue. Operational SLOs must state measured replica lag (p50/p99) and repair throughput, not the word “eventual” alone. Under sustained load, anti-entropy must keep pace or lag grows without bound.

Session guarantees (Terry et al.): Weaker than linearizability but stronger than blind eventual reads: read-your-writes (session sees its own updates), monotonic reads (never go backward in time within a session), monotonic writes (client’s writes apply in order), and writes-follow-reads (causal ordering relative to prior reads). Implement via sticky sessions, version tokens on cookies, or client-side readTimestamp passed to quorum reads—document which APIs honor which guarantee.

Hinted handoff: When a preferred replica is down, Cassandra-style coordinators store hints and replay when the replica returns—reducing visible staleness for hot keys without full quorum on every read. Hints have TTL and disk limits; backlog alerts indicate repair debt.

Anti-entropy vs read repair: Read repair fixes divergence when a query touches inconsistent replicas—cheap for hot keys, blind to cold data. Anti-entropy (Merkle-tree comparison, incremental repair jobs) scans ranges on a schedule—necessary for inventory keys that are rarely read but must still converge. Plan repair bandwidth: rule of thumb is sustained repair throughput ≥ peak write rate divided by replica count, or lag accumulates after spikes.

Measuring staleness: Export replication_lag_seconds per shard, sibling-version counters, and “stale read served” flags when clients request below minimum version. Compare p99 lag to signed staleness budgets (e.g., catalog 30 s, cart 0 s with stickiness). Incidents trigger when lag exceeds budget for more than N minutes, not when a single slow query appears.

When NOT to use eventual consistency: Double-spend prevention, seat inventory with fixed capacity, and safety interlocks need coordination or CP paths—do not patch with “we will reconcile later” without a legal and product story for users who acted on stale data.

Common failure modes

  • Clock skew with LWW: The faster node’s timestamp wins; the slower writer believes its update stuck.
  • Replication backlog: Under load, convergence stretches from milliseconds to seconds while SLOs still assume the happy path.
  • Session routing bug: Post-save refresh hits a cold replica—users resubmit and create duplicates.
  • Scalar counter under LWW: Parallel increments collapse to one bump—use CRDT counters or centralized aggregation.
  • Oversell on stale stock: Two checkouts read different replica quantities—hold inventory with conditional writes or a CP reserve store.
  • Monotonic-read break: Pagination walks backward in time when reads bounce across replicas.
  • Saga visibility lag: UI polls Fulfillment while Payment events are still in the broker backlog.
  • Live repair surprise: Anti-entropy rewrites keys applications treated as immutable after first write.

Decision checklist

  • Which entities must be strongly consistent vs eventually consistent?
  • What merge strategy applies per field: LWW, vector clocks, CRDT, or application merge?
  • Are counters and sets modeled with CRDT types instead of scalar LWW columns?
  • Do interactive APIs publish session guarantees where UX demands them?
  • What is measured p99 convergence under peak writes for each consumer?
  • Are money, inventory holds, permissions, and legal records excluded from eventual stores?
  • Do event consumers and saga steps stay idempotent through convergence windows?
  • Have partition, repair, and backlog scenarios been chaos-tested?
  • Are consistency rules documented per API operation, not only per cluster?
  • Does an ADR capture measurable acceptance criteria for staleness?

Example use cases

  • Illustrative scenario — At Meridian Commerce, the shopping cart is eventually consistent — items may flicker across replicas during faults, but the cart stays writable so checkout does not hard-fail on a partition.
  • Illustrative scenario — Meridian’s catalog CDN caches product images and list prices with TTL staleness; the checkout BFF re-reads authoritative price from Inventory before payment capture.
  • Illustrative scenario — OrderPlaced events reach Fulfillment seconds after Payment accepts capture — warehouse pick lists converge without locking Order and Fulfillment in one distributed transaction.
  • Illustrative scenario — Meridian’s merchandising CMS tolerates nightly deploy downtime; editors accept minutes of lag on draft previews while the customer-facing catalog prioritizes read availability over immediate consistency with the CMS.
  • Illustrative scenario — A family wishlist at Meridian uses an OR-Set CRDT at the edge so concurrent edits converge; checkout still reads authoritative price from Inventory before capture.
  • Illustrative scenario — During a regional partition, Meridian’s session service pins shoppers to the replica that accepted their last cart write so read-your-writes holds even though other regions still show older line items.

Related patterns

  • CAP Theorem — names the AP side of the partition trade-off that most eventual stores implement.
  • PACELC Theorem — compares EL versus EC latency when the network is healthy, not only during splits.
  • Idempotency — required at consumers because replication and messaging are usually at-least-once.
  • Saga Pattern — stitches multi-service workflows without one globally consistent database.
