Domain Modeling

Representing business concepts and rules in code — entities, value objects, aggregates, and the techniques that keep domain logic clean.

⏱ 8 min read

What it is

Domain modeling is how you represent business concepts and rules in code—orders, accounts, shipments, prescriptions—not as anonymous rows and DTOs, but as types that speak the organization’s ubiquitous language.

The goal is executable documentation: invariants live on aggregates, meaningful state changes surface as domain events, and infrastructure (persistence, messaging, HTTP) stays at the edges. A reader of Order.place() or a Money value object should recognize the same vocabulary domain experts use in workshops.

Tactical Domain-Driven Design gives the usual building blocks—entities, value objects, aggregates, domain events, repositories, and domain services—while strategic patterns such as bounded contexts decide where each model applies and where language may legitimately differ.

Why it exists

Without an explicit model, logic drifts into the anemic domain model anti-pattern: mutable data bags with getters and setters, while every rule hides in procedural service classes. Rules like “cancel only before ship” scatter across layers, become hard to test, and disappear from conversations with the business.

Co-locating behavior on the types it protects makes rules discoverable. When Order.cancel() enforces shipping state, you unit-test the rule without spinning up HTTP or SQL. That cohesion pays off across years of evolving regulation, pricing, and fulfillment policy.

Rich models also clarify where strong consistency ends. Aggregate boundaries mark the scope of invariants that must succeed or fail together—an idea that later informs service decomposition, though an aggregate is not automatically one microservice.

Testing benefits directly: domain rules expressed as methods on types need few mocks, survive refactors that move infrastructure, and show up in review as diffs on behavior—not buried SQL in application services.

When to use

  • Long-lived products whose business rules will keep changing and must stay traceable in code and reviews.
  • Teams that pair with domain experts and invest in a shared ubiquitous language—not only UI copy but type names and events.
  • Event-sourced or event-heavy designs where domain events are first-class facts, not afterthought integration DTOs.
  • Regulated domains that require auditable enforcement of policy in application code.
  • Microservice or modular monolith boundaries that should align with consistency clusters, even when deployment units differ.
  • Platforms replacing legacy modules where the hardest risk is losing implicit business rules embedded in stored procedures.

When not to use

  • Simple CRUD with few invariants—a thin service over tables is cheaper and clearer.
  • Teams that will not protect the domain layer from framework leakage—ceremony without discipline produces hollow DDD shapes.
  • Automatic one-aggregate-per-service mapping without checking operational cost, data ownership, and team boundaries.

Pros and cons

Pros

  • Rules sit beside the concepts they protect—easy to find, test, and change during refactors.
  • Immutable value objects reduce bugs from shared mutable state and primitive obsession.
  • Domain events integrate contexts without reaching inside another aggregate’s persistence.
  • Aggregates clarify transaction boundaries for designers and operators tuning contention.
  • Shared vocabulary with domain experts cuts mistranslation between requirements and code.

Cons

  • More design time up front than table-first CRUD, especially before ubiquitous language stabilizes.
  • ORMs and aggregates conflict unless loading boundaries, lazy graphs, and concurrency are deliberate.
  • Skill depth varies; coaching is required to avoid cargo-cult layering.
  • Over-modeling simple domains adds types nobody needed—match richness to rule complexity.

Implementation notes

Entities vs value objects: Entities carry identity across attribute changes—order #42 remains the same order after status moves to SHIPPED. Value objects are defined by their data—two Money(10, USD) instances interchange. Prefer immutability on values; “change” means replace. Wrapping primitives with OrderId, Email, and Money centralizes validation instead of scattering it in controllers.

Aggregate design: One root is the only entry for writes; invariants that must hold together stay inside the boundary. Reference other aggregates by identifier, not navigable object graphs. Keep aggregates small—roots that own catalog, customer, and inventory become lock magnets and obscure ownership.

Event Storming: Sticky notes for events, commands, aggregates, and policies on a timeline reveal language splits and seam candidates before code structure locks in. It aligns developers and experts faster than jumping straight to service diagrams.

Domain services: Use when a rule genuinely spans aggregates (for example, transferring value between two accounts) but still belongs in domain language. Distinguish them from application services, which coordinate use cases and persistence without embedding business policy.

Repositories and factories: Repositories rehydrate aggregates as whole consistency clusters; avoid exposing child entities that let callers bypass invariants. Factories encapsulate complex creation rules so constructors do not leak invalid aggregates into the model.

Anti-corruption at the edge: When translating foreign APIs or legacy schemas, map into your ubiquitous language at the boundary—never let alien field names become entity properties without an explicit translation layer.

Specification by example: Where rules are data-heavy, complement the model with examples and property tests keyed on invariants—not only happy-path unit tests—so refactors cannot weaken cancel rules or credit checks unnoticed.

Domain vs integration events: Domain events name what happened inside the model (OrderCancelled); integration events are the published wire shape other contexts consume—often with extra metadata and schema version. Map between them in the application layer or outbox publisher so refactoring entities does not break foreign subscribers.

Concurrency: Use optimistic versioning (@Version, row version column, or equivalent) on aggregate roots; on conflict, reload and retry or surface a business error. Hot aggregates may need sharding by business key or redesigning the invariant boundary—pessimistic locks across HTTP requests rarely scale.

Transactional outbox: Persist domain changes and outbound messages in one database transaction; a relay process publishes to the broker. This avoids dual-write races between the DB commit and the event bus without requiring distributed two-phase commit across contexts.

Common failure modes

  • Anemic model: Entities are structs; every rule sits in OrderService.
  • God aggregate: One root owns customer, catalog, and stock—contention and unclear ownership follow.
  • Leaky repository: Returning OrderLine to callers who mutate totals without passing through Order.
  • Events as wire DTOs: Names and payloads shaped only for integration, not for what the business said happened.
  • Silent aggregates: State changes with no events, forcing other contexts to poll or couple tightly.
  • Invariant bypass in tests: Suites construct invalid aggregates directly, masking production paths that should have failed earlier.

Decision checklist

  • Which invariants define each aggregate boundary—and what happens when they are violated?
  • Are primitives at the edge replaced with value types where meaning and validation matter?
  • Are value objects immutable in this language and runtime?
  • Do all writes go through the aggregate root, never around it?
  • Do meaningful operations publish domain events other teams can subscribe to?
  • Is the domain layer free of database, HTTP, and framework annotations?
  • Did domain experts participate in Event Storming (or equivalent) before locking the model?
  • Will a single-aggregate transaction stay small enough under peak load and contention?
  • When rules span contexts, is integration explicit through events or facades rather than shared tables?

Example use cases

  • Illustrative scenario — In Meridian Commerce’s Order context, an Order aggregate with OrderLine children and Money value objects enforces credit limits inside place(), not in a generic checkout orchestration layer.
  • Illustrative scenario — Meridian’s Payment context models PaymentIntent as the aggregate root; capture() and void() publish domain events that Order and Fulfillment consume without importing Payment persistence types.
  • Illustrative scenario — Event storming on Meridian’s checkout-to-delivery flow surfaces separate aggregates for catalog merchandising, stock reservation, payment capture, and warehouse pick—each with distinct invariants.
  • Illustrative scenario — Catalog and Inventory both mention “Product” with different rules; Meridian references the other context by ProductId instead of one shared entity graph.
  • Illustrative scenario — A healthcare-style workflow models Prescription as a root with Medication as a value object and a domain service validating interactions—policy stays in domain language while integration uses events outward.
