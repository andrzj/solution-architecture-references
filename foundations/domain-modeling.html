Domain Modeling

Representing business concepts and rules in code — entities, value objects, aggregates, and the techniques that keep domain logic clean.

⏱ 8 min read

What it is

Domain modeling is how you represent business concepts and rules in code—orders, accounts, prescriptions—not as anonymous rows and DTOs, but as types the business already talks about. A developer reading Order.place() or Money as a value object should recognize the same language domain experts use in workshops.

Done well, the model is executable documentation: invariants live on aggregates, side effects surface as domain events, and infrastructure stays at the edges.

Why it exists

Without an explicit model, logic drifts into service classes around anemic data objects. Rules like "cancel only before ship" hide in three procedural services, become hard to test, and vanish from conversation with the business. Every change risks breaking a rule nobody remembered was there.

Co-locating rules on the types they govern makes behavior discoverable. When Order.cancel() enforces shipping state, you can unit-test the rule without spinning up HTTP or SQL. That cohesion pays off over years of evolving regulation and product rules.

When to use

  • Long-lived products with non-trivial business rules that will keep changing.
  • Teams pairing with domain experts and investing in a ubiquitous language.
  • Event-sourced or event-heavy designs where domain events are first-class facts.
  • Regulated domains where rules must be traceable in code and reviews.
  • Microservices where aggregate boundaries hint at consistency and transaction limits (not automatic service cuts).

When not to use

  • Simple CRUD with little invariant surface—a thin service over tables is enough.
  • DDD patterns pasted onto an anemic core (entities that are only bags of fields).
  • Treating every aggregate as its own microservice without checking operational cost.

Pros and cons

Pros

  • Rules sit next to the concepts they protect—easy to find, test, and change.
  • Immutable value objects cut down shared-mutation bugs.
  • Domain events integrate contexts without reaching inside another aggregate.
  • Aggregates clarify where one transaction must succeed or fail as a unit.
  • Shared vocabulary with domain experts reduces mistranslation in requirements.

Cons

  • More design time up front than table-first CRUD.
  • ORMs and aggregates fight unless boundaries and loading are deliberate.
  • Skill spread varies; teams need coaching to avoid cargo-cult DDD.
  • Easy to over-model simple domains with layers nobody needed.

Implementation notes

Entities vs value objects: Entities have identity that outlives attribute changes—this order is still order #42 after status moves to SHIPPED. Value objects are defined only by their data—two Money(10, USD) instances are interchangeable. Prefer immutability on values; "change" means replace. Replacing raw strings with OrderId, Email, and Money concentrates validation instead of scattering it in controllers.

Aggregate design: An aggregate is the consistency cluster: one root is the only entry for writes, and invariants that must hold together stay inside. Reference other aggregates by id, not by navigable object graphs. Keep aggregates small—fat roots that own catalog, customer, and inventory become lock magnets.

Event Storming: Sticky notes for events, commands, aggregates, and policies on a timeline surface where language splits and where boundaries should fall. It is the fastest way to align developers and experts before coding structure.

Domain services: Use when the rule genuinely spans aggregates (e.g., transferring between two accounts) but still belongs in domain language—not for orchestration or SQL, which stay in application services.

Common failure modes

  • Anemic model: Entities are structs; every rule sits in OrderService.
  • God aggregate: One root owns customer, catalog, and stock—contention and unclear ownership.
  • Leaky repository: Returning OrderLine to callers who bypass Order invariants.
  • Events as wire DTOs: Names and payloads shaped for integration, not for what the business said happened.
  • Silent aggregates: State changes with no events, forcing other contexts to poll or couple tightly.

Decision checklist

  • Which invariants define each aggregate boundary?
  • Are primitives at the edge replaced with value types where meaning matters?
  • Are value objects immutable in this language/runtime?
  • Do all writes go through the aggregate root?
  • Do meaningful operations publish domain events others can subscribe to?
  • Is the domain layer free of DB, HTTP, and framework leakage?
  • Did domain experts participate in Event Storming (or equivalent) before locking the model?
  • Will a single aggregate transaction stay small enough under peak load?

Example use cases

  • E-commerce Order aggregate with OrderLine children and Money—credit limit enforced inside place(), not in a generic checkout service.
  • Banking Account—each debit or credit emits TransactionRecorded for ledger and reporting contexts.
  • Healthcare Prescription root with Medication values and a domain service checking interactions against patient history.
