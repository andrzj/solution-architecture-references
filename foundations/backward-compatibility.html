Backward Compatibility

Evolving systems without breaking existing consumers — the patterns and strategies that enable independent deployment and continuous delivery.

⏱ 6 min read

What it is

Backward compatibility means a new version of a producer still satisfies existing consumers built against an older contract.

Forward compatibility is the mirror image: an older server tolerates a newer client (unknown fields, optional data).

Northwind Logistics runs the FieldOps mobile app against GET /v1/drivers/{id}. Drivers keep older app builds on their phones. When the driver API team ships a new service version, responses must still include fields those builds parse — or changes must be additive only.

Postel’s Law (the Robustness Principle): be conservative in what you send, liberal in what you accept. Northwind’s API gateway strips nothing consumers rely on; clients ignore fields they do not yet understand.

Why it exists

In a monolith, one deploy updates producers and consumers together. Northwind’s driver API, dispatch service, and FieldOps app ship on different cadences.

A breaking rename on the driver API can blank out contact info in FieldOps until every user updates — a failure mode you cannot fix from the server alone.

Compatible contracts also enable rolling deploys: during a canary, old and new API pods must serve both lagging mobile builds and the latest beta.

When to use

  • Yes: mobile or third-party clients you cannot force-upgrade (FieldOps, partner TMS integrations).
  • Yes: HTTP or gRPC between Northwind microservices with independent release trains.
  • Yes: Kafka/Avro events where multiple consumers read at different schema revisions.
  • Yes: shared database columns touched by more than one service — treat schema like a public API.
  • Yes: any production endpoint you expect another team to build on for longer than one sprint.

When not to use

  • No: a single deployable unit where all callers rebuild every release — runtime compat matters less (libraries may still semver).
  • No: explicit v0 or beta APIs with no external dependents — document that breaks are allowed.
  • No: a tiny, coordinated consumer set with a written migration window — still prefer expand-contract to shrink blast radius.

Typical architecture

The expand–contract pattern (parallel change) is how Northwind makes breaking database or API shifts without a flag day. Expand: add first_name and last_name beside legacy full_name. Migrate: dual-write, move FieldOps and dispatch readers. Contract: drop full_name only when telemetry shows zero use.

Pros and cons

Pros

  • FieldOps and dispatch can ship without locking to the same release train as the driver API.
  • Rollbacks and canaries avoid “stop the world” upgrades when a field disappears.
  • Teams deploy smaller batches because consumers are not blockers on every PR.
  • Partners trust Northwind’s public TMS hooks when deprecations are announced, not surprise breaks.

Cons

  • Legacy fields linger — driver payloads accumulate aliases and deprecated columns.
  • Supporting /v1 and /v2 in parallel doubles handlers and tests.
  • Expand–contract needs a migration tracker; otherwise dual-write phases never end.
  • Clients must ignore unknown JSON keys — easy to forget in strongly typed mobile models.

Implementation notes

Pact in CI: FieldOps defines the driver response shape it needs; the driver API provider verification job runs on every PR. Northwind caught a proposed email rename because the contract still expected email_address.

Semver and policy: Breaking driver API changes bump major path (/v2/...). Additive fields are minor documentation updates. Publish how long v1 stays after v2 GA. Return Deprecation and Sunset headers on aging routes so FieldOps telemetry can plan upgrades.

Protobuf discipline: If Northwind moves driver events to gRPC, field numbers are the wire identity. Rename freely; never reuse numbers. Mark retired slots with reserved so a future engineer does not recycle them.

Schema registry: Avro changes for DriverStatusChanged go through registry compatibility checks before merge — incompatible writer schemas fail the build.

Common failure modes

  • Silent rename: driver_id becomes driverId in JSON with no alias — FieldOps shows empty IDs without a hard error.
  • New required field: home_terminal becomes mandatory — older app builds get 400 on every fetch.
  • Enum shrink: Removing ON_BREAK breaks FieldOps switches and downstream reports.
  • Stuck expand phase: Both full_name and split names stay forever; writers disagree on canonical source.
  • No contract tests: Integration tests mock ideal responses; production clients still break.

Decision checklist

  • Is the driver API change additive-only? If not, is there a new major version path?
  • Did you search FieldOps, dispatch, and partner repos for usages of fields you remove or tighten?
  • Does CI run provider verification against consumer Pact files (or equivalent)?
  • For DB changes on the driver store, are you in expand, migrate, or contract — with an owner for contract?
  • For Protobuf/Avro, did registry compatibility pass on the PR?
  • Is there a written deprecation window for FieldOps and external TMS consumers?
  • Do deprecated Northwind endpoints emit Deprecation / Sunset headers?

Example use cases

Northwind’s driver profile work follows one thread:

  • Additive response: Optional preferred_language ships; old FieldOps builds ignore it.
  • Expand–contract names: Split full_name while dual-writing until FieldOps release notes say all fleets are on the new build.
  • Major version: /v2/drivers/{id} introduces redesigned status enums; v1 keeps old values until sunset headers say otherwise.
  • Pact gate: A PR that drops email_address fails provider verification until FieldOps publishes an updated consumer contract.
