Backward Compatibility

Evolving systems without breaking existing consumers — the patterns and strategies that enable independent deployment and continuous delivery.

⏱ 6 min read

What it is

Backward compatibility means a newer producer still honors the contract that existing consumers were built against—same field names, types, semantics, and error behavior unless you explicitly version a breaking change.

Forward compatibility is the converse: an older server tolerates a newer client that sends unknown fields or optional data the producer does not yet model.

Together they enable independent deployment. Microservices, mobile clients, partner integrations, and batch consumers rarely upgrade in the same maintenance window; the runtime mix of versions is normal, not an edge case. Treat that mix as a design input, not a bug.

Postel’s Law (the Robustness Principle) captures the design posture: be conservative in what you emit and liberal in what you accept. Producers should not remove or rename fields others depend on; consumers should ignore unknown keys and treat optional data as optional. That split lets each side evolve without synchronized releases.

Why it exists

In monoliths, compatibility is largely a compile-time concern—one artifact ships and every caller updates together. Distributed systems flip the problem to runtime: a mobile build in the field, a partner still on last quarter’s SDK, and a downstream service waiting for its own release train may all call the same endpoint while you roll out a new pod set.

Breaking API or schema changes without a migration path force a coordinated cutover. That pattern is expensive, risky, and fights team autonomy. Compatibility is how you keep velocity when components deploy on different schedules.

It also underpins continuous delivery and zero-downtime deploys. Blue-green, canary, and rolling updates all assume old and new producer versions interoperate with both lagging and current clients during the transition. Without that overlap, every change becomes a flag day.

Libraries and SDKs inherit the same constraint: a minor semver bump should not break compile-time callers; runtime APIs consumed across process boundaries need even stricter additive defaults because you cannot recompile every downstream binary on deploy day.

When to use

  • Public or partner APIs where you cannot force every client to upgrade on your timeline—especially mobile apps and third-party integrations.
  • Network boundaries between microservices that release on independent pipelines and must keep talking during partial rollouts.
  • Event topics and stream schemas where multiple consumers read at different code and schema revisions.
  • Shared database columns touched by more than one service—treat schema like a published interface, not a private implementation detail.
  • Any production endpoint another team will depend on for longer than a single sprint, which is effectively all durable APIs.
  • GraphQL and gRPC schemas exposed to multiple generated clients, where field removal breaks compilation or queries in the wild.

When not to use

  • Internal systems deployed atomically as one unit, where every caller rebuilds each release—runtime compatibility adds little, though libraries may still semver.
  • Early v0 or beta surfaces with no external dependents, when rapid iteration legitimately requires breaking changes and expectations are documented.
  • Tiny, controlled consumer sets with a written migration window and appetite for a flag day—though expand–contract still reduces blast radius even here.

Typical architecture

Most evolution splits into additive changes (new optional fields, endpoints, enum values consumers must ignore) versus breaking changes (removals, renames, tighter validation, semantic shifts). Breaking work either needs a new major API version or a phased migration.

The expand–contract pattern (parallel change) is the canonical database and API migration shape: expand by adding the new shape beside the old; migrate consumers and dual-write or backfill until traffic moves; contract by removing the legacy path only when telemetry proves zero use. That yields zero-downtime migration without a synchronized deploy.

When a breaking HTTP contract is unavoidable, common versioning styles include path segments (/v1/ vs /v2/), content negotiation headers, query parameters, or subdomain splits—pick one per API surface and document deprecation policy. For serialized payloads, Protobuf wire identity is field numbers (never reuse), Avro evolves through registry-checked reader/writer rules, and JSON needs explicit OpenAPI or AsyncAPI discipline because the wire format enforces nothing by itself.

Pros and cons

Distinguish compatibility modes: Backward readers must deserialize historical payloads; forward writers must not break older consumers; registries often enforce one mode per subject. Document which mode your stream or API promises—confusion here shows up as “compatible” schema checks with still-broken consumers.

Pros

  • Producers and consumers upgrade on different schedules without coordinated cutovers.
  • Rollbacks and canaries stay safe when new pods must serve both old mobile builds and current web clients.
  • Continuous delivery ships smaller batches because consumer readiness is not a gate on every merge.
  • Stable public APIs build partner trust—deprecations with notice beat surprise field loss years later.

Cons

  • Additive-only evolution accumulates legacy fields and aliases that burden new integrators.
  • Running v1 and v2 in parallel doubles handlers, tests, and operational attention.
  • Expand–contract migrations need an owner and tracker—dual-write phases otherwise linger indefinitely.
  • Forward-compatible clients must ignore unknown data—a discipline easy to skip in strongly typed models.

Implementation notes

Consumer-driven contract testing: Frameworks such as Pact invert the usual integration test: each consumer publishes the requests and responses it actually needs; the provider’s CI replays those contracts against the latest code. Breaking renames or missing fields fail the provider pipeline before deploy, not in production traffic.

Semantic versioning and deprecation: Treat major bumps as breaking contract changes (new URL major, new topic subject version), minors as additive capabilities, patches as bug fixes without contract drift. Publish how long the previous major remains available. Emit Deprecation and Sunset headers (and changelog entries) so client telemetry and partner runbooks can schedule upgrades.

Protobuf discipline: Field numbers are wire identity—rename freely, never recycle numbers. Use reserved for retired slots: reserved 3, 4; reserved "old_name";. Breaking evolution usually means a new message type or a new service package, not in-place number reuse.

Schema registry for Avro and friends: Register schemas before publish; let CI reject incompatible writer evolution. Pair registry checks with human review when semantics change but structure looks additive—registry green does not guarantee business meaning is unchanged.

OpenAPI and JSON: Where the wire format is schemaless, publish machine-readable contracts, lint pull requests for breaking diffs, and keep examples that reflect what oldest supported clients still send.

Migration telemetry: Track field-level access and schema versions in access logs or APM attributes. Contract phases should close on evidence—dropping a column because the sprint ended, not because traffic quieted, is how silent regressions return.

gRPC and Buf: Run buf breaking (or equivalent) against a baseline commit in CI before merging .proto changes. Package versioning (billing.v1, billing.v2) beats in-place wire-type changes. JSON transcoding at the gateway does not excuse breaking field semantics—mobile clients may still parse transcoded JSON.

Production gates: Dashboards should show percentage of traffic on deprecated API majors and schema versions. Automated alerts when sunset dates pass but v1 traffic remains above an agreed threshold (for example 1% of requests) block contract-phase DDL until integrators migrate.

Expand–contract mechanics: Expand adds optional columns, shadow tables, or dual-write paths. Contract removes old shapes only when telemetry proves zero consumers. The dangerous middle phase is dual-write drift—monitor row counts and checksums between legacy and new stores nightly during migration.

Schema registry modes: Confluent Schema Registry enforces BACKWARD, FORWARD, FULL, or NONE per subject. BACKWARD lets new consumers read old data; FORWARD lets old consumers read new data; FULL is both. Pick per topic: payment events often need FULL; analytics may accept BACKWARD only.

GraphQL and OpenAPI: GraphQL breaking changes include removing fields, tightening nullability, or changing enum values—use @deprecated with reason and removal date. Federation composition checks block conflicting types across subgraphs. OpenAPI diffs in CI (oasdiff, Optic) catch accidental required-field additions.

Rollback during expand: Keep feature flags that route traffic to legacy handlers until contract phase completes. Database expand steps should be reversible—add column nullable before backfill, never drop until contract.

Operational numbers: Plan sunset with RFC 8594 Sunset headers at least 90 days ahead for partner APIs; mobile apps may need two release cycles. Log schema version or API major on every request for SRE dashboards.

When NOT to promise compatibility: Internal services with a single deployable consumer can ship breaking changes with coordinated deploys—compatibility tax is wasted. Security incidents that require immediate field removal may supersede normal sunset policy with explicit incident ADR.

Common failure modes

  • Silent rename: user_id becomes userId without an alias—clients read null instead of a hard error, corrupting downstream state quietly.
  • New required field: A previously optional attribute becomes mandatory; every client that omits it receives 400 responses until upgraded.
  • Enum shrink: Removing a status value breaks consumers with switches, constraints, or reports that still expect it.
  • Stuck expand phase: New and old columns both stay writable with no canonical source—migrations never reach contract and data diverges.
  • No contract tests: Suites mock ideal JSON while real clients parse stricter shapes—production breaks despite green unit tests.
  • Semantic drift: A field keeps its name but changes meaning—registry and type checks pass while finance or fulfillment reports skew.

Decision checklist

  • Is the change additive only? If not, is there a new major version path and published deprecation timeline?
  • Have all known consumers been audited for usage of fields you remove, rename, or tighten?
  • Does CI run provider verification against consumer contracts (Pact or equivalent) before production deploy?
  • For database or shared-column work, are you in expand, migrate, or contract—with a named owner to finish contract?
  • For Protobuf, Avro, or JSON Schema, did registry or linter checks pass on the PR?
  • Do deprecated endpoints return Deprecation / Sunset headers and documented replacement URLs?
  • Will canary metrics distinguish errors from old clients versus new clients during rollout?
  • After contract, is there a time-boxed cleanup ticket to remove shims, aliases, and dual-write paths?

Example use cases

  • Illustrative scenario — Northwind Logistics adds optional preferred_language on driver profiles; legacy FieldOps builds ignore the field without crashing.
  • Illustrative scenario — Northwind splits full_name into first_name / last_name using expand–contract dual-write until telemetry shows zero reads of the legacy column.
  • Illustrative scenario — Northwind ships /v2/drivers/{id} with redesigned status enums while v1 remains until sunset headers and partner notices expire.
  • Illustrative scenario — A provider PR that drops email_address fails Pact verification until FieldOps publishes an updated consumer contract.
  • Illustrative scenario — A payments API team cites long-running public API stability—fields deprecate with years of notice rather than silent removal, echoing how mature payment platforms treat integrator trust.

Related patterns

  • Architecture Decision Records — document breaking contract changes, deprecation windows, and expand–contract phases so the next team inherits rationale, not archaeology.
  • Idempotency — retry semantics and key handling are part of the outward contract; version bumps must not change dedupe behavior without notice.
  • Architecture Principles — evolvability and stable interfaces are principle-level goals that backward compatibility operationalizes at the API and schema layer.
