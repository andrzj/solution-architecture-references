What it is

Threat modeling is a structured design-time exercise that maps what you are building, enumerates how it could be attacked, assigns mitigations, and verifies those mitigations before or during implementation. Adam Shostack's four-question framing remains the spine: What are we building? What can go wrong? What will we do about it? Did we do enough? Outputs typically include a Data Flow Diagram (DFD) with trust boundaries, a threat catalogue, risk scores, and tracked remediation tasks.

STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) categorises threats per DFD element or per data flow. PASTA (Process for Attack Simulation and Threat Analysis) aligns technical threats to business impact through staged analysis. Attack trees decompose adversary goals into alternative paths. DREAD (Damage, Reproducibility, Exploitability, Affected users, Discoverability) prioritises remediation. OWASP's threat modeling guidance and Threat Dragon integrate these techniques for web and API systems, emphasising trust boundaries where unvalidated input crosses into privileged components—a pattern that surfaces OWASP Top 10 issues such as injection and broken access control early.

Threat models are most valuable when architecture is still plastic. Moving an auth decision from client to server, adding field-level encryption, or choosing OIDC instead of custom tokens costs hours in design and weeks in retrofit.

Why it exists

Most catastrophic flaws are architectural: trusting the client for authorisation, storing refresh tokens in mobile storage, exposing admin APIs on the public internet without mutual TLS. Code review catches local bugs; threat modeling catches wrong designs. It converts vague "we should be secure" requests into testable statements—"spoofing of webhook callbacks is mitigated by HMAC with rotated secrets"—that auditors and penetration testers can verify.

Security Development Lifecycle (SDL) gates and SOC 2/ISO 27001 evidence increasingly expect documented risk assessment. A maintained threat model proves proactive analysis rather than reactive scanning alone. For API-heavy products, seeding models from the OWASP API Security Top 10 accelerates workshops without reinventing categories like BOLA or broken authentication.

Quantitative impact studies vary, but industry experience consistently shows design-stage fixes cost far less than emergency patches after disclosure. Threat modeling also reduces rework: teams discover that a proposed mobile offline cache would store PII unencrypted before sprint commitment, not after penetration testers file the finding. In organisations adopting Zero Trust, the model documents which components act as policy enforcement points and which trust boundaries require continuous re-authentication—direct inputs to NIST 800-207 implementations.

When to use

  • New features touching authentication, authorisation, PII, payments, or external integrations.
  • Greenfield services, major refactors, or platform changes (new IdP, new database tier, new partner feed).
  • Pre-launch reviews for high-risk launches and third-party data sharing agreements.
  • After incidents—to capture missed threats and update the living model.
  • Acquisition due diligence when inheriting unknown architectures and legacy auth mechanisms.
  • Annual refresh of critical systems even when no major feature ships—attackers and dependencies change continuously.

When not to use

  • Low-risk cosmetic UI tweaks with no security surface change—apply proportionality.
  • As a substitute for SAST, DAST, or penetration testing—models hypothesise; tests prove.
  • Post-implementation archaeology on frozen legacy—still valuable for risk registers but cheaper mitigations are gone.

Pros and cons

Done well, threat modeling becomes the bridge between compliance checklists and engineering reality: each high-rated threat should map to a control you can demonstrate to auditors, not a vague aspiration on a slide deck.

Pros

  • Shifts security left—fixes in design are far cheaper than production breaches.
  • Shared vocabulary between engineering, architects, and security teams.
  • Produces prioritised backlogs instead of undifferentiated "make it secure" tickets.
  • Provides compliance evidence of risk analysis.
  • Reusable patterns (OAuth/OIDC login, webhook ingestion) speed later features.

Cons

  • Full STRIDE on trivial features wastes time without risk-based scoping.
  • Models rot without owners when architecture evolves.
  • Quality depends on facilitator skill and attacker mindset.
  • Perceived as delivery drag unless tied to clear outcomes and timeboxes.

Implementation notes

Keep DFDs at level 1–2: external entities, processes, data stores, flows, and trust boundaries clearly drawn. Use OWASP Threat Dragon or Microsoft Threat Modeling Tool for version control alongside repos. For APIs, add abuse cases beyond STRIDE—mass assignment, excessive data exposure, unsafe consumption of third-party webhooks.

Timebox workshops (90–120 minutes) on high-value flows first. Score with DREAD or a simple High/Medium/Low matrix; assign each high item an owner and issue ID. Store models in Git or the wiki linked from the service catalog. Re-run when trust boundaries move—new OAuth client, GraphQL endpoint, or AI tool calling internal APIs. Validate mitigations in code review checklists and automated tests (e.g., assert BOLA checks exist on new routes).

Invite engineers who own the code path, not only security specialists—the best models surface pragmatic mitigations engineers will actually ship. Pair STRIDE with abuse stories written in plain language ("attacker replays webhook without signature") so product managers can prioritise alongside features. For OAuth and OIDC flows, explicitly model token storage, redirect URI validation, refresh-token rotation, and consent phishing—common gaps in OWASP ASVS verification. Link each mitigation to a verification method: unit test, integration test, WAF rule, or pen-test case, so "addressed" is measurable rather than aspirational.

In mature programmes, maintain a library of pattern threat models—standard login, file upload, admin API, batch export—that new features clone and diff. That reduces workshop time while preserving consistency. Align outputs with your secure SDLC gate: no production deploy for high-risk components without an updated model or a documented risk acceptance signed by an owner.

Common failure modes

  • Analysis paralysis: Endless enumeration without shipping mitigations—cap threats per session and iterate.
  • Stale artifacts: Model from launch year still hanging on Confluence while architecture doubled in services.
  • Missing boundaries: DFD treats the database as inside the app trust zone—misses SQL injection and IDOR surfaces.
  • Unowned mitigations: Threat list with no tracker linkage—nothing gets built.
  • Security-only authorship: Developers absent; proposed mitigations ignored as impractical.
  • Ignoring supply chain: Third-party SDKs drawn as opaque boxes—missing tampering threats on update channels and signature verification gaps.
  • Overfitting to STRIDE: Privacy and abuse scenarios (scraping, rate evasion) omitted because they lack a neat letter—extend with abuse-case brainstorming.

Decision checklist

  • Does the DFD include all external entities, stores, flows, and trust boundaries?
  • Has STRIDE (or equivalent) been applied at each boundary crossing?
  • Are threats risk-ranked and assigned owners with due dates?
  • Is the model stored in version control and updated on architectural change?
  • Are mitigations verified in review, tests, or DAST rules—not only documented?
  • For auth flows, are OAuth/OIDC and session threats explicitly enumerated?
  • Does every high-risk threat link to a regression test or monitoring rule?
  • Did product and engineering sign off that residual risk is within appetite?

Example use cases

  • Illustrative scenario — Meridian Commerce checkout: STRIDE on payment webhooks catches spoofing (→ HMAC signatures with key rotation), tampering with amounts (→ server-side signed cart), elevation via coupon API (→ server-side validation and rate limits).
  • Public API gateway: Top threat BOLA; mitigation checklist requires object-level authorisation tests in CI for every new route.
  • Partner data feed: PASTA aligns exfiltration risk to contractual fines; mitigations add field-level encryption and egress rate limits.
  • LLM tool-calling feature: DFD marks the model broker as a trust boundary; threats include prompt injection leading to excessive API scope—mitigated by fixed allow-listed tools and per-user OAuth tokens with least scopes.
  • Mobile offline sync: Tampering and information disclosure threats drive encrypted local storage and server-side conflict resolution rather than trusting client timestamps.
