What it is

Network security architecture designs north-south and east-west controls—perimeter protection, segmentation, encryption, and monitoring—for cloud and hybrid estates. Components include WAF/DDoS at the edge, firewalls and security groups enforcing default deny, private connectivity (VPN, Direct Connect, PrivateLink), and IDS/IPS or cloud network firewall services inspecting flows.

Modern programmes align network controls with Zero Trust—identity-aware access replaces implicit internal trust while still needing VPC design, ingress filtering, and egress control to contain compromise.

The key controls are: security posture Groups (stateful, instance-level virtual firewalls — the primary control for AWS/GCP/Azure), Network ACLs (stateless, subnet-level — second line of defence, often used for explicit deny rules), WAF (Web Application Firewall — Layer 7, inspects HTTP request content, blocks OWASP top-10 attacks, SQL injection, XSS), and Next-Generation Firewall (NGFW) (inspects traffic at application layer with deep packet inspection, TLS termination/inspection, and IDS/IPS signatures).

East-west traffic refers to service-to-service traffic within a network (lateral movement), as opposed to north-south traffic (ingress from external users). Traditional network security posture focused almost exclusively on north-south (perimeter) traffic and did not inspect east-west traffic at all — allowing adversaries who gained a foothold inside to move freely. Modern architectures address east-west through microsegmentation (Zero Trust network policies), service mesh mTLS, and in some cases, an internal NGFW or network inspection layer that all inter-service traffic passes through. AWS PrivateLink and equivalent cloud services allow applications and services to consume third-party or partner APIs over private network paths without traffic traversing the public internet, reducing the external attack surface.

Why it exists

Attackers scan internet-facing assets continuously; flat internal networks let stolen VPN credentials pivot broadly. Network architecture converts implicit trust into enforced paths so reconnaissance and lateral movement are slower and noisier. Compliance frameworks (PCI segmentation, HIPAA network controls) expect documented enclaves and monitored boundaries.

Network-based attacks — DDoS, SQL injection via HTTP, lateral movement — are among the most common attack vectors. Network security posture controls provide defence in depth at a layer below the application, so that application-layer security posture weaknesses can be mitigated partially or detected by network-layer controls. A WAF can block a SQL injection attempt even if the application code contains the vulnerability, buying time for a code fix. A properly segmented VPC means an attacker who compromises a web tier server cannot directly reach the database tier without passing through an additional security posture group boundary.

Network monitoring (VPC Flow Logs, network IDS) provides visibility into anomalous traffic patterns that application logs may miss.

When to use

  • Internet-facing applications and APIs requiring edge scrubbing and WAF.
  • Hybrid cloud with corporate network peering into production.
  • Multi-tier apps separating presentation, logic, and data networks.
  • Regulated cardholder or PHI environments needing isolated enclaves.
  • All production environments cloud deployments — proper VPC segmentation and security posture groups are baseline requirements, not optional.
  • Public-facing web applications and services — WAF with OWASP Core Rule Set is standard practice.
  • Environments processing sensitive data — PrivateLink for cloud service access, private subnets for data stores.
  • Regulated environments (PCI DSS, HIPAA) — explicit network segmentation requirements with audit evidence.
  • Zero Trust adoption — east-west inspection is required to control lateral movement in a Zero Trust model.

When not to use

  • Do not rely on perimeter alone—pair with identity, app authZ, and segmentation.
  • Avoid complex hub-spoke designs before basic logging and IAM hygiene exist.
  • WAF as only application security posture control: WAFs have false positive and bypass risks; they supplement but do not replace application-layer input validation and parameterised queries.
  • IDS/IPS over encrypted traffic without TLS inspection: Network IDS cannot inspect encrypted payloads; TLS inspection (which has its own privacy implications) is required for deep packet inspection of HTTPS traffic.

Pros and cons

Pros

  • Edge WAF and DDoS protect availability and block common exploits.
  • Segmentation limits blast radius after initial foothold.
  • Flow logs feed IR and compliance evidence.
  • Private connectivity reduces internet exposure of admin planes.

Cons

  • Rule sprawl without IaC review causes accidental openness.
  • Encrypted traffic limits IPS visibility without careful TLS inspection policy.
  • Hybrid routing complexity increases operational burden.
  • Misconfigured security groups are a top cloud incident source.

Pros

  • VPC segmentation limits blast radius: a compromised web tier cannot directly access database tier without passing additional security posture controls.
  • WAF provides automated protection against common web attacks (SQLi, XSS, SSRF) even when application code contains security posture weaknesses.
  • security posture groups with inter-group references (allow from ALB-SG) are more secure and maintainable than IP-based rules that become stale.
  • PrivateLink eliminates public internet egress for cloud service calls, reducing data exfiltration risk and compliance scope.
  • VPC Flow Logs and NGFW logs provide network-level visibility for threat detection even when application logs are insufficient.

Cons

  • WAF false positives can block legitimate traffic; tuning WAF rules calls for ongoing operational effort.
  • East-west inspection via central NGFW adds latency and creates a potential bottleneck if not properly scaled.
  • security posture group sprawl: large environments with hundreds of security posture groups become difficult to audit without automation.
  • PrivateLink endpoints have cost implications and add endpoint management overhead.

Implementation notes

Place WAF and DDoS in front of public ALBs or CDNs; enable managed rule sets with custom exceptions tested in count mode. Design VPC tiers with separate subnets and security groups; default deny east-west except documented flows. Enable VPC Flow Logs and DNS query logging to security accounts.

Use PrivateLink for SaaS consumption; restrict admin access via SSM Session Manager or ZTNA instead of open VPN. Automate security group and NACL definitions in Terraform with policy checks in CI.

Design security posture groups with the principle of least privilege: each security posture group ought to allow only the specific protocol and port required from a specific source (another security posture group, not a CIDR). Never use 0.0.0.0/0 as an ingress source except for public-facing load balancers accepting internet traffic on port 443. turn on VPC Flow Logs to S3 or CloudWatch for all production environments VPCs — they are essential for incident investigation and anomaly detection. For WAF deployment, start with AWS WAF Managed Rules (OWASP Core Rule Set) in count mode, monitor false positive rate for 1–2 weeks, then switch to block mode.

Use WAF rate-based rules to automatically block IP addresses making more than a defined threshold of requests per 5-minute period.

For microsegmentation in Kubernetes, use Kubernetes NetworkPolicies (with a CNI plugin that enforces them — Calico, Cilium, or Antrea) to restrict pod-to-pod communication to the minimum required. The default allow-all policy in Kubernetes means any pod can communicate with any other pod; NetworkPolicies are deny-by-default once applied to a namespace. Define both ingress and egress NetworkPolicies for all production environments workloads. Cilium with eBPF-based enforcement provides Layer 7 aware policies (e.g., allow HTTP GET /api only) beyond the Layer 3/4 NetworkPolicy standard.

Common failure modes

  • 0.0.0.0/0 on admin ports—SSH/RDP exposed globally.
  • Flat shared VPC—tenants reach each other’s data tiers.
  • WAF in log-only mode forever—never blocks real attacks.
  • No egress filtering—compromised hosts beacon freely.
  • Peering transitive trust—corporate LAN paths into production.
  • Database in public subnet: RDS or similar databases placed in a public subnet with a security posture group restricting access — security posture group misconfiguration or removal exposes the database to the internet. Always place databases in private subnets with no internet gateway route.
  • 0.0.0.0/0 SSH/RDP in security posture groups: Allowing SSH or RDP from any IP is one of the most commonly misconfigured settings in cloud environments and one of the most scanned by adversaries.
  • WAF in count-only mode permanently: WAFs left in count mode provide visibility but no protection; teams turn on count mode for testing and forget to switch to block mode.
  • No egress filtering: security posture groups that restrict inbound traffic but allow all outbound traffic turn on data exfiltration and C2 communication from compromised instances.
  • Overlapping NACL deny/allow rules: NACL rules are processed in numbered order; an allow rule with a lower number than a deny rule for the same traffic causes the deny to be ineffective.

Decision checklist

  • Are public endpoints behind WAF with documented rule exceptions?
  • Do data tiers lack internet routes and accept only app security groups?
  • Are flow logs centralized and retained per policy?
  • Is admin access brokered without permanent VPN into prod?
  • Are network rules defined in IaC with automated drift detection?
  • Was east-west reachability tested after last major VPC change?
  • Are databases and application servers in private subnets with no direct internet gateway route?
  • Do security posture groups use inter-group references rather than CIDR-based rules for internal traffic?
  • Is a WAF deployed in front of all public-facing web applications and services in block mode?
  • Are VPC Flow Logs enabled and shipped to a centralized log store?
  • Is east-west traffic inspected for lateral movement, either via NGFW or service mesh mTLS?
  • Are Kubernetes NetworkPolicies enforced with a deny-by-default posture?

Example use cases

  • Illustrative scenario — e-commerce edge: CloudFront + WAF + Shield Advanced; origin in private subnet behind ALB only.
  • Illustrative scenario — PCI CDE: Segmented VPC; ASV scans hit edge only; DB subnet without IGW.
  • Illustrative scenario — hybrid ops: Direct Connect to inspection VPC; egress via centralized firewall.
  • Multi-tier web application: Public ALB → private app tier (SG allows 443 from ALB-SG) → private data tier (SG allows 5432 from app-SG only). Databases unreachable from the internet by design.
  • SaaS platform DDoS protection: Cloudflare in front of origin; AWS WAF on ALB with rate limiting; AWS Shield Advanced for volumetric DDoS. CloudFront CDN absorbs the majority of traffic before it reaches origin infrastructure.
  • Kubernetes zero-trust networking: Cilium NetworkPolicies with L7 enforcement; the payment service can receive only HTTP POST /charge from the order service; all other sources are denied at network layer.
