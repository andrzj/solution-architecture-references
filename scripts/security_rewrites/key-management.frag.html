What it is

Key management governs generation, distribution, use, rotation, backup, and destruction of cryptographic keys. Customer master keys (CMKs) in cloud KMS or keys in HSMs anchor trust; applications use envelope encryption rather than embedding key material. NIST SP 800-57 defines key states (pre-activation, active, suspended, deactivated, destroyed) and rotation expectations.

Distinct from secret management, which handles passwords and API tokens, key management focuses on symmetric and asymmetric keys powering TLS, data encryption, and signing—with stricter residency, FIPS, and dual-control requirements.

Why it exists

Encrypted data is only as strong as key hygiene. Keys checked into Git, shared in tickets, or never rotated convert cryptography into theatre. Auditors ask for proof of rotation, access logging, and separation of duties on HSM admin. Central KMS with IAM policies provides attributable decrypt events and automated annual rotation for symmetric CMKs.

When to use

  • Any production use of cloud KMS, database TDE, TLS server certs, or code signing.
  • Regulations requiring FIPS 140-2 Level 3 or dedicated HSM tenants.
  • Multi-region DR needing replicated keys with clear primary and replica roles.

When not to use

  • Do not import homemade keys into KMS without entropy and policy review.
  • Avoid per-developer CMKs—use account or workload-scoped keys with IAM.

Typical architecture

CMKs in KMS anchor envelope encryption; HSM-backed roots satisfy high-assurance rotation and audit requirements.

Pros and cons

Pros

  • Central audit of every encrypt/decrypt operation.
  • Automatic symmetric key rotation on supported CMKs.
  • HSM backends meet high assurance customer requirements.
  • Envelope pattern limits exposure of raw key material in apps.

Cons

  • KMS quotas and latency affect high-throughput apps.
  • Multi-region key strategy adds cost and complexity.
  • Asymmetric key rotation requires certificate orchestration.
  • Cloud lock-in concerns for on-prem hybrid estates.

Implementation notes

Use separate CMKs per environment and sensitivity tier; deny decrypt from CI except dedicated roles. Enable rotation on symmetric CMKs; document manual rotation for asymmetric signing keys with overlapping validity windows. Store HSM admin credentials in break-glass procedure separate from daily ops.

Integrate cert-manager or ACME for TLS cert lifecycle. For multi-region, use multi-Region keys or replicate with documented failover drills. Monitor KMS CloudTrail or equivalent for anomalous decrypt spikes.

Common failure modes

  • One CMK, many services—over-broad decrypt IAM policies.
  • Disabled rotation—years-old symmetric keys without justification.
  • Pending deletion panic—accidental key schedule destroys data.
  • Cross-account CMK without trust review—partner decrypts all data.
  • Manual cert renewal forgotten—production TLS outages.

Decision checklist

  • Are CMKs scoped per environment with least-privilege IAM?
  • Is automatic rotation enabled or documented for each key type?
  • Are HSM or multi-Region requirements satisfied for regulated data?
  • Is every decrypt logged to immutable audit storage?
  • Are TLS and signing certificates renewed before expiry automatically?
  • Was key compromise runbook tested in the last year?
