What it is

JSON Web Tokens (JWTs) are compact, signed claims objects used as access tokens, ID tokens, and service credentials. Best practices cover algorithm choice (RS256/ES256, avoid none), short lifetimes, audience and issuer validation, secure storage on clients, and rotation of signing keys via JWKS endpoints.

JWTs are not sessions—they are bearer credentials unless bound with mTLS, DPoP, or sender-constrained tokens. RFC 9700 and OWASP guidance stress validating every claim and never trusting client-side parsing alone.

Why it exists

Mis-implemented JWTs caused widespread API breaches—algorithm confusion, weak HMAC secrets, tokens without expiry, and log leakage of bearer strings. Standardising validation (signature, exp, aud, iss, nbf) in shared middleware reduces per-service mistakes. OIDC builds on JWTs for identity; APIs must treat access tokens distinctly from ID tokens.

When to use

  • OAuth 2.0 / OIDC access and ID tokens from enterprise IdPs or self-hosted authorization servers.
  • Service-to-service auth with short-lived JWT-SVID or signed service tokens.
  • Stateless BFF layers when session store cost is prohibitive—still prefer HttpOnly cookies over localStorage.

When not to use

  • Do not store JWTs in localStorage for browser apps—XSS exfiltration risk; use HttpOnly cookies or token handlers.
  • Avoid long-lived JWTs without refresh rotation—use server sessions when revocation must be immediate.
  • Never use JWTs for opaque server-side session IDs without need—prefer random session keys in Redis.

Pros and cons

Pros

  • Standard format across languages and gateways.
  • JWKS enables key rotation without redeploying every consumer.
  • Claims carry authorization context when sized carefully.
  • Works well with zero-trust service identity patterns.

Cons

  • Bearer tokens stolen via XSS or logs grant access until expiry.
  • Large claim sets bloat headers and caches.
  • Revocation requires short TTL, deny lists, or introspection endpoints.
  • Algorithm agility mistakes enable critical vulnerabilities.

Implementation notes

Validate signatures using issuer JWKS with pinned issuers; reject alg: none and unexpected algorithms. Enforce exp, nbf, aud, and iss; use clock skew tolerance under five minutes. Keep access token TTL minutes, refresh tokens rotation-bound. Log token IDs (jti) not full bearer strings.

For microservices, centralize validation in gateway or sidecar library versioned with security patches. Prefer asymmetric signing so verifiers never hold private keys. Document which claims services may trust for authorization versus authentication only.

Common failure modes

  • Algorithm confusion—accepting HS256 with public key as secret.
  • Missing audience check—token for one API accepted by another.
  • localStorage storage—XSS steals bearer tokens.
  • Forever tokens—no expiry or refresh invalidation path.
  • PII in claims—JWTs logged by proxies and browsers.

Decision checklist

  • Does middleware validate signature, alg, iss, aud, exp, and nbf?
  • Are access token lifetimes minutes, with refresh rotation?
  • Are signing keys rotated with published JWKS and overlap?
  • Are tokens excluded from logs and error reports?
  • Is client storage chosen to resist XSS (HttpOnly cookies)?
  • Is there a documented revocation or deny-list strategy?
