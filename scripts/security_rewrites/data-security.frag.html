What it is

Data security protects information across its lifecycle—classification, access control, encryption, masking, retention, and secure disposal. It combines governance (who may use what data) with technical controls (field encryption, tokenisation, DLP, row-level security) so confidentiality, integrity, and availability survive misconfiguration and insider risk.

Cloud data stores (RDS, S3, BigQuery) provide platform encryption; architects add column-level protection for regulated attributes, catalog sensitivity in a data catalog, and align retention with legal holds and privacy erasure requests.

The foundation is data classification: assigning sensitivity levels to data (Public, Internal, Confidential, Restricted) based on the harm that disclosure would cause, and applying proportionate controls at each level. Encryption at rest protects data stored on disk from physical media theft; encryption in transit (TLS) protects data from network interception; and column-level encryption (also called application-level encryption or field-level encryption) protects specific sensitive fields even within a database to which the application has legitimate read access.

Tokenisation replaces a sensitive value (credit card number, SSN) with a non-sensitive surrogate token that has no mathematical relationship to the original value and can only be de-tokenised by authorised parties with access to the token vault. It differs from encryption in that the token cannot be de-tokenised without the vault, even with the algorithm. Data masking transforms data for lower-trust environments: static masking creates a de-identified copy for development/testing; dynamic masking returns masked values in real-time to unprivileged users. PII (Personally Identifiable Information) handling calls for additional controls under GDPR and CCPA: data minimisation (don't collect what you don't need), purpose limitation (don't use data beyond its stated purpose), retention limits (delete data when no longer needed), and the right to erasure (technical ability to delete all data associated with a user).

Why it exists

Data is the target of most breaches—exfiltrated customer records drive fines under GDPR, HIPAA, and state privacy laws. Uniform “encrypt everything” without classification wastes budget and complicates analytics. Data security programmes define tiers (public, internal, confidential, restricted) and map controls so detectives and auditors see intentional design—not accidental exposure from shared replicas or over-broad IAM.

Data breaches are among the most costly security posture incidents: the IBM Cost of a Data Breach Report 2023 found an average cost of $4.45M per breach. Encryption at rest means that stolen database backups or cloud storage contents are unreadable without access to the encryption keys. Column-level encryption for the most sensitive fields (SSNs, payment card data, medical records) means that even a SQL injection attack that reads the database returns ciphertext rather than plaintext PII. GDPR/CCPA have created significant legal and financial obligations for data protection: GDPR fines can reach €20M or 4% of global revenue, whichever is higher.

Technical controls (encryption, masking, access logging) provide both security posture and the compliance evidence required during regulatory audits.

When to use

  • Any system storing PII, PHI, PCI, or trade secrets.
  • Analytics lakes combining multiple sources—risk rises without column policies.
  • Multi-tenant SaaS requiring logical isolation per customer dataset.
  • Cross-border processing subject to residency and transfer rules.
  • All systems storing personal data (PII) — GDPR/CCPA technical controls including encryption, access logging, and erasure capability are legally required.
  • Payment card data — PCI DSS mandates tokenisation or encryption of stored card data.
  • Healthcare data — HIPAA calls for encryption of PHI at rest and in transit.
  • Shared development/staging environments — production environments data ought to never be used; masked or synthetic data need to be used instead.

When not to use

  • Do not tokenise or encrypt operational metrics with no sensitivity—focus controls on classified fields.
  • Avoid copying production data to dev without masking—synthetic or subset data instead.
  • Column-level encryption on all fields: Column-level encryption prevents database-side filtering, aggregation, and indexing on encrypted fields. Apply it only to the most sensitive fields (SSN, credit card, password, medical record number) where the performance cost is justified by the protection requirement.

Pros and cons

Pros

  • Classification drives proportional spend on strongest controls.
  • Tokenisation limits PCI/PHI scope in application databases.
  • DLP and audit trails deter insider exfiltration.
  • Retention automation supports privacy erasure and litigation holds.

Cons

  • Field encryption complicates search and reporting without careful key design.
  • Catalog drift—unlabelled tables bypass policies.
  • DLP false positives interrupt legitimate workflows.
  • Global residency rules fragment architecture.

Pros

  • Encryption at rest ensures that stolen database backups provide no value to adversaries without the encryption keys.
  • Tokenisation of payment card data removes PAN from application storage entirely, dramatically reducing PCI DSS scope.
  • Data masking in development environments eliminates the risk of PII exposure to engineering teams and in development security posture incidents.
  • Data access logging creates the immutable audit trail required for compliance audits and enables detection of insider threats or compromised service accounts.

Cons

  • Column-level encryption prevents database-side predicates on encrypted fields; queries like WHERE ssn = ? cannot use indexes and require full table scans or application-side decryption.
  • Key management complexity: column-level encryption calls for application-level key management, key rotation processes, and re-encryption of existing data on key rotation.
  • Data erasure in event-sourced or append-only log architectures is architecturally challenging; erasure calls for crypto-shredding (destroying the encryption key for erased user's data) rather than physical deletion.
  • Data masking tools may not perfectly preserve data relationships needed for integration testing.

Implementation notes

Start with discovery and classification in the catalog; tag columns with sensitivity labels consumed by IAM and query engines. Enable platform encryption by default; add application-layer envelope encryption for crown-jewel fields using KMS. Mask or tokenise non-production environments; automate anonymisation pipelines.

Enforce row-level security or ABAC in analytics tools. Monitor bulk export APIs and warehouse queries with UEBA. Document retention schedules and legal hold overrides in runbooks accessible to legal and engineering.

Use envelope encryption for column-level encryption: generate a unique data encryption key (DEK) per-record or per-field, encrypt the sensitive value with the DEK, then encrypt the DEK with a KMS-managed key encryption key (KEK). Store the encrypted DEK alongside the ciphertext. This pattern means key rotation only calls for re-encrypting the DEKs (lightweight), not re-encrypting all the data. AWS KMS, Google Cloud KMS, and HashiCorp Vault all support this pattern.

For searchable encrypted data, consider deterministic encryption (same plaintext always produces same ciphertext, allowing equality comparison) for low-cardinality fields, or use a blind index (hash of the plaintext, indexed separately) for lookups, understanding that this leaks some information about equality.

For GDPR erasure, design the system from the start to support pseudonymisation: store a stable internal user_id as a foreign key in all data tables rather than PII like email. On erasure, the PII record is deleted or nulled, but the user_id foreign key rows in analytics and audit tables remain intact (now pseudonymous). For event streams and append-only logs, operationalize crypto-shredding: encrypt user-specific events with a per-user encryption key; when erasure is requested, delete the user's encryption key from KMS — all their encrypted events become unreadable.

Common failure modes

  • Replica sprawl—backups and ML copies lack same controls as primary.
  • Over-privileged analysts—warehouse roles see raw PII without masking.
  • Encryption without key governance—keys beside data in config buckets.
  • Stale classification—new columns default to internal without review.
  • Erasure without cascades—privacy requests miss derived tables.
  • Encryption at rest but plaintext backups: Databases with transparent encryption but unencrypted backup files that are exported to S3 without encryption — the backup provides plaintext access.
  • Encryption keys stored alongside data: Encryption keys stored in the same database as the encrypted data provide no security posture — an attacker who reads the database reads both the data and the key.
  • PII in application logs: Request logging that captures HTTP bodies or query parameters may inadvertently log PII (email addresses in query strings, names in JSON bodies) — logs are often stored with weaker access controls than the database.
  • No data retention policy enforcement: Data is collected with stated retention periods (GDPR: retain for purpose duration only) but deletion jobs are never implemented, resulting in data retained indefinitely.
  • No erasure capability for event streams: Kafka topics or event logs with no crypto-shredding strategy make GDPR erasure technically infeasible.

Decision checklist

  • Is every production datastore classified with owner and sensitivity tier?
  • Are restricted fields encrypted or tokenised with KMS-backed keys?
  • Is non-prod data masked or synthetic?
  • Do access reviews cover analytics and backup roles?
  • Are export and bulk query paths monitored?
  • Are retention and erasure procedures tested annually?
  • Is all data classified with sensitivity levels and controls applied proportionately?
  • Is encryption at rest enabled for all databases, object storage, and backups?
  • Are the most sensitive fields (SSN, PAN, medical data) protected with column-level encryption or tokenisation?
  • Is production environments PII masked or synthetic before use in development/testing?
  • Is there a technical erasure capability for GDPR right-to-be-forgotten requests?
  • Are data access logs collected and retained in an immutable store?

Example use cases

  • Illustrative scenario — PCI scope reduction: Card numbers tokenised at edge; only tokens in app DB; PAN vault isolated in CDE.
  • Illustrative scenario — healthcare analytics: PHI columns masked in warehouse; researchers query aggregated views only.
  • Illustrative scenario — GDPR erasure: Catalog-driven job deletes user rows and propagates to search indices within SLA.
  • Healthcare patient records: PHI fields (diagnosis, medication, notes) encrypted at column level using AWS KMS; encrypted DEKs stored per-patient; only authorised service accounts have IAM permission to call KMS decrypt; all PHI access logged to immutable CloudTrail.
  • E-commerce checkout: Credit card numbers tokenised via Stripe or Braintree token vault; application stores only token and last 4 digits; PCI DSS scope reduced to tokenisation integration points only; full PAN never touches application servers.
  • GDPR erasure at scale: User requests account deletion; internal user_id retained in analytics tables; per-user encryption key deleted from KMS (crypto-shredding any encrypted PII in Kafka events); PII database fields nulled; erasure event logged with timestamp for compliance evidence.
