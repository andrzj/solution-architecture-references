What it is

API security protects programmatic interfaces from abuse, data leakage, and unauthorized access. It spans strong authentication (OAuth 2.0, mTLS), fine-grained authorization (object-level checks per OWASP API Top 10), input validation, rate limiting, and observability. Unlike browser apps, APIs are easily scripted—attackers enumerate IDs, replay tokens, and flood endpoints without rendering UI.

Defense patterns include schema validation (OpenAPI/JSON Schema), scope-limited access tokens, per-tenant rate limits, WAF rules for common payloads, and centralized audit of admin routes. BOLA/IDOR remains the top API risk when services trust client-supplied identifiers without server-side ownership checks.

The OWASP API security posture Top 10 catalogues the most critical API-specific security posture weaknesses, distinct from the OWASP Web Application Top 10.

The leading API vulnerability is Broken Object-Level Authorisation (BOLA / IDOR): an API that accepts a resource identifier (e.g., /api/orders/12345) but fails to verify that the authenticated user owns resource 12345 allows horizontal privilege escalation — any authenticated user can access any other user's data by iterating IDs.

Other critical OWASP API risks include: Broken Authentication (weak API key schemes, missing token expiry), Excessive Data Exposure (returning full data models and relying on the client to filter — a mobile app might show 5 fields but the API returns 50, including sensitive ones), Mass Assignment (blindly binding request body fields to data model objects, allowing a user to set fields like isAdmin: true), security posture Misconfiguration (debug endpoints left enabled, verbose error messages revealing stack traces), and Injection (SQL, NoSQL, command injection via API parameters). GraphQL introduces additional surface: introspection exposes the full schema to adversaries, deeply nested queries can cause denial of service by triggering deeply recursive database joins, and field-level authorisation need to be implemented explicitly as GraphQL does not have built-in field visibility controls.

Why it exists

Microservices and mobile clients multiplied attack surface—every JSON endpoint is a potential data exfiltration path. Public breaches often trace to missing object authorization, excessive data exposure in responses, and weak credential handling. OWASP API Security Top 10 and NIST 800-218 give shared language for design reviews and customer assessments.

APIs have become the primary attack target because they are the authoritative data access layer for all application types (web, mobile, IoT, third-party integrations). The Verizon Data Breach Investigations Report has consistently identified web application attacks (primarily API exploitation) as the top action in data breaches. API-specific security posture weaknesses are often invisible to traditional web application scanners, which check for HTML-form-based attacks but miss BOLA, mass assignment, and GraphQL depth attacks. The programmatic, predictable nature of API endpoints makes them highly amenable to automated scanning and exploitation: an attacker can enumerate /api/orders/1 through /api/orders/1000000 in minutes to exfiltrate all orders in the database if BOLA is not mitigated.

When to use

  • Any HTTP/GraphQL/gRPC surface reachable outside a single trusted process.
  • Partner and mobile APIs where clients cannot hold secrets safely.
  • Admin and internal APIs still need authZ—VPN is not authorization.
  • High-value operations (payments, PII export, privilege changes) requiring step-up auth.
  • All public-facing APIs — OWASP API security posture controls are baseline requirements.
  • Internal microservice APIs — BOLA and mass assignment security posture weaknesses are exploitable by internal adversaries or via lateral movement.
  • GraphQL APIs — require additional controls beyond REST (query depth limiting, complexity analysis, introspection disabling in production environments).
  • Partner or third-party API integrations — API key management and scoped authorisation are essential.

When not to use

  • Do not skip API controls because “clients are internal”—lateral movement uses the same endpoints.
  • Avoid duplicating auth logic per service—use a gateway or shared library with tested policies.
  • These are not "use or not use" controls — all APIs require security posture. The question is which specific controls apply. For read-only public APIs with no user data, BOLA is less relevant but rate limiting and injection prevention still apply.

Pros and cons

Pros

  • Central gateway enforces authN, rate limits, and schema validation consistently.
  • Object-level checks prevent horizontal privilege escalation at scale.
  • Structured audit logs support fraud and IR investigations.
  • Rate limiting protects backends from scraping and credential stuffing.

Cons

  • Gateway becomes critical path—design for HA and graceful degradation.
  • Per-service authorisation logic still required—gateways cannot guess ownership.
  • Complex OAuth scopes confuse integrators without clear documentation.
  • Overly verbose errors aid attackers—balance debuggability and disclosure.

Pros

  • Object-level ownership checks in all data retrieval and modification endpoints block the most common API breach vector.
  • Allowlist-based field binding (rather than mass assignment) makes it impossible to set unexpected fields via API request bodies.
  • API gateway–level rate limiting provides automated protection against credential stuffing, enumeration, and scraping attacks.
  • Explicit response schemas block accidental sensitive data exposure — only approved fields are included in API responses.

Cons

  • Object-level authorisation checks need to be implemented consistently in every endpoint; a single missed check creates a vulnerability.
  • Rate limiting calls for careful tuning — too strict blocks legitimate high-volume API consumers, too loose provides no protection.
  • GraphQL complexity analysis calls for upfront effort to assign complexity scores to each field and calibrate acceptable thresholds.
  • Disabling GraphQL introspection in production environments means engineering teams cannot use GraphiQL, requiring alternative documentation solutions.

Implementation notes

Validate every input against OpenAPI schemas; reject unknown fields on admin routes. Enforce authorization in the service layer using server-side resource IDs—never trust opaque client IDs alone. Issue short-lived access tokens with minimal scopes; use refresh rotation and sender-constrained tokens where supported.

Apply per-identity and per-IP rate limits with backoff headers. Log authentication failures, authorization denials, and admin mutations with correlation IDs. Pair edge WAF with positive security models for JSON APIs where feasible.

operationalize BOLA protection as a mandatory architectural pattern: every database query that retrieves a resource by ID need to include the authenticated user's ID (or tenant ID) as an additional filter condition. This pattern ought to be enforced through code review and automated testing with authorisation tests that verify cross-user access is denied. The authorisation logic belongs in the service layer, not the API gateway — the gateway validates the token but cannot know the ownership semantics of individual resources.

For excessive data exposure, define explicit response DTOs (Data Transfer Objects) rather than returning ORM model objects directly. Use serialisation libraries that require explicit field inclusion (opt-in) rather than opt-out exclusion. For pagination, enforce maximum page size limits to block bulk data extraction. For error handling, return generic error messages to API clients (do not include stack traces, SQL error messages, or internal service names), but log full details server-side.

Use structured error responses with error codes that engineering teams can reference in documentation.

API keys ought to be treated as credentials and tokens, not configuration values: hash them before storage, display them only once at generation time, prefix with a service/environment indicator (sk_live_, sk_test_), scope them to minimum necessary permissions, and set expiry dates for automated rotation. For high-value APIs, use mutual TLS (mTLS) between partners rather than API keys — certificates provide stronger identity guarantees and are harder to phish.

Common failure modes

  • BOLA—changing /orders/123 to /orders/124 returns another tenant’s data.
  • Mass assignment—clients set role: admin via unfiltered JSON bodies.
  • Verbose errors—stack traces reveal schema and internal hostnames.
  • Long-lived API keys—never rotated, embedded in mobile binaries.
  • No rate limits—scrapers exfiltrate catalogs overnight.
  • BOLA via integer ID enumeration: Sequential integer IDs in REST URLs (/api/users/1001) are trivial to enumerate. Use UUIDs or opaque IDs — but this reduces friction, it does not replace ownership checks, which are still mandatory.
  • Verbose error messages: APIs returning "User email@example.com not found" confirm to an attacker whether an email address is registered — use "Invalid credentials and tokens" uniformly.
  • Missing rate limiting on auth endpoints: Login, password reset, and OTP verification endpoints without rate limits are vulnerable to credential stuffing and brute force attacks.
  • Admin API endpoints accessible to regular users: Admin operations (GET /api/admin/users) that rely only on "obscurity" (the endpoint isn't in docs) rather than proper role checks are exploitable by anyone who discovers the endpoint path.
  • GraphQL introspection enabled in production environments: Introspection gives adversaries a complete map of all types, fields, and mutations, dramatically accelerating exploitation.

Decision checklist

  • Does every sensitive operation verify resource ownership server-side?
  • Are tokens scoped, short-lived, and revocable with documented rotation?
  • Do schemas validate requests and strip unknown privileged fields?
  • Are rate limits and anomaly detection enabled on auth and data export routes?
  • Do logs capture denials without leaking secrets or full PII?
  • Has an API-focused pen test covered OWASP API Top 10 in the last year?
  • Are all data retrieval endpoints scoped to the authenticated user/tenant (BOLA prevention)?
  • Is field binding explicit (allowlist) rather than implicit (mass assignment)?
  • Are API responses defined as explicit DTOs with no extra fields?
  • Is rate limiting applied per-user and per-IP at the API gateway?
  • Are GraphQL introspection, query depth, and complexity limits configured in production environments?
  • Are API keys hashed in storage with defined scopes and expiry?

Example use cases

  • Illustrative scenario — mobile banking API: OAuth with PKCE, per-account object checks, and device binding on high-risk transfers.
  • Illustrative scenario — B2B partner API: mTLS plus scoped client credentials; rate limits per partner ID; webhooks signed with rotating keys.
  • Illustrative scenario — admin GraphQL: Persisted queries only; field-level auth directives; introspection disabled in production.
  • Financial services API: Banking API enforces object-level authorisation on all account and transaction endpoints; account access calls for both valid JWT and verified account ownership; all access logged for compliance audit.
  • GraphQL BFF: Backend-for-frontend GraphQL API disables introspection in production environments, applies per-query complexity scoring (mutations capped at 200, queries at 1000), and implements per-field authorisation middleware that checks user roles before resolving sensitive fields.
  • Partner API gateway: Partner API keys scoped to specific resources (orders:read, inventory:write), rate limited to 10,000 requests/hour, keys hashed in database and stored only in partner's secrets manager.
