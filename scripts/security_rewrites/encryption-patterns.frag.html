What it is

Encryption patterns go beyond default volume and TLS encryption to address application-specific risks: envelope encryption with per-record data keys, field-level encryption for regulated columns, tokenisation replacing PAN/SSN with reversible references, searchable encryption trade-offs, and mTLS for service identity on east-west paths.

Patterns align with NIST SP 800-57 key hierarchies and cloud KMS APIs—architects choose where ciphertext is produced (client, app tier, database) based on threat model and query requirements.

In distributed systems, encryption is applied at two layers: encryption in transit (protecting data moving between systems over networks using TLS) and encryption at rest (protecting stored data using symmetric encryption of storage volumes, databases, or individual fields). The dominant algorithm for symmetric encryption at rest is AES-256-GCM (Advanced Encryption Standard, 256-bit key, Galois/Counter Mode) — AES provides confidentiality, GCM provides authenticated encryption with associated data (AEAD), ensuring both confidentiality and integrity in a single operation.

For asymmetric operations (key exchange, digital signatures), RSA-4096 and ECDSA/P-256 are standard.

Envelope encryption is the pattern used by all cloud KMS providers: data is encrypted with a Data Encryption Key (DEK) generated per-object or per-record; the DEK itself is then encrypted by a Key Encryption Key (KEK) managed in a KMS (AWS KMS, Azure Key Vault, GCP Cloud KMS). The encrypted DEK is stored alongside the ciphertext. This pattern solves the key management scaling problem: you never need to call the KMS for each data operation (the DEK is cached); you only call the KMS to unwrap the DEK, which limits KMS API calls and cost, while ensuring that rotating or revoking the KEK immediately invalidates all data encrypted under it. Bring Your Own Key (BYOK) is an enterprise pattern where the customer owns and controls the root KEK in a customer-managed KMS or HSM, providing cryptographic isolation from the cloud provider.

Why it exists

Platform encryption protects disks and buckets but not authorized application users or SQL injection exporting plaintext. Field-level and tokenisation patterns shrink compliance scope and limit insider blast radius. mTLS proves peer identity beyond network location—essential for Zero Trust service meshes and regulated interconnects.

Encryption at rest ensures that physical theft of storage media, an overprivileged cloud support engineer, or a misconfigured storage bucket that becomes publicly readable cannot expose sensitive data as plaintext. Encryption in transit prevents man-in-the-middle attacks, network sniffing on untrusted networks, and passive data collection at network chokepoints. Together, these controls are mandated by virtually every data protection regulation (GDPR, HIPAA, PCI DSS) and are baseline requirements in SOC 2 Type II audits. Key management — generating, rotating, and controlling access to encryption keys — is the hardest part of encryption: a perfectly encrypted database with its encryption key stored in plaintext in the same system is effectively unencrypted.

When to use

  • PCI PAN, PHI, or national ID fields needing scope reduction or extra confidentiality.
  • Multi-tenant SaaS where per-tenant keys limit cross-tenant decrypt after bug.
  • Service meshes or gRPC estates requiring cryptographic peer authentication.
  • Backup and analytics pipelines that must not store decryptable PII.
  • All data in transit need to be encrypted — TLS 1.2 minimum, TLS 1.3 preferred, with no fallback to insecure versions.
  • All data at rest in databases, object stores, block storage, and backups need to be encrypted — provider-managed keys at minimum, customer-managed keys for sensitive or regulated data.
  • Mutual TLS (mTLS) for service-to-service communication in Zero Trust architectures.
  • Field-level encryption for the most sensitive fields (PAN, SSN, PHI) that require independent access control and audit separate from the database.
  • BYOK for regulated industries (financial, healthcare, government) where contractual separation of duties calls for cryptographic proof the cloud provider cannot access customer data.

When not to use

  • Do not field-encrypt columns heavily used in ad hoc SQL without deterministic or blind-index strategies.
  • Avoid custom envelope schemes—use KMS wrap/unwrap APIs and audited libraries.
  • Encrypting non-sensitive public data: Public static assets (CSS, JavaScript, public images) do not benefit from encryption at rest; the operational cost is not justified.
  • Rolling your own crypto: Never operationalize cryptographic primitives from scratch. Use well-audited libraries (libsodium, Bouncy Castle, Go's crypto/tls). Custom implementations introduce subtle security posture weaknesses that are impossible to detect without cryptographic expertise.

Pros and cons

Pros

  • Per-tenant keys constrain blast radius of application bugs.
  • Tokenisation keeps PAN out of application databases.
  • mTLS ties traffic to workload identity, not IP alone.
  • KMS envelope patterns scale with object count via cached DEKs.

Cons

  • Key rotation and re-encryption projects are operationally heavy.
  • Search and sort on encrypted fields require careful design.
  • mTLS certificate lifecycle burdens large microservice fleets.
  • Client-side encryption complicates support and key escrow debates.

Pros

  • Encryption at rest limits the damage from storage media theft, misconfigured access controls, or cloud provider access.
  • Envelope encryption scales efficiently — KMS is called only for key operations, not for each data operation.
  • Key rotation provides forward secrecy: future key compromise event does not expose past data if old keys are revoked.
  • mTLS provides cryptographic proof of both client and server identity, beyond what TLS alone provides.
  • Field-level encryption enables fine-grained access control at the field level, enforced cryptographically rather than only by access control policies.

Cons

  • Encryption adds latency and CPU overhead; AES-NI hardware acceleration on modern CPUs mitigates this, but KMS API calls add network round-trips.
  • Key management is operationally complex; incorrect key rotation procedures can result in data that cannot be decrypted.
  • BYOK adds significant operational burden: the customer is responsible for HSM availability and key backup procedures.
  • Encrypted fields cannot be indexed for equality or range queries without additional patterns (deterministic encryption or searchable encryption schemes).
  • mTLS certificate rotation need to be automated; expired certificates cause outages as difficult to diagnose as other TLS errors.

Implementation notes

Generate a data encryption key per object or row; wrap DEKs with KMS; store ciphertext and wrapped key together. Cache DEKs briefly with TTL; never log plaintext keys. For tokenisation, use vault-style token service with format-preserving options only when required.

Roll out mesh mTLS with centralized issuance (SPIFFE/SPIRE or cloud PKI); automate cert rotation shorter than compromise windows. Document which patterns apply per data class in the security architecture decision record.

For TLS configuration, enforce TLS 1.2 minimum with TLS 1.3 preferred. Disable weak cipher suites (RC4, DES, 3DES, MD5, SHA-1). Use forward secrecy cipher suites (ECDHE) so that future compromise event of the server private key does not expose past sessions. Set HSTS (HTTP Strict Transport security posture) with a long max-age (1 year) and include subdomains.

For databases, turn on TLS on all connections (PostgreSQL: sslmode=require; MySQL: require_secure_transport=ON) and configure server certificate validation in the application client to block MITM. For S3, turn on default bucket encryption with AWS-managed or customer-managed KMS keys; enforce encryption at upload with a bucket policy denying PutObject without x-amz-server-side-encryption.

For nonce/IV management with AES-GCM: never reuse a nonce with the same key. Generate a new random 96-bit IV for each encryption operation (12 bytes is standard for GCM). The risk of IV reuse is catastrophic for GCM — it leaks both the plaintext and the authentication key. Use a cryptographically secure random number generator (CSPRNG), not a general-purpose RNG.

Store the IV alongside the ciphertext; it is not a protected secret.

Common failure modes

  • DEKs stored beside data unwrapped—defeats envelope design.
  • Single CMK for all tenants—one IAM mistake decrypts everyone.
  • mTLS optional—fallback to plaintext east-west under load.
  • Tokens reversible without vault controls—tokens become secrets themselves.
  • No re-encryption on CMK rotation—old data keys orphaned.
  • Encryption key stored alongside data: Storing the KMS key ID or DEK in the same database row as the ciphertext without further protection negates the security posture benefit — an attacker who can read the database can also read the key.
  • No certificate validation: Accepting any certificate (InsecureSkipVerify in Go, verify=False in Python requests) provides no protection against MITM and negates TLS entirely.
  • IV reuse in AES-GCM: Using a counter or a sequential IV that wraps around, or reusing the same IV on re-encryption of the same data, breaks GCM authentication.
  • Weak key derivation: Deriving encryption keys from passwords using MD5 or SHA-1 without key stretching (PBKDF2/bcrypt/Argon2) allows brute-force attacks on the derived key.
  • Certificate expiry: mTLS or internal service certificates that expire and are not auto-renewed cause immediate service outages. Automate certificate issuance and renewal with cert-manager or SPIRE.

Decision checklist

  • Are sensitive fields mapped to encryption or tokenisation patterns with owners?
  • Does KMS enforce least-privilege decrypt per workload?
  • Is mTLS required on critical east-west APIs with automated rotation?
  • Are DEKs never logged or cached beyond defined TTL?
  • Is there a tested plan for CMK rotation and bulk re-wrap?
  • Do backups inherit the same field protections as primary stores?
  • Is all data in transit protected by TLS 1.2+ with forward-secrecy cipher suites?
  • Is all sensitive data at rest encrypted with AES-256 (or equivalent) using KMS-managed keys?
  • Is envelope encryption used so that the KMS is not called for every data operation?
  • Is automatic key rotation configured on all KMS keys with appropriate rotation schedules?
  • For the most sensitive fields (PAN, SSN, PHI), is field-level encryption applied independently of database-level encryption?
  • Are TLS certificates auto-renewed with sufficient lead time before expiry?

Example use cases

  • Illustrative scenario — per-tenant SaaS: CMK alias per tenant; DEK per customer record; decrypt scoped to tenant middleware.
  • Illustrative scenario — payment tokenisation: PSP vault holds PAN; merchant DB stores only tokens.
  • Illustrative scenario — mesh gRPC: SPIFFE IDs in certs; Envoy enforces mTLS STRICT mode.
  • Healthcare application: PHI fields (diagnosis codes, medical notes) encrypted with field-level AES-256-GCM using per-patient DEKs wrapped by a customer-managed CMK in AWS KMS; database-level encryption provides a second layer for all fields.
  • Payment processing: PCI DSS calls for encryption of PANs at rest; tokenisation replaces PAN with a token in application databases; the actual PAN is stored only in an encrypted vault with independent access controls.
  • Service mesh: Istio/Linkerd configures mTLS between all pods in the cluster; SPIFFE SVIDs issued by SPIRE provide workload identity; certs rotate every 24 hours automatically.
