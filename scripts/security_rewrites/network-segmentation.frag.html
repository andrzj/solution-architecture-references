What it is

Network segmentation divides infrastructure into isolated trust zones with explicit allow rules for east-west traffic instead of implicit full mesh reachability. In cloud VPCs that usually means tiered subnets (public edge, private application, restricted data), security groups that default deny lateral movement, and optional micro-segmentation inside a tier via Kubernetes NetworkPolicies or service mesh mTLS. Segmentation limits blast radius after credential theft or workload compromise and produces audit-ready boundaries for PCI, HIPAA, and Zero Trust programmes.

Perimeter controls in network security architecture protect north-south paths; segmentation addresses east-west lateral movement. The CIS Critical Security Controls (Control 13) expect segmented networks, monitored boundaries, and restricted administrative paths—architecture choices here are how many organisations satisfy those expectations.

Why it exists

Flat networks assume that anyone inside the perimeter is trusted. Cloud estates break that assumption: hundreds of services share address space, VPN users reach production subnets, and one compromised pod or stolen token can scan the entire RFC1918 range. Segmentation converts implicit trust into enforced policy so a foothold in a web tier does not imply database reachability without crossing another control. VPC Flow Logs and micro-segmentation telemetry also give incident responders a narrower scope when reconstructing attacker movement.

Regulated customers require network diagrams with clear enclaves. When tiers are encoded in infrastructure-as-code, evidence for SOC 2, PCI, or ISO surveillance audits is repeatable instead of quarterly firewall screenshots.

When to use

  • Multi-tier web applications where data stores must never accept internet-routable paths.
  • PCI cardholder data environments, HIPAA PHI zones, or FedRAMP scopes needing isolated processing.
  • Multi-tenant Kubernetes or shared VPC offerings with contractual isolation between tenants.
  • Zero Trust rollouts replacing flat VPN trust with identity-aware, path-specific access.
  • Hybrid cloud with peering or transit—segment paths so corporate LAN compromise does not imply production data reachability.

When not to use

  • Over-segmenting tiny sandboxes where ACL maintenance exceeds risk—use one coarse non-production VPC instead.
  • Subnet labels without enforced deny-by-default rules—documentation without policy is not segmentation.
  • Treating VLANs or subnets alone as sufficient without identity, authorization, and application controls on sensitive APIs.

Typical architecture

Public subnets expose only load balancers and NAT; application tiers accept traffic solely from load-balancer security groups; data tiers sit in subnets without internet gateway routes and accept only application security groups on database ports. Administrative access uses PAM bastions, SSM Session Manager, or ZTNA—not unconstrained VPN into data subnets.

Pros and cons

Pros

  • Containment after initial compromise—additional boundaries protect crown-jewel data.
  • Clear compliance enclaves with evidence from IaC and flow logs.
  • Pairs with service mesh mTLS and Zero Trust identity policies beyond IP rules.
  • Reduces pen-test and scan scope when non-production is truly isolated.

Cons

  • Routing complexity across peering, transit gateways, and multi-account hub-spoke designs.
  • Firewall and NetworkPolicy sprawl without IaC review and reachability tests.
  • Debugging blocked service-to-service paths requires documented flow matrices.
  • One misconfigured 0.0.0.0/0 rule can negate an otherwise tiered design.

Implementation notes

Model tiers in Terraform or equivalent IaC; reference security groups by ID rather than static CIDRs that drift under autoscaling. Enable VPC Flow Logs on production segments. Run periodic reachability scans or policy-as-code tests in CI to catch accidental open admin ports.

In Kubernetes, deny-by-default NetworkPolicies per namespace; align node security groups with pod CIDRs. Map hardening to CIS cloud and Kubernetes benchmarks where auditors expect benchmark scan exports. Document required flows per microservice so engineers know which allow rules are intentional.

Common failure modes

  • Data in private subnet, public security group—placement without restrictive groups is not segmentation.
  • Shared VPC without tenant isolation—one broad application group behaves like a flat network.
  • Peering transitive trust—corporate LAN paths into production via unintended routes.
  • Flat Kubernetes—any pod talks to any pod without NetworkPolicy or RBAC boundaries.
  • Admin VPN into data tier—engineer laptops become lateral movement bridges.

Decision checklist

  • Are data stores in subnets with no internet gateway route and least-privilege groups?
  • Is east-west traffic default deny except documented flows?
  • Are rules managed as IaC with peer review?
  • Do reachability or policy tests run on a schedule or in CI?
  • Is admin access via PAM, SSM, or ZTNA—not open VPN into sensitive tiers?
  • Are flow logs enabled for incident reconstruction?
