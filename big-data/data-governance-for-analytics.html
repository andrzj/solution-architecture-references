Big Data & Analytics Governance

Data Governance for Analytics

Ownership, catalogs, engine-level access control, lineage, and PII handling for shared analytical platforms at scale.

⏱ 11 min read

What it is

Data governance for analytics is the operating model and tooling that make shared warehouses and lakehouses trustworthy: every dataset has an owner, sensitivity is classified, access is enforced at the engine, lineage is knowable, and quality expectations are explicit. Governance answers who may read which columns, where a metric originated, whether free-text fields contain PII, and who must be notified before a breaking schema change.

At scale—hundreds of tables, dozens of teams, and paths across batch, streaming, and BI—governance cannot live in spreadsheets of bucket ACLs. It combines a metadata catalog (DataHub, Apache Atlas, or cloud-native catalogs), policy enforcement on query engines (Apache Ranger, Unity Catalog, warehouse policy tags), lineage emission (OpenLineage into Marquez or the catalog), and optional PII discovery (for example Microsoft Presidio on ingest). Domain teams own data products; the platform team supplies standards and self-service primitives.

Why it exists

Mature analytics platforms collapse without governance in three predictable ways. Data swamps appear when no catalog records what exists, who owns it, or whether it is fit for production use. Compliance breaches follow when PII propagates into training sets, exports, and sandboxes because controls stop at the application, not the SQL engine. Unexplained quality incidents persist when a KPI moves and no lineage graph identifies which upstream job or source changed.

Formal governance ties metadata, policy, and lineage into the same surfaces engineers already use to query data, so discovery and enforcement stay aligned rather than living in a wiki nobody reads.

When to use

  • Multi-team platforms sharing lakehouse or warehouse gold assets with cross-domain consumers.
  • Regulated or sensitive domains—PII, payments, health—requiring column-level controls and audit evidence.
  • Self-serve BI and embedded analytics where metric definitions and row access must be consistent.
  • ML platforms pulling features from curated tables that must not leak labels or identifiers inappropriately.
  • Open table formats on object storage where bucket IAM alone cannot express table- or column-grain policy.

When not to use

  • Single-team sandboxes on synthetic data with no path to production consumers.
  • Short-lived proofs of concept torn down before another engineer needs discovery or access controls.
  • Immutable archives with no interactive SQL and governance already satisfied by object retention alone.

Typical architecture

Pipelines and query engines register datasets in a catalog, emit lineage, and enforce row and column policies before results reach analysts. Quality checks and PII scanning can run at ingest boundaries on the same metadata graph.

Pros and cons

Pros

  • Engine-enforced column and row controls protect PII even when consumers run ad hoc SQL outside curated dashboards.
  • Lineage graphs shorten impact analysis for schema changes and root-cause analysis for metric regressions.
  • Catalogs with ownership and glossary metadata reduce time spent hunting for the right dataset or accountable team.
  • Ingest-time PII scanning limits sensitive columns entering silver and gold before policies attach.

Cons

  • Self-hosted stacks (Atlas, Ranger, DataHub) add operational dependencies and upgrade cadence.
  • Programs need organizational buy-in: domains must steward tags, contracts, and change notices.
  • Lineage is incomplete until every critical orchestrator and engine emits events.
  • Masking and row filters add query latency on hot paths unless scoped carefully.

Implementation notes

Progressive rollout: Avoid launching catalog, lineage, PII scanning, and column security in one big bang. Classify and protect the highest-risk columns first, then instrument lineage for gold and feature pipelines, then expand catalog stewardship and glossary alignment.

Enforcement points: On Hadoop-style stacks, Apache Ranger policies on Hive, Spark, and Kafka integrate with Atlas tags. On cloud warehouses, use policy tags and authorized views. On lakehouses, register Delta, Iceberg, and Hudi tables in Unity Catalog, Glue Lake Formation, or an Iceberg REST catalog so grants travel with table metadata—see Delta Lake governance, Iceberg access control, and Hudi access control.

Lineage: Emit OpenLineage from Airflow, Spark, dbt, Flink, and quality frameworks into Marquez or DataHub so impact queries stay in one graph. PII: Run Presidio or similar on bronze text columns, persist tags to the catalog, and require masks before silver promotion.

Ownership: Name a data product owner per published dataset; tie schema contracts, freshness SLAs, and breaking-change notification to that role per data mesh practice.

Common failure modes

  • Governance without enforcement: Tags in a catalog that query engines never enforce—analysts read sensitive columns via direct SQL.
  • Orphan datasets: No owner for a production table; schema drift breaks consumers without a accountable fix or communication.
  • Lineage gaps: Critical jobs skip OpenLineage, so erasure and impact analysis miss derived tables.
  • Policy theater: Annual access reviews that never reconcile with live grants in Ranger or the catalog.

Decision checklist

  • Does every production dataset have a named owner and escalation path?
  • Are PII and sensitive columns tagged with engine-enforced masks or denies, not catalog-only labels?
  • Is OpenLineage (or equivalent) wired for pipelines that feed gold and ML feature tables?
  • Can engineers discover datasets, owners, and classifications in a single catalog?
  • Is there a documented, enforced process to notify consumers before breaking schema changes?
  • On lakehouse tables, are grants managed through the unified catalog rather than raw object paths?

Example use cases

  • Healthcare analytics platform (HIPAA): Bronze → Presidio PII scan on admit notes → PHI columns tagged in Atlas → Unity Catalog column filter enforced → only users with PHI role see unmasked values; OpenLineage tracks which ML training datasets derive from PHI source tables for audit.
  • GDPR right-to-erasure: Customer deletion request → DataHub lineage graph identifies all derived tables containing customer_id → automated deletion propagation script runs against each table.
