Batch Processing

Scheduled jobs over bounded datasets for lakehouse ETL, ML snapshots, and reconciliation—with idempotent partitions and warehouse-scale engines.

⏱ 10 min read

What it is

Batch processing is data computation that runs over a bounded input—files, table partitions, or a time window—on a schedule or on demand, then finishes. Unlike stream jobs that never “complete,” batch jobs have a defined start and end: ingest a dataset, transform it, write outputs, and exit. Orchestrators (Airflow, Dagster, cloud workflow engines) trigger runs; engines such as Apache Spark, Hive, or warehouse SQL perform the work.

Batch is the default shape for analytics pipelines: nightly marts, compliance exports, search index rebuilds, and ML training snapshots all assume you can wait minutes or hours for a correct answer over the full slice of data.

Why it exists

Most downstream decisions tolerate delay. Finance close, capacity planning, and historical reporting need accurate aggregates over complete datasets more than they need sub-second updates. Batch fits that profile: run when data is ready, exploit parallelism over the full partition set, and shut clusters down between runs so you pay for peak capacity only when you need it.

Batch also simplifies correctness. Given immutable inputs and deterministic transforms, the same job re-run for the same partition should produce the same outputs—making backfills, audits, and incident recovery predictable compared with long-lived streaming state.

When to use

  • You load curated tables in a lakehouse or warehouse on hourly, daily, or weekly cadences (ETL/ELT).
  • Freshness SLAs are measured in minutes to hours, not seconds.
  • You need full-history recomputation, reconciliation, or audit exports over known partitions.
  • ML feature stores or training sets are rebuilt from historical snapshots.
  • Downstream search indexes, caches, or embeddings are warmed from warehouse or lake exports.

When not to use

  • Product or risk workflows require sub-minute latency (fraud blocks, live personalization, operational alerting).
  • Regulatory rules demand per-event reporting with no acceptable micro-batch gap.
  • Data volume is small enough that interactive SQL or a single-node script is simpler and faster end to end.

Typical architecture

Sources land in raw or bronze zones; an orchestrator waits for upstream completeness, then launches idempotent transform jobs. Curated tables feed BI, ML, and serving systems. Raw layers stay append-only so partitions can be reprocessed without rewriting history in place.

Pros and cons

Pros

  • Economical at scale: clusters spin up for the run, then release capacity.
  • Deterministic replays over immutable partitions simplify backfills and audits.
  • Mature tooling—Spark, warehouses, table formats, and orchestration—is widely understood.
  • Peak throughput for heavy shuffles and joins is often higher than continuous streaming for the same hardware.

Cons

  • Minimum latency is the schedule interval plus job runtime.
  • Spiky resource use requires capacity planning or queueing during close periods.
  • Late-arriving data forces reprocessing windows or complex incremental logic at batch boundaries.

Implementation notes

Partitioning: Align job inputs and outputs with date or business keys so a single partition can be re-run without touching neighbors. Document partition keys in the catalog so consumers know what “latest” means.

Idempotency: Writes should overwrite or merge into a partition deterministically (for example merge into Iceberg/Delta, or `INSERT OVERWRITE` with explicit predicates). Avoid append-only fact tables without deduplication keys unless the pipeline is strictly once-only.

Readiness, not cron alone: Gate runs on upstream file arrival, row-count sensors, or data-quality checks—not only on wall-clock schedule—so partial upstream outages do not publish incomplete marts.

Observability: Record input/output row counts, bytes processed, and lineage per run; alert when metrics deviate from trailing baselines.

Common failure modes

  • Silent partial writes: Jobs exit successfully after writing only some partitions because upstream data was incomplete.
  • Non-idempotent reruns: Retries duplicate rows or double-apply transforms when merge semantics are undefined.
  • Clock-driven schedules: Pipelines run before dependencies finish, publishing stale or empty slices.
  • Unbounded backfills: Reprocessing entire history on every logic change instead of scoped partition ranges.

Decision checklist

  • Can the job be safely rerun for the same input partition without corrupting downstream tables?
  • Are raw inputs immutable and curated outputs versioned or partition-addressable?
  • Is the freshness SLA expressed as “data available by time T,” not merely “job started at T”?
  • Do orchestration sensors prove upstream completeness before transforms start?
  • Are late-arriving events handled with an explicit reprocessing window or incremental model?

Example use cases

  • Illustrative scenario — A retailer runs nightly Spark jobs that aggregate point-of-sale and web orders into a gold sales mart; dashboards read the mart each morning with a stated “data as of 06:00 UTC” freshness.
  • Case study — Netflix has long relied on large-scale scheduled batch analytics (including Spark on object storage) for recommendations and reporting pipelines where throughput and reproducibility matter more than per-event latency.
