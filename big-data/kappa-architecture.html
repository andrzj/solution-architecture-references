Kappa Architecture

Jay Kreps' Kappa Architecture: stream-only processing using a replayable immutable log (Kafka), reprocessing via new consumer groups, comparison with Lambda Architecture, and when single-pipeline simplicity is the right choice.

⏱ 10 min read

What it is

Kappa Architecture is a stream-first design for analytical and operational data products: one processing codebase reads an immutable event log, maintains serving views for live queries, and replays the same log when logic or schemas change. Jay Kreps proposed it as a simpler alternative to Lambda Architecture, arguing that a durable, replayable log can stand in for a separate batch “truth” layer when retention and reprocessing mechanics are designed deliberately.

The central idea is that long-retained, ordered logs (days, months, or longer via compaction or tiered storage) let you rebuild history by resetting consumer offsets, much as batch jobs re-scan HDFS—without maintaining parallel batch and speed implementations of the same business rules.

Why it exists

Lambda Architecture separates batch accuracy from stream freshness, but that split forces two code paths for one definition of truth. The batch job and the stream job diverge over time: bug fixes land in one place first, libraries age differently, and edge cases get handled inconsistently. Operations pay twice—for scheduling, monitoring, and incident response—whenever metrics disagree between layers.

Kappa collapses those paths when the organization already invests in stream processing and log infrastructure. Reprocessing becomes an operational procedure (new consumer group, parallel run, cutover) rather than a second platform. Kreps framed this in Questioning the Lambda Architecture after building Kafka-centric systems at LinkedIn.

When to use

  • You are building a new system and the team can own stream processing, log retention, and stateful jobs end to end.
  • Business rules change often, and you want a single place to version, test, and deploy transformations.
  • Full-history replay is infrequent (for example after a bug fix or model change) rather than a continuous batch recompute.
  • An immutable, replayable log such as Apache Kafka (or an equivalent) is already part of the platform.

When not to use

  • Workloads need multi-pass batch algorithms—large-scale ML training, graph iterations, or ad-hoc SQL over full history—that stream state models handle poorly.
  • Retention for the entire history you must replay is economically impractical without tiered storage or archival replay paths.
  • You inherit a mature Lambda deployment and migration cost outweighs relief from dual-code-path drift unless that drift is already causing production pain.

Typical architecture

Producers append events to a durable log; stream jobs project aggregates or entity state into a serving store; applications query that store. When processing logic changes, a new job replays from the earliest required offset into a isolated store until cutover.

Pros and cons

Pros

  • One implementation of business logic reduces drift between “batch truth” and “stream approximation.”
  • Operations center on a single processing engine, one log, and one serving tier instead of synchronized batch and speed stacks.
  • Parallel reprocessing and store cutover can refresh history without taking live queries offline.
  • Tiered log storage and compaction patterns can extend retention affordably when full replay is a requirement.

Cons

  • Replay duration grows with retained volume; large backfills stress compute and downstream stores.
  • Iterative graph or ML jobs still belong in batch engines; Kappa does not remove that need.
  • Long log retention has storage and operations cost even when tiered off hot disks.
  • Stateful streaming with exactly-once semantics demands careful checkpointing; mistakes surface as duplicates or gaps after replay.

Implementation notes

Consumer group isolation: Give each live or reprocessing job its own consumer group so offsets do not collide. Run the new version from the required starting offset while the previous version continues serving until the replay reaches the live tail.

Serving store versioning: Write replay output to a separate namespace or table suffix until lag is zero and spot checks match expectations; only then repoint readers. Treat partial replay as non-authoritative for customer-facing queries.

Retention policy: Document the oldest offset you must be able to seek to for compliance or rebuild SLAs, and size retention, compaction, and tiered storage to match—not default broker limits.

Common failure modes

  • Insufficient log retention: Data ages off the log before a replay starts, so the architecture cannot fulfill its rebuild promise.
  • Shared consumer groups: A reprocessing job steals or resets offsets and corrupts live consumption progress.
  • Weak delivery guarantees: Replays without idempotent writes or transactional sinks duplicate rows in materialized views.

Decision checklist

  • Does retention (including tiered or archived segments) cover the full history you must be able to replay?
  • Does every job version use a dedicated consumer group and documented starting offset?
  • Are producers and sinks configured for the delivery semantics you claim (at-least-once vs exactly-once)?
  • Can queries cut over to a replayed store only after lag and correctness checks pass?
  • Are multi-pass or training workloads routed to batch paths instead of forced into stream state?

Example use cases

  • Illustrative scenario — A social product streams activity events into Kafka; Flink maintains per-user counters in Redis, and when aggregation logic changes the team deploys a v2 job, replays from the earliest retained offset, and cuts query traffic to a new key prefix before retiring v1.
  • Illustrative scenario — A payments platform retains card-authorization events on a durable log, computes velocity features in Flink for live fraud scoring, and replays a month of history when a new model version ships.
  • Case study — LinkedIn developed Apache Kafka and stream-oriented processing patterns that underpin Kappa-style replay and single-pipeline reprocessing discussions.

Related patterns

  • Lambda Architecture — The pattern Kappa simplifies; useful when complex batch algorithms are genuinely required.
  • Spark Architecture — Spark Structured Streaming is a common stream processor in Kappa deployments; Spark batch is still used for multi-pass algorithms alongside Kappa.
  • Event Streaming — Kafka as the immutable log at the heart of Kappa Architecture.
