Lakehouse Governance

Policies and tooling to secure, classify, and audit tabular data on object storage with warehouse-grade controls.

⏱ 10 min read

What it is

Why it exists

Unrestricted S3/ADLS buckets create shadow data and regulatory risk. Governance binds identities, classifications, and audit trails to tables and volumes.

When to use

  • Multi-team analytics on shared lakehouse.
  • PII/PHI data on object storage.
  • Need fine-grained table/column ACLs.
  • Cross-region replication with policy enforcement.

When not to use

  • Single-team sandbox with no sensitive data.

Typical architecture

Catalog + policy engine + audit log over table storage.

Pros and cons

Pros

  • Unified security model.
  • Lineage for compliance.

Cons

  • Migration from legacy ACLs.
  • Performance of row/column masks.

Implementation notes

Centralize metastore; tag columns with classifications; enforce ABAC where possible. Automate lineage from Spark/DBT jobs. Retention and legal hold on table versions; block public bucket policies via policy-as-code.

Common failure modes

  • Shadow catalogs: Teams bypass governance with private buckets.
  • Over-broad grants: `*` readers on production marts.

Decision checklist

  • Are all production tables registered?
  • Is PII tagged and masked by default?
  • Can you produce an access report per regulation?

Example use cases

  • Healthcare lakehouse: Column masks on PHI; audit every analyst query via engine integration.
