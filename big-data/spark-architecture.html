Apache Spark Architecture

Driver, executors, Catalyst, and shuffle boundaries—the cluster model behind batch, SQL, and Structured Streaming on Apache Spark.

⏱ 12 min read

What it is

Apache Spark is a distributed analytics engine that runs user programs as a directed acyclic graph (DAG) of stages across a cluster. A single driver JVM coordinates work: it builds logical and physical plans, cuts the DAG at shuffle boundaries, and sends tasks to executors that read partitions, compute, and optionally cache data in memory. Cluster managers (YARN, Kubernetes, or standalone) allocate executor containers; Spark itself schedules tasks within those resources.

Most teams interact through DataFrames and SQL: Catalyst optimizes logical plans (predicate pushdown, join reordering), and Tungsten generates efficient bytecode for tight loops. RDDs remain the low-level fault-tolerance primitive—lineage lets Spark recompute lost partitions—but DataFrames are the default for ETL, lakehouse queries, and Structured Streaming micro-batches.

Why it exists

Hadoop MapReduce persisted intermediate results to disk after every map and reduce wave, which made iterative ML, graph algorithms, and multi-pass SQL painfully slow. Spark introduced in-memory iteration across stages and a unified API for batch, SQL, streaming, and MLlib—reducing the number of specialized systems in a data platform.

Spark also met teams where they already were: on YARN and HDFS, later on object storage and Kubernetes. Managed offerings (Databricks, EMR, Dataproc, Synapse) operationalized the cluster model so engineers could focus on transforms rather than JVM tuning—while still needing a mental model of drivers, shuffles, and partitions when jobs misbehave.

When to use

  • Large-scale ETL and lakehouse curation (bronze → silver → gold) over Parquet, Iceberg, Delta, or Hudi.
  • Heavy joins, windowed aggregations, or SQL over terabyte-scale datasets that exceed a single-node engine.
  • Distributed feature engineering or MLlib jobs that prepare training data before handing off to deep-learning frameworks.
  • Batch recomputation in Lambda-style deployments or replay workloads in Kappa-style designs via Structured Streaming.
  • You have—or can buy—a cluster or managed Spark plane and staff to tune shuffle, memory, and skew.

When not to use

  • Datasets fit comfortably on one machine and pandas, DuckDB, or warehouse SQL is faster to develop and operate.
  • You need millisecond per-record APIs; Spark’s driver and task scheduling overhead dominates small or ultra-low-latency work.
  • No operations capacity and no managed Spark—serverless SQL or warehouse-native ELT may be simpler.

Typical architecture

Client code calls actions on a SparkSession in the driver. The DAG Scheduler forms stages at shuffles; the Task Scheduler places tasks on executors. Executors run threads, cache blocks, and write shuffle files; the cluster manager only supplies containers or YARN slots.

Pros and cons

Pros

  • One engine spans batch, SQL, Structured Streaming, and MLlib, reducing the number of specialized runtimes to operate.
  • Catalyst and Tungsten optimize DataFrame plans and generate efficient loops for many ETL and SQL workloads.
  • Deep lakehouse ecosystem (Delta Lake, Iceberg, Hudi) and managed offerings integrate Spark as the default transform layer.
  • In-memory caching and lineage-based recovery speed iterative jobs versus disk-heavy MapReduce patterns.

Cons

  • JVM memory tuning is non-trivial: GC pauses, driver OOM from collects, and executor heap sizing require ongoing attention.
  • Wide transformations trigger costly shuffles that often dominate runtime and failure rates.
  • Job startup and executor provisioning make Spark a poor default for tiny or sub-minute interactive tasks.
  • Structured Streaming’s micro-batch cadence adds latency versus continuous stream engines when seconds matter.

Implementation notes

Partition sizing: Parallelism follows partition count. Aim for partitions roughly 128–512 MB at rest and enough tasks to keep cores busy without drowning the scheduler. After joins or group-bys, default spark.sql.shuffle.partitions (often 200) may be far too high or too low for your data volume—tune explicitly.

Shuffles and skew: Prefer narrow transforms where possible; broadcast small dimension tables; use salting or AQE (Spark 3.x) when a few keys dominate partition size. Review the Spark UI for stages with one straggler task.

API choice: Default to DataFrames/SQL so Catalyst can push filters and prune columns; reserve RDDs for primitives Catalyst cannot express.

Common failure modes

  • Executor OOM: Oversized shuffles, wide collects, or caching unbounded datasets exhaust heap; use the Spark UI and event logs before blindly raising memory.
  • Mis-tuned shuffle partitions: Too few partitions create giant tasks; too many create scheduler noise—both show up as timeouts or skew.
  • Driver collects: collect() or large broadcasts on big dimensions move too much data to the driver JVM.

Decision checklist

  • Are DataFrames used instead of RDDs (unless there is a specific reason for RDDs)?
  • Is spark.sql.shuffle.partitions tuned for the actual data volume and cluster size?
  • Are broadcast joins configured for small tables to avoid expensive sort-merge shuffles?
  • Is Adaptive Query Execution (AQE) enabled (Spark 3.x default: true) for automatic skew handling?
  • Is the Spark UI reviewed for skewed stages and excessive GC time?

Example use cases

  • Illustrative scenario — A lakehouse team runs Spark jobs that promote raw JSON from object storage into silver Parquet, then Spark SQL builds gold fact tables for BI tools, using Delta Lake for ACID merges and schema evolution.
  • Case study — Netflix has publicly described using Apache Spark for large-scale data processing alongside other engines in its data platform.
