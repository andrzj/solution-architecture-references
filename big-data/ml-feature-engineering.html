ML Feature Engineering

Engineering ML features on lakehouse and stream data: Feast, Tecton, and Vertex-style stores, offline vs online tiers, point-in-time joins, Spark/Flink pipelines, skew prevention, and drift monitoring.

⏱ 12 min read

What it is

ML feature engineering on a data platform is the work of turning curated warehouse and stream data into stable, entity-keyed signals models can train on and score with at runtime. That includes aggregations over sliding windows, encodings, joins across domains, and freshness choices—but also the operational contract: the same logic in batch retraining and online inference, discoverable definitions, and historical values addressable by entity and timestamp.

At scale, teams usually anchor that work in a feature store: a registry plus offline store (full history on S3 Parquet, BigQuery, Hive, or Delta) and online store (Redis, DynamoDB, Bigtable) fed by Spark or Flink materialisation. Feast, Tecton, and Vertex AI Feature Store implement the same split with different degrees of managed operations.

Why it exists

Gold tables and dashboards already answer “what happened,” but ML needs keyed, time-aligned inputs tied to each decision moment. Without platform patterns, the same failures recur. Training-serving skew appears when notebook SQL builds training columns while production services reimplement aggregates in another language. Duplication multiplies when every squad schedules its own rolling-window job from the same Kafka topic. Leakage hides in naive joins: a label at time T paired with a feature computed at T+1 inflates offline metrics until live traffic disproves them.

Formal feature engineering on the big-data stack—medallion sources, idempotent Spark jobs, optional stream enrichment, dual offline/online writes, and point-in-time training exports—makes features as reusable as any other data product while meeting latency and audit requirements.

When to use

  • Models consume shared signals built from lakehouse gold tables or high-volume event streams.
  • Both historical retraining and online scoring must read logically identical feature definitions.
  • Labels are time-stamped events and require point-in-time joins to time-varying features.
  • Cross-team reuse, lineage, and freshness SLAs matter as much as model accuracy.
  • Stream plus batch materialisation is required to bridge warehouse cadence and inference latency.

When not to use

  • One offline model with a handful of columns refreshed from a single SQL job on a relaxed schedule.
  • No online serving path and no expectation of sharing engineered features outside one team.
  • Features are passed through unchanged from raw operational tables with no aggregations or versioning needs.

Typical architecture

Raw and silver data feeds batch and streaming feature pipelines; computed values land in offline and online stores; trainers pull point-in-time datasets while inference services read latest values per entity key.

Pros and cons

Pros

  • Point-in-time correct exports align training labels with historical feature snapshots—reducing leakage on time-varying warehouse facts.
  • One registered definition for offline and online paths narrows training-serving skew—the dominant silent production regression for engineered features.
  • Reuse across squads avoids repeated Spark jobs for the same rolling-window metrics from shared gold tables.
  • Pre-materialised online values keep inference off the critical path instead of recomputing aggregates per API request.

Cons

  • Offline store, online store, registry, and materialisation jobs add platform surface area beyond warehouse SQL alone.
  • Registry and naming discipline is organisational work—features must be owned, documented, and versioned like data products.
  • Online store cost and hot-key risk scale with entity cardinality, feature width, and read QPS.
  • Large point-in-time training dataset builds are shuffle-heavy in Spark and need partition tuning and cache strategy.

Implementation notes

Naming and registry: Enforce a pattern such as {entity}_{source}_{aggregation}_{window} (for example user_transactions_count_30d) in the registry so teams discover existing features before launching another pipeline.

Batch vs stream materialisation: Nightly or hourly Spark jobs from gold tables cover most windows; reserve Flink or Kafka Streams for signals that must land in the online store within minutes. Each streaming feature needs explicit watermarking and out-of-order handling.

Single source of truth for logic: Where the store supports it, declare features once (Feast FeatureView, Tecton definition, Vertex entity type) and let the platform materialise both tiers; otherwise log served feature vectors for label joins.

Common failure modes

  • Training-serving skew: Different runtimes or null/time-zone handling between notebook training code and production serving—compare distributions on logged inference features.
  • Missing point-in-time joins: Any time-varying column joined without “as-of” semantics can leak future warehouse state and inflate offline metrics.
  • Online staleness: Materialisation lag or failed micro-batches leave scoring on outdated rollups—per-feature freshness alarms, not only job-level green checks.
  • Unbounded streaming state: Long-window aggregations without compaction or TTL blow memory in Flink executors or online store key cardinality.

Decision checklist

  • Are all time-varying features joined with point-in-time correct logic when building training sets?
  • Does one definition (or logged serving vectors) back both offline export and online lookup?
  • Which features are batch-only vs stream-materialised, and are freshness SLAs defined for each?
  • Are inference-time feature values logged for label joinback and skew debugging?
  • Is drift monitored (PSI, null rate, range) with alerts tied to materialisation runs?
  • Can teams discover and reuse registry features before adding new Spark jobs?

Example use cases

  • Real-time fraud scoring: On each payment event → online store lookup for 50 user features (velocity counts, historical amounts) with P99 < 5ms → fraud model inference → decision returned in < 50ms total; training uses PITC joins over 90-day transaction history; feature drift monitored daily.
  • Recommendation engine: Batch Spark job nightly materialises 200 user and item features to offline store (S3 Parquet); training dataset generated with PITC joins over 6-month history; hot features (session-level) added as streaming features via Flink → Redis; shared feature definitions reused by search ranking team.
