Lambda Architecture

Lambda architecture merges batch and speed layers over an immutable master dataset—accuracy from full recomputes plus low-latency recent views.

⏱ 10 min read

What it is

Lambda architecture is a big-data pattern, popularized by Nathan Marz, that answers queries by combining three layers: an immutable master dataset of raw events, a batch layer that periodically recomputes complete views from that history, and a speed layer that incrementally updates recent data between batch runs. A serving layer merges batch and speed views at query time so readers see both accurate history and low-latency recent updates.

The design treats batch computation as the source of truth for correctness—given enough time, MapReduce or Spark over the full raw log can rebuild arbitrary views—while the speed layer covers the latency gap with streaming or micro-batch processors (Storm, Flink, Spark Structured Streaming, and similar).

Why it exists

In the early 2010s, Hadoop batch pipelines over HDFS delivered dependable analytics but often finished hours after data arrived. Product teams still needed fresher counts, recommendations, and operational dashboards without giving up the ability to recompute everything from raw data when logic or regulations changed. Lambda architecture formalized running batch and real-time paths in parallel against the same immutable ingress, then merging results for queries—a compromise described in Marz’s writing and in Big Data: Principles and best practices of scalable realtime data systems (Manning).

Jay Kreps later argued in Questioning the Lambda Architecture that maintaining two implementations for one metric often costs more than disciplined log retention and replay on a stream platform. Lambda remains relevant when batch correction is non-negotiable, serving layers must hide merge semantics, or batch investment cannot be retired yet—but teams should budget explicit reconciliation tests between speed and batch views.

When to use

  • You genuinely need both near-real-time read models and the ability to recompute accurate historical views from immutable raw data.
  • A mature batch platform already exists and you must add streaming without replacing the batch investment.
  • Regulatory or product requirements mandate full historical reprocessing from raw events when algorithms or definitions change.

When not to use

  • You are building a greenfield system where a single replayable log and stream processor (Kappa architecture) can meet freshness and reprocessing goals.
  • Data volume and retention fit comfortably in one streaming pipeline with affordable log retention and occasional replay.
  • The team cannot afford to implement, test, and operate two code paths for the same business logic.

Typical architecture

All incoming data appends to an immutable master store. The batch layer scans history on a schedule to publish complete views; the speed layer consumes the live tail to update recent state. Query handlers read merged results from the serving layer, using a time cutoff to combine batch-backed history with speed-layer updates.

Pros and cons

Pros

  • Periodic batch recomputation from raw data can correct speed-layer mistakes and yields authoritative historical views.
  • The speed layer exposes recent updates without waiting for the next full batch cycle to finish.
  • Immutability at the master dataset simplifies audit trails because every correction is a new replay rather than an in-place edit.
  • The pattern is well documented and aligns with mature Hadoop-era tooling (HDFS, Hive, Spark) that many enterprises already operate.

Cons

  • The same business logic must be implemented twice—batch and stream—which invites divergence, duplicated tests, and doubled incident surface.
  • Operating batch engines, stream engines, multiple view stores, and merge logic in the serving layer increases cost and on-call complexity.
  • Full batch recomputes over growing history can be slow and expensive, which delays how quickly corrections reach readers.
  • Kappa architecture and replayable logs address many of the same goals with a single processing path for greenfield designs.

Implementation notes

Immutable master dataset: Treat the raw log as append-only on object storage or HDFS; never update or delete source events in place. Apply corrections by re-running batch jobs over the unchanged history and by defining speed-layer state that the batch layer will supersede.

Merge contract: Document the timestamp or version cutoff between batch-backed and speed-backed views, and test queries that span the boundary so you neither double-count nor leave gaps.

Dual implementation discipline: Share schemas, test fixtures, and golden datasets across batch and stream code paths; run differential tests on sampled historical data before promoting logic changes.

Historical context: Nathan Marz’s original formulation predates mature stream SQL and log compaction. Modern lakehouse streaming merges blur the boundary between the layers, but they do not remove the operational cost of two code paths while batch recompute still runs.

Serving layer: batch views and speed views must define merge semantics at query time—readers should not average conflicting values. Dremel-style columnar serving (see Google’s Dremel paper) informed many OLAP shells; lambda’s serving layer still needs explicit “batch wins after T” rules documented for analysts.

Detection: divergence metrics between speed and batch paths should page before executives see two different revenue numbers—schedule nightly diff jobs with tolerated epsilon per metric type.

Common failure modes

  • Speed and batch divergence: Teams patch bugs in one layer but not the other, so merged query results disagree with batch-only audits.
  • Incorrect merge cutoffs: Off-by-one window boundaries between layers create missing hours or duplicated metrics in serving-layer queries.
  • Mutable raw storage: In-place edits to the master dataset break the guarantee that batch recomputation can reconstruct truth from history.
  • Unbounded batch runtime: Batch layers that scan entire history every run cannot keep pace with data growth, so corrections and freshness SLAs slip together.

Decision checklist

  • Do you truly need both low-latency recent views and full historical recomputation from raw data—not just one of those properties?
  • Is the team committed to maintaining, testing, and deploying two implementations of the same logic for the foreseeable roadmap?
  • Have you evaluated Kappa architecture with a replayable log (for example Apache Kafka) as a simpler alternative?
  • Is the master dataset append-only with retention and access controls that prevent silent mutation?
  • Are merge rules between batch and speed views specified, tested, and monitored in production queries?

Example use cases

  • Illustrative scenario — A social product counts likes and followers: nightly Spark batch jobs rebuild authoritative totals from an immutable event log, while a streaming job maintains counts for the last hour and the serving API merges both for “last seven days” queries.
  • Illustrative scenario — An e-commerce site trains a collaborative filtering model in batch over purchase history and blends in session-level clicks from a speed layer until the next nightly model refresh lands.
  • Case study — Twitter (now X) was an early adopter of large-scale batch analytics alongside Storm for real-time computation; Nathan Marz created Storm at Twitter while advocating Lambda-style separation of batch correctness and stream freshness.

Related patterns

  • Kappa Architecture — Simpler alternative: single streaming pipeline with replayable log eliminates the dual code path.
  • Spark Architecture — Spark is the primary engine for both the batch and speed layers in modern Lambda deployments.
  • Data Pipeline Patterns — Medallion architecture and incremental processing patterns that complement Lambda.
