Feature Stores

Central registry and serving layer for ML features: offline warehouse history, online low-latency lookups, point-in-time training joins, and lineage across Spark and stream pipelines.

⏱ 11 min read

What it is

A feature store is the data-platform layer between lakehouse or warehouse tables and ML workloads. It holds a feature registry (definitions, owners, schemas), materialisation pipelines that turn curated gold-layer facts into model-ready signals, an offline store with full history for training and backfills, and an online store with the latest values per entity for real-time scoring. Implementations such as Feast, Tecton, and Vertex AI Feature Store share that split; they differ in how much registry, streaming, and operations are managed for you.

Point-in-time correct reads are the contract that matters for analytics at scale: training datasets must join each label to feature values that existed before the event, not whatever was computed last night. The store encodes that join semantics so teams do not reimplement fragile timestamp logic in every Spark job.

Why it exists

In many organisations the warehouse already holds the truth for orders, sessions, and device events—but three ML-adjacent failures still appear without a feature store. Training-serving skew shows up when batch SQL or PySpark builds training columns while a separate service recomputes “the same” aggregates at inference with different null handling or time zones. Duplicated pipeline work spreads when fraud, recommendations, and growth each schedule their own 30-day velocity jobs from the same Kafka topic. Data leakage slips in when trainers join fact tables on user_id alone and accidentally pull feature rows timestamped after the label event—offline AUC looks strong until production catches up.

A feature store pushes feature engineering into governed, reusable batch and stream jobs, writes consistent snapshots to offline and online stores, and exposes one retrieval API for training exports and serving. That is the same problem space data engineering already solves with medallion layers; the store adds entity-centric versioning, freshness SLAs, and serving latency guarantees on top.

Stores sit at the intersection of batch and stream chapters in DDIA: training wants historical snapshots; serving wants low-latency lookups. Platforms that only solve one side recreate skew. Event-time windows and watermarks from stream processing docs apply directly when velocity features are computed live then backfilled for training parity.

When to use

  • Several models or squads consume the same engineered signals from the lakehouse or stream (churn, LTV, fraud velocity, personalisation).
  • Training runs need historical snapshots with point-in-time joins on entity and event time.
  • Online inference needs keyed lookups in tens of milliseconds—materialise to Redis, DynamoDB, Bigtable, or a managed online store.
  • Governance expects lineage from raw ingestion through gold tables to model features and prediction logs.
  • Platform teams want one Spark/Flink materialisation pattern instead of ad hoc notebook exports.

When not to use

  • A single experimental model with a dozen columns and one owner—warehouse SQL plus a scheduled export may suffice.
  • Pure batch scoring on a monthly cadence with no latency SLA and no shared features across teams.
  • No capacity to operate materialisation jobs, online store HA, and freshness alerting.
  • Features are only raw identifiers with no shared aggregations—serving might be a thin lookup API.

Introduce a store when the second team asks for the same velocity window or when training-serving skew appears in incident reviews—not when a lone notebook export still meets latency and audit needs.

Typical architecture

Sources land in bronze/silver; feature pipelines (Spark batch, Flink or Spark Structured Streaming) compute entity-time series; dual writes or sync jobs populate offline history and online latest-value stores; trainers and inference clients read through the store SDK.

Pros and cons

Pros

  • One definition powers batch retraining and online scoring—skew investigations compare versions instead of diffing unrelated code paths.
  • Shared features cut duplicate Spark spend and align metrics across BI and ML consumers of the same gold tables.
  • Built-in or library-assisted point-in-time joins reduce leakage when labels are time-stamped events.
  • Registry metadata ties features to owners, freshness SLAs, and downstream models for governance.

Cons

  • Two storage tiers plus sync jobs are real platform ownership—staleness in the online path directly hurts models.
  • Streaming materialisation for sub-minute freshness costs more than nightly warehouse SQL alone.
  • Adopting Feast, Tecton, or Vertex abstractions adds onboarding time before the first production feature ships.
  • Online store outages or hot-key overload break scoring paths—capacity planning and paging are mandatory.

Implementation notes

Version features explicitly: Bump names or semantic versions when aggregation windows or source tables change (purchase_count_30d_v2). Pin versions at train time; migrate serving deliberately with shadow comparisons.

Match freshness to the model: Batch features can follow the gold table schedule; fraud or personalisation signals may need stream materialisation into the online store with monotonic event timestamps so out-of-order writes do not regress values.

Observe like data pipelines: Emit row counts, null rates, and max feature age per materialisation run into the same stack used for data quality—block promotion when drift or staleness crosses thresholds.

Offline/online split: the offline store (warehouse files, parquet exports) favours wide scans for training; the online store (key-value, wide-column) favours entity lookups at single-digit millisecond budgets—capacity planning must treat them separately. Spark batch backfills replay history; Flink or Beam streaming jobs maintain sliding windows that must honour event-time watermarks per the Dataflow model.

Point-in-time correctness: training sets need as-of joins so future facts never leak labels; serving reads latest materialised state—both must trace to one registered definition. Lambda estates risk double maintenance unless stream and batch feature jobs share registry metadata and version pins.

Privacy: features derived from PII inherit classification—online stores replicated globally multiply erasure work; keep sensitive aggregates offline or tokenised at ingest.

Common failure modes

  • Stale online values: A failed dbt or Spark job leaves yesterday’s rollups in Redis—alert on per-feature freshness, not only job success.
  • Cold-start entities: New keys have no history—define defaults, document imputation, and monitor how often models rely on them.
  • Schema drift upstream: Renamed event fields without bumping feature version silently change distributions—validate contracts at silver ingress.
  • Training-serving skew: Different languages or libraries for offline vs online transforms—prefer one definition, or log served feature vectors for label joins.

Decision checklist

Stores compound quickly—confirm shared-feature ROI and ops capacity before greenfield build.

Pin feature versions in model registries when definitions change.

Shadow-compare online lookups after materialisation logic changes before cutover.

Capacity-plan Redis or DynamoDB online tiers separately from offline warehouse storage growth.

Define on-call for materialisation failures.

  • Which features are shared across models and must not be recomputed per team?
  • Is batch freshness enough, or do specific signals need stream materialisation?
  • Are training labels joined point-in-time on entity and event timestamps?
  • Does a platform squad own materialisation schedules, backfills, and on-call?
  • What are online lookup latency, availability, and cache targets for scoring?
  • Is feature versioning defined before the first production model pins definitions?
