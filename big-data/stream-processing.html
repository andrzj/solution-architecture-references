Stream Processing

Continuous transforms over durable event logs—event-time windows, state, and idempotent sinks for operational and analytical use cases.

⏱ 10 min read

What it is

Stream processing is continuous computation over an unbounded sequence of events: each record arrives in order (per partition), operators update derived state or emit results, and the job keeps running until you stop it. Engines such as Apache Flink, Kafka Streams, Spark Structured Streaming, or cloud-native stream services read from durable logs (typically Apache Kafka or similar), apply windows, joins, and aggregations, and write to serving stores or downstream topics.

Stream processing treats event time—when something happened—as distinct from processing time—when the system saw it. That distinction drives watermarks, lateness handling, and whether dashboards reflect business reality or only ingestion order.

Why it exists

Batch schedules hide reality for minutes or hours. Fraud scoring, inventory allocation, personalization, and incident response need answers while the event is still actionable. A durable log plus stateful stream jobs closes that gap: consumers process the live tail for low latency and can rewind offsets to rebuild state after code or schema changes.

Streaming also unifies operational and analytical paths when the same event log feeds both real-time views and later batch snapshots—reducing duplicate ingestion if you design retention and replay deliberately.

The Dataflow model gives teams shared vocabulary for event time, processing time, watermarks, and triggers—whether the runtime is Flink, Kafka Streams, Spark Structured Streaming, or Beam runners. Without that discipline, “real time” dashboards disagree because each job picks different lateness bounds or deduplication rules.

When to use

  • Dashboards, alerts, or automations require seconds-to-minutes freshness.
  • Change-data-capture must propagate to search indexes, caches, or read models with low lag.
  • Sessionization, funnel metrics, or per-user aggregates must reflect live traffic.
  • Online ML features are materialized from the event stream into a low-latency store.
  • You already operate a replayable log and can accept the operational cost of stateful jobs.

When not to use

  • Stakeholders accept hourly or daily freshness and batch cost is lower.
  • Event volume is so low that periodic polling or micro-batch cron jobs suffice.
  • The team lacks capacity to debug event-time skew, consumer lag, and state growth.
  • Workloads need multi-hour scans over full history that batch engines handle more simply.

Micro-batching in Spark or short trigger intervals can satisfy “minutes fresh” KPIs without full stream state—choose stream processing when event-time semantics, stateful joins, or continuous ingress make batch slices misleading, not when cron with better sensors would suffice.

Typical architecture

Producers append to a partitioned log. Stream processors maintain keyed state (often RocksDB-backed), emit aggregates or enriched events, and sink to databases or topics. Serving APIs or alert rules read the hot path while retention on the log supports replay and audit.

Pros and cons

Pros

  • Low end-to-end latency from event to action or dashboard.
  • Durable logs enable replay, auditing, and Kappa-style reprocessing without a separate batch truth path.
  • Horizontal scale via partitioned topics and parallel operator tasks.
  • Incremental updates avoid full-table scans for many operational read models.

Cons

  • Stateful topologies are harder to test, reason about, and upgrade than finite batch jobs.
  • Event-time correctness requires explicit watermarks and late-data policies.
  • Consumer lag, checkpoint failures, and state size drive on-call load.
  • Exactly-once end-to-end semantics are expensive; many teams settle on at-least-once plus idempotent sinks.

Implementation notes

Time semantics: Define windows and joins on event timestamps; use watermarks with a documented allowed lateness. Reserve processing-time windows for debugging only unless SLAs explicitly allow ingestion-time approximations.

Delivery guarantees: Prefer at-least-once ingestion with idempotent sink keys or upsert semantics before investing in exactly-once across heterogeneous systems.

State bounds: Set TTLs on keyed state, compact changelog topics where appropriate, and monitor RocksDB or managed state store disk usage.

Operations: Track consumer lag, checkpoint duration, backpressure, and failed records (dead-letter topics). Version job logic with blue/green or savepoint-based deploys when the engine supports them.

Time semantics: the Dataflow Model separates event time, processing time, and watermarks—stream jobs must document lateness allowed before dropping records. Flink checkpoints align barriers with state snapshots; Kafka Streams uses changelog topics—each engine’s failure recovery story belongs in runbooks, not only “at-least-once consumer.”

Delivery: Kafka’s design docs describe producer durability and consumer group rebalancing—rebalances during deploys cause duplicate processing unless idempotent sinks or transactional sinks are configured. DDIA stream processing material complements vendor docs on ordering: per-partition order does not globalize across topics.

Beam portability: Apache Beam runners (Flink, Spark, Dataflow) trade operational control for portability—document which runner owns production and which features (side inputs, state TTL) differ per runner.

Common failure modes

  • Aggressive watermarks: Late events are dropped, so aggregates diverge from batch reconciliation.
  • Unbounded state: High-cardinality group-by keys without TTL exhaust disk and stall checkpoints.
  • Non-idempotent sinks: Redelivered messages double-charge customers or inflate counts.
  • Schema drift without compatibility: Deserialization failures poison partitions or stall jobs silently.

Decision checklist

Confirm operational readiness for watermarks, checkpoints, and consumer lag before declaring stream paths production-grade.

Beam and Flink docs both stress testing with out-of-order fixtures—checklist items should pass against recorded production skew, not only happy-path samples.

Document maximum tolerable consumer lag beside freshness SLIs.

Saved checkpoints should be validated after deploys before traffic returns.

Alert on rising state store size per operator.

  • Are business windows and SLAs defined in event time, with explicit late-data handling?
  • Can you replay from the log (or a savepoint) to rebuild serving state within an acceptable window?
  • Do sinks remain correct under at-least-once redelivery?
  • Are state size, lag, and checkpoint health monitored with actionable alerts?
  • Is there a documented plan to reconcile stream metrics with batch or warehouse totals?

Example use cases

  • Illustrative scenario — A payments platform joins card authorizations with device telemetry in a five-minute event-time window to raise fraud scores before settlement completes.
  • Case study — LinkedIn built Kafka and stream-oriented infrastructure to propagate profile and activity updates to many derived systems with low lag—patterns that influenced broader stream-processing adoption.
