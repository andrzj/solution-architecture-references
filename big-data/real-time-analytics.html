Big Data & Analytics

Real-Time Analytics

Sub-second OLAP at scale: Apache Pinot, Apache Druid (rollup on ingestion, segment structure), ClickHouse (MergeTree engine, columnar storage), pre-aggregation patterns, user-facing analytics, fraud monitoring, and operational alerting.

⏱ 11 min read

What it is

Real-time analytics (often implemented as real-time OLAP) is the practice of serving interactive aggregates and filters over fresh event data with sub-second query latency at high concurrency. Unlike warehouse BI that scans large tables on demand, real-time OLAP engines pre-structure data at ingest—columnar segments, rollups, star-trees, or materialized views—so dashboards and product APIs read pre-computed grains instead of raw events.

Apache Druid, Apache Pinot, and ClickHouse are common open-source engines in this space; each combines append-heavy ingestion from streams or object storage with vectorized execution and indexing tuned for time-range scans and grouped metrics.

Why it exists

Product teams embed analytics in customer-facing surfaces—ad performance, usage meters, live leaderboards—where latency is part of the user experience, not a back-office report. Operations teams need the same freshness for incident response: error bursts, payment velocity, or fraud signals must appear in rolling windows before a nightly warehouse refresh.

General-purpose warehouses excel at flexible SQL and batch freshness but struggle to sustain hundreds of concurrent, millisecond-budget queries over billions of rows without dedicated pre-aggregation and serving tiers built for that access pattern.

OLAP engines trade schema rigidity for ingest and query latency: dimensions are declared up front, segments are pre-aggregated, and late events trigger reindex or compaction policies that differ by product. Pairing them with Kafka or Flink ingestion without lag SLOs produces dashboards that look live while consumer groups are hours behind.

When to use

  • Dashboards or APIs must return aggregate answers in under a second over data ingested minutes ago.
  • Analytics ship inside a product where slow queries directly degrade customer trust or revenue.
  • You must group by moderately high-cardinality dimensions (campaign, device class, region) at event volumes warehouses would scan repeatedly.
  • Operational alerting depends on rolling metrics computed from a live stream rather than scheduled extracts.

When not to use

  • Stakeholders accept hourly or daily freshness and run exploratory SQL against a warehouse or lakehouse.
  • Event volume is low enough that warehouse materialized views or indexed marts meet latency and cost goals.
  • You need rich joins, multi-row transactions, or frequent row-level updates—OLAP engines are poor primary transactional stores.

Hybrid designs are common: warehouse holds detail history while OLAP serves rollups for live UI. Document which metrics are speed-layer approximations and how batch correction backfills segments—users should not see silent metric jumps without release notes.

Typical architecture

Events arrive on a stream or batch path into an OLAP cluster that segments and optionally rolls up data; a query tier exposes SQL or REST to product dashboards and monitoring tools.

Pros and cons

Pros

  • Pre-aggregation at ingest makes sub-second responses feasible over very large event histories.
  • Columnar encoding typically yields strong compression on telemetry and categorical dimensions.
  • Native stream ingestion paths keep dashboard freshness within minutes of production events.
  • Materialized views and rollup configs can shift work from query time to ingest time when patterns are known upfront.

Cons

  • Engines optimize for append and aggregate patterns, not arbitrary joins or OLTP-style updates.
  • Distributed OLAP clusters include multiple specialized roles that increase onboarding and on-call surface area.
  • Adding dimensions or finer time grains after launch usually requires backfill and schema planning.

Implementation notes

Rollup granularity: Pick the coarsest time bucket and dimension set that still answers required queries; finer grains explode storage and rebuild cost. Keep raw events in cheap object storage when occasional drill-down to individual records is required.

Write pattern: All three engines expect batched inserts or stream micro-batches; single-row synchronous writes degrade throughput and merge performance.

High-cardinality dimensions: Bitmap-style indexing works up to moderate cardinality; user- or device-level keys at millions of values may need dedicated lookup tables, sampling, or restricted query patterns.

Ingestion: Druid, Pinot, and ClickHouse each trade late-ingestion handling, compaction, and segment sizing differently—load tests should include out-of-order events at expected volume. The Dataflow paper’s windowing concepts map to rollup granularity: coarser segments reduce query cost but raise minimum queryable interval.

Lambda overlap: real-time OLAP cubes often pair with batch correction jobs—document whether queries read merged results or speed-only until batch catches up. Kafka as ingest bus needs consumer lag SLOs before the OLAP engine claims “real time.”

Cost: hot tier retention dominates bills—tiering old segments to object storage only helps when query patterns rarely scan ancient history.

Common failure modes

  • OLAP as system of record: Treating the engine like a transactional database leads to write amplification and inconsistent reads.
  • Untested materialized views: Logic errors in ingest-time aggregation surface as silently wrong KPIs until someone reconciles against raw data.
  • Schema drift without backfill: New dimensions added only to fresh segments make historical dashboards incomparable.

Decision checklist

OLAP clusters fail loudly on ingest backpressure before query latency degrades—verify ingest, segment, and query SLOs independently.

Load tests should mix historical backfill with live tail traffic; Dremel-class ad hoc patterns rarely match embedded dashboard query shapes.

Publish maximum safe query concurrency per datasource to product teams.

Monitor segment compaction lag as an ingest health signal distinct from query p95.

  • Are writes batched or stream-buffered to match the engine’s ingest expectations?
  • Does rollup or star-tree coverage match the dimension and time grains product queries need?
  • Is an archival path available when analysts need row-level history outside the serving store?
  • Have materialized or rolled-up outputs been reconciled against a sample of raw events?
  • Is cluster sizing validated for peak concurrent queries, not just ingest rate?

Example use cases

  • Case study — LinkedIn created Apache Pinot to power interactive analytics over high-volume engagement and advertising metrics with sub-second query latency at large concurrency.
  • Illustrative scenario — A payments team ingests authorization events into ClickHouse, materializes per-card velocity aggregates, and wires Grafana alerts when hourly transaction counts exceed a policy threshold.
