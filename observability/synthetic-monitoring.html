Synthetic Monitoring

Black-box synthetic monitoring in the Google SRE style: probers and canaries outside your network, scripted user journeys, multi-region availability, SLI coverage when real traffic is sparse, plus RUM for the full picture.

⏱ 9 min read

What it is

Synthetic monitoring is black-box probing: automated clients outside your stack execute representative requests on a schedule and report success, latency, and content checks. Google’s monitoring guidance treats these probers as part of measuring distributed systems — they observe what users would see at the edge without requiring live traffic.

Common probe types: HTTP/HTTPS API checks (status, latency, JSON assertions) for SLI floors and dependency SLAs; browser journeys (Playwright, Selenium) that render pages, run JavaScript, and validate multi-step flows; multi-step API workflows that authenticate, mutate state, and verify outcomes; network reachability (TCP/TLS/DNS) for non-HTTP dependencies. Probes run from multiple geographic and network vantage points so regional CDN, DNS, or routing failures surface even when one region looks healthy.

Synthetic results complement real user monitoring (RUM) and server-side metrics: synthetics give continuous, comparable baselines; RUM captures device diversity, cache state, and behaviour you cannot script. For SLOs, many teams include synthetic success in SLI numerators during low-traffic windows so error budgets still move when nobody is awake to hit the API.

Why it exists

Server metrics can be green while the edge returns errors — misconfigured load balancers, expired certificates, WAF blocks, or CDN faults often appear only on paths real users take. SRE monitoring emphasises measuring at user boundaries; synthetics are controlled transactions that cross those boundaries continuously. They shorten mean time to detect for deploy regressions (run after every release), cover overnight and holiday traffic lulls, and supply neutral evidence when disputing vendor uptime claims.

Real user monitoring only measures what actually arrived at the edge with telemetry enabled. Synthetics still run when traffic is quiet—catching a broken canary before peak hour—or when a partner API misbehaves but your pods report healthy. That proactive gap is why many teams treat synthetic availability as the floor of an SLI, with RUM layered on top when volume returns.

When to use

  • Critical journeys with low or bursty traffic — overnight APIs, admin consoles, launch spikes.
  • Post-deploy verification — smoke probes in CI/CD or progressive delivery before full traffic shift.
  • Multi-region products — at least one probe per region with meaningful users.
  • Third-party dependencies — objective external measurement for contract SLAs.
  • SLO dashboards — synthetic availability as a parallel SLI input when RUM is sparse.

When not to use

  • As the only SLI on high-traffic services — RUM and server metrics must dominate where volume exists.
  • Scripting every page — maintenance cost explodes; cover few golden journeys.
  • Production write paths without test accounts or sandboxes — probes must not corrupt customer data.
  • Single-location probes for global products — one healthy POP hides regional outage.

Typical architecture

Probers run outside your VPC on a schedule, execute golden journeys, emit success/latency metrics (often via OpenTelemetry export or vendor APIs), and fan into Prometheus-compatible storage. Alert rules treat multi-location failures as user-visible incidents; single-point blips stay warnings.

Pros and cons

Pros

  • Continuous SLI signal when organic traffic is thin—overnight, new regions, pre-launch.
  • Validates edge paths (DNS, TLS, CDN, WAF) server metrics never traverse.
  • Deterministic post-deploy smoke—fail fast in CI/CD or canary before burn-rate alerts would have enough real user events to fire.
  • Neutral third-party vantage for dependency SLA disputes.

Cons

  • Browser journeys are expensive and brittle without stable selectors and owned test code.
  • Idealised clients miss real-world variance—extensions, caches, mobile radios—that RUM must cover.
  • False positives from probe-network issues if alerting does not require multi-location quorum.
  • Writes and auth flows need sandbox accounts; sloppy scripts corrupt production data.

Implementation notes

Align synthetics with SLI definitions: each probe should map to a journey-level good/event ratio, not a bespoke check metric. Emit OTLP metrics with service.name and probe region labels that match Prometheus recording rules used in SLO dashboards.

Cover three to five golden journeys—login, core API health, highest-revenue transaction path. Prefer HTTP/TLS probes for SLI floors; reserve Playwright-style scripts for journeys where JavaScript or third-party widgets matter. Instrument per-step duration so degradation shows up before hard timeouts.

Run from every region with meaningful users. Alert with quorum: two consecutive failures or failures in two or more locations before P1; single-location blips become tickets. Export synthetic_check_success and latency histograms into the same TSDB as server metrics; combine with RUM SLIs using max() or weighted rules documented in your SLO spec.

Gate releases: run the same probe suite after deploy hooks. On failure, roll back before server-side error rates move. Store credentials in secrets managers; rotate test identities; teardown mutating steps in finally blocks.

Record probe version labels beside application deploy versions so failures correlate with the build they exercised.

Synthetic alerts fail when scripts are flaky. Captchas, CDN A/B tests, shared credentials hitting rate limits, and DOM timing races produce false positives that erode on-call trust. Prefer paging only after consecutive failures or agreement across two probe regions, and track a synthetic flake rate metric. When more than one percent of checks fail then succeed on retry without a deploy, fix the test before tightening thresholds. Alert text should distinguish assertion failures (application likely broken) from timeouts (network or script issue).

Run golden journeys from every region where you promise latency. Correlate probe metrics with the same recording rules as customer-facing SLIs, using a probe_region label. A single US-only probe green while EU users fail is a blind spot, not an SLO.

Common failure modes

  • Parallel SLI math — synthetic metrics never merged into official recording rules, so SLO dashboards disagree with pages.
  • Probe as only signal — on high-traffic services, RUM and server histograms must dominate; synthetics are guardrails, not the full story.
  • Shared IP rate limits — probers hit WAF or bot rules, creating fake outages; allowlist probe egress or use vendor-published IP lists.
  • Stale scripts after UI deploy — tests pass on cached CDN while users see broken selectors; tie test updates to frontend release checklist.
  • Runaway test data — journeys that create orders or users in production without teardown pollute analytics and exhaust idempotency keys; use dedicated tenants or cleanup hooks.

Decision checklist

  • Each synthetic check maps to a documented SLI journey and feeds the same Prometheus rules as paging?
  • Golden journeys covered with multi-region probes matching user geography?
  • Paging requires multi-location or consecutive failures, not a single blip?
  • Browser tests use stable data-test hooks and ship with the UI that changes them?
  • Mutating flows use isolated test tenants and cleanup?
  • RUM and synthetic SLIs combined with explicit weighting in the SLO spec?

Example use cases

  • Illustrative scenario — Post-deploy synthetics fail on checkout within three minutes; progressive delivery halts the traffic shift and rolls back automatically before organic error rates move the SLO burn chart.
  • Illustrative scenario — Tokyo and Singapore probes return HTTP 504 while US East stays green; on-call opens a regional CDN ticket with probe screenshots instead of guessing from a single-region dashboard.
  • Illustrative scenario — A five-minute API probe against a payment sandbox feeds a monthly availability workbook used with the vendor in quarterly SLA reviews—objective breach dates, not anecdotal support threads.
  • Case study — Google’s SRE monitoring material describes black-box probers as part of practical measurement alongside white-box service metrics.
