Distributed Tracing

End-to-end request tracing across services: spans, W3C Trace Context propagation via traceparent and tracestate, sampling strategies, and trace backends for latency debugging.

⏱ 12 min read

What it is

Distributed tracing records the end-to-end path of a single logical operation as it crosses process and network boundaries. A trace is the full story; each span is one unit of work inside that story — an HTTP handler, a database query, a message publish — with start time, duration, attributes, events, and status.

Spans form a tree (or directed acyclic graph when fan-out and links are modeled). Visualised as a waterfall or flame-style timeline, a trace answers where time went for one request, not just average latency across all requests.

Context propagation stitches spans together. When an upstream service calls downstream, it must pass the active trace identifiers and sampling decision. The W3C Trace Context recommendation standardises this for HTTP and other carriers via two fields:

  • traceparent — a dash-separated value {version}-{trace-id}-{parent-id}-{trace-flags}. Example: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01. The 32-hex trace-id identifies the whole trace; the 16-hex parent-id is the caller’s span id for the child to reference; flag 01 means sampled.
  • tracestate — optional vendor-specific key/value pairs that must not break interoperability; systems should ignore unknown entries.

OpenTelemetry and modern SDKs use W3C Trace Context by default. Legacy formats (Zipkin B3, AWS X-Ray) still appear in brownfield systems; collectors can translate headers, but greenfield services should emit and accept W3C headers on every synchronous and asynchronous hop.

Sampling decides which traces are retained. Head-based sampling decides at trace start (low overhead, uniform sampling). Tail-based sampling waits until the trace completes, then keeps errors, slow traces, and a probabilistic slice of normal traffic — higher value, more collector state.

Why it exists

Google’s Dapper paper (2010) framed the problem: one user action may touch dozens of services, and neither aggregated metrics nor uncorrelated logs explain why this request was slow. Microservices multiplied the pain — each team owned logs in isolation. Tracing provides a shared identifier (the W3C trace-id) and a hierarchical timeline so operators can localise delay or errors without manually joining log lines across hosts.

When to use

  • Any multi-service request path where cross-boundary latency dominates incident time-to-diagnosis.
  • Latency SLO work — traces expose which span blew the budget, not just that p99 rose.
  • Production incidents where metrics show symptoms but logs lack a common correlation key.
  • Dependency discovery — runtime parent/child span graphs reveal the real call graph.

When not to use

  • Single-process monoliths with no outbound calls — structured logs and profiling often suffice at lower operational cost.
  • 100% trace retention at extreme QPS without tail sampling — storage and ingest cost will dominate before insight does.
  • As a substitute for business audit logs — traces are operational telemetry, not legal records.

Typical architecture

Instrumented services create spans, inject traceparent on outbound calls, export OTLP to a collector, apply sampling and PII scrubbing, then store spans in a trace backend queried from Grafana or an APM UI.

Pros and cons

Pros

  • Per-request latency decomposition across services — the fastest route from “slow checkout” to “payment API span”.
  • Rich span attributes connect technical and business context when instrumentation is deliberate.
  • Service graphs derived from traces stay closer to production reality than static diagrams.
  • W3C Trace Context enables interoperability across languages and vendors.

Cons

  • One missing propagation hop breaks the trace chain — partial traces mislead if not understood.
  • Async and batch systems need explicit context in message metadata, not only HTTP headers.
  • Tail sampling adds collector complexity, buffering delay, and state sizing challenges.
  • Clock skew across hosts can distort waterfall ordering without disciplined time sync.

Implementation notes

Start with OpenTelemetry auto-instrumentation for HTTP, gRPC, and database clients, then add manual spans where business semantics matter. Configure the W3C Trace Context propagator as default; use collector processors to copy B3 or X-Ray headers only during migration windows.

For message brokers, inject context into message attributes or headers at publish time and extract at consume time. OpenTelemetry models many async paths with span links so consumers are related to producers without faking synchronous parent-child timing.

Align logs and metrics: structured logs should include trace_id (and often span_id) matching W3C values so Grafana or similar tools can pivot trace → logs → exemplars. Scrub SQL text and headers at the collector if auto-instrumentation captures sensitive parameters.

Common failure modes

  • Broken propagation at gateways — API gateways that strip or regenerate trace headers create orphan spans or duplicate traces.
  • Head sampling of errors — a 1% head sample also discards 99% of failures; combine tail policies that always retain error traces.
  • Mixing trace header formats — downstream reads B3 while upstream sends W3C only; standardise or translate centrally.
  • Sensitive data in attributes — full SQL, tokens, or PII in span fields; redact in SDK or collector.
  • Ignoring tracestate size limits — oversized vendor state can hit proxy header limits; keep tracestate minimal.

Decision checklist

  • Is W3C Trace Context (traceparent / tracestate) used on all synchronous egress paths?
  • Are async producers and consumers instrumented for context propagation?
  • Does tail sampling retain errors and SLO-violating latency traces?
  • Do logs and metric exemplars share the same W3C trace IDs?
  • Is trace retention sufficient for post-incident review?
  • Are gateways and meshes configured to forward, not replace, trace headers?

Example use cases

  • Illustrative scenario — N+1 after deploy: p99 latency doubles; filtered traces show every slow request spending most duration in a new repeated database span introduced in the latest release.
  • Case study — Google Dapper: Large-scale tracing at Google established the span model and sampling techniques later adopted industry-wide.
  • Illustrative scenario — trace-based tests: CI asserts that checkout produces spans with expected names and attributes, catching regressions in propagation or instrumentation.
