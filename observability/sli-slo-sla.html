Observability & Operations

SLI / SLO / SLA

Google SRE vocabulary for reliability contracts: indicators measured from user journeys, internal objectives that set error budgets, and external agreements—backed by Prometheus recording rules and OpenTelemetry semantics.

⏱ 12 min read

What it is

A service level indicator (SLI) is a quantitative measure of some aspect of service behaviour that matters to users—success ratio over a request class, latency below a threshold, freshness of data, or correctness of an outcome. Google’s SRE materials insist SLIs be user-observable: if customers cannot perceive the signal, it is operations telemetry, not an SLI.

A service level objective (SLO) is an internal target for an SLI over an agreed evaluation window (rolling 30 days is common). The complement of the target defines the error budget—see SLOs and Error Budgets. SLOs are negotiation tools between product and engineering, not marketing copy.

A service level agreement (SLA) is an external or business-facing commitment—often with financial remedies—built on the same SLI definitions but with deliberate margin below measured SLO performance so contractual breaches are rare. Engineering owns measurement; legal and sales own language and credits.

In practice the chain is: define the user journey → pick one or two SLIs per journey → implement measurement (often Prometheus recording rules or OTel-derived metrics in a time-series backend) → set SLO targets and alerting → optionally wrap a looser SLA around proven SLO attainment.

Why it exists

Teams without shared SLI definitions argue from incompatible graphs—load balancer 200 rates, pod readiness, and synthetic pings each tell a different story. SRE vocabulary forces alignment on what “good” means for users before debating how fast to ship or what to promise customers.

SLOs convert reliability into a budgeted quantity instead of a morale contest. SLAs translate that discipline outward only when measurement is trustworthy and historical attainment supports the committed number—typically SLO at 99.9% with SLA at 99.5% and documented exclusion windows, not the reverse.

When to use

  • Customer-facing APIs, web apps, or data products with measurable journeys (login, search, checkout, file sync).
  • Shared platform services where many teams depend on a single control plane (identity, CI, observability backend).
  • Enterprise sales or regulated sectors requiring documented uptime or latency commitments.
  • Any team adopting error budgets, burn-rate paging, or progressive delivery gates tied to reliability.

When not to use

  • Low-traffic or purely internal batch jobs with no user-visible SLO story—start with basic monitoring instead.
  • Dozens of SLOs per microservice—dilutes attention; prefer a handful of journey-level objectives.
  • Contractual SLAs before six months of credible SLI measurement—promises without data create liability.
  • SLAs stricter than internal SLOs without engineering sign-off and margin—breaches become inevitable.

Typical architecture

Architecture flows from journey to contract: instrument user-observable events with consistent labels (OpenTelemetry semantic conventions), roll up good and valid event counts in Prometheus or equivalent, compare rolling ratios to SLO targets on dashboards, and expose only the SLA layer to customers once internal attainment is stable.

Pros and cons

Pros

  • Shared vocabulary ends “is it up?” debates—everyone cites the same SLI queries.
  • SLO targets directly feed error budgets, release policy, and burn-rate alerts.
  • Well-chosen SLIs focus instrumentation on user pain, not vanity uptime.
  • SLAs with margin protect revenue while SLOs preserve engineering realism.

Cons

  • Wrong SLIs (node CPU, probe-only pings) optimise the wrong reliability story.
  • SLA language drafted without measurement definitions is legally risky.
  • Metric sprawl—every team inventing SLIs without platform conventions—breaks comparability.
  • Gaming numerators (excluding errors, narrowing “valid” events) erodes trust in budgets.

Implementation notes

Start from journeys, not endpoints. For each journey, choose availability (good/total), latency (events under threshold / total), or throughput SLIs. Document what counts as valid—client errors you accept, maintenance windows, dependency failures you exclude.

Instrument with OpenTelemetry (HTTP/gRPC semconv: http.response.status_code, rpc.grpc.status_code, duration histograms) and export to Prometheus-compatible backends. Encode SLIs as recording rules, for example sum(rate(http_requests_total{status=~"2..",le="0.5"}[5m])) / sum(rate(http_requests_total[5m])) for a latency-and-success composite. Keep label sets consistent (service.name, region, route) so SLO dashboards match alert queries.

Pick evaluation windows and targets deliberately—rolling 30 days for customer-facing APIs, shorter windows for batch freshness. Set SLO slightly above historical p95 attainment, then tune. Pair each SLO with multi-window burn alerts (Google workbook recipes). Publish internal dashboards; expose SLA status pages only from the same measurement pipeline.

When contracting: SLA target < SLO target, define measurement method and exclusion clauses, and retain raw SLI data for disputes. Review SLOs quarterly with product—tighten when UX demands it, loosen when budget is permanently exhausted.

Request-based vs window-based SLIs: Request-based SLIs count good events over valid events in a rolling window (30d availability = successful requests / total requests)—natural for HTTP. Window-based SLIs ask “was the system good for this interval?”—useful for batch freshness or uptime of a pipeline slot. Do not mix forms in one SLO without documenting the numerator.

User journeys: Define SLIs on product paths (search → add to cart → pay), not only /healthz. Synthetic probes plus server-side metrics on the same route template prevent green dashboards while checkout fails.

Encode multi-window burn alerts beside each SLO: fast burn (14.4× budget consumption over 1h with 5m windows) pages urgently; slow burn (6× over 6h/30m) escalates before the month ends—see Alerting Strategies.

Common failure modes

  • Availability-only SLIs — 100% success at 30s latency still fails users; pair success with latency threshold or percentile SLI.
  • White-box SLIs — kube pod ready or DB connection count is not user-observable; add black-box or edge-measured signals.
  • SLA without SLI specification — “99.9% uptime” with undefined requests, regions, or maintenance leaves every breach arguable.
  • Mismatched windows — SLO on 30d roll-up but paging on 5m spikes without burn logic causes alert fatigue or silent budget drain.
  • OTel/Prometheus label chaos — renaming service breaks year-over-year SLI history; govern semantic conventions.

Decision checklist

  • Each SLI maps to a named user journey and is measurable at the edge or client?
  • Good, valid, and bad event definitions are written and implemented in recording rules?
  • SLO window, target, and error budget policy are published to engineering and product?
  • Burn-rate alerts use the same queries as the SLO dashboard?
  • SLA target is below demonstrated SLO with agreed exclusion and measurement clauses?
  • OTel instrumentation and metric names are consistent across services in the journey?

Example use cases

  • Illustrative scenario — A payment API defines SLI as fraction of POST /charges returning 2xx within 800ms; SLO 99.95% over 30d; SLA 99.9% with credits. Prometheus rules and OTel histograms share the same route labels.
  • Illustrative scenario — A search product adds freshness SLI (results newer than 15 minutes) alongside availability because stale index data is user-visible failure even at HTTP 200.
  • Case study — Google’s SRE book and workbook popularised separating SLIs (measurable), SLOs (targets), and SLAs (contracts)—the model most vendor SLO products (Sloth, OpenSLO) encode today.
