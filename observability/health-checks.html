Health Checks and Probes

Health checks and Kubernetes probes — liveness vs readiness vs startup, shallow and deep endpoints, probe tuning, and safe dependency checks.

⏱ 10 min read

What it is

Health checks are the contract between an application and its platform: small, fast endpoints or commands that report whether a process should keep running, receive traffic, or is still starting up. Orchestrators and load balancers use these signals to restart crashed instances, remove unhealthy endpoints, and gate rolling deploys.

Kubernetes defines three probe types. Liveness asks whether the container is alive — repeated failure triggers restart. Readiness asks whether the instance should receive traffic — failure removes it from service endpoints without restart. Startup disables other probes during slow boot (JVM warmup, schema migration, model load) so liveness does not kill pods that are still initialising.

Shallow checks validate only in-process health (event loop responsive, deadlock detectors, internal watchdog). They suit liveness. Deep checks verify dependencies such as primary database TCP, cache ping, or broker connectivity. They suit readiness — not liveness — because an external outage should drain traffic, not restart every pod simultaneously.

Responses often follow patterns like Spring Boot Actuator or plain /live, /ready, and /health JSON with per-component status. HTTP 200 means healthy; 503 means unhealthy for load balancers. Optional components may report DEGRADED while the pod stays ready if product policy allows partial service.

Why it exists

Without health signals, platforms cannot distinguish a deadlocked JVM from a busy one, a pod still starting from one ready to serve, or a single bad instance from a fleet-wide dependency failure. Automated rollback, autoscaling, and service meshes depend on accurate readiness. Health endpoints are the minimum observability surface for control plane decisions — distinct from metrics and traces used for human diagnosis.

Probe success is not user happiness: a pod can be ready while still returning slow errors. Still, orchestrators must not send traffic to instances that cannot complete work. Pair health endpoints with SLI metrics and synthetic journeys so readiness flapping becomes an alert-worthy trend, not only kubelet noise.

When to use

  • Every containerised service behind Kubernetes, Nomad, ECS, or similar orchestration.
  • Load-balanced HTTP or gRPC services where backends must be removed from rotation cleanly.
  • Slow-starting runtimes — always pair startup probes with realistic failureThreshold budgets.
  • Progressive delivery — new pods must pass readiness before older replicas drain.
  • Stateful workloads with ordered startup — readiness gates membership in cluster quorum or replication set.

When not to use

  • Expensive dependency checks on liveness — never restart pods because a shared database blipped.
  • Health endpoints that perform unbounded work (full table scans, test transactions on production data).
  • Sole reliance on health checks instead of fixing chronic dependency flapping — constant readiness flicker is a design smell.

Typical architecture

The kubelet probes pod HTTP paths on a schedule. Readiness failure updates EndpointSlice objects; liveness failure restarts the container. Service meshes may duplicate health concepts — keep application probes the source of truth.

External load balancers often poll the same paths with separate intervals and bodies. Align timeout budgets so an LB does not mark a backend down while Kubernetes still considers it ready, or vice versa. Document which component is authoritative for customer traffic during incidents.

Pros and cons

Pros

  • Automated traffic shedding and restart without human paging for obvious failures.
  • Clear separation between crash recovery (liveness) and dependency degradation (readiness).
  • Startup probes remove fragile mega initialDelaySeconds values across environments.
  • Rolling deploy safety — bad versions fail readiness before taking full traffic share.
  • Structured JSON health bodies document component state for support without shell access.

Cons

  • Overly strict readiness checks cause thundering herds when shared dependencies hiccup.
  • Health code paths must stay maintained — a broken health handler is worse than none.
  • Detailed JSON responses can leak topology if exposed outside the cluster.
  • Dual health systems (app + mesh + LB) without alignment create contradictory signals.

Implementation notes

Implement liveness in microseconds to low milliseconds — no network I/O. Readiness may call dependencies in parallel with short per-check timeouts (100–500ms total budget). Classify dependencies as required vs optional; only required failures should flip readiness to down.

Debounce with failureThreshold and successThreshold. Use higher failure thresholds for liveness than readiness because restarts are more disruptive. For gRPC, use the gRPC health checking protocol where supported instead of bolting HTTP-only paths onto gRPC-only servers.

Expose health on a dedicated admin port if main traffic paths carry auth middleware that would block kubelet probes. Include build version in readiness metadata for deploy verification, not in public responses.

Emit probe events or metrics when readiness toggles—counters for `DOWN` transitions help SRE spot chronic dependency flapping. Cache dependency probe results for a few seconds inside readiness handlers to absorb single-packet blips without lying about sustained outage. For worker queues, replace HTTP readiness with leader-election or backlog depth signals agreed with platform owners.

Review probe configuration whenever thread pools, connection limits, or GC tuning change; a faster service under load may need shorter readiness timeouts but longer startup thresholds.

Common failure modes

  • Database check on liveness — shared DB outage restarts the entire fleet, amplifying the incident.
  • No startup probe for JVM/ML services — liveness kills pods mid-warmup; operators inflate delays blindly.
  • Probe timeouts longer than period — overlapping probes stack load and skew failure detection.
  • Health endpoint on authenticated route — kubelet receives 401 forever; pod never becomes ready.
  • Optional dependency fails readiness — analytics client blip removes pods serving core API traffic.
  • Mesh and kubelet disagree — sidecar ready while app readiness fails, sending traffic to broken combinations.

Decision checklist

  • Is liveness shallow with no external network calls?
  • Does readiness check only required dependencies in parallel with tight timeouts?
  • Are startup probes configured when cold start exceeds ~10 seconds?
  • Are failure thresholds tuned to ignore single flake failures?
  • Are health endpoints reachable only inside the cluster or mesh?
  • Do rollouts pause when new pods fail readiness?
  • Are readiness flapping rates exported for SLO-adjacent alerting?

Example use cases

  • Illustrative scenario — pool exhaustion: Readiness fails when DB pool is saturated; load balancer shifts traffic to healthier replicas; no restart storm.
  • Illustrative scenario — JVM warmup: Startup probe grants five minutes before liveness applies; pods finish class loading without restart loops.
  • Illustrative scenario — LB mismatch: External LB health uses deep checks while liveness stays shallow; operators retune paths so traffic drains when DB pool is saturated instead of restarting pods.
  • Case study — Kubernetes probes: Built-in liveness/readiness semantics became the de facto pattern for cloud-native health across ecosystems.
