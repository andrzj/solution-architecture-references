Observability & Operations

Log Aggregation

Log aggregation centralizes structured logs from ephemeral workloads into queryable stores such as Grafana Loki, correlates them with OpenTelemetry traces, and balances retention cost with SRE incident needs.

⏱ 10 min read

What it is

Log aggregation is the practice of collecting log events from many producers—containers, VMs, functions, and edge devices—into a centralized system where engineers can search, alert, and retain them under policy. Aggregation sits downstream of structured logging: applications emit JSON lines (often to stdout), and agents or the OpenTelemetry Collector ship those streams to durable stores. Without aggregation, every incident becomes a treasure hunt across replaced pods and rotated files.

Common ingestion paths include Promtail or Fluent Bit tailing Kubernetes container logs into Grafana Loki, Vector transforming and fanning out to multiple sinks, or OTLP log export through an OpenTelemetry Collector to Loki, Elasticsearch, or commercial platforms. Loki indexes labels (namespace, app, environment) and stores compressed chunks in object storage—cost-effective at high volume when labels stay low-cardinality, as Charity Majors and Honeycomb frequently remind teams about cardinality discipline, even though Honeycomb itself is event-native rather than Loki-shaped. Elasticsearch remains the choice when rich full-text investigation dominates; either way, log-trace correlation requires trace_id in the JSON body so Grafana can join Loki queries with Tempo traces and Prometheus incident timelines.

Why it exists

Distributed systems destroy the assumption that logs live on the failing machine long enough to read them. Central aggregation decouples log durability from instance lifetime and gives security, compliance, and SRE teams one interface for investigation. The Google SRE book treats logs as part of monitoring distributed systems—not instead of metrics, but as the narrative layer when charts show an anomaly you did not forecast. Aggregation also enables derived signals: LogQL metric queries can spot error spikes that were never instrumented as Prometheus counters, though metrics remain the primary home for SLO burn alerts.

When to use

  • Every production fleet with ephemeral compute, autoscaling, or more than one availability zone—local files are not a strategy.
  • Teams running Grafana with Prometheus who want Explore workflows that pivot from metrics to Loki lines sharing trace identifiers.
  • Regulated environments requiring centralized retention, access auditing, and immutable cold tiers.
  • Security operations that feed centralized logs into SIEM rules alongside metrics and traces.

When not to use

  • Skipping aggregation is not viable in production; what you avoid is duplicating full-fidelity DEBUG everywhere—sample verbose levels and rely on traces for per-request timing detail.
  • Do not place unbounded identifiers (request ID, user ID, trace ID) into Loki label sets; keep them in log lines to prevent the same cardinality pain Prometheus warns about.

Typical architecture

Agents on each node ship workload stdout to a centralized log store; Grafana provides query and correlation with metrics and traces.

Pros and cons

Pros

  • One query interface spans the fleet—LogQL or KQL filters on structured fields instead of SSH and grep across missing pods.
  • Grafana Loki’s label-indexed design keeps storage costs manageable when teams respect cardinality guidance similar to Prometheus label hygiene.
  • OpenTelemetry log pipelines let you enrich, sample, and route once in the Collector while applications stay vendor-neutral.
  • Trace identifiers in JSON bodies enable Grafana pivots from Tempo spans to the exact Loki stream for that request.

Cons

  • Loki line filters scan chunk content—broad queries over huge streams are slower than Elasticsearch full-text indexes tuned for ad-hoc search.
  • Ingestion volume dominates spend; uncontrolled DEBUG in hot paths can exceed application compute costs.
  • Elasticsearch or Splunk at scale demand dedicated platform skills—sharding, ILM, and licensing are ongoing work.
  • Shipper misconfiguration can drop logs silently unless you monitor agent lag with Prometheus metrics.

Implementation notes

Mandate JSON to stdout and ship with Promtail DaemonSets, Fluent Bit, or OTLP through the OpenTelemetry Collector. Label streams with coarse dimensions only—namespace, app, env, level—and parse JSON inside LogQL for trace_id, error_code, and business IDs. Define retention tiers explicitly: hot Loki for incident windows, object storage for months, glacier for compliance archives.

Wire Grafana datasources so Explore runs Loki beside Prometheus and Tempo. Export ingestion rate, dropped records, and shipper memory to Prometheus and page before buffers OOM. Scrub PII in the Collector when applications cannot guarantee omission. Align on-call runbooks with the SRE practice of starting from symptomatic metrics, then narrowing with logs—not the reverse during every page.

Choose backends based on how you query. Grafana Loki treats each unique combination of stream labels as an index entry and stores the raw line compressed; it excels when you know the namespace and service and filter inside JSON with LogQL. Elasticsearch and OpenSearch tokenize message text into inverted indexes, which makes unstructured grep and security analytics expensive but flexible. A Loki label per user ID recreates Prometheus-style cardinality and will stall compactions; keep labels coarse and put high-cardinality identifiers in the JSON body. Hybrid pipelines are common: Loki for the on-call window, with a Collector exporter sending ERROR-only or audit-class logs to search for compliance.

Finance should see projected monthly ingest cost before approving DEBUG in hot paths. Alert when daily gigabytes exceed budget so teams adjust sampling rather than discovering the overrun on the invoice.

Common failure modes

  • Regex parsing in the shipper: Unstructured logs parsed with grok break on the first template change; fix at the application with structured fields.
  • High-cardinality labels: Putting trace_id or user_id in Loki labels mirrors Prometheus cardinality explosions and stalls queries.
  • Logs-only debugging: Scanning terabytes for latency issues ignores traces; use metrics for detection, traces for path, logs for narrative.
  • Silent agent backlog: Without lag alerts, teams discover missing logs only after an incident is unsolvable.

Decision checklist

  • Do all services emit consistent structured JSON with OpenTelemetry trace context on request paths?
  • Are shippers highly available and monitored via Prometheus?
  • Are Loki or index labels limited to low-cardinality dimensions?
  • Are retention, compaction, and cold archive policies documented?
  • Can Grafana Explore link traces, metrics, and logs for a single investigation?
  • Are PII and secrets excluded or redacted before ingest?

Example use cases

  • Illustrative scenario — payment errors: After a Prometheus error-rate alert, on-call filters Loki for {app="payment-api", level="error"}, groups by error_code, and finds a provider rate limit during a traffic spike.
  • Illustrative scenario — trace pivot: From a slow Tempo trace, the engineer opens linked Loki logs filtered by trace_id and sees the exact database timeout message—no manual time guessing.
  • Case study — Grafana Loki at scale: Teams running the Prometheus/Loki/Tempo Grafana stack use label discipline and object storage to keep centralized logs affordable alongside metric retention in Mimir or Thanos.
