Continuous Profiling

Continuous profiling in production — CPU, memory, and lock profiles, flame graph interpretation, low-overhead agents, and correlation with traces and metrics.

⏱ 11 min read

What it is

Continuous profiling samples what code is doing in production over time — which functions consume CPU, allocate heap, or contend on locks — and stores profiles as queryable time series. Unlike one-off pprof captures triggered during incidents, always-on profilers run at low overhead (often 1–3% CPU) so historical profiles exist when regressions appear.

Common profile types include CPU (stack samples while on-CPU), heap/allocation (where bytes are allocated), goroutine or thread snapshots (concurrency leaks), and mutex/block profiles (lock contention). A flame graph visualises stacks: width is sample share, height is stack depth. Hot functions appear as wide plates near the top — the first place to look after a metric or trace says “this service got slower.”

Profiling complements traces: a span shows that JSON serialisation took 300ms; a CPU profile shows encoding/json dominates samples during that window. Where platforms support it, linking profiles to W3C trace IDs (the same identifier in traceparent) narrows investigation from a slow trace to the functions active in that request class.

Why it exists

Metrics flag regressions; traces localise slow spans; profiling names the functions and lines responsible. Without continuous data, teams replay incidents under artificial load or add speculative instrumentation. Parca, Pyroscope, and eBPF-based agents reduced the operational cost of keeping profiles always on, making code-level evidence a normal part of observability — sometimes called a “fourth pillar” beside metrics, logs, and traces.

When to use

  • Services with rising CPU, memory, or GC pressure without an obvious metric label to blame.
  • Post-deploy performance comparisons — diff profiles by version or commit label.
  • Cost optimisation in cloud environments where inefficient hot paths directly increase compute bills.
  • Concurrency debugging — goroutine or thread profiles exposing leaks and deadlocks.

When not to use

  • Latency-sensitive paths with untested profilers at aggressive sampling rates — validate overhead in staging first.
  • As the only signal for request-level errors — profiles rarely explain business logic failures without traces and logs.
  • When legal or policy constraints prohibit any production code introspection — rare, but verify compliance.

Typical architecture

Applications expose profiles via SDK push (Pyroscope) or pull (/debug/pprof, Parca agent scraping). Profiles land in a profiling backend object store and are visualised in Grafana alongside metrics and traces.

Pros and cons

Pros

  • Code-level root cause for CPU and memory regressions without redeploying debug builds.
  • Historical profiles enable before/after deploy comparison by version labels.
  • Modern agents target ~1% overhead at default sampling, suitable for many production tiers.
  • eBPF cluster profilers can cover workloads you cannot modify with SDKs.

Cons

  • Storage grows with services and retention — prioritise high-value tiers.
  • Flame graphs require training; misreading base blocks wastes time.
  • Inlined or optimised-away symbols can hide true hotspots without frame pointers or eBPF unwinders.
  • Runtime support quality varies — Go pprof is mature; some JVM and Python modes trade accuracy for overhead.

Implementation notes

Start with CPU and in-use heap profiles on top-traffic services. Tag every profile with service.name, deployment version, and environment — the same resource attributes used in OpenTelemetry traces. When investigating a slow trace, filter profiles to the trace timestamp window and service; emerging OTel profiling signals aim to attach profiles directly to span contexts.

Never expose /debug/pprof on public interfaces. Restrict with network policy and authentication. Prefer continuous agents over manual 30-second CPU captures during peak traffic unless on-call explicitly triggers them.

For Go, import net/http/pprof only on admin listeners. For Python, pyroscope or py-spy at moderate Hz. Compare profiles in CI smoke tests only when overhead is measured — do not enable full continuous profiling in unit test pipelines by default.

Common failure modes

  • Misreading flame graph bases — wide roots are expected; focus on wide leaf frames.
  • Public pprof endpoints — attackers trigger expensive profiles or map internals.
  • Missing version labels — cannot diff Tuesday’s deploy against Monday’s baseline.
  • Profiling without traces — optimising the wrong code path that rarely serves user traffic.
  • Inlining blind spots — hotspot appears inside a generic runtime frame; use alternative unwinders or disable inlining only in staging.

Decision checklist

  • Is continuous CPU profiling enabled on top-tier latency-sensitive services?
  • Are profiles labelled with version or git commit for regression diffs?
  • Are admin profile endpoints restricted to internal networks?
  • Can on-call pivot from traces (W3C trace_id) to profile time windows?
  • Is retention and cost reviewed quarterly?
  • Has the team practiced reading flame graphs on a known hotspot?

Example use cases

  • Illustrative scenario — JSON hotspot: CPU climbs after a library upgrade; flame graph shows deserialization dominating samples; revert or swap serializer restores baseline.
  • Illustrative scenario — goroutine leak: Memory grows over days; goroutine profile shows thousands blocked on HTTP clients without timeouts; adding context deadlines stabilises counts.
  • Case study — Google wide profiling: Google’s production profiling culture demonstrated that always-on sampling is viable at hyperscale when overhead is controlled.
