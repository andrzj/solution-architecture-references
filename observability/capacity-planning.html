Capacity Planning

Forecasting demand and reserving headroom for compute, storage, and network so growth and launches do not breach SLOs.

⏱ 12 min read

What it is

Capacity planning is the discipline of estimating future resource needs—CPU, memory, disk IOPS, network throughput, connection limits, queue depth, license seats, and vendor quotas—and acting before utilization breaches safe operating margins. It combines historical telemetry, business forecasts (launches, campaigns, tenant onboarding), and deliberate load testing to answer: “At expected peak, do we still meet SLOs with defined headroom?”

Autoscaling handles short-term variance but not unlimited growth: every autoscaler has maximum instance counts, regional quotas, database connection pools, and downstream dependencies that scale more slowly. Capacity planning sets those ceilings intentionally and schedules procurement (reserved instances, hardware lead times, CDN contracts) when elasticity alone is insufficient or uneconomical.

Why it exists

Surprise saturation produces user-visible latency, dropped messages, and emergency spending at the worst time—during a launch or seasonal peak. Proactive planning aligns engineering, finance, and vendors on expected growth, avoids last-minute quota increases, and surfaces architectural bottlenecks (single hot partition, synchronous choke point) early enough to refactor.

Overload handling (throttling, shedding, queueing) buys time during spikes, but sustained demand still requires capacity. Planning links reliability work to cost: right-sized headroom is cheaper than repeated incident firefighting and than permanent over-provisioning without data.

When to use

  • Seasonal traffic, major marketing events, or product launches with step-change demand.
  • Multi-tenant SaaS where tenant onboarding or noisy neighbors can shift load unpredictably.
  • Resources with long lead times: bare metal, reserved capacity, cross-region networking, enterprise licenses.
  • Platforms approaching saturation signals: rising p99 latency, queue age, disk queue depth, or error budget burn during peak hours only.

When not to use

  • Low-growth internal tools with flat usage—lightweight monitoring may suffice without formal quarterly models.
  • Planning CPU alone while ignoring database connections, egress bandwidth, or API rate limits that fail first.
  • Assuming autoscaling removes all planning without validating max limits, cold-start time, and cost guardrails.

Typical architecture

The loop is observe → forecast → plan → validate: metrics and business inputs feed models; plans drive scaling changes or purchases; load tests and synthetic traffic confirm assumptions before production events.

Pros and cons

Pros

  • Reduces incident risk from predictable growth and known events.
  • Improves FinOps: reserved capacity and architecture fixes are planned, not panic-bought.
  • Surfaces non-obvious bottlenecks (egress, metadata DB, license caps) before they page.
  • Creates shared assumptions between product, finance, and platform teams.

Cons

  • Forecasts wrong in volatile markets—plans must be revisited frequently.
  • Cross-team data collection (marketing calendars, sales pipeline) is slow and political.
  • Models rot without owners; stale plans create false confidence.
  • Excess headroom wastes money if not tied to explicit risk tolerance.

Implementation notes

Track saturation metrics, not averages alone: disk queue length, thread pool rejections, Kafka consumer lag, API 429 rates, and dependency latency at peak. Define a headroom policy (for example 30% below hard limits or N+1 failure tolerance) per tier-1 path.

Load tests should reproduce peak shape—mix of reads/writes, burstiness, cache cold start—not just a flat RPS number. Soak tests catch memory leaks and connection churn. Align autoscaling group maximums and rate limiter configs with the approved plan.

Integrate leading indicators into planning cadence: signup velocity, campaign dates, enterprise go-live dates, and partner integrations. Review quarterly at minimum; monthly before known events.

Write headroom down. For tier-1 APIs, many teams target thirty to fifty percent unused CPU and memory at forecast peak, or enough surplus that losing one availability zone still meets SLO. Headroom is not waste; it is the buffer that absorbs deploy spikes and retry storms without immediate paging.

Load labs rarely match production mix. When extrapolating lab RPS to fleet size, apply a conservative multiplier unless shadow traffic has validated the model, because production adds cache misses, cold starts, and chatty clients. Little’s Law states that average concurrent work in the system equals throughput multiplied by average time in the system (L = λ × W). If checkout runs at one hundred RPS with a two hundred millisecond p99, you need on the order of twenty in-flight requests before overhead—not ten replicas based on CPU alone. Size thread pools, connection pools, and queue consumers from that concurrency, not from naive CPU charts.

After a test, verify the first saturated resource: broker lag, database connections, or outbound API quotas often fail before Kubernetes adds pods.

Common failure modes

  • CPU-only planning: Application servers scale while the primary database or payment API becomes the choke point.
  • No pre-launch load test: First real traffic reveals synchronous calls and missing indexes.
  • License or quota walls: SaaS seats, cloud API quotas, or vendor TPS caps fail before Kubernetes scales out.
  • Thundering herd on cold caches: Scale-out amplifies backend load when caches are empty after deploy or region shift.
  • Ignoring downstream dependencies: Your stack scales; a third-party webhook endpoint does not.

Decision checklist

  • Is the peak traffic model updated with latest business forecasts?
  • Do load tests match production topology, data volume, and traffic mix?
  • Are autoscaling maximums, quotas, and rate limits aligned with the approved plan?
  • Have vendors confirmed capacity for contracted throughput or support windows?
  • Is there a degradation playbook if saturation persists despite scaling?
  • Does FinOps review reserved capacity and waste after each planning cycle?

Example use cases

  • Illustrative scenario — seasonal e-commerce: Meridian Commerce models holiday growth from prior-year telemetry, pre-warms CDN and search caches, adds read replicas, and validates checkout with load tests eight weeks before peak.
  • Illustrative scenario — multi-tenant SaaS: Noisy neighbor isolation via rate limits and per-tenant concurrency caps; capacity plan includes largest tenant’s contract growth.
  • Illustrative scenario — event streaming: Message broker disk and network sizing for publish spike during batch replays; consumer autoscale max tied to downstream DB write capacity.
