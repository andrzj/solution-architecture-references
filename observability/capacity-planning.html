Capacity Planning

Forecasting compute, storage, and network headroom before you need it.

⏱ 10 min read

What it is

Capacity Planning is the pattern to use when seasonal businesses and major launches. Capacity planning forecasts compute, storage, and network headroom using historical metrics, growth models, and upcoming launches.

Example: tracing Black Friday traffic growth, modeling 40% YoY increase, pre-provisioning database IOPS and CDN contracts 8 weeks early.

Why it exists

Surprises cause outages and emergency spend. Planning aligns finance, engineering, and vendors before demand spikes.

When to use

  • Seasonal businesses and major launches.
  • Multi-tenant platforms with bursty tenants.
  • Long lead-time hardware or reserved capacity.

When not to use

  • Over-planning static internal tools with flat usage.
  • Ignoring autoscaling limits — plan ceiling too.

Typical architecture

Pros and cons

Pros

  • Prevents performance incidents.
  • Smoother vendor negotiations.
  • Informs architecture refactors.
  • Links cost to growth.

Cons

  • Wrong forecasts waste money.
  • Elastic cloud reduces urgency — still need limits.
  • Cross-team data gathering slow.
  • Models drift without refresh.

Implementation notes

Use load tests reproducing peak shapes; monitor saturation (CPU, disk queue, network PPS). Maintain 30% headroom or defined N+1.

Track leading indicators — signups, campaign dates, tenant onboarding pipeline.

Common failure modes

  • CPU-only planning ignoring DB or egress.
  • No load test before launch.
  • License limits hit before infra.
  • Thundering herd on cold caches.

Decision checklist

  • Peak traffic model updated quarterly?
  • Load tests match production topology?
  • Autoscaling max aligned with plan?
  • Vendor capacity confirmed?
  • Rollback if saturation persists?
  • FinOps loop on reserved capacity?

Example use cases

  • E-commerce: Pre-warm caches; scale DB read replicas.
  • SaaS: Noisy neighbor isolation with rate limits.
  • Streaming: Kafka broker disk and network sizing.

Related patterns

  • Metrics and Monitoring — Inputs for models.
  • Synthetic Monitoring — Pre-launch validation.
  • Health Checks — Detect saturation early.
