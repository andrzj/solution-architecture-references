Feature Flags & Observability

Instrumenting feature flags so rollouts, experiments, and kill switches are visible in metrics, traces, and logs.

⏱ 12 min read

What it is

Feature flags decouple deployment (code present in production) from release (code exercised by users). Observability for flags means every evaluation that affects behavior is visible in telemetry: metrics broken down by flag key and variant, trace attributes that follow requests across services, and structured log fields for debugging “why did this user see behavior B?”

Without instrumentation, progressive delivery becomes guesswork: a canary at 5% may look healthy in aggregate while the canary cohort’s error rate is unacceptable—or a kill switch may be off while cached SDK state still routes traffic to a broken path. Treat flag state as a first-class dimension of observability, with bounded cardinality and consistent evaluation context (user, tenant, region, app version).

Why it exists

Teams adopt flags to reduce blast radius and accelerate experimentation. Those benefits only hold if you can compare variants on the same SLIs you use for production health—latency, error rate, conversion, resource usage—and roll back on data within minutes. Flag observability also accelerates incident response: during an outage, knowing which cohort received a new variant narrows the search space dramatically.

Open standards (for example OpenFeature) and vendor integrations increasingly export flag context into OpenTelemetry. The architectural goal is the same: one place to query “errors for checkout_redesign=true in region eu-west.”

When to use

  • Canary releases, percentage rollouts, and A/B tests where decisions depend on measured impact.
  • Kill switches for risky features where disabling must not require a full redeploy.
  • Per-tenant or per-segment entitlements in B2B products—observability proves correct targeting.
  • Shadow or dark launches where new code runs without user-visible effect but still emits comparative metrics.

When not to use

  • Stable, long-lived configuration (feature tiers, rate limits)—use a configuration service with normal change control.
  • Flags changed in production without audit logs—observability cannot replace governance.
  • High-cardinality targeting (per-user variant labels on every metric)—will explode time-series cost; aggregate or sample instead.

Typical architecture

Applications evaluate flags via an SDK or agent backed by a flag management service. Telemetry pipelines attach flag key and variant at request boundaries; dashboards and alerts group SLIs by those dimensions during rollouts.

Pros and cons

Pros

  • Fast rollback by toggling exposure without rebuilding artifacts.
  • Variant-level SLIs make canary and A/B decisions evidence-based.
  • Kill switches limit blast radius when a feature misbehaves after deploy.
  • Correlates incidents with recent flag changes in timelines and traces.

Cons

  • Flag debt multiplies code paths—observability labels do not remove testing burden.
  • Stale SDK cache can desync perceived vs actual rollout state.
  • Poor cardinality discipline on flag labels can inflate metrics cost.
  • Client-only evaluation is bypassable; server-side truth is required for security-sensitive flags.

Implementation notes

Standardize attribute names (feature_flag.key, feature_flag.variant) across services and propagate via OpenTelemetry context. Restrict metric labels to a bounded set of flag keys under active rollout; log detailed evaluation at debug level with sampling.

Define SDK failure modes explicitly: fail closed for kill switches that protect stability, fail open only when business accepts risk—document which is which per flag. Server-side evaluation is mandatory for entitlements, pricing, and authorization.

Automate hygiene: reports for flags older than 90 days without changes, mandatory removal tickets when rollout completes, and synthetic checks that assert both variants (where safe) emit expected telemetry.

Observability during rollout: Slice error-rate and latency metrics by feature_flag.variant with bounded cardinality—never per-user labels. Compare canary variant to control in the same dashboard panel product reviews during progressive delivery. Log flag evaluation at INFO once per request (variant + key), not per internal branch.

Tie kill switches to degradation runbooks: flipping a flag should emit a structured audit event and shift SLO dashboards to a documented “degraded tier” so incidents are not mistaken for dependency failure.

Common failure modes

  • Client-only gating: Sensitive features enforced in mobile or browser code are trivially bypassed.
  • Wrong defaults when the flag service is unreachable: SDK serves stale “on” while operators believe the kill switch worked.
  • Unbounded variant labels: Per-user IDs in metric dimensions overwhelm the time-series backend.
  • No change audit: Incidents cannot be correlated with who enabled a flag at what time.
  • Aggregate dashboards hide canary regression: Rollout continues because global error rate looks flat.

Decision checklist

  • Are security- and billing-related flags evaluated server-side only?
  • Do traces and metrics include flag key and variant with bounded cardinality?
  • Are kill switches tested in staging and exercised in game days?
  • Is there a defined flag removal process after full rollout?
  • Are production flag changes audited with actor, time, and old/new values?
  • Is SDK offline behavior documented per flag (fail open vs closed)?

Example use cases

  • Illustrative scenario — ranking canary: RideRelay routes 5% of search traffic to a new ranker; dashboards compare p99 latency and error rate by ranker_v2 variant; automatic promotion halts when burn rate exceeds threshold.
  • Illustrative scenario — enterprise beta: B2B tenant allowlists gate a beta API; logs and metrics include tenant_id in traces (not as metric labels) to verify only contracted tenants received the feature.
  • Case study — progressive delivery at scale: Large product organizations document flag-driven rollouts with automatic rollback when SLIs regress; public write-ups from vendors and practitioners describe tying experimentation to core monitoring stacks.
