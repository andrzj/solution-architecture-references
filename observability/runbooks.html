Observability & Operations

Runbooks

Documented operational procedures—manual, guided, or automated—that on-call engineers follow during alerts and incidents.

⏱ 12 min read

What it is

A runbook is a step-by-step operational guide for a specific, repeatable situation: a paging alert, a known failure mode, a maintenance window, or an emergency mitigation. Good runbooks state what the signal means, who should act, prerequisites (access, tools, dashboards), diagnostic steps, mitigation paths, rollback, verification, and when to escalate. They may be purely textual, interactive checklists in an incident tool, or partially automated scripts invoked from approved workflows.

Runbooks differ from general architecture docs: they are written for someone under time pressure, often at night, who may not own the service daily. Each step should be concrete (“check replica lag on dashboard X”; “run kubectl rollout undo on deployment Y”) rather than vague (“investigate database”).

Why it exists

Institutional knowledge otherwise lives in the heads of senior engineers—and walks out the door when they leave. Under stress, improvisation produces inconsistent fixes, missed rollback paths, and longer MTTR. Runbooks encode what already worked, shorten onboarding for new on-call rotations, and provide the scaffolding for safe automation later.

Linking runbooks directly from alert annotations closes the loop between detection and response: the page that wakes someone should explain user impact and the first actions to take within seconds.

When to use

  • Every alert that can page a human should reference a runbook—or the alert should not page.
  • Recurring operational tasks: certificate renewal failures, cache saturation, queue backlog, regional failover.
  • Compliance or change-management regimes that require approved, versioned procedures for production changes.
  • Candidates for automation: well-understood sequences with clear success criteria and rollback.

When not to use

  • Novel, first-seen failures where the correct steps are unknown—improvise, then author a runbook after the incident.
  • Pasting vendor documentation without hostnames, dashboard links, or environment-specific guardrails.
  • Multi-page narratives that nobody reads during an incident—split reference material from the “first 15 minutes” path.

Typical architecture

Runbooks sit between alerting and action: annotations deep-link from the paging system; execution may stay manual, use semi-automated runbook platforms, or call idempotent automation with approval gates for destructive steps.

Pros and cons

Pros

  • Consistent handling across shifts and regions reduces variance in MTTR.
  • Faster onboarding: junior on-call can execute proven steps with escalation criteria defined.
  • Clear prerequisites expose access gaps before an incident, not during one.
  • Version-controlled runbooks pair naturally with code review and game-day validation.

Cons

  • Stale runbooks are dangerous—wrong hosts and commands waste critical minutes.
  • Over-automation without guardrails can amplify mistakes at machine speed.
  • Ownership and review cadence create ongoing maintenance cost.
  • Over-long documents are ignored; constant curation is required.

Implementation notes

Structure each runbook with: impact statement, prerequisites, diagnostic tree, mitigation (primary and alternate), rollback, verification metrics, and escalation contacts. Keep the “first actions” section short enough to read on one screen on a phone.

Store runbooks in Git (or a wiki with review workflow) next to the services they describe. Require a last_reviewed date and named owner; block merges on alerts that page without a linked, reviewed runbook.

Scripts should support dry-run, be idempotent where possible, and log to stdout for capture in the incident timeline. Destructive operations (data deletion, forced failover) should use two-person approval or break-glass roles with audit logging—never plaintext secrets in the doc.

Automation: Encode safe steps in executable runbooks (Ansible, Terraform taint, AWS SSM Automation, internal bots) with approval webhooks for mutating paths. Automated remediation (restart consumer, scale HPA floor, flip feature flag) should mirror the manual doc one-to-one—drift between bot and wiki guarantees 3 a.m. failure. GameDays must execute the automated path, not only read the Markdown.

Attach runbook_url to Alertmanager annotations and PagerDuty custom details so the first link is always current Git main.

Common failure modes

  • Broken commands after infra churn: Kubernetes resource names, regions, or dashboard URLs drift; nobody re-ran the steps in a drill.
  • Missing escalation: Engineer burns an hour on a dependency they cannot control.
  • Secrets in runbooks: Credentials in Markdown leak via search indexes and ticket exports.
  • No verification step: Mitigation appears done while user-visible errors continue.
  • Runbook bypass: Veterans skip the doc; fixes are not reflected back into the canonical procedure.

Decision checklist

  • Does every paging alert include a runbook link and user-impact summary?
  • Is rollback documented and tested for each destructive mitigation path?
  • Does each runbook list owner, last review date, and required access?
  • Have game days or fire drills executed the runbook in the last two quarters?
  • Are automation hooks idempotent, logged, and gated for high-risk steps?
  • Is there a process to capture new steps after novel incidents?

Example use cases

  • Illustrative scenario — cache memory pressure: A “Redis memory high” alert links to a runbook that checks eviction policy, identifies hot keys, scales vertically if needed, and only flushes after explicit approval—with rollback if error rate spikes.
  • Illustrative scenario — queue backlog: Northwind Logistics consumers lag during a promotion; the runbook scales consumer replicas, verifies poison-message DLQ depth, and documents when to page the owning team.
  • Illustrative scenario — database failover: DNS or traffic-manager flip with pre-checks on replication lag and post-checks on read/write error budgets before closing the incident.
