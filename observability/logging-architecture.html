Observability & Operations

Logging Architecture

Logging architecture defines how production systems emit structured events, ship them reliably, retain them by tier, and query them during incidents—with OpenTelemetry correlation and Grafana/Loki or search-index backends.

⏱ 10 min read

What it is

Logging architecture is the end-to-end design for how a system produces, transports, stores, secures, and queries log data in production. It spans application choices (log levels, structured fields, correlation identifiers), platform choices (agents, buffers, streams), storage tiers (hot search, warm compression, cold archive), and operational contracts (retention, access control, cost budgets). A mature logging architecture treats logs as an event stream the application writes to stdout or stderr, not as files that operators must tail on individual hosts—consistent with the twelve-factor logs guidance and with how Kubernetes and most container runtimes collect workload output.

Effective logging architecture aligns with the wider observability stack described in the Google Site Reliability Engineering book: logs complement metrics for detection and traces for request-scoped causality. OpenTelemetry unifies that story by letting applications emit log records through the same SDK and Collector pipeline used for metrics and traces, injecting trace_id and span_id into log context so Grafana Explore can pivot from a latency spike to the exact lines that explain it. Backends such as Grafana Loki (label-indexed, object-store friendly) or Elasticsearch (full-text indexed) sit at the end of the pipeline; the architecture choice is less about the brand of store and more about whether labels, retention, and query patterns match your incident and compliance needs.

Why it exists

Without an explicit logging architecture, every team invents its own format, path, and retention. Incidents then stall on questions that should be mechanical: where did this pod write logs, how long are they kept, who can search them, and can we correlate them with Prometheus alerts or Tempo traces? Central pipelines exist because distributed systems destroy the assumption that the failing instance is still running when you investigate. Charity Majors and the Honeycomb team argue that high-fidelity, wide events beat sparse breadcrumbs for debugging novel failures; even when you adopt Loki or ELK rather than an event store, the same lesson applies—architecture must preserve rich, queryable fields instead of fragile grep workflows.

Regulated environments add non-negotiable requirements: immutable archives, time-bounded deletion for privacy, and evidence that log infrastructure was not tampered with during an audit. A deliberate architecture trades off ingestion cost against mean time to recovery (MTTR) and documents those tradeoffs so finance and compliance can reason about them.

When to use

  • Any production system with more than one deployable unit, ephemeral instances, or shared on-call—central collection is baseline operations, not an optional upgrade.
  • Teams practising SRE-style incident response that must correlate logs with SLI metrics in Prometheus and exemplar-linked traces in Grafana.
  • Organizations with compliance retention (PCI, HIPAA, SOC 2) that need tiered storage, access RBAC, and provable chain of custody.
  • Platform engineering groups standardizing how hundreds of services emit JSON logs and ship them through OpenTelemetry Collector or Fluent Bit.

When not to use

  • Logging architecture is always required in production; what you avoid is over-building cold paths. A single-process developer laptop does not need Kafka and OpenSearch, but it should still use the same structured schema the pipeline expects.
  • Do not route full request bodies, secrets, or payment instrument data through the log pipeline—architecture must include redaction and classification, not just volume controls.

Typical architecture

Workloads emit structured JSON to standard output; node-level agents forward once and fan out to streaming analytics, searchable hot storage, and inexpensive cold archives.

Pros and cons

Pros

  • Central search shrinks incident timelines because engineers query all services from one interface instead of SSHing to missing pods.
  • Tiered retention matches cost to value: hot Loki or Elasticsearch for the last days, object storage for months, glacier for years.
  • Stream consumers can derive metrics or security signals without re-parsing logs at query time—useful alongside Prometheus recording rules.
  • A published schema (ECS, OpenTelemetry semantic conventions, or an internal standard) makes cross-team analytics predictable.

Cons

  • Ingestion and indexing dominate spend at high volume; DEBUG in hot paths can dwarf application compute if architecture lacks sampling and level controls.
  • Misconfigured agents buffer until they crash or drop silently—monitor agent lag and export health metrics to Prometheus.
  • Hot clusters (Elasticsearch or Loki ingesters) need capacity planning; sudden log storms during deploys can exhaust disk or memory.
  • PII and secrets in logs create compliance exposure that no retention tier can undo; architecture must enforce redaction at the source.

Implementation notes

Standardize on structured JSON to stdout, UTC timestamps, and bounded fields. Propagate request, trace, and business identifiers through OpenTelemetry context so every line on a critical path includes trace_id when a span is active. Ship logs through Fluent Bit, Vector, Promtail, or the OpenTelemetry Collector depending on whether you target Loki directly or OTLP to multiple backends.

Define retention in policy, not tribal knowledge: for example seven to thirty days hot in Loki or Elasticsearch, ninety days warm, multi-year cold on WORM object storage for audits. Export ingestion rate, drop counters, and lag as Prometheus metrics and page when agents fall behind. Run the log control plane under separate IAM from application roles, and scrub sensitive fields in the Collector when applications cannot guarantee omission.

Common failure modes

  • Unstructured or multi-line logs: Parsing prose in the shipper breaks when developers change wording; structured JSON avoids brittle regex pipelines.
  • Logging inside tight loops: Synchronous I/O on hot paths saturates CPU and balloons volume; sample debug or push detail to traces.
  • No backpressure handling: Agents that never shed load OOM during traffic spikes and lose the very events needed for diagnosis.
  • Clock skew and missing correlation: Non-UTC timestamps disorder timelines; missing trace or request identifiers prevent joins with Tempo and Prometheus exemplars.

Decision checklist

  • Is structured JSON to stdout mandatory for all production services?
  • Are OpenTelemetry trace and span identifiers present on request-scoped log lines?
  • Are hot, warm, and cold retention tiers documented with owners and cost targets?
  • Are collection agents monitored (lag, drops, memory) with Prometheus alerts?
  • Is PII scrubbed at source or in the Collector before indexing?
  • Is query access RBAC-scoped and audited?

Example use cases

  • Illustrative scenario — Kubernetes platform: A platform team deploys Promtail DaemonSets, pushes to Grafana Loki, and exposes LogQL in Grafana; on-call pivots from Prometheus burn-rate alerts to correlated logs using shared labels.
  • Illustrative scenario — OpenTelemetry migration: Services switch from file appenders to OTLP logs export through a Collector that fans out to Loki and a compliance S3 bucket with distinct processors.
  • Case study — Google SRE logging practice: Production services treat logs as structured streams with strict level discipline, aligning detection with the monitoring guidance in the SRE book rather than ad-hoc tailing.
