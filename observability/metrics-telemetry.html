Metrics & Telemetry

Collecting and shipping telemetry data at scale with minimal overhead.

⏱ 10 min read

What it is

Example: a service exposes http_requests_total and latency histograms; Prometheus scrapes every 15s; recording rules pre-aggregate SLO burn rates.

Why it exists

Logs are too heavy for fleet-wide health views. Metrics enable dashboards, alerting, and autoscaling with predictable cost when cardinality is controlled.

When to use

  • SLO monitoring and capacity dashboards.
  • Autoscaling signals (CPU, queue depth, custom KPI).
  • Comparing canary vs stable during deploys.

When not to use

  • High-cardinality identifiers (user ids) as labels — destroys TSDB.
  • Replacing traces for deep debugging — use both.

Typical architecture

Pros and cons

Pros

  • Efficient aggregation at scale.
  • Mature alerting ecosystems.
  • Great for golden signals (latency, traffic, errors, saturation).
  • Enables horizontal autoscaling.

Cons

  • Cardinality explosions.
  • Histogram bucket design mistakes.
  • Pull model NAT challenges.
  • Metric naming sprawl.

Implementation notes

Follow RED/USE methods; cap label cardinality; use exemplars to link traces. Run recording rules for expensive queries.

Instrument client and server sides; export process metrics (GC, thread pools).

Common failure modes

  • unbounded label values.
  • Missing _total counters breaking rate().
  • Scrape timeout during GC pauses.
  • Dual write to multiple systems unsynchronized.

Decision checklist

  • Golden signals instrumented?
  • Label cardinality reviewed?
  • Recording rules for SLIs?
  • Dashboards per service owner?
  • Retention matches incident needs?
  • Alert routes on SLO burn?

Example use cases

  • Microservices: Prometheus federation per cluster.
  • Serverless: CloudWatch EMF for Lambda durations.
  • Mobile backend: Custom business KPI metrics per feature flag.
