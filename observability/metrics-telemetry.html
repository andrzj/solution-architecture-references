Metrics & Telemetry

The metrics telemetry pipeline — instrumentation, collection, aggregation, and export to time-series backends — with exemplars linking histograms to W3C Trace Context trace IDs.

⏱ 11 min read

What it is

Metrics telemetry is the end-to-end path from instrumented code to durable time-series storage: applications emit numeric signals (counters, gauges, histograms), collectors aggregate and ship them to backends, and operators query them for dashboards, alerting, and autoscaling.

Instrumentation typically exposes the golden signals — request rate, errors, duration, and saturation (RED for request-driven services, USE for resources). Histograms capture latency distributions; counters accumulate monotonically for rate() queries; gauges represent point-in-time values such as queue depth or connection pool usage.

Two dominant collection models coexist. Pull-based scraping (for example Prometheus scraping /metrics on an interval) keeps applications simple and centralises scrape configuration, but struggles behind NAT and requires network reachability from the scraper. Push-based export (OpenTelemetry OTLP metrics, Prometheus remote write, StatsD agents) suits ephemeral workloads, serverless, and multi-tenant clusters where pull targets change constantly.

Exemplars attach a reference sample to a histogram bucket — often the trace_id from an active distributed trace. That identifier is the same 128-bit value carried in the W3C traceparent header, so a spike on a latency histogram can pivot directly into the trace that experienced the slow request. Without exemplars, aggregate metrics show that p99 increased but not which request to investigate.

Why it exists

Logs are too voluminous and too unstructured for fleet-wide health views at millisecond resolution. Metrics compress behaviour into numbers that TSDBs can store and query cheaply for months or years. The telemetry layer exists because raw application output is not enough: teams need consistent naming, controlled cardinality, batching, retry semantics, and backend-specific export so that every service speaks a common language to SRE dashboards and SLO burn alerts.

As OpenTelemetry unifies traces, metrics, and logs, the metrics pipeline increasingly shares collectors and resource attributes (service.name, environment, version) with tracing — enabling correlated investigation without duplicate instrumentation silos.

When to use

  • SLO and error-budget monitoring — SLIs are almost always metric queries over request success and latency histograms.
  • Capacity planning and autoscaling — CPU, memory, queue depth, and custom business KPIs as control signals.
  • Deploy verification — compare canary vs stable on error rate and latency percentiles during progressive delivery.
  • Cross-signal correlation — exemplars on histograms linked to W3C trace IDs for “metric spike → specific trace” workflows.

When not to use

  • Per-request debugging detail — metrics cannot replace traces or structured logs; they aggregate away individual request context.
  • High-cardinality dimensions — using user IDs, order IDs, or raw URL paths as metric labels will explode TSDB cardinality and cost.
  • Long-form audit evidence — metrics are not an audit trail; retain events or logs for compliance records.

Typical architecture

Services instrument with OpenTelemetry SDKs or Prometheus client libraries, export via OTLP or scrape endpoints, pass through a collector for batching and enrichment, and land in a TSDB queried by Grafana or similar tools.

Pros and cons

Pros

  • Predictable storage cost when label cardinality is governed — numbers compress better than logs or full traces.
  • Mature alerting ecosystems (recording rules, multi-window burn rates) built on metric queries.
  • Native fit for autoscaling and capacity dashboards across large fleets.
  • Exemplars bridge aggregates and traces without sampling every request into long-term trace storage.

Cons

  • Cardinality mistakes are expensive to unwind — bad label design can degrade an entire TSDB cluster.
  • Histogram bucket design is permanent for historical data — wrong buckets distort SLO percentile calculations.
  • Pull scraping across dynamic networks requires service discovery discipline and security boundaries.
  • Metric naming sprawl without conventions makes cross-team dashboards inconsistent.

Implementation notes

Standardise metric names and labels (Prometheus naming conventions or OpenTelemetry semantic conventions). Cap label cardinality in code review — prefer bounded enums (status_code, route_template) over raw paths. Run recording rules or equivalent for expensive SLO queries so alert evaluation stays fast.

Enable exemplars on latency histograms where the SDK supports them; ensure the trace pipeline uses W3C Trace Context so exemplar trace IDs match what trace backends index. Instrument both client and server sides of RPC calls so blind spots do not hide downstream latency. Export process runtime metrics (GC, thread pools, event loop lag) alongside application RED metrics.

For Kubernetes, a common pattern is a node-level or cluster-level OpenTelemetry Collector receiving OTLP from pods and remote-writing to a central TSDB, avoiding per-pod scrape config churn.

Metric types: Counters only increase—use rate() or increase() for request volume. Gauges go up and down—pool size, queue depth. Histograms bucket observations so Prometheus can compute percentiles with histogram_quantile() across instances—prefer histograms for latency SLOs. Summaries pre-compute quantiles client-side; those quantiles cannot be averaged across pods in PromQL—avoid summaries for fleet-wide SLOs unless you accept per-instance-only views.

Pull vs push: Prometheus scrape keeps apps dumb (expose /metrics); federation and service discovery own the target list. OTLP push suits short-lived jobs, FaaS, and multi-tenant clusters where scrape would miss pods. Many estates use both: scrape for long-lived services, OTLP remote write for the rest—label sets must match or dashboards fork.

Native histograms: Prometheus native histograms (sparse buckets, better percentile accuracy, lower cardinality than classic `_bucket` series) are rolling out in newer releases; plan bucket strategy before years of legacy histogram data lock you into suboptimal buckets.

Label hygiene: Treat every new label as a capacity decision—route_template not path; status class or code bucket, not raw status on high-cardinality APIs. Use recording rules to collapse labels before alerts fire.

Common failure modes

  • Unbounded label values — dynamic IDs as labels multiply series count until queries timeout and storage costs spike.
  • Missing _total on counters — breaks rate() and SLO error-ratio recording rules.
  • Scrape timeouts during GC pauses — marks targets down and triggers false alerts; tune timeouts and use push export for jittery runtimes.
  • Dual-write without alignment — sending the same metrics to two systems with different label sets makes dashboards disagree during incidents.
  • Exemplars without trace correlation — exemplars help only when trace IDs follow W3C format and trace backends retain matching spans.

Decision checklist

  • Are RED or USE golden signals instrumented on every production service?
  • Is label cardinality reviewed in design and code review?
  • Do recording rules pre-compute SLI queries used in alerts?
  • Are exemplars enabled on latency histograms with W3C-compatible trace IDs?
  • Is retention aligned with incident investigation and compliance needs?
  • Do alert routes tie to SLO burn policies, not static thresholds alone?

Example use cases

  • Illustrative scenario — regional latency regression: A deploy raises p99 on checkout; the Grafana heatmap shows the spike; clicking an exemplar opens the trace whose traceparent matches the exemplar ID, revealing a new downstream timeout.
  • Case study — Prometheus at SoundCloud: Early Prometheus adoption demonstrated pull-based scraping plus label discipline as a template for cloud-native metrics at scale.
  • Illustrative scenario — federation per cluster: Edge clusters remote-write aggregated metrics to a global TSDB; regional dashboards stay local; global SLOs query the central store.
