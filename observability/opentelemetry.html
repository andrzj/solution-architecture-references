Observability & Operations

OpenTelemetry

OpenTelemetry — vendor-neutral traces, metrics, and logs with OTLP export, W3C Trace Context propagators, Collector pipelines, and semantic conventions.

⏱ 12 min read

What it is

OpenTelemetry (OTel) is a CNCF project that standardises how applications produce, enrich, and export telemetry — traces, metrics, and logs — without locking teams to a single observability vendor. Application code depends on the stable OTel API; the SDK implements sampling, batching, and export; the optional Collector receives OTLP (and other formats), processes telemetry centrally, and fans out to backends.

For traces, OTel’s default text map propagator implements W3C Trace Context: inject traceparent and optional tracestate on outbound HTTP/gRPC and extract them on ingress. The same 128-bit trace identifier flows to logs (via log bridges), metric exemplars, and downstream services — one correlation key across signals.

Auto-instrumentation (agents or library hooks) covers common frameworks — HTTP servers and clients, gRPC, JDBC, Redis, message consumers — with minimal code changes. Manual instrumentation adds domain spans and attributes (order identifiers, payment state, feature flags) that generic hooks cannot infer. Semantic conventions document standard attribute names (http.request.method, db.system, messaging.destination.name) so dashboards and alerts work across services written in different languages.

Beyond traces, the same SDK emits metrics and log bridges over OTLP (gRPC or HTTP). Exemplars on histograms can reference active trace IDs, and log appenders attach the same resource attributes as spans—so one bootstrap library feeds all three pillars without three proprietary agents.

Why it exists

Before OTel, organisations accumulated incompatible tracing APIs (OpenTracing, OpenCensus, vendor agents) and paid twice: once to instrument, again to switch backends. Merging those efforts produced a single SDK trajectory supported by major vendors. OTLP is now natively accepted by Jaeger, Tempo, Prometheus remote write paths, Datadog, New Relic, Honeycomb, and others — instrumentation becomes a durable asset, not a lease on one vendor.

As a top-tier CNCF project, OTel benefits from vendor contributions and long-lived semver on the API surface. Platform teams treat collector pipelines as shared infrastructure—much like ingress controllers—so application squads export OTLP locally and never embed vendor-specific exporters in service repos.

When to use

  • All new services that need production observability — OTel should be the default bootstrap choice.
  • Platform teams standardising propagation, resource attributes, and collector pipelines once for hundreds of microservices.
  • Multi-backend or multi-team routing — one OTLP stream, many exporter targets (security analytics, long-term trace store, metrics TSDB).
  • Migrations from B3, X-Ray, or proprietary agents — collectors translate headers while applications move to W3C-native SDKs.

When not to use

  • Mature services with stable vendor SDKs and no portability requirement — migrate opportunistically, not under arbitrary deadlines.
  • Ultra-constrained embedded firmware with no room for SDKs — use minimal metrics or logs only.
  • When a managed runtime provides sufficient bundled telemetry and export is not negotiable — weigh portability against integration cost.

Typical architecture

Applications export OTLP to a nearby Collector (DaemonSet or sidecar). A central Collector tier runs tail sampling, adds Kubernetes metadata, and exports to trace, metric, and log backends.

Pros and cons

Pros

  • Vendor-neutral instrumentation — retarget Jaeger, Tempo, or a commercial APM by editing Collector exporter blocks while JVM, Go, and Node services keep the same OTel SDK import.
  • Central Collector handles tail sampling, PII scrubbing, and fan-out once—capabilities that would otherwise be reimplemented per language or per team.
  • W3C Trace Context by default improves cross-language and cross-vendor correlation; meshes and API gateways can participate without custom header vocabularies.
  • Semantic conventions reduce bespoke attribute naming per team so a db.system filter in Grafana works whether the service was written in Java or Python.

Cons

  • SDK maturity varies by language; Java and Go are battle-tested, while some dynamic languages expose thinner auto-instrumentation libraries that need staging validation.
  • Collectors are another tier to size, upgrade, and monitor — misconfiguration can drop telemetry silently while applications still believe export succeeded.
  • Auto-instrumentation can conflict with exotic frameworks, bytecode weaving policies, or security agents—load tests should compare span counts before and after enabling agents.
  • Operational learning curve for pipeline YAML, receiver ports, and processor ordering—especially when tail sampling, auth extensions, and multiple exporters stack in one gateway deployment.

Implementation notes

Deploy agent Collectors per node for low-latency OTLP ingest; gateway Collectors for tail sampling and backend routing. Always place memory_limiter first in processor chains to avoid OOM under spike load—dropping spans under pressure is preferable to the collector process exiting and losing entire batches.

A common Kubernetes layout uses a DaemonSet agent on each node (applications talk over loopback) and a horizontally scaled gateway tier that owns tail sampling and multi-exporter fan-out. That split keeps application configuration dumb while expensive, stateful decisions live where operators can roll out collector upgrades independently of service deploys.

Set resource attributes at startup: service.name, service.version, deployment.environment. Enable the W3C propagator; disable legacy B3-only modes unless required for a specific dependency during migration.

Use baggage sparingly for cross-cutting business keys — never secrets. Prefer span attributes for data that should land in trace storage. Bridge logs to OTel so log records include trace and span IDs matching W3C values.

Configure tail sampling policies: retain errors, high latency, and debug headers; probabilistically sample the remainder. Document sampling rates so on-call engineers know expected trace completeness.

Common failure modes

  • Single-replica Collector — one pod crash loses telemetry; run HA gateway Collectors behind a service.
  • Missing resource attributes — traces without service.name are unfilterable in large estates.
  • Propagator mismatch — SDK configured for B3 while mesh injects W3C only; results in broken parent links.
  • 100% trace export — no tail sampling at high QPS overwhelms backends and budgets.
  • Sensitive baggage — tokens in baggage propagate to every downstream span and exporter.

Decision checklist

  • Are OTel SDKs or agents deployed on all new production services?
  • Is W3C Trace Context the default propagator for HTTP and gRPC?
  • Do Collectors run with HA, memory limits, and monitored export failures?
  • Are tail sampling rules documented and tested for error retention?
  • Do logs, metrics exemplars, and traces share OTel resource attributes?
  • Are semantic conventions used for standard operations instead of custom names?

Example use cases

  • Illustrative scenario — backend swap: A retailer moves observability from a hosted APM to Grafana Tempo and Mimir; squads change only Collector exporter stanzas while hundreds of microservices keep the same OTel bootstrap—migration weeks instead of re-instrumenting every repository.
  • Case study — CNCF OpenTelemetry: The OpenTracing and OpenCensus merger produced the neutral telemetry stack cloud vendors now document as the default onboarding path for new workloads.
  • Illustrative scenario — dual export: Security operations ingests a filtered OTLP stream of error spans into a SIEM while platform engineers browse tail-sampled traces in Tempo—one SDK emission, two governance-approved destinations configured in the gateway collector.
  • Illustrative scenario — cost-aware sampling: At tens of thousands of requests per second, engineers configure tail policies that retain all errors, retain slow traces above two seconds, and probabilistically sample routine traffic—trace storage spend drops roughly an order of magnitude while incident investigations still see failing paths.
