Structured Logging

Structured logging replaces free-text lines with schema-bound JSON events so teams can filter, alert, and pivot into traces—aligned with OpenTelemetry, Grafana Loki, and SRE-style incident workflows.

⏱ 10 min read

What it is

Structured logging is the practice of emitting each log record as a machine-parseable set of named fields—almost always one JSON object per line—rather than as free-form prose intended for human eyes only. A structured event carries a stable schema: severity, timestamp, service identity, human-readable message, error codes, duration, and domain identifiers such as order or tenant IDs. Compare an unstructured line like ERROR: payment failed for user after 3 retries with a structured record {"level":"error","message":"payment failed","retries":3,"trace_id":"4bf92f35","service":"checkout-api"}; the latter can be filtered, aggregated, and joined with traces without regular expressions.

Structured logging is the application-layer contract that makes logging architecture and log aggregation work. OpenTelemetry extends the contract by attaching trace context to log records so Grafana can move from a Prometheus latency panel to Tempo traces to Loki lines that share the same trace_id. Charity Majors argues that rich, wide events—not minimalist printf strings—are what make observability possible in production; structured fields are how you capture that width without drowning in text.

Why it exists

At scale, grep and regex parsing fail silently when developers change wording or add fields. Structured logging moves parsing to the edge—the application or a validated schema—so downstream systems (Loki LogQL, Elasticsearch KQL, SIEM rules, or Honeycomb-style analytics) operate on typed data. The Google SRE book treats useful logs as part of monitoring distributed systems: they must answer who, what, and when with fields tight enough to alert on, not essays that require a human transliterator during an outage.

Correlation across services is the other driver. When every hop logs the same request or trace identifier, investigators reconstruct async workflows without guessing time windows. Without structure, that correlation devolves into brittle string matching.

When to use

  • Every production service that participates in on-call, SLO measurement, or security monitoring.
  • Multi-step workflows spanning APIs, queues, and batch jobs that must share trace or business identifiers.
  • Compliance and audit pipelines that need predictable fields for retention, redaction, and access control.
  • Teams standardizing on OpenTelemetry logs export or Grafana Loki where labels stay low-cardinality and payload fields stay in the JSON body.

When not to use

  • Do not emit entire payloads, credentials, or personally identifiable information as structured fields without classification and redaction.
  • Do not invent unbounded keys per request (for example one field per user ID as a JSON property name); that is high cardinality in disguise and breaks indexing budgets in Loki and Elasticsearch alike.

Typical architecture

The application logger renders one JSON object per event, enriches it with OpenTelemetry trace context, and hands it to a collector that routes to durable storage.

Pros and cons

Pros

  • Indexed and label-scoped search in Loki or Elasticsearch is fast because filters target fields, not regex over raw text.
  • SIEM and compliance rules consume predictable JSON instead of fragile grok patterns.
  • Log-derived metrics—such as error counts by error_code—complement Prometheus counters without double-instrumenting every branch.
  • OpenTelemetry log bridges map the same fields to OTLP, keeping vendor portability alongside metrics and traces.

Cons

  • Schema drift across teams breaks dashboards unless you publish and enforce a common model (ECS, OTel conventions, or internal).
  • JSON lines are larger than minimal strings; volume grows unless levels and sampling are governed.
  • Without ergonomic libraries (zap, log4j2 JSON layout, pino, structlog), developers revert to string concatenation.
  • Structured fields make it easier to accidentally log secrets; governance must precede scale.

Implementation notes

Pick a schema and stick to it. Align field names with OpenTelemetry semantic conventions where possible (service.name, http.response.status_code, exception.type) so Grafana datasources map cleanly. Configure the logging framework to write JSON to stdout in UTC with a single newline per event—container platforms and Promtail expect that shape.

Inject trace_id and span_id via OpenTelemetry logging appenders or context variables, not ad-hoc thread locals. Use consistent level semantics: ERROR for operator action, WARN for recoverable anomalies, INFO for lifecycle events, DEBUG sampled in production. Add CI checks that critical paths include required fields, and cap log bytes per request so a bug cannot emit megabytes per call.

Common failure modes

  • JSON only in the message string: Wrapping JSON inside a msg field leaves pipelines blind; top-level keys must be real fields.
  • Dynamic keys: Logging {"user_12345":"failed"} explodes mappings; use user_id as a key and a scalar value.
  • Secrets and PII in structured fields: Typed data copies faster into indexes and SIEMs—mask before emit.
  • Clock skew: Non-UTC or unsynchronized clocks reorder events across nodes; always emit ISO-8601 UTC.

Decision checklist

  • Does every production service emit one JSON object per line to stdout?
  • Are OpenTelemetry trace and span identifiers on all request-scoped records?
  • Is the field schema documented and reviewed in code review?
  • Are sensitive attributes redacted or hashed at the logger?
  • Does each service have an agreed log volume budget and DEBUG sampling policy?
  • Does CI fail builds that omit required fields on payment, auth, or data-mutation paths?

Example use cases

  • Illustrative scenario — checkout API: A payment service logs error_code, provider, and trace_id; on-call filters Loki for errors during a Prometheus SLO burn and opens the matching Tempo trace.
  • Illustrative scenario — Go microservice: Uber zap production encoder writes JSON to stdout; Promtail ships to Grafana Loki with low-cardinality labels (app, env) and high-cardinality data in the line.
  • Case study — Honeycomb event model: Charity Majors advocates wide, structured events for exploratory debugging; structured logging in your own stack is the portable subset of that idea in Loki or Elasticsearch.
