Structured Logging

Emitting logs as machine-parseable key-value pairs for reliable search and correlation.

⏱ 10 min read

What it is

Example: {"level":"error","msg":"payment failed","order_id":"o-1","trace_id":"abc"} instead of a prose sentence.

Why it exists

Regex on plain logs breaks at scale. Structured fields power dashboards, alerts, and join with traces using shared correlation ids.

When to use

  • All production services.
  • Cross-service workflows needing join keys.
  • Security and audit pipelines.

When not to use

  • Logging entire payloads with secrets.
  • High-cardinality unique fields per line.

Typical architecture

Pros and cons

Pros

  • Fast indexed search.
  • Stable parsing in SIEM.
  • Easy metric derivation.
  • Works with OpenTelemetry logs.

Cons

  • Schema drift if ungoverned.
  • Larger bytes per event.
  • Developer friction without libraries.
  • PII fields need redaction.

Implementation notes

Adopt a schema (ECS or internal); provide SDK wrappers; lint in CI for required fields on critical paths.

Use log levels consistently; sample verbose debug in production.

Common failure modes

  • Stringly-typed JSON in message only.
  • Dynamic keys exploding mappings.
  • Logging PII without classification.
  • Clock skew breaking ordering.

Decision checklist

  • JSON logs to stdout?
  • trace_id on every request?
  • Schema documented?
  • PII redaction at source?
  • Log volume budgets per service?
  • CI checks for required fields?

Example use cases

  • Go: zap with production encoder.
  • Java: Logstash JSON layout.
  • Node: pino with serializers.
