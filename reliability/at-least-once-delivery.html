At-Least-Once Delivery

The messaging guarantee that every message will be delivered one or more times, accepting duplicates in exchange for no message loss.

⏱ 9 min read

What it is

At-least-once delivery is a messaging guarantee: every message will be delivered to a consumer one or more times, but never “lost” because the broker never saw a successful acknowledgement. If a consumer crashes after processing but before ACK, or the ACK is lost on the network, the broker redelivers. Duplicates are expected; correctness depends on idempotent handlers that recognise already-processed work.

Most production brokers default to at-least-once semantics when consumers acknowledge explicitly—Amazon SQS standard queues, RabbitMQ manual ACK, Kafka offset commits after processing. At-most-once trades away retries for simplicity; exactly-once adds infrastructure cost and tighter coupling. The common production compromise is at-least-once transport plus idempotent application logic.

Why it exists

Distributed messaging cannot distinguish “consumer never received” from “consumer processed but ACK never arrived” without expensive distributed transactions. To avoid silent loss, brokers must retry until they observe an ACK. That retry policy necessarily creates duplicate delivery whenever the first attempt succeeded but confirmation did not.

At-least-once accepts duplicates as the price of durability. Engineering effort shifts to consumer design: deduplication keys, unique constraints, outbox patterns, and visibility-timeout tuning so retries happen when work truly failed—not while work is still running.

When to use

  • Workflows where losing an event is unacceptable (money movement, inventory, notifications).
  • Systems that can implement or already implement idempotent consumption.
  • Kafka pipelines committing offsets after side effects with compensating dedup stores.
  • Event-carried state transfer where each event includes a stable identifier for deduplication.

When not to use

  • Operations that cannot be made idempotent and cannot tolerate even transient duplicates—consider exactly-once or synchronous workflows.
  • High-volume metrics or debug feeds where occasional loss is cheaper than ACK overhead—at-most-once may suffice.
  • Consumers that would corrupt state if a duplicate slipped past dedup for even milliseconds.

Typical architecture

The consumer commits business state with an idempotency key, then ACKs; redelivery after crash is absorbed by deduplication at the datastore layer.

Pros and cons

Pros

  • Strong protection against message loss under process and network failures.
  • Default in most brokers—little bespoke wire protocol work.
  • Clear separation: broker handles redelivery, app handles idempotency.
  • Avoids distributed transaction overhead of exactly-once infrastructure.
  • Failure modes are well understood and testable with fault injection.

Cons

  • Every consumer must implement deduplication—easy to forget on new handlers.
  • Visibility timeout and heartbeat tuning is error-prone for long tasks.
  • Dedup stores become critical dependencies with their own SLOs.
  • Duplicate side effects during races require careful transaction ordering.
  • Operational load from DLQs when poison messages exhaust retries.

Implementation notes

For SQS, set visibility timeout to roughly six times the p99 processing duration; call ChangeMessageVisibility for long tasks. Retain messages long enough to survive planned outages—often the maximum retention when in doubt. Pick dedup keys deliberately: SQS MessageId for standard queues, business ids when producers control identity, Kafka topic-partition-offset tuples when broker ids are insufficient.

Make “check dedup → apply effect → mark dedup” atomic where possible—database unique constraints plus ON CONFLICT DO NOTHING patterns, or transactional outbox with the same key. Test redelivery explicitly in integration suites: kill the consumer after write but before ACK and assert no duplicate charges. Pair with DLQs when maxReceiveCount exhausts on genuine failures.

Common failure modes

  • Short visibility timeout: parallel duplicate processing while the first attempt still runs.
  • Non-idempotent handlers: double inserts, duplicate emails, or repeated charges.
  • Dedup store outage: choose fail-closed vs fail-open explicitly—both have risk.
  • ACK-before-commit: message lost from queue though processing never durably stored.
  • No heartbeat for long jobs: broker assumes failure and redelivers mid-work.

Decision checklist

  • Is every handler safe under at-least-once redelivery?
  • Is visibility timeout sized to longest expected single-message work?
  • Is there a durable deduplication or uniqueness constraint on business keys?
  • Do integration tests simulate ACK loss and consumer crash?
  • Is the deduplication tier highly available and monitored?
  • Are DLQs configured for exhausted retries?

Example use cases

  • Illustrative scenario — order ingestion: INSERT INTO orders … ON CONFLICT (order_id) DO NOTHING absorbs SQS redelivery after deploy restarts.
  • Illustrative scenario — analytics: Bloom-filter dedup in Redis skips duplicate event UUIDs at millions of events per hour.
  • Illustrative scenario — email notify: A notifications_sent table keyed by (user_id, template_id) prevents duplicate sends on redelivery.

Related patterns

  • Exactly-Once Delivery — stronger broker-level guarantee with higher cost.
  • Idempotency — consumer-side requirement for safe at-least-once.
  • Dead Letter Queues — destination after retry exhaustion.
