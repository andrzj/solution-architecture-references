At-Least-Once Delivery

The messaging guarantee that every message will be delivered one or more times, accepting duplicates in exchange for no message loss.

⏱ 9 min read

What it is

At-least-once delivery is a messaging guarantee in which the broker commits to delivering a message to the consumer at least one time—but possibly more than once. If the broker does not receive a positive acknowledgement (ACK) from the consumer within a defined visibility timeout, it assumes the consumer failed and redelivers the message to another consumer or the same consumer on retry. Redelivery can happen multiple times in the presence of failures: network partitions, consumer crashes, slow processing that exceeds visibility timeout, or abnormal shutdown before the consumer sends its ACK.

At-least-once is the default delivery mode for most production-grade message brokers: SQS (standard), RabbitMQ with manual ACK, and Kafka with consumer offset management all implement at-least-once by default. At-most-once delivery (fire-and-forget) is simpler but loses messages on failure. Exactly-once delivery eliminates duplicates but is costly and bounded in scope. At-least-once is the pragmatic middle ground: no message loss, duplicates possible, consumer must be idempotent. Most production message-driven architectures operate on at-least-once delivery with idempotent consumers.

Why it exists

In a distributed system with unreliable networks and fallible processes, there is no way for a broker to know with certainty whether a consumer received, processed, and committed a message successfully without an acknowledgement. Network packets can be lost in either direction (delivery or ACK). Consumer processes can crash after processing but before sending ACK. To guarantee that no message is lost, the broker must retry delivery until it receives an ACK—which necessarily means it may redeliver messages that were actually processed successfully but whose ACK was lost.

At-least-once delivery accepts this tradeoff: it eliminates message loss at the cost of occasional duplicates. Engineering effort shifts to consumer design: deduplication keys, unique constraints, transactional outbox patterns, and visibility-timeout tuning so retries happen when work truly failed—not while work is still running on another worker.

When to use

  • Any system where message loss is unacceptable (orders, payments, notifications, state changes)—the default choice for reliable messaging.
  • Systems where consumer processing is or can be made idempotent—at-least-once plus idempotent consumer is the most common pattern in production systems.
  • Kafka-based pipelines where consumer offsets provide the at-least-once guarantee and transactional outbox or idempotency keys handle duplicate side effects.
  • Event-driven architectures where events drive downstream state updates and each event carries a stable event ID for deduplication.
  • Workflow orchestration and saga steps where compensating actions exist but losing the triggering event would leave durable state inconsistent.
  • Integration boundaries where upstream cannot replay history on demand and the broker is the system of record for in-flight work.

When not to use

  • When consumer operations are inherently non-idempotent and cannot be made idempotent—use exactly-once semantics or synchronous request–response within a certified boundary.
  • High-frequency telemetry, metrics, or analytics events where occasional loss is acceptable and the overhead of ACK is not worthwhile—use at-most-once.
  • When the consumer system cannot tolerate any duplicate data, even transient duplicates visible before deduplication catches them—requires exactly-once or synchronous deduplication at the consumer.

Typical architecture

The consumer commits business state with an idempotency key, then ACKs; redelivery after crash is absorbed by deduplication at the datastore layer.

Pros and cons

Pros

  • Guarantees no message loss—every message is eventually processed as long as consumers are available and retention has not expired.
  • Default and well-supported by all major message brokers—no special wire protocol work beyond explicit ACK semantics.
  • Simple to reason about: the broker handles reliability; the consumer handles idempotency.
  • No performance overhead of distributed transactions required by exactly-once semantics at the broker.
  • Well-understood failure modes—duplicate processing is predictable and testable with chaos and fault injection.

Cons

  • Requires all consumers to implement idempotency—a correctness requirement that must be maintained as the system evolves and new handlers are added.
  • Duplicate messages under normal operation are rare but not zero—systems must be tested for correct duplicate handling under failure conditions.
  • Visibility timeout tuning is critical: too short causes excessive redeliveries for slow consumers; too long means a failed consumer takes longer to recover.
  • Deduplication stores (used to track processed message IDs) must be highly available and fast, or they become a bottleneck and single point of failure.
  • Duplicate side effects during races between parallel redeliveries require careful transaction ordering and unique constraints.
  • Operational load from DLQs when poison messages exhaust retries—pairs with poison message handling discipline.

Implementation notes

For SQS, set the visibility timeout to 6× the expected maximum processing time for a single message. If processing takes up to 10 seconds, set visibility timeout to 60 seconds. Use ChangeMessageVisibility to extend the timeout for messages that require longer processing. Set message retention period long enough that a temporary consumer outage (deployment, incident) does not cause messages to expire before processing resumes—four days is the default; 14 days is the maximum when in doubt.

Implement idempotency in the consumer using a deduplication key stored in a Redis set, DynamoDB table, or relational DB unique constraint. For SQS standard queues, use the MessageId (UUID assigned by SQS) as the deduplication key when business identity is unknown. For SQS FIFO, use MessageDeduplicationId. For Kafka, use a combination of topic name, partition, and offset as a stable, globally unique message ID, or a business key when producers control identity.

Structure the deduplication check, business logic, and deduplication mark as an atomic unit where possible: database unique constraints plus ON CONFLICT DO NOTHING patterns avoid check-then-act races in concurrent consumer environments. Test redelivery explicitly in integration suites: kill the consumer after write but before ACK and assert no duplicate charges or notifications. Pair with DLQs when maxReceiveCount exhausts on genuine failures.

Kafka consumers: Commit offsets only after side effects are durable (or use transactional consume-process-produce with clear failure semantics). enable.auto.commit=true before processing is a common source of message loss under crash. For at-least-once, prefer manual commit after success; accept that a crash after commit but before finishing work may skip a message unless you reconcile—another reason idempotent handlers are the default SRE recommendation over chasing EOS everywhere.

Common failure modes

  • Visibility timeout too short: slow consumers time out repeatedly, causing the message to be redelivered to other consumers concurrently, leading to parallel duplicate processing that idempotency must handle correctly.
  • Non-idempotent consumer: the consumer applies side effects without a deduplication check, causing duplicates (double charges, duplicate inserts, duplicate notifications) when messages are redelivered.
  • Deduplication store unavailable: if the Redis deduplication store is down, the consumer either fails all processing (availability impact) or processes without deduplication (correctness risk)—choose fail-closed vs fail-open explicitly.
  • ACK lost but processing complete: consumer processed the message and committed results, but the ACK was lost (network issue), causing the broker to redeliver. Without idempotency, this causes a duplicate.
  • ACK-before-commit: consumer ACKs before durable write completes; message is deleted from queue though processing never durably stored—message loss masquerading as success.
  • Long processing with no heartbeat: consumer processes a complex message for 20 minutes but visibility timeout is 30 seconds—the broker redelivers to another consumer while the first attempt is still running.

Decision checklist

  • Is every consumer operation idempotent—safe to execute multiple times with the same result?
  • Is visibility timeout set to at least 6× the expected maximum per-message processing time?
  • Is there a deduplication mechanism (idempotency key plus DB constraint or deduplication store) in place?
  • Are duplicate scenarios tested in integration tests—not just happy path?
  • Is the deduplication store highly available and fast enough not to be a bottleneck?
  • Is there a DLQ configured for messages that exceed maxReceiveCount after genuine failures?
  • Is message retention set long enough to survive planned downtime (deployments, incidents)?
  • Do long-running handlers extend visibility or emit heartbeats so in-flight work is not double-scheduled?

Example use cases

  • Illustrative scenario — order ingestion: INSERT INTO orders … ON CONFLICT (order_id) DO NOTHING absorbs SQS redelivery after deploy restarts.
  • Illustrative scenario — analytics: Bloom-filter dedup in Redis skips duplicate event UUIDs at millions of events per hour.
  • Illustrative scenario — email notify: A notifications_sent table keyed by (user_id, template_id) prevents duplicate sends on redelivery.

Related patterns

  • Exactly-Once Delivery — stronger broker-level guarantee with higher cost.
  • Idempotency — consumer-side requirement for safe at-least-once.
  • Dead Letter Queues — destination after retry exhaustion.
