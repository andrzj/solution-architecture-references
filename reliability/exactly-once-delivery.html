Exactly-Once Delivery

Guaranteeing that a message is processed exactly one time — neither lost nor processed as a duplicate.

⏱ 11 min read

What it is

Exactly-once delivery is the strongest message delivery guarantee: a producer’s message is delivered to a consumer and its effects are applied to system state precisely one time, with no possibility of loss (at-least-once risk) or duplication (at-most-once risk). It is a compound guarantee comprising two properties: exactly-once delivery (the broker delivers the message exactly once end-to-end within a certified scope) and exactly-once processing (the consumer’s side effects are applied exactly once even if delivery or processing is retried due to failures).

True exactly-once delivery across arbitrary distributed systems is impossible under all failure models—the “exactly-once myth.” Production systems instead implement effectively-once behaviour within specific component boundaries: Kafka transactional read-process-write within topic boundaries, SQS FIFO deduplication for producer retries, Flink checkpointing with idempotent sinks, or Transactional Outbox for database-and-broker spans. The architectural decision is which boundary you certify and document, not whether magic exists outside it.

Why it exists

At-least-once is the pragmatic default for reliable messaging, but many operations are not safely repeatable: ledger postings, inventory decrements, entitlement grants, and fee assessments. Pushing deduplication entirely into every consumer works, yet teams repeatedly miss edge cases—concurrent redelivery, partial batch ACK, crash between write and ACK. Infrastructure-level exactly-once semantics (or broker-assisted deduplication) centralise correctness for the highest-risk paths so application code does not reimplement the same race-prone check in every handler.

When to use

  • Stateful stream processing where duplicate outputs corrupt aggregations, joins, or windowed totals.
  • Payment, billing, or ledger pipelines where a duplicate side effect has regulatory or monetary impact.
  • Order or inventory mutations tied to physical fulfilment where stock must not drift negative.
  • Bounded broker pairs that officially support coordinated commits (Kafka source→sink loops, FIFO queues with business-key deduplication).

When not to use

  • Operations that are naturally idempotent—prefer at-least-once plus a unique constraint or idempotency key; it is simpler and faster.
  • High-volume telemetry, metrics, or logs where duplicate samples are acceptable and transactional overhead hurts cost.
  • Spans that cross a relational database and a message broker without Outbox or 2PC—you cannot honestly claim exactly-once across that gap.
  • Brokers without native idempotent producers, transactions, or deduplication—the guarantee becomes bespoke application complexity with no platform help.

Typical architecture

Pick one certified boundary per pipeline: in-broker transactions for stream loops, broker deduplication for enqueue retries, or outbox plus idempotent consumers for DB-plus-queue flows.

Pros and cons

Pros

  • Eliminates duplicate processing without requiring each consumer to implement deduplication logic individually on certified paths.
  • Simplifies application code for operations where duplicate application would cause correctness or financial errors.
  • Kafka’s exactly-once semantics (EOS) provides auditable, transaction-scoped processing that can be replayed to a consistent point.
  • SQS FIFO deduplication integrates transparently at the broker level for producer retries within the deduplication window.
  • Documents an explicit correctness contract for downstream teams and SLO owners.

Cons

  • Significant performance overhead: Kafka EOS adds latency due to transactional coordination; SQS FIFO has lower throughput than standard queues.
  • Exactly-once semantics apply only within bounded components—a Kafka EOS producer cannot atomically commit to a database without transactional Outbox.
  • Complex failure recovery: transactional aborts must roll back writes atomically; partial failures leave inconsistent state if not handled correctly.
  • SQS FIFO deduplication is scoped to a five-minute window—duplicates outside this window still require idempotent consumers.
  • “Exactly-once” is a marketing term that must be examined carefully per broker—the scope and guarantees vary significantly across implementations.

Implementation notes

Kafka: Enable enable.idempotence=true, assign a unique transactional.id per producer instance, and use read_committed on consumers of transactional topics. Benchmark EOS on realistic batch sizes; 15–30% overhead is common. Prefer Kafka Streams or Flink EOS connectors instead of hand-rolled transaction lifecycle if possible.

SQS FIFO: Derive MessageDeduplicationId from a stable business key (payment ID, order ID), not random UUIDs per retry. Treat the deduplication window as producer-retry protection only; persist processed IDs in the consumer for longer horizons. Enable content-based deduplication only when message bodies are byte-identical for logical duplicates.

Database plus broker: Use Outbox or inbox patterns; never “write DB, then send message” without a shared commit. Consumers should use INSERT … ON CONFLICT DO NOTHING or a deduplication table keyed by message ID. Document the certified boundary in the service README and architecture diagram.

Default to at-least-once plus idempotent consumer for cross-system flows—EOS is expensive and bounded. Reserve Kafka transactions or FIFO deduplication for producer retry windows where duplicate publish is the primary risk. End-to-end “exactly once” across DB, API, and email still requires an application-level idempotency key and observable dedupe store, not broker configuration alone.

Common failure modes

  • Scope confusion: believing Kafka EOS guarantees atomicity with external databases—it only guarantees atomicity within the Kafka topic-to-topic scope.
  • Transactional ID reuse: multiple producer instances sharing the same transactional.id causes epoch conflicts and broker fencing of one producer.
  • read_committed omitted: consumers using read_uncommitted (the default on some clients) read messages from aborted transactions, causing exactly-not-once processing.
  • SQS FIFO throughput limits: FIFO queues have lower per-queue throughput than standard queues—using FIFO for high-throughput paths causes throttling.
  • Relying on five-minute window only: treating the SQS FIFO deduplication window as a permanent guarantee without implementing idempotent consumers for the broader case.
  • Dual writes: database commit succeeds while publish fails (or the reverse)—classic split-brain without transactional Outbox.

Decision checklist

  • Is the operation genuinely non-idempotent and would duplicates cause correctness errors or financial harm?
  • Is the scope of exactly-once bounded to a component pair that supports it (Kafka-to-Kafka, SQS FIFO-to-consumer)?
  • Have you benchmarked the performance overhead of transactional production and confirmed it is acceptable?
  • For Kafka EOS: is isolation.level=read_committed set on all consumers of the output topic?
  • For SQS FIFO: is the deduplication ID deterministic and collision-resistant for the message business key?
  • For operations spanning message broker plus database: is the transactional Outbox pattern being used instead of naked dual writes?
  • Are integration tests exercising redelivery, transactional abort, and producer retry—not only happy path?
  • Is the exactly-once boundary documented so future developers understand its scope and limitations?

Example use cases

  • Illustrative scenario — Northwind routes settlement events through Kafka EOS so each payment ID updates the rolling balance once across restarts; external ledger export still uses Outbox because it crosses JDBC.
  • Illustrative scenario — A checkout API retries enqueue to SQS FIFO with MessageDeduplicationId=order_id; fulfilment workers idempotently insert orders so late redeliveries noop.
  • Case study — Confluent’s Kafka transactions design (see Confluent blog on transactions) documents how idempotent producers and transactional commits bound duplicates inside the broker.
  • Case study — Stream processors such as Apache Flink combine checkpointing with exactly-once sinks for fault-tolerant analytics pipelines—documented in Flink’s delivery semantics guides.

Related patterns

  • At-Least-Once Delivery — the substrate; exactly-once adds coordination or deduplication.
  • Idempotency — still required at boundaries EOS cannot certify.
  • Transactional Outbox — effectively-once across database and broker.
  • Poison Message Handling — duplicates and poison messages interact in DLQ design.
