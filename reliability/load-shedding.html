Load Shedding

Intentionally dropping low-priority requests under overload to preserve capacity for critical workloads.

⏱ 10 min read

What it is

Load shedding is intentional overload protection: when a service measures that it is at or beyond safe capacity, it refuses some incoming work immediately instead of accepting everything and collapsing. Refusals are usually fast errors (often HTTP 503 with Retry-After) so threads, memory, and connection pools stay available for higher-priority traffic. Shedding is a server-side admission decision based on global health, distinct from per-client rate limits that police fairness.

Effective shedding requires classifying work by priority, watching multiple saturation signals, and cooperating with clients that backoff when told. The goal is not zero errors—it is preventing total failure where every request times out and no critical path succeeds. Shedding complements per-client rate limiting: rate limits enforce fairness; shedding protects the fleet when aggregate demand exceeds safe capacity.

Why it exists

Under overload, systems that accept unbounded work build queues. Latency rises for all callers, retries amplify load, and eventually the process OOMs or the kernel thrashes. High-priority transactions (payments, auth, health checks) wait behind bulk exports or analytics traffic unless something actively refuses low-value work.

A system that accepts every request under overload will queue them, consuming memory, threads, and CPU for work that may time out before completion. As the queue grows, latency for all requests increases—including high-priority ones—until the fleet enters collapse: fully occupied timing out low-value work while critical requests cannot get service at all.

Shedding converts uncontrolled meltdown into a controlled trade-off: some callers receive explicit “try later” signals while the service preserves correct behaviour and SLOs for the workloads that matter most. It is a last-resort layer after autoscaling and queueing have been exhausted or cannot react quickly enough.

Google’s SRE guidance on handling overload treats shedding as a deliberate product decision: you choose which traffic to sacrifice so survival traffic keeps meeting its SLO. Without that choice, retry storms and queue growth can take down otherwise healthy tiers.

When to use

  • User-facing APIs with mixed criticality (reads versus batch, premium versus free tenants, checkout versus analytics).
  • Burst-prone systems where horizontal scale lags demand (viral events, flash sales, coordinated traffic spikes, DDoS).
  • Shared pools where background jobs, exports, and webhooks compete with synchronous user traffic on the same fleet.
  • Services where a partial error rate is acceptable if core journeys keep succeeding and stakeholders understand the trade-off.
  • Gateways or meshes that can classify requests from path, header, JWT claims, or tenant metadata before work reaches application threads.
  • Microservices behind a BFF where the BFF can shed optional aggregation calls while preserving thin critical endpoints.

When not to use

  • When every request is equally critical and no priority order exists—fix capacity or partition workloads instead.
  • When clients cannot honour 503/backoff and will retry-storm the service harder.
  • When queueing with SLA-aware delay delivers better UX than hard failure (and backlog is bounded).
  • When shedding would mask chronic under-provisioning—shed counters should drive capacity fixes, not permanent high refusal rates.
  • Single-tenant dedicated capacity where every request is P0 and isolation is already guaranteed by partitioning.

Typical architecture

Admission control at the edge classifies priority, compares load signals to thresholds, and admits or rejects before work reaches application threads.

Pros and cons

Pros

  • Protects tail latency and success rate for prioritized traffic during spikes instead of universal timeouts.
  • Surfaces overload explicitly—HTTP 503 with Retry-After semantics are machine-actionable for well-behaved clients.
  • Cheaper than runaway retry loops that amplify outages across tiers and dependent services.
  • Composable with autoscaling: shed while scale-out catches up without melting the current fleet.
  • Metrics on shed volume per priority explain incident impact to stakeholders and product owners.
  • Bounds memory and thread usage—rejected work never enters the application queue.

Cons

  • Users and partners still see errors—product and comms planning required.
  • Priority taxonomies decay as new endpoints ship without labels.
  • Wrong thresholds cause chronic over- or under-shedding.
  • Naive clients ignore Retry-After and worsen overload.
  • Does not replace right-sizing, caching, or bulkhead isolation.

Implementation notes

Combine signals: queue depth and in-flight counts often lead CPU for I/O-bound services. Use hysteresis—open shedding at 85% saturation, close at 70%—to stop flapping. Implement admission at the API gateway, service mesh, or a sidecar so classification uses stable metadata (route, JWT claim, tenant tier) before requests acquire locks or database connections.

Define an explicit priority matrix with product and SRE sign-off, then encode it in configuration rather than ad hoc incident toggles. Revisit the matrix when new endpoints ship—unlabeled routes default to low priority and get shed first unless you fix the taxonomy.

Return consistent refusal bodies: HTTP 503, meaningful Retry-After, and optional headers such as X-Reason: load-shedding for client telemetry. Emit counters per priority tier and alert when P0 shed count is non-zero—that usually indicates misconfiguration or a true hard limit. Load-test shedding paths: clients must parse 503 and jitter retries; document behaviour in public API guides and SDK defaults.

During incidents, coordinate shedding with graceful degradation and circuit breakers: shedding refuses work at the edge; degradation trims features for admitted requests; breakers stop callers from hammering unhealthy downstreams.

Common failure modes

  • Wrong priority mapping: checkout labelled P2 while marketing pixels are P0.
  • Retry storms: mobile or partner SDKs retry immediately without backoff.
  • Single-metric triggers: CPU low while every thread blocks on a slow database.
  • Missing Retry-After: clients pick arbitrary delays and re-hit overload.
  • Shedding without observability: incidents look like mysterious 5xx with no priority breakdown.
  • Chronic shedding as capacity plan: refusal rate stays high because autoscaling or right-sizing never catches up—shedding hides under-provisioning.

Decision checklist

  • Is every route or tenant mapped to an explicit priority tier?
  • Do shedding rules use multiple load signals with hysteresis?
  • Do 503 responses include Retry-After and structured reason headers?
  • Are shed and admitted requests metered separately in dashboards?
  • Have representative clients been tested for cooperative backoff?
  • Is shedding disabled or relaxed automatically when load returns below close threshold?

Example use cases

  • Case study — Google: Production systems described in the SRE book shed non-critical background work to protect user-facing search under extreme load.
  • Illustrative scenario — API gateway: Webhook delivery (P3) and CSV exports (P2) receive 503 while synchronous JSON APIs (P1) and payment callbacks (P0) continue.
  • Illustrative scenario — stream processing: A consumer pauses analytics partition consumption during payment backlog while keeping fraud-scoring partitions fully staffed.
  • Illustrative scenario — flash sale: Read-only catalogue endpoints stay admitted at 90% CPU while write-heavy wishlist sync and recommendation prefetch receive 503 with five-second Retry-After.

Related patterns

  • Graceful Degradation — reduces features instead of rejecting requests.
  • Bulkhead Pattern — pre-partitions capacity so shedding is less needed.
  • Circuit Breaker — client-side fail-fast; shedding is server-side admission.
