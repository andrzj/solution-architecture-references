Reliability & Resilience Resilience

Fallback Pattern

Providing a degraded but functional alternative when the primary path fails.

⏱ 8 min read

What it is

The Fallback pattern defines an alternate response path when the primary path cannot complete successfully—because of exceptions, timeouts, an open circuit breaker, or bulkhead rejection. The fallback does not repair the dependency; it returns a degraded but useful outcome: cached data, a static default, a simplified computation, or an explicit empty result the UI can render.

Azure resilience guidance treats fallback as the completion step of retry and circuit-breaker chains. Resilience4j registers fallback methods on decorated callables; Polly uses FallbackAsync policies. The fallback must be fast, local, and ideally side-effect-free—a fallback that performs another unreliable network call deepens the failure tree Nygard warns about in Release It!

Graceful degradation is the product philosophy; fallback is the implementation hook at the call site. Google’s SRE framing favors measurable user-visible availability: partial pages beat hard 500s when non-critical features fail.

Why it exists

Users tolerate missing recommendations or stale catalog snippets more than complete request failure. Designing fallbacks forces teams to classify features by criticality during architecture, not only during outages. When breakers open or budgets burn, fallbacks keep core journeys working while dependencies recover.

Fallback activation rate is also a leading indicator: sustained elevation means the primary path or its SLO needs engineering attention, not wider fallback coverage.

When to use

  • Non-critical enrichments (recommendations, social proof, secondary pricing).
  • Read paths where slightly stale cache is acceptable with disclosed or bounded TTL.
  • Secondary data sources or precomputed defaults (static shipping rate, “popular items” list).
  • Any path already protected by circuit breaker or bulkhead—define what happens when those trip.
  • Feature flags and config with safe defaults when control plane is unreachable.

When not to use

  • Writes where silent drop equals data loss—fail explicitly or queue for later replay.
  • Security decisions—never default to “allow” when authz service is down.
  • Fallback chains that call additional remote services without their own breakers/timeouts.
  • Substitute for fixing chronic primary-path unreliability when activation rate is routinely high.

Typical architecture

Fallback executes synchronously at the call site; each step must stay within remaining latency budget.

Pros and cons

Pros

  • Converts hard outages into partial functionality—protects top-line SLOs.
  • Forces explicit criticality decisions at design time.
  • Works naturally with circuit breakers and bulkheads.
  • Cache-backed fallbacks can improve steady-state latency.
  • Improves incident UX while primary dependency recovers.

Cons

  • Stale or wrong defaults can mislead users (inventory, pricing, permissions).
  • Extra code paths require testing and maintenance.
  • High activation rates can hide dependency neglect.
  • Deep fallback chains become hard to reason about in postmortems.

Implementation notes

Define staleness TTL per cached fallback—permissions and prices need tighter bounds than marketing tiles. Include metadata (stale=true, cached_at) for API consumers and UIs that must disclose freshness.

Instrument fallback_activations_total labeled by dependency and reason (timeout, breaker, bulkhead). Log exception type on activation for RCA. Polly and Resilience4j callbacks make this straightforward.

Keep fallbacks O(1) local: in-memory defaults, local cache, preloaded static assets. If a secondary remote read is unavoidable, give it a aggressive timeout and its own breaker. AWS Builders Library narratives on resilient APIs often assume cache-first read models specifically to enable fallback.

Common failure modes

  • Network fallback — second dependency fails; user still sees error after double latency.
  • Unbounded staleness — cache never expires; users act on wrong data.
  • Silent activation — no metrics; dependency degraded for days unnoticed.
  • Fallback on writes — appears success while data never persisted.
  • Unsafe security defaults — open circuit implies open access.

Decision checklist

  • Is there a documented fallback for every breaker-protected call?
  • Is the fallback free of required remote calls?
  • Are TTL and staleness rules defined per data class?
  • Are activation metrics and alerts configured?
  • Are write paths excluded or using explicit async recovery instead of silent fallback?
  • Fallback behavior covered in chaos or game-day exercises?

Example use cases

  • Illustrative scenario — product page: Recommendation service fails; API serves Redis-cached last results, then static popular products, then empty carousel with copy—page still loads.
  • Illustrative scenario — shipping quote: Carrier API times out; checkout uses configured flat-rate fallback with banner that final rate may adjust.
  • Illustrative scenario — feature flags: Control plane unreachable; SDK serves last-known flags from disk with safe defaults for kill-switch features.
