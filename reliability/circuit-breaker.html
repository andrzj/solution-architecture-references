Reliability & Resilience Essential

Circuit Breaker

Stopping calls to a failing dependency after a threshold to prevent cascading failures and allow recovery.

⏱ 11 min read

What it is

A circuit breaker is a call-site guard that tracks recent outcomes to a dependency and, when failure or slowness crosses a threshold, stops calling that dependency for a cooling-off period. While open, requests fail fast (or invoke a fallback) without waiting for network timeouts. After waitDurationInOpenState, a limited number of half-open probe calls test recovery; success closes the circuit, failure reopens it.

Michael Nygard introduced the pattern in Release It! as the software analogue of an electrical breaker: remove load from a failing subsystem so it can recover and so callers do not drown in blocked threads. Martin Fowler’s summary and Azure’s circuit-breaker pattern document the same three states—Closed, Open, Half-Open. Resilience4j and Polly provide production implementations with sliding windows, slow-call detection, and metrics hooks.

Retries assume the next attempt might succeed; breakers assume the dependency is unhealthy now and continued calls harm both sides. In a resilience stack, retries handle blips; breakers handle sustained degradation and cascading failure.

Why it exists

Without fast failure, each call to a sick dependency holds a thread, connection, or servlet until timeout. Under load, the caller’s pool fills with blocked operations that are not doing useful work—classic cascading failure. Google’s SRE guidance on overload emphasizes failing quickly and shedding work; an open breaker is application-level load shedding targeted at one dependency.

Breakers also protect the downstream: zero new traffic during open state is often what allows a overloaded database or third-party API to drain queues and recover. Pairing breakers with fallbacks preserves partial user experience while the dependency heals.

When to use

  • Remote dependencies (HTTP, gRPC, DB, cache, SaaS APIs) where timeouts would otherwise consume shared pools.
  • High fan-out services where even a low single-digit error rate can exhaust threads at scale.
  • When a defined fallback or degraded response exists for open-circuit periods.
  • Per-dependency configuration—never one global breaker for all outbound calls.
  • Together with explicit client timeouts and retry caps (breaker observes aggregated outcomes after retries).

When not to use

  • Very low traffic where sliding windows lack statistical signal—false opens from single errors.
  • In-process calls with no resource contention—breaker overhead exceeds benefit.
  • When any failure must propagate immediately with no alternate path (rare, critical writes).
  • As a substitute for fixing chronic dependency performance—chronic open state is an incident, not a steady state.

Typical architecture

State machine implemented at the client or sidecar; metrics should expose current state per dependency.

Pros and cons

Pros

  • Fails fast—preserves caller threads and connection pools.
  • Reduces load on failing dependencies during recovery.
  • Explicit signal for monitoring and incident response (state gauge per dependency).
  • Enables predictable fallback activation at the call site.
  • Supported in Resilience4j, Polly, Envoy/Istio outlier detection, Azure guidance.

Cons

  • Threshold tuning is workload-specific; false opens degrade availability.
  • Half-open probes may not represent full production traffic mix.
  • Without fallback, open circuit is still user-visible failure—just faster.
  • Operational burden: per-dependency policies, dashboards, and runbooks.
  • Slow-call detection needed—200 OK at 30s is still a breaker trip candidate.

Implementation notes

Configure one breaker instance per downstream dependency. Resilience4j supports count- and time-based sliding windows, failureRateThreshold, slowCallRateThreshold, and slowCallDurationThreshold. Polly’s circuit breaker exposes similar thresholds with onBreak/onReset callbacks.

Decoration order: timeout → retry (bounded) → circuit breaker → bulkhead → primary call; fallback executes when breaker is open or call fails. Export state transitions to metrics (Prometheus circuitbreaker_state) and alert on open events—they are symptom alerts worth a runbook link.

Service meshes (Envoy outlier detection, Istio destination rules) can enforce outlier ejection without app code; align app-level breakers with mesh policy so behavior is explainable. AWS Builders Library articles on avoiding overload often assume breakers or equivalents at the edge of synchronous call graphs.

Common failure modes

  • Shared breaker across dependencies — one bad service blocks calls to healthy services.
  • Threshold too aggressive — brief spikes open circuit unnecessarily.
  • No slow-call rule — dependency “succeeds” but is effectively unavailable.
  • No fallback — users see hard errors with no degraded path.
  • Unmonitored open state — silent partial outage for hours.

Decision checklist

  • Separate breaker per downstream dependency?
  • Failure-rate and slow-call thresholds both configured?
  • Fallback defined and tested for open state?
  • Client timeouts set below breaker’s slow-call threshold where appropriate?
  • Metrics and alerts on state transitions?
  • Half-open probe count and open-state wait duration tuned for dependency recovery time?
  • Retry policy bounded so breaker sees representative failure signal?

Example use cases

  • Illustrative scenario — checkout: Payment gateway latency spikes; breaker opens after slow-call threshold; checkout completes with “pay later” queue using cached cart state.
  • Illustrative scenario — recommendations: ML service errors exceed 50% in a ten-call window; breaker opens; product page loads with an empty recommendations block from fallback cache.
  • Case study — service mesh: Envoy outlier detection ejects unhealthy endpoints from load balancing, analogous to half-open probing at the data plane.

Related patterns

  • Retry Pattern — handles transients before breaker trips.
  • Fallback Pattern — response path when circuit is open.
  • Bulkhead Pattern — limits concurrent calls so timeouts cannot fill one shared pool.
  • Exponential Backoff — spacing between retries under closed circuit.
