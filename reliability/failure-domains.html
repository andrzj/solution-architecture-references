Reliability & Resilience Architecture

Failure Domains

Architectural boundaries that contain the blast radius of failures, preventing faults in one domain from propagating to others.

⏱ 10 min read

What it is

A failure domain is a set of components that share a single underlying failure mode—when one member fails for that reason, peers in the same domain are likely to fail too. Components in different domains should be isolated by hardware, network, software process, or dependency boundaries so one fault cannot take everything down. Failure domain analysis maps those groupings and deliberately sizes blast radius: a bad deploy, AZ outage, or shared dependency crash should degrade a bounded fraction of capacity or tenants, not the whole platform.

Domains nest: rack, AZ, region, Kubernetes node, deployment cell, microservice, database primary, shared cache cluster. Architecture succeeds when the domain you design for (e.g. “single AZ loss”) matches real shared fate—not when services merely spread replicas without eliminating shared databases, NAT gateways, or config stores that collapse isolation.

A shared dependency (central auth, one Redis cluster, one feature-flag backend) can unintentionally merge many services into one domain even when compute is spread across AZs. SRE blast-radius planning and Principles of Chaos both assume you can name the domain under test before injecting a fault—if you cannot articulate “what fails together,” experiments and SLO math lack a denominator for impact fraction.

Why it exists

Without explicit domains, correlated failures dominate incident history: one Redis cluster, one auth service, one bad flag, one NAT—all become global outages. Domain design aligns impact with failure size: lose one AZ → ~1/N capacity; lose one cell → that tenant slice only; lose one canary → 5% of traffic. The system should degrade in proportion to the scope of the failure rather than failing completely for any fault at any layer.

SLO math, chaos experiments, and deployment strategy all depend on knowing which components share fate. Achievable availability is bounded by the worst single-domain impact on the user journey—treating components as independent when they share a database overstates reliability.

It also forces trade-offs into the open: per-service databases and per-AZ NAT gateways cost more but remove hidden single points. Documented domains make those costs accountable to availability targets and error-budget discussions instead of surprises during postmortems.

When to use

  • Any production system with availability or recovery objectives—not optional for multi-AZ or multi-region designs.
  • When designing multi-AZ or multi-region topologies—boundaries must be real isolation, not labels on the same shared resource.
  • Before adopting shared infrastructure (one broker, one cache, one config server) for many services.
  • When defining SLOs, error budgets, and incident severity—impact fractions come from domain maps.
  • When scoping chaos experiments and GameDays—fault injection should respect domain edges per Principles of Chaos.
  • When planning cell-based or sharded architectures for highest-criticality paths.

When not to use

  • Depth should match criticality—internal sandboxes may accept a single domain with simple ops.
  • Over-sharding tiny systems creates cost and complexity without measurable availability gain.
  • Domain maps that are never updated become dangerous fiction—skip only if you will not maintain them.
  • Early-stage prototypes where any outage is acceptable and team size cannot sustain cell operations yet.

Typical architecture

Model region → AZ → compute; mark shared dependencies that span domains and break isolation unless mitigated. For each shared node in the diagram, record expected user impact fraction if that node fails 100%—that number feeds chaos hypotheses (“losing AZ 1b drops 33% capacity but checkout SLO holds”) and incident severity runbooks.

Pros and cons

Pros

  • Caps maximum blast radius for deploys, hardware, and dependency failures.
  • Makes SLO and capacity-loss calculations explicit (1 of N AZs, 1 of M cells).
  • Supports graceful degradation and bulkheads aligned to real shared fate.
  • Enables canary and cell deploys that limit bad release impact.
  • Guides chaos experiments toward realistic, bounded faults aligned with Principles of Chaos.
  • Supports independent deploy and rollback within a cell or AZ slice.

Cons

  • Strong isolation increases cost—more gateways, databases, and redundancy.
  • Cross-domain workflows add latency and operational complexity.
  • Hidden dependencies erode domains unless architecture reviews repeat.
  • Cell or shard sprawl can overcomplicate small teams without platform support.
  • Cross-AZ reads and distributed transactions fight data locality—isolation and consistency trade off.

Implementation notes

Draw a dependency graph and highlight every shared node (database, cache, broker, identity provider, feature-flag SDK backend). For each shared node, list dependents and ask: “If this fails 100%, what fraction of users or revenue is down?” Mitigate with per-service data stores, circuit breakers, local caches, multi-AZ replicas, or queue isolation.

Use one NAT gateway per AZ; distribute load balancer nodes across AZs; run config and secrets services highly available with client-side cache and TTL. Spread Kubernetes workloads with topology spread constraints and anti-affinity so a single node or rack does not host all replicas of a critical Deployment. For top-tier services, consider cells: partition tenants or geography into stacks with no shared mutable state between cells—Stripe-style payment cells are the reference pattern. Stagger deploys across cells; never push one revision to all cells simultaneously without a prior canary cell.

Revisit domain maps in architecture reviews when teams add dependencies—new gRPC calls, shared caches, or global config flags erode boundaries silently. Pair with Bulkhead and Circuit Breaker at domain crossings so faults do not propagate across boundaries. Chaos experiments should target one domain at a time and compare observed impact to the predicted fraction on the map.

DR tiers and objectives: Document RPO (max acceptable data loss window) and RTO (time to restore service) per product tier. AWS’s disaster-recovery whitepaper maps patterns to cost: backup and restore (highest RTO), pilot light (minimal warm footprint), warm standby (scaled-down duplicate), and active-active (multi-region traffic with conflict handling). Multi-AZ within one region is a failure domain, not a DR strategy for regional loss—state replication and traffic routing must match the chosen tier.

AZ, region, cell: An Availability Zone is one failure domain within a region—design for roughly 1/N capacity loss when one AZ fails. A region loss requires DR traffic routing and data promotion. A cell is an application partition (tenant shard, metro stack) with its own data plane—failure should strand only that cell’s users, not the global fleet.

Shuffle sharding: AWS Builders Library describes assigning workloads to pseudo-random subsets of resources (for example DNS resolver subsets) so a bad shard affects a fraction of customers, not everyone sharing one pool. Apply the same idea to broker partitions, cache namespaces, and deployment cells.

Static stability: Prefer pre-provisioned multi-AZ capacity over aggressive scale-from-zero during incidents—autoscaling while impaired can amplify timeouts. AWS’s static-stability guidance keeps enough warm instances in each AZ so shedding and failover have headroom without waiting for cold start.

Common failure modes

  • Shared database: “microservices” that still share one primary DB.
  • Single-AZ choke points: NAT, DNS, or control plane in one AZ only.
  • Big-bang deploy: one revision to every cell before validation.
  • Implicit shared state: same cache namespace or table across services.
  • Global control plane outage: one regional config store takes all regions when mis-scoped.
  • Paper multi-AZ: replicas exist but traffic or data still single-AZ.
  • Stale domain map: diagram says isolation; production shares a broker added last quarter.

Decision checklist

  • Failure domain diagram reviewed with every new shared dependency?
  • Single-AZ loss bounded to ~1/N capacity for N balanced AZs?
  • Shared dependencies multi-AZ or protected with breakers and local fallback?
  • NAT, LB, and config paths verified per-AZ—not single-AZ hidden SPOFs?
  • Deploy pipeline staggers cells or AZs; canary precedes full promotion?
  • SLO calculations include correlated failure modes, not independent component math only?
  • Error-budget policy defines when domain isolation work is mandatory versus deferred?
  • Chaos experiments target one domain at a time with documented expected impact fraction?
  • Post-incident updates refresh the domain map when new shared fate is discovered?

Example use cases

  • Illustrative scenario — RideRelay maps ride-matching cells by metro; a bad config in one cell strands 8% of trips while others operate—rollback scope is the cell deployment, not global.
  • Illustrative scenario — Five services share one Redis cluster; failure domain review gives each service a dedicated namespace and breaker; a memory pressure event affects one vertical instead of all checkout paths.
  • Illustrative scenario — Chaos GameDay impairs one AZ; measured checkout success drops 31% versus predicted 33%—domain map validated, SLO holds on remaining AZs.
  • Case study — AWS fault isolation whitepaper describes region and AZ boundaries and how managed services contain blast radius within partitions.
  • Case study — Stripe and similar payment platforms publicly describe cell-based architectures that shard merchants into isolated stacks for blast-radius control.
  • Case study — Google SRE guidance on managing incidents emphasises limiting scope early—failure-domain maps are the architectural input for that scoping decision.

Related patterns

  • Bulkhead Pattern — concurrency isolation inside a service.
  • Circuit Breaker — protects calls across domain boundaries.
  • Chaos Engineering — validates domain assumptions under fault.
  • Self-Healing Systems — recovery scoped within each domain.
