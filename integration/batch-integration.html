Batch Integration

Batch integration runs extract-transform-load work on a schedule or trigger, processing bounded datasets with checkpoints and predictable cost—when freshness can wait minutes to days.

⏱ 10 min read

What it is

Batch integration moves or transforms data in discrete, scheduled bulk runs rather than record-by-record in real time. A job collects a defined window—all orders in the last 24 hours, all changes since the prior watermark, every file in a landing prefix—and processes the dataset in sequence before writing results to a destination. Windows are defined by clock time (nightly at 01:00 UTC), volume (every 10,000 records), or external event (object-store notification when a partner file lands).

Core frameworks include Spring Batch (chunk-oriented Java processing with a persistent JobRepository, restart, and retry), Apache Spark for distributed transforms, AWS Glue (managed serverless Spark with visual pipeline design), Azure Data Factory (orchestration across 90+ connectors), and cron-driven SQL or shell scripts. Microbatching—jobs every 5–60 seconds—narrows the latency gap toward streaming without stateful event-time semantics.

Why it exists

Many workloads are inherently periodic: payroll once a week, regulatory filings monthly, ML retraining nightly on accumulated history. Real-time streaming adds stateful processing, exactly-once contracts, and watermark tuning that is unnecessary when the business accepts hourly or daily freshness.

Batch is also more efficient for bulk SQL inserts, sorted aggregations, and columnar file writes—large datasets processed in memory beat row-at-a-time streaming for throughput. Batch integration supports reconciliation and audit: a nightly compare between OLTP and warehouse snapshots surfaces discrepancies that continuous replication might hide after reordering or partial failures. The determinism of a named window—“records created between 00:00 and 23:59 UTC on a given date”—simplifies reasoning about completeness.

When to use

  • Nightly data warehouse ETL/ELT loads where sub-hourly freshness is not required and bulk columnar writes are most efficient.
  • Regulatory and compliance reports submitted daily or monthly that must be reproducible for a specific time window.
  • ML feature engineering that scans and transforms large historical datasets once per run.
  • End-of-day settlement, ledger reconciliation, or billing that must process the complete closed period as one logical operation.
  • Bulk migrations between databases, file formats, or storage tiers where the entire corpus is scanned intentionally.
  • Destinations with bulk-load APIs or maintenance windows where batching is far cheaper than row-by-row streaming.

When not to use

  • When business requirements demand freshness under one minute—streaming integration or synchronous APIs fit better.
  • Event-driven triggers where work must start immediately after a domain event (payment notification cannot wait for the next cron).
  • Steady low volume (for example ~100 rows per day) where scheduler and job-repository overhead exceeds a simple CDC stream or API push.
  • When failure recovery is extremely time-sensitive—a job that processes eight hours of data may need hours to replay after an outage.

Typical architecture

A scheduler or object-store event starts the job; orchestration tracks dependencies, upstream freshness, and SLA deadlines. Extract reads a bounded slice from databases, APIs, or files—often via replica or watermark—then transform validates, enriches, and aggregates in chunks sized to memory and transaction limits. Load writes with bulk APIs, MERGE/upsert, or partitioned file outputs so retries do not duplicate rows. Job metadata (status, checkpoint, skip counts, duration) lives in a JobRepository or control table so operators can restart failed steps without reprocessing completed chunks.

Pros and cons

Pros

  • High throughput: bulk COPY, JDBC batch inserts, and Parquet writes vastly outperform row-by-row streaming on large slices.
  • Simpler mental model: a job processes a well-defined window deterministically—no late-event or watermark tuning.
  • Checkpoint/restart: Spring Batch and similar frameworks persist step state so failed jobs resume from the last committed chunk.
  • Lower infrastructure cost: compute runs on demand during the processing window instead of always-on streaming clusters.
  • Audit and compliance: a batch produces a complete, reproducible snapshot of a time window for regulators and finance.

Cons

  • High latency: data is only as fresh as the schedule—a daily job means up to 24 hours of staleness.
  • Resource spikes: large jobs stress shared OLTP, networks, and warehouses during the run window.
  • Partial failure handling: mid-run failures force choices between checkpoint resume, full replay, or compensating partial writes.
  • Long recovery: re-running a multi-hour job after failure extends data delay and may breach SLAs.
  • Scheduled bottleneck: downstream DAGs queue behind a single “nightly complete” gate with no incremental fallback.

Implementation notes

Spring Batch’s chunk model—read N items, process N, write N inside a transaction, commit, repeat—provides natural checkpoints. Persist JobRepository state to a relational database so jobs restart from the last committed chunk after failure. Tune chunk size to memory and transaction overhead: 1,000–10,000 rows is typical for JDBC destinations; 50,000+ for object-store writes where each put has higher fixed cost. For AWS Glue, use job bookmarks to track processed S3 prefixes or DynamoDB segments and avoid manual checkpoint files on incremental runs.

Extract from read replicas or incremental watermarks (updated_at, binlog position, CDC offsets) rather than full-table scans on OLTP primaries during peak hours. Cap concurrent instances of the same logical job so a slow run cannot overlap the next cron trigger. Orchestrate with Apache Airflow or AWS EventBridge Scheduler: model DAG dependencies, SLA sensors, and alerts on duration, rows processed, and skip counts—not only exit code.

For microbatching, Spark Structured Streaming’s Trigger.Once() or Trigger.AvailableNow() drains available data as one batch and exits—batch throughput with near-streaming freshness when a scheduler fires every minute. Define skip limits and error thresholds: a SUCCESS status with 15% skipped records is a data-quality incident, not a green dashboard.

Document each job’s input window, expected row counts, and idempotency guarantees in an internal runbook. Rehearse disaster recovery: restore checkpoints from backup, replay with compensating deletes, and verify downstream consumers tolerate at-least-once delivery during planned recovery drills.

Define processing windows and financial cut-off times explicitly—jobs that miss midnight close need documented grace or manual reconciliation. Replays should overwrite partitions by business key or use merge semantics so a second run does not duplicate facts. Late-arriving rows belong in a supplemental batch or sliding watermark, not silent drops. Spring Batch, Glue bookmarks, and Flink savepoints each give checkpoint/restart; persist execution metadata in a job repository operators can inspect. Monitor duration and row counts against SLA thresholds; backfills require change tickets and consumer notification when historical partitions rewrite. Airflow models cross-job DAGs with SLA miss callbacks; Dagster adds data-aware scheduling—materialize only when upstream partitions land, which reduces empty runs on object-storage sensors.

Tag every batch run with business date and source lineage so forensic replay after a bad deploy can target one partition without reprocessing years of history.

Emit row-level data quality metrics—null rates and key cardinality spikes often predict upstream outages before hard job failures.

Common failure modes

  • Job overlap: A nightly run exceeds 24 hours; the next schedule starts before the previous finishes, causing duplicate loads or race conditions.
  • Missing checkpoint configuration: An in-memory JobRepository loses all state when the JVM exits; the entire job restarts from row zero.
  • Source database contention: A full-table scan on production OLTP during peak hours consumes I/O and degrades user-facing latency.
  • Unbounded memory growth: A step buffers the full result set before write instead of chunking, triggering OOM as data grows.
  • Silent partial success: The job reports SUCCESS but skipped a large fraction of rows due to validation errors; missing data surfaces only when downstream reports diverge.

Decision checklist

  • Is maximum acceptable data latency compatible with the proposed batch window (hourly, daily, weekly)?
  • Are checkpoint and restart configured so failed jobs resume from the last committed step?
  • Does extract use a replica, snapshot, or incremental watermark—not the primary OLTP under load?
  • Are schedule duration and SLA breaches monitored with paging, not weekly log review?
  • Is there a tested re-run strategy when the destination already holds partial data from a failed run?
  • Are skip and error thresholds set so operators know whether one bad row or N failures should fail the job?

Example use cases

  • Illustrative scenario — Northwind Logistics runs an Airflow DAG at 01:00 UTC that triggers a Glue job: incremental extract from Postgres using an updated_at watermark, transform in Spark, bulk load into the analytics warehouse for morning BI.
  • Illustrative scenario — Meridian Commerce executes a Spring Batch job on the first of each month—reads closed usage for the prior period, applies discounts, writes invoice rows, and generates statement files for delivery.
  • Illustrative scenario — RideRelay runs nightly EMR Spark jobs that scan 90 days of interaction events on object storage, compute aggregated rider features, and publish Parquet to a feature store for model training.
  • Case study — Netflix and other large platforms publicly describe Spark batch pipelines for recommendations and reporting, complementing streaming paths only where sub-minute freshness is required.
