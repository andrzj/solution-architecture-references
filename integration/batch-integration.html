Batch Integration

Batch integration runs extract-transform-load work on a schedule or trigger, processing bounded datasets with checkpoints and predictable cost—when freshness can wait minutes to days.

⏱ 10 min read

What it is

Batch integration moves and transforms data between systems in jobs that run on a schedule or external trigger, processing many records inside a defined window or dataset boundary instead of reacting to each change in real time. A run typically follows extract → transform → load steps, commits work in chunks, and records progress so a failed job can resume instead of starting over.

Common engines include Spring Batch (chunk-oriented Java jobs with a persistent job repository), Apache Spark for distributed transforms, managed services such as AWS Glue and Azure Data Factory, and cron-driven SQL or shell scripts. Microbatching—jobs every few seconds to a minute—narrows the freshness gap with streaming without adopting full stream-processing semantics.

Why it exists

Many business processes are naturally periodic: payroll, regulatory filings, model retraining, and period-close accounting all assume a bounded slice of data. Streaming adds always-on compute, state management, and delivery semantics that do not pay off when stakeholders accept hourly or daily freshness.

Batch also wins on efficiency for sort-heavy aggregations, bulk database loads, and columnar file writes—operations that amortize I/O across millions of rows. A explicit processing window (“all orders closed between T₀ and T₁”) makes completeness and audit easier than inferring it from a continuous stream that may reorder or duplicate events.

When to use

  • Data warehouse or lake loads where freshness of minutes to hours is acceptable and bulk writes beat row-at-a-time inserts.
  • Compliance or finance reports that must be reproducible for a named time window.
  • Feature pipelines or analytics that scan large historical datasets once per run.
  • Period-close settlement, billing, or reconciliation that must see the full closed interval before posting.
  • Migrations or backfills that intentionally touch an entire corpus in one controlled job.
  • Destinations that expose bulk-load APIs or maintenance windows tuned for batch ingest.

When not to use

  • Sub-minute freshness or immediate reaction to domain events—prefer streaming integration or synchronous APIs.
  • Low-volume, steady trickle data where a scheduler and job repository cost more than CDC or API push.
  • Recovery SLAs measured in seconds; a multi-hour batch re-run may violate them after failure.
  • Downstream chains that block on a single nightly critical path with no incremental fallback.

Typical architecture

A scheduler or object-store event starts the job; orchestration tracks dependencies and SLA; each step reads a bounded slice, transforms in chunks, and loads with idempotent or upsert semantics. Job metadata (status, checkpoint, skip counts) lives in a repository or control table for operations and restart.

Pros and cons

Pros

  • Throughput: bulk COPY, JDBC batch inserts, and Parquet writes scale better than per-record streaming for large slices.
  • Predictability: each run targets a known window; operators reason about completeness without watermark or late-event logic.
  • Checkpoint/restart: persisted step state limits rework after failure.
  • Cost: compute spins up for the job duration instead of running continuously.
  • Auditability: reruns and exports for a fixed interval satisfy many regulatory evidence requirements.

Cons

  • Staleness bounded by the schedule—daily jobs imply up to 24 hours lag.
  • Spiky load on sources, networks, and warehouses during the run window.
  • Partial failure forces explicit policies on idempotent loads, compensating deletes, or full window replay.
  • Long reruns extend recovery time when jobs are hours in duration.
  • Downstream DAGs often serialize on one “nightly completed” gate.

Implementation notes

In Spring Batch, tune chunk size to memory and transaction boundaries (often 1,000–10,000 rows for JDBC; larger for object-store writes). Persist JobRepository state in a database, not in-memory, and cap concurrent runs of the same job to prevent overlap.

Read from replicas or incremental watermarks (updated_at, binlog position, or Glue job bookmarks) instead of full-table scans on OLTP primaries. Orchestrate with Airflow, EventBridge Scheduler, or similar: model dependencies, SLA sensors, and alerting on duration and row counts—not only exit code.

Define skip limits and error thresholds explicitly; “SUCCESS” with a high skip rate is a data-quality incident. For microbatching, Spark structured streaming’s Trigger.AvailableNow() or frequent scheduled Glue runs can deliver near-real-time freshness while keeping batch economics.

Common failure modes

  • Overlapping runs: a slow job meets the next cron trigger and double-loads or races on the same window.
  • Lost checkpoints: in-memory job metadata forces full reruns after JVM death.
  • OLTP contention: heavy extract during peak hours starves transactional workloads.
  • Heap blowups: loading entire files or result sets before write instead of chunking.
  • Ignored skip storms: validation failures logged but not alerted until BI diverges.

Decision checklist

  • Does the business accept the maximum staleness implied by the schedule?
  • Are checkpoints durable and is only one active instance allowed per logical job?
  • Does extract avoid primary OLTP under load, using replicas or CDC when possible?
  • Are duration, rows processed, skip count, and SLA breaches monitored?
  • Is there a tested strategy for partial loads and idempotent replays?
  • Are error and skip thresholds set so “green” runs still mean trustworthy data?

Example use cases

  • Illustrative scenario — An orchestrator triggers a nightly warehouse load: incremental extract by updated_at, transform in Spark or Glue, bulk load into the analytics store for morning dashboards.
  • Illustrative scenario — A monthly billing job reads closed usage for the prior period, calculates charges, writes invoices, and emits statement files for downstream delivery.
  • Case study — Netflix and many data platforms publicly describe large-scale Spark batch pipelines for recommendation features and reporting, complementing real-time paths where needed.
