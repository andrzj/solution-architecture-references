Change Data Capture

Change data capture turns database transaction logs into change event streams for search, caches, and analytics without modifying application code.

⏱ 11 min read

What it is

Change data capture (CDC) reads a database’s transaction log—PostgreSQL WAL, MySQL binlog, SQL Server change tables, Oracle redo—and turns committed row changes into a stream of insert, update, and delete events. Applications keep writing SQL as usual; integration consumes the log, which avoids dual-write races and many invasive code changes in legacy systems.

CDC is infrastructure-level integration: events describe storage-level diffs, not domain intents. Platforms such as Debezium (Kafka Connect), AWS Database Migration Service and MSK Connect, Azure Event Hubs with capture, and Oracle GoldenGate sit at this layer. Downstream teams often wrap or map CDC into CloudEvents or canonical schemas before business services consume them.

Why it exists

Publishing “what changed” alongside an application transaction is hard: message brokers and databases do not share one atomic commit unless you use patterns like the transactional outbox. CDC treats the database log as the authoritative chronology of committed state—integration replays truth the database already recorded.

That enables near-real-time search indexes, caches, warehouses, and read models without polling wide tables or retrofitting event emission into every legacy code path. It is a common extract mechanism for ELT and streaming pipelines when operational stores remain system of record during modernization.

When to use

  • You need change streams from systems you cannot modify to emit domain events directly.
  • Search, cache, or replica stores must track inserts, updates, and hard deletes with low latency.
  • Incremental warehouse or lake loads should replace large batch extracts.
  • Cross-region or cross-store replication needs ordered, durable change feeds.
  • An outbox table in the same database can be tapped via CDC instead of application polling.
  • Strangler migrations must keep a new service’s datastore aligned with a monolith table during cutover.

When not to use

  • The managed database forbids logical replication or external log access required by your connector.
  • Consumers need rich domain events (OrderShipped) rather than row diffs—you still need a translation or outbox layer.
  • Tables undergo constant disruptive DDL without a schema governance process connectors can follow.
  • Sensitive columns cannot be masked before events reach shared topics, and policy cannot enforce field-level controls.

Typical architecture

A log-reading connector publishes per-table or unified topics; stream processors or sink connectors fan out to indexes, warehouses, and cache invalidation workers.

Pros and cons

Pros

  • No application code changes to start streaming committed changes.
  • Captures deletes and updates polling often misses or delays.
  • Low latency compared with batch extracts for large tables.
  • Per-partition ordering preserves mutation sequence for a key when keyed correctly.
  • Initial snapshot plus streaming supports backfill and steady-state in one connector.

Cons

  • Events are storage-shaped; domain meaning requires interpretation or an ACL.
  • DDL and type changes can break deserialization without registry discipline.
  • Replication slots and binlog retention consume disk; lag can become unrecoverable.
  • Connectors, offsets, and Kafka Connect clusters add operational surface area.
  • Full row payloads may expose PII unless masked before publication.

Implementation notes

On PostgreSQL, set wal_level = logical, create a replication user and slot, and monitor lag against max_slot_wal_keep_size. On MySQL, use row-format binlog with full row images. Run Debezium on Kafka Connect or use AWS DMS / MSK Connect / Azure-hosted equivalents where managed ops matter.

Register Avro or Protobuf schemas for change events; apply Debezium single message transforms to mask fields or route topics. Enable delete tombstones when topics use log compaction. Document topics in AsyncAPI for consumers that are not JVM-based.

Downstream, idempotent sinks apply upserts and handle out-of-order arrivals where needed. Combine with an anti-corruption layer or stream processor to emit CloudEvents domain notifications instead of leaking table column names into every microservice.

Common failure modes

  • Slot or binlog pressure: Connector lag fills disk; recovery requires painful resnapshot.
  • Schema surprise: DDL without registry update breaks consumers mid-deploy.
  • Snapshot overlap: Duplicate or out-of-order events during initial load if consumers lack idempotency keys.
  • PII on the bus: Unmasked columns replicated to broadly readable Kafka topics.
  • Schema coupling: Services embed table-layout assumptions instead of stable contracts.

Decision checklist

  • Does the database expose a supported logical log or capture API?
  • Can operations monitor connector lag, disk retention, and offset health?
  • Is there a schema evolution process aligned with CDC serializers?
  • Are sensitive fields masked or tokenized before publication?
  • Do consumers need domain events—and if so, where will translation happen?
  • Is transactional outbox a better fit when you own the writing application?

Example use cases

  • Illustrative scenario — Product row changes stream to Kafka; a search sink connector updates an index within seconds of merchandising edits.
  • Illustrative scenario — Warehouse staging tables merge CDC events keyed by primary key instead of nightly full-table exports.
  • Case study — Debezium, widely used with Kafka Connect, documents connectors and event formats for major relational and NoSQL databases as an open CDC reference implementation.
