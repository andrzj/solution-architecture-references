Change Data Capture

Change data capture turns database transaction logs into change event streams for search, caches, and analytics without modifying application code.

⏱ 11 min read

What it is

Change data capture (CDC) monitors a database’s transaction log—PostgreSQL WAL, MySQL binlog, SQL Server change tables, Oracle redo—and emits row-level insert, update, and delete events for downstream consumers in near real time. Unlike timestamp polling, which can miss deletes and races against in-flight transactions, CDC reads the same replication infrastructure the database already maintains for HA. Application SQL stays unchanged; integration attaches at the storage boundary.

CDC is infrastructure-level integration: events carry before and after column images plus operation metadata, not business intents such as OrderShipped. Open tooling includes Debezium on Kafka Connect, AWS DMS and MSK Connect, Azure capture paths, and Oracle GoldenGate. Teams often map envelopes into CloudEvents or a canonical model before domain services subscribe.

Connectors combine an initial snapshot (consistent table export) with streaming (ongoing log tail). Offsets—LSN, binlog position, or SCN—bookmark progress so restarts resume without full reloads when retention permits.

Why it exists

Publishing integration events in the same transaction as a database write is the classic dual-write problem: unless you use a transactional outbox or XA, one side can commit while the other fails, and replicas diverge silently. CDC sidesteps application cooperation by treating the commit log as the single source of truth for “what definitely changed.”

That unlocks search indexes, denormalized read models, cache invalidation, and warehouse staging without retrofitting emitters into legacy code you do not own. During strangler migrations, CDC can feed a new service’s database from monolith tables until traffic cuts over. For ELT, CDC supplies a continuous extract leg—often paired with Kafka and dbt—so freshness moves from daily batches to minutes without widening the operational blast radius of writers.

When to use

  • Non-invasive legacy: You need change streams but cannot change source application code or stored procedures.
  • Search and cache: Elasticsearch, OpenSearch, or Redis must reflect hard deletes and updates, not only inserts.
  • Incremental analytics: Lake or warehouse loads should merge keyed upserts instead of nightly full-table exports.
  • Cross-region copy: Sub-second propagation with ordered per-partition feeds matters more than byte-level snapshot simplicity.
  • Outbox fan-out: An outbox table in the same database can be tapped via CDC instead of pollers in application pods.
  • Parallel migration: A new datastore must track monolith writes until cutover validation passes.
  • Audit and lineage: Compliance needs an append-only change trail without dual-writing audit tables in every service.

When not to use

  • No log access: Managed DBaaS tiers forbid logical replication, external slots, or binlog consumers your connector requires.
  • Domain events only: Consumers need rich business semantics—you still need translation, an outbox, or a stream processor on top of CDC.
  • DDL churn: Tables change shape weekly without registry or connector governance; pipelines will break in production.
  • PII exposure: Sensitive columns cannot be masked or tokenized before events land on broadly readable topics.
  • You own the writer: Greenfield services you control may get cleaner contracts from transactional outbox than from table leakage.

Typical architecture

A connector tails the source log, serializes change records, and publishes to one topic per table or a unified stream. Sink connectors, stream jobs, or materialized-view workers consume with idempotent upserts; lag and offset health are first-class operational metrics alongside database replication slot pressure.

Pros and cons

Pros

  • Starts streaming committed changes without modifying source application code.
  • Captures hard deletes and in-place updates that timestamp polling misses.
  • Sub-second latency versus batch extracts on large, churning tables.
  • Per-partition ordering preserves mutation sequence per key when keyed correctly.
  • Snapshot plus streaming supports backfill and steady-state in one connector lifecycle.
  • Leverages database replication plumbing already maintained for HA.

Cons

  • Events expose storage shape; business meaning needs translation or an ACL.
  • DDL and type changes break deserializers without strict registry governance.
  • Slots and binlog retention tie connector health to database disk pressure.
  • Kafka Connect clusters, offsets, and replay drills add operational surface area.
  • Full-row payloads can publish PII unless masked before shared topics.
  • Hot tables can overwhelm brokers if message size and partitioning are not planned.

Implementation notes

On PostgreSQL, set wal_level = logical, create a replication user and slot, and alert on lag versus max_slot_wal_keep_size before WAL retention becomes an outage. On MySQL, require row-format binlog with full row images so updates carry complete before/after payloads. Size Kafka Connect workers for parsing throughput; connector tasks are often CPU-bound on wide tables.

Register Avro or Protobuf in a schema registry; block incompatible DDL from production until serializers accept new versions. Use Debezium single message transforms to mask columns, route topics, or flatten keys. Enable delete tombstones when topics are compacted. Publish topic contracts in AsyncAPI so polyglot consumers know envelope shapes without reading JVM-only examples.

Downstream sinks must be idempotent on primary key or natural key plus source LSN. During snapshot plus streaming, consumers may see duplicates at the handoff—dedupe keys or upsert semantics are mandatory. Place translation in a dedicated stream job or anti-corruption layer so microservices never import raw column names as their public API.

Common failure modes

  • Replication slot starvation: A stalled connector lets WAL or binlog grow until disks fill; recovery may require a full resnapshot and hours of catch-up.
  • Schema surprise: A nullable-to-required column change ships without a registry bump; deserializers fail mid-deploy and poison consumer groups.
  • Snapshot overlap: Events during initial load duplicate rows unless sinks treat LSN or offset as an idempotency token.
  • PII on the bus: Full-row replication publishes regulated fields to shared Kafka ACLs; remediation becomes a cross-team incident.
  • Schema coupling: Domain logic branches on storage column renames; every DDL becomes a coordinated multi-service release.
  • Throughput cliffs: Wide tables or hot keys produce oversized messages that breach broker limits or stall connect tasks.

Decision checklist

  • Does the database expose logical replication, binlog, or an supported capture API on your tier?
  • Can operations monitor slot lag, offset lag, and disk retention with paging before databases fail?
  • Is DDL gated with schema-registry compatibility checks for CDC topics?
  • Are sensitive fields masked or hashed before publication to shared infrastructure?
  • Do consumers need domain events—and where will translation run (stream job vs ACL vs outbox)?
  • When you own the writer, is transactional outbox simpler than leaking table semantics enterprise-wide?
  • Have you sized network and broker capacity for peak write rates including delete volume?

Example use cases

  • Illustrative scenario — A merchandising catalog table streams to Kafka; a search sink connector upserts Elasticsearch within seconds of price or availability edits, including deletes that would never appear in poll-based jobs.
  • Illustrative scenario — Operational MySQL feeds Snowflake staging through CDC and JDBC sinks; finance dashboards move from 24-hour batch freshness to sub-five-minute incremental merge.
  • Illustrative scenario — During a strangler cutover, an orders table in the monolith replicates into a microservice database until traffic shifts and the dual-write window closes.
  • Case study — Debezium documents connectors, event envelopes, and offset semantics for major relational and document stores as a widely referenced open CDC stack on Kafka Connect.

Related patterns

  • Transactional Outbox — Publishes domain events in the same database transaction when you control the writer and want cleaner semantics than row diffs.
  • Streaming Integration — Flink or Kafka Streams jobs enrich, join, and fan out CDC records into multiple derived topics.
  • ETL vs ELT — CDC replaces bulk extract steps with continuous incremental loads into lake or warehouse landing zones.
  • Anti-Corruption Layer — Translates low-level change envelopes into stable inward contracts and CloudEvents for product teams.
  • Data Synchronization — Bidirectional or multi-store sync may use CDC as the detection leg on the authoritative database.
