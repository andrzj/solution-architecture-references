Anti-Corruption Layer

An anti-corruption layer translates at the integration boundary so your domain model stays independent of legacy and vendor schemas.

⏱ 9 min read

What it is

An anti-corruption layer (ACL) is a boundary component that translates between your domain model and an external or legacy system so foreign concepts never leak into core business logic. Eric Evans introduced the pattern in Domain-Driven Design for upstream/downstream context relationships where the external model is awkward or hostile; Martin Fowler and the Azure Architecture Center describe the same idea for microservice and cloud migrations: the ACL is the only place that speaks the legacy dialect.

Structurally it combines a facade (stable inward-facing API your application calls), an adapter that speaks the external protocol—SOAP, gRPC, JDBC, vendor SDKs, or message bindings—and translators that map payloads in both directions. That split mirrors Enterprise Integration Patterns Gateway and Message Translator. The ACL may be a library module inside one service, a dedicated adapter microservice that owns a single boundary, or integration routes in Apache Camel or MuleSoft between bounded contexts.

In DDD context mapping, the ACL sits on the downstream side of an upstream/downstream relationship: your model is the translation target, and the foreign model stops at the edge. That differs from a conformist context that adopts the upstream schema wholesale, or an open host service that publishes a stable outward API—here you deliberately insulate inward code from awkward partner semantics.

Why it exists

Legacy and vendor systems encode decades of local trade-offs: customer identifiers as prefixed strings, order status as integers documented only in old runbooks, product rows that mash SKU, price tier, and bundle into one flat record. Partner APIs, ERP exports, and mainframe feeds share the same problem—opaque codes, overloaded nouns, money in minor units. If new domain code imports those shapes directly, accidental complexity becomes permanent coupling.

Without a translation boundary, every schema tweak or vendor upgrade forces refactors across services that should not know those details. The ACL concentrates coupling in one replaceable seam. Inside the boundary you keep expressive types—typed CustomerId, explicit OrderStatus, separated aggregates—while translators absorb ugly mapping. When the external system is swapped or retired—often during a strangler-fig migration—you change adapters and translators, not domain rules. That matches hexagonal architecture: ports face inward, the ACL implements outward.

When to use

  • Integrating with legacy or vendor systems whose nouns, codes, and lifecycles conflict with your ubiquitous language.
  • Incremental decomposition where a new service must read or write through a monolith API or database during migration.
  • Third-party boundaries (payments, shipping, CRM) where you need a neutral internal model and the freedom to change providers.
  • High-risk semantic gaps—time zones, money, units of measure, ambiguous status enumerations—where silent mistranslation becomes a production bug.
  • Event or message integration where you want CloudEvents or domain events on the inside and proprietary wire formats only at the edge.
  • When multiple consumers must share one stable inward contract while the upstream source remains volatile.
  • Two internal bounded contexts whose ubiquitous languages diverged and cannot agree on a shared kernel.

When not to use

  • Both sides already share the same bounded-context language and schema—prefer conformist or shared-kernel relationships over extra translation (per Evans’s context-mapping vocabulary).
  • The integration is a one- or two-field passthrough with no semantic risk; inline mapping in the application layer is enough.
  • The external dependency is a short-lived bridge with a fixed sunset—formal ACL investment may not pay back before decommission.
  • Ultra-low-latency paths where translation cost dominates and a denormalized read model or cache is the better trade-off.

Typical architecture

Domain code depends on inward ports (repositories, gateways). The ACL implements those ports, calls the legacy system through its native client, and owns all mapping and error translation at the edge.

Pros and cons

Pros

  • Keeps domain types and rules free of foreign field names, magic numbers, and vendor SDK types.
  • External replacement or upgrade is localized to the ACL instead of rippling through business services.
  • Creates a test seam: mock inward ports for domain tests, contract or recorded-traffic tests for the boundary.
  • Surfaces semantic mismatches explicitly instead of hiding them in shared DTOs.
  • Supports strangler-fig and dual-write cutovers by absorbing temporary integration quirks.

Cons

  • Extra code, fixtures, and monitoring for a layer that feels like “plumbing” until the first vendor change.
  • Translation can be lossy when the external model carries fields with no domain counterpart.
  • Per-call mapping adds latency; caching must respect staleness and invalidation rules.
  • The ACL must track evolution on both sides; frequent upstream changes can make it a bottleneck team.
  • Risk of creeping business rules in translators when domain modeling is deferred.

Implementation notes

Own all external knowledge in the ACL module. Domain and application layers depend only on inward ports—OrderRepository, CustomerGateway, and similar interfaces—not on vendor SDKs, SOAP stacks, or legacy DTO packages. Nothing in the domain package imports the ACL; dependency always points inward. Document message or HTTP boundaries with AsyncAPI or OpenAPI so partners see the stable inward contract, not the legacy wire format.

Implement translators as explicit, unit-tested functions with golden fixtures from sandbox traffic or recorded production samples. Use Camel transform / marshal steps or MuleSoft DataWeave in integration-centric estates; in microservices, a dedicated adapter service with timeouts, circuit breakers, and bulkheads often isolates failure better than a fat library. Map upstream errors to domain exceptions with meaningful names—never let raw HTTP status, SOAP faults, or vendor error codes bubble into business services.

For CDC or queue ingress, normalize to CloudEvents or internal domain events in the ACL so downstream consumers never parse vendor envelopes. Use contract tests (Pact) or replay suites when the external API churns. Emit metrics on translation latency, mapping failures, and circuit-open events at this boundary; that is where integration regressions show up first.

Exercise outbound paths in the same test suites as reads: idempotency keys, partial-update semantics, and mandatory legacy fields on write differ from GET mapping and are where production skew usually appears. During strangler cutovers, compare ACL responses from the new store and the legacy source before routing production traffic.

Common failure modes

  • Leaky boundary: Legacy DTOs, SDK types, or vendor exceptions appear in domain services, reintroducing the coupling the ACL was meant to block.
  • Rules in translators: Conditional mapping such as “if legacy status 07 and region US, treat as shipped” encodes policy that belongs in domain code, not the translator.
  • One-way mapping: Inbound reads translate correctly but outbound writes still emit legacy field shapes, silently corrupting data at the source.
  • Untranslated errors: Opaque upstream failures surface as generic 500s with no correlation id for support or retry decisions.
  • Fixture rot: Unit tests pass on hardcoded samples while production payloads drift after a silent vendor or mainframe release.
  • Stale read-through cache: The adapter caches legacy responses with an oversized TTL, so domain code serves inventory or entitlement data that lags the authoritative system.
  • Dual-write skew: A strangler ACL persists to the new datastore but the legacy callback fails; dashboards look healthy while the two sources disagree on truth.

Decision checklist

  • Does the external model conflict with your ubiquitous language or aggregate boundaries?
  • Are there known semantic traps (money, time, units, status codes) on this interface?
  • Will you need to replace or dual-run the external system within the system’s lifetime?
  • Is a formal ACL cheaper than the cost of domain refactors on every upstream change?
  • Have you defined inward ports and forbidden legacy imports above the ACL?
  • Do you have contract or replay tests for both directions of translation?

Example use cases

  • Illustrative scenario — At Harborline Retail, a new order microservice reads fulfillment status through an ACL that maps mainframe numeric codes to a domain ShipmentState enum while the monolith remains authoritative during strangler cutover.
  • Illustrative scenario — Crestwave Commerce runs per-provider ACL modules so two payment gateways both map to the same PaymentOutcome type, keeping checkout logic provider-agnostic.
  • Illustrative scenario — Summit Outfitters syncs catalogue data from a legacy material-master feed; the ACL converts flat ERP rows into a clean Product aggregate with unit-of-measure and status mapping isolated at the edge.
  • Case study — Microsoft documents the anti-corruption layer as a first-class Azure architecture pattern for isolating microservices from external and legacy dependencies during modernization programs.

Related patterns

  • Canonical Data Model — An ACL frequently maps foreign payloads into a team-owned canonical schema instead of exposing proprietary formats at context boundaries.
  • Bounded Contexts — Eric Evans positions the anti-corruption layer as the integration pattern that keeps upstream models from polluting a bounded context’s ubiquitous language.
  • Change Data Capture — CDC streams can pass through an ACL that turns row-level changes into domain events with stable CloudEvents types.
  • Data Synchronization — Ongoing sync jobs often place an ACL between the source system and your internal representation.
