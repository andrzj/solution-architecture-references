Integration Consistency

Data Synchronization

Data synchronization propagates changes so multiple systems hold aligned copies—via replication, events, or bidirectional merge—under an explicit consistency and conflict policy.

⏱ 10 min read

What it is

Data synchronization is the practice of keeping representations of the same logical data aligned across databases, SaaS products, caches, search indexes, or mobile clients. One system (or field) is usually authoritative; changes propagate through replication, change logs, messaging, or scheduled compare-and-repair jobs until replicas converge within an agreed staleness bound.

Unidirectional sync copies from a master outward. Bidirectional sync allows writes on multiple sides and requires explicit conflict rules: last-write-wins, field-level ownership, operational transforms, human review queues, or CRDTs where the data model permits automatic merge.

Why it exists

Polyglot architectures duplicate customer, product, and order data because each application optimizes for its workflow—sales, billing, support, analytics. Querying one golden API for every read couples availability and latency. Local replicas plus sync preserve autonomy while limiting divergence.

Offline-first clients and multi-region deployments add the same problem at the edge: devices or regions must write locally and reconcile later without silently dropping legitimate concurrent edits.

When to use

  • Several systems own overlapping entities and need reasonably fresh local copies.
  • Active-active or multi-region replicas must absorb local writes and converge globally.
  • Mobile or edge clients work offline and upload changes on reconnect.
  • Services keep denormalized read models warmed from a system of record.
  • Parallel-run migrations validate a new store while the legacy system still takes writes.
  • SaaS-to-SaaS bridges where each product is master for a subset of fields.

When not to use

  • A single clear master and read-only followers—prefer simple replication or CDC fan-out.
  • Cross-system invariants that require atomic commit (inventory + payment)—use sagas or workflow orchestration, not lazy sync.
  • Write rates where version comparison and conflict handling dominate CPU.
  • State machines where blind merge would create illegal business states.

Typical architecture

Each side emits changes (API webhook, CDC, or outbox). A sync engine or bus compares versions, applies routing rules, and resolves conflicts before writing the peer. Metadata—vector clocks, hybrid logical clocks, or monotonic version fields—distinguishes stale updates from true conflicts.

Pros and cons

Pros

  • Local reads and writes without synchronous cross-system RPC on every request.
  • Resilience when a peer is down—work continues against local state.
  • Supports offline and edge scenarios with later reconciliation.
  • Enables strangler migrations with both stacks live.
  • CRDTs or field-merge rules can guarantee convergence for suitable data types.

Cons

  • Bidirectional paths are easy to get wrong; subtle bugs erase edits.
  • Eventual consistency—temporary disagreement is normal, not exceptional.
  • Naive last-write-wins drops concurrent legitimate field updates.
  • Schema drift on either side breaks mappings until coordinated fix.
  • Lag and divergence need metrics; silent stall is a common production failure.

Implementation notes

Prefer hybrid logical clocks or version vectors over raw wall-clock LWW when conflicts matter. Stamp records with source_system, version, and optional per-field timestamps. Suppress echo: do not re-publish inbound changes that originated from the peer (use lineage flags or conditional writes).

Assign field-level authority where possible—marketing vs billing attributes—so most updates never conflict. For SaaS bridges, integration platforms (Boomi, MuleSoft) or iPaaS workflows often beat bespoke two-way glue for audit and operator tooling.

Measure end-to-end lag (time from write on A to visible read on B), conflict queue depth, and periodic checksum compares on sample entities. Throttle mobile reconnect storms with jittered backoff and server-side rate limits.

Common failure modes

  • Echo loops: received changes trigger outbound sync that ping-pongs indefinitely.
  • LWW data loss: concurrent edits to different fields collapse to one timestamp winner.
  • Clock skew bias: one node’s fast clock wins every conflict.
  • Reconnect overload: mass offline clients crush the sync API at once.
  • Schema mismatch: required new fields dropped on the weaker adapter.

Decision checklist

  • Can this stay unidirectional with a named system of record?
  • What maximum staleness is acceptable per consumer?
  • How are conflicts detected, surfaced, and resolved (auto vs human)?
  • Which fields does each system own exclusively?
  • Are echo and loop prevention rules implemented and tested?
  • Are lag, error rate, and divergence sampling on dashboards with alerts?

Example use cases

  • Illustrative scenario — CRM and ERP exchange customer rows with field-level authority; marketing attributes flow one way, billing attributes the other, with a review queue for true conflicts.
  • Illustrative scenario — Field technicians update work orders offline; on reconnect, operation-based merge reconciles dispatcher and device edits.
  • Case study — CockroachDB and similar globally distributed databases document built-in replication and transactional semantics for multi-region active-active deployments.

Related patterns

  • Change Data Capture — detects changes for outbound sync.
  • Eventual Consistency — typical guarantee for replicated copies.
  • Vector Clocks — causality metadata for conflict detection.
  • Batch Integration — periodic full or incremental reconcile jobs.
