Integration Consistency

Data Synchronization

Data synchronization propagates changes so multiple systems hold aligned copies—via replication, events, or bidirectional merge—under an explicit consistency and conflict policy.

⏱ 10 min read

What it is

Data synchronization keeps representations of the same logical entity—customer, product, order—aligned across databases, SaaS tenants, caches, search indexes, or mobile clients. Propagation may be event-driven (webhook, CDC, message bus), scheduled (compare-and-repair batch), or continuous (streaming merge). One side is usually authoritative for a given field or entity type; replicas converge within an agreed staleness window.

Unidirectional sync copies from a system of record to dependents. Bidirectional sync permits independent writes on multiple sides and demands explicit conflict policy: last-write-wins (LWW), first-write-wins, field-level ownership, operational transforms, human review queues, or CRDTs where the data model supports commutative merge. The hard part is not transport—it is deciding whose edit wins when two legitimate updates overlap.

Sync differs from a single shared database: each store optimizes for its workload (CRM workflows, ERP finance, support tickets) while integration mechanics move deltas until business-defined consistency goals are met.

Why it exists

Enterprise estates routinely duplicate customer and product records across CRM, ERP, support, marketing automation, and the warehouse. A single “query everything from master” API couples latency, availability, and release cadence: one slow partner API blocks every screen. Local replicas plus synchronization preserve team autonomy while bounding how far copies diverge.

Offline-first mobile apps and multi-region active-active databases extend the same tension to the edge: users must write when disconnected or when routed to the nearest region; reconciliation cannot assume a single global mutex. CouchDB/PouchDB-style replication and globally distributed SQL engines bake sync into the storage layer; SaaS iPaaS tools productize the same problem for non-technical operators.

When to use

  • Overlapping masters: Multiple systems legitimately write overlapping entities and need fresher local copies than nightly batch.
  • Multi-region active-active: Each region serves local writes that must propagate globally with bounded conflict handling.
  • Offline and edge: Mobile or field apps maintain local databases and reconcile on reconnect.
  • Denormalized read models: Microservices cache prices or catalog slices and sync when upstream rows change.
  • Parallel migration: Old and new systems run together while validators compare row counts and checksums.
  • SaaS bridges: Each SaaS product owns different field subsets (marketing vs billing) on the same customer key.
  • Partner B2B: Counterparties exchange entities on different schedules but need eventual alignment for settlement.

When not to use

  • Clear read-only followers: One master and read replicas—use database replication or CDC fan-out instead.
  • Atomic cross-system invariants: Inventory and payment must commit together—use sagas or workflow orchestration, not lazy bidirectional sync.
  • Extreme write rates: Conflict detection and version churn dominate CPU; consider partitioning authority instead.
  • Strict state machines: Automated merge can create business-illegal transitions unless rules are encoded in the sync engine.
  • Sub-second global strong consistency: If every read must see the latest write everywhere, distributed consensus beats eventual sync.

Typical architecture

Each side emits changes through webhooks, CDC, or application outboxes into a sync engine or message bus. The engine compares versions, routes updates to peers, and applies conflict policy before writing the target. Metadata—vector clocks, hybrid logical clocks (HLC), or monotonic version counters—separates stale replays from genuine concurrent edits worth merging or escalating.

Pros and cons

Pros

  • Local reads and writes avoid synchronous cross-system RPC on every user action.
  • Peers can fail independently; work continues against local state within SLO.
  • Offline and edge clients operate productively and merge on reconnect.
  • Parallel-run migrations validate new systems without big-bang cutover.
  • CRDTs or field-merge rules guarantee convergence for commutative data types.
  • Field-level authority eliminates whole classes of conflicts in SaaS bridges.

Cons

  • Bidirectional sync is subtle; incorrect echo or merge logic erases legitimate edits.
  • Eventual consistency means transient disagreement is expected, not exceptional.
  • Naive LWW on whole records drops concurrent updates to different fields.
  • Schema drift on either side breaks mappings until coordinated release.
  • Lag, divergence, and conflict queue depth demand dedicated metrics and paging.
  • Operational tooling (replay, audit, operator UI) is as important as transport code.

Implementation notes

Prefer hybrid logical clocks or version vectors over wall-clock LWW when concurrent edits matter—skewed clocks systematically favor the fast node. Stamp every record with source_system, monotonic version, and optional per-field version metadata. Suppress echo: inbound rows that originated from the peer must not trigger another outbound publish (lineage flags, conditional writes, or “touched_by_sync” columns).

Assign field-level authority early—CRM owns campaign attribution, ERP owns payment terms—so most updates are one-way merges instead of conflicts. For SaaS-to-SaaS bridges, iPaaS tools (Boomi, MuleSoft, Workato) often ship conflict UI, audit trails, and connector catalogs that bespoke scripts lack. For mobile, use operation-based or CRDT sync libraries when the data model allows; otherwise cap batch size on reconnect.

Dashboard end-to-end lag (write on A to readable on B), conflict backlog depth, error rate by entity type, and sampled checksum compares on hot keys. Run game days that disconnect a peer for an hour and verify convergence and absence of sync loops. Document maximum staleness per consumer in SLOs, not only in architecture diagrams.

Common failure modes

  • Sync loops: A receives from B and immediately pushes back; traffic ping-pongs until operators disable the pipeline.
  • LWW data loss: Concurrent edits to phone and email on one record collapse to a single timestamp winner.
  • Clock skew bias: A node five minutes ahead wins every LWW decision regardless of real edit order.
  • Thundering herd on reconnect: Thousands of clients sync simultaneously and overwhelm API rate limits.
  • Schema mismatch: Required fields added upstream are dropped by a lagging adapter, producing invalid rows.
  • Silent stall: Lag metrics flatline while business teams assume CRM and ERP still agree.

Decision checklist

  • Can this remain unidirectional with a named system of record per entity?
  • What maximum staleness is acceptable for each consuming workflow?
  • How are conflicts detected, surfaced, auto-merged, or queued for humans?
  • Which fields does each system own exclusively, documented in integration standards?
  • Are echo suppression and loop prevention covered by automated tests?
  • Do dashboards alert on lag, divergence samples, and conflict queue age?
  • Is a strangler or decommission date defined so bidirectional sync does not become permanent glue?

Example use cases

  • Illustrative scenario — CRM and ERP mirror customer rows with field-level authority; marketing attributes sync one way, billing the other, and a review queue handles rare simultaneous status edits.
  • Illustrative scenario — Field technicians complete work orders offline; on reconnect, operation-based merge reconciles dispatcher schedule changes with device-captured timestamps.
  • Illustrative scenario — A product catalog microservice warms denormalized prices from CDC on the monolith until the strangler path owns writes.
  • Case study — Globally distributed SQL engines such as CockroachDB document built-in replication and transactional semantics for multi-region active-active workloads where sync is a storage feature.

Related patterns

  • Change Data Capture — Common detection leg that streams authoritative database changes into sync pipelines.
  • Eventual Consistency — The consistency model most replicated sync topologies provide.
  • Vector Clocks — Causality metadata for spotting true conflicts versus stale replays.
  • Batch Integration — Nightly compare-and-repair jobs complement or backstop continuous sync.
  • Saga Pattern — Coordinates multi-system workflows when atomic sync cannot enforce invariants.
