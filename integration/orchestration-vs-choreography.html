Orchestration vs Choreography

Orchestration keeps workflow control in a central coordinator; choreography lets each service react to events—choose based on visibility needs, ownership boundaries, and how hard rollback is.

⏱ 12 min read

What it is

Orchestration coordinates a multi-step business process from a central component. The orchestrator invokes participating services (or activities), records outcomes, branches on results, and runs compensating steps when something fails. Participants expose task-shaped APIs; they do not need to know the full saga—only how to perform their step when asked. Workflow engines (Temporal, Camunda, AWS Step Functions) and dedicated orchestrator services implement this model.

Choreography spreads coordination across services: one service publishes a domain event, others subscribe and react, then publish their own events. No single component holds the entire process graph; end-to-end behavior emerges from published contracts on a broker or log. The Saga pattern can be implemented either way—orchestration saga with an explicit coordinator, choreography saga with compensating events and idempotent consumers.

Neither style replaces the other. Orchestration optimizes for explicit state and operator visibility; choreography optimizes for loose coupling and independent deployment. Many estates use both: orchestrated sagas for money-moving flows, choreographed reactions for analytics and notifications.

Why it exists

Monoliths coordinate with in-process calls and often a single database transaction. Microservices forbid two-phase commit across boundaries; long-running processes become sequences of local commits with eventual alignment. Someone—or something—must decide what runs next, what to do on failure, and how to correlate partial progress.

Central orchestration answers “where is order 8472 in fulfillment?” with one query against workflow history. Choreography answers “how do we add a new consumer without redeploying producers?” by subscribing to an existing topic. The trade is visibility and controlled rollback versus autonomy and fewer shared runtime dependencies.

ESB-era hubs blurred integration and process control; modern guidance keeps orchestrators thin—flow and compensation only—and pushes domain rules into services. Choreography without design discipline devolves into undebuggable event chains. The decision is where process knowledge and operational tooling live, not whether you avoid distributed work.

When to use

  • Use orchestration when steps have branching, timers, human approval, or ordered compensation that is hard to reconstruct from events alone.
  • Use orchestration when support and SRE must query in-flight state, retry a failed step, or cancel one workflow instance without code archaeology.
  • Use orchestration when one product team owns the end-to-end process and the orchestrator is a natural home for flow—not domain rules.
  • Use choreography when independent teams own services and must ship without a central workflow release train.
  • Use choreography when an event backbone already exists and services publish facts as part of normal operation.
  • Use choreography when new reactions (search indexing, loyalty points) should attach to existing events without changing publishers.

When not to use

  • Avoid pure choreography for multi-step financial rollback where compensation order and legal audit matter—without a saga audit projection or coordinator, failures lack a clear owner.
  • Avoid fat orchestrators that encode pricing, eligibility, or inventory rules—those belong in domain services; otherwise you recreate the ESB “smart hub” at workflow scale.
  • Avoid orchestration for trivial reactions (signup → welcome email) where a single consumer on one event suffices.
  • Avoid choreography when event schemas churn weekly and every consumer must redeploy—stability may favor a versioned orchestration contract or fewer, broader events.

Typical architecture

In orchestration, clients or upstream services start a workflow; the engine schedules steps, persists history, and invokes workers. In choreography, producers append to a log; consumers in separate deployable units process at their own pace and emit downstream events. Correlation identifiers should appear in both models so logs and traces stitch the same business operation.

Pros and cons

Orchestration pros

  • Instance state and step history live in one queryable store—ideal for support and compliance replay.
  • Compensation and timeouts are first-class; engines schedule retries and human tasks across days.
  • New engineers read the flow in one workflow definition instead of hunting emit/listen pairs.
  • Durable execution (event-sourced replay) survives worker crashes without duplicating side effects when activities are idempotent.

Choreography pros / orchestration risks

  • Teams deploy consumers independently; adding a subscriber does not require orchestrator changes.
  • Throughput scales with partitioned logs and consumer groups—not a single workflow cluster.
  • Orchestrator outage or misconfiguration can stall every in-flight process that depends on it.
  • Central workflow code can absorb domain logic if not guarded—governance must cap orchestrator scope.
  • Choreography without correlation IDs and a saga read model often lacks “where is my order?” answers operations expect.

Implementation notes

Orchestration: Write workflows as deterministic control flow; perform I/O in activities or task workers with explicit retry policies. On Temporal, avoid non-deterministic calls inside workflow code—clock and randomness come from the engine. On Step Functions, keep state machines focused on integration and use activity ARNs or Lambda tasks for side effects; store business payloads by reference when histories grow large. Version workflow definitions so in-flight instances finish on the definition they started with.

Choreography: Register event schemas (Avro, Protobuf) with compatibility rules. Design consumers to be idempotent and safe under at-least-once delivery. Propagate correlation identifiers on every message header. Build a saga audit projection—one read model that ingests all saga-related events and exposes current status—to recover operations visibility choreography does not provide by default. Document compensating events (“payment failed → publish RefundRequested”) and who emits them.

Hybrid: Orchestrate the critical path (payment, inventory commit) and choreograph side effects (email, search, data warehouse). Boundaries stay clearer than putting every reaction inside one giant workflow.

Common failure modes

  • Event chain fog: Ten services each publish and listen; nobody can diagram the happy path without grep across repositories.
  • Orphaned saga step: Payment succeeds; inventory consumer crashes; no compensating event or orchestrator step triggers a refund.
  • Workflow non-determinism: Direct use of wall-clock or randomness in replay-based engines breaks recovery after restart.
  • Breaking schema rollout: A required field is added to an event; one stale consumer stops processing and blocks the pipeline silently.
  • Orchestrator capacity: All workflow traffic hits one region or cluster; hot partitions on the log are easier to scale than a saturated workflow control plane.

Decision checklist

  • Is the process mostly linear with defined failure handling (orchestration) or an evolving set of reactions (choreography)?
  • Must operations answer “current state of instance X” within seconds?
  • Will workflows run longer than a single request timeout (days, weeks)?
  • Do multiple teams own steps and need decoupled release cadences?
  • Are compensating actions explicit, tested, and owned—regardless of style?
  • For choreography, is there a saga audit or equivalent read model for visibility?
  • Is the orchestrator restricted to routing, timers, and compensation—not business rules?

Example use cases

  • Illustrative scenario — Meridian Commerce runs checkout fulfillment in Temporal: charge, reserve, ship, and notify each as retried activities, with refund and release activities on a defined compensation path.
  • Illustrative scenario — RideRelay publishes TripCompleted; billing, driver payout, and analytics consumers react independently—marketing can add a new subscriber without touching the trip service.
  • Case study — Uber and other large platforms describe choreographed domain events for many operational flows, while payment and safety-critical paths often retain stricter centralized coordination—mixed models are normal at scale.
  • Case study — AWS customers widely use Step Functions for human-in-the-loop processes (claims, provisioning) where wait states and visual execution history justify orchestration overhead.

Related patterns

  • Saga Pattern — Distributed transactions as orchestrated or choreographed sagas with compensating steps.
  • Event-Driven Architecture — Foundation for choreography and for event-carried state transfer.
  • Enterprise Service Bus — Historical hub orchestration; compare with thin workflow engines and direct service APIs.
  • Transactional Outbox Pattern — Reliable event publication so choreographed steps see consistent facts.
