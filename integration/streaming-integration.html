Streaming Integration

Streaming integration moves and transforms data as continuous event flows—when sub-minute freshness justifies always-on processors, state, and careful delivery semantics.

⏱ 12 min read

What it is

Streaming integration moves and transforms data continuously as events are produced, with latency typically in milliseconds to seconds instead of the minutes-to-hours of batch jobs. A stream processor subscribes to durable logs—Apache Kafka topics, Amazon Kinesis shards, Azure Event Hubs, or Google Pub/Sub—applies filters, joins, windows, and aggregations, and writes results to other topics, databases, search indexes, or APIs.

Common runtimes include Kafka Streams (embedded JVM library for Kafka-centric transforms), Apache Flink and Spark Structured Streaming (clustered engines with rich state and SQL APIs), Apache Beam with Google Dataflow or Flink runners, and managed Flink on Amazon Managed Service for Apache Flink or Azure Stream Analytics. Pipelines may be stateless maps or stateful joins and windows backed by RocksDB with checkpointed delivery semantics from at-least-once toward exactly-once when brokers and sinks participate in transactions.

Why it exists

Fraud scoring, inventory holds, live product recommendations, and infrastructure autoscaling need reactions within seconds—or milliseconds—of the triggering event. Nightly batch cannot bound financial loss from card testing or stockouts from lagging cache invalidation. Product and risk stakeholders often articulate freshness as a ceiling (“under 60 seconds”) that batch schedules cannot meet without unrealistic micro-batch churn.

Streaming enables patterns batch cannot: continuously updated materialized views, search and cache refresh fed by CDC, reactive microservices that subscribe to domain topics, and operational intelligence that detects burst patterns before humans open tickets. Historical Lambda architectures split batch and speed layers; modern Flink and Beam deployments often unify real-time and reprocessing in one engine with savepoints and log replay, reducing dual-pipeline maintenance. The trade is operational: you trade cron simplicity for always-on jobs, consumer lag runbooks, and schema compatibility across every producer on the shared log.

When to use

  • Fraud and anomaly detection that must evaluate transactions within milliseconds of authorization.
  • Operational dashboards where business users expect freshness under one minute.
  • Event-driven microservices where downstream services react to domain events instead of polling OLTP databases.
  • Streaming ETL that keeps warehouses, lakes, or search indexes current from CDC or application logs.
  • IoT and telemetry at high volume—filter, aggregate, and route sensor readings inline.
  • Automated remediation—circuit breakers, autoscale, or paging driven by live metric or event streams.

When not to use

  • Batch-grade freshness: Hourly or daily SLAs—use batch integration for simpler ops and cost.
  • Global exact aggregates over complete history (e.g., month-to-date rank of all users)—batch or OLAP is more accurate.
  • Mandatory exactly-once without transactional Kafka consumers or idempotent upsert sinks—end-to-end guarantees will not hold.
  • Immature operations: No capacity for checkpoints, state sizing, consumer lag alerting, and staged replay drills.
  • Low event volume: A handful of messages per hour does not justify always-on Flink clusters—a well-instrumented batch or API push is cheaper and easier to reason about.

Typical architecture

Producers or CDC connectors append to partitioned logs; consumer groups or Flink parallelism assign partitions to workers. Stream jobs maintain keyed state locally (RocksDB) or in managed stores, checkpoint asynchronously to object storage, and emit to sinks with delivery semantics matched to each destination. Event-time watermarks bound how long windows wait for late records; side outputs route stragglers to reconciliation topics instead of silent drops. Schema Registry (Avro/Protobuf/JSON Schema) keeps serde compatible across job upgrades.

Pros and cons

Pros

  • Low latency: Results visible milliseconds to seconds after the event—enables real-time products batch cannot.
  • Continuous output: Downstream consumers receive a stream of updates instead of waiting for a batch window.
  • Incremental work: Process only new records; avoid rescanning full history each scheduled run.
  • Event-time correctness: Watermarks and windowing attribute out-of-order events to the time they occurred, not arrived.
  • Fault tolerance: Checkpoints and changelog-backed state enable recovery without re-reading unbounded source history.
  • Fan-out: One durable log feeds many independent stream processors with isolated consumer groups.

Cons

  • Complexity: Watermarks, state TTL, serde evolution, and delivery semantics exceed batch cognitive load.
  • Always-on cost: Continuous compute and state storage exceed on-demand batch for the same raw volume.
  • State burden: RocksDB or remote state backends must be sized, checkpointed, and compacted.
  • Harder debugging: Reproducing bugs requires offset replay or savepoint restores with the same event ordering.
  • Late-data trade-off: Longer watermark delays improve completeness but hurt freshness—permanent tuning, not one-time setup.

Implementation notes

Kafka Streams: Use the DSL (KStream, KTable, GlobalKTable) for embedded Kafka-to-Kafka transforms without a separate cluster. Changelog topics back local RocksDB for fault tolerance. Prefer GlobalKTable for small reference joins to avoid co-partitioning constraints. Tune commit.interval.ms and cache.max.bytes.buffering for latency versus throughput. See Kafka Streams documentation for semantics and operational metrics.

Apache Flink: Configure WatermarkStrategy.forBoundedOutOfOrderness for skewed event time; use allowedLateness or side outputs so late events reconcile instead of vanish. Enable incremental RocksDB checkpoints to S3, GCS, or Azure Blob every 30–60 seconds; align checkpoint timeout with interval to avoid cascade failures. For Kafka sources/sinks, set semantic = EXACTLY_ONCE only when downstream participates—see Flink Kafka connector transactional settings.

Spark Structured Streaming: Choose micro-batch (default) or continuous processing based on latency targets; pair with Delta Lake or Iceberg for idempotent sink merges. Monitor query progress and state store size; trigger backpressure when shuffle or state explodes.

Managed and Beam: Dataflow and Managed Flink absorb cluster upgrades when you can accept vendor operational models. Beam unifies batch and stream APIs—portable pipelines trade some engine-specific tuning for consistency across runners.

End-to-end semantics: Treat exactly-once as a chain: transactional Kafka consume-produce, idempotent upserts (PostgreSQL ON CONFLICT, Elasticsearch external version), or explicit dedupe keys at HTTP sinks. Document replay: reset consumer offsets with approval, or restore Flink from savepoint in staging before production.

Observability: Export Flink’s built-in metrics or Kafka Streams streams-metrics to Prometheus or CloudWatch; correlate operator backpressure with sink latency. Trace with OpenTelemetry where brokers and jobs support context propagation across topic boundaries. Run game days that pause a partition leader, restore from savepoint, and measure duplicate rate at sinks—teams discover “exactly-once on paper” gaps only under failure injection.

Monitor consumer lag per partition, checkpoint duration, state size, and records-per-second dropped as late. Alert when lag approaches retention.ms—unprocessed data loss is irreversible after broker retention trims the log. Size Kafka partitions for parallelism you will actually use; rebalancing without planned rebalance causes latency spikes that look like application bugs.

Common failure modes

  • Unbounded state growth: Keyed state without TTL or idle-time eviction fills RocksDB until checkpoints time out and the job fails.
  • Watermark stall: Idle partitions (no events) freeze minimum watermark; event-time windows stop closing across the job.
  • Checkpoint timeout cascade: State or shuffle too large for the interval; Flink aborts checkpoints, fails over repeatedly, and creates processing gaps.
  • Consumer lag explosion: Traffic spike overwhelms throughput; hours of stale enrichment propagate to fraud rules or dashboards.
  • False exactly-once: Transactional Kafka read-write but duplicate HTTP or search index writes on recovery—sink did not participate.
  • Schema mismatch on deploy: Producers ship a new Avro field without registry compatibility; deserializers crash mid-window.
  • Kafka retention overrun: Consumer lag exceeds retention.ms; brokers delete unread segments and backfill requires costly historical replay from object storage or warehouse exports.

Decision checklist

  • Is sub-batch latency a documented requirement—not a default preference for “modern” architecture?
  • Is the engine appropriate: Kafka Streams for light Kafka transforms, Flink for heavy state, Beam for portable multi-cloud?
  • Are checkpoints reliable, state backends capacity-planned, and TTL defined for keyed state?
  • Are watermark, lateness, and side-output policies explicit instead of silently dropping late events?
  • Does each sink support the delivery guarantee you advertise to downstream teams?
  • Is consumer lag alerted per topic/partition with thresholds tied to retention and business SLAs?
  • Can operators replay from offsets or savepoints in a staging environment before touching production?

Example use cases

  • Illustrative scenario — Meridian Commerce runs a Flink job on payment events: per-account five-minute tumbling windows track velocity; alerts publish to a Kafka topic within 200 ms of each authorization.
  • Illustrative scenario — Kafka Streams consumes Debezium CDC topics, joins orders against a GlobalKTable of product reference data, and writes enriched records for a warehouse connector with sub-minute freshness.
  • Illustrative scenario — A Flink application ingests 100k sensor readings per second from Kinesis, computes thirty-second rolling averages per device, and pages maintenance when readings exceed three sigma from baseline.
  • Case study — Streaming Systems (Akidau, Chernyak, Lax) documents watermark and correctness models used in Google-scale pipelines and adopted widely in Flink deployments.

Related patterns

  • Batch Integration — Higher latency and fewer moving parts when freshness goals allow scheduled jobs.
  • Change Data Capture — Common upstream; Debezium and similar connectors feed Flink or Kafka Streams.
  • Event Streaming — Kafka, Kinesis, and Pub/Sub as the durable log substrate.
  • Event Sourcing — Application design that often pairs with stream processors building read models.
