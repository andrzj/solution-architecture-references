Streaming Integration

Streaming integration moves and transforms data as continuous event flows—when sub-minute freshness justifies always-on processors, state, and careful delivery semantics.

⏱ 12 min read

What it is

Streaming integration connects systems by processing a continuous flow of events—usually from a durable log such as Kafka or Kinesis—through stream processors that filter, enrich, join, aggregate, and write results to operational stores, other topics, or analytics sinks. Processing is incremental: each event is handled as it arrives (or within micro-batches), rather than waiting for a scheduled batch window.

Runtimes include Kafka Streams (library embedded in your service), Apache Flink and Spark Structured Streaming (clustered engines), and managed offerings (Kinesis Data Analytics, Google Dataflow). Pipelines may be stateless transforms or stateful (windows, sessions, fraud counters) with checkpoints and configurable delivery semantics from at-least-once toward exactly-once where the stack and sinks support it.

Why it exists

Fraud scoring, live dashboards, inventory reactions, and operational alerting need answers in seconds or milliseconds. Batch windows cannot meet those SLAs without unacceptable risk or customer impact.

Streaming also powers event-driven architectures: materialized views, search and cache refresh from CDC, and cross-service reactions without polling databases. Unified stream engines increasingly handle both real-time and historical reprocessing, reducing the old split between “speed” and “batch” layers.

When to use

  • Detection or customer-facing behavior must react within seconds of an event.
  • Dashboards or operational views need freshness well under a batch period.
  • Downstream services subscribe to domain events instead of polling source databases.
  • Search, cache, or warehouse loaders should track CDC or logs continuously.
  • High-volume sensor or telemetry streams need inline filter, aggregate, and route.
  • Automation (scale, breakers, alerts) driven by live metrics or event patterns.

When not to use

  • Hourly or daily freshness is sufficient—use batch integration.
  • Global exact aggregates over complete history—batch or OLAP is a better fit.
  • Mandatory end-to-end exactly-once without transactional or idempotent sinks.
  • No capacity to operate checkpoints, state stores, lag alerts, and replay drills.

Typical architecture

Producers or CDC connectors append to partitioned logs. Stream jobs consume with consumer groups, maintain keyed state in RocksDB or similar, checkpoint to durable storage, and emit to sinks. Event-time watermarks bound how long windows wait for late records; side outputs can capture stragglers for reconciliation.

Pros and cons

Pros

  • Low end-to-end latency from event to action or visible metric.
  • Incremental work—no full rescan of history each run.
  • Event-time windows handle out-of-order delivery when watermarks are tuned.
  • Fault tolerance via checkpoints and changelog-backed state.
  • Same log can feed many independent streaming consumers.

Cons

  • Higher design and ops burden than batch (state, watermarks, lag).
  • Always-on compute cost versus scheduled jobs.
  • State growth without TTL or compaction risks disk and recovery time.
  • Incidents need replay and time-travel debugging skills.
  • Freshness vs completeness trade-off on late events is permanent tuning work.

Implementation notes

Kafka Streams suits embedded Kafka-to-Kafka transforms; use GlobalKTable for small reference data joins and tune commit.interval.ms for latency. Flink fits heavy state, event-time joins, and managed cloud runners—set bounded-out-of-order watermarks, allowedLateness or side outputs for late records, and incremental checkpoints to object storage.

Treat end-to-end exactly-once as a contract: transactional Kafka producers/consumers, idempotent upserts, or dedupe keys at sinks that cannot enlist in a transaction. Monitor per-partition lag, checkpoint duration, and state size; alert before retention would delete unread inputs.

Document replay procedures: reset offsets or launch savepoint restores in staging before production incidents.

Common failure modes

  • State bloat: missing TTL on keyed state fills RocksDB.
  • Stuck watermarks: idle partitions freeze event-time progress.
  • Checkpoint timeouts: state too large for the chosen interval.
  • Lag avalanches: spike overwhelms throughput; downstream sees stale joins.
  • False exactly-once: transactional read from Kafka but duplicate HTTP writes to search indexes.

Decision checklist

  • Is sub-batch latency a hard requirement, not a default preference?
  • Is the engine choice matched to state complexity (Streams vs Flink vs Beam)?
  • Are checkpoints reliable and state backends capacity-planned?
  • Are watermarks, lateness, and side outputs defined—not silent drops?
  • Does each sink support the delivery guarantee you advertise?
  • Is consumer lag alerted per topic/partition with retention-aware thresholds?

Example use cases

  • Illustrative scenario — A payment stream job maintains per-account velocity windows and publishes fraud signals within hundreds of milliseconds of each transaction event.
  • Illustrative scenario — CDC order events are enriched with product reference data and streamed into a warehouse loader for sub-minute analytics freshness.
  • Case study — LinkedIn’s public engineering writing describes Kafka-scale stream processing for metrics and product features; Flink and Kafka Streams power similar patterns across the industry.

Related patterns

  • Batch Integration — higher latency, lower moving parts.
  • Change Data Capture — frequent upstream for integration pipelines.
  • Event Streaming — durable log substrate (Kafka, Kinesis).
