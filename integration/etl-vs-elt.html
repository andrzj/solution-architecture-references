ETL vs ELT

ETL shapes data before load; ELT lands raw data first and transforms in the warehouse—choose based on where compute, compliance, and flexibility must live.

⏱ 10 min read

What it is

ETL (extract, transform, load) runs transformation in a pipeline or integration engine before shaped data lands in the destination warehouse or mart. ELT (extract, load, transform) loads raw or lightly typed data into the destination first—often cloud object storage plus a warehouse—and transforms it there with SQL, Spark, or dbt. The choice is where compute and schema commitment happen, not a branding distinction between vendors.

Classic ETL matched expensive, capacity-constrained warehouses and dedicated ETL servers (Informatica, SSIS, IBM DataStage). Cloud platforms with cheap storage and elastic SQL (Snowflake, BigQuery, Amazon Redshift, Azure Synapse) made landing raw data first practical; teams version transforms as code in the warehouse. Many estates mix both: ETL for heavy cleansing or compliance at the edge, ELT for analytics marts inside the warehouse.

Why it exists

Operational systems are optimized for transactions, not cross-domain reporting. Integration must extract from databases, APIs, files, and streams, align schemas, enforce quality rules, and deliver datasets analysts and applications can trust. When warehouse storage was scarce, transforming upstream minimized bytes stored and simplified physical models loaded once.

ELT reframes the warehouse as the transformation engine: storage is inexpensive, compute scales elastically, and keeping raw landing zones preserves optionality when definitions change. Incremental ingestion from change data capture and managed connectors (Fivetran, Airbyte, AWS DMS, Azure Data Factory) feeds the same pattern—load first, model in SQL—with shorter time-to-insight for new sources.

When to use

  • ETL when the destination has limited storage or CPU and you must filter, aggregate, or mask before any byte is persisted.
  • ETL when transforms need engines beyond warehouse SQL—graph algorithms, ML features, or calls to external validation APIs during the pipeline.
  • ETL when compliance requires redacting or tokenizing sensitive fields before they enter the analytics environment.
  • ELT when the target is a cloud warehouse or lakehouse with scalable SQL/Spark and separated storage and compute.
  • ELT when analysts need retained raw history to explore, re-run models, or backfill after logic changes.
  • ELT with dbt when transformation should live in version-controlled SQL with tests, documentation, and lineage in CI.

When not to use

  • Do not run a heavyweight ETL server when warehouse-native SQL and dbt already meet quality and scheduling needs.
  • Do not land completely unvalidated garbage into raw zones without structural checks—fail fast at extract or staging.
  • Do not force batch ETL tools onto sub-minute freshness requirements—use streaming integration or CDC instead.
  • Do not combine extract, complex transform, and load in one opaque script—stages should restart independently with clear observability.

Typical architecture

ETL pipelines stage data, transform in a dedicated engine, then load curated tables. ELT loads into raw layers inside the warehouse or lake, then builds staging and mart models with SQL transformations orchestrated by a scheduler.

Pros and cons

ELT pros

  • Raw history remains available for new models without re-extracting from operational sources.
  • SQL models in dbt are reviewable, testable, and approachable for analytics engineers.
  • Warehouse compute scales for large transforms without operating separate ETL clusters.
  • Faster iteration when business rules change—rebuild marts from raw, not re-pull sources.
  • Built-in lineage and documentation patterns in modern transformation frameworks.

ELT cons / ETL strengths

  • Raw zones may store regulated data that must be masked earlier—ETL enforces policy at ingress.
  • Ad hoc full-table dbt runs can spike warehouse spend without guardrails.
  • ELT needs a capable SQL/Spark platform; weak destinations cannot absorb in-place transforms.
  • Non-SQL logic (complex dedupe, ML, external enrichment) still wants Spark or ETL engines.
  • Ingestion and query pricing on some clouds penalize wide raw tables if not lifecycle-managed.

Implementation notes

For ELT, use managed extract/load (Fivetran, Airbyte, AWS Glue connectors, Azure Data Factory copy activities) into a raw schema or lake path. Layer dbt models: staging renames and casts, intermediate joins, marts for consumption. Apply dbt tests and freshness checks; orchestrate with Airflow, Dagster, or cloud schedulers.

For ETL, separate landing on object storage, transform on Spark (EMR, Dataproc, Databricks), and idempotent load via MERGE or warehouse bulk APIs. AWS Glue and Azure Data Factory provide managed ETL with lineage hooks; Apache Camel can orchestrate file/API extracts in hybrid estates. Use incremental watermarks or CDC instead of nightly full extracts when sources grow.

Document batch interfaces with AsyncAPI or internal catalogs when pipelines are event-triggered. Align retention and encryption on raw layers with security policy; reverse ETL tools should respect operational write conflicts with explicit merge rules.

Common failure modes

  • Schema drift: Connector or API changes leave new columns unmapped; marts silently degrade.
  • Runaway warehouse cost: Full-scan models on huge raw tables run on every schedule without cost alerts.
  • Quality after load: Invalid rows reach marts because checks ran only in a forgotten staging step.
  • Non-incremental extract: Full reloads time out as source volumes grow.
  • Reverse ETL clobber: Warehouse pushes overwrite concurrent edits in operational CRMs.

Decision checklist

  • Does the destination support scalable in-warehouse transformation?
  • Must raw sensitive data ever land in the analytics environment?
  • Do transforms require capabilities beyond SQL?
  • Is historical raw retention required for reprocessing?
  • Who owns transformation code—platform engineers or analytics?
  • Are extracts incremental and idempotent end to end?

Example use cases

  • Illustrative scenario — SaaS billing data lands in Snowflake via a connector; dbt builds subscription marts while raw invoices remain for audit re-runs.
  • Illustrative scenario — An on-prem ETL job de-identifies clinical extracts before they touch a constrained Oracle warehouse.
  • Case study — dbt Labs popularized warehouse-native transformation as code—the pattern most cloud analytics teams label ELT today.

Related patterns

  • Change Data Capture — CDC supplies the extract leg of ELT when you need incremental freshness instead of polling source tables on a schedule.
  • Batch Integration — Traditional ETL jobs are a batch-integration flavor; compare schedule and SLA against streaming or micro-batch alternatives.
  • Data Warehouse — Curated warehouse tiers remain the usual publish target after transform logic in either ETL or ELT.
  • Data Lakehouse — Lakehouse platforms favor ELT with dbt- or Spark-style transforms directly on open table formats.
  • File-Based Integration — File drops still implement extract stages when partners cannot expose APIs or change logs.
