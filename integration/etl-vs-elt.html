ETL vs ELT

ETL shapes data before load; ELT lands raw data first and transforms in the warehouse—choose based on where compute, compliance, and flexibility must live.

⏱ 10 min read

What it is

ETL (extract, transform, load) is a data-integration pattern: data is extracted from source systems, transformed into the target schema in a dedicated processing engine outside the destination, then loaded into the warehouse or mart. On-premise Oracle, Teradata, and similar platforms charged heavily for storage and offered limited in-database compute—so heavy joins, aggregates, and cleansing ran on Informatica, SSIS, or DataStage servers and only refined rows crossed the load boundary.

ELT (extract, load, transform) reverses the order: connectors land raw or lightly typed data into cloud storage and the warehouse first, and transformation runs inside the destination with native SQL, Spark, or dbt models. Tools like dbt operationalize ELT by versioning transformation logic as SQL reviewed in pull requests. Massively parallel warehouses (Snowflake virtual warehouses, BigQuery slots, Redshift, Databricks SQL) made in-place transform cost-effective. The architectural choice is where compute and schema commitment live—not which vendor logo appears on the slide deck.

Many enterprises run a hybrid: ETL at the edge for PII masking, non-SQL enrichment, or constrained destinations; ELT inside the warehouse for analyst-owned marts and exploratory raw layers.

Why it exists

ETL emerged in the 1990s when enterprise warehouses were scarce, expensive on-premise appliances. Pre-transforming before load reduced storage bills and query complexity. Dedicated ETL servers moved, joined, aggregated, and cleansed data into star or snowflake physical schemas whose shape was fixed at load time—schema design upfront was mandatory because re-landing raw history was impractical.

ELT followed cloud platforms that decouple storage from compute and scale both independently. When object storage (S3, GCS) is cheap and warehouse SQL elastic, external transformation clusters lose their cost advantage. Loading raw first preserves optionality: business rules change, and teams re-run dbt models instead of re-extracting from operational sources. Reverse ETL—pushing curated warehouse metrics back to CRMs, ad platforms, or support tools—extends the warehouse from analytics terminus to operational hub. Incremental extraction via change data capture and managed EL tools (Fivetran, Airbyte, AWS DMS, Azure Data Factory) shortens time-to-insight for new sources while keeping the same load-first, transform-in-SQL rhythm.

When to use

  • ETL when the destination has limited storage or CPU (on-prem RDBMS, undersized managed warehouse) and raw volume would be prohibitively expensive to retain.
  • ETL when transformation needs capabilities SQL cannot express efficiently—ML feature engineering, fuzzy deduplication, graph traversals, or synchronous calls to external validation APIs during the pipeline.
  • ETL when compliance or data residency requires masking, tokenizing, or filtering PII before any record enters the analytics environment.
  • ELT when the target is a cloud warehouse or lakehouse (Snowflake, BigQuery, Redshift, Databricks, Synapse) with elastic SQL or Spark compute.
  • ELT when data science and analytics teams need raw, unfiltered history alongside curated marts for exploration and ad-hoc reprocessing.
  • ELT with dbt when transformation logic should live in version-controlled SQL with pull-request review, data tests (not_null, relationships), and generated lineage documentation.

When not to use

  • Do not operate a heavyweight ETL cluster when the warehouse and dbt already meet quality, scheduling, and lineage needs—the operational tax rarely pays off.
  • Do not load completely raw, unparsed payloads into ELT raw zones without structural validation; discovering corrupt rows in mart models delays remediation.
  • Do not force batch-oriented ETL tools onto sub-minute freshness—use stream processing (Flink, Kafka Streams) or CDC-fed micro-batches instead.
  • Do not combine extract, complex transform, and load in one opaque script—distinct restartable stages improve testability and observability.

Typical architecture

ETL pipelines stage data, transform in a dedicated engine, then load curated tables. ELT loads into raw layers inside the warehouse or lake, then builds staging and mart models with SQL transformations orchestrated by a scheduler.

Pros and cons

ELT pros

  • Raw data preserved in the warehouse; transformations re-run when requirements change without re-extracting from sources.
  • SQL logic version-controlled and tested via dbt—accessible to analytics engineers without a dedicated ETL operations team.
  • Cloud warehouse compute scales to large transforms; no separate transformation cluster to patch and capacity-plan.
  • Faster iteration: prototype models in SQL and promote to production without provisioning new infrastructure.
  • Lineage and documentation built into dbt—upstream and downstream dependencies traceable for impact analysis.

ELT cons / ETL strengths

  • Raw landing zones may retain PII requiring governance; ETL can mask and filter before data ever reaches analytics storage.
  • Warehouse compute costs spike when large dbt models full-scan multi-terabyte raw tables on every schedule.
  • ELT requires a capable destination; underpowered on-prem databases cannot absorb heavy in-place transformation.
  • Complex transforms (ML, external APIs, fuzzy matching) remain awkward or impossible in pure SQL ELT.
  • Some clouds charge for ingestion or repeated scans of wide raw tables—lifecycle and partition pruning matter.

Implementation notes

For modern ELT, use Fivetran or Airbyte for extract and load—managed connectors handle incremental sync, schema drift detection, and retries across hundreds of SaaS and database sources. Land into a dedicated raw schema or lake path. Build dbt layers: staging models rename and cast columns; intermediate models encode joins and business rules; mart models expose reporting-ready aggregates. Apply dbt tests and source freshness checks; orchestrate with Airflow, Dagster, or cloud-native schedulers.

For Spark-style ETL, structure distinct restartable stages: extract to a landing zone on S3 or GCS, transform on EMR, Dataproc, or Databricks, load via JDBC or warehouse bulk APIs (COPY INTO on Snowflake, bq load on BigQuery). Use checkpoint directories for stateful stream stages. Prefer MERGE over blind INSERT so reruns stay idempotent. AWS Glue and Azure Data Factory provide managed ETL with job bookmarks and lineage hooks; Apache Camel can orchestrate hybrid file and API extracts.

Use CDC or high-water marks instead of nightly full-table extracts as sources grow. Document pipeline contracts in internal catalogs or AsyncAPI when jobs are event-triggered. Align raw-layer retention and encryption with security classification; reverse-ETL syncs need explicit conflict rules so warehouse pushes do not overwrite concurrent edits in operational CRMs.

Common failure modes

  • Schema drift breaks EL jobs: A source adds or renames a column; the connector fails or silently loads nulls into raw tables; downstream dbt aggregates drift for weeks.
  • Runaway warehouse costs: A dbt model full-scans a multi-terabyte raw table on every run; cost spikes surface only on the monthly cloud invoice.
  • No data quality gates in ETL: Invalid records (negative prices, impossible dates) load into the warehouse; reports show wrong figures until someone audits staging.
  • Big-bang load without incremental extract: Jobs re-read entire source tables each run; runtime grows until jobs time out.
  • Reverse ETL double-write: Warehouse sync overwrites changes users made directly in the operational CRM, causing confusion and data loss.

Decision checklist

  • Is the destination a cloud warehouse that supports scalable in-database SQL transformation?
  • Must raw sensitive data ever land in the analytics environment, or only cleaned shapes?
  • Does transformation logic require capabilities beyond SQL (ML, external APIs, complex algorithms)?
  • Are PII or residency rules compatible with retaining raw history in the warehouse?
  • Do analysts or analytics engineers own SQL transformation via dbt with review and test discipline?
  • Are extract and load strategies incremental and idempotent end to end?

Example use cases

  • Illustrative scenario — Harborline Retail loads billing, CRM, and product Postgres replicas into Snowflake via connectors; dbt builds a customer-360 mart while raw invoice JSON remains for audit re-runs.
  • Illustrative scenario — Summit Outfitters runs an on-prem ETL pipeline that de-identifies clinical-adjacent wellness program extracts before they reach a capacity-constrained Oracle warehouse.
  • Illustrative scenario — Crestwave Commerce syncs lifetime-value scores from BigQuery to its sales CRM via reverse ETL, with merge keys and timestamps so rep edits in the CRM are not blindly overwritten.
  • Case study — dbt Labs popularized warehouse-native transformation as code—the pattern most cloud analytics teams now label ELT.

Related patterns

  • Change Data Capture — CDC provides low-latency incremental extraction for ELT pipelines, replacing batch polling of wide OLTP tables.
  • Batch Integration — Classic ETL jobs are a batch-integration flavor; compare schedule and SLA against streaming or micro-batch alternatives.
  • Data Warehouse — Curated warehouse tiers remain the usual publish target after transform logic in either pattern.
  • Data Lakehouse — Lakehouse platforms often combine ELT with dbt or Spark on Delta Lake, Iceberg, or Hudi.
  • File-Based Integration — Partner file drops still implement the extract leg when APIs or change logs are unavailable.
