File-Based Integration

File-based integration moves data as batch files between partners or systems—drop zones, polling, and events—when APIs are impractical and an archivable artifact matters.

⏱ 9 min read

What it is

File-based integration exchanges data as files between systems or trading partners: a producer writes a batch to a agreed location (SFTP directory, object-storage prefix, AS2 endpoint), and a consumer picks it up, validates, parses, and loads downstream stores. Timing is asynchronous—neither side must be online at the same instant—and each transfer is a discrete artifact you can archive, replay, or quarantine.

Formats range from CSV and fixed-width legacy layouts through JSON and XML to EDI (X12, EDIFACT) and columnar Parquet or Avro for analytics handoffs. Transport is commonly SFTP, AS2, or cloud object storage with event notifications; plain FTP should be avoided where security standards matter.

Why it exists

Store-and-forward decoupling survives outages: files accumulate in a landing zone until the consumer is healthy. That model fits partners who cannot host APIs, regulated workflows that need a point-in-time evidence bundle, and bulk transfers too large for comfortable synchronous HTTP.

B2B ecosystems standardized on files long before REST became ubiquitous; mandating SFTP or EDI for purchase orders, claims, or statements is still the pragmatic lowest common denominator across thousands of counterparties with uneven engineering maturity.

When to use

  • Trading partners standardize on SFTP, AS2, or EDI rather than bespoke APIs.
  • Exports and imports are inherently batch (statements, regulatory bundles, catalog snapshots).
  • Compliance needs an immutable received file with timestamp and checksum evidence.
  • Legacy sources can only drop files; changing them is out of scope.
  • Multi-gigabyte payloads fit object storage better than chatty APIs.
  • Intermittent connectivity makes polling or event-driven pickup acceptable.

When not to use

  • Sub-minute or interactive latency—use APIs, queues, or streams.
  • Synchronous request–response with immediate business acknowledgement.
  • One-file-per-transaction at high frequency—overhead dominates versus messaging.
  • Sensitive data at rest in shared landing zones without encryption, retention policy, and access controls commensurate with risk.

Typical architecture

Partners land files in an inbound zone; a poller or object-created event invokes an ingestion service that validates schema, checksum, and completeness signals before transform and load. Successful files move to processed or archive prefixes; failures go to a quarantine path with alerts on age and backlog depth.

Pros and cons

Pros

  • Loose coupling across time zones and maintenance windows.
  • Archivable, replayable artifacts for audit and dispute resolution.
  • Ubiquitous support—minimal client software beyond SFTP or upload tooling.
  • Efficient bulk load paths (COPY, bulk APIs) once files land.
  • Buffers bursts when the consumer is temporarily unavailable.

Cons

  • Freshness tied to schedule, poll interval, or event propagation delay.
  • Risk of reading incomplete files without atomic write or sentinel conventions.
  • Coarse error granularity—whole-file reject versus partial accept is a product decision.
  • Operational tax: keys, allowlists, partner onboarding, and EDI mapping.
  • Slow coordinated schema change across many producers.

Implementation notes

On object storage, subscribe to ObjectCreated events via SNS or SQS and pass object key plus ETag into workers. Track processed fingerprints (ETag, SHA-256) in a small registry to make redelivery safe. Move successful objects to processed/ or archive/ immediately.

Use write-then-rename or companion .done files so consumers never parse in-flight payloads. Version file layouts in names or headers and reject unknown versions at the edge. For EDI, prefer managed translation (SPS Commerce, TrueCommerce, AWS B2B Data Interchange) over hand-rolled segment parsers.

Alert on oldest-unprocessed-file age, error rate per partner, and disk or prefix growth; partner-specific dashboards catch silent stalls before finance or ops does.

Common failure modes

  • Truncated ingest: consumer reads before the producer finishes writing.
  • Double load: manual re-drop or at-least-once pickup without idempotency keys.
  • Backlog blindness: consumer down while files pile up with no age alert.
  • Credential rot: expired SSH keys or certificates block pickup until reported manually.
  • Capacity surprise: file size jumps and blows memory or timeout limits.

Decision checklist

  • Is minutes-to-hours latency acceptable for this data product?
  • Does the partner mandate file protocols you must support?
  • Are completeness rules (rename, sentinel, checksum) agreed and tested?
  • Is reprocessing idempotent end-to-end through the database?
  • Are backlog age, quarantine depth, and per-partner failure rates monitored?
  • Is the format versioned with validation before load?

Example use cases

  • Illustrative scenario — A retailer ingests EDI purchase-order files from many suppliers via AS2, translates to canonical orders, and hands events to internal fulfillment.
  • Illustrative scenario — Finance ingests daily bank statement files from SFTP, matches ledger lines, and routes exceptions to an analyst queue.
  • Illustrative scenario — A clearinghouse exchanges nightly claim and remittance file pairs with payers over secured drop folders.

Related patterns

  • Idempotency — required for safe replays and partner redelivery.
