Integration B2B

File-Based Integration

File drop-and-pickup patterns for moving data between systems using files—S3 event triggers, SFTP polling, EDI transports, and idempotent processing with a durable audit trail.

⏱ 11 min read

What it is

File-based integration exchanges data by writing structured files to a shared location—a file server, SFTP drop zone, AS2 endpoint, or object-store prefix—that a receiving system polls or processes when object-created events fire. Despite API-first and event-driven alternatives, file transfer remains the workhorse of B2B settlement, healthcare batch feeds, retailer EDI, and government reporting because it is simple, auditable, and tolerates flaky connectivity.

Common formats include CSV and fixed-width flat files (legacy host output), JSON and XML, EDI (ANSI X12 in North America, EDIFACT internationally), and columnar Parquet or Avro for analytics handoffs. Transport is typically SFTP (SSH file transfer), AS2 over HTTPS with MDN receipts, or Amazon S3, Azure Blob, and Google Cloud Storage with event notifications. Plain FTP lacks encryption in transit—avoid it where partners or regulators expect modern controls; use AWS Transfer Family or equivalent managed SFTP when operational overhead of keys and HA file servers is a concern.

Why it exists

Store-and-forward decoupling lets producers and consumers run on different schedules and time zones: the sender writes a file; the receiver ingests when capacity and business windows allow. If either side is down, files accumulate in the landing zone rather than timing out synchronous calls. Every transfer is a named artifact with size, checksum, and receipt time—requirements regulators and auditors phrase as “the exact file we received on date D”—that streaming APIs rarely capture without additional logging discipline.

B2B ecosystems standardized on files when real-time APIs were impractical at scale. A retailer mandating AS2 EDI 850 purchase orders from hundreds of suppliers cannot require each supplier to build bespoke REST integrations; SFTP and EDI remain the lowest common denominator across counterparties with uneven engineering maturity. File integration also amortizes bulk work: loading ten million rows via COPY or bulk APIs from one landed file beats per-row HTTP under bandwidth and rate limits.

When to use

  • Trading partner standards: Counterparties require SFTP, AS2, or EDI for orders, claims, remittance, or catalog interchange.
  • Inherently batch exports: End-of-day reconciliation, monthly billing extracts, regulatory submissions, or snapshot catalogs.
  • Compliance evidence: Immutable received-file records with checksums and retention for financial clearing or healthcare claim trails.
  • Legacy-only outputs: Source systems can drop files but cannot be modified to expose APIs in the planning horizon.
  • Large payloads: Multi-gigabyte or columnar extracts where object storage and parallel readers outperform chatty APIs.
  • Intermittent connectivity: Cross-network transfers where asynchronous delivery is acceptable and polling or events are reliable enough.

When not to use

  • Near-real-time latency: Polling intervals and event propagation delay rule out sub-minute reactions—prefer APIs, queues, or streams.
  • Synchronous acknowledgement: Order placement, payment authorization, or inventory holds that must confirm in the same session.
  • High-frequency micro-files: One file per transaction at thousands per minute—message buses or Kafka topics handle overhead better.
  • Uncontrolled sensitive data at rest: Shared landing zones without encryption at rest, least-privilege IAM, retention limits, and virus scanning commensurate with risk.

Typical architecture

Partners write to an inbound prefix or SFTP path; an ingestion service triggered by cron, SQS, Lambda, or ECS on s3:ObjectCreated validates naming, schema version, checksum, and completeness signals (rename pattern or sentinel file). Valid payloads transform through a rules engine or EDI mapper, load downstream OLTP or warehouse tables with idempotent keys, then move to processed/ or immutable archive/. Malformed files land in quarantine/ with correlation metadata for partner outreach. Operations monitor oldest file age, error rates per partner, and prefix growth—not only “last job succeeded.”

Pros and cons

Pros

  • Temporal decoupling: Producer and consumer need not be online simultaneously; maintenance windows do not block the other party.
  • Audit trail: Each file is an archivable artifact—reprocess, compare checksums, and satisfy dispute resolution without reconstructing API logs.
  • Universal tooling: SFTP clients, object uploads, and EDI VANs are commodity skills; no bespoke SDK per partner.
  • Bulk efficiency: Database COPY, JDBC batch, and warehouse bulk loads from one landed file maximize throughput.
  • Natural buffering: Backlog in the drop zone absorbs consumer outages without producer-side retry storms.

Cons

  • Freshness ceiling: Data is only as current as the poll interval, partner cadence, or event latency—not suitable for interactive SLAs.
  • Partial-read risk: Without atomic rename or sentinel conventions, consumers may parse incomplete files and load corrupt rows.
  • Coarse errors: Row 50,000 of 100,000 failing forces a product choice between whole-file reject and partial commit with reconciliation.
  • Partner operations: SSH key rotation, IP allowlists, EDI map maintenance, and AS2 certificate renewal scale with partner count.
  • Slow schema change: Adding a CSV column requires coordinated cutover across every producer and consumer.

Implementation notes

Object storage triggers: Configure S3 Event Notifications for s3:ObjectCreated:* to fan out to SNS, SQS, or EventBridge. Pass bucket, key, size, and ETag into workers so idempotency keys are stable. Track processed fingerprints (ETag or SHA-256 of content) in DynamoDB, PostgreSQL, or Redis; skip duplicates on partner redelivery. Enable server-side encryption (SSE-S3, SSE-KMS, or customer-managed keys) and bucket policies that deny public access. For Azure, use Blob Storage event notifications; for GCS, use Eventarc storage triggers.

Completeness and parsing: Use write-then-rename (orders.csv.tmp → orders.csv) or a zero-byte control file (orders.csv.done) before ingestion starts. Validate MIME, delimiter, and schema version in the first stage; quarantine early rather than polluting production tables. Stream-parse large CSV and EDI on disk or object ranges instead of loading entire files into heap. Cap concurrent transforms per partner so one hot batch cannot starve others.

SFTP and AS2: Prefer managed SFTP (Transfer Family, Azure SFTP, partner VAN) for HA and audit. Rotate keys on a calendar with automated expiry alerts. For AS2, retain MDN receipts and map them to business acknowledgements. For EDI, use managed translation (AWS B2B Data Interchange, SPS Commerce, TrueCommerce) instead of hand-rolled X12 segment loops—997/999 functional acknowledgements and partner-specific quirks are where homegrown parsers fail.

Operations: Dashboard oldest-unprocessed-file age, quarantine count, and per-partner error rate. Run periodic reconciliation jobs that compare file manifests to loaded row counts. Document replay: move from archive back to inbound with a new idempotency key or controlled offset reset in the job repository.

Common failure modes

  • Partial file processing: Consumer reads before the producer finishes writing; truncated files load corrupt records unless checksum validation fails the batch.
  • Duplicate processing: Manual re-drop or at-least-once pickup without idempotency creates duplicate orders, payments, or claims.
  • Silently stuck queue: Consumer crashes while files accumulate; without age alerting, data stays stale until a business user reports missing settlements.
  • SFTP key or certificate expiry: Connection failures linger until partner rotation; automate monitoring of key not-after dates and AS2 cert health.
  • File size growth: A ten-times spike in row count OOMs the parser or exceeds Lambda timeout—size histograms and adaptive chunking prevent surprise crashes.
  • Encoding and locale drift: Partner switches UTF-8 to Latin-1 without notice; garbled characters pass validation but break downstream matching.

Decision checklist

  • Is minutes-to-hours latency acceptable for this data product and downstream consumers?
  • Does the partner mandate SFTP, AS2, or EDI—and who operates the endpoint (you, VAN, cloud managed)?
  • Are atomic write, sentinel, or checksum completeness rules documented and tested with the partner?
  • Is ingestion idempotent end-to-end using file fingerprint plus business natural keys?
  • Are backlog age, quarantine depth, and per-partner failure rates monitored with paging thresholds?
  • Is the file format versioned with rejection of unknown layouts at the edge?
  • Are encryption at rest, retention, and least-privilege access aligned with data classification?

Example use cases

  • Illustrative scenario — Northwind Logistics ingests EDI 850 purchase-order files from dozens of suppliers via AS2; a managed EDI service maps X12 to canonical JSON and publishes OrderCreated events to fulfillment.
  • Illustrative scenario — Finance receives daily BAI2 bank statement files over SFTP; S3-triggered workers parse fixed-width records, reconcile against the general ledger, and route unmatched lines to an analyst queue.
  • Illustrative scenario — A medical billing service uploads nightly EDI 837P claim batches to a payer SFTP drop; acknowledgements (277) and remittance (835) return files close the loop in the partner’s outbound directory.
  • Case study — Enterprise Integration Patterns’ File Transfer pattern formalizes the drop-and-pickup model that still underpins most B2B file exchanges decades after publication.

Related patterns

  • Batch Integration — File-based integration is often the ingest path for scheduled batch jobs that transform and load landed files.
  • Idempotency — Safe replays when partners redeliver or operators requeue from archive require idempotent loaders.
  • Claim Check Pattern — Store large payloads in object storage and pass references in messages instead of in-band bytes.
  • Enterprise Service Bus — File adapters on a bus normalize partner drops into canonical messages for downstream services.
