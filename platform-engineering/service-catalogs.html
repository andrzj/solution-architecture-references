Service Catalogs

The system of record for components, APIs, teams, and dependencies—fed by repo metadata, Kubernetes discovery, and Crossplane resources so incidents and changes start with accurate ownership.

⏱ 11 min read

What it is

A service catalog is the organisational graph of software components, APIs, resources, teams, and dependencies—most often implemented with Backstage’s Software Catalog and catalog-info.yaml descriptors, sometimes alongside Port, Cortex, or cloud vendor catalogs. It answers “what exists, who owns it, what does it depend on, and how mature is it?” without spelunking repositories.

On Kubernetes platforms, catalogs ingest cluster workloads (Deployments, Argo CD Applications) and Crossplane managed resources so infrastructure appears alongside application Components. The catalog is the index; TechDocs, scorecards, and software templates are the actions layered on top.

Why it exists

Microservice estates outgrow human memory. Incidents stall when ownership, runbooks, and upstream dependencies are unknown. Change risk is opaque without a dependency graph.

A maintained catalog turns platform investments—golden paths, self-service claims, SLO dashboards—into discoverable entities linked to teams and lifecycle state.

When to use

  • Tens to hundreds of services across multiple teams with rotation on-call.
  • Developer portal (Backstage) as the front door to engineering systems.
  • Production readiness or security scorecards tracked over time.
  • Kubernetes and Crossplane estates where automated ingestion beats manual YAML drift.
  • Need to gate deploys or audits on catalog metadata completeness.

When not to use

  • Single monolith, single repo—CODEOWNERS and README may suffice temporarily.
  • No process to update or validate metadata—stale catalogs are worse than none.
  • Catalog treated as wiki only with no relations to runtime (cluster, cloud).

Typical architecture

Pros and cons

Pros

  • Single pane for owner, docs, SLIs, and dependency blast radius.
  • Enables scorecards and deploy gates tied to metadata quality.
  • Foundation for golden paths—templates register entities on creation.
  • Kubernetes visibility links running pods to catalog Components.
  • API entities document consumers and deprecation timelines.

Cons

  • Requires CI validation and ownership culture—otherwise metadata rots.
  • Graph completeness is continuous work, not a one-time import.
  • Custom Crossplane-to-catalog bridges need maintenance.
  • Poor search UX leads to low adoption despite backend quality.
  • Duplicate entities when both Git and cluster invent the same service name.

Implementation notes

Mandate catalog-info.yaml via CI: block production deploy merges when missing or failing schema validation (Backstage catalog model). Co-locate with repos; use pull request review for dependsOn and owner accuracy.

Register clusters in Backstage; enable the Kubernetes plugin for runtime tabs. Build a small processor or use annotations on Crossplane claims to emit Resource entities with cloud IDs and cost tags.

Define entity kinds deliberately: Component (service), API (contract), Resource (database, bucket), System (product boundary), Domain (business area). Avoid orphan APIs without implementing Components.

Integrate on-call: link Group entities to PagerDuty services; nightly sync catches rotation drift. Publish scorecards (production readiness, on-road vs off-road) on entity pages.

TechDocs builds documentation from MkDocs in the service repo and surfaces it on the entity page—scorecards can fail entities whose TechDocs publish job has not succeeded recently. Keep catalog rows fresh: processors compare Git push timestamps to catalog metadata, nightly jobs mark entities whose source repo was archived, and deploy pipelines reject production promotion when catalog-info.yaml fails schema validation. Plugins (Kubernetes, Crossplane) attach runtime status beside static metadata so operators see drift between declared owner and live cluster labels.

Common failure modes

  • Ghost services: Decommissioned apps remain in catalog—tie deletion to deploy pipeline or quarterly catalog review.
  • Wrong on-call: PagerDuty integration stale; page platform when sync fails.
  • YAML fiction: dependsOn lists aspirational not actual dependencies—validate with service mesh or APM where possible.
  • Cluster-only entities: Workloads ingested without Git metadata lack docs links—require annotation to source repo.
  • Scorecard fatigue: Too many checks; teams ignore red status—prioritise few meaningful gates.

Decision checklist

  • Is catalog metadata validated in CI on every production-bound change?
  • Can on-call be resolved from any Component page in under thirty seconds?
  • Are Kubernetes workloads and key Crossplane resources represented as entities?
  • Do scorecards or deploy gates enforce minimum metadata before promote?
  • Is there an owner for catalog integrity (not “everyone”)?
  • Are decommissioned services removed on a defined lifecycle event?

Example use cases

  • Case study — Spotify: Backstage originated as their internal portal and catalog; open-sourcing spread the entity model widely.
  • Illustrative scenario — incident response: During a database outage, responders traverse dependsOn from the failing API to owning team and recent deploy via linked Argo CD Application.
  • Illustrative scenario — acquisition integration: Imported repos bulk-registered via template; scorecards highlight missing SLOs before cutover to shared Kubernetes.
