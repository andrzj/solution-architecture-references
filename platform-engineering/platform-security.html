Platform Engineering Security

Platform Security

Platform security delivers guardrails as platform services—admission policy, signed artifacts, automated secrets, and namespace RBAC—so the default path is compliant without per-team security archaeology.

⏱ 12 min read

What it is

Platform security is the set of controls the internal developer platform applies so every team inherits baseline posture—identity, secrets, network boundaries, and artifact trust—without reimplementing them in each repository.

On Kubernetes, admission is the primary enforcement point: OPA Gatekeeper and Kyverno evaluate create/update requests against versioned policies (non-root containers, required labels, approved registries, signed images). Gatekeeper runs Rego via ConstraintTemplates; Kyverno uses Kubernetes-native YAML rules and can mutate resources (for example inject labels or sidecars). For infrastructure-as-code, Open Policy Agent in CI or HashiCorp Sentinel in Terraform Cloud/HCP Terraform blocks plans that violate tagging, encryption, or network rules before apply.

Around the workload lifecycle, Cosign (Sigstore) signs images in CI; admission verifies signatures. The External Secrets Operator syncs secrets from Vault or cloud secret managers into namespaces on a schedule. Templated RBAC and NetworkPolicy bundles ship with each namespace. Backstage can surface security ownership, plugin links to vulnerability data, and catalog annotations that tie components to compliance scope.

Platform security is not a separate programme sitting beside the IDP: it is how paved roads enforce posture. Golden-path workflows should fail closed when scans, signatures, or policy checks do not pass, and namespace provisioning should attach the same RBAC and network defaults whether teams click “Create Service” in Backstage or call a platform API. That coupling is what turns “security guidelines” into measurable compliance signals auditors can sample from Git, registry metadata, and admission audit logs rather than slide decks.

Why it exists

Distributed ownership of security defaults produces predictable gaps: privileged pods, secrets in git, wide-open security groups, unsigned images. Central security teams cannot review every manifest at scale; admission and pipeline policy convert standards into automatic deny/warn decisions with an audit log.

Embedding controls in golden paths and platform APIs shifts effort from education to mechanics. A developer using a Backstage template or namespace provisioner receives IRSA bindings, default-deny network policy, and ESO-backed secrets whether or not they read the hardening guide.

Regulators and customers increasingly expect continuous evidence—SBOMs, signature provenance, policy reports—not quarterly attestations. Platform security generates that evidence as a side effect of delivery.

The economic argument matters too. When every squad rebuilds scanning, signing, and secrets plumbing, security cost scales linearly with team count and platform engineers become reviewers of endless one-off manifests. Centralising those capabilities behind self-service interfaces lets stream-aligned teams spend cognitive budget on product risk—fraud rules, data handling, customer trust—while the platform owns undifferentiated hardening that should not vary by repository.

When to use

  • Any multi-tenant Kubernetes fleet where workloads share a control plane—admission policy (OPA or Kyverno) from day one, audit mode before enforce.
  • Production clusters subject to SOC 2, PCI, or SSDF supply-chain expectations—Cosign signing plus admission verification.
  • Organisations standardising on Vault, Secrets Manager, or similar—ESO or equivalent as the only path for runtime secrets.
  • Terraform or OpenTofu at scale—OPA conftest or Sentinel policies on plans alongside Kubernetes admission.
  • Namespace-per-team models where RBAC and network policy must be provisioned atomically with the namespace.
  • Post-incident mandates to prove images were built internally and have not been tampered with in transit—signature verification at admission is the enforcement hinge.

When not to use

  • Enforce-before-audit: Shipping strict Gatekeeper or Kyverno deny rules directly to production without an audit window breaks legitimate workloads such as security scanners or legacy init containers that need specific UIDs.
  • Secrets sync without rotation design: External Secrets Operator mirrors vault values into the cluster, but applications that only read credentials at startup will keep stale passwords after rotation until reload paths are tested.
  • Keyless Sigstore offline: Cosign keyless flows depend on Fulcio and Rekor reachability; air-gapped fleets need private CAs, offline keys, or an internal Sigstore deployment.
  • Policy without paved roads: Mandatory controls that are not embedded in Backstage templates or golden-path CI still rely on voluntary compliance and will not scale across hundreds of services.

Typical architecture

Build-time scans and signing feed admission-time policy; runtime secrets and network segmentation complete the loop with centralized audit export.

Pros and cons

Pros

  • Platform-layer controls align with the CNCF Platforms White Paper promise: secure defaults ride along with self-service instead of living in optional wiki pages.
  • Versioned Gatekeeper or Kyverno policies in git give auditors a reviewable history of who changed which constraint and when.
  • Cosign signatures and transparency log entries tie running images to CI commits, which satisfies modern supply-chain evidence requests.
  • External Secrets Operator keeps long-lived credentials out of manifests while central stores retain rotation and access logging.
  • Namespace-scoped RBAC bundles lower the blast radius when a service account token leaks because cluster-admin is never the default.

Cons

  • Admission mistakes block deploys cluster-wide; audit mode and staged enforcement are mandatory operational habits, not nice-to-haves.
  • Rego and Kyverno policy languages require sustained expertise that competes with feature work on the same platform squad.
  • Keyless signing couples release velocity to Sigstore availability unless break-glass paths are rehearsed.
  • ESO itself becomes a high-value target because it can read many upstream secrets from one control plane.
  • Default-deny networking fails loudly when dependency graphs are incomplete, which forces upfront discovery work before enforcement.

Implementation notes

Roll out OPA Gatekeeper or Kyverno in audit mode across representative clusters, export violations to the same backlog rhythm as other platform defects, then enforce pod security baselines before cosmetic label rules. Store ConstraintTemplates in git and deploy them with the same GitOps pipeline that applies application manifests. Mirror critical policies in CI with conftest on rendered Helm or Kustomize output so pull requests catch issues before they reach the API server.

Treat the audit window as a remediation sprint, not a reporting exercise. Tag each violation with owning team, severity, and whether the workload is customer-facing. Enforce in waves: block privileged and hostPath patterns first, then unsigned images, then metadata hygiene. Pair each new constraint with a paved-road fix—Helm chart defaults, template parameters, or a documented exception workflow—so developers know how to pass policy without filing platform tickets.

For image trust, standardise on organisation-scoped registries and CI identities that can sign. Pin base-image digests in templates, attach CycloneDX or SPDX SBOMs as OCI artifacts, and verify signatures in admission with a policy that trusts only your internal issuers. Rehearse break-glass: annotated deploy requests, secondary signing keys, and time-bounded waiver CRDs should be documented in the runbook before the first production outage blocks a hotfix.

For External Secrets Operator, provision a ClusterSecretStore per environment with least-privilege IAM or Vault policies—not a single god-role for every namespace. Automate ExternalSecret creation in the same transaction as namespace creation; use path conventions like /platform/{team}/{env}/{secret} and reject hand-applied Secrets labelled otherwise. Run quarterly rotation drills: rotate upstream credentials, confirm ESO refreshes Kubernetes Secrets within the configured interval, and validate that applications reload without manual pod deletion unless a sidecar reloader is part of the golden path.

Wire image signing in shared golden-path workflows: build, scan, generate SBOM, sign with Cosign, and verify at admission. Document break-glass annotations that require on-call approval. Provision namespaces through Backstage or platform APIs so ExternalSecret objects, network policies, and RBAC bindings are created atomically. Surface ownership and compliance tags in the catalog so security champions know which components inherit which controls.

Workload identity binds runtime to policy: SPIFFE identities and SPIRE attestation issue short-lived SVIDs for mesh and batch jobs; on AWS IRSA and GCP Workload Identity map Kubernetes ServiceAccounts to cloud IAM roles so pods never mount long-lived access keys. Tenant RBAC scopes RoleBindings to namespace plus catalog Group; production namespaces deny privileged pods and hostPath via admission while sandbox tiers stay relaxed during onboarding. Supply-chain admission ties Cosign verification to trusted CI identities—unsigned or foreign-registry images fail closed unless a rehearsed break-glass waiver is recorded.

SPIFFE IDs are stable workload identifiers; SVIDs are short-lived certificates derived from them. SPIRE (or mesh integrations) rotates SVIDs before expiry and revokes on compromise. For tenant isolation, provision namespaces with default-deny NetworkPolicy (or Cilium equivalents) and explicit egress allowlists generated from golden-path dependency graphs. Graduate Pod Security Admission from baseline in sandboxes to restricted in production, with audit warnings in staging first. Platform-scoped Roles prevent one tenant’s CI from reading another namespace’s Secrets; reserve cluster-admin for break-glass automation only.

Common failure modes

  • Instant enforce: A new resource-limit constraint lands in production and blocks every deploy for services that never declared limits, turning a security win into a sev-1.
  • Signing outage during incident response: Fulcio downtime prevents hotfix images from passing admission even though application code is ready.
  • Over-scoped secret access: One ClusterSecretStore IAM role can read every environment’s passwords, so a single ESO bug becomes org-wide credential exposure.
  • CI with cluster-admin: Pipeline tokens bound too broadly let a compromised workflow rewrite any namespace, undoing namespace isolation goals.
  • Network policy late binding: Services start under default-deny without egress to their database because dependency edges were never captured in the golden path template.
  • Policy drift between CI and cluster: Teams pass conftest locally but production clusters run an older ConstraintTemplate revision until GitOps sync fails silently; treat policy repos as production dependencies with the same deployment alarms as application charts.

Decision checklist

  • Did admission policies accumulate at least two weeks of audit data with zero unresolved critical violations before enforce mode?
  • Do production clusters verify Cosign signatures on every deploy, with a tested break-glass exception path?
  • Are runtime secrets delivered only through ESO or an equivalent integration, with rotation drills documented per workload type?
  • Are namespace RBAC and network policies created automatically alongside the namespace, never hand-edited in production?
  • Does every production image produce and retain an SBOM artifact linked to the registry digest?
  • Do Backstage templates and platform APIs embed the same controls that admission enforces at the API boundary?

Example use cases

  • Illustrative scenario — admission hardening: A forty-person product org runs Kyverno in audit for three weeks against staging and production; the platform exports a CSV of privileged workloads and unbounded CPU pods. Streams fix chart defaults, then enforce mode flips on; regressions fail pull-request previews before they hit shared clusters. Monthly Gatekeeper or Kyverno compliance snapshots feed SOC evidence packs without manual screenshot hunts.
  • Illustrative scenario — signed images only: After a compromised public image appears in a sandbox cluster, leadership mandates internal-only base layers. Shared CI emits Cosign signatures bound to the build pipeline identity; admission rejects unknown digests. On-call carries a rehearsed waiver path for break-glass deploys, but every exception is logged to the transparency log for later review.
  • Illustrative scenario — secrets hygiene at scale: An audit finds database passwords embedded in Deployment YAML across dozens of repos. Over two quarters the platform migrates workloads to External Secrets Operator golden paths, purges history with approved git tooling, and blocks new plaintext secrets via pre-commit hooks plus admission denial of unlabelled Secret objects.
  • Case study — Shopify: Public engineering writing on bootstrapping security with policy-as-code and hardened supply chains informed many IDP teams’ sequencing of scan-then-sign-then-admit pipelines.

Related patterns

  • Internal Developer Platform — platform security controls are delivered as a component of the IDP, not as a separate security programme.
  • Platform APIs and Abstractions — Gatekeeper and RBAC templates are applied at the Kubernetes API layer, integrating with the platform API infrastructure.
  • Paved Roads and Golden Paths — security controls (image signing, SBOM generation) are embedded in golden path CI pipeline templates, making secure behaviour the default path.
  • Policy as Code — OPA, Kyverno, and Sentinel policy lifecycle across CI and clusters.
