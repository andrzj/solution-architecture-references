Policy as Code

Policy as code version-controls guardrails—OPA, Kyverno, Sentinel—and enforces them in CI, Kubernetes admission, and IaC plans so compliance is continuous, not a gate at release time.

⏱ 12 min read

What it is

Policy as code expresses organisational rules—security context, tagging, approved regions, license allowlists—as executable policies stored in git, reviewed in PRs, and evaluated automatically at enforcement points in the delivery path.

Open Policy Agent (OPA) evaluates Rego policies against JSON inputs. In Kubernetes, Gatekeeper implements admission with ConstraintTemplates; in CI, conftest tests Terraform plans, Helm charts, or Kubernetes manifests before merge. Kyverno is a Kubernetes-native alternative: policies are YAML resources that can validate, mutate, or generate resources without Rego. HashiCorp Sentinel embeds in HCP Terraform/Terraform Enterprise policy sets, running on plan output before apply—common for multi-workspace cloud governance.

Effective programs treat policies like shared libraries: named bundles per environment, explicit owners, semver or calendar versioning, and denial messages that link to fix documentation in Backstage or the developer portal.

Why it exists

Manual architecture review cannot keep pace with hundreds of daily deploys. Checklist fatigue produces inconsistent decisions—the same public S3 pattern is caught in one team and missed in another. Machine enforcement applies the same rule every time and leaves an attributable denial log.

Auditors ask for proof that controls run continuously. Policy repositories, CI test fixtures, and admission audit events provide evidence without screenshot archaeology.

Platform productization depends on policy: self-service CRDs and golden paths only stay safe if admission and plan policies guard what developers can declare.

When to use

  • Kubernetes production clusters—Kyverno or Gatekeeper for pod security, labels, image provenance, and resource quotas.
  • Terraform/OpenTofu org-wide—OPA conftest or Sentinel on every plan in CI or Terraform Cloud.
  • Pull-request gates—license scanning, secret patterns, and dependency policies before code merges.
  • Cost and compliance tags—deny cloud resources missing owner, environment, or cost-center metadata.
  • Platform APIs and Backstage templates—validate generated manifests against the same policy bundles developers use locally.

When not to use

  • Greenfield experiments where blocking would halt all learning—use audit/warn modes with time limits.
  • Policies without owners, tests, or semver—orphan rules become mysterious denials.
  • Duplicating the same rule in five tools without a single source of truth—consolidate bundles and sync to enforcement points.
  • One-shot “compliance theater” policies that are never enforced in production admission or apply paths.

Typical architecture

Policies flow from a central repository through CI test jobs, IaC plan gates, and cluster admission—with optional runtime drift detection feeding feedback to policy authors.

Pros and cons

Pros

  • Consistent, fast enforcement at every gate in the path to production.
  • Git history and PR review for policy changes, same as application code.
  • Reusable bundles across CI, Terraform, and Kubernetes reduce drift between teams.
  • Audit-friendly denial logs and exception registries.

Cons

  • Rego and advanced Kyverno patterns require training and peer review discipline.
  • Overly broad deny rules block delivery and erode trust—tuning takes sustained effort.
  • Exception processes can calcify into permanent bypasses if not time-boxed.
  • Multiple policy engines (Sentinel plus OPA plus Kyverno) need clear boundaries to avoid duplication.

Implementation notes

Start in audit or warn mode on production-adjacent clusters; collect violations for two to four weeks before enforce. Publish policy bundles per tier: baseline (always on), regulated (PCI/SOC scope), sandbox (relaxed). Test every rule with positive and negative fixtures in CI—Gatekeeper’s gator and Kyverno’s CLI support offline validation.

For OPA: keep Rego packages small; share helpers for label and tag assertions. For Kyverno: prefer mutate policies for defaults (labels, sidecars) and validate policies for hard denies. For Sentinel: scope policy sets per workspace and environment; return human-readable messages in policy outputs.

Instrument denials—count by policy, team, and cluster—and review monthly with platform and security stakeholders. Pair with Backstage documentation links in denial messages so developers know how to remediate without opening a ticket.

OPA Gatekeeper runs Rego via admission webhooks and ConstraintTemplates—ideal when the same Rego bundle already gates Terraform plans in CI. Kyverno expresses validate, mutate, generate, and cleanup rules in Kubernetes YAML without Rego, which lowers the bar for cluster admins but duplicates logic if Terraform policy lives elsewhere. Roll out audit mode first, export violations by team, remediate with template fixes, then enforce tier by tier. Time-bound exceptions live in a registry (annotation, waiver CRD, or ticket ID) with compensating controls and expiry—permanent bypasses defeat the purpose.

Common failure modes

  • Policy explosion: Hundreds of overlapping rules with conflicting semantics—consolidate into tiered bundles and delete unused constraints.
  • Enforce-day surprise: Flipping to deny without audit data blocks production deploys—always graduate enforcement after measurable cleanup.
  • Break-glass gap: Incidents stall because no documented, audited override exists for emergency deploys.
  • Untested Rego: A typo in a deny rule blocks an entire resource kind cluster-wide—fixture tests in CI catch this before promotion.
  • Engine sprawl: Terraform Sentinel and Kubernetes Kyverno encode the same tag rule differently and diverge—designate one source bundle and generate or mirror where possible.

Decision checklist

  • Does every production admission path run Kyverno or Gatekeeper policies synced from git?
  • Are Terraform/OpenTofu plans evaluated by OPA or Sentinel before apply in all workspaces?
  • Do policies have owners, semver or review dates, and CI tests with fixtures?
  • Is there a time-bound exception workflow with compensating controls recorded in the catalog?
  • Do denial metrics feed a monthly policy tuning ritual?
  • Do portal docs and denial messages point to the same remediation steps?

Example use cases

  • Illustrative scenario — FinOps tags: Sentinel policies reject Terraform plans when EC2 or RDS resources lack cost-center and owner tags; Kyverno audit reports list non-compliant namespaces for cleanup campaigns.
  • Illustrative scenario — image provenance: Kyverno verifies Cosign signatures on all Deployments in production; unsigned images fail admission with a link to the internal signing runbook.
  • Case study — Google Binary Authorization: Admission control tied to signed attestations influenced many platforms’ pattern of CI-generated provenance checked at deploy time—conceptually parallel to Gatekeeper/Kyverno plus Sigstore in open ecosystems.
