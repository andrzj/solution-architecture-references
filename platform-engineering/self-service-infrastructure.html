Platform Engineering

Self-Service Infrastructure

Policy-gated, automated provisioning of namespaces, data stores, and cloud resources through Crossplane on Kubernetes and portal workflows—without central ticket bottlenecks.

⏱ 11 min read

What it is

Self-service infrastructure lets product engineers provision approved platform resources—Kubernetes namespaces, databases, queues, caches, object storage—without ticketing a central ops team, while policy engines enforce guardrails before anything reaches production. The user experience is usually a portal form, CLI, or API; the implementation is declarative workflows (Crossplane on Kubernetes, Terraform/OpenTofu modules, or operators) plus audit and cost metadata.

On Kubernetes-heavy platforms, Crossplane compositions expose high-level claims (XRDs) that hide cloud provider APIs; reconciliation runs in the cluster control plane alongside application workloads. GitOps can manage claim YAML in app repos or a dedicated infra repo; either way the provisioned state is observable via kubectl, the catalog, and cloud audit logs.

Why it exists

Ticket-driven provisioning does not scale with microservice growth: developers wait days for environments, context-switch out of flow, and sometimes create shadow accounts. Self-service restores autonomy within boundaries the platform team defines once.

It also improves reliability—every provisioned database uses the same backup window, encryption, and network placement because the composition encodes those rules, not individual runbooks.

When to use

  • Mature landing zones (network, IAM, org policies) and a staffed platform team.
  • Crossplane compositions or vetted Terraform modules for high-demand resource types.
  • Ephemeral environments (per pull request) with automated TTL teardown.
  • Developer portal integration where request status is visible without Slack pings.
  • Policy-as-code (Kyverno, OPA, Sentinel) ready to validate plans and claims.

When not to use

  • No baseline security boundaries—self-service multiplies misconfiguration speed.
  • One-off bespoke infra where automation cost exceeds rare ticket cost.
  • Teams unable to operate Kubernetes or Crossplane control planes reliably.
  • Resources lacking automated destroy paths (orphan risk).

Typical architecture

Pros and cons

Pros

  • Provisioning latency moves from days to minutes for standard resources.
  • Compositions eliminate snowflake databases and buckets.
  • Full audit: who applied which claim, when, and resulting cloud resource IDs.
  • Quotas and label policies enforced uniformly at admission.
  • Developers stay in familiar GitOps and kubectl mental models on K8s platforms.

Cons

  • Building and maintaining compositions for every resource type is expensive.
  • Poor UX (opaque errors, no status page) sends teams back to tickets.
  • Crossplane control plane is another critical system to on-call.
  • Destroy flows are often neglected compared to create—cost and security debt.
  • Over-privileged provider credentials in the cluster are a high-value target.

Implementation notes

Start with a narrow catalog: dev Postgres, S3 bucket, K8s namespace, Redis—resources that generate the most tickets. Expand from ticket taxonomy quarterly.

Expose claims as namespaced CRDs with small parameter surfaces. Use composition Functions or patches for environment differences (dev vs prod) instead of duplicate XRDs. Store provider credentials in scoped IRSA/GCP WI identities per composition family.

Integrate Backstage: software templates for greenfield, “Add database” actions for brownfield. Return deep links—Grafana dashboards, runbooks, secret names, claim status conditions.

Implement TTL controllers or scheduled GitOps pruning for ephemeral envs. Make delete as automated as create; test teardown in CI with disposable accounts.

Crossplane exposes team-facing XRDs backed by Compositions that patch Managed Resources; developers apply claims with kubectl or portal actions while credential scope stays in ProviderConfigs. Terraform modules behind the same portal suit foundation resources or estates without a Kubernetes control plane—runs post plan artifacts and OPA/Sentinel gates before apply. Quotas cap claims per namespace or team; guardrails restrict parameter enums (instance sizes, regions). Require cost-center and owner labels on every claim so FinOps can join cloud billing exports to catalog owners for showback and anomaly alerts.

Common failure modes

  • Orphaned resources: PR namespaces and databases without TTL; run reapers and chargeback reports.
  • God-mode provider config: One cloud credential creates any resource; split ProviderConfigs per environment and use least privilege.
  • Claim stuck pending: Developers retry and duplicate; surface events in portal and alert platform on reconciliation errors.
  • Drift outside GitOps: Manual console edits fight Crossplane; enable management policies and drift detection.
  • Quota blind spots: Single team exhausts RDS subnet IPs; enforce per-team quotas at policy layer.

Decision checklist

  • Can developers see claim/workflow status without paging platform?
  • Are destroy/teardown paths automated and tested?
  • Do quotas prevent one team exhausting shared network or API limits?
  • Are provider credentials scoped and rotated with break-glass documented?
  • Does every provisioned resource appear in the service catalog with owner?
  • Are policy denials actionable (message + doc link), not opaque?

Example use cases

  • Illustrative scenario — PR environments: Opening a pull request applies a namespaced Claim set; Argo CD deploys the branch; TTL job deletes claims after seventy-two hours.
  • Illustrative scenario — data team self-serve: Analysts request read-only warehouse connections via portal; composition creates IAM role + Secret; catalog records lineage owner.
