Platform Engineering Pattern

Golden Paths

Executable, end-to-end workflows—from portal template to repo, catalog entry, Argo CD deploy, and optional Crossplane claims—so the fastest path to production is also the compliant one.

⏱ 11 min read

What it is

A golden path is a pre-built, tested, end-to-end workflow for a repeatable engineering task—creating a microservice, standing up a worker, or provisioning a standard environment—so the fastest way to complete the task is also the compliant way. Golden paths are usually delivered through a developer portal (Backstage Software Templates), shared CI workflows, and infrastructure claims that apply platform defaults automatically.

Unlike ad hoc documentation, a golden path is executable: it creates repositories, wires GitHub Actions or GitLab CI, registers catalog-info.yaml, applies Argo CD Applications or Flux Kustomizations, and optionally submits Crossplane claims (for example PostgresDatabase or Namespace) on Kubernetes. Developers interact with parameters (service name, tier, team) rather than low-level cloud or cluster APIs.

Why it exists

When every team assembles its own scaffold, security scanning and observability are uneven and platform engineers drown in one-off questions. Golden paths productise expertise: the platform team encodes the paved road once; product teams consume it many times.

They also create a feedback loop—template usage metrics reveal which stacks matter, and version bumps to shared CI workflows propagate improvements to every consumer without N separate migrations.

When to use

  • Workflows performed by three or more teams at least a few times per year (REST API, async consumer, cron job, data ingest).
  • Stacks the platform team can commit to maintain (language runtime, framework, deploy target).
  • When onboarding time and production-readiness gaps are measurable pain points.
  • When Kubernetes + GitOps is the target runtime and you want Applications generated from day one.
  • When compliance requires mandated steps (SAST, SBOM, image signing) in every new service.

When not to use

  • One-off spikes or research prototypes that should not inherit production controls.
  • Niche runtimes with no maintainer—shipping a stale generic template harms trust.
  • When the underlying cluster or Crossplane compositions are not production-ready.
  • Tasks better served by pure documentation (organisational process) rather than automation.

Typical architecture

Pros and cons

Pros

  • Time-to-first-production-deploy drops from days to hours for supported stacks.
  • Mandated security controls (scanning, SBOM, cosign) ship in shared CI—not per-repo copy-paste.
  • Consistent repo layout and metadata simplify incidents and ownership lookup.
  • Template semver lets teams schedule upgrades; platform rolls out CI workflow patches centrally.
  • Kubernetes namespaces and Crossplane claims inherit landing-zone guardrails automatically.

Cons

  • Templates require ongoing owners; stale frameworks erode adoption.
  • Backstage template authoring (Nunjucks + actions) has a learning curve.
  • Over-prescriptive templates fight legitimate architectural variation.
  • Breaking changes in reusable CI workflows can affect many repos at once without careful versioning.
  • Crossplane and GitOps failures during scaffold show up as poor first-run DX.

Implementation notes

Shadow two real “new service” attempts before building v1; time each step and remove friction that does not add safety. Ship a template that covers ~80% of cases with a documented escape hatch to off-road registration.

Pin reusable workflows with major tags (@v3); announce deprecations in portal news. For Kubernetes, generate an Argo CD Application or Flux Kustomization in-repo rather than mutating cluster state only from the template run—Git remains source of truth.

Custom Backstage actions can apply Crossplane claims via the Kubernetes API (same RBAC as CI) or trigger a Git commit to an infra repo watched by GitOps. Return links to dashboards, runbooks, and connection secrets (via External Secrets) in the template output.

Track: new repos created via template vs manual; template version distribution; failed scaffold runs. Interview off-path teams monthly.

Common failure modes

  • Template rot: Generated services reference EOL Python or vulnerable base images; schedule quarterly template releases aligned with cluster upgrades.
  • Fork and forget: Teams duplicate template repos and stop receiving CI updates; publish from a central template repository only.
  • Mandate without quality: Forced template usage when scaffold is flaky drives shadow repos; fix SLO on template success rate before mandates.
  • Missing catalog contract: Template skips catalog-info.yaml; services become invisible—block merge on catalog validation.
  • Silent Crossplane failure: Claim stuck in READY=False; expose claim status in portal post-scaffold and alert platform on failure.

Decision checklist

  • Does each golden path have a named owner and published deprecation policy?
  • Are mandated controls in shared CI separate from recommended linters?
  • Does the template produce GitOps manifests and catalog metadata every time?
  • Are Crossplane claims optional parameters with safe defaults, not required for all stacks?
  • Is escape-hatch registration required when teams skip the template?
  • Are adoption and scaffold-failure metrics visible to platform leadership?

Example use cases

  • Case study — Spotify: Internal “golden path” messaging emphasises supported ways of building so teams avoid reinventing delivery plumbing—culture plus tooling, not checklist enforcement.
  • Illustrative scenario — API factory: Three golden paths (sync HTTP, Kafka consumer, scheduled job) account for 90% of new repos; average bootstrap time falls from two days to under thirty minutes including namespace and Grafana folder.
  • Illustrative scenario — regulated workload: FinTech template pins signed images and stores SBOM artifacts in an audit bucket; auditors sample template version tags instead of individual repos.
