Platform Engineering Advanced

Platform APIs and Abstractions

Platform APIs are the versioned, self-service interfaces—CRDs, catalog REST endpoints, and portal actions—that let teams declare what they need while the platform reconciles safe defaults behind the scenes.

⏱ 12 min read

What it is

Platform APIs and abstractions are the technical contracts between the platform team and product engineering: declarative resource types, HTTP endpoints, and portal workflows that expose databases, environments, credentials, and catalog entries as self-service operations instead of tickets or console clicks.

Application teams should receive connection strings and scoped credentials, not root IAM keys. A typical flow starts when a developer applies a manifest or clicks through a Backstage template; the platform records intent in etcd (or the catalog), admission checks policy, an operator or composition calls the cloud control plane, and the result lands as a Secret or catalog entity the workload can consume. That boundary keeps expert wiring—subnets, KMS keys, parameter groups—inside controllers product engineers never debug at 2 a.m.

The most common pattern treats Kubernetes as the control plane. Custom Resource Definitions (CRDs) add platform-specific kinds—PostgresDatabase, Environment, MessageQueue—to the same API server that already enforces RBAC and admission. An operator watches those CRDs and reconciles desired state against cloud APIs, writing status and secrets back into the cluster. Crossplane can implement the cloud side via providers and compositions so one CRD shape works across vendors. Admission controllers running OPA Gatekeeper or Kyverno validate every create/update before it is stored, so security and tagging rules apply uniformly at the API boundary.

Not every interaction belongs in kubectl. Backstage exposes a Software Catalog API (REST and GraphQL) for registering and querying components, systems, and APIs; Software Templates invoke the same underlying APIs when developers scaffold repos. GitOps controllers (Argo CD, Flux) treat platform manifests like application manifests, giving PR review and rollback for infrastructure changes.

Why it exists

Direct cloud console and raw Terraform modules scale poorly across dozens of teams. Each squad interprets networking, encryption, and IAM differently; audit findings cluster on the same misconfigurations. Platform APIs compress expert decisions into a small schema: a size: medium field hides instance class, storage type, backup window, and subnet placement that the operator already encodes.

Reconciliation is the other payoff. Operators continuously compare declared CRD state with live resources and repair drift, so manual console edits do not become permanent shadow changes. The same manifests flow through GitOps, producing an audit trail tied to commits and catalog entities rather than anonymous console sessions.

Backstage and catalog APIs close the loop for humans and automation: CI pipelines register new services, cost tools join spend to spec.owner, and incident routers read ownership metadata without bespoke integrations per tool. When those identifiers stay accurate, pager routes, chargeback reports, and dependency maps reference one graph instead of three spreadsheets that diverge after every reorg.

When to use

  • Three or more teams request the same resource type (relational DB, cache, TLS cert) with similar security defaults—operator economics improve with reuse.
  • Kubernetes is already the deployment substrate; extending the API with CRDs reuses RBAC, admission (OPA/Kyverno), and GitOps muscle memory.
  • Crossplane compositions when the same higher-level claim (for example Environment) must provision AWS and GCP equivalents from one schema.
  • Backstage Catalog API when portals, CI, FinOps, or paging need stable identifiers for components, owners, and dependencies.
  • Documented escape hatches (annotations or elevated tiers) for the minority of workloads that legitimately need non-default instance classes or regions.

When not to use

  • Low demand: One or two teams with unique needs are better served by a curated Terraform module than a multi-replica operator.
  • Unstable surface area: If the underlying cloud service changes weekly, freeze abstractions until the platform team can version CRDs and conversion webhooks deliberately.
  • No Kubernetes footprint: Running a control plane solely for abstractions may cost more than a thin provisioning API backed by your existing IaC pipeline.
  • Parallel bespoke API servers: Custom REST gateways that duplicate Kubernetes semantics lose admission, audit, and ecosystem tooling—extend the API server instead.

Typical architecture

Developers interact through Backstage or Git; manifests hit admission policy, then operators and providers reconcile cloud resources and publish credentials back to the cluster.

Pros and cons

Pros

  • Versioned platform APIs align with the CNCF Platforms White Paper model: product teams declare intent while the platform owns safe defaults and reconciliation.
  • Kubernetes RBAC and admission (OPA or Kyverno) enforce who may create which API kinds without building a parallel authorisation service.
  • Desired-state controllers repair drift between declared CRDs and live cloud resources, which keeps GitOps and console edits from diverging silently.
  • GitOps applies the same PR-and-rollback workflow to platform manifests that application teams already use for deploys.
  • The Backstage Software Catalog API gives incident, cost, and CI tooling one graph of components instead of bespoke spreadsheets per integration.

Cons

  • Operators built on controller-runtime demand Go proficiency and ongoing upgrades when Kubernetes minor versions ship.
  • Crossplane compositions and XRDs grow verbose quickly; multi-cloud parity often trades schema simplicity for operations complexity.
  • Every escape hatch in a CRD schema reintroduces parameters the abstraction was meant to hide, which increases review and test surface.
  • A defective reconcile loop can affect every instance of a resource type at once, so blast radius dwarfs a single team's misconfiguration.
  • Promoting CRDs from alpha to stable requires conversion webhooks, deprecation windows, and coordination with consumers who cached old field names.

Implementation notes

Scaffold operators with Kubebuilder or the Operator SDK so reconcile loops, caching, and leader election are standardized. Keep reconcile functions idempotent: repeated application of the same spec should not create duplicate cloud objects. Guard creates with owner references or deterministic external IDs so a thundering herd of applies cannot spawn duplicate RDS instances. Use finalizers on delete paths so cloud teardown completes before the CRD object disappears from etcd.

Prefer Crossplane compositions for cloud primitives so credential handling and provider upgrades stay centralized rather than embedded in bespoke SDK calls. Populate the status subresource with conditions (Ready, Progressing, Degraded) and human-readable messages so portals and CLIs can show provisioning state without scraping cloud APIs.

Expose self-service through Backstage Software Templates and actions that call the same APIs as kubectl. Populate the catalog from catalog-info.yaml plus discovery, and from CI jobs that POST entities after merge. Derive spec.owner, spec.system, and spec.lifecycle from version-control metadata so paging routes stay accurate. Run integration tests against ephemeral clusters that exercise create, update, scale, and delete for each promoted API version.

Publish OpenAPI or CRD reference docs in the portal so API consumers understand versioning, deprecations, and supported fields, mirroring product API conventions. Pair docs with worked examples that show both the happy path and the documented escape hatch so advanced teams do not fork around the platform quietly.

Version platform CRDs deliberately: bump apiVersion, add conversion webhooks when fields rename, and publish sunset dates in the portal. Operators remain the reconcile loop; optional portable fronts include Score workload specs and Open Application Model (OAM) component/trait separation—useful when the same application description must deploy to multiple clusters or runtimes without forking bespoke YAML per team.

Common failure modes

  • Abstraction too thin: The CRD is a one-to-one mirror of a cloud resource, so engineers must still master low-level knobs and the platform saves no cognitive load.
  • Abstraction too thick: Legitimate needs such as cross-region replicas cannot be expressed, so teams fork Terraform or open tickets and the API becomes optional.
  • Operator availability gaps: A single-replica controller in CrashLoopBackOff stalls every provision request until someone notices queue depth, not SLO burn.
  • Unplanned schema breaks: Renamed fields in a new API version leave stored objects un-reconciled because conversion webhooks were deferred until “later.”
  • Catalog drift: Archived repositories still appear as owned entities in Backstage, which routes incidents to departed teams until deletion is automated.
  • Status starvation: Operators write only to logs when reconciliation fails, leaving CRDs stuck in an empty status block while developers assume provisioning is still progressing.
  • Dual paths: Teams provision through the API for speed but hot-fix through the console during incidents, reintroducing drift the controller later “corrects” in ways nobody expects.

Decision checklist

  • Does demand from multiple teams justify the cost of operating a controller and documenting a supported API surface?
  • Are encryption, network placement, and backup retention defaults on by default rather than opt-in fields?
  • Is there a tested escape hatch (annotations, elevated tiers, or break-glass roles) for non-standard configurations?
  • Do operators run with leader election, health probes, and SLOs that page platform on-call on reconcile errors?
  • Is an API versioning policy in place before the first production consumer, including conversion for breaking changes?
  • Does every new service register in Backstage through templates or CI rather than manual catalog edits?

Example use cases

  • Illustrative scenario — database CRD: A PostgresDatabase operator backed by Crossplane enforces encrypted storage, automated backups, and private subnets; dozens of squads apply manifests or use a Backstage template; median time from request to ready Secret drops from multi-day tickets to single-digit minutes with zero public endpoints in audit samples.
  • Illustrative scenario — catalog-driven paging: Incident tooling polls the Backstage catalog API for spec.owner on the failing component; misrouted pages shrink because ownership is machine-readable rather than inferred from a wiki table that lagged the last reorg.
  • Case study — Spotify Backstage: Open-sourcing Backstage showed how catalog and template APIs centralize service metadata and scaffolding so integrations (CI, ownership, docs) share one registry instead of custom spreadsheets per team.
  • Illustrative scenario — multi-cloud claim: A composite Environment CRD provisions namespace, object store, and managed database via Crossplane compositions on AWS or GCP from the same spec field set, reducing forked Terraform per cloud and letting migration programs rehearse cutovers in non-production tiers first.
