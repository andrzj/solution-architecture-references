Model Monitoring

Last updated: January 2025

What it is

Model monitoring for Meridian Commerce’s Catalog search ranking watches whether live traffic still matches what the ranker was trained on. Data drift compares query, session, and product features to the training baseline. Prediction drift tracks score distributions and rank positions. When click or purchase labels arrive, performance monitoring recomputes NDCG and related metrics against offline benchmarks.

APM latency and error rates are not enough — Meridian’s ranker can answer every gRPC call quickly while silently reordering search into irrelevance. Monitoring operates on semantics: features, scores, and eventual labels, tied to model version in the prediction log.

Why it exists

Meridian shipped a new ranking model after a strong offline NDCG gain, then saw conversion soften over two weeks. No exceptions fired; load balancers were green. Query mix had shifted (more mobile, more long-tail SKUs) and competitor pricing changed item click propensity — classic drift the model never saw at train time.

Without monitoring, Catalog discovers problems through revenue dashboards. With it, PSI on session features and score histogram shifts page the team before shoppers churn. Logged predictions joined to delayed click labels also feed the next training pipeline run instead of one-off exports from serving logs.

When to use

  • Meridian ranking (or any revenue-facing model) where wrong orderings have direct business impact.
  • Non-stationary catalog traffic — seasonality, campaigns, new categories.
  • Delayed labels (clicks, purchases) require proxy metrics and drift detectors between label arrivals.
  • Canary or shadow rollouts need per-version drift and performance comparison.

When not to use

  • One-off batch scores with no continuous serving — skip full prediction-log pipelines.
  • Internal sanity-check models where humans review every output anyway.
  • Truly static backtest-only models — rare in Meridian’s live catalog.

Typical architecture

Drift jobs compare live features and scores to training baselines; the ground-truth collector joins clicks when they arrive; dashboards show drift heatmaps and NDCG trends; alerts can trigger retraining or rollback.

Pros and cons

Pros

  • Meridian catches ranking drift before conversion dashboards move — PSI on query features often leads NDCG drops.
  • Click joins build labeled search datasets for the next training run automatically.
  • Drift highlights broken feature pipelines upstream of the ranker, not only model weights.
  • Version-tagged logs support incident replay and stakeholder audits.

Cons

  • Click labels lag impressions — NDCG is always retrospective unless proxies are used.
  • Holiday catalog shifts trigger false drift alerts without segment-aware thresholds.
  • Full feature logging at Meridian search volume is costly — sampling must preserve segment stats.
  • Bad thresholds either fatigue on-call or miss slow ranking erosion.

Implementation notes

Log query_id, timestamp, model version, candidate SKU list, feature vector (or hash + sample), and scores for every ranking call — same schema for canary and production.

Until clicks arrive, monitor search CTR, add-to-cart from search, and score distribution stability as proxies. Stratify drift by device, category, and logged-in vs guest — aggregate stability can hide mobile-only shifts.

Run KS/PSI on features in the transformed space the ranker sees (normalized price, embedding norms), not raw warehouse columns.

Wire critical drift to human review before auto-retrain — a broken feature store can look like concept drift.

Common failure modes

  • Alert fatigue: Black Friday traffic shifts features yearly — tune seasonal baselines and severity tiers.
  • Biased click joins: Logging only clicked impressions inflates NDCG — sample impressions representatively.
  • Wrong feature space: Drift on list price while the model consumes log-scaled price misses the real shift.
  • Blind auto-retrain: Retraining on a week of bad embeddings locks in the failure — validate data before pipeline trigger.

Decision checklist

  • Does every Meridian ranking log include features, scores, model version, and request ID?
  • What is click label delay, and which proxies fire first?
  • Are drift thresholds set per segment (mobile, category, locale)?
  • Does alerting require human approval before retrain or rollback?
  • Is log sampling statistically valid for segment-level drift?
  • Do model owners review dashboards on a cadence, not only when paged?

Example use cases

  • Meridian ranking drift: PSI on session depth and category mix fires when a campaign steers traffic; score histograms shift before NDCG on delayed clicks confirms degradation.
  • Canary comparison: Side-by-side drift and proxy CTR for v1.2 vs v1.3 during the canary window shown in the serving diagram.
  • Retrain trigger: Sustained drift plus NDCG drop opens a ticket to rerun Catalog’s training pipeline on recent logged features and clicks.
