Model Monitoring

Last updated: January 2025

What it is

Model monitoring observes production ML beyond CPU graphs: it tracks whether inputs, outputs, and delayed labels still match what the model was trained to handle. Traditional APM reports healthy latency while ranking or fraud scores drift into nonsense; ML monitoring works at the semantic layer — features, scores, calibration, and business proxies — tied to model version on every log row.

Signal types stack together. Data drift compares live feature distributions to the training baseline — shoppers search differently, fraudsters change tactics, sensors recalibrate. Concept drift means the relationship between inputs and the target shifted even when marginals look stable. Prediction drift watches score or label distributions over time as a leading indicator when labels lag. Performance monitoring recomputes precision, NDCG, RMSE, or SLA metrics when ground truth arrives.

For an e-commerce catalog search ranking service, that means logging each query’s features and scores, comparing session and category mix to the training window, and joining clicks days later to recompute NDCG — not merely checking that the gRPC tier returns 200 responses.

Latency, error rate, and GPU utilization belong in the same executive view, but they answer a different question: whether the scoring tier is up, not whether it is still ranking sensibly for the traffic mix arriving this hour.

Why it exists

Models degrade without exceptions. A ranker can serve every request at low latency while silently ordering search results into irrelevance; load balancers stay green until conversion or support tickets move weeks later. Root cause then spans feature pipelines, embeddings, and promo traffic — expensive detective work.

Real-world distributions are non-stationary: campaigns, seasonality, new categories, competitor pricing, and mobile mix shifts change the query and catalog regime. Historical training slices become progressively less representative. Monitoring exposes when the live population crossed from “in distribution” to “needs retrain or rollback” before revenue dashboards scream.

Deliberate prediction logging also feeds continuous improvement. Pairing requests with eventual click or purchase labels builds labeled datasets for the next training pipeline run — but only if architects design join keys, sampling, and retention up front instead of scraping serving logs after an incident.

Infrastructure metrics remain necessary: GPU utilization, queue depth, and autoscaling errors explain serving outages. ML monitoring complements that layer; it does not replace it. Healthy pods plus drifting scores is a common failure mode during campaign weeks.

When to use

  • Revenue- or safety-facing models where wrong outputs have direct business or compliance impact.
  • Non-stationary input streams: user behavior, pricing, fraud, logistics ETAs, sensor feeds.
  • Delayed labels (clicks, churn, chargebacks) where proxies and drift detectors must bridge the gap.
  • Canary or shadow rollouts that require per-version drift and performance comparison.
  • Regulated settings needing an auditable time series of model behavior and interventions.
  • Fleet or pricing models whose inputs shift with geography, season, or contract — segment dashboards are mandatory.

When not to use

  • One-time batch scoring with no continuous serving path — full prediction-log plumbing may be overkill.
  • Low-risk internal tools where humans review every output and errors are cheap.
  • Truly static backtests never connected to live data — rare for customer-facing catalog or dispatch systems.

Typical architecture

The flow below starts at serving: each ranking request lands in a durable prediction log. Batch or stream jobs run drift statistics; a ground-truth collector joins labels when they arrive; an accuracy engine computes ranking or classification metrics; dashboards layer feature heatmaps, score histograms, and latency; alerting routes breaches to on-call or to an MLOps retrain trigger with human approval where appropriate.

Pros and cons

Pros

  • Drift on query and session features often leads NDCG drops — teams react before conversion moves.
  • Click joins build labeled search datasets for retraining without ad hoc log archaeology.
  • Upstream feature pipeline failures surface as feature drift, not only as mysteriously bad weights.
  • Version-tagged logs support incident replay, stakeholder review, and regulatory audit.
  • Proxy metrics (search CTR, add-to-cart from search) cover label delay when clicks lag impressions.
  • Chi-square and population-stability tests on categorical query intents catch campaign-driven mix shifts early.

Cons

  • Click labels lag impressions — accuracy metrics are always somewhat retrospective.
  • Legitimate seasonality triggers false drift without segment-aware baselines and severity tiers.
  • Full feature logging at search volume is costly — sampling must preserve segment statistics.
  • Poor thresholds create alert fatigue or miss slow erosion — calibration is per-model work.
  • Concept drift can hide inside stable marginals — prediction and business proxies must complement KS/PSI.

Implementation notes

Log schema: Capture query_id, timestamp, model version, candidate list, features (or hashed/sampled payloads), and scores on every ranking call — identical schema for canary and production shards.

Label delay: Until clicks arrive, monitor search CTR, add-to-cart from search, and score stability. Stratify drift by device, category, and logged-in vs guest — aggregate stability can hide mobile-only shifts.

Transformed space: Run KS, PSI, or chi-square on features in the space the model consumes — normalized price, embedding norms — not raw warehouse columns that never reach the graph.

Human gates: Wire critical drift to review before auto-retrain; a broken feature store can mimic concept drift and poison the next training cut.

Sampling: If storage cost forces sampling, prove sample rates support segment-level drift and unbiased click joins — survivorship bias in labels is a common NDCG trap.

Baselines: Store training-window histograms and quantiles as versioned artifacts beside the model; drift jobs should compare live traffic to the exact slice that produced the registered artifact, not an informal “last month.”

Ownership: Name a model owner on-call rotation for monitoring dashboards separate from generic platform paging — ranking teams interpret NDCG moves faster than central SRE alone.

Integration with MLOps: Alert webhooks should open retrain tickets with links to drift charts and registry stages rather than only posting raw PSI numbers to a chat channel.

Common failure modes

  • Alert fatigue: Holiday traffic shifts features yearly — tune seasonal baselines and severity tiers instead of one global PSI threshold.
  • Biased click joins: Logging only clicked impressions inflates NDCG — sample impressions representatively.
  • Wrong feature space: Drift on list price while the model consumes log-scaled price misses the real shift.
  • Blind auto-retrain: Retraining on a week of corrupted embeddings locks in failure — validate data before pipeline trigger.
  • APM-only ops: Green latency masks ranking collapse — require semantic dashboards in on-call runbooks.

Decision checklist

  • Does every ranking log include features, scores, model version, and request ID?
  • What is click label delay, and which proxy metrics fire first?
  • Are drift thresholds set per segment (mobile, category, locale)?
  • Does alerting require human approval before retrain or rollback?
  • Is log sampling statistically valid for segment-level drift?
  • Do model owners review dashboards on a cadence, not only when paged?
