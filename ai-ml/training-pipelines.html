Training Pipelines

Last updated: January 2025

What it is

At a ride-hailing product, a training pipeline is the automated DAG that turns historical trip and demand signals into a versioned zone-level demand-forecast model — the same way CI/CD turns commits into deployable artifacts. Each run records data snapshots, hyperparameters, and evaluation metrics so ops can reproduce or compare any prior forecast model.

The workflow is expressed as containerized steps (ingest → validate → preprocess → train → evaluate → register). Frameworks such as Kubeflow Pipelines, Airflow with ML operators, Metaflow, or SageMaker Pipelines implement that graph; the pipeline is the orchestration layer around business logic, distinct from Model Training at Scale, which focuses on multi-GPU distributed training mechanics.

Optional branches attach hyperparameter sweeps or champion-challenger training on a quarterly cadence while nightly jobs stay in fixed refresh mode. The artifact leaving step 5 is not a notebook cell — it is a registry entry with lineage tags that downstream serving pipelines consume.

Why it exists

The product’s first demand models lived in notebooks. When the company opened new cities, analysts reran cells manually, disagreed on feature windows, and could not explain which data build produced Friday’s surge-pricing forecast. Scheduled retraining became mandatory: the forecast must refresh on new trips, events, and weather without someone babysitting a laptop job.

Daily runs over a rolling 90-day window are too many steps to trigger by hand. The pipeline fires on cron or when the warehouse lands a complete day of trip facts; validation gates abort before GPU time is spent on empty partitions or schema drift from a bad ingest. Experiment tracking (MLflow, Weights & Biases) attaches to each run so the team remembers which horizon and loss settings beat production — not only who ran a notebook last.

Continuous training keeps surge pricing ahead of seasonality: when trip mix shifts after a holiday weekend, the next scheduled run promotes only if holdout wMAPE beats the registry champion. Manual notebook retrains become exceptions rather than the production path.

Reproducibility matters for incident review — replaying pipeline run 2025-03-14-zone-forecast with the same data snapshot ID and container SHA must yield bitwise-comparable metrics within floating tolerance, or the platform team cannot trust automated promotion.

When to use

  • The product’s demand forecast (or sibling models) must retrain daily or weekly as trip distributions and events shift.
  • Several data scientists share one model family and need identical containers, seeds, and data snapshots.
  • Finance or ops require an audit trail linking each registered artifact to data version, code SHA, and metrics.
  • Evaluation must include bias and fairness gates before models influence rider pricing or driver incentives.
  • Retraining chains validation, training, evaluation gates, and registry promotion — not a single fit() call.
  • The product is standardizing MLOps and wants training to follow the same promote/rollback discipline as app deploys.

When not to use

  • The product is still exploring forecast horizons and features every day — a rigid DAG slows that iteration.
  • One-off backfill training that will never repeat — pipeline setup cost is not justified.
  • A tiny team with no platform support yet — start with a scripted retrain before Kubeflow-level orchestration.

Typical architecture

The product’s demand-forecast pipeline follows the staged flow below: cron or a “day closed” event starts ingest from the feature store and warehouse; validation must pass before preprocessing and train/val/test splits; training emits metrics to experiment tracking; evaluation gates block registry promotion; an approved artifact triggers the serving rollout path.

Step 3 in the fallback diagram is where large horizon models may shard zones across GPU nodes and AllReduce gradients — even when the forecast itself is modest, sharing the cluster with ranking experiments requires queueing and priority tags so pricing models preempt research jobs during incident windows.

Step 4 compares metrics to production baselines and runs fairness checks (per-zone error parity, airport vs suburban segments). Failures notify the pricing on-call; nothing registers. Step 5 writes version, data snapshot, metrics, and deployment stage (staging → canary → prod) before handing off to the same promotion discipline used for mobile apps.

Pros and cons

Pros

  • The platform can replay any forecast run with the same trip snapshot, code tag, and config — essential for incident review and regulatory asks.
  • Ingest validation stops training when trip facts are missing or zone IDs drift, before bad weights reach surge pricing.
  • Every scheduled run logs metrics to a searchable history — no more “which notebook was production last Tuesday?”
  • Overnight refresh keeps zone demand models aligned with events and seasonality without manual triggers.

Cons

  • Containerizing ingest, validation, train, and eval steps is real platform work before the first automated forecast ships.
  • Failures deep in the DAG are harder to debug than a single notebook cell — correlate logs across steps and clusters.
  • Researchers may still train ad hoc during experiments, risking divergence from the production DAG unless merges are enforced.
  • GPU steps for large horizons burn budget if autoscaling and “refresh vs tune” modes are not separated.
  • Promotion automation can ship a worse model if baseline thresholds drift without quarterly human review.

Implementation notes

Containerize each pipeline step (ingest, Great Expectations validation, preprocess, train, evaluate) with pinned deps and an image tag tied to git SHA. Keep training code out of shared “kitchen sink” environments so local, CI, and cluster runs match.

Make validation a hard gate on trip and weather tables: expected row counts per city, zone ID schema, and distribution checks on requests-per-zone. Failures should page data platform, not register a model.

Attach dataset versioning (DVC, lakeFS, or warehouse snapshot IDs) to every run so trainers can diff Tuesday’s trip join against Wednesday’s without guessing which export was live. When validation fails, persist the failing rows sample for data engineering — not only a boolean abort flag.

Split refresh mode (nightly retrain with frozen hyperparameters on the latest 90 days) from tune mode (quarterly sweeps over horizon and regularization). Demand forecasting on this path rarely needs full search every night.

Point-in-time joins from the feature store must respect forecast labels — no future trips in training rows for a given zone-hour. Fit scalers on the train split only after the temporal split.

Treat each step as an independently testable container: ingest images pin Great Expectations suite versions; train images record git SHA and dependency lockfiles. Avoid a shared “kitchen sink” conda env that passes locally but diverges on the cluster.

Emit structured logs from every step with a shared run_id so failures in step 4 trace back to the Spark executor or GPU node that produced the artifact. Store intermediate dataset artifacts (validated parquet, split manifests) in object storage with retention policies — they are evidence for regulators and for debugging “why did Tuesday’s model spike airport MAPE?”

Wire registry promotion to deployment automation: staging serving pulls the candidate artifact, shadow traffic compares live surge impact, and only then does production promotion occur — mirroring the canary path described in model serving articles.

Validate training inputs with Great Expectations or TFX ExampleValidator before GPU time burns. Scale with data parallelism, model parallelism (FSDP, ZeRO), or pipeline stages when single-GPU memory is insufficient. Checkpoint frequently to object storage and resume after spot preemption. Hyperparameter search belongs outside the hot path with budget caps. Full fine-tuning updates all weights; LoRA/PEFT adapts smaller adapter layers for cheaper iteration—pick based on task and governance. Block registry writes unless offline eval gates pass. End-to-end ranked-model job orchestration is illustrated in model training pipelines.

Tag training data snapshots in the run manifest—replays without identical partitions are not reproducibility.

Spot capacity needs checkpoint resume tested monthly—teams discover corrupt shards only during the first real preemption.

Hyperparameter search runs should write candidates to a scratch registry stage—never overwrite production tags from an experiment worker.

FSDP and ZeRO configs should be recorded for audit when training large generative adapters on multi-GPU clusters.

Common failure modes

  • Leakage in zone features: Fitting normalization on all cities before holdout inflates offline MAPE; fit only on training zones and time ranges.
  • Unpinned seeds: Prophet, XGBoost, or PyTorch forecasts differ run-to-run, hiding real regressions when comparing to production.
  • Bad-day training: A partial warehouse load passes row-count checks but under-represents airport zones — evaluation gates on segment MAPE catch this.
  • Registry clutter: Registering every nightly attempt without MAPE/wMAPE gates makes rollback ambiguous during a pricing incident.
  • Distributed step blind spots: AllReduce timeouts surface as vague “step 3 failed” unless each worker logs shard progress and data read stats.
  • Notebook bypass: Researchers train a one-off champion in Jupyter and ops promote the export without pipeline lineage — recreate the run in the DAG or block promotion.

Decision checklist

  • Does every production pipeline step ship as a versioned container linked to a git SHA?
  • Does validation abort on schema or distribution failure before the train step starts?
  • Are data snapshot ID, hyperparameters, and metrics logged for every run?
  • Does evaluation block registry unless holdout MAPE beats production baselines (overall and key zones)?
  • Are preprocess fits applied only after train/val/test temporal splits?
  • Is the trigger documented — daily cron, “warehouse day closed” event, or manual tune?
  • Does a failed step halt downstream promotion automatically and page the right owner?
  • Are intermediate artifacts retained long enough for replay during pricing incidents?

Example use cases

  • Illustrative scenario — RideRelay orchestrates nightly demand-forecast retraining from the feature store through registry promotion.
  • Illustrative scenario — RideRelay demand forecast: Nightly pipeline ingests 90 days of zone trip counts and weather from the feature store, validates, retrains the horizon model, promotes to the registry when MAPE improves, and hands off to serving for surge and driver positioning.
  • Illustrative scenario — Event-driven refresh: When a stadium event is added to RideRelay’s calendar, an API trigger reruns training with augmented event features before the first surge window.
  • Illustrative scenario — Contrast with training at scale: RideRelay’s distributed GPU pipeline trains a separate rider-matching ranker; demand forecasting stays on this lighter orchestrated DAG.
  • Illustrative scenario — Fairness gate: Evaluation rejects a model whose airport-zone MAPE improved overall but degraded suburban zones; pricing on-call receives the failed run ID and keeps the prior registry champion live.
