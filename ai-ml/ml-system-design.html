ML System Design

Last updated: January 2025

What it is

Product ranking for an e-commerce catalog is a production ML system, not a single model file. Click and purchase events land in a data lake; batch and stream jobs build user, session, and SKU features in a feature store; a training pipeline fits a learning-to-rank model; a registry records lineage; a serving API scores candidate products on each browse request; and monitoring watches drift, latency, and revenue-linked metrics. Sculley et al. describe how most engineering effort in such systems sits outside the model code — in data plumbing, configuration, serving, and glue — which is the debt teams must design for up front.

End-to-end design means one thread from raw events to ranked shelves: the same feature definitions feed offline training and online inference, promotion flows through staged environments, and bad models roll back without redeploying the storefront monolith.

Why it exists

The team's data science team shipped strong offline NDCG in a notebook, but production search still used a static sort key. Training pulled features from nightly SQL while the API computed rolling counts in Redis, so live ranking quietly diverged from what was learned — a classic training-serving skew problem Google’s Rules of ML treat as a top reliability risk.

Ranking also feeds on its own outputs: models trained only on clicks reinforce what was already shown. Without logged impressions, held-out evaluation, and monitoring tied to business KPIs, teams cannot tell whether a release helped shoppers or amplified a feedback loop.

Platform architecture turns “we retrain when someone remembers” into versioned data, reproducible pipelines, and alerts when distributions or conversion move — the same lifecycle Azure’s MLOps v2 guidance and AWS’s Machine Learning Lens describe for managed production ML.

ML behavior is data-dependent: a partner feed glitch can shift rankings without any deploy. Reproducibility therefore covers data snapshots, container images, random seeds, and feature-store pointers — not only git SHA on the training script. Teams that treat “model shipped” as the finish line usually rediscover the same skew and leakage bugs on the next seasonal release.

When to use

  • Adopt full ML system design when E-commerce ranking directly affects revenue and must stay fresh as catalogs and seasons change.
  • Adopt it when multiple squads will ship models and need shared feature, registry, and serving patterns instead of one-off notebooks.
  • Adopt it when training and serving features are produced by different teams or schedulers and skew must be prevented by structure, not hope.
  • Adopt it when compliance or incident response requires lineage from a live prediction back to data snapshot, code revision, and metrics.

When not to use

  • Skip a full platform when the product only needs a weekly batch report that no customer-facing path calls.
  • Skip it while the product question is still “should we rank at all?” — prove value with a simple baseline before investing in a feature store.
  • Skip it when a transparent sort (price, arrival date) meets the job and ML adds latency and ops cost without measurable gain.
  • Skip it if no one can own monitoring and on-call; a half-built ranking stack that silently rots is worse than rules.

Typical architecture

In this reference layout, diagram boxes map as follows: data sources are orders DB, clickstream Kafka, and partner feeds; ingestion lands curated tables in the lake; the feature store holds offline training sets and online keys for session and user signals; the training pipeline emits registry artifacts; serving is the ranking gRPC/REST tier behind category pages; monitoring compares feature distributions, scores, and add-to-cart rate and can trigger retrain.

Pros and cons

Pros

  • The team can promote a ranking model through staging, shadow traffic, and canary slices without forking the search codebase for each experiment.
  • Shared feature definitions in the store cut training-serving skew and let category and home ranking reuse the same user embeddings.
  • Registry lineage ties each live model to a data snapshot and metric report, which shortens post-incident reconstruction.
  • Automated retrain hooks respond to catalog seasonality instead of waiting for quarterly manual runs.

Cons

  • The team pays platform cost before every category page benefits — feature pipelines and serving SLOs land before the second model ships.
  • Ranking plus real-time features adds operational surface area (Kafka lag, store freshness, GPU queues) beyond classic CRUD services.
  • Over-abstracted “one pipeline for all models” slows Merchandising if the platform team does not co-design with search owners.
  • Versioned features, logs, and model artifacts grow storage and governance work that must stay automated.

Implementation notes

Start from the shelf: Fix p95 ranking latency and required feature freshness before sizing GPU training. Serving SLOs drove whether session counts could be five-minute streaming features or only daily batch.

One feature definition: Product popularity, user affinity, and price-band signals are registered once in the feature store and used for point-in-time offline joins and online lookups — matching Google’s guidance to test serving skew early.

Metadata on every artifact: Each training run records data cut, git SHA, hyperparameters, NDCG@10, and slice metrics (mobile vs desktop). Merchandising promotes only registry entries that beat the incumbent on held-out weeks.

Safe defaults: The ranking API falls back to a deterministic sort when the model times out, caps candidate list size for tail latency, and logs impression IDs so offline eval can join clicks without training on unlogged exposure.

Environments and contracts: Mirror dev, staging, and production feature-store namespaces with isolated online stores so experiments never write training keys into live Redis. Add data-contract tests on clickstream and catalog ingestion — block training when null rates or schema drift exceed thresholds agreed with merchandising.

CI for models: Package training as a repeatable pipeline job that emits artifact bundles (weights, transforms, feature manifest). Promotion gates compare slice metrics, latency in shadow traffic, and serving memory — not only headline NDCG from a single validation week.

Common failure modes

  • Training-serving skew: Training used SQL windowed counts but served Redis TTL counters; fix by materializing the same transform in the feature store for both paths and alerting when distributions diverge.
  • Silent schema drift: A partner feed renamed brand_id and null rates spiked; fix with contract tests at ingestion and block training when validation fails.
  • Feedback loops: Retraining only on clicks boosted already-visible SKUs; fix by logging impressions, using inverse-propensity or random explore buckets, and monitoring diversity metrics.
  • Stale seasonal models: Holiday inventory shifted but no retrain fired; fix with calendar triggers plus business-metric monitors on conversion, not only statistical drift tests.
  • Temporal leakage: Future purchases leaked into feature windows and inflated offline NDCG; fix with strict event-time splits and point-in-time joins from the offline store.
  • Registry without rollback: Teams promoted models but kept only the latest artifact; fix by retaining N−1 checkpoints, wiring one-click revert in serving, and rehearsing rollback in game days.
  • Feature store partition bleed: Staging jobs wrote into production online keys; fix with per-environment API keys, ACLs, and automated checks that training queries cannot target prod serving tables.

Decision checklist

  • Has the team documented ranking latency and throughput targets and traced them to feature freshness choices?
  • Do offline training and online serving read the same feature definitions from one store or contract?
  • Does every production model in the registry link to data version, code revision, metrics, and deployment stage?
  • Does monitoring alert on feature drift, score drift, and commerce KPIs together?
  • Are retrain triggers defined for schedule, drift, and business threshold breaches?
  • Does the ranking API degrade to a non-ML sort when inference fails or exceeds SLO?
  • Does every promotion pass shadow or canary comparison against the current production ranker?

Example use cases

  • Illustrative scenario — Meridian Commerce product ranking threads clickstream data, a feature store, training, serving, and monitoring into one production ML system.
  • Illustrative scenario — Shoppers open a category page; search requests top‑200 catalog candidates, hydrates user and session features from the online store, and calls the ranker within the p95 latency budget.
  • Illustrative scenario — Overnight Spark jobs refresh SKU and user features into the offline store; the training pipeline builds point-in-time labels from impression and purchase logs.
  • Illustrative scenario — A new ranker registers with NDCG and slice metrics; staging shadow-traffic compares scores; a small canary on mobile traffic precedes full promotion.
  • Illustrative scenario — Monitoring notices rising null rates on a partner attribute and falling add-to-cart rate; an alert blocks promotion and opens a retrain with validated data only.
