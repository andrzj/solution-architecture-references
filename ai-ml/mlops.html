MLOps

Last updated: January 2025

What it is

MLOps applies DevOps discipline to the full machine-learning lifecycle: versioned data and code, automated training and evaluation, staged promotion to serving, production monitoring, and retraining triggers — treating each hop as a reproducible system instead of a sequence of manual handoffs. It spans experiment tracking, model registries, continuous training, continuous delivery, monitoring, and feedback loops that return labels into the next dataset build.

Capability-wise, experiment tracking binds hyperparameters, metrics, and artifacts to a run ID; model versioning records lineage in a registry with staging and production stages; continuous training retrains when schedules or drift demand; continuous delivery promotes only candidates that pass gates; monitoring watches data, predictions, and business KPIs; feedback loops route ground truth back into feature and label pipelines. On a logistics ML platform, those pieces connect ETA and congestion models from Git commit through dispatch serving without emailing opaque weight files.

Google’s MLOps maturity model names Level 0 (manual notebooks), Level 1 (automated training plus tracking and registry), and Level 2 (full pipeline CI/CD where data, code, and config changes re-run the entire validated path). Most organizations live at Level 0–1; Level 2 suits high churn models with strong reliability requirements. Azure MLOps v2 and Google’s continuous delivery architecture describe the same stage graph with different product names.

Why it exists

Research environments make it easy to fit a strong offline model; production makes it hard to keep that model correct for months. Retraining after seasonal demand shifts, rolling back a bad promotion, proving which data snapshot trained Tuesday’s artifact, and debugging silent drift all require shared process — not heroics in a shared drive folder.

Without MLOps, teams lose reproducibility (no pinned data or code), ship models trained on leaky or biased slices, cannot roll back because nothing authoritative records production version, and discover degradation only when business metrics move. Incidents stretch because scientists, ML engineers, and platform owners lack a common artifact vocabulary.

MLOps bridges that organizational gap with named stages — candidate, staging, production — shared registries, and monitoring wired into promotion policy. It also aligns ML change management with application CD so compliance and incident response can trace a live prediction to commit SHA, data version, and evaluation metrics.

Continuous delivery for ML is not “run kubectl apply on a pickle.” Pipelines must re-validate data, re-score holdout slices, rebuild serving containers, and attach observability dashboards as first-class promotion steps — the same closed loop Martin Fowler’s CD4ML essay describes for testable, incremental model releases.

When to use

  • Multiple production models that retrain on fresh operational data and need reliable promotion and rollback.
  • Customer-facing or SLA-backed scoring where audit trails and version history are mandatory.
  • Data scientists and platform engineers who must collaborate on pipelines, serving, and monitoring with shared tooling.
  • Prior incidents where unversioned artifacts, manual deploys, or missing monitoring extended outages.
  • Regulated domains — finance, healthcare, insurance — that require documented training lineage.

When not to use

  • Pure research with no serving path in the next quarter and no compliance obligation to track runs.
  • A single low-risk batch report never called by customer-facing systems.
  • Early validation before product value is proven — design hooks, but defer full registry automation until first production model.
  • One or two scientists with no platform support; scripted retrain may beat premature Kubeflow complexity.

Typical architecture

The lifecycle below maps to a typical platform flow: Git stores model and pipeline code; the training pipeline validates data and runs evaluation gates; artifacts land in the model registry; staging runs integration and shadow tests; production serving consumes promoted versions; monitoring and continuous-training triggers close the loop when drift, latency, or schedules demand a new candidate — without renaming the neutral boxes in the diagram.

Pros and cons

Pros

  • Automated retrain and promotion reduce manual artifact copying; teams manage more models with the same headcount.
  • Lineage — data snapshot, code SHA, hyperparameters, metrics — makes artifacts reproducible and audit-friendly.
  • Monitoring-linked retrain closes feedback loops instead of waiting for executive escalation.
  • Shared registry vocabulary reduces friction between scientists, ML engineers, and platform owners.
  • CI on pipeline code catches broken feature imports before expensive GPU schedules fire.

Cons

  • High upfront investment in tooling, runbooks, and cultural adoption before benefits compound.
  • The MLOps vendor landscape fragments quickly — deep proprietary coupling creates migration tax.
  • Auto-retrain without validation can amplify bad data weeks; gates must be part of the pipeline, not an afterthought.
  • Level 2 CI/CD for every model overwhelms platform teams when data contracts are still immature.
  • Scientists must adopt Git review norms; shadow notebook deploys bypass the whole system.
  • Undocumented one-off promotion scripts become tribal knowledge — encode promotions in the registry API or pipeline, not runbooks only.

Implementation notes

Level 1 first: Automate training, tracking, and registry promotion before wiring every merge to full CD. Sculley’s hidden-debt essay argues stable data and serving paths matter more than fastest automation — debug the process, then automate it.

Registry authority: Production serving resolves models by registry stage and semantic version; object storage URIs are implementation details. Staging, production, and archived stages must be obvious in on-call runbooks.

Gates before prod: Pipelines fail closed when holdout error regresses or Great Expectations-style validation fails. Staging shadow comparison against live traffic should be mandatory for customer-facing models.

Human promotion: Fully automated prod promotion suits mature, well-instrumented use cases. High-stakes models keep a human reviewer at the staging-to-production gate with dashboards, diff views, and business context.

Portability: Prefer ONNX for serving artifacts and MLflow or open metadata for runs where possible so a future cloud move does not erase history.

Feature-store coupling: Training and serving should read features from the same registry-backed definitions; MLOps promotion is hollow if scientists retrain on warehouse SQL while production still calls a forked microservice.

Documentation as code: Store pipeline parameters, evaluation thresholds, and approval policies in Git beside model code so diffs are reviewable and rollback restores policy as well as weights.

Common failure modes

  • Automation without validation: Bad joins or label leaks reach production; hard metric thresholds block registration when the candidate does not beat the incumbent on fixed slices.
  • Experiment sprawl: Thousands of untagged runs hide the best model; enforce naming like eta/hub-mae/{date} and archive stale experiments.
  • Tooling lock-in: Irreplaceable proprietary hooks stall migration — abstract training and tracking interfaces behind thin adapters.
  • Monitoring after rollout: Dispatch learns about bias from tickets, not dashboards; attach drift and SLA monitors to the first production release.
  • Skipping staging: Direct prod pushes bypass shadow tests; require staging stage and recorded approval for revenue-facing models.

Decision checklist

  • Has the organization chosen Level 1 or Level 2 MLOps per model based on change frequency and risk?
  • Does the registry record version, lineage, and stages for every serving model?
  • Does every experiment log data snapshot, hyperparameters, and primary metrics under a team naming convention?
  • Do training pipelines block registration when evaluation or data-quality gates fail?
  • Does each production model ship with drift and business KPI monitoring on day one?
  • Are continuous training triggers documented for schedule, drift, and label-backlog events?
