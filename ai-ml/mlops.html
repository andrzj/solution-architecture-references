MLOps

Last updated: January 2025

What it is

MLOps at Northwind Logistics is how ML changes move like product code: Git holds training and pipeline source; CI runs tests and builds container images; automated training produces registry candidates; human or policy gates promote staging to production serving; monitoring feeds continuous training triggers. Experiment tracking records metrics and artifacts per run so any ETA or congestion model can be replayed.

Google’s MLOps maturity model names Level 0 (manual), Level 1 (automated training plus tracking), and Level 2 (full pipeline CI/CD). Northwind targets Level 1 for most models — nightly retrain with evaluation gates — and Level 2 for high-churn ETA scoring where data and code changes should re-run the whole path automatically, aligned with Google Cloud’s continuous delivery architecture and Azure MLOps v2 stage design.

Why it exists

Northwind once shipped a congestion model by emailing an ONNX file to the serving team; nobody recorded which feature snapshot trained it. When hub latency spiked, engineers could not reproduce the run or compare metrics to the prior week.

MLOps gives Northwind one promotion rail: only registry-tagged artifacts reach production, rollbacks swap stages, and audit can answer which commit and data version scored a shipment on a given day — the operational discipline AWS’s Machine Learning Lens groups under reliability and performance pillars.

It also reduces friction between data scientists, ML engineers, and platform owners by naming shared artifacts (data, model, deployment) instead of hiding them in personal notebooks.

When to use

  • Adopt MLOps when Northwind runs several production models that retrain on fresh logistics data.
  • Adopt it when ETA or capacity models must stay auditable for carrier SLAs and customer contracts.
  • Adopt it when scientists and platform engineers need the same registry, pipeline, and monitoring vocabulary.
  • Adopt it after a production incident where an unversioned model could not be rolled back quickly.

When not to use

  • Skip heavy MLOps when Northwind is doing pure research with no serving path in the next quarter.
  • Skip full Level 2 automation for a single low-risk batch report that never touches dispatch APIs.
  • Skip building a central registry until the first model actually serves customer traffic — but plan hooks early.

Pros and cons

Pros

  • Northwind’s ETA pipeline retrains nightly without hand-copying artifacts; on-call promotes only runs that beat the production baseline on hub-level error.
  • Registry stages make rollback a registry pointer change instead of a firefighting redeploy.
  • CI on pipeline code catches broken feature imports before they burn GPU hours.
  • Shared experiment naming lets dispatch and planning compare congestion and ETA runs in one tracker.

Cons

  • Northwind invested months in registry and pipeline hardening before every squad felt benefit.
  • Level 2 CI/CD for all models can drown the platform team in flaky tests if data contracts are immature.
  • Auto-retrain without validation once shipped a model trained on bad GPS nulls; guardrails must be part of the pipeline.
  • Scientists must adopt Git and review culture — residual notebook-only workflows bypass the system.

Implementation notes

Level 1 first: Northwind automated ETA retrain, tracking, and registry promotion before wiring every Git push to a full CD deploy — Sculley’s debt themes show why stable data and serving paths matter more than fastest automation.

Registry authority: Production serving resolves models by registry stage and semantic version; object storage paths are implementation details, not the contract.

Gates before prod: Pipelines fail closed when holdout MAE regresses or data validation fails; staging must pass shadow comparison against live ETA traffic before ops approves promotion.

Open interfaces: Northwind exports ONNX for serving and MLflow for metadata so a future cloud move does not require retraining history loss.

Common failure modes

  • Automation without validation: A bad weather join trained into production ETAs; add schema and range checks plus a rule that new models must beat incumbent metrics on fixed hub slices.
  • Experiment sprawl: Thousands of untagged runs hid the best congestion model; enforce names like eta/hub-mae/{date} and archive stale experiments quarterly.
  • Monitoring after rollout: Dispatch learned about bias from customer calls, not dashboards; attach drift and SLA monitors to the first production release.
  • Skipping staging: Direct prod pushes bypassed shadow tests; require staging stage and signed approval for customer-facing models.

Decision checklist

  • Has Northwind chosen Level 1 or Level 2 MLOps per model based on change frequency and risk?
  • Does the registry record version, lineage, and stages for every serving model?
  • Does every experiment log data snapshot, hyperparameters, and primary metrics under a team naming convention?
  • Do training pipelines block registration when evaluation or data quality gates fail?
  • Does each production model ship with drift and business KPI monitoring on day one?
  • Are continuous training triggers documented for schedule, drift, and label-backlog events?

Example use cases

Northwind MLOps for ETA and congestion models:

  • A merged PR to the feature pipeline triggers CI, then the nightly training workflow on labeled arrival data.
  • The run registers a candidate with holdout metrics; staging deploys shadow ETAs beside production for selected hubs.
  • Ops promotes the registry stage after shadow error improves; serving pulls the new version via the registry API.
  • Monitoring detects feature drift after a carrier API change and opens a retrain job without manual file handoff.
