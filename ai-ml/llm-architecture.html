LLM Architecture

Last updated: January 2025

What it is

LLM architecture is how you run transformer language models in production: tokenize prompts, run prefill and decode phases, manage the growing key-value (KV) cache, and stream tokens back to clients. It is the serving layer beneath chat, RAG, and agent features — distinct from choosing which model weights you call.

An e-commerce retailer’s shopper copilot (product Q&A, outfit suggestions, post-add-to-cart nudges) hits an LLM gateway that rate-limits mobile clients, routes traffic between Azure OpenAI chat completions and a vLLM pool for overflow, and streams responses over SSE. Peak holiday traffic is why the team owns this stack instead of naïvely pinning one request per GPU.

Autoregressive decode means each new token reuses prior KV activations; long RAG contexts plus chat history make inference memory-bandwidth heavy. vLLM’s PagedAttention stores KV cache in fixed-size pages (like virtual memory) to cut fragmentation (Kwon et al., PagedAttention), and continuous batching schedules decode steps across concurrent shopper sessions so finished chats free GPU slots immediately (vLLM documentation).

Larger catalog-tuned checkpoints may need tensor parallelism inside an NVLink-connected GPU group, while weight quantization (INT8 or INT4 via GPTQ, AWQ, or SmoothQuant) trades a small quality hit for higher concurrent session count. Architecture separates who routes traffic (gateway) from who schedules GPU memory (vLLM engine)—not from which foundation model SKU product management selected.

Why it exists

The team's first copilot prototype called a single GPU with static batching: Black Friday threads queued behind one power user pasting entire care guides, time-to-first-token missed latency targets, and GPUs sat half-empty between bursts.

LLM serving needs iteration-level scheduling, not batch-at-end classification serving. The diagram’s Prefill worker ingests the fat RAG prompt; Decode workers stream short recommendation blurbs; the KV cache manager tracks pages per session; optional tensor-parallel GPU group shards a larger catalog-tuned model when Azure capacity is throttled.

Azure OpenAI covers baseline copilot traffic with managed scale; vLLM on the team’s GPU fleet handles burst routing and keeps PII-heavy prompts inside the VPC when policy requires it — same OpenAI-compatible request shape on both sides (Azure OpenAI endpoints).

Classification-style batching queues requests until a batch fills, then returns—all or nothing. Copilot generation is token-streamed and heterogeneous: one shopper ends after two tokens while another streams a size guide. Iteration-level scheduling avoids head-of-line blocking where short replies wait on long ones, which is why dedicated LLM engines (vLLM, TensorRT-LLM, SGLang) exist instead of reusing generic Triton classification paths unchanged.

When to use

  • Large-scale concurrent shopper chats where one-GPU-one-session wastes HBM and misses latency SLOs.
  • Copilot prompts with long catalog RAG context (retrieved chunks + transcript) where KV cache sizing dominates capacity planning.
  • Hybrid routing: Azure OpenAI primary, vLLM warm standby or overflow with identical chat-completions schemas.
  • Open-weight models (e.g., Llama-family) that must run in the team’s region for data residency.
  • Token streaming UX — outfit picks that render word-by-word in the mobile storefront.

When not to use

  • Low-volume internal tools where Azure OpenAI alone is simpler than operating GPU schedulers.
  • Tasks with no generation path — embedding-only catalog indexing belongs in the vector pipeline, not decode workers.
  • Small models that fit one GPU without paging when traffic never overlaps.

Typical architecture

Read the diagram top-down as a copilot request: the mobile client → LLM gateway (auth, quotas) → Prefill worker (tokenize + build KV for retrieved catalog chunks) → Decode workers with continuous batching → KV cache manager (paged blocks per session) → Response streaming (SSE). Heavy catalog models optionally flow through the tensor-parallel GPU group.

Pros and cons

Pros

  • vLLM continuous batching keeps GPUs full during drop-day traffic instead of serializing one copilot thread per card.
  • PagedAttention raises concurrent session count when every shopper carries a fat RAG prefix.
  • Gateway dual-routing preserves UX when Azure throttles — failover to private vLLM without app rewrites.
  • Prefix caching on static copilot system prompts trims prefill cost for repeat mobile opens.
  • Quantized checkpoints stretch HBM budget so more concurrent RAG-heavy sessions fit before spill to pay-per-token overflow.

Cons

  • The team’s SRE group owns GPU drivers, vLLM upgrades, and KV fragmentation tuning — not just REST integrations.
  • Warm GPU fleets cost money on quiet Tuesday mornings compared with pure pay-per-token APIs.
  • Model rollovers need blue/green engine deploys so copilot sessions do not die mid-stream.
  • One shopper pasting a huge care guide can still inflate tail latency for neighbors on shared decode workers.

Implementation notes

Gateway: The team’s copilot API enforces shopper auth, per-device rate limits, and prompt logging with redacted payment fields before prefill. Routes pick Azure vs. vLLM from health, cost, and data-class flags.

Prefill vs. decode: Catalog RAG makes prefill compute-heavy (many retrieved tokens); decode stays relatively short for shopper replies. Separate pools or disaggregated workers let operators scale each phase independently — prefill on FLOPs-heavy cards, decode on memory-bandwidth-heavy pools when traces show imbalance.

vLLM ops: Run with OpenAI-compatible /v1/chat/completions, cap max_tokens for mobile snippets, and set max_model_len from worst-case context (system + RAG + history). Monitor KV cache usage and batch size in vLLM metrics.

Context budget: Copilot truncates oldest transcript turns before dropping retrieved catalog chunks; Azure and vLLM paths share the same token budget logic.

Parallelism and quantization: Tensor parallelism inside an NVLink pair lowers single-request latency for large catalog models; sharding decode across slow Ethernet links often makes AllReduce dominate — keep TP intra-node. Benchmark INT8 or INT4 weights on real shopper prompts before promotion; outfit suggestions may tolerate INT4 while sizing advice may need INT8. Reserve roughly 2–3 GB per GPU for framework overhead when sizing max_model_len and concurrent batch depth.

Context window management: Define maximum context from product limits (system prompt + retrieved chunks + transcript). Use prefix caching for static system instructions, and cap generation length so one verbose shopper cannot monopolize decode slots during peak events.

Common failure modes

  • KV cache exhaustion: Flash drop exhausts paged blocks; new sessions get HTTP 429 unless operators shed load or spills to Azure-only routing.
  • OOM at load: Shipping a bigger catalog-tuned checkpoint without re-sizing tensor-parallel width prevents the model from loading — capacity planning must include CUDA overhead.
  • Head-of-line blocking: Unlimited max_tokens lets one user generate an essay; cap generation length for copilot and prioritize interactive SSE sessions.
  • Cross-node tensor parallel: Sharding vLLM across Ethernet-heavy nodes makes AllReduce dominate; keep TP inside NVLink pairs.
  • Quantization regression: Aggressive INT4 shrinks memory but pushes apparel sizing or allergy disclaimers off-policy; validate slice metrics on high-risk intents before fleet-wide rollout.
  • Prefill-decode skew: RAG catalog growth lengthens prefill while decode stays short; without separate scaling signals one pool starves the other during document-heavy campaigns.

Decision checklist

  • What are the team’s p50/p95 targets for time-to-first-token and tokens/sec on mobile copilot?
  • What is the worst-case prompt size (system + RAG chunks + history) in tokens?
  • Does vLLM capacity cover Azure overflow, or only residency-sensitive traffic?
  • Are prefill and decode pools sized from measured traces, not guesswork?
  • Is there a blue/green path for vLLM model and tokenizer updates?
  • Do gateway logs correlate shopper session IDs across Azure and vLLM backends?
  • Have you profiled quantization quality on sizing, care, and policy-intent slices before promoting a smaller checkpoint?
  • Is tensor parallelism confined to high-bandwidth GPU pairs, with overflow routing tested when Azure quota throttles?
  • Does capacity planning multiply worst-case KV footprint by target concurrent sessions, including framework memory overhead?

Example use cases

  • Illustrative scenario — Meridian Commerce shopper copilot end-to-end across gateway, RAG prefill, and streamed decode.
  • Illustrative scenario — Browse assist: “Waterproof trail shoes under $120?” — gateway → prefill with retrieved catalog chunks → decode streams three SKU cards with short rationales over SSE.
  • Illustrative scenario — Cart nudge: After add-to-cart, copilot pulls care-guide chunks; KV cache pages hold the RAG prefix while decode emits a one-line leather-care tip.
  • Illustrative scenario — Peak routing: Azure OpenAI serves steady traffic; when quota pressure rises, gateway shifts new sessions to vLLM on Meridian GPUs without changing the mobile SDK.
  • Illustrative scenario — Residency path: EU shoppers whose prompts may include address hints stay on EU vLLM; US traffic uses Azure US regions — same prompt templates, different backend target.
