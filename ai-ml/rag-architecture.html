RAG Architecture

Last updated: January 2025

What it is

Retrieval-augmented generation (RAG) answers questions by retrieving relevant passages from an indexed corpus and conditioning the LLM on that evidence at inference time. Lewis et al. formalized the pattern as retrieve-then-generate: a retriever surfaces supporting documents, then a seq2seq generator produces the answer grounded in those passages (Lewis et al., 2020).

At an e-commerce retailer, the Customer Support assistant answers “Can I return this jacket after 45 days?” by retrieving chunks from policy PDFs, Zendesk macros, and resolved ticket threads — not by hoping the base model memorized published return windows.

The diagram’s two halves match production RAG. The indexing pipeline (offline) flows from Document Sources through the Document Processor and Chunking Strategy, then through embedding and the vector database (see the text fallback for embedding, ANN index, and metadata). The query pipeline (online) embeds the shopper’s question, runs ANN search, optionally re-ranks, assembles a prompt with retrieved chunks, and calls the LLM — the same retrieve→augment→generate loop Azure OpenAI documents for grounding on your own data (Azure OpenAI “use your data”).

The team adds hybrid search (dense vectors plus BM25 over policy titles), a cross-encoder re-ranker on the top-K hits, and metadata filters (region, product line) so agents only see authorized snippets.

Why it exists

A support LLM once quoted a 30-day return policy that marketing had extended to 60 days — the model was confident and wrong. Policy PDFs, carrier SLAs, and SKU-specific warranty tables change weekly; retraining a chat model on every merchandising edit is not viable.

RAG keeps the generator’s weights stable while injecting fresh evidence per request, which is exactly the non-parametric memory Lewis et al. targeted for knowledge-intensive QA. When retrieval returns the right policy clause, the model synthesizes and cites; when retrieval misses, the team can abstain or escalate instead of inventing policy.

Fine-tuning still helps the desired tone (“friendly, brief, no legalese”) and output shape, but factual answers about returns, recalls, and loyalty tiers belong in the indexed knowledge base, not in weights.

Full retraining or continual fine-tune on every policy PDF is costly and still lags same-day merchandising edits. RAG keeps parametric weights stable while retrieval injects current clauses at request time — the pattern Lewis et al. used as non-parametric memory for knowledge-intensive QA. Fine-tuning remains complementary: adapt phrasing and escalation etiquette; let the index own verifiable dates, dollar thresholds, and region-specific tables.

When to use

  • E-commerce Q&A over private corpora: support playbooks, compliance addenda, and internal runbooks that must not leak into public model training.
  • Answers that must reflect today’s catalog and policy state — return windows, recall notices, shipping embargoes — without a model redeploy.
  • Experiences that require grounding citations (chunk IDs, article URLs) for QA auditing and chargeback disputes.
  • Reducing hallucinated policy language when agents paraphrase retrieved text instead of free-generating from parametric memory.
  • Incrementally onboarding new document sets (e.g., a acquired brand’s warranties) by re-indexing only the delta.

When not to use

  • Purely generative tasks with no factual lookup — marketing taglines, email rewrites of text the user already pasted — where retrieval only adds latency.
  • Tiny, static policy sets that fit comfortably in a long-context prompt with room for chat history; measure before building an index.
  • Multi-hop questions (“compare my last three orders’ return eligibility”) unless operators invest in query decomposition or tool calls beyond single-round ANN retrieval.

Typical architecture

The team's support RAG maps directly onto the diagram: SharePoint policies and Zendesk exports feed the offline processor and chunker; Azure OpenAI embeddings write to the catalog-backed vector index; live chats embed the question, retrieve, re-rank, then call chat completions with a grounded system prompt.

Pros and cons

Pros

  • Support agents answer from retrieved policy clauses, cutting hallucinated return windows and warranty terms.
  • Legal publishes a revised EU refund addendum; support sees it after incremental indexing — no model fine-tune.
  • Each answer can attach chunk IDs and SharePoint links for dispute review and supervisor coaching.
  • Hybrid retrieval catches both SKU numbers (BM25) and paraphrased customer complaints (dense vectors).

Cons

  • If ANN search returns the wrong macro, the LLM confidently misstates policy — retrieval quality dominates outcome.
  • Chunking 512-token slices through tables splits “45-day footwear exception” from its footnote; recall suffers.
  • Every chat pays embed + search + optional re-rank latency before the first token streams.
  • “Why was order 8842 ineligible?” needs Order data tools, not one vector lookup over PDFs alone.

Implementation notes

Chunking: Teams chunk help articles on section boundaries with modest overlap so recall notices stay whole. Hierarchical parent/child IDs let retrieval hit a precise span but pass surrounding context into Prompt Assembly.

Embeddings: Index and query share one Azure OpenAI embedding deployment (same model version and dimensions); mismatched models break ANN semantics. Cap chunk length below the embedding model’s context limit so warranty tables are not silently truncated.

Grounded generation: The assembled prompt follows Azure’s pattern — system instructions to answer only from supplied context, user question last — with temperature low for policy extracts (Azure OpenAI prompt engineering).

Evaluation: Support maintains a golden question set with expected source doc IDs; CI tracks retrieval recall and answer faithfulness when chunking or embedding settings change.

Indexing cadence: Wire change feeds from SharePoint and Zendesk so updates upsert within minutes, with tombstones when legal pulls a bulletin. Version embedding model deployments alongside the index — re-embed corpora when the embedding SKU changes or ANN recall drifts in golden tests.

Latency budget: Account for embed + ANN + optional cross-encoder before first token; cache frequent policy queries only when answers are stable and PII-safe. Cap retrieved chunks with token budgeting so prompt assembly leaves room for shopper transcript history.

Security filters: Apply metadata filters (region, product line, agent role) at retrieval time so vectors never return chunks the shopper’s session is not authorized to see — authorization belongs in search predicates, not only in post-hoc prompt scrubbing.

Chunk with intentional overlap—fixed windows are fast; recursive splits respect headings; semantic chunking tracks topic boundaries at embed cost. Pick an embedding model family and dimension that match your index; re-embed when you change it. Hybrid retrieval fuses lexical BM25 with dense vectors via reciprocal rank fusion; cross-encoder rerankers improve precision on the top candidates at extra latency. Query rewriting and HyDE-style expansion help vague questions. Ground answers with citations tied to chunk IDs; measure context precision/recall and faithfulness (RAGAS-style suites). Refresh indexes on content change—stale vectors are silent quality regressions.

Hold a weekly golden-query eval—if recall drops after a catalog deploy, fix ingestion before tuning temperature.

Document chunk overlap and embedding SKU in the index manifest so re-embed projects scope cost before they start.

Reciprocal rank fusion weights should be tuned on labeled retrieval sets, not copied from blog defaults.

Citation grounding should fail closed when no chunk clears the relevance threshold.

Common failure modes

  • Lost in the middle: Ten policy chunks bury the footwear exception; re-rank to three snippets and places the highest-scoring chunk first in the prompt.
  • Vocabulary mismatch: Shoppers say “free delivery”; docs say “complimentary shipping.” Hybrid BM25 + dense retrieval plus synonym tables in the processor reduce misses.
  • Stale index: A recalled blender SKU still appears in vectors after the safety bulletin is pulled; change-feed indexing and tombstone deletes on doc removal are required.
  • Context overflow: Pasting entire warranty PDFs fills the context window; dynamic top-N and token budgeting before chat completions prevent silent truncation.
  • Embedding version skew: Index built with one embedding deployment but queries hit another; fix with pinned model versions and automated golden-set recall checks on every deploy.
  • Citation without substance: The model cites chunk IDs but paraphrases beyond retrieved text; fix with faithfulness evals, lower temperature on policy answers, and abstain rules when top-K scores fall below a confidence floor.
  • Multi-hop shopper questions: “Compare my last three orders’ return eligibility” fails with single-round ANN; fix with query decomposition, order lookup tools, or human escalation rather than forcing one vector search.

Decision checklist

  • Is chunk size validated on the team’s golden support questions (recall@K, not guesswork)?
  • Do indexing and query paths call the same embedding model version?
  • Is hybrid search required for SKU codes, regulation numbers, and policy section labels?
  • Does the cross-encoder re-ranker earn its p95 latency budget on supervisor-reviewed chats?
  • Are SharePoint/Zendesk updates reflected incrementally with delete semantics?
  • Can support auditors trace each answer to retrieved chunk IDs?
  • Do indexing jobs enforce tombstones and re-embed when legal retracts a policy document?
  • Is there a faithfulness or citation-accuracy gate in CI before chunking or embedding settings change?
  • When retrieval confidence is low, does the assistant abstain or escalate instead of inventing policy language?

Example use cases

  • Illustrative scenario — Meridian Commerce Customer Support assistant grounds answers on policy PDFs, Zendesk macros, and resolved tickets.
  • Illustrative scenario — Indexing: Nightly jobs pull policy PDFs, carrier guides, and anonymized ticket resolutions through the document processor and chunker, embed with Azure OpenAI, and upsert into the vector database with region and product_line metadata.
  • Illustrative scenario — Live chat: “Can I exchange worn boots?” → query embedding → ANN top-20 → re-ranker → prompt assembly → grounded reply citing the footwear hygiene clause.
  • Illustrative scenario — Supervisor review: Escalations attach the same retrieved chunks agents saw, so QA scores grounding rather than prose polish alone.
  • Illustrative scenario — Recall spike: Compliance uploads a bulletin; incremental index within minutes; the assistant stops citing superseded return language from parametric memory.
