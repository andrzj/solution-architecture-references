Vector Databases

Last updated: January 2025

What it is

A vector database stores embedding vectors and answers approximate nearest neighbor (ANN) queries: given a query embedding, return the IDs whose vectors are closest in cosine or dot-product space. It is the retrieval engine behind RAG and semantic catalog search.

Exact nearest-neighbor search over millions of 768-dimensional points is too slow for copilot turn budgets. ANN indexes — especially HNSW graph layers and IVF cluster probes shown in the diagram fallback — trade a small recall loss for millisecond queries at catalog scale.

An e-commerce retailer maintains a catalog embedding index: every product description chunk, care guide section, and FAQ paragraph is embedded and stored with metadata (sku, category, region, in_stock). Shopper copilot and the support assistant both query the same collection with different filters.

The diagram’s write path runs Documents / Items / Events → Embedding model (768/1536-d floats) → Vector database with an ANN index (HNSW in the fallback sketch). The read path embeds the query with the same model, ANN-searches top-K, applies metadata filters, and returns IDs, scores, and payload for downstream RAG or search APIs. Multimodal catalogs may add CLIP-style image embeddings beside text chunks in the same store with separate payload namespaces.

Why it exists

The team's OpenSearch keyword index missed paraphrases (“breathable summer dress”) and could not feed the copilot’s RAG context without brittle join queries against Postgres. Embeddings encode meaning; ANN retrieves in single-digit milliseconds at catalog scale.

Support RAG and shopper copilot share one indexing investment: nightly catalog exports and help-center articles land in the same vector store with different metadata namespaces. When merchandising publishes new SKUs, projectors re-embed changed chunks — the same operational pattern as Lewis-style retrieval corpora, but tuned for commerce facets.

Retailers keep transactional truth in Postgres and search faceting in OpenSearch; the vector index is a specialized read model for similarity, not a system of record.

Teams sometimes start with pgvector or Elasticsearch dense vectors when chunk counts stay below a few hundred thousand. Purpose-built engines (Qdrant, Pinecone, Weaviate, Milvus) earn their keep when RAM for HNSW graphs, filter-aware indexes, and billion-vector sharding outgrow a single Postgres volume.

Hybrid retrieval pairs ANN with BM25: copilot may union keyword hits for exact SKU codes with semantic neighbors for vague gifts — architects document how scores merge so support does not double-count the same chunk.

Recommendation-style features also map cleanly: a shopper embedding (from recent views) becomes the query vector; ANN returns visually or semantically adjacent PDPs for “you may also like” rails without maintaining hand-tuned synonym tables.

Capacity planning should include query concurrency during marketing pushes: copilot traffic spikes when email campaigns land, and ANN latency is sensitive to concurrent ef_search settings. Load tests mix filtered and unfiltered queries so autoscaling rules see realistic CPU and RAM footprints.

Document an explicit recall vs latency knob per use case: support RAG may accept lower recall with stricter filters, while browse similarity rails need higher ef_search to avoid empty shelves.

When to use

  • A product catalog and help RAG where each copilot or support turn needs top-K chunks within a tight retrieval latency budget.
  • Semantic “find similar products” widgets that go beyond keyword match on titles.
  • Duplicate listing detection — near-identical descriptions from marketplace sellers.
  • Filtered retrieval: in-stock, shippable-to-DE, adult-category exclusions via payload indexes.
  • Shared embedding index serving both Azure-hosted and vLLM generation paths with identical retrieval results.
  • Image or audio similarity widgets where deep embeddings encode perceptual features beyond catalog text.
  • Near-duplicate listing review when marketplace sellers paste nearly identical descriptions.

When not to use

  • Authoritative inventory counts or price — vectors are eventually consistent projections, not ACID ledgers.
  • Tiny pilot corpora (<50k chunks) where pgvector beside existing Postgres may suffice.
  • Exact SKU lookup by primary key — use Catalog’s SQL or OpenSearch term queries instead of ANN.
  • Use cases that require deterministic exact neighbors — ANN may omit the true top match; do not rely on vectors alone for compliance keyword blocklists without verification.

Typical architecture

The team's catalog index mirrors the diagram: Kafka ProductPublished events trigger embed jobs; vectors land in HNSW collections with payload indexes on category and stock; copilot and support APIs embed the user utterance and call ANN + filter before LLM generation.

On the write side, batch re-embed jobs rebuild shadow collections while online upserts stream incremental points for changed chunks. Metadata JSON (price band, age gate, locale) lives beside vectors so filters do not require a second database round trip.

On the read side, architects choose pre-filtering (constrain ANN to eligible SKUs) versus post-filtering (retrieve extra neighbors then discard out-of-stock rows). Pre-filter improves precision for strict rules but shrinks the searchable pool; post-filter keeps recall but wastes work when stock filters are tight. Payload-aware indexes exist precisely to preserve recall under pre-filter.

Latency budgets usually allocate single-digit milliseconds to ANN plus one embedding round trip. Copilot chains may retrieve top-20, rerank with a cross-encoder, then pass five chunks to the LLM — the vector DB still must return a broad candidate set quickly so the reranker has material to judge.

Deletion and tombstone paths matter: when a SKU leaves the catalog, vectors must disappear from ANN results before marketing emails quote obsolete pricing. Event-driven consumers listen for delist messages and issue point deletes; periodic compaction reclaims graph edges so searches do not wander through ghost nodes.

Pros and cons

Pros

  • A product copilot retrieves semantically related catalog chunks even when shoppers never utter the official product name.
  • HNSW incremental inserts keep pace with hourly SKU updates without full index rebuilds each night.
  • Payload filters combine ANN with in_stock and region rules in one query — critical for lawful catalog answers.
  • One index feeds support RAG and browse similarity, amortizing embedding cost.
  • Engine-native sharding and replication primitives scale out read QPS without copying the entire corpus into every app tier.

Cons

  • Large chunk counts and high-dimensional embeddings plus HNSW graph overhead dominate RAM; size clusters with deliberate headroom and rehearse Black Friday growth on shadow hardware.
  • ANN misses the exact neighbor occasionally — unacceptable for compliance keywords unless hybrid BM25 backs retrieval.
  • Embedding model upgrades force full re-embed; shadow collections and alias cutover are mandatory.
  • Heavy in_stock=true AND region=EU pre-filters shrink candidate pools and hurt recall without partitioned collections.
  • Operating yet another datastore splits expertise — someone must own backup, access control, and on-call playbooks distinct from Postgres and OpenSearch.

Implementation notes

Embeddings: Teams index with the same Azure OpenAI embedding deployment used at query time (aligned with Azure “use your data” guidance). Store embedding_model_version on every point.

HNSW tuning: Start M=16, ef_construction=100, tune ef_search against catalog golden queries (recall@10 on labeled “expected SKU set”). For billion-scale shards, IVF with carefully chosen nlist can reduce RAM at the cost of build-time clustering jobs.

Metadata: Index category_path, price_band, and compliance flags for pre-filter; copilot passes shopper locale into the filter expression on every ANN call.

Lifecycle: Keep raw chunk text in object storage; rebuild vectors into a shadow collection when dimensions or models change, then flip the alias used by RAG and search.

Chunking: Product pages split on semantic boundaries (care instructions vs marketing fluff) so ANN does not return irrelevant paragraphs. Overlap windows (50–100 tokens) reduce edge-cut misses when shoppers quote mid-paragraph phrases.

Operations: Monitor insert lag, graph build queue depth, and recall@K weekly on held-out query sets. Plan replica counts for multi-region read paths where GDPR keeps EU indexes separate from US corpora.

Security: Treat the index as sensitive merchandising IP — restrict who can export raw vectors, audit copilot retrieval logs, and scrub PII from chunks before embedding support transcripts.

Cost: Embedding every variant description nightly is linear in token count; debounce embed jobs on low-signal attribute tweaks and batch text through the same rate-limited deployment used at query time.

Common failure modes

  • Model mismatch: Staging embeds with a new model while production queries the old — ANN scores become noise. Namespace collections per model version.
  • RAM underestimate: Black Friday growth fills HNSW RAM; pods OOM mid-query. Autoscale memory from observed graph size, not raw vector bytes alone.
  • Filter starvation: Aggressive stock filters return three neighbors; copilot hallucinates gaps. Partition by region or widen ef_search when filters bite.
  • Stale vectors: Discontinued SKUs remain searchable until tombstone deletes run on ProductDelisted events.
  • Chunk drift: Merchandising rewrites titles without re-embed jobs — ANN returns outdated claims until the write path catches up.
  • Unbalanced shards: Hot categories dominate one IVF partition; latency spikes even when average QPS looks healthy.

Decision checklist

  • Does every query path call the same embedding deployment as the indexer?
  • What recall@K does the product require for copilot vs. support, and is it measured weekly?
  • Is HNSW memory sized with graph overhead, and is there a shadow reindex playbook?
  • Do payload indexes cover every mandatory filter (region, stock, age gate)?
  • Is canonical chunk text retained for full re-embed on model change?
  • When should teams duplicate collections per locale vs. one global index with filters?
  • Is hybrid BM25 documented with merge weights and fallback when ANN returns empty post-filter results?
  • Who owns on-call for index lag, and what is the maximum acceptable minutes between PIM publish and searchable vectors?

Example use cases

  • Illustrative scenario — Copilot RAG: “Gift for picky teenager who hikes” → embed query → ANN top-15 product-description chunks → filter in_stock + US ship → pass hits to LLM gateway.
  • Illustrative scenario — Similar items rail: PDP loads vector neighbors by SKU embedding, blended with OpenSearch for keyword tie-break.
  • Illustrative scenario — Support overlap: Same store holds care-guide chunks filtered to content_type=policy for the support assistant’s retrieval tier.
  • Illustrative scenario — Model migration: Merchandising adopts text-embedding-3-large; shadow index builds from stored chunk text; eval gates alias swap on recall@10.
