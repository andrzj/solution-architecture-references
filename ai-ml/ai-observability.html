AI Observability

Telemetry tailored to nondeterministic models—quality, cost, latency, and safety—not just CPU metrics.

⏱ 10 min read

What it is

AI observability is telemetry purpose-built for models: traces across retrieval and generation, versioned prompts and model IDs, quality and safety eval signals, cost and latency per feature — not just whether CPUs are busy. It answers whether the system is right, not only whether it is up.

At a logistics operator, observability centers on dispatch ML plus an LLM assist in the dispatch console: a gradient-boosted model ranks carrier options for a load, while a copilot explains delays, drafts dispatcher notes, and suggests reschedule wording grounded in live shipment context. OpenTelemetry spans stitch routing scores, model calls, and prompt hashes so on-call can follow one loadId from the scheduling API through to the text shown to a dispatcher.

An e-commerce retailer may run a parallel posture on catalog RAG — different domain, same pattern of traced LLM calls and nightly golden-set evals — but logistics dispatch is the reference story below because ML ranking and LLM explanation share one operational clock.

Why it exists

A healthy inference endpoint can still assign the wrong carrier, hallucinate a delivery time, or burn budget on verbose copilot replies. Traditional APM shows green while dispatchers lose trust in the assist panel.

Operators learned that after a prompt tweak shortened ETA explanations but dropped grounding on CarrierCommitment facts. Support tickets rose before infrastructure alarms fired. AI observability closes that gap: trace attributes carry prompt version and retrieval IDs; sampled traffic runs automatic faithfulness and toxicity checks; offline evals compare prompt releases against a frozen golden set.

Without those signals, teams debate whether a regression came from routing data, the ranking model, or the LLM — and rollback becomes guesswork.

When to use

  • Logistics-style production paths that combine classical ML scores with LLM-generated explanations or suggestions.
  • RAG or tool-using copilots where retrieval quality dominates answer quality.
  • Features that change often — prompt edits, model swaps, retrained rankers — and need diffable behavior.
  • Agent workflows with side effects (reschedule proposals, customer-visible messages) where quality regressions have operational impact.
  • Platforms that must attribute token cost and latency to a business feature such as dispatch assist, not only to a shared model deployment.

When not to use

  • One-off notebook prototypes with no production traffic or privacy obligations.
  • Batch scoring jobs where wrong outputs are cheap to spot in downstream QA and never reach users directly.
  • When the organization lacks retention and redaction policy for prompts — turning on full prompt logging before privacy design is a liability, not observability.

Typical architecture

Instrument every ranking inference and LLM call from the dispatch console assist service. OpenTelemetry exporters emit spans with loadId, prompt.hash, model name, retrieval chunk IDs, and token usage. A log store retains sampled prompts and completions with redaction; an online eval worker scores a fraction of traffic for JSON validity, groundedness against retrieved shipment facts, and toxicity. Dashboards and alerts tie those signals to release markers for prompts and ranker versions.

Pros and cons

Pros

  • Teams can pinpoint whether a bad ETA explanation came from retrieval, the ranker, or the LLM span in one trace.
  • Prompt and model version tags make before/after diffs possible on release day, not after a week of tickets.
  • Per-feature token and latency metrics show which copilot flows deserve caching or smaller models.
  • Golden-set evals catch safety and grounding regressions before dispatchers see them in production.
  • OpenTelemetry GenAI semantic conventions align LLM spans with the rest of the platform’s platform traces.

Cons

  • Storing even sampled prompts demands retention limits, redaction, and access controls from day one.
  • Faithfulness and grounding metrics must be designed for logistics language — generic toxicity scores miss wrong carrier names.
  • Online eval workers add cost and complexity beside the inference path they monitor.
  • Too many dashboards without SLOs become vanity charts — token counts without quality thresholds waste attention.
  • Cross-vendor models complicate consistent span attributes unless the gateway normalizes metadata.

Implementation notes

Trace shape: the platform’s assist gateway creates a parent span per dispatcher action. Child spans cover feature-store reads for ranker inputs, the scoring RPC, retrieval of shipment and carrier snippets, and the LLM completion. Attributes follow OpenTelemetry GenAI conventions where possible — gen_ai.request.model, gen_ai.usage.input_tokens, and custom loadId / prompt.version fields.

Versioning: Prompts and ranker artifacts live in git or a model registry; each request logs immutable hashes so engineers can diff traffic between dispatch-copilot@2.4.0 and @2.4.1 without guessing.

Evals: A nightly job replays a golden set of real dispatch scenarios (sanitized) through the stack. Online sampling runs lighter checks — JSON schema validity for structured suggestions, embedding distance to retrieved commitment text, and toxicity — on a fraction of live traffic.

Privacy: PII is stripped at ingest; raw prompts never land in the analytics tier. Retention differs by store: short for security investigation, longer for aggregated quality metrics without content.

Retail parallel: Catalog’s shopper assistant uses the same exporter pattern on product RAG; Teams reuse the collector and dashboard templates but ship separate golden sets per domain.

Trace LLM calls with OpenTelemetry GenAI semantic conventions—span per request, record model ID, token counts, latency phases, and tool invocations. Attribute cost per tenant and feature. Run eval pipelines on golden sets; treat LLM-as-judge scores as biased signals, not ground truth. Pair online checks (schema validity, toxicity sampling) with offline suites. Classical serving signals (latency, error rate) live here; model drift statistics and population stability are detailed in model monitoring for tabular and ranking models.

Sample prompt content under retention policy—aggregates without exemplars rarely explain sudden faithfulness drops.

Export span attributes your finance team can join to invoices—input and output token counts per tenant beat monthly guesses after the fact.

Golden sets should rotate when policies change—LLM-as-judge prompts need the same versioning discipline as production templates.

Shadow model deploys should tag spans with challenger IDs so cost and quality splits are obvious in production dashboards.

Join traces to business IDs only under policy—correlation beats storing raw prompt text in shared analytics tiers.

Common failure modes

  • Logging PII: Dispatcher names and addresses appear in trace backends with no redaction, creating compliance exposure.
  • Vanity metrics: Dashboards chart tokens per minute but omit groundedness, so cost rises unnoticed while quality falls.
  • Unlabeled releases: Prompt changes deploy without version tags, making regressions non-reproducible.
  • Missing retrieval context: RAG spans log completion tokens but not chunk IDs, so bad answers cannot be tied to stale index rows.
  • Eval drift: Golden sets rot while production scenarios evolve; nightly green checks mask new failure modes.

Decision checklist

  • Can the platform diff copilot behavior between prompt versions using trace filters, not manual log grep?
  • Do ranker and LLM spans share loadId (or equivalent) with upstream HTTP and Kafka correlation IDs?
  • Are retrieval scores, chunk IDs, and ranker feature versions logged on the spans that need them?
  • Do safety and grounding evals run against a fixed golden set on a schedule, with alerts on regression?
  • Are prompts and completions redacted before long-term storage?
  • Do on-call runbooks name which dashboard ties to dispatch assist versus classical routing latency?

Example use cases

  • Illustrative scenario — At Northwind Logistics, AI observability ties dispatch ML ranking and an LLM assist in FieldOps to OpenTelemetry traces keyed by loadId.
  • Illustrative scenario — Carrier ranking regression: Data drift on lane features triggers alerts on prediction distribution; traces show whether the LLM copilot started parroting stale ETAs from bad inputs or from its own prompt change.
  • Illustrative scenario — Prompt release for delay explanations: After shipping dispatch-copilot@2.5.0, groundedness evals on the golden set fail; rollback happens before FieldOps shifts see hallucinated cutoff times.
  • Illustrative scenario — Incident replay: Support exports a trace bundle for one loadId — ranker scores, retrieved CarrierCommitment rows, and the final explanation — to settle a dispatcher dispute without reproducing production data by hand.
  • Illustrative scenario — Meridian catalog RAG (secondary): Shopper assist traces retrieval and generation separately; index migration triggers groundedness alerts using the same collector Northwind uses, with catalog-specific golden questions.
