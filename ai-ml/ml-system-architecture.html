AI & ML Systems

ML System Architecture

End-to-end design connecting data, experimentation, deployment, and monitoring for reliable ML products.

⏱ 10 min read

What it is

ML system architecture maps machine learning work into explicit layers—data and features, training, registry, serving, and monitoring—so models ship as versioned products with owners and SLOs, not ad hoc notebooks on a shared drive.

A logistics operator might run several models—ETA prediction, hub congestion scoring, route risk—on shared ingestion, metadata, and deployment rails aligned with Google’s MLOps architecture guidance and Azure’s MLOps v2 design.

Why it exists

The platform’s ETA model lived in one repo, fraud scoring in another, and each team built its own feature SQL. When dispatch changed event schemas, two models broke on different timelines because nobody owned the path from raw telemetry to served tensors.

Sculley et al. argue that glue code, configuration, and data dependencies dominate real ML systems; the platform’s reference architecture makes those paths explicit so integration failures surface in staging instead of during peak load.

When to use

  • Adopt this architecture when the platform ships more than one production model and needs a repeatable experiment-to-serving path.
  • Adopt it when dispatch and planning require reproducible training, registry promotion, and canary rollout before full traffic.
  • Adopt it when auditors or customers require lineage from a live ETA back to training data and metrics.
  • Adopt it when inference latency SLOs force dedicated serving tiers separate from batch analytics.

When not to use

  • Skip a platform layer when the platform maintains one static annual retrain with no online inference.
  • Skip it for a one-off research spike that will not share data or deployment with operations.

Typical architecture

The platform maps the diagram left to right: Data is shipment events and weather feeds; Features are hub dwell, lane speed, and carrier reliability; Training runs scheduled pipelines; the Registry holds staged and production versions; Serving is the ETA and congestion APIs; Monitoring tracks drift and delivery KPIs; the Retrain loop fires when thresholds breach.

Pros and cons

Pros

  • The platform onboarded a congestion model reusing ETA feature definitions and registry promotion instead of a second bespoke stack.
  • Shared GPU pools and pipeline templates cut idle cost compared with per-team training clusters.
  • One monitoring fabric surfaces drift on hub features across models that consume the same streams.

Cons

  • The platform’s platform team becomes a dependency; squads wait on golden-path updates during incidents.
  • Training, serving, and observability tiers multiply outage domains beyond classic microservices.
  • Mandatory platform APIs can slow a small experiment unless sandbox tiers stay lightweight.

Implementation notes

Hard boundaries: the platform keeps training clusters and serving autoscaled fleets separate so a retrain surge does not steal inference CPU during peak dispatch.

Registry as gate: Only signed artifacts with evaluation reports promote from staging; production serving pulls by registry stage, not by mutable object storage paths.

Batch vs online: Lane risk scores run nightly batch; per-shipment ETAs hit a low-latency service backed by precomputed hub features plus live GPS deltas.

Logged predictions: ETA calls emit feature snapshots and model version to the lake (with retention policy) so offline drift analysis mirrors Google’s emphasis on measuring real serving behavior.

Common failure modes

  • Notebook promotion: A dispatcher “hot fixed” weights in prod without registering lineage; freeze production changes to registry-only promotion and require pipeline reruns for any weight change.
  • No shadow or canary: A new ETA model inflated predicted times and starved drivers; route all releases through shadow comparison on live requests before traffic shift.
  • Shared feature rot: One team altered hub dwell computation and broke two models; version features in the store and run contract tests on every publish.

Decision checklist

  • Does every the platform production model appear in the registry with owner, metrics, and current stage?
  • Do training and serving pull shared features from one store or generated contract?
  • Can operators roll back serving to the prior registry version without redeploying application code?
  • Does monitoring tie model drift alerts to delivery SLA dashboards?

Example use cases

  • Illustrative scenario — Northwind Logistics maps data, features, training, registry, serving, and monitoring into one ML platform reference architecture.
  • Illustrative scenario — Shipment events and weather snapshots land in the lake; feature jobs materialize lane and hub signals for training and online lookup.
  • Illustrative scenario — The ETA training pipeline registers a candidate; staging serves shadow predictions beside production for hub pairs with heavy volume.
  • Illustrative scenario — After promotion, the driver app calls the serving tier; monitoring compares predicted vs realized arrival and pages when error drifts.
  • Illustrative scenario — Drift triggers the retrain loop; the new artifact repeats registry and canary steps before replacing the production tag.
