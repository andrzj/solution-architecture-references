Model Serving

Last updated: January 2025

What it is

Model serving at an e-commerce retailer is how the Catalog search ranking model reaches shoppers. Online inference exposes a gRPC ranking endpoint: each query fetches candidate product features, scores them within a latency budget, and returns a reordered list. Batch inference (the separate path in the diagram) pre-scores catalog segments overnight for email campaigns and category landing pages where millisecond latency is unnecessary.

A third mode — stream inference — scores cart and browse events as they arrive on Kafka: lightweight models update session-level signals that the online ranker consumes minutes later. Stream paths tolerate slightly higher per-event latency but must keep up with peak traffic without backpressure into checkout.

The team's serving layer handles routing, autoscaling, canary traffic splits, and versioned model servers (Triton, TorchServe, TensorFlow Serving, or SageMaker endpoints). The storefront BFF does not load ONNX weights directly — it calls serving, which owns GPU batching, health probes, and rollout semantics. A stable request contract (candidate SKU IDs in, scores and model version out) lets Catalog swap rankers without redeploying PHP or Next.js tiers.

Why it exists

The team's ranking model lived in a data-science repo long after it beat the rules engine in offline NDCG. Search still called legacy heuristics because no one owned production inference, versioning, or GPU pooling. Serving turns the trained artifact into a contract the storefront can depend on.

Catalog search cares about p99 latency and safe rollout more than batch throughput. Production inference engineering differs from notebook training: tail percentiles matter more than mean batch time, accelerators must be bin-packed across rankers and embedding servers, and version swaps must avoid draining shopper sessions mid-query.

Multiple ranking versions coexist for A/B tests, canaries, and shadow evaluations. Gradual promotion — 95% on v1.2, 5% on v1.3 in the diagram — compares live score distributions and click-through before full cutover. Unlike a blue/green app deploy alone, serving can silently worsen long-tail discovery while headline CTR looks flat; per-version observability is not optional.

When to use

  • Search needs real-time ranking within tens of milliseconds — online gRPC with feature-store lookup.
  • Marketing needs batch scores for all active users or SKUs — nightly Airflow/Spark job on the batch path in the diagram.
  • Ranking experiments require canary or shadow traffic without redeploying the web tier.
  • GPU inference must be centralized so Catalog and recommendations do not each provision idle GPUs.
  • Predictions must be logged for monitoring (see Model Monitoring) and ground-truth join.
  • Continuous stream scoring must refresh session features faster than nightly batch alone can support.

When not to use

  • One-off analyst batch jobs — a notebook writing parquet may suffice without a scheduled batch pipeline.
  • Trivial filters (e.g., in-stock bit) with no learned model — embed in the API, skip a server.
  • Sub-millisecond scoring where network RTT dominates — consider in-process ONNX for a tiny model only after measuring end-to-end latency.

Typical architecture

The diagram’s top path is the team's online search flow: clients hit the gateway (auth, rate limits, 95%/5% split), model servers pre-process requests, pull ranking features from the feature store, run GPU inference, optionally cache hot SKU scores in the prediction store, and emit logs to observability. Post-processing may attach calibration scores or explainability summaries before the BFF merges results with business rules (stock, brand exclusions).

The batch path is the overnight catalog job — scheduler → feature prep in Spark → batch score on a GPU cluster → scores land in S3 or the warehouse for campaigns. Batch jobs partition by category so a bad segment file cannot monopolize the whole cluster.

Below the fold in operations, a model registry pointer tells each server which artifact bundle to load; health checks fail pods that cannot reach the registry or load tensors within the SLO. Stream consumers follow the same embedding and ranking contracts but write scores to Redis or the online store instead of answering HTTP directly.

Pros and cons

Pros

  • The team swaps ranking v1.3 without a storefront release — search keeps a stable gRPC contract.
  • Canary and shadow paths compare listwise scores before shoppers see a bad reorder.
  • Shared Triton/SageMaker GPU pools cut cost versus per-team inference pods.
  • Platform team operates one serving playbook; Catalog ships artifacts, not custom Flask wrappers.

Cons

  • Extra hop from search BFF to serving adds RTT and must stay inside the team's search latency budget once feature fetch is included.
  • Gateways, autoscaling, and GPU health checks are ongoing ops work.
  • Idle GPU replicas during overnight traffic troughs are expensive without scale-to-zero policies.
  • Sharing GPUs between ranking and embedding models can create noisy-neighbor tail latency.

Implementation notes

Profile search ranking end-to-end: gateway, feature-store reads, tensor assembly, GPU forward pass, post-processing. Ranker compute is often smaller than bulk feature retrieval — cache hot product features and co-locate serving near the online store region.

Enable dynamic batching on the ranking server for burst traffic; cap batch wait time so p99 does not violate SLA. For wide transformers, consider INT8 or FP16 exports only after measuring NDCG regression on a frozen eval set — quantization saves VRAM but can reorder tail SKUs.

Run shadow ranking: v1.3 scores every query alongside v1.2 but only v1.2 answers the user until NDCG and score-distribution checks pass. Log both score vectors with request_id so offline analysts can diff rank lists without exposing v1.3 to shoppers.

Version input schemas (query_id, candidate SKU list, feature vector layout) and reject malformed requests before inference. Return a typed output schema — scores, optional confidence, model_version — so downstream caches never misinterpret a partial response after rollout.

Batch jobs use the same preprocessing code path as online serving (shared container or library pin) and write parquet with identical column order. Prediction caches help when the same SKU sets repeat (category browse rails); set TTL below merchandising refresh so stale scores do not survive major sale events.

Instrument the observability block in the diagram: histogram latency per model version, log input feature checksums on sample rate, and export prediction distribution drift metrics to the same stack that pages SRE during app deploys.

Choose gRPC when search sends large candidate feature tensors; REST JSON may suffice for smaller tabular rankers but watch payload size on mobile clients. Either way, enforce auth at the gateway and cap batch sizes so a buggy BFF cannot submit entire catalog SKU lists per query.

Online inference serves synchronous requests; batch scores offline tables; streaming scores event windows. Dynamic batching improves GPU utilization when latency SLOs allow queuing. vLLM and TGI use continuous batching and paged KV memory for generative models; Triton hosts multiple backends. Quantized weights (INT8, 4-bit) cut memory at accuracy cost—validate per task. Autoscale on GPU utilization, queue depth, and time-to-first-token; cold starts need warm pools or preloaded weights when SLOs are tight.

Keep preprocessing in a shared library artifact—serving v2 with training v1 transforms is a silent accuracy cliff.

Expose model revision in response metadata so client logs and drift jobs align complaints with the artifact that actually served.

Shadow traffic should duplicate requests, not split user sessions—compare scores on identical feature vectors.

GPU autoscaling on queue depth avoids thrashing better than CPU alone during burst checkout and search traffic.

Warm pools should preload weights before traffic shift—cold model load dominates tail latency on large checkpoints.

Common failure modes

  • Cold start after scale-out: Loading the wide ranking network on new GPU pods spikes p999 — keep minimum replicas and pre-warm on deploy.
  • Feature fetch dominates: Online store timeouts blow the latency budget while the GPU sits idle — circuit-break to cached defaults only where product allows.
  • Runaway batch score: A marketing segment typo scores the entire catalog — partition batch jobs and cap row counts.
  • Steep ranking shifts: A canary passes average CTR but collapses long-tail discovery — watch score histograms, not only top-line CTR.
  • GPU memory fragmentation: Loading multiple ranker variants on one card can fail mysteriously when free VRAM looks sufficient — prefer explicit model slots or one primary model per replica.
  • Silent post-rollout drift: v1.3 ships with a preprocessor bug that only affects mobile clients — segment dashboards by client type before promoting canary traffic past 5%.

Decision checklist

  • Are online ranking SLAs defined (p50/p99) including feature retrieval?
  • Is GPU serving shared with autoscaling and dynamic batching tuned for Catalog peaks?
  • Does the gateway implement the team's 95/5 (or similar) canary split with per-version metrics?
  • Is shadow traffic enabled for every major ranker promotion, with a documented stop condition?
  • Are stream, online, and batch paths pinned to the same preprocessing library version?
  • Are request ID, features, scores, and model version logged for every online and batch run?
  • Is rollback a registry pointer flip plus traffic shift, tested in staging?
  • Does batch inference reuse the same preprocessing contract as the real-time path?

Example use cases

  • Illustrative scenario — Meridian Commerce serves product ranking online from the feature store and runs batch scoring for campaign modules.
  • Illustrative scenario — Meridian search ranking (online): A shopper query hits gRPC ranking; features for the candidate set load from the online store; the model returns reordered SKUs within the agreed search SLO.
  • Illustrative scenario — Meridian campaign batch: Overnight Spark prepares features; the batch path scores every active loyalty member; results land in DynamoDB for email “top picks” modules.
  • Illustrative scenario — Canary promotion: v1.3 receives 5% of live queries per the diagram until monitoring clears drift and NDCG against click labels.
  • Illustrative scenario — Stream enrichment: browse events update session embeddings in Redis; the online ranker merges them at query time without scoring the full catalog per click.
