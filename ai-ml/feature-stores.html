Feature Stores

Last updated: January 2025

What it is

At Northwind Logistics, the feature store is the single place dispatch ML reads ETA and delay-history signals. The offline store holds timestamped values for training delay and ETA models with point-in-time joins — Parquet on S3 or BigQuery tables keyed by loadId and event time. The online store (Redis or DynamoDB) holds the latest rolling delay stats and route ETA features for FieldOps and driver apps at inference latency.

The feature registry documents definitions such as rolling_delay_p90_7d and hub_to_customer_eta_minutes, owners in Dispatch Scheduling, and which models consume them — Feast, Tecton, or Vertex Feature Store implement the same pattern at different maturity levels.

Why it exists

Northwind’s ETA model looked excellent offline until dispatch noticed FieldOps showed different delay minutes than training SQL. Two teams had written “last seven days late percentage” differently — one used hub departure time, the other customer dock arrival. Training-serving skew made the model untrustworthy for driver messaging.

Dispatch, Routing, and Fleet each recomputed similar aggregates from Kafka and the warehouse. A feature store lets Northwind compute delay history once, materialize to offline and online stores, and reuse features for ETA prediction, dispatch ranking, and billing dispute models. Point-in-time correctness prevents labeling a Monday shipment with Friday’s delay rollup — a common leakage path when joining warehouse facts without timestamps.

When to use

  • Northwind dispatch models share ETA, delay, and dwell features across teams — publish once, consume many.
  • FieldOps needs sub-100ms feature lookup at scoring time — pre-materialize to the online store.
  • Training-serving skew is a known risk for rolling delay and route features with non-trivial SQL.
  • Historical retraining requires point-in-time joins on loadId / shipmentId timelines.
  • Northwind is scaling ML beyond one notebook and needs registry, ownership, and lineage.

When not to use

  • Models use only raw GPS coordinates with no shared aggregates — a thin API may suffice.
  • Batch-only monthly billing scores with no latency SLA — warehouse SQL without an online store.
  • Early ETA experiments before product value is proven — store overhead may wait.
  • No data engineering capacity to operate Spark/dbt materialization jobs.

Typical architecture

Northwind maps the diagram to dispatch data: Kafka shipment events and the warehouse feed batch and stream transforms that compute ETA and delay features; offline store feeds training pipelines; online store feeds FieldOps and serving; the registry sits underneath for definitions and lineage.

Pros and cons

Pros

  • FieldOps and training both read the same delay-history definition — skew investigations shrink from weeks to diffing versions.
  • Routing and Dispatch reuse hub congestion features instead of duplicating Spark jobs.
  • Point-in-time joins give honest offline ETA metrics for shipments still in flight.
  • Registry and stats turn “what is rolling_delay_p90_7d?” into a documented answer.

Cons

  • Operating offline plus online stores and sync jobs is real platform ownership for Northwind.
  • Materialization lag means ETAs may trail live GPS until stream paths catch up.
  • Onboarding Feast/Tecton abstractions slows first experiments.
  • Online store outages directly break dispatch scoring — HA and paging are mandatory.

Implementation notes

Version Northwind features explicitly: rolling_delay_p90_7d_v1 vs v2 when the window changes from hub to customer dock. Models pin versions at train time; serving migrates deliberately.

Stream ShipmentDelayed and GPS enrichment into Flink for five-minute freshness on hot lanes; nightly Spark backfills the offline store for retraining. Materialization jobs push latest values to Redis with monotonic event timestamps so stale writes lose.

Emit feature statistics on each materialization — null rate on ETA, p90 delay drift — into the same observability stack as model monitoring.

Common failure modes

  • Stale delay rollups: A failed dbt run leaves yesterday’s p90 in Redis — alert on freshness SLAs per feature.
  • New load, empty history: Brand-new loadId rows lack delay history — define defaults and monitor imputation rate.
  • Schema drift on events: Kafka renames dockArrivalUtc without bumping feature version — validate contracts at ingest.
  • Online overload: Peak dispatch rescoring spikes Redis p99 — pool connections and cache at the serving layer.

Decision checklist

  • Which Northwind features (ETA, delay, dwell) are shared across models and teams?
  • Is hourly batch enough for ETA, or do certain corridors need stream freshness?
  • Are training labels joined point-in-time on shipment event timestamps?
  • Does a data platform squad own materialization and on-call?
  • What are online lookup latency and availability targets for FieldOps?
  • Is feature versioning planned before the first production model pins definitions?

Example use cases

  • Northwind dispatch ETA: Stream and batch pipelines publish hub_to_customer_eta_minutes and rolling_delay_p90_7d; FieldOps pulls them at score time; retraining uses the offline store with point-in-time joins.
  • Delay prediction training: Historical delay labels join delay-history features from the offline store without future dock events leaking into past rows.
  • Fleet platform reuse: Fleet’s capacity model consumes the same hub congestion features from the registry without recomputing from raw GPS.
