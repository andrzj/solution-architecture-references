Prompt Engineering

Practical patterns for structuring prompts and tests so LLM behavior is reliable, measurable, and upgradeable.

⏱ 10 min read

What it is

Prompt engineering is how teams turn brittle chat strings into versioned templates, typed variables, and measured behavior before production. It covers system/developer/user message roles, grounding instructions, output shape, and the eval harness that guards model or template changes.

At an e-commerce retailer, Customer Support does not paste free-form prompts into a playground. They ship support_answer_v3 templates in git: system rules (“answer only from {{retrieved_context}}”), developer guardrails (tone, escalation triggers), and the shopper’s message — then parse JSON answers with citation fields.

The diagram flows Template v3 → vars (context chunks, locale, order hints) → LLM (Azure OpenAI chat completions) → parser (schema validation) → unit + LLM eval suite. That pipeline matches Azure’s guidance to separate instructions, grounding content, and the user task (Azure OpenAI prompt engineering).

Why it exists

Teams once “fixed” a support hotfix by adding “always offer free shipping” to the system prompt in prod without a version bump; returns policy accuracy dropped and nobody could diff what changed. LLM outputs shift with tiny wording, model upgrades, and temperature.

Templates plus semver and golden eval sets let support swap GPT-4o for a newer deployment, add EU locale variables, or tighten citation JSON without guessing. When Lewis-style RAG feeds the model, the prompt layer is what forces grounding instead of parametric improvisation.

When to use

  • Product support RAG answers that must cite chunk IDs and refuse when context is empty.
  • Structured extraction — return eligibility { "eligible": boolean, "reason_code": string } for supervisor tooling.
  • Copilot routing prompts that classify shopper intent before tool calls.
  • Moderation and PII-redaction pre-prompts shared across Azure and vLLM backends.

When not to use

  • Ultra-high-volume classification where fine-tuned small models beat giant prompts on cost — measure tokens/month first.
  • One-off internal scripts with no SLA; a pinned notebook may suffice until usage repeats.

Typical architecture

The team's prompt service renders Template v3 with Handlebars-style vars, calls chat completions with response_format JSON schema where supported, runs the parser, and only then returns text to Zendesk. CI executes the unit + LLM eval suite on every template merge.

Pros and cons

Pros

  • Teams ship template v3.2.0 and rolls back to v3.1.0 without redeploying RAG indexes.
  • JSON schema outputs slot into supervisor dashboards without regex fragility.
  • Eval suite catches regressions when Azure bumps a model version behind the same API name.
  • Few-shot examples live in the template repo only when A/B evals prove lift — no mystery examples in prod env vars.

Cons

  • Long system prompts plus RAG chunks burn tokens on every support message.
  • Without evals, “small wording tweaks” silently raise escalation rates.
  • Template sprawl — checkout, returns, loyalty — needs ownership or diagrams lie about one true template.

Implementation notes

Message roles: System holds grounding and policy; developer holds tool JSON and schema reminders; user holds the shopper text only — Azure recommends keeping evidence out of the user role when possible.

Variables: {{retrieved_context}}, {{locale}}, and {{order_summary}} are injected server-side; agents never edit raw template files in the CRM.

Structured output: Support answers use a parser-validated schema { "answer", "citations[]", "escalate" }; temperature 0–0.2 for policy tasks.

Eval harness: A curated golden ticket set (human-labeled ideal answers plus must-cite doc IDs) runs in CI with deterministic template tests and LLM-judged faithfulness on a pinned model snapshot; deploys block when citation quality regresses.

Few-shot: Teams added three return-eligibility examples only after offline eval raised macro-F1; shots are part of template v3, not ad-hoc agent copy-paste.

Keep policy in the system role; user content is untrusted input. Few-shot examples belong in versioned templates—change them only when regression evals prove benefit. Chain-of-thought can help reasoning tasks but increases tokens and leak risk; hide scratch work from end users when possible. Version prompts in git and run golden-set evals on every change. Prompt injection arrives via user text or poisoned retrieval—delimiter tricks are weak alone; pair with guardrails and tool restrictions. Treat prompts as code: owners, review, and rollback paths.

Indirect injection via retrieved policy PDFs is as common as pasted jailbreaks—sanitize or rank sources before they enter the system block.

Store few-shot packs separately from system policy so merchandising can update examples without touching safety instructions.

Regression evals should include adversarial strings from recent incidents, not only happy-path shopper questions.

Chain-of-thought prompts should not echo hidden reasoning into user-visible channels or client-side logs.

Prompt semver tags in deployment metadata make support incidents searchable without guessing which template was live.

Common failure modes

  • Prompt drift: Ops edits the live system string in Azure studio; git template v3 no longer matches production.
  • Context stuffing: Pasting ten RAG chunks “to be safe” blows token budget and triggers lost-in-the-middle omissions.
  • Schema sprawl: Parser accepts free text some days and JSON others; downstream automations break silently.
  • Eval stale: Golden set reflects 2024 policies; new EU directive ships but CI stays green while prod lies.

Decision checklist

  • Are Product support templates in git with semver tags and change logs?
  • Does CI run unit renders plus LLM evals on every template and model pin change?
  • Are RAG grounding rules explicit (“if context empty, escalate”)?
  • Is output schema-validated before Zendesk sees text?
  • Do evals include adversarial shopper prompts (jailbreak, fake policy quotes)?
  • Are few-shot blocks justified by measured offline lift?

Example use cases

  • Illustrative scenario — Meridian Commerce versions support prompt templates and gates merges with CI eval suites.
  • Illustrative scenario — support_answer_v3: Renders retrieved policy chunks, outputs JSON with citations pointing at vector chunk IDs for audit.
  • Illustrative scenario — support_triage_v2: Classifies “shipping delay vs. return vs. warranty” before choosing retrieval filters.
  • Illustrative scenario — Release gate: PR bumps template to v3.3.0; eval suite compares faithfulness and escalation rate against v3.2.0 on golden tickets before merge.
  • Illustrative scenario — Model upgrade: Azure announces a new chat model; Meridian re-runs the same template pin on shadow traffic and promotes only when citation quality matches the prior model on the golden set.
