Caching Strategies

Cache-aside, read-through, write-through, write-behind; eviction policies (LRU, LFU, TTL), warm-up strategies, multi-level caching (L1/L2/CDN), and thundering herd on cold cache.

⏱ 13 min read

What it is

Caching stores frequently used data in a faster tier—process memory, a distributed store such as Redis, or a CDN edge—so requests avoid repeated work against the authoritative source (database, upstream API, object store). On a hit the caller reads from the fast tier; on a miss it loads from origin, optionally populates the cache, and returns. Latency ratios of 100× or more versus a database round trip make caching the default first lever for read-heavy systems.

Four application patterns dominate: cache-aside (application loads on miss), read-through (cache library loads transparently), write-through (synchronous cache and DB update), and write-behind (cache first, async persistence). Redis supports all four via client libraries, Lua scripts for atomic read-modify-write, and optional persistence (RDB/AOF) when the cache must survive restarts without full cold reload.

Why it exists

DDIA treats caches as read replicas in memory: they duplicate authoritative state to avoid repeating expensive work. A round trip to PostgreSQL or a remote API pays latency, CPU, and contention on shared storage that a Redis GET or an in-process hit avoids entirely. For skewed read workloads, a modest Redis cluster routinely achieves 90–99% hit ratios on catalog, config, and session keys, which can translate into an order-of-magnitude reduction in primary read load compared with adding more database replicas alone.

Caching also decouples your SLA from someone else’s. Third-party APIs impose quotas, variable latency, and outage risk; caching their responses for bounded intervals cuts cost and shields users when upstream fails. Cloudflare and Fastly extend the same idea to the edge: geographically distributed PoPs serve static and selectively cacheable dynamic responses in single-digit milliseconds, multiplying effective origin capacity during viral spikes when auto-scaling alone cannot keep pace.

When to use

  • Read frequency dominates write frequency and stakeholders accept documented staleness between invalidation or TTL expiry.
  • Origin work is costly: multi-table joins, aggregation, geocoding calls, or model inference that should not run on every HTTP request.
  • Many clients request the same key space concurrently, so shared Redis or CDN entries amortize work across users.
  • Traffic is bursty or viral and you need a buffer before read replicas, connection pools, or primary CPU saturate.
  • Global users fetch static or semi-static assets and cacheable JSON from origins far away; edge caching shifts bytes closer to eyeballs.
  • Horizontally scaled stateless apps need a central session or token store—Redis is the usual shared-nothing session backplane.

When not to use

  • Each request returns a unique payload with no reuse across users, so every key is a miss and cache memory is wasted.
  • Read-your-writes or linearizable reads are mandatory and you have not invested in write-through, versioning, or invalidation on commit.
  • Access patterns are uniformly random across huge key spaces, producing persistently low hit ratio despite operational overhead.
  • Regulation or threat models forbid retaining certain fields outside the primary datastore, even encrypted in Redis or at a CDN vendor.

Typical architecture

Requests traverse L1 in-process, L2 Redis, then origin; writes choose cache-aside, write-through, or write-behind depending on durability needs.

Pros and cons

Pros

  • Sub-millisecond reads from RAM shrink user-facing latency and free primary database connections for writes and rare misses.
  • App tiers can scale out under DDIA’s shared-nothing model while hot keys concentrate in Redis and CDN rather than every pod.
  • Graceful degradation is possible: serve slightly stale catalog from Redis when the primary is degraded, within policy.
  • Cloudflare and Fastly edge hits cut cross-region egress bills and latency for assets and cacheable API responses.
  • Write-behind queues smooth write spikes into the database at the cost of durability complexity you can document explicitly.

Cons

  • Consistency is never free; cache-aside without invalidation guarantees stale reads until TTL, as Kleppmann emphasizes for derived data.
  • Operators must tune eviction policies, warm caches on deploy, and alert on hit ratio and memory pressure.
  • Write-behind loses in-flight updates if Redis restarts before the async flush completes unless you add durable queues.
  • Popular key expiry can synchronize stampedes; mitigate with Redis single-flight locks or probabilistic early refresh.
  • A single bad write poisons every consumer of that key until deletion—validate before SET and namespace keys carefully.

Implementation notes

Eviction and TTL tuning: TTL is the most important parameter — too short and cache hit rate drops; too long and stale data accumulates. Start with empirical measurement: P95 time between updates for the data type. For product catalogs updated hourly, TTL=5 minutes is appropriate. For user profile data updated rarely, TTL=1 hour is fine.

Use LRU eviction for general caches where access patterns follow a power law (20% of keys receive 80% of traffic). Use LFU for caches where frequency of access is a better predictor of future access than recency (e.g., global top-K popular items). Use TTL-only eviction when data expires independently of access pattern (session tokens, rate limit counters).

Redis eviction and memory: Set maxmemory-policy to allkeys-lru or volatile-lru per access pattern; monitor evicted_keys and used_memory. Use separate logical databases or key prefixes for session, catalog, and rate-limit data so one tenant cannot evict another's keys. For cluster mode, design keys so hot keys shard across hash slots—see Redis cluster slot guidance before pinning everything on one hashtag.

Thundering herd prevention: Use probabilistic early expiration (XFetch) or a miss mutex: SET lock:{key} 1 NX EX 10 in Redis, single loader refreshes, others re-read the key. Cache warming: After deploy or failover, run a warm-up job that preloads top-N keys from read replicas or primary before shifting traffic; pair with explicit invalidation on writes so warm data is not stale.

Redis vs Memcached: Memcached’s simple slab allocator and multithreaded model suit opaque blob caching with horizontal scale-out via client-side consistent hashing. Redis adds structures, persistence options, and richer eviction policies—choose Memcached when you need a minimal GET/SET fleet; Redis when locks, pub/sub invalidation, or rate counters share the same tier.

Stampedes and dogpiles: A cache miss on a hot key can fan out identical origin queries—the “dogpile” effect. Mitigate with request coalescing (single-flight): one worker loads while others wait on the same lock or in-process future. The XFetch paper (Vattani, Chierichetti, Lowenstein) adds probabilistic early expiration: each reader may refresh before hard TTL with probability that rises as expiry nears, spreading reload cost. Add random TTL jitter (±10–20%) so deploys and bulk imports do not align expiries across pods.

Negative caching: Cache short-lived tombstones for known-miss keys (404 product, unauthorized tenant) so repeated probes do not hammer the database—use a shorter TTL than positive entries and invalidate on create events. Without it, abuse and buggy clients convert cache misses into sustained origin load.

Hit ratio and latency: Mean origin latency ≈ (1 − hit_ratio) × miss_latency + hit_ratio × hit_latency. A 95% hit ratio with 1 ms Redis and 50 ms SQL still averages ~3.5 ms—dropping to 80% jumps past 11 ms. Size memory so the working set fits: Redis used_memory near maxmemory with rising evicted_keys means your effective hit ratio is capped until you add RAM or shard keys.

Eviction policies: Classic LRU/LFU trade recency vs frequency; Redis 4+ defaults to approximated LFU with W-TinyLFU (a compact frequency sketch plus admission window) that resists one-hit-wonder pollution better than pure LRU. In Caffeine and similar L1 libraries, W-TinyLFU is the usual default—align L2 policy with whether your skew is trending (LFU/TinyLFU) or session-like (LRU).

Keys and warming: Namespace keys as {schemaVersion}:{entity}:{id} so rolling deploys never read v1 payloads. Warm top-N keys from offline aggregates after deploy; measure warm-up completion before shifting load. Pair warming with jittered TTL so the fleet does not expire together on the next cycle.

Common failure modes

  • Thundering herd on expiry: A hero key’s TTL aligns across pods; simultaneous misses overload the primary. Use Redis SET lock NX, early refresh, or a longer soft TTL with background reload.
  • Uninvalidated staleness: Writers update the database but readers keep serving old Redis values until TTL. Pair cache-aside with post-commit invalidation for freshness-sensitive types.
  • Key namespace collisions: Numeric IDs reused across entity types produce cross-talk. Prefix every key with type and schema version, for example v2:product:42.
  • Cache-as-source-of-truth: Business logic assumes Redis always has state; restart empties data and breaks checkout. Always implement miss paths to the authoritative store.
  • Eviction-driven collapse: maxmemory is too small for working set; Redis evicts hot keys continuously and hit ratio falls off a cliff. Track evicted_keys and scale memory or shard.

Decision checklist

  • Target hit ratio and acceptable staleness per data class are documented and measurable in metrics.
  • Read/write pattern (cache-aside, read-through, write-through, write-behind) matches consistency needs and team operational skill.
  • TTL defaults come from measured change frequency, not copied from another service’s config.
  • High-cardinality hot keys have stampede protection tested under load.
  • Key naming conventions prevent collisions across services, tenants, and deployment versions.
  • Miss and Redis-outage behavior is defined (fail open to DB vs fail closed) and covered in chaos or integration tests.
  • Dashboards alert on hit ratio drops, memory near maxmemory, and elevated eviction rates alongside origin latency.

Example use cases

  • Illustrative scenario — product catalog: Product detail JSON lives in Redis with five-minute TTL and product:{id} namespacing. Hit ratio above 95% cuts database reads roughly 20× and median latency from ~120ms to single-digit milliseconds.
  • Illustrative scenario — session store: A stateless API fleet stores sessions in Redis with 30-minute TTL; any pod validates tokens without sticky sessions or database lookups.
  • Case study — Cloudflare CDN: Static assets and cacheable API responses are served from edge PoPs with Cache-Control headers set at origin, offloading origin egress during traffic spikes.
  • Illustrative scenario — upstream API budget: Third-party geocoding responses cache in Redis for ten minutes; one origin call per key per window keeps the integration inside vendor rate limits.
