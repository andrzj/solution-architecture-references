Request Throttling

Server-side request queuing and admission control; token bucket on ingress, priority queues, backpressure to clients, AWS API Gateway throttling, NGINX rate limiting, and gRPC flow control.

⏱ 11 min read

What it is

Request throttling is the server-side practice of controlling the rate at which incoming requests are admitted for processing, typically by queuing excess requests or signaling backpressure to clients rather than immediately rejecting them. While rate limiting counts requests over a window and rejects excess ones, throttling focuses on the processing rate — ensuring the server never accepts more work than it can handle at a given moment. Throttling is admission control at the ingress: it regulates the flow of work into a system to prevent overload.

Key mechanisms include: concurrency limiting (limiting the number of requests being processed simultaneously, not just the rate), queue-based throttling (excess requests wait in a queue bounded by a maximum depth), priority queuing (high-priority requests like health checks or premium users get served ahead of low-priority bulk operations), and adaptive throttling (automatically adjusting the admission rate based on server health metrics like CPU usage, queue depth, or downstream response times).

Why it exists

Every process has a finite concurrency budget—threads, goroutines, event-loop turns. Admitting unbounded in-flight work drives context-switch storms, heap growth, and thread pool starvation. A bounded queue trades some wait time for predictable failure instead of melting down every dependent.

Little’s Law (L = λW) explains why: when arrival rate λ times service time W exceeds what the machine can sustain, concurrency L climbs without bound. Ingress throttling caps effective λ so L stays inside the operating envelope. Databases amplify the effect—latency that looks fine at modest concurrency can spike tenfold once locks and I/O queues saturate.

Shaping load at the service boundary keeps deeper tiers—SQL, GPUs, partners—from becoming the accidental fuse for an upstream spike. Throttling is preferable to accepting every request and watching p99 latency climb until the process OOMs or the datastore refuses connections.

When to use

  • Dependencies with non-linear slowdown under parallel load (OLTP, synchronous ML RPC, partner APIs with strict concurrency).
  • CPU- or memory-heavy handlers where extra goroutines mostly add scheduling tax, not throughput.
  • Mixed traffic classes—bulk import versus interactive read—where priority lanes must not starve each other.
  • Burst-prone services that prefer short queueing to hard fail when spikes are seconds, not minutes.
  • Call graphs that must propagate backpressure when a downstream returns saturation signals.
  • Worker pools draining queues from Kafka or SQS where unbounded prefetch would pin memory and threads.

When not to use

  • Latency-sensitive UX where a 503 with Retry-After beats an opaque thirty-second queue.
  • Ultra-light handlers bound by network bandwidth, not process concurrency—queues add delay without protecting anything.
  • Clients with hard timeouts shorter than your maximum queue wait—work will abort client-side anyway.

Typical architecture

Concurrency caps, priority queues, adaptive client-side throttle, NGINX limit_req, and gRPC flow control shed load.

Pros and cons

Pros

  • Stops overload cascades by pinning in-flight work to a tested concurrency ceiling.
  • Priority queues preserve health checks and premium paths while shedding bulk jobs.
  • Adaptive client throttling (SRE-style) nudges callers to slow down when servers raise error rates.
  • Short queues absorb micro-bursts that would otherwise trigger immediate 503s.
  • Streaming protocols propagate pressure—gRPC flow control and reactive backpressure limit upstream buffering.

Cons

  • Queued requests inflate tail latency—SLO burn shows up as wait time, not error rate.
  • Depth and timeout tuning is fragile: shallow queues reject early; deep queues hoard memory and stale work.
  • Sustained overload can starve low-priority classes unless aging or fair-share policies exist.
  • Adaptive policies need clean signals; noisy dashboards cause over-throttling.
  • More moving parts than a single rate counter—servers and clients must cooperate on timeouts and retries.
  • Mis-set queue timeouts cause work to finish after clients gave up, wasting CPU without improving success rate.

Implementation notes

Concurrency vs. rate limiting: Rate caps requests per second; concurrency caps simultaneous executions. Ten threads can serve ten slow 1s jobs (10 RPS) or ten fast 10ms jobs (~1k RPS). Long-held slots break rate-only designs—deploy both per-client limits and global semaphores.

Always implement both: rate limiting curbs abusive identities; concurrency throttles protect the fleet even when every client is well behaved.

Queue depth and timeout: Start with queue depth around 2× max concurrency. Set max wait to client timeout minus expected service time—if clients time out after 5 seconds and processing takes 1 second, queue timeout should be about 4 seconds. Completing work the caller already abandoned wastes capacity and poisons latency histograms.

Priority and shedding: Classify traffic (health, interactive, bulk) into lanes; drain high priority first during overload. NGINX limit_req with burst and nodelay offers edge shaping; inside the process, prefer semaphores with timed tryAcquire over unbounded blocking queues.

Expose queue depth, wait time, and reject counts as first-class metrics; tune from load tests rather than defaults copied from blog posts. Adaptive client throttling (Google SRE) can complement server queues when mobile or browser clients can honor overload signals.

Common failure modes

  • Queue buildup under sustained overload: Arrivals exceed service for minutes; waits grow until memory blows—cap depth and return 503 with Retry-After when full.
  • Head-of-line blocking: FIFO queues behind one slow job stall fast requests—use worker pools with semaphores or separate lanes per latency class.
  • Thundering herd on queue drain: Releasing a full queue at once hammers downstream—shape drain with token or leaky bucket on the egress.
  • Downstream overload via queue release: Draining the API queue without pool limits floods SQL—throttle each hop, including connection checkout limits.
  • Adaptive throttle mis-tuning: Noisy error or latency metrics cause clients to throttle prematurely—smooth signals and require minimum sample windows before reducing call volume.
  • Priority starvation: Low-priority lanes never drain during chronic overload—use aging, weighted fair queuing, or occasional promotion of long-waiting jobs.

Decision checklist

  • Safe concurrency established by load test with realistic payload sizes and dependency latency.
  • Queue depth, wait timeout, and shed policy aligned with client timeouts and memory budget.
  • Request classes mapped to priority tiers with documented preemption rules.
  • 503/429 on saturation include Retry-After and structured error bodies for SDKs.
  • Each tier (edge, app, datastore) owns its own throttle—not only the outer gateway.
  • Backpressure surfaced to callers (stream pause, error rate headers) instead of silent infinite queue growth.
  • Load tests include long-running and bulk requests mixed with interactive traffic to validate priority shedding.
  • Runbooks document when operators should raise concurrency temporarily versus when to shed load upstream.

Example use cases

  • Batch file processing API: An API that converts uploaded documents throttles concurrent processing to 50 files, regardless of how many are submitted. A submission backlog of up to 200 files is queued; beyond that, new uploads receive 503 with Retry-After: 60. Interactive document preview requests bypass the batch queue via priority queuing.
  • Database-backed microservice: A product search service has a database connection pool of 100 connections. The service uses a semaphore of 100 to limit concurrency, ensuring it never sends more than 100 concurrent queries to the database. Under heavy load, the semaphore queue holds up to 50 additional requests briefly while concurrent queries complete.
  • gRPC streaming service: A data export service uses gRPC server-side streaming with flow control. When the client's receive buffer is full (slow client), the server pauses sending automatically via HTTP/2 flow control windows, preventing unbounded memory accumulation in the server's send buffer.

Related patterns

  • Rate Limiting — rejects excess arrivals per identity; throttling shapes how admitted work executes.
  • Connection Pooling — checkout limits are a datastore-facing throttle tied to SQL concurrency.
  • Bulkhead Pattern — isolated pools per tenant; global throttling caps the sum across bulkheads.
