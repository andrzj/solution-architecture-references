Connection Pooling

Database and service connection pools; pool sizing formula (HikariCP, PgBouncer), connection leak detection, pool exhaustion symptoms, PgBouncer transaction mode vs session mode, and connection multiplexing.

⏱ 12 min read

What it is

A connection pool is a managed set of warm, reusable connections to a database, cache, or upstream HTTP/gRPC endpoint. Instead of opening a new TCP session, completing TLS, and authenticating on every request, workers borrow an existing connection, run work, and return it. That lifecycle turns setup that often costs tens of milliseconds into microseconds on the hot path.

Pools enforce a borrow–use–return contract with explicit limits: when all connections are checked out, callers wait up to connectionTimeout or fail fast. Healthy pools also validate idle connections (SELECT 1, ping, or driver keepalive) and retire connections past maxLifetime so firewall drops and rolling restarts do not surface as random I/O errors mid-request.

Why it exists

PostgreSQL spawns a new OS process per connection. A PostgreSQL instance with 1,000 active connections is running 1,000 OS processes, each consuming ~5MB of RAM for the connection state — 5GB just for connections, before any data is processed. The OS scheduler adding context-switch overhead across 1,000 processes causes significant CPU overhead even when most connections are idle. PostgreSQL's recommended max_connections is typically 100–300; exceeding this causes serious performance degradation.

External poolers such as PgBouncer, RDS Proxy, and Hyperscale pool options multiplex many client sessions onto a smaller set of server backends. PgBouncer queues short transactions and reassigns server connections between them—ideal when hundreds of pods each hold a modest in-process pool. That separation matters most in Kubernetes and serverless fleets where instance count swings faster than database max_connections can safely grow.

When to use

  • Production services that open a database handle on almost every request—pooling is the default discipline, not an optional optimization.
  • Fleets that scale out horizontally: aggregate client connections from dozens or hundreds of replicas would otherwise exceed safe max_connections on the datastore.
  • PostgreSQL-backed workloads, where each session is an OS process and idle sessions still consume RAM and scheduler time.
  • Microservice meshes that chatter over HTTP or gRPC: shared client pools (keep-alive, channel reuse) amortize TLS and TCP setup across high fan-out call graphs.
  • Serverless and bursty compute that touches SQL—without an external pooler or managed proxy, cold starts and concurrency spikes translate directly into connection storms.

When not to use

  • Engines with lightweight thread-per-connection models on very large instances (for example MySQL at thousands of max_connections)—pooling still helps, but the penalty of skipping it is smaller than on PostgreSQL.
  • Strictly single-threaded, sequential workers where one long-lived connection suffices; configuring a pool of size one adds indirection without gain.
  • Sessions that depend on PostgreSQL advisory locks, SET LOCAL, or LISTEN/NOTIFY while routed through PgBouncer transaction mode—server backends are reassigned between transactions, breaking session stickiness.

Typical architecture

Each pod keeps a small in-process pool; an external pooler multiplexes many client sessions onto a capped set of server connections.

Pros and cons

Pros

  • Reuses warm TCP/TLS/database sessions, stripping 10–100ms of setup from requests that would otherwise pay full connect cost.
  • Caps simultaneous server sessions independent of thread count—protecting the datastore from unbounded connection growth.
  • External multiplexers (PgBouncer, RDS Proxy) let large pod counts share a modest, tunable backend pool on PostgreSQL.
  • Lifecycle settings (validation queries, maxLifetime, idle eviction) retire half-dead sockets before they surface as intermittent I/O failures.
  • Pool capacity doubles as a backpressure signal: maximum checkout equals maximum in-flight database work per process.

Cons

  • When every connection is checked out, callers block on acquire—P99 latency climbs and threads may hit connectionTimeout.
  • Leaked checkouts (missing close, swallowed exceptions) shrink the effective pool until the service appears “up” but cannot serve SQL.
  • Transaction-mode PgBouncer breaks session semantics: server-prepared statements, SET, advisory locks, and LISTEN/NOTIFY need session mode or a bypass path.
  • Isolated serverless invocations do not share in-process pools across requests; without a proxy, each cold path may still open a fresh backend session.
  • Another moving part in the stack—pooler HA, auth wiring, metrics, and version skew between app drivers and pooler features.

Implementation notes

Sizing the pool: Treating “more connections always equals more throughput” is a common mistake. Past an optimum, additional sessions increase lock waits and scheduling overhead on both app and database CPUs. HikariCP’s rule of thumb—pool_size = (core_count × 2) + effective_spindle_count—lands near ~9 connections on a four-core host with SSD-backed I/O.

I/O-heavy apps may justify modest overshoot, but plot completed transactions per second as pool size rises; throughput should flatten or fall. Set minimumIdle equal to maximumPoolSize so bursts do not pay cold-pool expansion on every traffic ramp.

PgBouncer modes: Prefer transaction mode for short, read-heavy transactions where multiplexing buys the most headroom. Choose session mode when prepared statements, SET LOCAL, advisory locks, or LISTEN must persist across statements. Avoid statement mode in production—it cannot span multi-statement transactions. In transaction mode, disable client-side prepare in JDBC (prepareThreshold=0 for pgjdbc) because backends rotate per transaction and server-side prepare handles become invalid.

Common failure modes

  • Pool exhaustion under load: Slow queries or forgotten transactions hold every checkout; newcomers block until timeout while the database shows all sessions ACTIVE. Right-size pools to datastore capacity, tune slow SQL, and enforce statement_timeout on runaway statements.
  • Connection leak: A branch acquires a connection and never returns it—often an exception path without finally or try-with-resources. Enable leakDetectionThreshold and standardize scoped connection helpers.
  • Stale connections after database restart: Rolling restarts or firewall idle drops leave dead sockets in the pool until the next query fails with broken pipe. Keep maxLifetime below server idle limits and run lightweight validation on checkout or idle eviction.
  • Serverless cold start connection storm: Hundreds of concurrent invocations each open a backend session after a spike, tripping max_connections. Front the database with RDS Proxy or PgBouncer sized for burst connect, not burst Lambdas.

Decision checklist

  • Maximum pool size validated with load tests and the sizing heuristic—not a round number copied from another service.
  • Leak detection (leakDetectionThreshold) enabled in non-production at minimum; promoted to production where overhead is acceptable.
  • connectionTimeout bounded so threads fail fast instead of wedging request worker pools.
  • maxLifetime shorter than database idle_in_transaction_session_timeout and network middlebox idle timers.
  • Transaction-mode PgBouncer: JDBC prepare disabled and session-feature code paths audited or moved to session pooling.
  • Product of maximumPoolSize × replica count (plus pooler server pool) fits under database max_connections with headroom.
  • Dashboards track active, idle, pending, and acquire-wait time with alerts before user-visible timeouts dominate.

Example use cases

  • Illustrative scenario — Meridian Commerce: Fifty API pods each run HikariCP with maximumPoolSize=10, yielding 500 client connections against a PostgreSQL primary capped at 200. PgBouncer in transaction mode multiplexes those clients through 150 server backends while engineers monitor pending acquire time and leak warnings.
  • Case study — AWS RDS Proxy: Serverless and burst workloads connect to Proxy's endpoint instead of the database directly; Proxy maintains a warm pool to Aurora or RDS, absorbing connection storms from concurrent Lambda invocations without exhausting max_connections.
  • Illustrative scenario — downstream HTTP: A microservice calling a REST partner configures keep-alive agents (maxSockets: 50) so repeated calls reuse TCP sessions and TLS state, trimming per-request handshake overhead on high fan-out paths.
  • Illustrative scenario — session features: An app that relies on PostgreSQL advisory locks uses PgBouncer session mode (or routes lock-heavy paths outside transaction pooling) because transaction mode cannot hold session state across statements.

Related patterns

  • Request Throttling — checkout limits mirror semaphore-based admission control; an exhausted pool behaves like a saturated throttle queue.
  • Read Replicas — maintain distinct pools (or pooler databases) for primary writes versus replica reads so routing does not starve either tier.
  • Bulkhead Pattern — per-tenant or per-feature pools isolate blast radius when one workload holds connections longer than others.
