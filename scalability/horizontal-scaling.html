Horizontal Scaling

Adding more instances to distribute load; stateless design requirements, load balancer configuration, session affinity, auto-scaling triggers, and shared state externalization.

⏱ 12 min read

What it is

Horizontal scaling (scale-out) increases capacity by adding more interchangeable compute instances that share incoming work, rather than enlarging a single machine. In Kleppmann’s terms (Designing Data-Intensive Applications), the application tier becomes a shared-nothing pool: each node holds no durable private state that other nodes must observe, and a front door—typically a load balancer—distributes requests across the fleet using round-robin, least-connections, weighted, or consistent-hash algorithms.

Elastic fleets are the default in cloud-native systems: AWS Auto Scaling groups, Azure Virtual Machine Scale Sets, Google Managed Instance Groups, and Kubernetes Deployments with the Horizontal Pod Autoscaler (HPA) all implement the same idea—desired replica count tracks load signals. Throughput can grow roughly linearly only when work partitions cleanly across instances; shared databases, session state, or leader-elected singletons become the limiting factors described in DDIA’s discussion of coordination costs versus partition tolerance.

Why it exists

Single-host vertical limits and maintenance windows cannot sustain bursty internet traffic. AWS’s Builders Library articles on load-shedding and static stability emphasize that more boxes behind a load balancer convert capacity into a dial you turn during peak and dial back during trough—paying for peak only when it happens. Lose one instance and the remainder absorb traffic; replace the bad node without taking the whole service offline.

Automated scale-out closes the loop between observability and capacity. Kubernetes HPA reads metrics from the metrics server (CPU, memory) or custom metrics APIs (requests per second, queue depth, Pub/Sub lag) and adjusts replica count within min/max bounds. That pattern—metric → controller → scheduler → healthy endpoints—is the same feedback loop cloud VMs use, expressed at the pod granularity for faster iteration and finer bin-packing.

When to use

  • The request path is stateless, or session and cache state live in Redis, DynamoDB, or another external store every replica can reach.
  • Traffic is spiky, seasonal, or unknown; you need minutes-not-months capacity changes without change windows on a monolith host.
  • You require instance-level fault isolation: blast radius of a bad deploy or memory leak is one pod or VM, not the whole tier.
  • Microservices or worker pools scale independently—checkout API replicas need not track batch-export workers.
  • Cost efficiency matters: smaller instances plus autoscale often beat one oversized server running at low utilization 24×7.
  • You already operate health checks, structured logs, and traces—without them, debugging a growing fleet is painful.

When not to use

  • The bottleneck is a single-writer database, licensed appliance, or hardware dongle that cannot shard—more app servers only deepen the queue at the choke point.
  • Strong affinity to local disk, GPU, or NUMA-local RAM makes remote state externalization slower than one large node.
  • Per-instance licensing makes a fleet more expensive than a vertically sized host, even after autoscale savings.
  • The workload is tiny and stable; operational cost of load balancers, discovery, and autoscale policies exceeds benefit.
  • Global transactions or chatty cross-instance coordination dominate—DDIA’s reminder that distribution has a latency tax applies.

Pros and cons

Pros

  • Near-linear read and compute scaling when instances do not contend on shared mutable state.
  • Rolling, blue/green, and canary deploys drain unhealthy targets while the fleet serves traffic.
  • Fault isolation: one bad replica is cycled by the orchestrator or ASG without customer-visible outage.
  • Elastic cost: HPA and ASG shrink fleets during quiet hours.
  • Geographic expansion: replicate the same pattern in multiple regions behind global load balancing.
  • Aligns with twelve-factor and cloud-native guidance: processes are disposable and replaceable.

Cons

  • Requires disciplined state externalization; retrofitting sticky sessions is fragile under scale-in.
  • Connection and cache storms when many cold replicas start at once—Builders Library calls this a classic overload failure mode.
  • Observability cardinality grows with instance count; sampling and aggregation become mandatory.
  • Session affinity reduces load-balancing quality and complicates draining during deploys.
  • Does not scale the data plane; without read replicas, caches, or sharding, the database remains the ceiling.

Implementation notes

Statelessness: Store HTTP sessions in Redis or encrypted cookies with short TTL. Read configuration from the environment or a config service at boot, not from mutable local files. Treat local disk as ephemeral; persist uploads to object storage. For WebSockets, prefer shared pub/sub backplanes over in-memory-only fan-out.

Load balancing: Application load balancers terminate TLS, enforce HTTP/2, and support slow-start on new targets. Tune health checks to match real dependencies—return 503 from /ready when the database is unreachable so traffic does not land on broken replicas. On scale-in, use connection draining longer than your P99 request time; Kubernetes preStop hooks sleep before SIGTERM to let the Service endpoints update.

Kubernetes HPA: Define minReplicas, maxReplicas, and stabilization windows to prevent flapping. Prefer custom metrics (requests per second, queue depth) over CPU alone for I/O-bound services. Pair HPA with cluster autoscaling only when pending pods cannot schedule; otherwise you scale empty nodes. Set resource requests truthfully—HPA decisions are wrong if requests understate actual usage.

AWS and Azure patterns: Target-tracking ASG policies on ALB request count per target often track user-visible load better than average CPU. Azure’s scale-out guidance recommends idempotent handlers and externalized session state—assumptions identical to DDIA’s shared-nothing app servers.

Common failure modes

  • Database connection storm: Ten new pods each open fifty connections; primary hits max_connections. Mitigate with PgBouncer or RDS Proxy and staggered scale-out.
  • Cache stampede: A flush or cold start makes every replica miss simultaneously. Use single-flight locking, jittered TTL, and warmup jobs on deploy.
  • Thundering herd on recovery: All replicas become ready at once and hammer a cold dependency. Use slow-start on load balancers and readiness gates that verify dependency health.
  • Affinity imbalance: Sticky sessions pile traffic on one instance. Prefer externalized sessions; if affinity is unavoidable, cap duration and monitor per-target RPS skew.
  • Version skew during rollout: Mixed schema and code versions cause subtle errors. Use backward-compatible migrations and feature flags.
  • HPA runaway: A misconfigured metric or retry storm scales the fleet into a cost incident. Cap maxReplicas and alert on replica count derivatives.

Decision checklist

  • All mutable request state externalized or reconstructable from client tokens?
  • Readiness distinct from liveness; dependencies checked before accepting traffic?
  • Graceful shutdown and LB drain exceed longest in-flight request?
  • Autoscale signals tied to user-visible saturation, not only CPU?
  • Database pooling and per-replica connection limits documented?
  • maxReplicas / ASG maximum and cost alarms configured?
  • Deploy strategy tested under partial fleet failure?

Example use cases

  • Illustrative scenario — Northline Commerce runs product search as stateless pods behind an ALB; HPA on ALB RequestCountPerTarget doubles replicas during a marketing push, then scales in overnight while sessions stay in Elasticache.
  • Illustrative scenario — A Kubernetes API fleet uses HPA on custom metrics from Prometheus (in-flight requests); preStop sleeps fifteen seconds so EndpointSlices update before SIGTERM.
  • Illustrative scenario — Transcode workers on an SQS-driven ASG scale on approximate queue depth, using spot instances for batch work and on-demand for SLA-bound jobs.
  • Case study — Azure Architecture Center scale-out guidance describes idempotent handlers and external session stores as prerequisites for elastic web tiers.
  • Case study — Kubernetes documentation defines HPA v2 resource and custom metrics as the standard horizontal loop for pod replica count.
