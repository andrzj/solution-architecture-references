Partitioning Patterns

Database table and index partitioning within a single node; range, list, hash, and composite partitioning, partition pruning, partition key selection, PostgreSQL declarative partitioning, and partition-wise joins.

⏱ 11 min read

What it is

Table partitioning splits one logical table into multiple physical child segments inside a single database instance. Queries reference the parent; the optimizer applies partition pruning to skip segments that cannot contain matching rows. PostgreSQL declarative partitioning supports range, list, and hash strategies; Oracle and MySQL offer similar primitives, including composite partitioning.

Sharding distributes partitions across servers; partitioning keeps them on one host but still delivers maintenance and scan-scope benefits DDIA describes for segmented storage—detach old time ranges instantly, rebuild indexes per segment, and colocate hot and cold data on different tablespaces. It is the stepping stone many teams use before accepting cross-node sharding complexity.

From the query planner’s perspective, each child is a first-class table with its own statistics; the parent is a routing label. That separation is why partition-wise joins can parallelize across children while a single billion-row heap cannot.

Why it exists

Billion-row tables punish vacuum, statistics refresh, and broad indexes even on fast hardware. Monthly range partitions let operators drop or archive March’s data by detaching events_2025_03—metadata operations—not deleting row by row. Time-bounded queries touch one partition instead of the full heap, shrinking I/O and lock contention for OLTP neighbors on the same instance.

Tiered storage follows naturally: recent partitions on NVMe, older ones on cheaper volumes or detached to archive databases. Azure and AWS guidance on data lifecycle management mirrors this pattern—keep hot partitions lean, push cold history to cheaper tiers without rewriting application SQL beyond the partition key in predicates.

Partitioning is also a rehearsal for sharding: teams learn partition-key discipline, archival cadence, and planner behavior while still on one host—skills that transfer directly when shards move to separate instances later.

When to use

  • Time-series, audit, or event tables where filters almost always include a bounded date or tenant key.
  • Retention requires dropping or archiving whole periods regularly.
  • Maintenance windows strain on monolithic tables—VACUUM, index builds, or ALTER block production.
  • Partition-wise aggregates or joins can run in parallel on PostgreSQL 11+.
  • Multi-tenant list partitions isolate large customers for operational or compliance reasons.
  • You are not yet ready for cross-server sharding but need scan and ops relief now.
  • Compliance requires provable data excision for a date range—detach beats long-running deletes.

When not to use

  • Tables are small—planner overhead exceeds pruning benefit.
  • Queries rarely filter on the partition key, forcing scans of all children.
  • Global uniqueness constraints across partitions are required but unsupported without workarounds.
  • Thousands of empty partitions accumulate—planning latency rises.
  • Frequent updates move rows across partition boundaries (mutable partition keys).
  • You depend on foreign keys from many unrelated tables into one giant partitioned fact table without partition alignment—planner and lock behavior become brittle.

Typical architecture

Range partitions by month enable pruning on date filters; composite range-then-hash splits large quarters when a single file grows too wide. Application SQL continues to target the parent table while operations manage child lifecycle.

Pros and cons

Pros

  • Pruning narrows scans for keyed queries—often an order-of-magnitude I/O reduction.
  • Detach and drop archives cold data without long deletes.
  • Per-partition index maintenance limits production blast radius.
  • Tablespace mapping places hot and cold partitions on different storage tiers.
  • Logical model stays one table—ORMs and ad hoc SQL change little.

Cons

  • Unique constraints spanning partitions are limited—design keys carefully.
  • Unpruned queries pay planning and scanning costs across all children.
  • Partition lifecycle must be automated—missing next month’s partition breaks inserts.
  • Foreign keys and triggers on partitioned parents have version-specific caveats.
  • Too many partitions inflate planning time even when pruning works.
  • Backup and restore windows stretch when every child is huge—without archival, partition count rises forever.

Implementation notes

Automate creation: Cron, pg_partman, or CI jobs pre-create next month’s partition before the first insert. Alert if creation fails—default partitions can hide errors until they grow unbounded. Runbooks should include manual CREATE TABLE … PARTITION OF steps when automation is impaired during an incident.

Partition key immutability: Choose columns that are set once—created_at, ingest timestamp, tenant_id. Updates that change partition keys require delete-plus-insert semantics.

Granularity: Aim for tens to low hundreds of partitions; each child between roughly one and fifty gigabytes on disk is a practical band. Daily partitions for multi-year history explode planner work—prefer monthly with subpartition hash if needed.

Pruning-friendly SQL: Avoid volatile functions in predicates (NOW() without stabilization) that prevent compile-time pruning; use explicit bounds in application queries when possible.

Statistics and maintenance: Run ANALYZE per partition after bulk loads so the planner chooses pruning. VACUUM heavy children during off-peak rather than one monolithic table lock. For BRIN indexes on append-only time series, pair them with range partitions so each child’s BRIN stays small and selective.

Composite layouts: Range partition by month plus hash subpartition by tenant_id when a single month’s file grows past comfortable backup or restore windows—Azure partitioning guidance recommends composite schemes when one dimension alone skews size.

Not distributed sharding: Table partitioning keeps one planner, one primary writer, and partition pruning on a single instance. It improves manageability and scan locality but does not multiply write throughput the way horizontal sharding does across nodes. Choose partitioning when history grows unwieldy before accepting cross-shard query semantics.

When partitions are not enough: If the primary still saturates writes after archival, move to Citus or Vitess-style sharding with the same logical partition key as the distribution column—migrations can detach old monthly partitions to cold storage while new writes land on a sharded fleet. Key selection rules mirror sharding: prefer tenant or user cardinality over bare timestamps.

Lifecycle without downtime: PostgreSQL ATTACH PARTITION and DETACH CONCURRENTLY (supported versions) let you roll cold months to object storage or a reporting cluster while inserts keep hitting the parent. Plan default-partition traps: rows that miss explicit children land in a catch-all child—monitor its growth and alert before pruning stops working.

Common failure modes

  • Missing partition: Inserts fail at month boundary when automation lags—page the partition manager, not the app on-call only.
  • Default partition bloat: Rows that fit no child accumulate in a catch-all segment, defeating pruning.
  • No-prune queries: ORMs omit partition key filters—full scans return, latency spikes.
  • Detach without archive plan: Detached children linger on disk, filling storage.
  • Excess partition count: Five years of daily partitions slows planning—archive and drop aggressively.
  • Global index myths: PostgreSQL global indexes on partitioned tables need care during attach/detach—follow version-specific docs.
  • Constraint drift: Check constraints added only on the parent fail on children in some versions—validate per-child DDL in CI.
  • Replication lag on detach: Detaching while logical replication still streams the parent confuses subscribers—coordinate topology changes.
  • Backup bloat: Including every detached archive in nightly full backups wastes space—exclude cold tablespaces or use partition-specific backup policies.

Decision checklist

  • Partition key appears in the majority of production query filters?
  • Automated pre-creation with failure alerting in place?
  • Retention policy maps to detach, archive, or drop schedules?
  • Uniqueness requirements revisited—UUID or application checks where needed?
  • Partition count bounded with archival of historical children?
  • Load tests confirm pruned and unpruned query latencies?

Example use cases

  • Illustrative scenario — CivicWorks Audit ingests fifty million events daily into monthly PostgreSQL partitions; compliance queries scoped to one quarter prune to three children instead of scanning years of history.
  • Illustrative scenario — A SaaS metrics table list-partitions by tenant_id; noisy tenants move tablespaces without migrating neighbors.
  • Illustrative scenario — An e-commerce orders table range-partitions by year so finance reports hit only the current-year child during month close.
  • Illustrative scenario — TelemetryCo attaches a new weekly partition every Sunday via Terraform and pg_partman; Grafana alerts fire if tomorrow’s partition is missing before ingest spikes Monday morning.
  • Case study — PostgreSQL documentation on declarative partitioning describes pruning, attach, and detach semantics used in production time-series designs.
  • Case study — Azure partitioning guidance documents when to choose range versus hash segments before scaling out to multiple servers.
