Hot Partition Mitigation

Detecting and mitigating hot partitions in sharded and NoSQL stores: partition-key design, write scatter, read caching, Azure Cosmos DB RU limits, and DynamoDB partition ceilings.

⏱ 11 min read

What it is

A hot partition (hot shard) is a logical or physical slice of a distributed store that receives far more read or write traffic than its peers. The rest of the cluster may have spare capacity, but requests keyed to that slice throttle, queue, or fail—capping effective throughput and inflating tail latency. Hot partitions undo the point of horizontal partitioning: you paid for scale-out and still hit a single choke point.

Skew comes from partition-key choice (timestamps, monotonic IDs), popularity (viral products, celebrity accounts), or access patterns (everyone reads the same config document). Mitigation mixes key design (high-cardinality keys, salting, synthetic shard suffixes), read path changes (caching, replicas, materialized copies), and platform knobs (Azure Cosmos DB autoscale partition splits, DynamoDB on-demand/adaptive behavior within per-partition ceilings). Microsoft’s partition guidance and DynamoDB’s partition-key docs describe the same constraint: throughput and storage are ultimately bounded per physical partition.

Why it exists

Uniform hash distribution is a model, not a guarantee. Business data is power-law shaped: a few keys dominate QPS. Time-series workloads concentrate writes on “now.” Multi-tenant SaaS may place an entire tenant on one shard if the key is tenantId alone and one tenant is ten times larger than the median.

Managed services enforce hard per-partition limits. Azure Cosmos DB documents request-unit (RU) ceilings per physical partition; sustained hot keys trigger 429 throttling even when account-wide RU/s headroom looks healthy. DynamoDB caps roughly 3,000 read and 1,000 write request units per partition per second. Cassandra hotspots land on token ranges. Without observability at partition granularity, teams misdiagnose “we need more RU/s” when the fix is key redesign.

When to use

  • Metrics show a small set of partition keys or shards at sustained high RU/s, IOPS, or throttle rates.
  • The partition key is time-ordered, low-cardinality, or encodes tenant alone on uneven tenants.
  • Read or write spikes cluster on “hero” entities—featured SKUs, global config, leader election rows.
  • Clients return 429, ProvisionedThroughputExceededException, or growing queue depth while cluster CPU looks idle.
  • You are greenfielding a partitioned store and want key design reviewed before data volume locks in resharding cost.

When not to use

  • Traffic is already even across keys and partitions—avoid salting fan-out with no measured skew.
  • A short-lived launch spike is handled by temporary cache scale or raised RU/s; permanent key surgery can wait for post-mortem data.
  • Salting forces read fan-out that costs more than raising throughput on a proven hot key (do the math).
  • The bottleneck is not partition-local (app thread pools, network)—fix the actual constraint first.

Typical architecture

Classify write vs read hotspots, then apply scatter, cache, or platform scale—often in combination.

Pros and cons

Pros

  • Restores headroom so aggregate cluster RU/s or IOPS can be used.
  • Reduces user-visible throttling and retry storms from single-key saturation.
  • Salting and composite keys are portable across Cosmos DB, DynamoDB, and Cassandra models.
  • Read caches collapse fan-out on hero entities without resharding.
  • Autoscale and partition split buy time while key design is corrected.

Cons

  • Write salting forces multi-partition reads and complicates aggregations.
  • Caches on mutable hot keys need invalidation discipline to avoid stale merchandising or counts.
  • Platform autoscale cannot exceed per-partition physics—extreme skew still fails.
  • Partition-level metrics are harder to obtain than account-level dashboards suggest.
  • Resharding or key migration is costly once production data adopts a bad key.

Implementation notes

Measure before mitigating: Use Cosmos DB metrics (normalized RU consumption per partition key range, 429 ratio), DynamoDB contributor insights, or application logs with partition-key hashing. Confirm skew with live traces—not guesswork from schema review alone.

Write scatter: Append #0…#N-1 salt buckets to logical keys or embed a write shard in the partition key for counters and time buckets. Pick N from measured hotspot ratio (10× load → at least 10 buckets). Reads that need the full logical aggregate fan out with bounded parallelism and merge in the app layer.

Azure Cosmos DB: Prefer high-cardinality partition keys; include tenant plus entity type when tenants vary in size. For provisioned throughput, enable autoscale on containers subject to hot keys; for serverless, throttling still occurs per partition—design keys accordingly. Use Azure Cache for Redis in front of point reads on hot documents; pair with cache invalidation on writes.

Time series: Never use raw timestamp alone; combine deviceId or rotating ingestShard with time bucketing. For DynamoDB, add GSIs that spread query patterns; for Cosmos, model hierarchical keys so hot windows do not collapse to one logical partition.

Common failure modes

  • Salting the wrong key: Fan-out reads increase cost while throttling continues on an uncorrected hot key.
  • Undersized salt range: N=2 on a 100× skewed counter still breaches per-partition limits.
  • Cache stampede: Identical TTL on a viral object expires simultaneously; use jitter and probabilistic early refresh.
  • Account RU misread: Raising total RU/s without key redesign leaves throttling on the same physical partition.
  • Hot logical partition in SQL: Partitioned tables with RANGE on “current month” concentrate inserts—split ranges or switch to hash sub-partitioning.

Decision checklist

  • Partition-key cardinality and access distribution were measured under realistic load.
  • Time-ordered or monotonic keys include scatter or companion high-cardinality components.
  • Write hotspots have a validated salt or composite strategy with benchmarked read fan-out.
  • Read hotspots use cache/CDN with TTL jitter and invalidation on update.
  • 429/throttle alerts tie to partition-key dimensions, not only account aggregates.
  • Runbook exists for temporary RU/s scale plus permanent key migration.

Example use cases

  • Illustrative scenario — RideRelay stores live driver location tiles in Cosmos DB; ingestion shards {driverId}_{epochMinute} with a rotating writeSlot suffix so flash traffic during a city-wide event spreads across 16 physical partitions instead of one.
  • Illustrative scenario — Northwind Logistics caches global rate tables in Azure Cache for Redis with 30-second TTL and tag invalidation on admin updates, eliminating repeated reads of a single configuration document that previously saturated one partition.
  • Case study — AWS and Microsoft both document partition-key design and throttling behavior for DynamoDB and Azure Cosmos DB; teams routinely combine high-cardinality keys with on-demand/autoscale throughput for unpredictable skew.
