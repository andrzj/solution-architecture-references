Materialized Views

Pre-computed query results; refresh strategies (on-commit, scheduled, incremental), PostgreSQL MATERIALIZED VIEW, query performance vs staleness tradeoff, and CQRS read model as materialized view.

⏱ 11 min read

What it is

A materialized view stores the result of a query as physical data. Unlike a virtual view, which re-runs its defining query on every access, a materialized view pays the computation cost at refresh time so reads become simple scans or index lookups. The explicit tradeoff is staleness: consumers see data as of the last successful refresh, not necessarily the latest write.

The pattern appears at every layer. Azure SQL Database and PostgreSQL expose CREATE MATERIALIZED VIEW (or indexed views in SQL Server) for in-database rollups. Azure Synapse Analytics supports materialized views over dedicated SQL pools for warehouse-style pre-aggregation. In CQRS, the read side is an application-level materialized view: a projector consumes domain events from Event Hubs or a change feed and maintains a denormalized store—often Azure Cosmos DB, Azure Cache for Redis, or Azure AI Search—optimized for query shapes the write model does not serve. Microsoft documents this pairing as the Materialized View pattern alongside the CQRS pattern on Azure Architecture Center.

Designing Data-Intensive Applications frames the same idea as derived data: systems of record stay normalized and authoritative, while downstream consumers maintain purpose-built copies transformed for specific query patterns. Whether you refresh a warehouse rollup nightly, stream deltas through Azure Stream Analytics into a serving layer, or run an idempotent Cosmos projector off Event Hubs, you are trading duplication and bounded inconsistency for read latency and isolation from write-path contention.

Why it exists

Heavy joins, window functions, and cross-shard aggregations routinely take seconds on large datasets. Serving that work on every HTTP request or BI drill-down consumes CPU and I/O that OLTP traffic also needs. Materialized views amortize cost: refresh once (or incrementally), read many times at millisecond latency.

In CQRS, the motivation is structural as well as performance. The write model enforces invariants on a normalized schema; storefront and reporting APIs need flat documents, facet counts, or dashboard grains. Projectors build those shapes asynchronously so command handlers stay small and the read tier scales on its own engines. Acceptable lag is a product decision—published as SLA text (“search index within 30 seconds of catalog change”) rather than hidden accidental staleness.

When to use

  • Expensive read queries run far more often than underlying data changes relative to query cost.
  • Dashboards and APIs tolerate bounded staleness when latency and cost targets require pre-aggregation.
  • CQRS or event-driven designs need denormalized read stores fed from commands or change feeds.
  • Cross-service reads would otherwise fan out N+1 calls; a maintained projection collapses them into one store.
  • Search indexes, facet caches, and ranking tables are materialized views under another name.

When not to use

  • Reads must reflect the authoritative write within the same user session without lag (balances, inventory locks, authorization)—query the write store or use synchronous projection only where proven.
  • Change rate is so high that refresh cost rivals ad-hoc query cost; the view never catches up.
  • The underlying SELECT is already fast with proper indexing; maintenance and storage duplication buy little.
  • Storage, replay, and projector ownership cannot be funded—materialized views are not a shortcut around operational discipline.

Typical architecture

Two refresh topologies dominate production Azure systems. In the database-native path, OLTP remains the system of record; Elastic Job, pg_cron, or Synapse pipelines run REFRESH on schedule while dashboards and internal APIs read the materialized table directly. In the CQRS path, command handlers append to Azure SQL or Cosmos transactional storage, publish through transactional outbox or change feed to Event Hubs, and stateless projectors upsert denormalized documents into a read tier sized independently—autoscale RU/s on Cosmos, dedicated search replicas, or Redis fronting hot keys. Pros and cons

Pros

  • Turns multi-second aggregations into millisecond lookups after refresh.
  • Shifts CPU and I/O to refresh windows instead of every user read.
  • CQRS read models let query and command tiers scale on different Azure SKUs.
  • Derived stores can be rebuilt from the event log after schema or projector bugs.
  • Indexes on materialized views support the same filter/sort paths as base tables.
  • Azure CQRS deployments can place read APIs in a separate region or subscription from command handlers, limiting blast radius during projector or refresh outages.

Cons

  • Staleness is inherent unless you invest in synchronous or near-real-time projection.
  • Full refresh on large views spikes CPU; overlapping schedules compound load.
  • Non-concurrent refresh blocks readers; CONCURRENT refresh needs unique indexes and runs longer.
  • Projector or job failures leave silent drift unless freshness metrics are monitored.
  • Denormalization duplicates storage and complicates GDPR-style erasure across projections.
  • Ordering and causal semantics across multiple materialized targets require version vectors or monotonic sequence fields—DDIA’s stream-processing materialization guidance applies when one event updates several derived stores.

Implementation notes

In-database views: On PostgreSQL and Azure Database for PostgreSQL, prefer REFRESH MATERIALIZED VIEW CONCURRENTLY when unique indexes exist; otherwise schedule blocking refresh in maintenance windows. Azure SQL indexed views use SCHEMABINDING and different invalidation rules—validate against Microsoft guidance before treating them like PostgreSQL materialized views. In Synapse dedicated pools, size compute for refresh jobs separately from interactive queries; Microsoft recommends autostats and distribution hints when the defining query scans large fact tables.

CQRS on Azure: Commands write to Azure SQL or Cosmos DB transactional containers; integrate events through transactional outbox tables, Change Data Capture, or Cosmos change feed. Azure Functions or containerized workers subscribe via Event Hubs or Service Bus and upsert read documents into Cosmos (partitioned for query keys), Azure AI Search indexes, or Redis caches. Keep projectors idempotent—at-least-once delivery is the default. For multi-region active-active, treat each read store as eventually consistent with the event log as the rebuild source of truth, matching Azure’s CQRS guidance on separate command and query data stores.

Incremental and streaming paths: Where full refresh is too slow, maintain delta tables fed by CDC or append-only logs and merge incrementally—the same operational model as Flink or Spark structured streaming materialized into a serving tier. Even without a stream processor, batch “apply changes since watermark” jobs often beat nightly full recompute on fact tables above hundreds of millions of rows.

Freshness contract: Expose last_projected_at or version fields on API responses when lag matters. Measure p95 projection delay; alert when it exceeds the documented SLA. Document a full replay procedure: new read container, replay from offset zero or snapshot plus delta, alias cutover.

Read scaling trade-off: Materialized paths trade write amplification and staleness for O(1) reads—Amdahl’s insight applies to refresh jobs: if 30% of the projection must scan live OLTP rows serially, speeding up the parallel 70% eventually stops helping. Profile the defining query before adding replicas; sometimes pre-aggregation beats another read copy.

Refresh strategies: Full refresh locks readers on PostgreSQL unless you use REFRESH MATERIALIZED VIEW CONCURRENTLY, which requires a unique index on the view and still costs I/O. Incremental paths maintain delta tables fed by CDC or append-only changelogs and merge on a schedule—often cheaper than nightly full scans on hundred-million-row facts. Blue/green materialized tables (build v2, swap view name) avoid long locks during cutover.

Common failure modes

  • Silent stale views: Elastic Job, Functions, or pg_cron failures stop refresh with no alert; dashboards show week-old totals. Track last-success timestamps and staleness SLO breaches.
  • Blocking refresh during peak: Full refresh without CONCURRENT holds locks through a traffic spike. Use concurrent refresh, smaller incremental batches, or blue/green materialized tables.
  • Projector drift: A handler bug writes wrong facet counts; search and OLTP disagree until someone notices. Run periodic reconciliation queries and support full replay.
  • Coupling commands to read stores: Command handlers query the search index to validate uniqueness—reintroduces latency and failure modes CQRS was meant to remove.
  • Storage underestimate: Wide denormalized projections exceed budget; compaction and TTL policies were never designed.
  • Schema migration gap: Base-table DDL changes invalidate indexed views or break projector mappings; ship backward-compatible events and dual-write projections until cutover completes.
  • Unbounded catch-up: After an outage, projectors or refresh jobs fall behind faster than they can replay; define maximum backlog depth and shed non-critical projections before user-facing SLOs fail.

Decision checklist

  • Maximum acceptable staleness is written down per consumer and matches refresh or projection latency.
  • Production refresh uses non-blocking paths where traffic requires it (CONCURRENT, incremental, dual-table swap).
  • Refresh or projection duration is measured; schedules include headroom to prevent overlap.
  • Monitoring alerts on last-success time and projection lag, not only error logs.
  • CQRS read models are rebuildable from the event stream or change feed with a tested runbook.
  • Storage, replay time, and erasure impact of denormalized copies are estimated.
  • Azure command and query tiers use separate connection strings, secrets, and autoscale policies so read spikes do not starve writers.
  • Periodic reconciliation jobs compare sampled aggregates between system of record and materialized store.

Example use cases

  • Illustrative scenario — Meridian Commerce runs commands on Azure SQL and publishes OrderPlaced events to Event Hubs. A Function projector maintains an order_summary container in Cosmos DB; the storefront query API reads partition-key lookups in under 10 ms while the normalized write schema stays unchanged.
  • Illustrative scenario — A regional analytics team refreshes PostgreSQL monthly_sales_by_region every 15 minutes via Elastic Job; Power BI hits the materialized view instead of scanning 80 million fact rows on each report open.
  • Case study — Azure Architecture Center’s CQRS and Materialized View patterns describe separating command and query workloads with dedicated read data stores—common in catalog, IoT telemetry dashboards, and order-tracking UIs on Azure managed services.
  • Illustrative scenario — A multi-tenant SaaS billing service writes invoice events to Event Hubs; projectors maintain per-tenant AR aging summaries in Cosmos and a warehouse materialized view in Synapse. Finance exports hit Synapse with 15-minute freshness while the customer portal reads Cosmos documents scoped by tenantId without joining normalized line-item tables.

Related patterns

  • CQRS — read models are durable materialized views fed by events or change feeds.
  • Normalization vs Denormalization — materialized views are controlled denormalization for read paths.
  • Caching Strategies — ephemeral cache vs durable materialized store; often layered (Redis in front of Cosmos documents).
  • Lazy Loading — compute-on-read opposite; combine when only a fraction of aggregates are hot.
