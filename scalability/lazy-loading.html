Lazy Loading

Deferring initialization until needed; lazy singleton, lazy DB relations (N+1 problem and its fix), lazy loading in UI (Intersection Observer), virtual scrolling, and skeleton screens.

⏱ 11 min read

What it is

Lazy loading defers fetching or initializing a resource until code or the user actually needs it, instead of loading everything at startup or on the parent query. The pattern trades a possible latency spike on first access for smaller memory footprints, faster cold start, and less wasted I/O on paths that never touch the deferred data.

It appears at every tier: lazy initialization of expensive singletons, ORM lazy associations (load children only when traversed), viewport-driven assets (loading="lazy", Intersection Observer), route-based code splitting in SPAs, and virtualised lists that render only visible rows while paging data in the background.

Why it exists

Time-to-interactive dominates product metrics: booting dozens of services, prefetching thousands of assets, and pulling large JSON graphs before the first paint keeps users staring at spinners. Deferring non-critical work lets the critical path finish first; everything else can hydrate, stream, or download after the shell is usable.

Memory pressure is equally real. A grid that shows twelve SKUs while the catalog holds hundreds of thousands cannot afford to materialize the full collection in RAM—pagination, virtual windows, and on-demand fetches keep resident data in kilobytes instead of gigabytes.

ORM layers amplify the tradeoff. Returning a parent row without joined children is fast; eager-fetching every optional association for every list endpoint multiplies joins and payload size for code paths that never read those fields—exactly the waste lazy loading was meant to avoid when associations are truly optional.

Front-end performance budgets (LCP, INP, total blocking time) reward deferring below-the-fold assets and non-critical JavaScript while keeping the critical rendering path lean.

When to use

  • Assets or data are bulky, costly to fetch, and only some requests or personas touch them (images, admin modules, infrequent reports).
  • Cold start or first paint matters—initialize security and routing first; defer analytics exporters, feature probes, and heavy SDKs until after listen/ready.
  • Feeds, tables, or infinite scroll where rendering every row would overwhelm the DOM—load the viewport plus a small prefetch margin.
  • Domain models with optional associations: default to lean queries; fetch children only when a handler actually traverses the graph.
  • Large front-end bundles—split by route or feature so mobile users do not download checkout code on the home page.

When not to use

  • Every request touches the resource on the hot path—deferral only adds indirection and a guaranteed miss on first access.
  • Lazy association access inside loops over parents—the classic N+1 pattern; replace with JOIN/eager fetch for that path.
  • Authn, authz, WAF rules, and input validation that must guard the first byte served—never delay these to “first request.”
  • Hero, logo, and other above-the-fold media required for LCP—eager or priority-load them; lazy below-the-fold content instead.

Typical architecture

On access, choose eager fetch for the critical path or defer until first touch—with eager JOINs when loops would otherwise cause N+1 queries.

Pros and cons

Pros

  • Shrinks boot and first-load budgets by moving optional work off the synchronous startup path.
  • Never-loaded resources cost zero RAM and zero egress—waste tracks actual access patterns.
  • Skeleton screens and progressive enhancement make the app feel fast even while deferred chunks arrive.
  • Back ends see fewer speculative queries and smaller payloads when handlers fetch only what the code path reads.
  • Virtualization keeps DOM node count bounded for long lists that would otherwise choke the renderer.

Cons

  • First touch pays the full fetch/parse cost—latency moves from startup to the moment of need.
  • Implicit lazy associations in loops remain the most expensive ORM foot-gun (N+1).
  • Thread-safe lazy singletons and module init require explicit synchronization or language primitives.
  • Images without reserved dimensions reflow on load, hurting CLS and Core Web Vitals scores.
  • Virtual lists demand extra engineering for focus management, keyboard nav, and screen-reader semantics.

Implementation notes

The N+1 problem: Listing N parents then touching a lazy child on each row fires N extra round trips—101 queries for 100 orders is the textbook failure. Profile SQL in development; ORM code rarely advertises the pattern. Fix with JOIN fetch, include/includes, @EntityGraph, or a dedicated DTO query for list endpoints.

In Hibernate/JPA, prefer JOIN FETCH or fetch graphs on the repository method that backs the list API. In Sequelize and Rails, scope include/includes to the handler that needs children—not the global default scope. Enable SQL logging or APM database spans in non-production and treat “queries per request” as a release gate.

Make “list view” and “detail view” fetch plans explicit in code review: optional associations belong on detail queries, not default scopes. Staging should fail CI or warn when query count per request exceeds a budget.

Intersection Observer for images: Prefer native loading="lazy" for images and iframes; pair with explicit width/height or aspect-ratio to reserve layout. For custom sections or dynamically imported components, Intersection Observer with rootMargin of 200–400px prefetches just before scroll arrives, hiding network latency without eager-loading the whole page.

Code splitting: In React, Vue, and Angular, lazy-route imports shrink the initial bundle; prefetch critical routes after idle. On the server, lazy-init expensive SDK clients only in workers that need them so API pods that serve health checks do not load heavy ML runtimes at boot.

Serial chains: Each lazy boundary adds another network round trip; deep dependency waterfalls inflate tail latency the same way microservice fan-out does—prefetch or batch where the user journey is predictable, and measure p99 end-to-end, not only first-byte time on the shell document.

Common failure modes

  • N+1 query problem: Hidden lazy getters inside service loops—catch with ORM statistics, Micrometer query tags, or integration tests that assert query count per HTTP call. One extra query per row at 10k rows can DDOS your own database during a product launch.
  • Layout shift on lazy image load: Missing intrinsic size or aspect-ratio boxes causes CLS spikes; use placeholders, blur-up LQIP, or fixed aspect containers. Reserve space even when using responsive srcset.
  • Race conditions in lazy singleton initialization: Double-checked locking without volatile, or unsynchronized module init in multi-threaded runtimes—use holder idiom, sync.Once, Kotlin lazy, or equivalent.
  • Deferred security initialization: First request races ahead of middleware registration—register auth and validation in the main bootstrap before accepting traffic.
  • Waterfall bundles: Chained dynamic imports without preloading can serialize network fetches on navigation—prefetch likely next routes and colocate critical CSS with the shell.

Decision checklist

  • Hot list endpoints use eager/JOIN plans; lazy associations limited to optional detail flows.
  • Development and staging emit per-request query counts or slow-query alerts for N+1 regression.
  • Below-the-fold media lazy-loads with reserved layout; LCP candidates are prioritized or preloaded.
  • Lists beyond ~1,000 visible rows use virtualization or keyset pagination, not full DOM materialization.
  • Shared lazy singletons reviewed for safe publication under concurrency.
  • Security, tracing, and health middleware initialize before the server advertises ready.
  • Route-level and component-level lazy boundaries are documented so on-call engineers know which chunks affect which user journeys.

Example use cases

  • Illustrative scenario — RideRelay catalog: Product grids server-render the first page; below-the-fold images use native lazy loading and infinite scroll fetches the next page only when the sentinel nears the viewport.
  • Illustrative scenario — checkout bundle: A React storefront splits routes with React.lazy so the heavy checkout chunk downloads only after navigation, shrinking the initial JavaScript payload on mobile networks.
  • Illustrative scenario — operations grid: A 500k-row report uses virtual scrolling (TanStack Virtual or similar) so the DOM holds ~50 rows while the data source pages in the background.
  • Illustrative scenario — ORM discipline: Engineers enable SQL logging in staging and replace lazy association loops with include / JOIN FETCH before promotion when list endpoints fan out to dozens of queries per request.

Related patterns

  • Materialized Views — front-load computation so reads stay cheap; opposite default from on-demand fetch.
  • Caching Strategies — cache-aside combines lazy first fetch with fast repeat hits from the cache tier.
  • Partitioning Patterns — paging and keyset cursors lazily load one slice of a large dataset at a time.
