Rate Limiting

Token bucket, leaky bucket, fixed window, sliding window log, sliding window counter algorithms; per-user/per-IP/per-key limits, 429 with Retry-After, and distributed rate limiting with Redis.

⏱ 13 min read

What it is

Rate limiting caps how many requests a client—or tenant, API key, or IP—may make to an API within a time window. When the limit is exceeded, the edge returns HTTP 429 Too Many Requests (often with Retry-After and rate-limit headers) instead of admitting more work. The control is deliberately harsh: excess demand is rejected, not queued, so one caller cannot consume shared capacity indefinitely.

Production systems choose among several counter shapes. Fixed-window counters are simple but allow boundary bursts. Sliding-window counter blends two windows for a practical distributed default. Token bucket permits bounded bursts while enforcing a long-term average. Leaky bucket smooths output to protect strict downstream rates. Sliding-window log is exact but memory-heavy—usually reserved for low-cardinality keys.

Why it exists

Unbounded clients can monopolize CPU, sockets, and database time. Runaway retries, aggressive crawlers, and volumetric attacks look like legitimate traffic until the shared tier collapses—rate limits cap how much damage one identity can inflict before overload propagates.

Commercial APIs encode entitlements as numbers: free, standard, and enterprise tiers differ by requests per minute and burst allowance. Enforcement at the edge turns pricing into mechanical truth instead of hoping noisy neighbors behave. A free tier capped at 100 requests per minute cannot crowd out a paid tier at 10,000 requests per minute when counters are enforced consistently.

The same counters guard fragile downstreams—inference clusters, partner webhooks, and OLTP pools—so aggregate demand cannot exceed documented safe throughput. A database comfortable at 5,000 queries per second will not survive 50,000 unless the API tier shapes arrivals first.

When to use

  • Internet-facing endpoints where callers are unauthenticated, unknown, or only weakly identified.
  • Multi-tenant products that must isolate noisy neighbors before one tenant skews P99 for everyone else.
  • Monetized APIs where plan limits are part of the contract and support tooling.
  • Facades over capacity-constrained dependencies—third-party SaaS, GPUs, or shards with hard QPS ceilings.
  • Authentication surfaces (login, MFA, password reset) to blunt brute force and credential-stuffing automation.
  • Webhook receivers and partner callbacks where retry storms from one integration can drown shared workers.

When not to use

  • East-west calls inside a mesh with mTLS, service identity, and existing bulkheads—prefer breakers and budgets there.
  • Dedicated single-tenant integrations with contractual traffic profiles and private networking.
  • Workloads that need queueing and backpressure rather than hard 429—pair with request throttling when delay is acceptable.

Typical architecture

Middleware evaluates a counter keyed by client identity; allowed requests continue, rejected ones return 429 with standard headers.

Pros and cons

Pros

  • Hard per-identity ceilings stop one bad actor from pinning CPU, threads, or connection pools.
  • Fairness across tenants and API keys preserves SLA headroom for paying customers.
  • Coarse abuse controls on login and webhook endpoints reduce fraud and amplification risk.
  • Token buckets honor short legitimate bursts while constraining sustained averages.
  • Central counters in Redis (Lua/CAS) stay consistent across horizontally scaled gateway replicas.

Cons

  • Fixed windows admit 2× traffic across boundaries unless you blend or slide windows.
  • Exact sliding logs need O(requests) storage—impractical at millions of keys and high RPS.
  • Every check adds datastore RTT unless you embed limits in the edge or sidecar with local cache.
  • NAT and carrier-grade NAT collapse many humans into one IP bucket—false positives abound.
  • Clients that hammer retries on 429 multiply load; backoff discipline must be documented and tested.
  • Misconfigured limits on shared infrastructure (API gateway + app) can double-charge clients or reject legitimate traffic.

Implementation notes

Algorithm selection: Default to sliding-window counter in Redis—two buckets per key, near-ideal accuracy, O(1) memory, typically within ~0.5% of a true sliding window. Choose token bucket when onboarding bursts are expected (an analytics job that reads 500 rows then trickles). Use leaky bucket when shaping output to a partner’s rigid RPS (for example an external AI API capped at 10 req/s). Reserve sliding-window logs for audits or tiny cardinalities, not production hot paths—O(requests) memory per key explodes at scale.

Rate limit keys: Authenticated traffic should key on API key or user ID; reserve IP keys for pre-auth routes. IP limits are appropriate for login and registration but unreliable behind corporate NAT or mobile carrier CGNAT. Layer dimensions: per-IP guardrails, per-key quotas, per-route expensive POST caps, and optional global circuit breakers on pathological endpoints.

Namespace keys deliberately (rl:ip:{ip}, rl:key:{id}:{route}) so TTL eviction and observability stay understandable during incidents. Run limiter logic in a single Lua script or atomic transaction so horizontally scaled gateways do not double-count under race.

Response contract: Standardize on HTTP 429 with Retry-After, X-RateLimit-Limit, X-RateLimit-Remaining, and X-RateLimit-Reset (or IETF RateLimit-* headers where adopted). Clients and SDKs should parse headers instead of guessing backoff intervals.

Downstream occupancy: Limits cap effective arrival rate λ at protected dependencies; Little’s Law still governs how many in-flight calls accumulate behind successful 200 responses. Pair per-identity limits with global concurrency caps when downstream latency rises—429 on one tenant does not stop others from filling the database queue.

Common failure modes

  • Redis unavailability: Decide fail-open vs fail-closed before the outage—open preserves revenue but invites abuse; closed protects capacity but creates total outage. Automate health checks and page when limiter bypass activates.
  • Retry storm amplification: Clients ignore Retry-After and retry in tight loops—document backoff, jitter, and cap client concurrency; optionally penalize repeat offenders with longer windows.
  • Shared IP rate limit starvation: Corporate NAT exhausts a single IP quota—require API keys for steady-state traffic and raise IP limits only on login-specific routes.
  • Clock skew in distributed counters: Mixed host clocks desynchronize fixed windows—use Redis TIME or a single authority for window boundaries.
  • Boundary burst on fixed windows: Attackers or buggy clients may send limit traffic at window rollovers—blend previous and current window counts or migrate to sliding counter/token bucket.
  • Limiter cache staleness: Edge-local counters that lag central Redis may admit brief overages—tune sync interval versus accuracy for your SLA tier.

Decision checklist

  • Algorithm matches burst profile: sliding counter by default, token bucket where spikes are contractual.
  • Limiter keys align with identity: user/key for auth, IP only where identity is unknown.
  • 429 responses carry Retry-After plus limit/remaining/reset headers clients can parse.
  • Fail-open/closed policy documented; Redis SLO monitored with runbook.
  • SDKs and public docs mandate exponential backoff with jitter on 429.
  • Heavy routes have stricter limits than cheap GETs—cost-aware quotas per endpoint class.
  • Limiter metrics (allowed, rejected, near-limit) are dashboarded per route and tenant for capacity planning.
  • Load tests validate limiter behavior under parallel clients, not only single-threaded functional tests.
  • Documentation explains tier limits, burst behavior, and how to request quota increases for enterprise customers.

Example use cases

  • Illustrative scenario — Northwind Logistics API: Tiered API keys map to sliding-window limits in Redis (100/min free, 1_000/min standard, 10_000/min enterprise). Over-limit calls receive 429 with Retry-After and remaining quota headers for SDK backoff.
  • Illustrative scenario — login hardening: Unauthenticated login routes rate-limit by IP (10 attempts per 15 minutes) and pair with account lockout after repeated failures to slow credential-stuffing bots without throttling the whole site.
  • Case study — Stripe: Public REST APIs document rate limits per key and rely on counter infrastructure that scales with horizontal API tiers—an established reference for algorithm choice and client backoff expectations.
  • Illustrative scenario — inference burst: A model-serving façade applies per-user token buckets (50 burst, 5/min sustained) so batch jobs can spike briefly while protecting GPU-backed upstream quotas.

Related patterns

  • Request Throttling — queue and shape excess work server-side when rejection is worse than delay.
  • Circuit Breaker — clients stop calling unhealthy upstreams; rate limits stop upstreams from unhealthy clients.
  • CDN Architecture — edge WAF and CDN tokens enforce coarse limits before origin compute.
