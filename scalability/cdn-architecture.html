CDN Architecture

Content delivery networks; edge PoPs, cache-control headers, origin shield, edge computing (Lambda@Edge, Cloudflare Workers), cache purging, and dynamic content acceleration.

⏱ 12 min read

What it is

A content delivery network (CDN) is a distributed set of edge points of presence (PoPs) that cache HTTP responses and serve them close to end users. Anycast DNS or HTTP routing directs each request to a nearby PoP; cache hits return in single-digit milliseconds without contacting origin. On a miss the edge fetches from origin (often via an intermediate shield PoP), stores the object under rules derived from Cache-Control and provider-specific headers, and serves it to subsequent clients in that region.

Providers such as Cloudflare, Fastly, and Amazon CloudFront extend beyond static files: they terminate TLS, cache selective API responses, run edge functions (Cloudflare Workers, Fastly Compute@Edge, Lambda@Edge), enforce WAF rules, and ride private backbones to reduce last-mile latency to origin. CDNs complement application caches like Redis—Redis holds hot dynamic fragments; the CDN absorbs geographic fan-out and volumetric traffic.

Why it exists

Physics sets a floor on round-trip time between a browser in Asia and an origin in North America. DDIA’s latency numbers are blunt: long distances dominate p95 before your application does any work. Cloudflare and Fastly place PoPs in hundreds of cities so the first byte often travels kilometers, not continents, which is why edge hits routinely land in single-digit milliseconds where cross-ocean routes cost hundreds.

Product teams track that gap in revenue. Extra latency correlates with lower conversion and higher bounce on mobile networks, so shaving tens of milliseconds at the edge is a business lever, not only an infrastructure preference.

CDNs also multiply origin throughput. When Fastly or Cloudflare serves 99.9% of requests from edge SSD, a modest origin fleet survives flash crowds that would swamp auto-scaling groups still booting instances. The same anycast footprint that accelerates static assets absorbs volumetric attacks before they reach your VPC, which is why public sites treat CDN as mandatory perimeter capacity rather than an optional accelerator.

When to use

  • Customers spread across regions and origin RTT materially affects UX or API SLAs.
  • Responses are cacheable by URL, surrogate key, or cache tag—assets, public JSON, SSR pages with shared fragments.
  • Marketing or news events can spike QPS far beyond origin autoscaling limits within minutes.
  • You want WAF, bot management, and DDoS scrubbing in front of origins without building your own global network.
  • Cloud egress fees dominate cost at scale and edge hits reduce bytes pulled from the data center.
  • Workers or Compute@Edge can run auth, redirects, or experiments without a full round trip to origin Redis or databases.

When not to use

  • Traffic stays inside a private network colocated with origin; a CDN hop adds cost without latency win.
  • Every response is unique per session cookie or auth header, so edge hit ratio stays near zero.
  • Data residency or contractual terms forbid caching payload bytes on third-party edge disks.
  • The workload is long-lived duplex streams (WebSockets, gRPC bidi) where HTTP caching semantics do not apply.

Typical architecture

Users hit the nearest PoP; misses collapse at an origin shield before a single fetch reaches the application tier.

Pros and cons

Pros

  • Edge PoPs shrink time-to-first-byte for global audiences compared with always reaching centralized origins.
  • Cached responses decouple user-visible capacity from origin replica count during spikes and flash sales.
  • Bytes served from Fastly or Cloudflare edge reduce origin egress charges and cross-region transfer on cloud bills.
  • Managed scrubbing and rate limits absorb abuse before it consumes application CPU or Redis connection pools.
  • Edge compute runs token checks, header normalization, and experiments close to users with bounded cold-start cost.

Cons

  • Purge and surrogate-key invalidation propagate asynchronously; DDIA-style eventual consistency applies worldwide.
  • Request and egress pricing accumulates at scale and must be modeled against origin-only alternatives.
  • Highly personalized HTML or APIs see poor hit rates and may add an extra hop without caching benefit.
  • Edge runtimes impose CPU, memory, and duration ceilings that rule out heavy aggregation or database access.
  • Global edge storage complicates GDPR, HIPAA, or sovereign-cloud requirements unless you restrict cacheable content classes.

Implementation notes

Cache-Control header strategy: The most critical CDN configuration decision is setting correct Cache-Control headers on origin responses. For static assets with content-addressed URLs (filenames including a hash like app.a8f3b2.js), use max-age=31536000, immutable — the content never changes so it can be cached for one year. For dynamic API responses that can be shared across users, use public, max-age=300, stale-while-revalidate=60 — cached for 5 minutes with 60 additional seconds of stale serving while background revalidation occurs. For user-specific responses, use Cache-Control: private, no-store to prevent CDN caching.

Use Surrogate-Control or CDN-Cache-Control headers for CDN-only TTLs that differ from browser cache TTLs.

Origin shield: Enable CloudFront Origin Shield, Fastly shielding, or Cloudflare tiered caching so one designated PoP fetches on behalf of all edges. Concurrent misses for the same cache key collapse to one origin request—critical when TTLs expire on viral assets. Shield PoPs also retain hot objects longer than small regional caches, improving hit ratio on the edge.

Fastly vs Cloudflare knobs: Fastly exposes VCL and surrogate keys for fine-grained cache keys and soft purges; Cloudflare Workers plus cache rules handle URL normalization and bot filtering before origin. Document which headers enter the cache key (Vary, cookies, query strings) in runbooks—misconfiguration is a common source of low hit rate or cache leakage.

Latency tails: Even with high hit ratio, a miss fan-out to origin can synchronize across PoPs when TTLs align—Dean and Barroso’s tail-at-scale insight applies at the edge: shielding and staggered TTL jitter prevent many edges from collapsing on origin at once.

Cache keys and Vary: Only Accept-Encoding (and similar negotiation headers) belong in the cache key by default—each additional Vary dimension multiplies stored objects. Prefer content-hashed filenames for static assets so purge is a deploy, not an API storm. Use stale-while-revalidate and stale-if-error (RFC 5861) to serve slightly old JSON while revalidating or when origin blips—document maximum staleness for product owners.

Edge compute: Cloudflare Workers and Fastly Compute@Edge run authorization, URL normalization, and A/B routing before origin—shrinking miss bytes and hiding latency for personalization that must not be cached globally.

Common failure modes

  • Cross-user cache leakage: Omitting Cache-Control: private or caching on session cookies stores authenticated JSON at the edge; the next client may receive the wrong body. Mark sensitive routes non-cacheable and test with two accounts.
  • Cache key fragmentation: Unsorted query strings and tracking parameters explode variants of the same resource. Normalize cache keys in Fastly VCL or Cloudflare rules and strip marketing params.
  • Purge throttle during launch: Bulk URL purges hit provider rate limits; some PoPs serve stale marketing pages for minutes. Prefer cache tags or surrogate keys and rehearse purge runbooks.
  • Origin bypass attack or misconfiguration: DNS or firewall rules expose origin directly; traffic bypasses shielding and DDoS protection. Allow-list only CDN egress IPs on origin load balancers.
  • Over-broad Vary: Including User-Agent or uncommon headers multiplies stored objects and destroys hit ratio. Limit Vary to encoding negotiation where required.

Decision checklist

  • Every response class has explicit Cache-Control, optional CDN-Cache-Control, and documented browser vs edge TTL intent.
  • Fingerprinted static assets use immutable long TTL; mutable HTML uses shorter edge TTL plus purge hooks.
  • Origin shield or tiered caching is on for high-traffic properties to collapse concurrent misses.
  • Cache key recipes (query allow lists, cookie ignore lists) are reviewed in security and performance review.
  • Purge paths for CMS, pricing, and legal holds are automated and load-tested, including Fastly soft purge and Cloudflare tag purge.
  • Origins reject traffic not from known CDN address ranges; monitoring alerts on direct-to-origin spikes.
  • Edge Worker or Compute scope is bounded: no secret DB credentials at PoP, clear fallback to origin on failure.

Example use cases

  • Illustrative scenario — media metadata: Thumbnail and JSON metadata responses cache at PoPs with long max-age; origin serves only novel uploads, cutting egress during viral clips.
  • Illustrative scenario — flash sale SSR: Product pages use stale-while-revalidate for 60 seconds at the CDN so concurrent shoppers see edge-cached HTML while origin refreshes in the background.
  • Case study — Fastly edge: Surrogate-key purges invalidate all PDP and listing variants when merchandising updates a SKU, without waiting for passive TTL.
  • Case study — Cloudflare: Workers validate JWTs at the edge; cacheable public JSON uses cache rules while authenticated routes bypass cache with Cache-Control: private.

Related patterns

  • Caching Strategies — treat the CDN as L3 in a multi-tier cache stack above Redis and in-process stores.
  • Cache Invalidation — edge purges are the hardest invalidation problem because propagation is global and eventually consistent.
  • Rate Limiting — enforce coarse per-IP and per-path limits at the edge before requests hit application Redis counters.
  • Circuit Breaker — pair origin shield with breaker semantics when upstream health degrades during miss storms.
