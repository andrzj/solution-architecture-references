Sharding Strategies

Horizontal data partitioning across multiple database nodes; range sharding, hash sharding, directory-based sharding, consistent hashing, cross-shard queries, resharding complexity, and shard key selection.

⏱ 14 min read

What it is

Sharding partitions a dataset across multiple independent database nodes so each shard owns a disjoint subset of keys and serves reads and writes for that subset only. A router—Vitess VTGate, MongoDB mongos, application-side logic, or a managed control plane—maps a shard key to the correct backend. Unlike replication, where every replica holds the full dataset, sharded storage grows aggregate write throughput and disk capacity with the number of shards.

DDIA treats sharding as application-aware partitioning: you gain horizontal scale at the cost of losing naive joins, global secondary indexes, and single-node transactions across shard boundaries. Azure’s sharding guidance describes the same contract—choose a partition key with high cardinality and even spread, design queries to be single-shard by default, and treat cross-shard operations as expensive scatter-gather workflows.

At the application layer, shard awareness belongs in the data access library or repository layer so engineers cannot accidentally issue cluster-wide scans from an ORM default.

Why it exists

A single relational or document primary eventually saturates write IOPS, WAL throughput, or on-disk size. Vertical scaling and read replicas extend the runway but do not multiply write paths. Internet-scale systems (messaging graphs, multi-tenant SaaS, telemetry ingress) need many writers in parallel—sharding is how Dynamo-style systems, Cassandra, and sharded MySQL fleets keep piling on capacity linearly until operational complexity becomes the limit.

Geographic and regulatory sharding also motivate the pattern: pinning EU tenants to EU shards satisfies residency without copying the world’s data everywhere. AWS Builders Library essays on cell-based architecture echo the idea—smaller failure domains with clear ownership boundaries—even when the implementation is logical shards rather than full microservice cells.

Kubernetes itself does not shard your database, but statefulSets with one writer per shard and headless services illustrate the same topology at the orchestration layer: stable network identity per data partition, routers elsewhere. The operational lesson crosses tiers—know which layer owns partition placement.

When to use

  • Write throughput or total data size on one node exceeds comfortable vertical limits and cost targets.
  • Primary access paths include a stable shard key (user id, tenant id, conversation id) in every hot query.
  • You can accept weakened cross-shard guarantees or redesign features to avoid them.
  • The data platform offers managed sharding (DynamoDB, Cosmos DB, Aurora Limitless) or mature routers (Vitess).
  • Hot spots are manageable with salting, compound keys, or mitigation runbooks.
  • Operations can backup, monitor, and migrate per shard—not only one monolithic database.

When not to use

  • Reporting workloads need ad hoc joins across arbitrary dimensions without shard keys.
  • You require frequent multi-entity ACID transactions that do not co-locate on one shard.
  • No shard key exhibits even load—celebrity tenants or time buckets will concentrate writes.
  • Dataset fits a single large instance with replicas and caches at acceptable cost and risk.
  • Team lacks runbooks for resharding, schema parity, and router failover.

Typical architecture

Application routers hash or range-map keys to shard primaries; consistent hashing limits data movement when topology changes.

Pros and cons

Pros

  • Write and storage scale roughly with shard count for well-chosen keys.
  • Blast radius shrinks—a failed shard affects its slice, not the global catalog.
  • Regional shards cut latency and support data residency policies.
  • Single-shard queries stay local—no distributed coordinator on the hot path.
  • Large tenants can move to dedicated shards without rewriting the whole schema.

Cons

  • Cross-shard queries fan out—latency and cost multiply by shard count.
  • Resharding and rebalancing are risky, long-running operations.
  • Distributed transactions across shards are slow and fragile; design them out when possible.
  • Shard key mistakes are expensive to fix after production data lands.
  • Operational surface area: N primaries, N backups, N migration pipelines.

Implementation notes

Shard key design: Prefer high-cardinality, application-meaningful keys aligned with queries—tenant_id, user_id, conversation_id. Avoid monotonic time-only keys that create append hot spots unless combined with hash salting. Composite keys (tenant_id + entity_id) isolate noisy neighbors in multi-tenant fleets.

Routing strategies: Range shards simplify ordered scans within a range but need manual boundary maintenance. Hash and consistent-hash rings (Dynamo, Cassandra vnodes) spread load evenly and minimize remapping when nodes join. Directory-based routing stores explicit mappings—flexible for migrations but adds a metadata service to keep highly available.

Resharding: Use dual-write or change-data-capture backfill phases; verify row counts per shard before cutting reads. Azure’s documentation recommends validating distribution metrics and capacity per shard before decommissioning old nodes.

Router HA: Run multiple stateless router instances behind a load balancer; losing VTGate or mongos should not be a single point of failure.

Observability per shard: Export lag, replication health, disk usage, and top queries per shard—not only cluster aggregates. HPA-style autoscale rarely applies to stateful shards, but autoscaled routers and connection pools still need saturation metrics before incidents.

Global indexes: Secondary indexes that span shards (global indexes in DynamoDB-style stores) incur write amplification and cross-partition reads. Prefer covering indexes co-located with the shard key or accept asynchronous index maintenance.

Common failure modes

  • Hot shard: One key dominates traffic—mitigate with salt prefixes or split hot tenants to dedicated shards.
  • Scatter-gather accident: ORM queries without shard filters hit every backend—enforce linters or middleware checks.
  • Incomplete migration: Cutover before backfill finishes loses rows—automate count reconciliation gates.
  • Schema drift between shards: Migrations must roll forward identically; use idempotent DDL and verification jobs.
  • Router outage: Centralized router failure blocks all traffic—run N+1 routers and health-checked pools.
  • 2PC deadlock: Cross-shard transactions stall under partition—prefer saga or outbox patterns per DDIA guidance.
  • Uneven replica lag: One shard’s replica falls behind during cross-region replication—reads routed there return stale data unless monitored per shard.
  • Capacity surprise: Adding shards without reallocating tokens leaves new nodes idle—rebalance jobs must follow topology changes.

Decision checklist

  • Shard key present in every performance-critical query path?
  • Cross-shard operations enumerated with acceptable latency budgets?
  • Strategy chosen among hash, range, directory, or consistent hash with resharding plan?
  • Backfill, dual-write, and rollback steps tested on a staging cluster?
  • Per-shard backup, restore, and monitoring dashboards provisioned?
  • Distributed transactions minimized; sagas documented where needed?

Example use cases

  • Illustrative scenario — Threadline Messaging shards messages by conversation_id so timeline reads never cross shards, while Vitess routers fail over behind an internal load balancer.
  • Illustrative scenario — Harbor SaaS maps tenant_id to shards; a enterprise customer graduates to a dedicated shard without changing application URLs.
  • Illustrative scenario — An IoT platform consistent-hashes device_id across Cassandra nodes, adding vnodes during a planned expansion with minimal token movement.
  • Case study — Microsoft Learn — Azure sharding guidance covers partition keys, scatter-gather costs, and elastic scale-out patterns for cloud-native databases.
