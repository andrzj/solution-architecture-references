Vertical Scaling

Increasing CPU/RAM of a single instance; when vertical beats horizontal, NUMA architecture, database vertical scaling, diminishing returns, downtime requirements, and cost model.

⏱ 10 min read

What it is

Vertical scaling (scale-up) increases throughput or capacity by giving an existing host more CPU, memory, faster storage, or network bandwidth—not by adding peers. The same process image, connection string, and deployment unit run on a larger instance type (for example AWS RDS db.r6g.2xlarge to db.r6g.8xlarge) or on bare metal with additional DIMMs and sockets.

In DDIA’s vocabulary, vertical scaling keeps data and compute on one failure domain and one memory space. That simplifies transactions, joins, and in-process caches but inherits a hard ceiling: the largest SKU your provider sells, and Amdahl’s law for workloads that do not parallelize. Cloud “live resize” often applies to disks more easily than vCPU; compute changes commonly imply restart or brief failover on managed databases.

Scale-up remains the default first response in incident playbooks when replication lag and cache hit ratio are healthy but the primary still misses latency SLO—because it changes capacity without changing application code paths or shard maps.

Why it exists

Many production bottlenecks are genuinely single-node problems. A PostgreSQL write primary benefits from more RAM for shared_buffers and OS page cache; doubling memory can turn random disk reads into buffer hits overnight. Legacy binaries that cannot be sharded without a multi-year rewrite still need headroom—vertical scaling is the fastest lever during an incident.

Operators also choose scale-up to defer sharding complexity. DDIA notes that distributing data solves scale but introduces cross-shard queries and operational multiplicity. When read replicas and caching still leave the write primary CPU-saturated, a larger instance is often the next lowest-risk step—provided profiling confirms the limiting resource is CPU or RAM, not lock contention or disk IOPS caps.

Managed databases expose vertical scale as a first-class API because customers still need it: Aurora storage autoscales independently of compute, but writers still bump instance classes when CPU pegs. Kubernetes vertical pod autoscaling (VPA) and “limits requests” tuning are the container analogue—though stateless apps more often scale horizontally, statefulSets for databases still grow PVCs and CPU requests when metrics justify it.

When to use

  • Profiling shows a clear resource ceiling on one node (memory for cache working set, CPU for single-writer OLTP, IOPS for NVMe-bound analytics).
  • The component cannot horizontally shard without redesign (relational write leader, ZooKeeper quorum member, singleton license).
  • You need hours-not-weeks relief and can accept a maintenance window or managed failover during instance class change.
  • In-memory engines (column stores, embedded analytics) reward larger RAM more than more network hops.
  • Operational headcount favors fewer, larger databases over dozens of shards to patch and back up.
  • You are below the cloud maximum instance size with budget for the jump in hourly cost.

When not to use

  • You already run the largest SKU and still miss SLO—only partitioning, sharding, or architecture change remains.
  • Traffic is spiky; a always-on mega-instance wastes money versus autoscaling fleets.
  • High availability cannot tolerate failover during resize; active-active horizontal patterns fit better.
  • Adding cores increases mutex contention; profiling shows regressions on larger machines (common on heavily contended OLTP).
  • Licensing charges per core—doubling vCPU doubles license fees, erasing hardware savings.

Typical architecture

Scale-up moves the working set from disk-bound to memory-resident; on multi-socket hosts, NUMA locality determines whether extra RAM actually accelerates queries.

Pros and cons

Pros

  • No application partitioning logic; same SQL and drivers, bigger box.
  • Lower tail latency for hot in-memory structures that would fragment across a cluster.
  • Simpler operations: one backup schedule, one failover pair, one upgrade window.
  • Effective bridge while planning sharding or read-scale-out.
  • Managed services automate storage autoscaling and some class changes with Multi-AZ failover.

Cons

  • Finite ceiling at max instance size; no elastic shrink during quiet periods.
  • Resize events can still page on-call even when automated.
  • Single failure domain unless expensive standby pairs are maintained.
  • Diminishing returns past the point where serial work or lock contention dominates.
  • Cost curve is non-linear—largest SKUs have poor price-performance per core.

Implementation notes

Profile before purchase: Use pg_stat_statements, wait event analysis, and I/O metrics to distinguish CPU, memory, and disk bounds. AWS RDS Performance Insights and Azure Database advisories highlight top waits; upgrading CPU when the database is I/O-starved wastes money.

Right-size dependent pools: After RAM grows, increase connection pool sizes and PostgreSQL max_connections cautiously—more RAM invites more concurrent queries, which can increase lock traffic. JVM heaps and G1 region sizes need retuning on larger nodes.

NUMA on metal and large VMs: Pin database processes to NUMA nodes with numactl when cross-socket memory access shows in profiler. Cloud “metal” instance types expose topology; small burstable instances hide it.

Change procedure: Schedule class modifications during low traffic; verify standby lag before failback. Document rollback to the previous class if latency does not improve—sometimes contention, not capacity, was the culprit.

Combine with read path scale: Vertical scale on the primary does not add read replicas. Pair class upgrades with read replicas or caches so the write leader stops serving analytical scans. AWS Builders Library notes that scaling the wrong tier—apps when the database is the limit—only relocates the queue.

Storage and IOPS: Scale-up is not only vCPU. Provisioned IOPS, throughput mode on EBS, and local NVMe instance stores must match the larger compute or queries remain disk-bound despite ample CPU. Azure premium SSD v2 and similar SKUs expose independent IOPS sliders—use them when pg_stat_io or equivalent shows wait time dominating.

Expect a plateau: Gunther’s Universal Scalability Law applies even on one host: contention for row locks and coherency across NUMA sockets limits speedup from additional vCPUs. If profiling still shows serial segments after the last SKU jump, the next lever is architecture change—partitioning, read replicas, or shedding work—not another size class.

NUMA and licensing: On large metal or high-memory VMs, cross-socket memory access shows up in profilers—pin database processes with numactl when latency grows despite idle CPU. Per-core database licenses (Oracle, SQL Server) can make doubling vCPUs uneconomical; model cost per transaction before the next SKU jump. Resize operations on managed databases often trigger brief failover—schedule during low traffic and verify client reconnect logic.

Common failure modes

  • Wrong dimension upgraded: More CPU added while buffer cache miss ratio stays high—RAM was the need.
  • License cliff: Oracle or SQL Server per-core licensing makes scale-up economically irrational.
  • Contention plateau: More parallel workers pile onto the same row-level hot spots; p99 latency worsens.
  • Heap and GC pain: Large Java heaps without GC tuning cause long pause times on bigger boxes.
  • Failover surprise: Resize triggers Multi-AZ failover; applications without reconnect backoff see error bursts.
  • Disk not scaled: Compute class increases but EBS/IOPS limits remain—throughput caps persist.
  • Monitoring blind spot: Dashboards show green CPU while p99 grows—check memory pressure and I/O wait, not only utilization averages.
  • Overshoot cost: Jumping two SKUs at once doubles bill before validating the first step improved SLO.

Decision checklist

  • Evidence identifies CPU, RAM, I/O, or network as the binding constraint?
  • Target instance cost compared to horizontal alternatives including engineering time?
  • Maintenance window, failover path, and customer communication planned?
  • Pool sizes, thread counts, and JVM flags updated for new limits?
  • Rollback instance class documented if improvement is under threshold?
  • Standby or replica resized in lockstep to avoid skewed failover performance?

Example use cases

  • Illustrative scenario — Ledgerstone OLTP PostgreSQL hits eighty percent CPU on db.r6g.2xlarge during month-end; class change to 4xlarge restores headroom while the team designs shard-by-tenant for next year.
  • Illustrative scenario — An analytics node on ClickHouse moves to a high-memory SKU so the full thirty-day working set stays in RAM, cutting scan latency an order of magnitude.
  • Illustrative scenario — A legacy single-threaded payroll binary cannot distribute; the team chooses higher clock-speed metal instances while wrapping new APIs in horizontally scaled services at the edge.
  • Case study — AWS RDS documentation describes modifying instance class with Multi-AZ failover to minimize write unavailability.

Related patterns

  • Read Replicas — scale reads while keeping a vertically sized write primary.
  • Connection Pooling — prevents connection storms after larger max_connections.
  • Sharding Strategies — when vertical and replica strategies are exhausted.
