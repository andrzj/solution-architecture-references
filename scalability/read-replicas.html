Read Replicas

Offloading read traffic to replicas; replication lag implications, read-your-writes consistency, replica sets, Aurora read replicas, routing reads to replicas, and replica promotion.

⏱ 10 min read

What it is

A read replica is a read-only database instance that applies the primary's replication stream (PostgreSQL WAL, MySQL binlog, SQL Server transaction log) and serves SELECT traffic while the primary handles writes. Routing separates two scaling planes: write throughput stays bounded by the primary, while read throughput grows with the number of healthy replicas behind a connection router or proxy.

Managed engines expose replicas as first-class resources—Amazon RDS and Aurora, Google Cloud SQL, Azure Database for PostgreSQL—each with different replica limits and lag characteristics. Aurora's shared storage layer keeps replica lag typically under tens of milliseconds because replicas read from the same distributed volume instead of replaying a byte stream. Classic streaming replicas still depend on apply speed and network bandwidth between regions.

Why it exists

In DDIA’s replication chapter, the leader handles every write while followers apply a log and serve reads—a classic way to scale read-heavy OLTP without fragmenting data across shards. Many production databases see 80–95% SELECT traffic; the primary still serializes writes but may spend most CPU on index scans and sort operations that replicas can absorb. Provisioning additional read-only nodes multiplies SELECT capacity at the cost of extra instances and replication bandwidth, which is usually cheaper than premature sharding or a datastore rewrite.

Followers also shorten recovery time. A cross-AZ or cross-region replica that has been catching up the WAL or binlog can be promoted when the writer fails, giving you a warm standby without cold backups alone. That dual role—horizontal read scale plus failure target—is why managed PostgreSQL, MySQL, and Aurora expose replicas as first-class resources alongside Redis caching for the hottest keys.

When to use

  • Measured read/write ratio is dominated by reads and the primary CPU profile shows query execution, not write fsync, as the limit.
  • BI exports, admin search, or batch reports contend with checkout traffic on the same writer connection pool.
  • You need more read QPS before accepting cross-shard queries, dual writes, and DDIA’s distributed-transaction tax.
  • Disaster recovery runbooks require a promotable standby in another AZ or region with replication already flowing.
  • API contracts document eventual consistency and callers tolerate seconds (or bounded tens of seconds) of replication lag.
  • Long scans or aggregate queries should run against a replica connection string so OLTP locks stay on the primary.

When not to use

  • Writes saturate disk, WAL, or row locks; more followers do not increase commit throughput on the leader.
  • Product flows require read-your-writes on every GET after POST and you cannot pin sessions or compare LSN/GTID tokens.
  • Inventory, ledger, or authorization reads must be linearizable; follower lag would cause visible user-facing errors.
  • Profiling shows primary pressure from write amplification or migration DDL, not SELECT volume—replicas add cost without relief.

Typical architecture

Writes always land on the primary; a router load-balances reads across replicas and can pin sessions to the primary after writes when read-your-writes consistency matters.

Pros and cons

Pros

  • Read QPS grows roughly with follower count for workloads Kleppmann classifies as read-skewed, without resharding keys.
  • Managed providers provision replicas via API or console; replication plumbing is largely operational toil you do not reimplement.
  • Heavy reporting connects to a dedicated follower so ad hoc aggregates do not steal buffer pool from writers.
  • Cross-AZ followers are rehearsed promotion targets, aligning with DDIA’s goal of availability through redundant copies.
  • Applications already separate read and write DSNs; pairing followers with Redis for hot rows is a small incremental step.

Cons

  • The leader still serializes every write; followers never remove write-path bottlenecks or multi-master conflicts.
  • Asynchronous replication implies lag; readers may see pre-update state unless you route carefully or cache writes in Redis.
  • Misrouted INSERT statements to a read-only endpoint fail loudly, but subtle read-after-write bugs are harder to detect.
  • Each follower stores a full copy—storage and license cost multiplies with data set size.
  • Failover promotion pauses writes and may lose the last seconds of async commits unless you adopt synchronous or quorum replication.

Implementation notes

Measure lag before routing. Export ReplicaLag (RDS/Aurora), pg_stat_replication replay lag, or ProxySQL ConnUsed vs lag gauges into the same dashboard as API latency. Alert when lag exceeds the staleness budget for each query class—reporting may tolerate 60s; account balances may tolerate none.

Read-your-writes routing: Three practical options: (1) sticky primary for N seconds after any write in the session; (2) return the PostgreSQL LSN or MySQL GTID with the write response and only read from a replica whose position is ≥ that token; (3) offload hot keys to Redis on the write path so the next read never touches a lagging replica. Pair replicas with a short-TTL cache only when invalidation on write is explicit—replicas are not a substitute for cache coherence.

Connection pools: Size write and read pools independently. Replicas often need more connections because they absorb fan-out traffic; the primary pool should stay small enough that long transactions cannot starve writers. Use separate DSNs or proxy rules so migrations and DDL never target replicas.

For eventually consistent reads (leaderboards, recommendations), document the maximum acceptable lag in the API contract and route those endpoints only to replicas whose lag gauge is within bounds.

Tail latency: Dean and Barroso’s “Tail at Scale” argument applies to replica pools—if routing ignores lag, one slow follower can dominate p99 even when median replication health looks fine. Prefer lag-aware load balancing or drop degraded replicas from rotation before clients observe nine-second reads on an otherwise healthy cluster.

Measuring lag: PostgreSQL exposes replay lag in pg_stat_replication; MySQL uses seconds behind primary / GTID gap; Aurora publishes ReplicaLag. Define SLAs per query class and exclude followers that breach them from read pools.

Read-your-writes: Sticky sessions to the primary for a few seconds after write; or return LSN/GTID with the write response and block reads on replicas until replay_lag catches up to that token; or read-through Redis on the hot entity. Pick one contract and test mobile clients that parallelize POST+GET.

Promotion risk: Async failover can promote a follower that has not applied the latest WAL—document RPO and rehearse promotion with chaos tests. Synchronous quorum replicas narrow the gap at the cost of write latency; weigh that against financial or inventory reads that cannot tolerate torn histories.

Common failure modes

  • Lag avalanche from long transactions: An open transaction on the leader holds back WAL recycling; every follower falls behind together. Enforce statement_timeout and move analytics to dedicated followers.
  • Post-create 404 on follower: Mobile clients POST then GET from a replica before the binlog event applies. Pin the session to the leader briefly or return a read token with LSN/GTID.
  • Promotion gap loss: Async failover promotes a follower seconds behind; committed rows vanish. Document RPO and use synchronous replicas or quorum rules where money moves.
  • Uniform pool sizing: Identical PgBouncer limits starve writers while read pools idle. Size write and read pools from distinct traffic measurements.
  • DDL on followers by mistake: Migration tools that round-robin hosts apply indexes on replicas and break replication. Restrict schema changes to the leader endpoint only.

Decision checklist

  • Production metrics confirm SELECT load—not write I/O—drives primary scaling pressure.
  • ORM and job configs use separate writer and reader URLs; integration tests assert writes never target read_only roles.
  • Lag dashboards (pg_stat_replication, RDS ReplicaLag) page before user-visible staleness budgets are breached.
  • Write-then-read UX paths define sticky primary, LSN tokens, or Redis read-through for hot entities.
  • Failover and promotion drills occur on a schedule with recorded RTO/RPO outcomes.
  • Follower count matches measured read QPS without oversharding replication bandwidth on the leader.

Example use cases

  • Illustrative scenario — analytics slice: An operations dashboard runs heavy aggregates. Queries route to a dedicated replica so OLTP writes on the primary keep sub-100ms latency while dashboards run multi-second reports.
  • Illustrative scenario — publishing feed: A content API serves homepage feeds from replicas; publish and comment writes stay on the primary with a 30-second read-pin window after each author action.
  • Case study — Amazon Aurora: Aurora replicas share the storage volume with the writer, giving many teams replica lag low enough to serve nearly fresh reads without a separate cache tier for catalog data.
  • Illustrative scenario — nightly export: A compliance export scans millions of rows against a cross-region replica so long table scans never contend with checkout writes in the primary region.

Related patterns

  • Caching Strategies — Redis in front of followers absorbs repeated keys so replicas run fewer identical SELECTs.
  • Cache Invalidation — when Redis mirrors database rows, invalidate on write so followers and cache do not disagree.
  • Vertical Scaling — scale the leader up when writes, not reads, cap throughput.
  • Eventual Consistency — formal model for follower reads; document lag in APIs consumers trust.
