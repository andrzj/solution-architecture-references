Cache Invalidation

TTL-based, event-based, write-through invalidation; cache stampede, probabilistic early expiration, tag-based invalidation, distributed cache coherence, and cache poisoning risks.

⏱ 11 min read

What it is

Cache invalidation removes or refreshes entries when authoritative data changes so clients do not read stale values from Redis, in-process memory, or CDN edge caches. The practice balances performance (long TTLs, high hit rates) against correctness (fresh prices, permissions, and inventory). Most production systems combine passive expiry with active delete-on-write because neither alone covers every consistency requirement.

TTL expiry bounds staleness without coupling writes to the cache. Event-driven invalidation deletes keys or publishes purge messages after a successful commit. Write-through updates cache and database together. At scale, tag-based invalidation (invalidate all keys for product:42) and surrogate keys on CDNs (Fastly, Cloudflare cache tags) avoid enumerating millions of URLs. Probabilistic early refresh reduces stampedes when a popular key expires.

Why it exists

Kleppmann’s Designing Data-Intensive Applications lists cache invalidation among the hardest problems in distributed systems for good reason: every cache entry is a copy that can diverge from the authoritative store. Without explicit invalidation or refresh, that copy survives until TTL expiry or process restart, so a committed price or permission change in PostgreSQL can remain invisible to shoppers reading from Redis or from a Cloudflare PoP. Invalidation is the mechanism that lets you keep aggressive TTLs and high hit rates while bounding how long wrong answers can survive.

Shared caches amplify the coordination problem. A write on pod A must evict or update keys that pods B and C might still serve from L1 memory, from a regional Redis cluster, and from CDN edge storage in another continent. DDIA’s replication discussion applies directly: you are managing multiple replicas of the same data with weaker consistency than the primary. Purge APIs, Redis pub/sub, and tag-based invalidation are how teams propagate “this version is dead” across those replicas without shutting down the cache entirely.

When to use

  • TTL alone would keep business-critical fields stale longer than your SLA allows after writes (pricing, entitlements, inventory reservations).
  • Users must observe their own writes or admin actions within seconds, not after a passive five-minute Redis TTL.
  • Cloudflare or Fastly edge caches hold HTML or API fragments that change on publish, promotion, or legal takedown and cannot wait for long max-age values.
  • One logical entity maps to many cache keys (detail page, listing card, RSS fragment) and you need surrogate keys or Redis tag sets to drop them atomically.
  • You run stale-while-revalidate at the CDN or application layer and need a deliberate invalidation path when authoritative data changes, not only background refresh on miss.

When not to use

  • Content is immutable or versioned by URL (hashed static assets); new versions get new keys and old TTLs can expire naturally without purge traffic.
  • Keys are cold or per-user with near-zero sharing, so the Redis round trips and purge quota cost more than occasional staleness.
  • Only a process-local cache is in play and you accept best-effort coherence via short TTLs rather than cross-node invalidation fan-out.
  • The product explicitly documents eventual consistency (leaderboards, aggregated metrics) and stakeholders accept the documented lag window.

Typical architecture

After a committed write, the application deletes Redis keys, optionally fans out CDN purge API calls, and lets the next read repopulate from origin.

Pros and cons

Pros

  • Delete-on-write after commit narrows the stale window to replication plus one miss reload, which is adequate for many commerce and auth flows.
  • TTL remains a cheap safety net when invalidation messages are lost or purges fail, matching DDIA’s advice to layer defenses rather than trust a single mechanism.
  • Fastly surrogate keys and Cloudflare cache tags collapse millions of URL-specific entries into one purge call during catalog or CMS bulk updates.
  • Probabilistic early expiration spreads refresh load before hard expiry, reducing synchronized stampedes on hot Redis keys.
  • Stale-while-revalidate at the edge keeps p99 latency flat while origin or Redis repopulates fresh payloads in the background.

Cons

  • Every write path must know which keys, tags, and CDN URLs to touch—tight coupling that grows with denormalized cache shapes.
  • Classic race: a slow reader repopulates stale JSON after your DEL but before the database commit is visible everywhere.
  • Category-wide tag purges can empty large fractions of Redis or edge cache at once, recreating the database load you were trying to avoid.
  • Tag indexes and surrogate-key headers must stay consistent with application naming; drift yields either orphaned keys or accidental mass deletion.
  • Global CDN purge propagation is eventually consistent and rate-limited; users may still see old content for seconds even when origin and Redis are correct.

Implementation notes

Delete, do not overwrite: After COMMIT, call DEL (or UNLINK for large values) on affected Redis keys. Never push uncommitted rows into cache—rolled-back transactions poison every replica that reads the key. The next cache-aside miss reloads from the database.

Redis coordination: Use keyspace notifications or pub/sub channels sparingly for cross-instance L1 invalidation; at high volume prefer explicit PUBLISH cache:invalidate product:42 from the write service. Tag indexes can live in Redis sets (SADD tag:product:42 key1 key2) and delete in a Lua script for atomicity. Keep TTL as a safety net even when invalidating on write.

CDN purges: Cloudflare supports purge by URL, prefix, hostname, and cache tags; Fastly uses surrogate keys with soft and hard purge. Purge APIs are rate-limited—batch by tag during bulk catalog updates instead of one request per object. Expect global propagation in seconds to tens of seconds; monitor API responses and retry failures.

Races: A slow reader can repopulate stale data after your delete. Mitigate with version fields in cached payloads, short TTL caps, or CDC-driven invalidation ordered on the replication stream so deletes never precede visible writes.

Common failure modes

  • Republish-after-delete race: A cache-aside miss loads pre-commit or lagging-replica state and writes it back into Redis after your invalidation. Cap TTL, cache versions, or invalidate from CDC ordered on the replication stream.
  • Thundering herd after bulk purge: A merchandising job purges an entire tag; every edge and app instance misses together. Stagger purges, pre-warm top keys, or use single-flight refresh in Redis.
  • Poisoned cache entries: Buggy serializers or unvalidated upstream JSON gets cached and served globally until expiry. Validate at the write-to-cache boundary; treat cache as untrusted input on read.
  • Broken tag metadata: A key is cached without the surrogate-key header or Redis tag set membership, so partial updates leave sibling fragments stale. Enforce tagging in code review and integration tests.
  • Silent CDN purge failure: Cloudflare or Fastly returns throttling or 5xx on purge; only one region clears. Retry with backoff, alert on non-2xx responses, and keep short edge TTL on high-risk content.

Decision checklist

  • Each data class has a written maximum staleness budget that drives TTL length and whether post-commit invalidation is mandatory.
  • Write handlers perform delete (not blind overwrite) on Redis keys and enqueue CDN purges only after successful transaction commit.
  • Read-your-writes and invalidation races are covered by version fields, primary reads, or replication-position checks where UX requires it.
  • Bulk invalidation runbooks include rate limits, batch tag purges, and warm-up steps so origin and Redis are not surprise-overloaded.
  • Purge success, latency, and quota usage are on dashboards with paging when error rates spike during releases.
  • Security-sensitive keys (sessions, roles, tokens) have immediate invalidation hooks on password change, logout-all, and revocation events.

Example use cases

  • Illustrative scenario — CMS publish: On publish, the API deletes article:{id} in Redis and calls Cloudflare purge-by-URL; readers see updates after edge propagation instead of waiting for hour-long CDN TTL.
  • Illustrative scenario — permission revoke: Admin revocation triggers immediate DEL permissions:{userId} so the next request cannot serve cached allow rules.
  • Case study — Fastly surrogate keys: Product pages carry Surrogate-Key: product-42 category-electronics; one soft purge on product-42 invalidates detail and listing fragments without URL enumeration.
  • Illustrative scenario — price event: A pricing consumer invalidates product:{id} keys when Kafka price events arrive, beating the passive five-minute TTL during flash updates.

Related patterns

  • Caching Strategies — choose cache-aside, write-through, or write-behind first; invalidation policy follows from how writes populate the fast tier.
  • CDN Architecture — edge caches add geographic fan-out; surrogate keys and purge APIs are invalidation at planetary scale.
  • Event Notification — Kafka or Redis pub/sub can fan invalidation to many consumers without synchronously coupling every writer to every cache node.
  • Read Replicas — replica lag creates another stale-read surface; pair routing rules with cache invalidation on the write path.
