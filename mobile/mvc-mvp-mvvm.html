Mobile Architecture

MVC vs MVP vs MVVM

How MVC, MVP, and MVVM split presentation responsibilities on mobile—and when each pattern fits native, React Native, and Flutter codebases.

⏱ 11 min read

What it is

MVC, MVP, and MVVM are three presentation-layer patterns that assign different roles to the user interface, the code that reacts to input, and the data the screen displays. In Model-View-Controller (MVC), a controller orchestrates updates between model and view; on classic UIKit and early Android, the “controller” often absorbed so much logic that the view and controller became tightly coupled. In Model-View-Presenter (MVP), the view stays passive and a presenter formats data and handles events on the view’s behalf, usually behind a small view interface. In Model-View-ViewModel (MVVM), the view model exposes observable state; the view subscribes and renders, which matches Android Jetpack ViewModel plus flows and SwiftUI’s model-data APIs.

None of these patterns replaces the whole app architecture: the model side still typically uses repositories, DTOs, and domain types. Teams often extend MVVM with unidirectional data flow (sometimes called MVI) when they need one immutable screen state and explicit events.

Why it exists

Mobile UIs churn with lifecycle events, animations, and accessibility while business rules should remain stable. When view controllers or activities own networking and validation, changes become risky and tests require devices. MVP and MVVM were adopted to pull that logic into testable classes and to align with platform guidance—Google’s architecture components and Apple’s SwiftUI both assume observable presentation state rather than imperative view patching.

A shared vocabulary across iOS and Android (and cross-platform stacks) also speeds reviews and hiring; the same words describe boundaries whether the UI is Compose, SwiftUI, a React Native screen component, or a Flutter widget tree.

When to use

  • MVVM for new native screens using Jetpack Compose, XML with state collection, or SwiftUI; also for Flutter and React Native when you adopt a single observable store per screen.
  • MVP when extending legacy UIKit or Android view-based screens that already use presenter interfaces and passive views.
  • MVC only for very small tools or throwaway prototypes where extra types do not pay back.
  • Incremental migration from MVC to MVVM screen by screen when product pressure allows interface tests and feature freeze on touched modules.
  • Shared Kotlin or Rust core with platform view models implementing the same contracts on each OS.

When not to use

  • Do not force MVP’s view interfaces into declarative UI where the framework expects observable state (Compose, SwiftUI).
  • Avoid bolting MVVM onto a screen with no asynchronous state—plain MVC may be clearer.
  • Do not pick a pattern because of fashion; match team skill and existing modules.
  • Skip heavy presenter hierarchies in greenfield cross-platform apps when Flutter or React Native docs already recommend a simpler state container.

Pros and cons

Pros

  • MVVM aligns with Android and Apple first-party guidance and declarative UI, minimizing custom glue code.
  • MVP makes view behavior explicit through interfaces, which suits legacy imperative UIs and contract tests.
  • All three patterns clarify where to put formatting, validation, and error mapping before data reaches widgets.
  • Observable MVVM state simplifies accessibility and preview-driven development on modern toolkits.

Cons

  • MVC on mobile often collapses into fat controllers unless discipline is enforced.
  • MVP introduces view interfaces and forwarding calls, which feels verbose on small screens.
  • MVVM with undisciplined two-way binding can create update loops; prefer one-way state flow.
  • Choosing the wrong pattern for the UI toolkit increases boilerplate without improving tests.

Implementation notes

MVP on legacy UI: Define a narrow view interface (show loading, show items, show error). The presenter subscribes to repositories, maps results, and calls view methods. The view forwards taps to the presenter. Keep Android Activities and iOS view controllers as thin as possible.

MVVM on native declarative UI: On Android, use a Jetpack ViewModel exposing StateFlow; collect in Compose with lifecycle awareness. On iOS, use @Observable or ObservableObject types that views read; perform async work in methods that update published properties on the main actor when needed.

Cross-platform: Flutter’s recommended layering uses view models or controllers above repositories; React Native screens combine hooks with context or external stores. In both cases, avoid importing native UI types into shared logic packages.

Security and data: Presenters and view models should call repositories, not Keychain or Keystore APIs directly, so MASVS storage controls stay in the data layer. See Mobile Architecture Patterns for MVI and full layering.

Testability is the practical differentiator: MVP’s view interface and MVVM’s observable state let you assert presentation logic with mocked repositories, while classic MVC often leaves “Massive View Controller” or Activity code that only runs on device. SwiftUI and Compose reward a single owner of screen state—usually a view model or observable model—while views remain pure functions of that state; two-way data binding without discipline reintroduces update loops when every property write triggers another render pass.

Prefer one-way flow: bind UI to read-only state snapshots and route user actions through intents or methods that update state on a known executor (@MainActor, main-thread coroutine scope). When migrating legacy UIKit or XML screens, keep presenters thin and avoid smuggling layout knowledge into presentation types; greenfield modules can adopt MVVM directly per platform guidance. Document which pattern each module uses in the README so reviewers spot accidental MVC regression during feature work.

Common failure modes

  • Leaky view model: Storing Context, UIView, or navigation controllers in presentation classes breaks lifecycle rules and unit tests.
  • Presenter doing layout: MVP presenters that know about view hierarchy IDs become as brittle as massive view controllers.
  • Binding loops: Two-way bindings that write back on every render cause oscillation; hold one authoritative state copy.
  • Model in the view: Passing raw DTOs into SwiftUI or Compose without a view-specific model leaks API shapes into the UI.
  • Pattern mismatch during migration: Half the module on MVP and half on MVVM without boundaries confuses ownership of navigation and analytics.

Decision checklist

  • Is the view passive or purely declarative relative to the chosen pattern?
  • Can presentation logic run in unit tests with mocked repositories and no device?
  • Does the pattern match the UI toolkit’s recommended data flow (Jetpack, SwiftUI, Flutter, React Native)?
  • Are navigation, analytics, and permissions handled as effects rather than buried in model updates?
  • Is there a written rule for which pattern new screens use during any MVC-to-MVVM migration?

Example use cases

  • Illustrative scenario — legacy settings screen: An Android XML settings page keeps MVP: the presenter loads preferences from DataStore through a repository and toggles switches via a view interface while fragments remain thin wrappers around the view interface.
  • Illustrative scenario — greenfield onboarding: SwiftUI onboarding uses MVVM with an observable model per step; validation and API calls sit in the model type, and previews inject mock repositories.
  • Case study — Apple’s SwiftUI documentation models data with Observable types and views that read state, illustrating MVVM-style separation without UIKit view controllers.
