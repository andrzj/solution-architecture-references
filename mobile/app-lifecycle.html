Mobile Architecture

App Lifecycle Management

How to design apps that survive foreground/background transitions, OS suspension and termination, memory pressure, and platform-specific background execution limits without losing user work.

⏱ 11 min read

What it is

App lifecycle management is how a mobile application responds to operating-system events: moving between foreground and background, being suspended or killed under memory pressure, and waking for background tasks, push payloads, or deep links. Architecture here covers what state to persist, when to flush data, and which platform APIs are allowed for work that continues after the user leaves the screen.

iOS (UIKit/SwiftUI scenePhase, BGTaskScheduler) and Android (Activity/Fragment lifecycle, ProcessLifecycleOwner, WorkManager, foreground services) expose different callbacks and stricter background limits. A sound design maps domain state to durable storage and keeps UI state reconstructable after process death—not merely pausable in RAM.

Why it exists

Mobile users context-switch constantly: messages, camera, phone calls, and multitasking mean your app may leave the foreground dozens of times per session. If drafts, carts, or in-progress workflows live only in memory, a single OS kill restores an empty screen and erodes trust.

Operating systems aggressively reclaim resources. Background apps face suspension, CPU throttling, and termination without warning. Battery and privacy policies further cap how long code may run when the user is not looking at the app. Lifecycle-aware architecture aligns product behaviour with these constraints instead of fighting them.

When to use

  • Multi-step flows (checkout, onboarding, forms) where partial progress must survive backgrounding and process death.
  • Media, navigation, or fitness apps that need foreground services or audio session continuity on Android and iOS respectively.
  • Apps with sync engines that must enqueue or flush outbox rows when entering background.
  • Push-driven or deep-link entry where the app cold-starts into a specific screen with restored session context.
  • Any app targeting older or low-memory devices where the OS kills background processes frequently.

When not to use

  • Always-on background polling: Periodic timers in background violate platform guidance and drain battery; use push, BGAppRefreshTask, or WorkManager with constraints instead.
  • Duplicating OS state in custom globals: Reimplementing lifecycle in singletons bypasses configuration-change and process-death handling already provided by ViewModel, SavedStateHandle, and SwiftUI state restoration.
  • Foreground service for non-user-visible work: Misclassified foreground services risk Play policy violations and user uninstalls.
  • Assuming onPause means "app is gone forever": Fast app switching causes rapid foreground/background churn; idempotent save logic must tolerate duplicate calls.

Typical architecture

The UI observes lifecycle-aware presenters; on background transitions, critical state is written to local storage while deferrable work is handed to OS-scheduled workers.

Pros and cons

Pros

  • Users resume where they left off after interruptions, improving completion rates for long flows.
  • Cooperating with OS power rules reduces battery complaints and store-policy risk.
  • Explicit persistence boundaries simplify testing and crash recovery.
  • Background workers consolidate deferrable sync and upload work with retry semantics.

Cons

  • Dual-platform lifecycle APIs increase shared-code complexity for Kotlin Multiplatform or cross-platform frameworks.
  • Over-eager persistence on every onStop can waste I/O and drain battery if not debounced.
  • Foreground services and location modes require careful UX disclosure and maintenance across OS versions.
  • Rapid switchers expose race conditions between in-flight network calls and saved snapshots.

Implementation notes

Persist early, restore cheaply: On Android, combine SavedStateHandle for small navigation args with Room or DataStore for durable drafts. On iOS, use SwiftData/Core Data for drafts and @SceneStorage only for lightweight, non-sensitive UI restoration. Target completing critical writes within a few hundred milliseconds of the background transition—long synchronous disk work on the main thread causes jank and ANRs on resume.

Background execution: Use WorkManager with network and battery constraints for upload retries on Android. On iOS, register BGAppRefreshTask for short refresh windows and BGProcessingTask for longer work; silent push can nudge sync but is throttled and not guaranteed. Never rely on a fixed timer firing in background on either platform.

Process death testing: Enable "Don't keep activities" in Android developer options; use Xcode's "Simulate memory warning" and terminate the app from the debugger. Verify cold start restores the same screen and data users expect—not a generic home reset.

Configuration changes: Retain ViewModels across rotation; release camera, location, and sensor listeners in onStop / scenePhase inactive unless a foreground service or active navigation session requires them.

Map platform states explicitly: on iOS, scenePhase and multi-window scenes decide when UI is visible versus suspended; on Android, activity lifecycle callbacks plus process death mean anything not in onSaveInstanceState, ViewModel-saved state, or persistent storage vanishes when the system reclaims RAM. After a kill, cold start must rebuild navigation from durable records—not from static globals that died with the process.

Background execution is quota-driven. Android Doze and App Standby defer network and alarm work until maintenance windows unless you use exempted foreground-service types or high-priority FCM channels appropriately; WorkManager is the default for deferrable sync with constraints. iOS BGTaskScheduler hands limited wall-clock budget—register identifiers in Info.plist, avoid assuming silent push will wake you, and coalesce upload work with offline-first outbox drains when the user returns to foreground-active state. Instrumented tests should rotate the device, background mid-form, and kill the process to confirm drafts and navigation stacks match product expectations.

Common failure modes

  • Checkout or form loss: In-memory cart or wizard state with no flush on onStop / background phase—users return to an empty flow after a phone call.
  • Resume ANR: Reloading large datasets or running migrations on the main thread in onResume blocks input for seconds.
  • Stale token after long background: Session expired while suspended; resume attempts API calls without refresh and shows opaque errors.
  • Duplicate sync: Both lifecycle callback and push handler trigger the same flush without idempotency, causing double uploads.
  • Leaked location: Fused location client or CLLocationManager left running after the user backgrounds a non-navigation screen.

Decision checklist

  • Is every multi-step flow restorable after process death without server round-trips for draft data?
  • Are background tasks scheduled only through WorkManager, BGTaskScheduler, or approved foreground-service types?
  • Does the app release expensive resources (camera, GPS, audio) when not in foreground-active state?
  • Are lifecycle edge cases covered in instrumented tests (rotation, background, kill, deep link)?
  • Is session refresh handled on resume when the app was backgrounded longer than token TTL?
  • Do sync flushes on background use the same idempotent outbox semantics as foreground sync?

Example use cases

  • Illustrative scenario — retail checkout: Cart and address steps persist to local DB on background; payment step revalidates inventory on resume; abandoned carts trigger a push deep link that cold-starts into the cart screen with restored state.
  • Illustrative scenario — active navigation: Turn-by-turn uses a foreground service (Android) or active navigation mode (iOS) only while guidance runs; waypoints sync via WorkManager when the trip ends.
  • Case study — music streaming: Major streaming apps use platform audio session APIs and background modes so playback continues under lock screen while UI state is rebuilt from local queue metadata on relaunch.
