Mobile Architecture

App Lifecycle Management

Foreground/background state management, background tasks, and memory pressure handling.

⏱ 10 min read

What it is

Background execution limits differ: iOS is strict (BGTaskScheduler, push-driven refresh); Android offers WorkManager, foreground services, and doze mode constraints.

Why it exists

Users switch apps constantly; mishandled background transitions lose form input and break payments.

OS kills memory-heavy background apps; architecture must restore gracefully.

When to use

  • Apps with long forms, media playback, or location tracking.
  • Sync engines that must flush queues on background.
  • Push notification handlers that update UI state.

When not to use

  • Relying on infinite background execution — will be throttled.

Typical architecture

Pros and cons

Pros

  • Better UX on resume.
  • Battery and memory compliance with OS rules.

Cons

  • Platform differences complicate shared Kotlin/Swift code.
  • Easy to mishandle race on fast app switching.

Implementation notes

Persist critical UI state to disk on onStop/scenePhase background. Defer heavy work to WorkManager/BGTask.

Test lifecycle with instrumented tests simulating rotation and background.

Common failure modes

  • Lost checkout state: No save on background — use local DB or saved state handle.
  • Background ANR: Long work on main thread during resume.

Decision checklist

  • Is user data saved within 200ms of background transition?
  • Are background tasks using approved APIs per platform?

Example use cases

  • Ride app: Trip state in Room/SwiftData; location via foreground service only during active ride.
