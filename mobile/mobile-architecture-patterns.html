Mobile Architecture

Mobile Architecture Patterns

Presentation-layer patterns and recommended layering for mobile apps—how MVC, MVP, MVVM, and MVI separate UI from logic, align with Android and Apple guidance, and pair with declarative toolkits and cross-platform frameworks.

⏱ 12 min read

What it is

Mobile architecture patterns are repeatable ways to structure a client app so that user interface, application logic, and data access stay separated and testable. On phones and tablets, that usually means a presentation layer (screens and navigation), a domain or use-case layer for business rules, and a data layer that hides network APIs and local storage behind repositories. Within presentation, teams choose among MVC (Model-View-Controller), MVP (Model-View-Presenter), MVVM (Model-View-ViewModel), and MVI (Model-View-Intent) depending on how tightly the UI couples to platform widgets and how predictable screen state must be.

Google’s Android architecture guidance and Apple’s SwiftUI data-flow documentation both assume observable state driving the UI, lifecycle-aware holders of that state, and repositories as the single entry point for reads and writes. React Native and Flutter apply the same ideas with different primitives (hooks and context, or widgets and state-management packages), but the goal is unchanged: keep platform UI thin and push decisions into code you can unit test without an emulator or simulator.

Why it exists

Mobile platforms tie every screen to strict lifecycle callbacks, configuration changes, and background restrictions. When Activities, Fragments, or view controllers accumulate networking, formatting, and validation, teams get “massive” UI classes that are hard to change and expensive to verify. Presentation patterns move that logic into presenters or view models that survive rotation on Android, outlive individual SwiftUI views on iOS, and accept fake repositories in tests.

Asynchronous data—REST calls, local databases, sync queues, and sensor streams—also needs a consistent home. Repository and use-case boundaries keep ViewModels from knowing whether data came from cache or network, which is the usual integration point for offline-first and security controls described in OWASP MASVS storage and communication chapters.

When to use

  • MVVM when you adopt Android Jetpack (ViewModel, StateFlow / LiveData) or SwiftUI observable models; this is the default for new native screens.
  • MVI (unidirectional data flow) when a screen has many interacting flags—loading, errors, pagination, permissions—and you want one immutable state object and an explicit event log for debugging.
  • MVP when maintaining legacy XML layouts or UIKit storyboards where passive views and presenter interfaces are already established.
  • Layered clean architecture (presentation → domain → data) when multiple features share rules, you need clear OWASP MASTG test boundaries, or Kotlin Multiplatform / shared modules expose one domain core to Android and iOS.
  • MVC in the small only for prototypes or trivial tools where a single screen does not justify extra types.

When not to use

  • Do not stack full clean architecture on every settings toggle; match pattern depth to screen complexity.
  • Avoid mixing MVP, MVVM, and MVI on adjacent screens without a documented migration path—onboarding and code review become inconsistent.
  • Do not let “view models” become new god objects; extract use cases or interactors when one class owns unrelated flows.
  • Skip custom presentation frameworks when the platform or cross-platform toolkit already documents a recommended approach (Android Architecture Components, SwiftUI, Flutter BLoC or Riverpod, React Native recommended patterns).

Typical architecture

Presentation patterns differ in who drives the view and where observable state lives; data still flows through repositories regardless of whether the screen uses MVP or MVI.

Pros and cons

Pros

  • MVVM and MVI keep presentation logic off the main UI class, so JVM and native unit tests can run without devices.
  • A single observable state (or MVI state object) reduces contradictory loading flags and stale partial UI updates.
  • Android ViewModel scopes survive configuration changes, avoiding duplicated fetches after rotation.
  • Repositories isolate APIs, databases, and secure storage—aligning with MASVS guidance to centralize sensitive data access.
  • Explicit MVI intents create an audit trail of user actions and state transitions for debugging and analytics pipelines.

Cons

  • More types and indirection than ad hoc MVC; simple screens pay a readability tax.
  • Extra domain and use-case layers help large teams but slow small products if every feature gets the same ceremony.
  • Large sealed-class intent hierarchies need discipline; otherwise MVI becomes harder to navigate than loose MVVM.
  • Legacy two-way XML data binding on Android can hide errors; prefer explicit state collection in Compose or clear binding diagnostics.

Implementation notes

Android (Jetpack): Follow the official app architecture guide: UI layer (Compose or Views) collects from a ViewModel; the ViewModel calls repositories and exposes StateFlow or LiveData. Launch work in viewModelScope, never hold an Activity or Fragment reference, and map domain errors to user-visible state. Use the data-layer offline-first pattern when local Room is the source of truth.

iOS (SwiftUI): Model types conforming to Observable or legacy ObservableObject own screen state; views remain declarative functions of that state. Keep URLSession and Core Data/SwiftData behind repository protocols so XCTest can inject mocks. Use @MainActor where UI mutations belong on the main thread.

MVI and effects: Route user events into a reducer that returns the next immutable state; emit one-off navigation, dialogs, or haptics through a separate effects channel consumed by the UI layer once. This matches unidirectional flow described for Compose and SwiftUI and keeps side effects out of pure state reducers.

React Native and Flutter: React Native teams often colocate UI state in hooks and lift shared flow into context or lightweight stores; Flutter commonly uses ChangeNotifier, Riverpod, or BLoC with the same repository boundary. In both ecosystems, treat platform modules (Keychain, Keystore, biometrics) as data-layer adapters per MASTG storage controls.

Unidirectional data flow—whether MVI reducers, The Composable Architecture on Apple platforms, or Redux-like stores—keeps navigation and side effects out of pure state transitions and pairs well with SwiftUI and Jetpack Compose. Clean architecture rings (entities, use cases, interface adapters) stay valuable at scale: modularize by feature or layer to shrink incremental build times, and wire dependencies through Hilt on Android or Swinject-style containers on iOS so tests swap repositories without reflection.

Cross-platform choices trade velocity for integration depth: React Native’s new architecture and JSI reduce bridge overhead for native modules; Flutter owns rendering and suits greenfield UI; Kotlin Multiplatform shares domain logic while keeping platform UI native. For when to pick MVP versus MVVM and how binding affects tests, see MVC, MVP and MVVM—this article stays at module boundaries and data-flow shape. Feature modules should expose narrow public APIs so Gradle or SPM graphs stay shallow and incremental builds stay under team CI budgets.

Common failure modes

  • Massive ViewModel: Moving code from a view controller without splitting use cases recreates the same maintainability problem one layer up.
  • Context or view references in view models: Retaining UI objects in view models causes leaks and breaks test isolation; use application-scoped dependencies only when required.
  • Split sources of truth: Multiple unrelated LiveData or published fields on one screen make it easy to show inconsistent loading and content states.
  • Repositories that always hit the network: Bypassing cache ignores offline-first and burns battery on poor radio conditions.
  • Navigation inside reducers: Coupling navigation to state transitions complicates tests and preview; emit effects instead.

Decision checklist

  • Does the presentation layer avoid direct references to Activities, Fragments, UIViewControllers, or equivalent RN/Flutter view handles?
  • Can core presentation logic run in unit tests with mocked repositories?
  • Is screen state observable from one primary structure (or a clearly documented MVI state type)?
  • Do repositories hide local versus remote sources and encryption details from view models?
  • Are navigation, permissions prompts, and analytics separated from pure state updates?
  • Does the structure map to Android Architecture Components, SwiftUI guidance, or your chosen Flutter/RN state library without one-off shortcuts?

Example use cases

  • Illustrative scenario — catalog checkout flow: A product list screen uses MVI: intents for search, filter, and add-to-cart feed a single list state; Jetpack Compose renders from that state while a repository mediates Room cache and checkout APIs.
  • Illustrative scenario — regulated sign-in: MVVM plus a domain use case performs authentication; biometric and token storage sit in a data-layer adapter backed by Keystore or Keychain, satisfying MASVS storage requirements while view models stay platform-agnostic.
  • Case study — Google’s Android architecture samples demonstrate layered UI, domain, and data modules with ViewModels and repositories; they are a practical reference for structuring production Kotlin apps.

Related patterns

  • Mobile Security — Data-layer boundaries make it easier to apply MASVS controls consistently.
  • Mobile Performance — Lifecycle-aware view models reduce duplicate work across rotation and backgrounding.
