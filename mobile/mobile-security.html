Mobile Architecture Security

Mobile Security

A comprehensive reference for mobile application security: network transport protection, credential and secret storage, biometric authentication, app attestation, integrity checks, and the OWASP Mobile Top 10.

⏱ 14 min read

What it is

Mobile security architecture is the set of client and API controls that protect data on lost devices, on hostile networks, and inside reverse-engineered binaries. It spans transport (TLS 1.2+, optional certificate or public-key pinning), storage (Android Keystore, iOS Keychain, encrypted SQLite), authentication UX (biometrics bound to hardware keys), and integrity signals (Play Integrity API, Apple App Attest).

Practitioners map controls to OWASP MASVS (verification requirements), validate with OWASP MASTG (test cases and tools), and prioritise risks using the OWASP Mobile Top 10. MASVS level L1 is baseline for all apps; L2 adds defence-in-depth for sensitive data; MASVS-R adds resilience against tampering and reverse engineering for high-threat domains.

Mobile security is not only client hardening—API design choices (token storage endpoints, no secrets in push payloads, attestation on sensitive writes) are part of the same threat model as on-device controls. See Mobile API Design and Push Notifications for transport-adjacent patterns.

Why it exists

Phones are easily lost, jailbroken, or malware-instrumented; binaries are trivial to decompile; café Wi-Fi enables trivial MITM without pinning. Web security assumptions (SameSite cookies, HttpOnly, short-lived browser sandboxes) do not transfer—mobile apps persist tokens locally and ship static secrets unless disciplined build pipelines forbid them.

Regulators and app stores increasingly expect demonstrable baselines (encryption in transit and at rest, least-privilege permissions, secure authentication). A structured standard (MASVS) turns ad hoc checklists into testable requirements the security team can run in CI and pen tests via MASTG recipes.

When to use

  • Any app handling accounts, payments, health, location history, or enterprise data—start with MASVS L1 minimum.
  • Financial, identity, or healthcare flows—target MASVS L2 storage, auth, and network chapters.
  • High-value targets (mobile banking, government, premium IP)—add MASVS-R integrity controls and server-side attestation verification.
  • Apps using push for security events—ensure payloads do not leak secrets; enforce authenticated fetches on open.
  • BYOD enterprise apps—combine MDM policies with app-managed Keychain/Keystore accessibility flags.

When not to use

  • Pinning without rotation — leaf or single-pin strategies brick clients during CA migration; use SPKI pins and backups.
  • MASVS-R everywhere — obfuscation and anti-tamper for a wallpaper app adds cost without matching threat.
  • Client-only security — attestation and jailbreak detection supplement, never replace, server-side authorization and fraud models.
  • Hard-block all rooted devices — can alienate power users; prefer degraded mode unless policy mandates block.
  • Secrets in source or plist — assume extracted; use short-lived tokens from backend after integrity checks.

Typical architecture

Defense in depth: the app pins TLS, stores tokens in hardware-backed storage, optionally attests before high-risk calls; the API gateway enforces OAuth/mTLS; sensitive operations re-check attestation server-side.

Pros and cons

Pros

  • TLS with pinning and disabled cleartext aligns with OWASP MASVS network requirements and blocks many on-path interception tools used in MASTG test cases.
  • Android Keystore and iOS Keychain with Secure Enclave backing keep long-lived refresh tokens off easy-to-dump app sandboxes when combined with hardware-backed keys.
  • Play Integrity and App Attest give the server cryptographic evidence about app and device integrity before high-value mutations such as wire transfers.
  • Biometric prompts tied to CryptoObject or access-control flags ensure unlocking a session also unlocks the underlying key, not just a UI gate.

Cons

  • Mis-managed pinning breaks legitimate users during certificate rotation; Apple and Android both recommend backup pins and operational runbooks before enforcing SPKI hashes.
  • Attestation verdicts are signals, not proofs—sophisticated fraud can replay tokens or run on emulators unless the server enforces authorization independently.
  • Hard jailbreak or root blocks frustrate power users and researchers, and may push risky audiences toward tampered APKs distributed outside Play or the App Store.
  • Strong client controls increase release friction: R8 mapping, entitlement reviews, and MASTG regression tests must ride every store submission.

Implementation notes

Network (MASVS-NET)

Enforce HTTPS everywhere; disable cleartext (Android Network Security Config, iOS App Transport Security). Pin SPKI hashes of intermediates with backup pins and documented rotation runbooks. Test with MASTG network chapters (MITM proxies, certificate validation bypass attempts).

Storage (MASVS-STORAGE)

Store refresh tokens and cryptographic keys in Android Keystore / EncryptedSharedPreferences and iOS Keychain with kSecAttrAccessibleWhenUnlockedThisDeviceOnly where backups must not export secrets. Never log PII or tokens; disable Android backup for sensitive databases or encrypt SQLCipher contents.

Authentication (MASVS-AUTH)

Use platform OAuth or passkey flows where possible. Bind high-value actions to BiometricPrompt / LocalAuthentication with CryptoObject-backed keys so biometrics gate key use, not just UI gates.

Integrity (MASVS-RESILIENCE)

Request Play Integrity or App Attest tokens before wire transfers or admin actions; verify server-side with Google/Apple APIs. Treat jailbreak/root signals as risk scores, not sole gatekeepers.

Engineering process

Run MASTG-guided tests in release pipelines; map findings to MASVS controls. Strip debuggable flags, enable R8/ProGuard on Android, and remove verbose logging in release builds. Align third-party SDK inventory with OWASP Mobile Top 10 supply-chain risks (M2).

Common failure modes

  • Plaintext preference storage — tokens in SharedPreferences/UserDefaults (MASTG storage tests).
  • ATS / cleartext exceptions — “temporary” HTTP endpoints that ship to production.
  • Pinning false confidence — no backup pins; outage during cert rotation.
  • Hardcoded API keys — extractable from IPA/APK; violates MASVS secret handling.
  • Over-logging — request/response logs with authorization headers or PHI.
  • Attestation-only trust — client says “I’m safe” but server skips authorization checks.
  • Push payload leakage — OTP or account numbers visible on lock screen.

Decision checklist

  • Which MASVS level (L1, L2, R) is documented for this app and reviewed annually?
  • Are MASTG network, storage, and auth test cases in the release checklist?
  • Are tokens and keys only in Keystore/Keychain (no UserDefaults/SharedPreferences)?
  • Is pinning configured with SPKI hashes and at least one backup pin?
  • Is cleartext traffic disabled in production builds?
  • Are release builds non-debuggable with shrinking/obfuscation enabled?
  • Is attestation verified server-side on sensitive mutations?
  • Do push and deep-link flows avoid exposing secrets on the lock screen?

Example use cases

  • Illustrative scenario — A mobile bank targets MASVS L2+R: SPKI pinning, biometric-gated signing key, Play Integrity on transfers, server-side limits when integrity fails.
  • Illustrative scenario — Meridian Commerce wallet stores cards in Keychain/Keystore, uses L1 controls only for catalog browsing, and escalates to step-up auth for checkout.
  • Illustrative scenario — A clinical notes app keeps PHI off iCloud backup, requires device passcode, and runs MASTG storage tests in CI before each store submission.
