Mobile Architecture

Offline-First Design

Local-first data, background sync, and conflict handling so mobile apps stay usable when the network is slow, intermittent, or absent.

⏱ 13 min read

What it is

Offline-first design is an approach to mobile applications where the on-device store is the authoritative read path for the UI and network calls refresh or upload changes asynchronously. The presentation layer observes local data through reactive streams (Room with Kotlin Flow, Core Data or SwiftData, SQLite in React Native, or Hive or Drift in Flutter) and does not block on connectivity for ordinary reads and writes. A repository mediates between the local database, a sync component, and remote APIs so screens stay ignorant of whether a row arrived from cache or from the last sync.

This differs from network-first or online-only designs, where each screen waits on HTTP before showing content and fails closed when offline. Offline-first trades implementation complexity—sync queues, conflict policies, migrations, and encrypted storage—for responsiveness and resilience on unreliable cellular and Wi‑Fi links.

Why it exists

Mobile clients move through tunnels, aircraft mode, and congested cells; latency spikes even when a signal icon is present. Product workflows such as capturing notes, completing checklists, or reviewing schedules cannot assume always-on connectivity. Google documents an offline-first data layer as part of recommended Android architecture; Apple’s background task and persistence frameworks exist partly to reconcile local state with servers when the app is not in the foreground.

Batching outbound changes also reduces redundant API traffic and gives operators control over when expensive sync runs relative to battery and network type—constraints that WorkManager on Android and BGTaskScheduler on iOS express explicitly.

When to use

  • Productivity, field operations, or inventory apps where users must continue work without a live connection.
  • Read-heavy experiences with cacheable catalogs, manuals, or maps that change on a schedule rather than every second.
  • Multi-device experiences where each handset should show the last known state immediately and converge later.
  • Features already structured with repositories and view models, so adding a local source of truth is a natural extension.
  • Regulated apps that must encrypt data at rest on device per OWASP MASVS storage requirements while still offering offline access.

When not to use

  • Server-authoritative financial or identity actions that cannot be optimistically committed without fraud and compliance review.
  • Live collaborative editing that needs sub-second merge semantics beyond simple last-write-wins or CRDT subsets.
  • Highly personalized feeds where cached content is misleading unless refreshed continuously.
  • Data that must not reside on device under policy, in which case local persistence is prohibited regardless of UX benefits.
  • Thin clients with no local storage budget and no security model for encrypted databases on shared devices.

Typical architecture

Reads and writes hit the repository first; a worker or scheduler pushes pending operations to the API when constraints allow.

Pros and cons

Pros

  • Perceived performance improves because the UI renders from local queries instead of waiting on round trips.
  • Core workflows continue in airplane mode, dead zones, and during backend outages.
  • Outbound work can be batched, retried with backoff, and constrained to unmetered or charging conditions.
  • Repositories can serve identical APIs to view models whether data is stale or freshly synced.
  • Encrypted local stores support MASVS storage controls while still allowing offline reads.

Cons

  • Sync engines, migrations, and conflict policies add sustained engineering cost.
  • Users may see stale data unless the UI surfaces sync status and refresh affordances.
  • Conflict resolution can require explicit UX when automatic merge is unsafe.
  • Local databases must be migrated carefully across app versions and platform backups.
  • Testing matrix expands to cover offline, flaky network, and multi-device convergence cases (MASTG scenarios).

Implementation notes

Single source of truth: Follow Android’s offline-first data-layer guidance: UI collects from the database; repositories write locally first, then enqueue remote synchronization. On iOS, use Core Data or SwiftData with background contexts and merge policies; schedule BGAppRefreshTask or BGProcessingTask when Apple’s background execution rules allow.

Sync queue: Persist pending mutations with operation type, entity identity, payload, and retry metadata. WorkManager on Android and BGTaskScheduler on iOS should respect network and battery constraints. Use exponential backoff on failures and idempotent server APIs where possible.

Delta and cursor sync: Store a per-collection sync cursor or high-water timestamp; request only changes since the last successful sync. Server entities need monotonic versioning or reliable updated_at fields indexed for range queries.

Conflict strategies: Last-write-wins fits low-criticality fields; three-way merge helps structured documents; CRDTs suit specific collaborative types when you accept their data-model limits. Document the chosen rule per entity and test clock skew and duplicate delivery.

Cross-platform: React Native often pairs SQLite or Realm with background fetch; Flutter uses Drift, Hive, or sqflite with isolates for I/O. Apply the same repository boundary so JavaScript or Dart UI code does not embed raw SQL.

Security: Encrypt databases holding credentials or PII (SQLCipher, EncryptedSharedPreferences for keys, iOS Data Protection classes) and exclude sensitive backups per MASVS.

Offline-first means the local database (Room, Core Data, SwiftData, or Realm) is the source of truth the UI queries: repositories write rows and enqueue the same mutation in an outbox table inside one transaction so process death never leaves “shown to user” without a durable record. Optimistic UI applies the local change immediately, marks sync state pending, and rolls back or surfaces conflict UI when the server rejects—never silently discard the user’s edit on timeout.

Choose conflict behavior per entity at the product layer (last-write-wins for low-risk flags, explicit merge for shared notes); algorithm details, vector clocks, CRDTs, and tombstone garbage collection live in sync engine design. Enforce storage quotas with LRU eviction for caches, cap attachment downloads on cellular, and expose sync status so stale reads are intentional, not mysterious. UI tests should cover airplane mode through optimistic send, failed rollback, and successful reconcile when connectivity returns. Index outbox rows by sync state so drain workers avoid full-table scans after long offline periods.

Common failure modes

  • Silent overwrite: Downloading server snapshots without merging local pending edits discards user work.
  • Unbounded queue: Long offline periods create a thundering herd when connectivity returns; batch and rate-limit uploads.
  • Migration gaps: Shipping a schema change without a tested Room, Core Data, or Drift migration bricks upgrades.
  • Hidden staleness: No “last synced” or error affordance erodes trust when data is old.
  • Main-thread I/O: Performing large reads or writes on the UI thread causes jank; use background executors or coroutines with clear dispatchers.
  • Non-idempotent APIs: Retried POSTs double-charge or duplicate records unless the server accepts idempotency keys.

Decision checklist

  • Does the UI observe the local database (or equivalent store) as the primary read path?
  • Are pending writes durable and replayable after process death?
  • Is incremental sync defined for each entity type that can grow large?
  • Are conflict rules documented, implemented, and covered by automated tests?
  • Do background jobs honor platform constraints for network type, charging, and expedited work limits?
  • Is sensitive data encrypted at rest and excluded from insecure backups?
  • Can QA reproduce offline, slow, and partition scenarios per MASTG network guidance?

Example use cases

  • Illustrative scenario — field maintenance: Technicians complete work orders in a local database underground; WorkManager uploads completed jobs when the device regains connectivity, applying last-write-wins only to low-risk status fields.
  • Illustrative scenario — personal notes: Notes save instantly to Room or SwiftData on device; sync merges paragraph-level changes with a documented CRDT or three-way merge when phone and tablet both edited offline.
  • Illustrative scenario — retail catalog: A repository seeds product rows from cache on launch and runs periodic delta sync over Wi‑Fi so browsing works in-store when the LAN is down.
  • Case study — Google’s offline-first architecture guide walks through repository patterns with local and remote data sources, which is the reference model for Android Jetpack apps.
