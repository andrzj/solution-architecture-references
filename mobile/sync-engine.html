Mobile Architecture

Sync Engine Design

How to reconcile local mobile data with server truth using outbox queues, versioning, merge policies, and user-visible conflict handling— the technical core of offline-first apps.

⏱ 12 min read

What it is

A sync engine is the client-side subsystem that moves data between a local store and a remote source of truth: enqueueing mutations made offline, downloading deltas since a cursor, detecting conflicts, applying merge rules, and surfacing cases that need human resolution. It sits behind the repository layer in offline-first architectures and hides network timing from the UI.

Merge policies range from simple last-write-wins (LWW) on scalar fields to server-authoritative merges, vector clocks, CRDTs for commutative structures, and operational transforms for ordered collaborative text. The right policy depends on domain semantics—not every field can tolerate silent overwrites.

Why it exists

Mobile networks drop, lag, and switch interfaces without warning. Users expect edits made in airplane mode to appear on other devices later—without duplicates, silent data loss, or unexplained rollbacks. A dedicated sync layer turns "retry until success" into a structured protocol with versions, idempotency, and observable sync status.

Naive approaches—compare client timestamps, overwrite server rows, or re-fetch entire tables—fail under clock skew, multi-device edits, and partial failures. Sync engines make trade-offs explicit: what merges automatically, what blocks until the user chooses, and what the server always wins.

When to use

  • Field, retail, or logistics apps where staff work offline for long stretches.
  • Notes, tasks, and personal productivity data that must sync across phone, tablet, and web.
  • CRUD domains with moderate write rates and clear per-entity ownership.
  • Collaborative data where automatic merge is possible (counters, sets) or conflict UI is acceptable.
  • When product requirements include "syncing…" indicators, manual retry, or per-item sync errors.

When not to use

  • Read-mostly catalogue apps: HTTP cache plus periodic full refresh may be enough; avoid outbox complexity until users must edit offline.
  • Strong global consistency: Financial ledger or inventory locks often need online server validation; optimistic local commits without reconciliation rules are unsafe.
  • Real-time multiplayer state: Sub-second shared state usually needs a dedicated realtime channel (WebSocket, game server), not batch sync alone.
  • Binary-heavy media: Large video or RAW photo uploads belong in resumable object-storage APIs with background URL sessions, not row-by-row outbox tables.

Typical architecture

Local writes are append-only operations in an outbox; a worker pushes them upstream while a pull channel applies server deltas and triggers merge logic.

Pros and cons

Pros

  • Predictable offline UX: the UI reads local data immediately while sync status is explicit.
  • Idempotent, queued uploads survive process death and flaky networks.
  • Delta sync reduces bandwidth versus full-table refresh.
  • Clear extension point for analytics (queue depth, conflict rate, time-to-sync).

Cons

  • Merge semantics and conflict UI are product decisions—engineering cannot hide ambiguity in shared fields.
  • CRDTs and OT add substantial complexity for rich text and ordered lists.
  • Dual-write bugs between outbox and main tables cause subtle duplication if transactions are not atomic.
  • Server must expose versioned, idempotent change APIs—sync is a cross-team contract, not only mobile work.

Implementation notes

Outbox pattern: Wrap local business writes and outbox inserts in a single database transaction. Each operation gets a stable client-generated ID used as the HTTP idempotency key. Store operation type (create/update/delete), entity type, payload snapshot, and optional dependency ordering (parent before child).

Versioning: Prefer monotonic server-assigned versions or per-replica vector clocks over device timestamps for conflict detection. For LWW, scope wins per field or per document—not globally per table—so unrelated fields on the same record do not clobber each other.

Pull cursors: Persist the last successfully applied change cursor per collection. After push ACK, run pull to absorb concurrent edits from other devices before declaring the entity clean. Use tombstones or soft-delete flags so deletes propagate and resurrected rows do not reappear.

Backoff and fairness: Exponential backoff with jitter on 5xx and network errors; cap retries and surface a user-visible "sync failed" with manual retry. Pause or throttle sync on low battery, data-saver mode, and metered networks—expose toggles in settings for power users.

When to reach for CRDTs: Use CRDT structures (G-Counter, OR-Set, LWW-Register) when commutative merges are provably correct. For linear collaborative text, OT or CRDT text types are warranted; for simple task titles, field-level LWW plus audit log is usually enough.

Delta sync exchanges change tokens or cursors: the client sends the last acknowledged server revision; the API returns only creates, updates, and deletes since that point. Server-side version columns, change logs, or per-replica vector clocks make conflicts detectable without trusting device clocks. Tombstones or soft-delete flags propagate removals; schedule garbage collection so resurrected rows do not reappear after a stale pull.

Scope sync to what the user opened—partial collections reduce battery—and persist cursor progress so interrupted pulls resume after process kill rather than restarting full-table downloads. The offline-first layer owns optimistic UX and outbox enqueue; this engine owns convergence, backoff fairness, and cross-device merge correctness on the wire. Dashboard sync queue depth, conflict rate, and time-to-convergence so regressions in merge rules surface before users report duplicated rows. After push ACK, run a bounded pull on the same scope so concurrent edits from other devices apply before the UI shows synced.

Common failure modes

  • Duplicate creates on retry: Missing idempotency key causes two server rows for one user action.
  • Lost deletes: Hard-delete locally without tombstone; another device or a stale pull resurrects the record.
  • Sync loops: Merge produces a diff that re-enqueues upload; missing convergence check or version comparison.
  • Clock-skew LWW: Device time wrong → wrong winner; server clock or logical versioning avoids this.
  • Full-table pull after push: O(n) downloads erase battery and obscure incremental errors.
  • Blocking UI on sync: Awaiting network in the repository blocks reads; UI should always observe local state first.

Decision checklist

  • Are all server mutation endpoints idempotent with respect to client operation IDs?
  • Is every automatic merge rule documented per entity and field?
  • Is there a user-facing path when automatic merge cannot proceed?
  • Are outbox writes transactional with the domain tables they represent?
  • Do pull and push share a single versioning model the backend team owns?
  • Does sync respect battery, metered network, and lifecycle pause hooks?
  • Are delete, conflict, and retry metrics visible in observability dashboards?

Example use cases

  • Illustrative scenario — field CRM: SQLite outbox for visit notes and status updates; LWW on status with server audit log; MQTT or HTTPS push with pull-on-reconnect for rural connectivity.
  • Illustrative scenario — shared task list: OR-Set for assignees, LWW for title and due date; conflict badge when two users edit the same field offline.
  • Case study — local-first research: The local-first community documents merge and ownership patterns that influenced products such as collaborative notebooks and design tools—useful reference when choosing CRDT vs server authority.
