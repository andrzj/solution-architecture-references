Mobile Architecture

Push Notifications

End-to-end architecture for push notifications: APNs and FCM infrastructure, device token lifecycle, payload design, silent push, delivery analytics, and opt-in UX patterns.

⏱ 12 min read

What it is

Mobile push notifications are server-initiated messages delivered through platform-operated channels: Apple Push Notification service (APNs) on iOS, iPadOS, watchOS, and macOS, and Firebase Cloud Messaging (FCM) on Android and as a cross-platform relay when the iOS app uses the Firebase SDK. Your backend never talks to the handset directly—it sends an authenticated HTTP/2 request to APNs or FCM with a device token (or topic subscription), and the OS wakes or alerts the app.

Two delivery classes matter in architecture. User-visible notifications (APNs alert/sound/badge; FCM messages with a notification payload) appear in the system shade and require user permission on modern iOS and Android 13+. Background / data-only messages (APNs content-available: 1 with appropriate apns-push-type; FCM data-only) can trigger limited background work but are throttled and must not carry time-critical business logic alone.

Push sits beside your mobile APIs: token registration, topic opt-in, and notification-open deep links are part of the same security and versioning story as REST (see Mobile API Design).

Why it exists

Polling and aggressive foreground refresh keep the cellular radio active and waste power—among the most expensive operations on a phone. Push lets the server signal “something changed” at event time so the OS batches delivery and the app fetches details on demand.

Platform push infrastructure also solves long-lived connection management, certificate rotation at scale, and device reachability when apps are suspended. Building a proprietary persistent socket fleet for consumer devices rarely beats APNs/FCM for cost, reliability, and store policy compliance.

When to use

  • Transactional events users expect immediately: messages, delivery status, fraud alerts, appointment reminders.
  • Re-engagement with explicit user-controlled categories (marketing vs account alerts).
  • Low-frequency background sync hints when combined with offline-first workers—not as the sole sync mechanism.
  • VoIP / Live Activities / communication notifications where Apple’s dedicated push types apply.
  • Broadcast segments via FCM topics or APNs broadcast capabilities (with consent and unsubscribe paths).

When not to use

  • Sub-second interactive data (live maps, gaming state)—use WebSockets or in-app polling while foregrounded.
  • Guaranteed delivery of business-critical state—push is best-effort; persist outcomes server-side and reconcile on app open.
  • High-frequency silent sync—iOS and Android throttle background pushes; expect delayed or coalesced delivery.
  • Secrets in clear text in the payload—treat notification bodies as untrusted display surfaces (align with OWASP MASTG network communication tests).
  • Mandatory marketing pushes without granular opt-out—violates platform policies and erodes opt-in.

Typical architecture

Registration flows upward (app → your API → token store); delivery flows downward (event → notification service → APNs/FCM → OS). Many teams isolate outbound push in a worker with rate limiting and dead-letter handling for invalid tokens.

Pros and cons

Pros

  • Server-initiated alerts replace tight polling loops, which aligns with Android power guidance and reduces unnecessary radio wakeups.
  • FCM and APNs operate vendor-managed delivery networks, so your backend sends one HTTPS request per batch instead of maintaining millions of idle sockets.
  • Data payloads with stable deep links let a cold-started app route directly to the relevant screen when the user taps, improving conversion on transactional messages.
  • FCM topic and condition targeting broadcast to segments without iterating every device row, while APNs supports similar patterns for live activities and service extensions where appropriate.

Cons

  • iOS requires an explicit user grant for alert-style notifications; a single denial during onboarding often permanently caps reach unless you educate before the system sheet.
  • Neither FCM nor APNs guarantees immediate delivery—devices offline, in low-power modes, or with Focus filters may defer or suppress messages.
  • Background and silent pushes are rate-limited on both platforms and must not carry security-sensitive content visible on the lock screen per OWASP MASVS privacy guidance.
  • Token tables rot quickly across reinstalls, restores, and multi-device households; without automated cleanup of FCM UNREGISTERED and APNs 410 Gone responses, cost and metrics drift from reality.

Implementation notes

APNs provider setup

Use token-based authentication with a .p8 key (preferred over legacy certificates). Send to the correct environment host (sandbox vs production). Set apns-topic to your bundle ID, apns-push-type to alert, background, or voip as appropriate, and match apns-priority to urgency (10 for visible alerts, 5 for background). See Apple’s sending notification requests to APNs.

FCM HTTP v1

Migrate off legacy server keys to the HTTP v1 API with OAuth2 service-account credentials. Structure messages with separate notification (display) and data (always delivered to the app) sections; use android and apns blocks for platform overrides. Handle batch responses and per-token errors for cleanup.

Token and identity model

Store (user_id, device_id, platform, token, app_version, updated_at). Upsert on every registration call; invalidate on logout. For multi-device users, fan out sends or target the most recently active device for non-critical alerts.

Payload and deep links

Include a stable notification_id, deep-link URL or app-specific route, and enough display text for the tray without another round trip for the common case. Fetch sensitive detail after open via authenticated API. Use Notification Service Extension on iOS to enrich media safely.

Opt-in UX

On iOS, show a value explanation before the system permission sheet; one denial forces Settings detours. On Android 13+, request POST_NOTIFICATIONS in context. Align categories with in-app notification preferences synced to the server.

Analytics funnel

Log enqueued, accepted_by_platform (HTTP 2xx from APNs/FCM), delivered (where platform receipts exist), and opened. Correlate with notification_id. Drops between accepted and opened usually indicate token rot or irrelevant copy.

APNs and FCM are complementary transports: Apple devices need APNs (directly or via FCM’s APNs bridge); Android uses FCM’s connection to Google Play services. Token lifecycle matters—reinstalls, restores, and logout invalidate rows; honor FCM UNREGISTERED and APNs HTTP 410 responses immediately. Silent and data-only pushes are throttled and may not wake force-quit apps; use them to nudge sync, not as a chat bus.

Set priority and collapse keys deliberately: high priority for time-sensitive alerts, normal for marketing; collapse keys dedupe stale campaign updates on the device. Rate-limit fan-out batches at the sender, shard large audiences across worker queues, and measure delivery versus open rate per notification_id so product and platform teams spot token rot or permission denials before campaign ROI collapses. Load-test the sender against provider rate limits before major campaigns—HTTP 429 storms are easier to fix in staging than during a product launch. Isolate transactional sends from marketing bursts so password resets never queue behind promotional fan-out.

Common failure modes

  • Stale token sends: Campaigns keep targeting rows after FCM returns UNREGISTERED or APNs returns HTTP 410 with Unregistered, which inflates send volume without reaching users.
  • Premature permission prompts: Requesting notification access before the user sees value correlates with permanent denial on iOS and ignored Android 13+ POST_NOTIFICATIONS flows.
  • Silent push as a data bus: Relying on background pushes for chat, GPS, or payment state violates platform throttling limits and fails when the app is force-quit or restricted by battery saver.
  • Broken cold-start deep links: Payloads include routes the app only handles when already running, so taps from the tray land on home instead of the intended order or thread.
  • Sandbox and production mismatch: APNs tokens registered against the wrong environment or Firebase project strand entire builds until you rotate credentials and re-register devices.
  • Lock-screen secret leakage: OTPs, balances, or health data appear in notification bodies and violate OWASP MASVS privacy and MASTG notification testing expectations.

Decision checklist

  • Is the first permission request preceded by an in-app explanation tied to a concrete user benefit?
  • Are FCM HTTP v1 and APNs token-authenticated providers configured with separate credentials per environment?
  • Does every outbound message include a stable notification_id and deep link tested on cold start?
  • Are invalid tokens deleted automatically from the device store when providers report unregister errors?
  • Do analytics distinguish enqueued, accepted, delivered (where available), and opened events?
  • Are display payloads limited to non-sensitive summary text, with detail fetched over authenticated APIs after open?
  • Do promotional and transactional categories honor per-user preferences and platform quiet-hour constraints?

Example use cases

  • Illustrative scenario — Meridian Commerce sends order-shipped alerts with tracking deep links; a low-priority data message nudges cart sync overnight when saved-item prices change.
  • Illustrative scenario — RideRelay uses high-priority APNs for “driver arriving” and in-app WebSocket for live map position while foregrounded—avoiding abusive silent push frequency.
  • Illustrative scenario — A breaking-news product batches digest pushes by user locale at 07:00 local time via FCM topic conditions.

Related patterns

  • Mobile API Design — Authenticated token registration and idempotent device rows that notification services consume.
  • Mobile Security — MASVS controls for payload redaction, extension network calls, and lock-screen disclosure.
  • Offline-First Design — Background fetch and silent nudges that wake sync workers without replacing durable outboxes.
  • App Lifecycle — Foreground, background, and terminated states that determine whether data or notification blocks are processed.
  • Mobile Performance — Avoiding polling by push must still respect power budgets and main-thread work when handling arrivals.
