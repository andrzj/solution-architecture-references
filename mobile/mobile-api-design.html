Mobile Architecture API Design

Mobile API Design

Designing backend APIs that account for the unique constraints of mobile clients: limited bandwidth, battery concerns, intermittent connectivity, and the need to serve multiple client shapes.

⏱ 12 min read

What it is

Mobile API design is the practice of shaping HTTP (and occasional binary) interfaces so phone and tablet clients can render screens with minimal radio use, predictable latency on poor networks, and contracts that remain valid across app versions users refuse to upgrade. It spans payload size, round-trip count, cache semantics, sync-friendly list endpoints, and edge concerns such as registering Firebase Cloud Messaging (FCM) and Apple Push Notification service (APNs) device tokens.

Architecturally, teams usually combine a mobile BFF or experience API (see Backend for Frontend) with domain services that stay client-agnostic. The mobile layer aggregates per-screen data in parallel, applies sparse field selection, and returns DTOs mapped to UI models—not full domain graphs. Transport choices (HTTP/2 or HTTP/3 multiplexing, Accept-Encoding: br, gzip, conditional GET with ETag) reduce bytes and connection churn; optional Protocol Buffers or gRPC on selected hot paths trade tooling cost for smaller payloads.

Mobile API design also encodes lifecycle constraints: apps cannot be force-updated, offline queues replay on flaky networks, and notification-driven refresh must not assume the app is foregrounded. Those constraints affect versioning, idempotency keys on writes, and how much context you embed in push-related registration endpoints.

Why it exists

Generic REST APIs built for web dashboards or partner integrations often return wide JSON documents, assume always-on connectivity, and encourage chatty composition on the client. On mobile, each TLS handshake and idle timeout on the cellular radio consumes battery; sequential waterfalls inflate time-to-interactive on high-latency links; and oversized responses waste metered data.

Without deliberate mobile API design, product teams compensate with aggressive client caching hacks, duplicate business rules in the app, or polling loops that drain battery. A BFF or mobile-tuned surface moves aggregation server-side, keeps domain services narrow, and lets architects enforce pagination, field masks, and stable list contracts once—benefiting every screen.

When to use

  • Multiple client types (iOS, Android, web, TV) that need different field sets or aggregation for the same domain.
  • Home or hub screens that fan out to several microservices and must load in one or two round trips.
  • Markets where bandwidth is costly or connectivity is intermittent—payload and cache discipline matter for retention.
  • Products where battery impact is visible (navigation, fitness, background location, frequent refresh).
  • Apps that register for push and need authenticated token-management APIs co-located with user session handling.
  • Offline-first or sync-heavy apps that need cursor-based delta endpoints and conflict-aware writes (see Offline-First Design).

When not to use

  • A single mobile platform with one thin client—a shared REST API plus query parameters may suffice without a dedicated BFF.
  • Low-traffic internal tools where operational overhead of another service exceeds UX gain.
  • Teams without capacity to run, secure, and on-call a BFF—fix domain boundaries before adding adaptation layers.
  • Binary protocols on every endpoint when gzip JSON already meets SLOs—protobuf/gRPC is a targeted optimisation, not a default.
  • GraphQL or batching solely to avoid designing proper list and detail resources—start with resource-oriented contracts.

Typical architecture

Traffic flows from native clients through a gateway (TLS, auth, rate limits) into a mobile BFF that parallel-fetches domain services, registers push tokens, and returns screen-specific payloads. Notification delivery uses a separate outbound path to FCM/APNs (see Push Notifications).

Pros and cons

Pros

  • A mobile BFF can return screen-shaped DTOs in one or two round trips, which shortens time-to-interactive on high-latency cellular links and keeps parsing work off the UI thread.
  • Sparse fieldsets and list-specific projections cut JSON size on card views, which matters when users are on metered data or weak 3G/4G as described in Android’s network usage guidance.
  • HTTP/2 or HTTP/3 multiplexing reuses a single encrypted connection for parallel reads, reducing radio wakeups that Apple documents as a major battery drain.
  • Authenticated push-token registration endpoints beside the BFF keep FCM and APNs device identity aligned with the user session without scattering token logic across domain services.
  • Transport compression and conditional GET with validators let repeat visits return 304 responses, lowering bytes transferred without bespoke client caching hacks.

Cons

  • Each BFF variant adds deployment, observability, and security review surface; teams must define who owns schema drift when domain APIs change.
  • Field masks and projections push complexity into repositories and indexes; naïve ORM queries may still fetch wide rows if projections are not enforced in code review.
  • Push reach depends on server-side token hygiene—FCM UNREGISTERED and APNs HTTP 410 responses must delete stale rows or campaigns silently miss devices.
  • Long-lived app builds cannot be revoked, so backward-compatible versioning and additive JSON fields become a permanent tax on API design.
  • Premature gRPC or GraphQL on every path increases build tooling and attack surface unless OWASP MASVS network controls are applied consistently end-to-end.

Implementation notes

Screen-oriented aggregation

Define explicit endpoints or GraphQL operations per major screen (GET /mobile/home, GET /mobile/order/{id}/tracking). Fan out to domain services concurrently with a parent deadline; return partial data with degraded: true flags when non-critical dependencies fail rather than failing the entire response.

Sparse fields and pagination

Support field masks (?fields=id,title,thumbnail_url) or fixed list DTOs so card views never download detail graphs. Use cursor pagination for infinite scroll; never rely on deep offsets on mobile lists (see API Pagination).

Compression, HTTP/2+, and caching

Enable Brotli or gzip at the CDN and origin. Prefer HTTP/2 or HTTP/3 to multiplex parallel reads on one connection. Mark stable reads with Cache-Control and validators; the client should send If-None-Match to receive 304 bodies on repeat visits.

Versioning and compatibility

Ship mobile clients you cannot revoke—plan for N and N−1 major API versions. Use path (/v2/) or vendor Accept types; avoid breaking field renames without additive periods. Pair deprecations with minimum app version gates only for security fixes, not routine features.

Token registration APIs

Expose an authenticated PUT /devices/push-token (or equivalent) accepting platform (apns | fcm), token string, app version, and locale. On Android, handle onNewToken in FirebaseMessagingService; on iOS, observe APNs device token updates and FCM mapping when using Firebase. Store tokens per user and device row; dedupe on token value. When sending via FCM HTTP v1, delete rows on UNREGISTERED; for APNs, remove on HTTP 410 Gone with reason=Unregistered.

Writes on unreliable networks

Accept Idempotency-Key headers on POST/PATCH from mobile clients so offline replay does not double-charge or duplicate orders. Return stable error bodies the app can persist in an outbox queue.

A mobile BFF (or dedicated mobile-facing service) owns DTOs shaped for cards and wizards rather than exposing desktop graphs. Pair trimmed payloads with cursor pagination and optional GraphQL persisted queries so repeat launches do not download multi-megabyte introspection or ad hoc query strings. Version APIs knowing old store builds linger for months: support additive fields, sunset features with soft prompts, and reserve forced minimum-version gates for security or incompatible contract breaks.

Make reads cheap on flaky radio: return ETags or Last-Modified on stable resources so clients send conditional requests and receive 304 bodies without re-parsing JSON. On writes, idempotency keys dovetail with the client outbox. Prefer HTTP/2 multiplexing or HTTP/3 (QUIC) through the CDN so connection migration across cell handoffs does not reset TLS for every parallel screen fetch. Contract tests between BFF and domain services catch additive-only promise breaks before old store builds ship. Publish a minimum supported app version endpoint the client checks on launch so security fixes can block ancient binaries without surprising users on routine releases.

Common failure modes

  • Waterfall screens — five sequential GETs before first paint; fix with BFF aggregation or HTTP/2 parallel client calls with a single loading state.
  • Desktop-shaped JSON — nested graphs and nullable blobs on list endpoints; define mobile list DTOs with stable field names.
  • No idempotency on writes — duplicate submissions when the client retries after a timeout.
  • Breaking changes without versioning — old app builds crash on missing fields; use additive schemas and contract tests.
  • Token table rot — FCM/APNs errors ignored; delivery metrics look healthy while reach collapses.
  • Polling instead of push — background timers for inbox counts; burns battery and fights store review guidelines.
  • Ignoring certificate and ATS policy — cleartext exceptions for “quick fixes”; see Mobile Security for transport requirements.

Decision checklist

  • Is Brotli or gzip enabled end-to-end through CDN and origin?
  • Does each primary screen load with at most two round trips under nominal conditions?
  • Is there a documented mobile API versioning and sunset policy before store release?
  • Are list endpoints cursor-paginated with bounded page sizes?
  • Is push token registration authenticated, idempotent, and tied to device records?
  • Do write endpoints accept idempotency keys from the mobile outbox?
  • Are contract or consumer-driven tests run when domain services change?
  • Is notification-triggered refresh distinguished from user-initiated refresh in analytics?

Example use cases

  • Illustrative scenario — A news product’s list API returns only id, headline, hero_image_url, and published_at; article body loads on tap with ETag caching.
  • Illustrative scenario — RideRelay mobile BFF exposes /v1/rider/home combining active trip, payment instrument summary, and promo banner; FCM data messages nudge the map layer while the user is in-app.
  • Illustrative scenario — Meridian Commerce catalogue sync uses protobuf on a single nightly delta endpoint for field sellers on 3G, while storefront checkout stays JSON over HTTP/2 for easier debugging.
