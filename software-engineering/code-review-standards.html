Code Review Standards

Establishing team standards for code quality, review turnaround, and automation gates.

⏱ 10 min read

What it is

Code review standards are the written quality bars and merge policies that turn informal review culture into predictable outcomes: which checks must pass in CI, what reviewers must evaluate, how fast review should happen, and when extra scrutiny (security, architecture) is mandatory. They complement code review practices — the interpersonal how-to — with objective rules that apply regardless of who is on call.

Google’s public Engineering Practices describe a similar split: authors and reviewers share a standard of code review (every approved change should improve overall code health), while automation owns formatting, obvious lint violations, and regressions caught by tests. Your standards document should be short enough to read in ten minutes and concrete enough to encode in branch protection and PR templates.

Why it exists

Without standards, review quality varies with reviewer mood, timezone, and familiarity with the area. One teammate blocks on naming preferences while another approves a thousand-line diff unread — defects and architectural drift slip through the gaps. Written standards set a floor: the same tests, the same risk tiers, and the same expectations for description, size, and documentation updates.

Distributed and async teams cannot rely on hallway norms. Standards also scale onboarding: new contributors learn what “good enough to merge” means from the checklist and CI gates, not from guessing what the tech lead would have said. That reduces rubber-stamping and reduces bike-shedding by pushing mechanical rules into bots.

When to use

  • Organisations with more than one squad sharing repositories, libraries, or platform components.
  • Open source or inner-source programs where occasional contributors must meet the same bar as core maintainers.
  • Regulated or audit-sensitive environments where evidence of review and automated gates is required.
  • Repositories with high blast radius (shared SDKs, auth, payment, infra modules).
  • Teams adopting Ship / Show / Ask tiers — standards define which change types need which approval path.
  • Platform engineering teams publishing golden-path templates used by many product teams.

When not to use

  • Encyclopaedic style guides: Fifty-page documents that nobody reads; keep human standards under a page and push formatting to linters.
  • Duplicate automation: Standards that repeat what CI already enforces — reviewers should not re-litigate failing checks.
  • One-size-fits-all on experiments: Throwaway spikes may use lighter gates if clearly labelled and not deployed to production paths.
  • Standards without owners: A checklist nobody updates when tooling changes becomes misleading shelfware.

Typical architecture

Standards stack in layers: machines enforce mechanical rules first; humans spend attention on design, security, and maintainability; merge policy enforces who must approve and which checks are blocking.

Pros and cons

Pros

  • Consistent quality floor across reviewers and time zones.
  • Faster human review when bots catch trivia and authors self-review first.
  • Auditable evidence of what was checked before merge.
  • Clear escalation path for high-risk changes (security, schema, dependencies).
  • Easier onboarding — contributors read standards instead of inferring tribal rules.

Cons

  • Standards decay without owners and CI alignment — quickly become shelfware.
  • Over-long checklists cause fatigue and checkbox approval without thinking.
  • Rigid rules can slow legitimate emergencies if hotfix paths are not defined.
  • Encoding everything in required checks can block urgent fixes when flaky tests exist.
  • Cross-team standards need negotiation — one team’s “must-have” may be noise elsewhere.

Implementation notes

Encode the Google reviewer checklist in your own words. The reviewer guide expects attention to design, functionality, complexity, tests, naming, comments, style, and documentation — in that priority order. Publish a one-page checklist mirroring those categories; map each item to either CI (style, tests) or human review (design, complexity). Reviewers should not re-debate issues linters already enforce.

Author standards: The change author guide emphasises small changelists, self-review, descriptive titles and bodies, and splitting unrelated refactors from feature work. Add a PR template with sections: context, testing performed, rollout/risk, and links to tickets or ADRs. Require green CI before requesting review — assigning a human while checks are failing wastes attention.

Merge policy: Use branch protection for required status checks, dismiss stale approvals when new commits push, and CODEOWNERS for sensitive paths. Define review SLAs (for example, first response within one business day) and a process for escalation when SLAs slip. Differentiate hotfix paths: allow merge with post-merge review only when incident severity warrants it, documented in the standard.

Risk tiers: Tag dependency bumps, database migrations, auth changes, and public API edits for additional reviewers or security review. Align dependency standards with dependency management — major version upgrades should not auto-merge without changelog review.

Publish what reviewers must verify versus what robots own: design, correctness, tests, and rollout risk stay human; style, SPDX headers, and formatter output are merge-blocking only through linters. Map the Google reviewer checklist categories to your PR template. Require self-review and test evidence before assignment. Escalation paths when SLAs slip belong here; day-to-day queue discipline and diff sizing live in code review practices.

Require two approvals on auth, payments, and schema migrations; one sufficient elsewhere unless CODEOWNERS demands more. Document hotfix merge-with-follow-up criteria in the same standard so incidents do not erode protection.

Publish exemplar PR descriptions so new hires learn what “testing performed” evidence looks like for your stack. Update exemplars when stack or compliance rules change quarterly.

Common failure modes

  • Rubber-stamp reviews: LGTM on large diffs — enforce size guidelines and require authors to split changes.
  • Bike-shedding: Debating formatting in comments — block merge only on failing automated checks.
  • Standards bypass: Administrators merging without checks — undermine trust; use break-glass roles with audit.
  • Flaky required checks: Teams ignore red CI or bypass protection; fix or quarantine flaky tests urgently.
  • Checklist without teeth: Human items never discussed because CI is green but design is wrong — train reviewers on design and test adequacy, not only lint.
  • Inconsistent hotfix policy: Emergency merges without post-review accumulate debt — log every exception.

Decision checklist

  • Are blocking CI checks documented per repository template and mirrored in branch protection?
  • Does the human checklist match reviewer priorities (design, behaviour, tests before style)?
  • Is there a published SLA for review turnaround and an escalation path?
  • Do standards differentiate feature, dependency, hotfix, and docs-only change paths?
  • Are high-risk paths covered by CODEOWNERS or mandatory second approvals?
  • Does every merged PR require a description that explains why, per Google CL guidance?

Example use cases

  • Platform shared library: PR template links standards; SonarQube quality gate blocks merge; two CODEOWNER approvals for breaking API changes; Renovate PRs auto-merge only patch/minor with passing tests.
  • Payment service hotfix: Standards allow single senior approver during SEV-1 with mandatory post-incident review of the diff within 24 hours.
  • Case study — Google-scale review culture: Public eng-practices docs describe continuous integration and small CLs as prerequisites for fast review; teams adopting the same author/reviewer split often report shorter cycle times without dropping defect detection.
