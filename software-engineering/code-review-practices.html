Code Review Best Practices

Effective code review processes that improve code quality, spread knowledge, and maintain team velocity without becoming a bottleneck.

⏱ 9 min read

What it is

Code review best practices are the habits and guardrails that make peer review useful at scale: keep changes small enough to read in one sitting, let CI enforce mechanical quality before a human looks, write PR descriptions that explain intent, and give feedback that improves code health without blocking velocity on taste. Review complements automated tests by catching design mistakes, missing edge cases, and knowledge gaps that machines cannot see.

Effective code review is as much a cultural practice as a technical one. The most rigorous process fails if it breeds adversarial dynamics, slows delivery until developers bypass it, or if reviewers rubber-stamp changes to avoid conflict. Google's internal research (Caitlin Sadowski et al., 2018) found that developers value review most for logic errors and knowledge sharing, not style — which belongs in linters and formatters. The Google Engineering Practices documentation codifies similar expectations for authors and reviewers: every change should leave the codebase in better shape than it found it.

Why it exists

Human review catches whole classes of failure that automation still misses: wrong invariants, race conditions buried in async code, authorisation gaps, and architectural drift. Formal inspection studies (IBM and others) showed large defect removal rates before test execution; contemporary engineering surveys (including Microsoft Research field work) echo that reviewers surface design flaws and fragile error paths tests never exercise. Review also distributes ownership—fewer modules depend on a single expert who happens to be on holiday when production breaks.

Organisations that measure delivery stability (DORA-style metrics) tie healthy review culture to lower change failure rates when reviews stay small and timely. The practice creates a social contract: authors explain intent in the PR, reviewers treat comments as collaboration rather than gatekeeping, and both sides assume the merge should leave the tree healthier than it was. That expectation nudges better naming, smaller commits, and tests written before review is requested—the “audience effect” that makes review a quality multiplier beyond defect spotting.

When to use

  • Every change destined for production, including one-liners—config typos and off-by-one fixes have taken down services.
  • Infrastructure-as-code diffs (Terraform, Pulumi, Helm, Kubernetes) where a missed dependency affects fleet-wide availability.
  • AuthN/AuthZ, crypto, PII handling, and input validation where mistakes become security incidents.
  • Versioned public or partner APIs where backward compatibility promises bind external consumers.
  • Onboarding mentorship—senior engineers review junior PRs with teaching comments and links to standards.
  • Boundary moves: new imports across modules, shared library changes, or database schema that couples services.

When not to use

  • Generated artefacts: Skip reviewing protobuf/Java stubs or ORM migrations emitted by tools; review the source schema, generator config, and regeneration pipeline instead.
  • Mechanical style: Prettier, Spotless, ESLint, and Ruff should enforce formatting; human cycles belong on behaviour and design.
  • Active incident response: During SEV-1, ship the fix, restore service, then schedule a blameless post-merge review within 24 hours.
  • WIP on private branches: Use draft PRs or skip review until the change is ready for feedback; noise erodes reviewer trust.

Typical architecture

A mature review pipeline runs automation first—lint, unit and integration tests, SAST, dependency scans—then assigns human reviewers only after green checks. The diagram shows author → CI → reviewer → merge; tooling enforces size guidelines and optional CODEOWNERS routing for sensitive areas.

Pros and cons

Pros

  • Surfaces logic defects, unsafe defaults, and hot-path regressions before they reach customers.
  • Rotates contextual knowledge so no single engineer becomes a single point of failure.
  • Raises the bar on clarity—authors anticipate questions and leave better commit messages and PR descriptions.
  • Aligns implementation with documented architecture and team conventions.
  • Preserves rationale in searchable PR threads when future maintainers ask “why this way?”

Cons

  • Queue time grows when reviewers juggle on-call and feature work without rotation.
  • Centralised “must review everything” rules stall teams that lack sufficient reviewer capacity.
  • Rubber-stamp approvals feel faster but erase the safety benefit entirely.
  • Unautomated style nitpicks consume attention better spent on invariants and threat models.
  • Hierarchical tone in comments discourages dissent and hides real risks junior engineers notice first.

Implementation notes

Right-size pull requests: Empirical studies (including SmartBear’s analysis of Cisco review data) show review quality falls sharply beyond roughly 300–400 changed lines per session. Treat that as a team norm, not a hard gate: stack small PRs behind feature flags, ship vertical slices, and use bots to comment when diffs exceed agreed thresholds. The goal is reviewer focus, not arbitrary line counting.

Comment conventions: Prefix intent—nit:, question:, suggestion:, or explicit blocking:—so authors triage quickly. The Conventional Comments taxonomy helps. Prefer curious questions (“What happens if this cache is cold?”) over commands unless policy is violated. Pair review with CODEOWNERS for security, payments, or shared libraries so the right expertise sees the diff early.

SLAs and load balancing: Publish expected first-response time (often one business day) and designate a daily review shepherd who clears the queue. Track time-to-first-review and time-to-merge; chronic breaches usually mean staffing or PR size problems, not reviewer laziness.

Empirical review data—Google’s eng-practices guidance and SmartBear’s Cisco study—shows effectiveness drops past a few hundred lines per session; default to stacked PRs and feature flags instead of mega-diffs. Use CODEOWNERS so security and platform paths get the right eyes early. Delegate formatting and lint to CI; humans focus on design and invariants per code review standards. Stacked or dependent PRs (Graphite, ghstack, or documented merge queues) keep each reviewable chunk green while preserving a coherent feature narrative.

Dashboard review latency weekly: median time-to-first-comment and time-to-merge expose bottlenecks earlier than retrospective complaints about “slow culture.”

Rotate review shepherd duty so one senior does not become the permanent bottleneck for every team. Pair with office hours for authors blocked on feedback.

Common failure modes

  • Rubber-stamping: Approving without reading because velocity KPIs punish wait time—worse than no review because CI green looks like full diligence.
  • Approval inflation: Requiring many unrelated sign-offs diffuses accountability; two informed reviewers beat five drive-by LGTMs.
  • Manual linting in comments: Debating tabs vs spaces while missing a missing null check—automate the boring parts.
  • Rotting branches: PRs idle for days accumulate conflicts and forgotten context; close or rebase aggressively.
  • Humans as CI: Assigning reviewers before tests pass wastes attention on compile errors bots should catch.
  • Drive-by refactors: Mixing unrelated cleanup in a feature PR forces reviewers to untangle behavioural vs structural changes.

Decision checklist

  • Did CI (lint, tests, security scans) complete successfully before reviewers were pinged?
  • Can a reviewer understand and verify this change in one focused session (target under ~400 lines)?
  • Did the author self-review, run tests locally, and attach screenshots or traces where relevant?
  • Does the description state user impact, rollout plan, and rollback path—not only file lists?
  • Are comments scoped to risk: blocking issues separated from optional nits?
  • Is there a published review SLA and an on-call rotation when the queue backs up?

Example use cases

  • Illustrative scenario — expand/contract migration: Database reviewers confirm expand-deploy-contract steps so old and new binaries coexist during rollout.
  • Illustrative scenario — Meridian Commerce onboarding: A new hire’s first three PRs pair with a mentor who leaves learning-oriented comments and links to internal standards.

Related patterns

  • Test-Driven Development — Green tests give reviewers executable proof of intended behaviour.
  • Technical Debt Management — When review approves known shortcuts, log them in the debt registry with owners.
  • API-First Development — Review the OpenAPI contract in its own PR before implementation lands.
  • Code Review Standards — Team checklists encode what reviewers must verify every time.
