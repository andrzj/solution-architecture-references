Domain-Driven Design

Eric Evans’s practice of modeling business language in code through strategic context maps and tactical aggregates, repositories, and domain events.

⏱ 12 min read

What it is

Domain-Driven Design (DDD) is Eric Evans’s approach to building software around a rigorously shared business model, split into strategic design (bounded contexts, context maps, core/supporting domains) and tactical design (entities, value objects, aggregates, repositories, domain events) inside each context.

The method treats domain complexity—not framework churn—as the primary design risk. Developers and domain experts coin a ubiquitous language reflected in class names, events, and workshop artifacts so that code, tests, and conversation use the same words for the same concepts. Evans’s 2003 book argues that when the model and language diverge, projects stall; when they align, refactors track real policy changes instead of accidental schema drift.

Why it exists

Three-tier templates encouraged “entity” classes with getters while “service” layers swelled with every conditional the business invented. Evans saw that layout as procedural code wearing OOP syntax—rules scattered, invariants undocumented, and tests exercising databases instead of policies. DDD recenters invariants inside the model so a Money value object rejects currency mismatch and an Order aggregate refuses shipment without payment capture.

Large enterprises also reuse terms with incompatible meanings: “account” in sales differs from “account” in finance. Strategic DDD accepts polysemy instead of forcing one enterprise data model. Bounded contexts publish explicit relationships—partnerships, customer–supplier, anti-corruption layers—so integrations translate deliberately rather than leak legacy nouns into greenfield services.

When to use

  • Domains whose rules change often and cannot be expressed as generic create-read-update-delete screens.
  • Products where multiple teams own different subdomains and need stable, published integration contracts.
  • Systems expected to outlive several rewrites and must preserve institutional knowledge in the model.
  • Monolith decomposition efforts that need semantic—not purely technical—service boundaries.
  • Regulated or revenue-critical flows where incorrect state transitions have measurable cost.
  • Organizations that can place domain experts in recurring modeling sessions with engineers.

When not to use

  • Thin CRUD products: Admin portals that mirror tables rarely justify aggregate design workshops.
  • Pre–product-market fit startups: Context splits crystallize assumptions that pivoting invalidates weekly.
  • Teams modeling alone: Without experts, ubiquitous language devolves into guessed jargon.
  • Pure infrastructure code: Compilers, drivers, and build tools have no business domain to discover.

Typical architecture

Strategic DDD draws how bounded contexts publish language and data; tactical DDD keeps invariants inside aggregates so each context can evolve its model without dragging neighbors along.

Pros and cons

Pros

  • Executable models let product owners read tests and workshops instead of decoding SQL.
  • Context boundaries align with team ownership and published APIs or events.
  • Aggregate roots serialize consistency decisions and shrink transactional footprints.
  • Ubiquitous language lowers miscommunication during audits and compliance reviews.
  • Domain events integrate contexts without shared tables or nightly ETL coupling.

Cons

  • Event storming, context mapping, and modeling iterations consume calendar time up front.
  • Tactical patterns are easy to mis-size—mega-aggregates and repository leaks are common mistakes.
  • Simple domains pay ceremony tax for patterns they never exercise.
  • Expert availability often vanishes after launch, letting language drift unchecked.
  • Delivery pressure revives anaemic entities when teams chase screen-count over invariants.

Implementation notes

Aggregate sizing: Evans treats the aggregate as a consistency island entered only through its root. Order lines belong inside Order because totals and quantities must move atomically; Customer stays outside as an ID reference because buyers outlive individual carts. Keep graphs small so locks release quickly and sagas handle cross-aggregate workflows.

Strategic relationships: Document how contexts cooperate. Shared Kernel shares code but demands joint review. Customer–Supplier links give downstream teams input while upstream retains veto. Anti-corruption layers translate hostile legacy schemas before they infect nouns. Open Host Service plus Published Language (versioned REST or async contracts) scales fan-out without pairwise negotiations.

Modeling cadence: Brandolini’s EventStorming supplies orange stickies for domain events, hot spots for policy debates, and aggregates as command handlers. Revisit maps quarterly; contexts evolve when org structure or regulation shifts.

Application layer boundaries: Application services orchestrate transactions, authorization, and infrastructure calls but should not host business rules that belong in the domain model. When you catch yourself encoding discounts inside a service class, move the policy into an entity or domain service and leave the application layer to fetch, invoke, and publish results.

Read models may denormalize for queries, yet command paths should still load only the aggregate roots required for the transaction. That split keeps write models honest while CQRS-style projections serve dashboards without bloating roots.

Strategic design starts with bounded contexts and a context map: customer–supplier, conformist, anti-corruption layer, shared kernel, and open-host relationships describe how teams negotiate language and data. Event storming surfaces domain events, commands, and hotspots before code exists. Ubiquitous language must appear in APIs, events, and tests—not only workshops. Integration events cross boundaries; domain events stay inside until translators publish outward. Tactical aggregates, repositories, and ACL implementation patterns live in DDD tactical patterns so this page does not duplicate coding recipes.

Core versus supporting subdomain investment guides staffing: pour modeling effort where competitive advantage lives, integrate commodity capabilities with ACLs instead of perfect internal models.

Revisit context maps when teams reorganize—structure drift is the main reason integrations suddenly need new ACL translations.

Common failure modes

  • Anaemic entities: Services grow while entities mirror tables, erasing the benefit of modeling.
  • Cart-sized aggregates: Loading entire customer histories per request creates contention and timeout retries.
  • Shared databases: Two contexts writing the same tables reintroduce the monolith you were escaping.
  • Language drift: UI copy, Jira epics, and code diverge because nobody owns glossary updates.
  • One-off storming: A single workshop poster rots on the wall while sprints ignore newly discovered events.
  • Context-free microservices: Services split by team headcount but share one database schema recreate distributed monolith coupling.
  • Integration events as commands: Publishing “create invoice” events that bypass aggregate invariants in the billing context lets consumers invent illegal states.

Decision checklist

  • Can you articulate non-trivial rules that justify modeling workshops instead of scaffolding CRUD?
  • Are domain experts scheduled with the same regularity as sprint planning?
  • Have you mapped commands, events, and policies collaboratively—not only in architecture documents?
  • Do context lines follow linguistic boundaries rather than package names or database schemas?
  • Can each aggregate enforce its invariants without live queries to sibling roots?
  • Do repositories and application services speak the same ubiquitous language as executives?

Example use cases

  • Illustrative scenario — Northwind Retail splits Catalogue, Inventory, Checkout, Fulfilment, and Billing contexts, each redefining “product” and “customer” locally while events synchronize stock.
  • Illustrative scenario — A hospital platform models patients, scheduling, clinical pathways, and revenue cycle as separate contexts linked by HIPAA-aware ACLs.
  • Illustrative scenario — An insurer publishes underwriting decisions as events consumed independently by claims and reinsurance services.
  • Case study — Evans’s Domain-Driven Design narratives (shipping, payroll, cargo routing) remain the canonical strategic and tactical walkthrough.
  • Case study — Fowler’s bliki on DDD and bounded contexts distills the approach for architects bridging business and engineering.

Related patterns

  • Microservices — Service boundaries gain legitimacy when they wrap a bounded context’s language and data.
  • Event Sourcing — Event-sourced stores persist the same domain events aggregates already raise.
  • CQRS — Separate read models relieve aggregates from supporting every dashboard query.
  • SOLID Principles — Aggregates and repository ports exemplify SRP and DIP inside a context.
