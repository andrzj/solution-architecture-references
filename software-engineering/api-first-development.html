API-First Development

A development approach where the API contract is designed and agreed upon before any implementation begins, enabling parallel development and treating APIs as first-class products.

⏱ 10 min read

What it is

API-first development designs and agrees the HTTP (or RPC) contract before implementation begins. Teams express that contract in machine-readable form—most often OpenAPI 3.x for REST—review it with consumers, then build backends and clients in parallel against the same artifact. The spec is the source of truth for paths, schemas, authentication, pagination, and error shapes; code implements the spec rather than the spec trailing undocumented behaviour.

The approach treats APIs as products with explicit consumers, versioning, and stability guarantees. Design starts from the client’s needs—what resources, fields, and failure modes integrators depend on—then wires persistence and domain logic underneath. Mock servers generated from OpenAPI (Prism, Microcks) give frontends and partners a stable target while backends catch up. Contract tests and Spectral linting in CI keep implementation and documentation aligned over time.

Why it exists

When backends lead, contracts reflect persistence shapes and framework defaults—not what clients need. Frontends integrate late, discover awkward pagination and error payloads, and force rework once code is merged. Auto-generated “documentation” from controllers describes accidental behaviour, not promises integrators can rely on. Parallel work stalls because every consumer waits on a moving endpoint list.

Microservices and multi-channel clients multiply the blast radius of breaking changes. API-first inverts the sequence: agree the contract while design is cheap, mock it for parallel builds, and enforce alignment in CI so integration week is not a negotiation marathon. Governance boards and partner programmes need that stability—published specs are product artefacts, not afterthought PDFs.

Contract-first also improves security review: auth schemes, scopes, and rate limits are visible before implementation hardens accidental endpoints. Performance discussions—pagination limits, bulk operation caps, idempotency keys—happen on the spec diff where they are cheap to adjust, not after load tests discover unbounded queries.

When to use

  • Split frontend and backend teams shipping on the same milestone.
  • External or partner APIs with explicit SLA and versioning commitments.
  • Service boundaries where each team’s HTTP/RPC surface is the integration contract.
  • Multiple clients (web, mobile, partners) sharing one backend contract.
  • Organisations running Pact or similar consumer-driven contract verification.
  • API review boards that must approve design before implementation headcount is spent.
  • Regulated APIs where auditors expect versioned, reviewable contract artefacts.

When not to use

  • Single team, single client: A lightweight README plus types in code may suffice without full OpenAPI ceremony.
  • Discovery spikes: During domain exploration, prefer short-lived prototypes; codify the contract once nouns stabilise.
  • GraphQL services: Schema-first GraphQL already embodies the principle; use GraphQL SDL tooling instead of OpenAPI.
  • Events and streams: Model contracts in AsyncAPI (or CloudEvents schemas), not HTTP-centric OpenAPI alone.

Pros and cons

Pros

  • Shortens calendar time by decoupling client and server schedules.
  • Design review surfaces naming, pagination, and idempotency issues early.
  • Mocks give designers and mobile engineers a deterministic backend surface.
  • One spec feeds portals, SDK generation, and compliance evidence.
  • Style linting spreads consistent error shapes and security headers org-wide.

Cons

  • Up-front modelling delays first line of code—requires discipline to keep specs lean.
  • Without response validation in CI, specs become historical fiction.
  • OpenAPI cannot express every constraint (hypermedia, streaming, rich polymorphism).
  • Toolchain setup (mocks, generators, brokers) has ongoing maintenance cost.
  • Cultural shift: engineers must treat the spec PR as the first merge, not the last.

Implementation notes

Spec in Git: Store openapi.yaml beside the service (or in a contracts repo). Lint with Spectral or Vacuum against organisational rules—naming, pagination, error envelope, auth schemes. Publish Prism or Microcks mocks to preview environments on every spec merge. Generate server interfaces and typed clients with openapi-generator or Kiota; validate responses in staging via middleware such as openapi-validator or Springdoc’s response validator.

Pact in the loop: Consumers record minimal interactions they rely on; the broker stores versioned contracts. Provider builds verify all consumer contracts before deploy. This complements—not replaces—OpenAPI: the spec declares the full surface; pacts pin the subset each consumer actually uses.

Versioning: Choose URL, header, or media-type versioning before launch; document deprecation windows in the spec and enforce via gateway policies.

Governance hooks: Run design review on the spec PR with API council or security representatives present. Record breaking changes in changelog fragments linked from the spec repo. For internal meshes, register each version in a service catalogue so callers know which contract SHA they validated against.

Treat OpenAPI and AsyncAPI as the contract source of truth: lint with Spectral or Vacuum in CI, stand Prism or Microcks mock servers from the same spec consumers will call, and fail builds when examples drift. Codegen accelerates typed clients but hides breaking field renames—regenerate in CI and diff. Prefer hand-authored specs for public APIs; annotation-generated specs often encode accidental MVC shapes. Pair mock-backed consumer development with contract tests so runtime behaviour stays pinned beyond JSON Schema validity.

Publish AsyncAPI for event contracts with the same rigour as REST: lint, version, and generate consumers. Store specs next to implementing services so every gateway route traces to a reviewed schema hash.

Version consumer SDKs from the same spec tag your gateway deploys so mobile and web never ship against an unreviewed draft.

Common failure modes

  • Reverse-engineered specs: Generating OpenAPI from annotations after coding locks in accidental APIs.
  • No response validation: Request-only checks let response drift break mobile clients silently.
  • Leaky DTOs: Exposing internal database columns couples consumers to schema refactors.
  • Happy-path only: Undocumented 4xx/5xx bodies leave clients guessing on retries and UX.
  • Version sprawl: Uncontrolled /v2 forks without sunset dates multiply operational load.
  • Hand-written clients only: Skipping generated SDKs lets mobile and web teams invent incompatible error handling.

Decision checklist

  • Was the contract reviewed and merged before controller code?
  • Does CI fail when responses violate the published schema?
  • Do all clients have a mock or stub generated from the same commit SHA?
  • Are auth, rate-limit, and error models documented for every operation?
  • Does Spectral (or equivalent) enforce naming, pagination, and security baselines?
  • For external consumers, are broker-published pacts verified on provider mainline?

Example use cases

  • Illustrative scenario — RideRelay launch: Week-one OpenAPI stabilises trip booking fields; iOS and web ship against Prism while JVM services implement behind contract tests.
  • Illustrative scenario — partner portal: Published spec plus Pact gates prevent accidental field removal on the B2B catalogue API.
  • Illustrative scenario — internal catalogue: Each microservice commits its spec; Backstage ingests versions so staging calls validate against the declared contract.
  • Illustrative scenario — webhook API: Async callbacks are documented in OpenAPI with signed payload schemas before the worker fleet implements handlers.
