SOLID Principles

Robert C. Martin’s five cohesion and coupling rules for object-oriented modules that stay testable as requirements shift.

⏱ 12 min read

What it is

SOLID is Robert C. Martin’s mnemonic for five object-oriented design rules—Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion—that keep modules cohesive, decoupled, and safe to extend.

Martin framed them in Design Principles and Design Patterns and later chapters of Agile Software Development as practical antidotes to the rigidity, fragility, immobility, and viscosity he saw in large C++ and Java programs. Each letter names a distinct failure mode: monolithic classes, edit-everywhere feature work, broken polymorphism, fat interfaces, and upward dependencies on databases or frameworks.

SRP says a module should answer to one actor—not necessarily one method. OCP favors adding behavior through new types instead of editing proven ones. LSP demands that subtypes honor the behavioral contract callers relied on when they programmed to the base type. ISP splits interfaces so clients depend only on operations they invoke. DIP places abstractions at the center so policy code never imports concrete infrastructure. Used together, the set yields classes that unit-test quickly because collaborators are swappable behind narrow ports.

Why it exists

Industrial OOP teams kept rediscovering the same change-tax: touch payment logic and suddenly tax, email, and SQL schema edits cascade. Martin’s early essays catalogued that pain as design rot and argued that most of it traced to accidental coupling—services that knew too much about persistence, entities that formatted reports, and interfaces grown without regard for who called them.

SOLID gave reviewers a shared vocabulary drawn from hard-won experience on billing, payroll, and telephony systems. The principles do not mandate patterns for their own sake; they explain why Strategy beats a growing switch statement (OCP), or why a repository interface belongs next to domain code (DIP). That alignment shows up in test suites: when constructors pull in ten concrete types, SRP and DIP violations are usually nearby.

When to use

  • Domain models whose rules will keep changing after the first release and must stay readable during refactors.
  • Published libraries or internal SDKs where semver stability depends on narrow, intention-revealing public surfaces.
  • Codebases with aggressive unit-test coverage where constructors should accept interfaces, not JDBC drivers.
  • Cross-team products that need a common review lexicon—naming an ISP violation is faster than debating ad hoc style.
  • Legacy extraction efforts where mapping pain to SRP, OCP, or DIP suggests the next safe refactor slice.
  • Products whose expected lifetime exceeds a single framework generation.

When not to use

  • One-shot scripts and spikes: Wrapping a fifty-line ETL script in abstract factories buys indirection without a second implementation on the horizon.
  • Pure DTOs and serializers: Anemic carriers for JSON or CSV rarely gain from extra interfaces; keep them thin.
  • Nanosecond hot loops: Virtual calls through deep interface stacks can cost more than the algorithm they protect in tight numeric kernels.
  • Micro utilities: A helper under a few hundred lines does not need a DI container to justify its existence.

Typical architecture

Martin’s letters stack from class-level focus through substitutability and interface shape to dependency direction; reviewers often walk this sequence when a module feels hard to test or extend.

Pros and cons

Pros

  • Constructors accept interfaces, which makes mocks trivial and speeds feedback from fast unit tests.
  • Smaller reasons-to-change shrink regression surfaces when product tweaks land weekly.
  • Teams can own abstractions in parallel because merge conflicts concentrate at composition roots.
  • Stable ports become shared packages other products import without dragging ORM annotations.
  • Review comments cite Martin’s letters instead of debating subjective taste.

Cons

  • Dogmatic ISP can sprout interfaces with one method and no second implementor—YAGNI with extra files.
  • More types mean newcomers trace indirection before they see business rules.
  • Stack traces bounce through adapters, which slows printf debugging until logging is disciplined.
  • Choosing the right abstraction early costs design time when change directions are still fuzzy.
  • Premature OCP—extension points nobody uses—freezes APIs that a simple edit could have fixed.

Implementation notes

SRP by actor: Martin’s payroll example ties change to the CFO, COO, and CTO—not to method count. Split Employee into payroll calculation, printable views, and persistence gateways so each stakeholder can evolve independently. TypeScript might expose PayrollCalculator, EmployeeReportBuilder, and EmployeeRepository as three injectable collaborators.

OCP with Strategy: Replace growing if (gateway === "visa") chains with a PaymentProcessor port and one class per gateway. Shipping Square support becomes a new type in the composition root, not a risky edit inside a thousand-line method. Spring or Nest DI wires the list of processors without reopening stable classes.

LSP and DIP: The Rectangle–Square hierarchy still teaches LSP: callers that set width and height independently break when a subtype couples the setters. For DIP, OrderService lives in domain packages and depends on OrderRepository defined beside it; the MySQL adapter implements that port from an outer layer and never pulls domain types toward JDBC imports.

ISP splits fat interfaces so clients depend only on methods they call; a single Storage god-interface forces irrelevant upload APIs on read-only consumers. Dogmatic SOLID—five classes for a script—wastes time; apply when change vectors multiply. Concrete violations matter: a service that reads files, sends email, and calculates tax breaks SRP; fixing it is usually extraction, not a pattern slide deck. When structure needs a named pattern, see design patterns for Strategy and Adapter examples that satisfy OCP and DIP in practice.

Liskov failures often appear in test doubles—stubs that throw on “unexpected” calls break substitutability. Keep interfaces narrow enough that mocks represent realistic consumers.

DIP violations often look like `import sqlalchemy` in domain modules—grep for framework imports in inner layers in CI.

Common failure modes

  • Grab-bag utilities: Static helper classes that format strings, parse dates, and send email serve every actor and violate SRP while looking harmless.
  • OCP as ban on edits: Bug fixes spawn subclass stacks because policy forbids touching “closed” classes.
  • LSP by exception: Subtypes that override methods to throw UnsupportedOperationException tell callers the base contract was a lie.
  • God interfaces: Twenty-method service interfaces force fakes to implement noise, hiding which operations a test actually exercises.
  • Interfaces beside implementors: Putting ports only in the infrastructure module inverts DIP—domain code ends up referencing concrete packages.

Decision checklist

  • Can you name the single stakeholder or policy area that would force each class to change?
  • Would a new discount or payment rail ship as a new type rather than edits across five files?
  • Do integration tests still pass when you substitute fakes or alternate subtypes for production classes?
  • Does each client see an interface sliced to the methods it calls—no unused operations?
  • Do domain packages compile without imports from framework, driver, or HTTP adapter packages?
  • Are ports declared in the module that calls them, not only where SQL lives?

Example use cases

  • Illustrative scenario — Harbor Checkout isolates tax in its own service (SRP), registers payment processors behind a shared port (OCP + DIP), and exposes read-only order queries through a slim interface (ISP).
  • Illustrative scenario — A compliance reporting tool adds CSV and PDF renderers as new classes while a report builder assembles datasets once (SRP + OCP).
  • Illustrative scenario — An auth microservice stores tokens behind TokenStore; Redis and in-memory fakes swap without changing AuthService (DIP + LSP).
  • Case study — Martin’s original Design Principles and Design Patterns paper walks payroll and shape examples that motivated SRP and LSP.
  • Case study — Fowler’s Beck Design Rules essay pairs simple OO heuristics with SOLID for teams calibrating how strict to be.

Related patterns

  • Design Patterns — Gamma, Helm, Johnson, and Vlissides catalog structures such as Strategy and Decorator that embody OCP and DIP in daily code.
  • Domain-Driven Design — Evans’s bounded contexts carry SRP to the team level: one model, one ubiquitous language per context.
  • Test-Driven Development — Kent Beck’s red-green-refactor loop surfaces untestable constructors long before production.
  • Refactoring Patterns — Extract Class and Introduce Interface are the mechanical steps toward SOLID without big-bang rewrites.
