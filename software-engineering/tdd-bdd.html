TDD & BDD

TDD shapes code with fast unit examples; BDD aligns product and engineering with executable Given/When/Then scenarios—use both at different layers.

⏱ 10 min read

What it is

Test-driven development (TDD) and behavior-driven development (BDD) are complementary practices for specifying software through examples before (or as) code is written. TDD, as Kent Beck described it, uses programmer-oriented unit tests in the red-green-refactor loop to shape APIs and domain logic. BDD, popularised by Dan North and the Cucumber community, expresses behaviour in business-readable Given / When / Then scenarios—often in Gherkin—so product, QA, and engineering share one executable specification.

Most mature teams combine them: TDD at the unit and component level for fast design feedback; BDD at acceptance boundaries for features stakeholders can read and sign off. Neither replaces the other—BDD without solid unit tests leaves logic holes; TDD without shared examples can build the wrong feature confidently.

Why it exists

Post-implementation testing validates what was built, not necessarily what was intended. TDD shortens the technical feedback loop; BDD shortens the requirements feedback loop by making examples conversation artifacts before implementation starts. Thoughtworks teams have long treated executable specifications as living documentation that reduces handoff ambiguity between “the spec” and “the code.”

BDD grew from noticing that unit test names were already mini-stories—North’s insight was to lift that language to a level non-developers could review. Cucumber, SpecFlow, and Behave connect those scenarios to automated checks via step definitions that call into the same domain code TDD exercises at finer granularity.

When to use

  • Features with acceptance criteria that product and engineering must agree on before build.
  • Regulated or audit-sensitive domains where human-readable evidence of behaviour is required.
  • Shared domain modules where TDD clarifies APIs and BDD anchors them to user-visible outcomes.
  • Regression-prone workflows (billing, eligibility, compliance) where examples double as guardrails.

When not to use

  • Pure spikes with no stable vocabulary yet—discover first, then capture examples.
  • BDD without collaboration—Gherkin written only by QA, never reviewed with product, becomes costly UI-duplicating tests.
  • Replacing unit TDD with slow end-to-end scenarios for every branch—keep the pyramid shape.
  • Low-level algorithm work where programmer tests are clearer than Given/When/Then ceremony.

Typical architecture

Acceptance scenarios sit above unit-level TDD loops; step definitions bridge readable examples to production code.

Pros and cons

Pros

  • Shared language between product, QA, and engineering reduces misunderstood requirements.
  • Two feedback loops—minutes at unit level, hours at acceptance—catch different defect classes.
  • Executable specs stay current when teams treat failing scenarios as blocking work.
  • TDD keeps scenario glue thin; complex rules stay testable in isolation.

Cons

  • Double investment in examples if layers duplicate the same assertions.
  • BDD tooling and step-definition maintenance add ceremony for small teams.
  • Flaky acceptance tests erode trust faster than flaky unit tests.
  • Poorly scoped scenarios become unreadable “Gherkin soup.”

Implementation notes

Write scenarios at the right altitude. Each scenario should describe one business rule or user outcome, not click paths through the UI. Push UI detail to unit or component tests unless the journey itself is the risk.

Keep step definitions thin. Steps call application services or domain APIs; avoid embedding selectors, SQL, or business rules in step files—those belong in code covered by TDD.

Three amigos / example mapping. Before coding, product, dev, and test (or QA) agree on examples for rules, questions, and edge cases. Capture the agreed examples in Gherkin or tables.

Tooling. Cucumber / Cucumber-JVM, SpecFlow (.NET), and Behave (Python) are common; pick one stack per repo. Run unit suites on every commit; run acceptance suites on PR or nightly depending on speed.

Deeper unit-level practice: Test-Driven Development.

Common failure modes

  • Implementation-detail scenarios: Tests break on refactors though behaviour is unchanged—assert on outcomes, not layout.
  • Absent product review: Scenarios encode developer assumptions nobody validated.
  • E2E-only BDD: Full-browser scenarios for every rule—slow, flaky; drive most rules at API or domain level.
  • Orphan step definitions: Unused steps and duplicate wording make suites unmaintainable.

Decision checklist

  • Did product and engineering review acceptance examples before implementation?
  • Are unit-level TDD tests covering rules scenarios do not need to repeat?
  • Can the acceptance suite finish within your PR CI budget?
  • Are step definitions free of business logic and duplication?
  • Does the team have a shared definition of “unit” vs “acceptance” test?

Example use cases

  • Illustrative scenario — A subscription billing service: unit TDD on proration math; Cucumber scenarios for “customer upgrades mid-cycle” signed off by finance and product.
  • Illustrative scenario — An eligibility API: Gherkin tables for jurisdiction rules; step definitions call the same pure functions unit tests exercise.
  • Case study — Cucumber’s BDD documentation describes how Given/When/Then scenarios align delivery with collaborative specification.
