DDD Tactical Patterns

Tactical DDD building blocks—aggregate roots, repositories, factories, domain events, and anti-corruption layers—in application code per Evans.

⏱ 10 min read

What it is

DDD tactical patterns are Eric Evans’s building blocks for expressing one bounded context in code—entities, value objects, aggregate roots, repositories, factories, domain services, and domain events—so invariants execute in the domain core rather than in HTTP handlers or generated persistence stubs.

Strategic partitioning and context maps appear in Domain-Driven Design; here the focus is execution detail inside a single context’s codebase. Tactical patterns answer where consistency stops, which port hides storage, and how downstream teams learn about facts without peering into your schema.

Why it exists

Renaming folders to domain while leaving thousand-line application services untouched produces “DDD theater.” Evans’s tactical vocabulary forces rules into constructible objects: value types fail fast at creation, roots arbitrate mutations, and repositories reload object graphs while SQL stays outside. That discipline makes regressions visible in focused unit suites instead of flaky integration runs.

Service decomposition needs the same rigor. A root delineates what you may edit inside one transaction; foreign keys become identifiers, not eager joins spanning teams. Sagas, process managers, and outboxes stitch multi-step stories without reintroducing shared tables. Tactical patterns therefore connect classroom DDD to deployable microservice seams.

When to use

  • Policies tie multiple fields together and must survive API or UI changes unscathed.
  • Command-side models append to event logs or rebuild CQRS read models from domain occurrences.
  • Strangler migrations need roots that align with team ownership and transactional ceilings.
  • Partner payloads require translation layers before enums infect entity naming.
  • Fast feedback demands domain tests that never open network sockets.
  • Workshop stickies for commands and events should map one-to-one to types in the repository.

When not to use

  • Generated admin screens that duplicate column constraints already enforced by the database.
  • Enterprise-wide aggregate designs that ignore bounded-context borders and recreate distributed monoliths.
  • Squads that will not groom ubiquitous language alongside sprint backlogs.
  • Greenfield utilities with no evolving business vocabulary to capture.

Typical architecture

Evans places an application layer outside the domain model: it coordinates use cases, loads roots by identifier, and commits transactional changes while infrastructure adapters implement repository and event ports.

Pros and cons

Pros

  • Workshop phrases become type names, so experts read pull requests like policy memos.
  • Roots demarcate where ORM sessions, version columns, and retry logic belong.
  • Past-tense events hand integration teams facts instead of database credentials.
  • Factories centralize valid birth stories for graphs too rich for constructors.
  • Translators quarantine vendor dialects before they rename your nouns.

Cons

  • Script-trained engineers must learn to push logic downward into entities.
  • Hot aggregates serialize writers; undersized graphs let invariants slip through cracks.
  • Without living glossaries, tactical names decay into meaningless suffixes.
  • Reporting queries smuggled through repositories blur persistence with presentation.

Implementation notes

Discover roots at concurrency pinch points—shared documents, carts, policies—not at one-table-per-entity defaults. External modules may hold references only to roots; nested entities stay encapsulated. Model attribute-defined concepts as immutable value types (TaxRate, SkuQuantity, PortCode) so invalid tuples never instantiate.

Define repository interfaces beside aggregates; adapters map rows to objects without surfacing SQL types upward. Use factories when defaults depend on tenant policy or feature flags. Record domain events only after persistence succeeds, then relay through transactional outbox tables to guarantee at-least-once delivery with idempotent consumers. Place anti-corruption translators in the infrastructure ring so HTTP clients never leak into entity methods.

Size aggregates for one transactional invariant—cart lines inside Order, not the entire customer history. Domain events express facts the business cares about inside the context; map them to integration events at the boundary so foreign teams never import your entity types. Ubiquitous language shows up in type and method names, not a glossary slide deck. Strategic bounded contexts, context-map relationships, and workshop cadence are covered in Domain-Driven Design; this article stays in the code.

Value objects validate invariants at construction; entities carry identity across mutations. Domain services hold cross-aggregate rules that do not belong on a single root without forcing artificial aggregates.

Integration tests should load aggregates through repositories the way production does, not short-circuit invariants via public setters.

Common failure modes

  • Company-wide root: A single aggregate serializes organizational writes and tanks throughput.
  • XA nostalgia: Two-phase commits across services hide missing saga choreography.
  • DTO repositories: Query APIs return screen-specific shapes, marrying UI refactors to persistence.
  • Premature publication: Emitting events before commit invites compensating workflows for ghosts.
  • Skipped translators: Entities that call REST clients directly import alien enums permanently.

Decision checklist

  • Does each mutation path load exactly one aggregate per business transaction?
  • Do value types enforce formatting and range rules at construction time?
  • Will illegal command attempts throw domain exceptions before flush?
  • Can subscribers tolerate duplicate events via idempotency keys?
  • Is every external feed normalized through a dedicated translator module?
  • Do pure domain tests finish in sub-second time on developer laptops?
