Test-Driven Development

Kent Beck’s red-green-refactor cycle: write a failing test first, implement the minimum to pass, refactor—driving design, living specs, and fast regression feedback.

⏱ 10 min read

What it is

Test-driven development (TDD) is a design practice in which you write an automated test that describes desired behaviour, watch it fail, write the smallest amount of production code that makes it pass, then refactor while keeping tests green. Kent Beck formalised the cycle as Red → Green → Refactor in Test-Driven Development: By Example and as a core practice of Extreme Programming. The loop is meant to run in seconds so design feedback stays inside the coding session.

TDD is primarily a design technique, not a post-hoc testing technique. Writing the test first forces outside-in thinking: what does the caller need, what are the inputs and outputs, and what should happen on failure? That pressure tends to produce smaller units, clearer boundaries, and APIs that are easy to substitute in tests. The growing test suite is a side effect—a living specification that catches regressions when you change code later.

Why it exists

When tests are written only after implementation, feedback arrives late (often days later in QA), and tests tend to mirror what the code already does rather than what stakeholders need. Beck’s motivation was to shorten the defect feedback loop and to make untestable designs painful early: if a test is hard to write, the design usually needs seams, dependency injection, or simpler responsibilities.

Teams that adopt TDD routinely report fewer production defects on changed code and safer refactoring, though the practice has an upfront learning cost. Martin Fowler’s TDD bliki and Thoughtworks’ guidance on test-driven development frame TDD as a habit that improves design and documentation, not as a coverage metric to game.

When to use

  • Domain logic with non-trivial rules, branches, and edge cases where behaviour must be specified precisely.
  • Libraries and internal APIs where the consumer-facing interface should be designed before implementation details.
  • Refactoring or modernising legacy modules—add characterisation tests, then change structure with confidence.
  • Bug fixes—reproduce the defect with a failing test first so the fix cannot regress silently.
  • Long-lived production code where automated regression nets pay back over many releases.

When not to use

  • Spikes and exploration when requirements and APIs are unknown; prototype freely, then rebuild with TDD or add tests once the shape stabilises.
  • Pure layout or visual design where pixel fidelity is better checked with visual regression tools or design review.
  • Code with no test seams in legacy systems—introduce seams (extract pure functions, inject dependencies) before strict test-first work; see Refactoring Patterns.
  • Broad integration concerns (database wiring, cross-service flows)—use integration tests and pyramid balance rather than forcing everything through the unit loop.

Typical architecture

The TDD loop is the architectural “shape” of the practice: each requirement slice moves through red, green, and refactor before the next example is added.

Pros and cons

Pros

  • Forces testable design—collaborators you cannot substitute in a test signal coupling problems early.
  • Short feedback loop keeps defects local to the change that introduced them.
  • Tests document intended behaviour in executable form for reviewers and future maintainers.
  • Builds a regression net incrementally, enabling fearless refactors on mature modules.
  • Encourages small commits aligned with one behaviour at a time.

Cons

  • Slower apparent velocity while the team learns the discipline and test design skills.
  • Easy to write brittle tests that assert internals instead of observable behaviour.
  • Heavy mocking can hide broken collaborations between real components.
  • Unit-level TDD alone does not prove wiring, schema, or cross-service compatibility.
  • Can be misapplied to UI-only or I/O-heavy layers where other test types fit better.

Implementation notes

One behaviour per test. Name tests after the scenario (should_reject_expired_coupon) and prefer arranging inputs, exercising the public API, and asserting on outputs or state—not on private methods or call order unless that order is itself the contract.

Keep the loop fast. Unit tests should run in milliseconds; the module suite should finish in seconds on a laptop so developers run it continuously. Push database, HTTP, and filesystem work to the integration layer described in Test Pyramids.

Complementary techniques. Property-based tools (Hypothesis, fast-check, jqwik) express invariants across many generated inputs. Mutation testing (PIT, Stryker) checks whether tests actually fail when logic is perturbed—a low mutation score usually means weak assertions.

Outside-in vs inside-out. Beck’s unit-level TDD often starts inside-out on domain objects; acceptance-level examples (see TDD & BDD) can drive the same cycle from user-visible behaviour downward.

Common failure modes

  • Skipping refactor: Green-phase code accumulates duplication and unclear names; schedule refactor before the next red test.
  • Testing the mock: Over-stubbed tests pass while real integrations fail in staging.
  • Test after the fact: Post-hoc tests confirm implementation quirks and miss missing requirements.
  • Large steps: Adding many behaviours in one red-green cycle makes failures hard to diagnose—slice smaller.
  • Slow suite: When unit tests hit network or disk, developers stop running them and the practice collapses.

Decision checklist

  • Is the next test written before production code for this behaviour?
  • Does the test exercise a public surface and assert on observable outcomes?
  • Can the unit suite run locally in a few seconds without external services?
  • After green, did you refactor names and structure before moving on?
  • Are integration and contract tests covering wiring this unit test cannot see?
  • Would mutation testing or property-based checks strengthen weak examples?

Example use cases

  • Pricing rules engine: Each discount rule is introduced as a failing example before calculation code exists; refactors extract shared predicates without changing behaviour.
  • State machine module: Illegal transitions are specified as failing tests before transition handlers are implemented.
  • Case study — Kent Beck’s Test-Driven Development: By Example walks through money and xUnit examples using the red-green-refactor rhythm end to end.
