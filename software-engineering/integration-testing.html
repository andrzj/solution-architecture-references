Integration Testing

Integration tests prove wiring with real databases, brokers, and HTTP—faster than E2E, broader than unit tests—usually with Testcontainers in CI.

⏱ 10 min read

What it is

Integration testing verifies that components work together correctly—application code with a real database, HTTP client with a running process, message handler with a broker—without exercising the entire product through the UI. It sits in the middle of the test pyramid: slower and broader than unit tests, faster and more targeted than full end-to-end journeys.

Effective integration tests use ephemeral dependencies (Testcontainers, in-memory brokers, localstack-style emulators) so each pipeline run owns its infrastructure. They answer questions unit tests cannot: Did the migration match the ORM mapping? Does serialization round-trip across the wire? Will the consumer’s timeout break the provider’s thread pool?

Why it exists

Unit tests isolate logic with doubles; they deliberately do not prove wiring, schema, network configuration, or permission boundaries. Pure E2E tests can catch those faults but at high cost—shared staging queues, flaky browsers, and slow feedback. Thoughtworks’ testing material recommends a strong integration layer so teams detect contract and persistence failures in minutes, not after a multi-service deploy.

Microservices and modular monoliths multiply integration surfaces. A disciplined middle layer reduces reliance on “everyone in one environment Friday afternoon.”

When to use

  • Repository and ORM code against the same database engine used in production.
  • HTTP APIs bootstrapped in-process with a real test database or embedded server.
  • Message consumers and producers against embedded or containerised brokers (Kafka, RabbitMQ, SQS emulators).
  • Auth, caching, and middleware chains where order and configuration matter.
  • After unit TDD on domain logic—to prove modules collaborate correctly.

When not to use

  • Re-testing every branch already covered by fast unit tests—integrate at boundaries, not duplicate logic assertions.
  • Shared long-lived staging as the only integration path—serialises teams and hides data pollution issues.
  • Replacing contract tests for cross-team API evolution—use both.

Typical architecture

Integration tests slot between isolated unit tests and a small E2E set.

Pros and cons

Pros

  • Catches schema, protocol, and configuration errors units miss.
  • More stable and faster feedback than full-stack UI tests.
  • Runnable on every PR when dependencies are containerised.
  • Documents realistic deployment assumptions (ports, credentials, migrations).

Cons

  • Slower than unit tests; CI needs CPU for containers.
  • Fixture and seed data mistakes cause order-dependent failures.
  • Can become mini-E2E suites if scopes creep unchecked.
  • Requires discipline to reset state between tests.

Implementation notes

Testcontainers pattern. Spin up Postgres, Kafka, Redis, or cloud emulators per test class or suite; wait on health checks before assertions. Parallelise by using separate database schemas or containers per worker.

State hygiene. Prefer transactional rollback, fresh schema per class, or truncation scripts—never assume execution order. Tag slow tests (@Tag("integration")) so developers run a fast subset locally.

Scope one collaboration per test. When a failure appears, you should know which integration broke—avoid multi-hop journeys better suited to E2E or contract tests.

CI resources. Cache container images, reuse Ryuk-disabled patterns only when you understand cleanup trade-offs, and cap parallelism to avoid Docker thrash on small runners.

Common failure modes

  • Shared staging bottleneck: Teams queue for one environment—move dependencies into pipeline-isolated containers.
  • Dirty data: Tests pass individually but fail in suite—isolate data per test method.
  • Over-broad integration tests: Multi-service flows that belong in contract or E2E layers.
  • No health gating: Flaky starts because tests race dependency readiness.

Decision checklist

  • Does CI provision dependencies automatically without manual staging?
  • Can developers run the integration subset locally with one command?
  • Is each test scoped to a single collaboration boundary?
  • Are fixtures isolated so order does not matter?
  • Do contract tests cover cross-team APIs this suite should not duplicate?

Example use cases

  • Illustrative scenario — An order API: Spring Boot test slice with Testcontainers Postgres, HTTP client exercises create/read paths; runs parallel to the unit job in under two minutes.
  • Illustrative scenario — A payment webhook consumer: embedded Kafka container, asserts idempotent handling when duplicate events arrive.
  • Case study — Testcontainers is widely used to bring production-like dependencies into integration tests without shared staging.
