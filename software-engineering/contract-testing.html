Contract Testing

Consumer-driven contracts (Pact) verify API compatibility without full integration stacks—publish pacts, verify providers, gate deploys with can-i-deploy.

⏱ 10 min read

What it is

Contract testing verifies that a service provider’s behaviour matches what its consumers depend on, without standing up every dependent system in one integration environment. A contract records the requests, responses, or message shapes a consumer actually uses; tests run on the consumer against a mock and on the provider against recorded interactions or a published spec.

Consumer-driven contracts (Pact is the common toolchain) let consumers publish examples; providers replay them in CI. Provider-driven approaches anchor on OpenAPI or AsyncAPI and tools such as Schemathesis or Dredd. Bi-directional setups compare consumer pacts to provider OpenAPI in a broker. See also API Design — Contract Testing for API-focused detail.

Why it exists

Microservices deploy independently; full-stack integration environments do not scale to dozens of teams and versions. Ian Robinson’s consumer-driven contracts essay (Martin Fowler’s site) and Thoughtworks’ promotion of the technique address a specific question: Will this provider version break a consumer already in production? Pact’s broker and can-i-deploy gate answer that in seconds per service.

Contract tests complement—not replace—unit and integration tests. They excel at boundary compatibility; they do not prove end-to-end workflows or performance.

When to use

  • Internal REST, GraphQL, or message APIs with multiple consuming teams.
  • Continuous deployment pipelines where provider and consumer release on different cadences.
  • Organisations willing to run a Pact Broker (or PactFlow) and provider verification jobs.
  • APIs already described in OpenAPI where provider-driven verification adds a safety net.

When not to use

  • Monoliths where all callers ship in one artifact—in-process tests suffice.
  • Prototypes without stable interfaces or external consumers.
  • Teams that publish consumer pacts but never verify on the provider—false confidence.

Typical architecture

Consumers publish contracts; providers verify against the broker before deploy promotion.

Pros and cons

Pros

  • Fast feedback on breaking API changes before integration environments catch them.
  • Documents what consumers actually use—not the entire provider surface.
  • Enables independent deployment when paired with broker gates.
  • Reduces need for multi-team shared staging for every PR.

Cons

  • Broker, provider states, and CI wiring add operational overhead.
  • Requires adoption on both sides of each boundary.
  • Covers exercised interactions only—untested routes can still break.
  • Provider state setup for data-heavy interactions is tedious to maintain.

Implementation notes

Use matchers, not literals. Pact contracts should express types and formats (like, term, regex) rather than ephemeral values so harmless data changes do not fail verification.

Provider verification in CI. Every main-branch build of the provider should fetch relevant consumer pacts from the broker and fail on mismatch. Publish verification results back to the broker.

can-i-deploy. Before promoting a version to production, ask the broker whether that provider build is compatible with consumer versions already deployed—wire this as a required pipeline stage.

Versioning and retention. Tag pacts with consumer version (git SHA or semver); prune obsolete pacts so stale contracts do not block providers unnecessarily.

Smoke E2E. Keep a handful of journey tests for irreducible cross-service risk; let contracts handle pairwise compatibility.

Common failure modes

  • Exact-value contracts: Brittle pacts break on valid provider responses.
  • Stale broker entries: Deleted consumer tests leave orphan pacts—enforce retention policies.
  • Missing provider states: Verification fails because setup data does not match interaction preconditions.
  • Contracts without provider job: Consumers green while providers ship breaking changes.

Decision checklist

  • Do consumer tests publish pacts on every relevant PR?
  • Is provider verification mandatory on main before deploy?
  • Are matchers used instead of hard-coded field values?
  • Does CI call can-i-deploy (or equivalent) per environment?
  • Are provider state handlers documented and owned by the provider team?

Example use cases

  • Illustrative scenario — Checkout calls inventory over HTTP: consumer pact asserts response shape; provider verification fails when a field is removed; deploy blocked until fixed or coordinated.
  • Illustrative scenario — An event publisher and two subscribers use message pacts; broker shows which consumer versions each provider build satisfies.
  • Case study — Pact documentation describes broker workflows, provider verification, and can-i-deploy.
