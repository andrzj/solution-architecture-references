Software Engineering

Design Patterns

The Gang of Four’s catalog of twenty-three recurring object structures—creational, structural, and behavioral—with intent, trade-offs, and when not to force them.

⏱ 12 min read

What it is

Design patterns are named, reusable micro-architectures for recurring object-oriented problems, documented by Gamma, Helm, Johnson, and Vlissides in Design Patterns: Elements of Reusable Object-Oriented Software (1994) as twenty-three solutions sorted into creational, structural, and behavioral families.

Every catalog page lists intent, motivation, applicability, structure, participants, collaborations, consequences, and sample sketches—patterns are prose templates, not Maven artifacts. Teams win when names travel: “Adapter on the vendor SDK” or “Chain of Responsibility in the pricing pipeline” anchors design reviews faster than redrawing UML from scratch. Concrete syntax shifts between languages, yet roles such as Subject, Observer, and ConcreteStrategy remain portable vocabulary.

Why it exists

GUI toolkit authors in the late 1980s independently built extension hooks, notification buses, and wrapper stacks; application developers duplicated the same shapes under different class names. Gamma, Helm, Johnson, and Vlissides mined Smalltalk, C++, and framework codebases—Interviews, ET++—to canonize those recurring collaborations so textbooks and reviews could refer to one pattern language.

When forces align, patterns shorten debate: a documented Builder flow moves stand-ups past constructor arguments toward domain defaults. They also flag hazards—Singleton documents global coordination assumptions; long Decorator chains foreshadow opaque stack traces. Contemporary guidance still invokes GoF when describing Nest middleware, React HOCs, or Spring bean factories even where idiomatic code favors functions over inheritance.

When to use

  • You recognize a problem statement the catalog already names—encode that name in types (ShipmentTrackingObserver, RateLimitDecorator).
  • Vendor plugins or skinnable UIs need creation seams documented in the creational catalog.
  • Legacy or generated classes must gain behavior without source edits (Decorator, Adapter, Proxy).
  • Multiple collaborators should react to state transitions without tight coupling (Observer, Mediator).
  • Algorithms or policies must swap at runtime without editing callers (Strategy, State).
  • Complex object graphs need stepwise assembly independent of representation (Builder).
  • Cross-cutting audit, metrics, or caching layers must attach without rewriting callers (Decorator or Proxy).

When not to use

  • Pattern-led design: Picking Abstract Factory before understanding data flow optimizes forUML instead of users.
  • Tiny programs: Scripts that run once and exit rarely earn the participant count a pattern demands.
  • Singleton as globals: GoF’s Singleton solves coordinated access to a scarce resource—not a replacement for dependency injection containers.
  • Redundant indirection: Languages with first-class functions and modules often need only a callback where Java needed a full Strategy hierarchy.

Typical architecture

The Gang of Four sorts patterns by the kind of force you face: who constructs objects, how parts compose, and how collaborators signal intent. The flow below is conceptual—real systems mix creational, structural, and behavioral solutions in the same module.

Pros and cons

Pros

  • Shared names shorten design meetings and make review comments precise.
  • Documented consequences surface trade-offs before code hardens the wrong structure.
  • Well-chosen patterns separate variation points from stable cores, improving cohesion.
  • Types like AuditLoggingDecorator document cross-cutting intent without prose comments.
  • Engineers transferring between Java, C#, and TypeScript recognize collaborators immediately.

Cons

  • Forced patterns inflate class counts when a plain function would suffice.
  • Community dialects diverge—Node’s EventEmitter resembles Observer but omits GoF’s update protocol.
  • Language evolution retires patterns; excessive class-per-role hierarchies feel dated in idiomatic Go or Rust.
  • Wrong-pattern fits create mysterious bugs until someone redraws the intent diagram.
  • Junior developers may memorize structures without reading applicability sections.

Implementation notes

Creational family: Factory Method leaves product selection to descendants—frameworks call create hooks while applications register concrete types. Abstract Factory batches interchangeable families—Win/Mac widgets or Postgres/MySQL gateways. Builder stages optional fields for compound documents; Prototype clones costly graphs after first parse. Treat Singleton as documented global policy, not a dependency-injection shortcut.

Structural and behavioral families: Stack Decorators when behaviors combine dynamically; reserve inheritance for stable is-a relationships. Adapter reshapes foreign APIs; Facade offers opinionated entry points over chaotic SDKs. Observer lists need teardown hooks in UI lifecycles. Command objects power undo stacks and transactional outboxes. Encode Strategy or State with functions in expressive languages when a single operation varies.

Choosing deliberately: Map each candidate pattern to the force it resolves—variation in creation, integration with foreign code, or notification fan-out—before you name classes. When two patterns compete (Facade versus Adapter on the same SDK), pick the one whose intent matches whether you are simplifying *your* module or reshaping *their* interface. Reviewers should ask “which GoF page?” not “which UML stencil?”

Prototype helps when object graphs are expensive to assemble; Mediator centralises chatty peer dependencies; Iterator hides collection mechanics behind a stable traversal port. None of these require ceremony when the language already offers modules, functions, or iterators—but naming the role still speeds design reviews.

GoF patterns earn their keep when the force is real—Strategy for interchangeable algorithms, Decorator for cross-cutting behaviour without subclass explosion, Adapter for hostile third-party APIs. Prefer composition over deep inheritance hierarchies that fight modern idioms (higher-order functions, traits, extension methods). Resist pattern nostalgia: not every service needs a Facade singleton. Structure and SOLID trade-offs pair with SOLID principles when reviewers ask whether a pattern clarifies or obscures intent.

Observer and pub-sub remain idiomatic for domain events inside a process; across services prefer explicit outboxes and message contracts instead of in-memory Observer graphs.

Code review question: does this pattern name a real variation point, or is it ceremony for a single implementation? Reject patterns that exist only to satisfy a checklist slide.

Common failure modes

  • Global Singletons: Hidden mutable state behind getInstance() breaks parallel tests and obscures dependency graphs.
  • Abstract Factory with one product family: Two-level factory trees without a second vendor waste navigation time.
  • Leaking observers: UI layers subscribe in onMount but never detach, so callbacks fire after components dispose.
  • Tower of decorators: Ten wrappers deep obscure where exceptions originate; pipelines or explicit middleware arrays read clearer.
  • Static strategy fields: Injecting a Strategy interface that never changes implementation is ceremony—inline the algorithm until the second variant appears.

Decision checklist

  • Can you state the recurring problem in one sentence before naming a pattern?
  • Does the GoF “Applicability” section describe your forces, not only the diagram shape?
  • Is the varying behavior extrinsic to the object’s core identity (Strategy/Decorator candidate)?
  • Must created objects stay compatible within a product family (Abstract Factory candidate)?
  • Should dependents learn about changes without polling (Observer candidate)?
  • Are you integrating code you cannot edit whose interface mismatches yours (Adapter candidate)?

Example use cases

  • Illustrative scenario — Ledgerstone Reports uses Builder for optional sections, Strategy for render targets, and Decorator for watermarking signed PDFs.
  • Illustrative scenario — A shipment tracker publishes OrderShipped to Observers that enqueue email, SMS, and webhook Commands with idempotent retries.
  • Illustrative scenario — A persistence layer picks dialect-specific repositories via Factory Method, wraps them in caching Proxies, and Adapters legacy Hibernate DAOs during migration.
  • Case study — The original GoF text documents Smalltalk and C++ collaborations that still inform modern framework extension points.
  • Case study — Fowler’s Patterns of Enterprise Application Architecture extends GoF ideas into repositories, gateways, and domain events at enterprise scale.
