Refactoring Patterns

A practical catalogue of code-level and system-level refactoring techniques for improving internal structure without changing observable behaviour.

⏱ 11 min read

What it is

Refactoring is a disciplined change to the internal structure of code—moving, renaming, extracting, or simplifying—without altering observable behaviour. Martin Fowler defined the term in Refactoring: Improving the Design of Existing Code (Addison-Wesley, 2nd ed. 2018): each step is small, reversible in principle, and guarded by tests that stay green. His refactoring catalog names the moves—Extract Method, Rename Variable, Replace Conditional with Polymorphism—that IDEs automate today.

At class and method scale, those catalog entries remove code smells (long methods, duplicated logic, feature envy). At system scale, complementary patterns such as the Strangler Fig (Martin Fowler) and the Mikado Method (Ellnestam & Brolund) tackle legacy replacement and large dependency graphs. Michael Feathers’ Working Effectively with Legacy Code adds characterisation tests when no suite exists. The common thread is safety: structure improves in verifiable increments, not big-bang rewrites.

Why it exists

First implementations encode yesterday’s understanding of the domain. As the team learns, names, boundaries, and abstractions that once fit begin to lie. Without deliberate restructuring, smells accumulate—long methods, duplicated rules, feature envy—and every new story costs more than the last. Refactoring closes that gap in small steps while behaviour stays proven by tests.

Fowler’s catalogue and Feathers’ legacy techniques exist because big rewrites fail more often than incremental improvement. The industry standard is to treat structure as a continuous product: refactor after green tests, before the next red, or as preparatory work when a feature cannot fit cleanly.

Refactoring is not rewrite cosplay—it is the main way teams repay design debt without betting a release train. Paid tools and IDE support lowered the cost of catalog moves, but judgement still matters: knowing which smell to fix now versus after the feature ships.

When to use

  • Inside red-green-refactor: clean structure immediately after tests pass.
  • Preparatory refactors when the current shape blocks a forthcoming feature.
  • Follow-up PRs from review that name smells still present in merged code.
  • Legacy modernisation via strangler routing instead of stop-the-world rewrites.
  • Mikado planning when a naive change breaks dozens of dependents.
  • Retiring feature flags whose branches hardened into nested conditionals.

When not to use

  • No safety net: Write characterisation or golden-master tests before touching untested legacy.
  • Mixed commits: Keep behaviour changes and structural changes separable for review and bisect.
  • Imminent deletion: Do not polish modules scheduled for removal next sprint.
  • Theoretical perfection: Refactor toward the next requirement, not an abstract ideal.

Pros and cons

Pros

  • Delivers structural wins without betting the company on a rewrite.
  • Strangler paths keep revenue flowing while legacy shrinks.
  • Mikado graphs turn daunting graphs of breakage into ordered leaf tasks.
  • IDE-supported moves reduce typo risk versus manual edit storms.
  • Aligning code to domain language sharpens team communication.
  • Smaller, clearer units make code review faster and more effective.

Cons

  • Safety depends on tests; thin coverage means high regression risk.
  • Stakeholders may not see feature points on refactor burndown charts.
  • Proxy layers add operational surface until explicitly removed.
  • Mikado programmes can span quarters and need executive air cover.
  • Automated refactors may skip aspects like transactions and telemetry.
  • Sponsors may underestimate calendar time for multi-quarter strangler programmes.

Implementation notes

Make the change easy: Beck’s mantra—prepare structure, then add behaviour—keeps reviews legible. Land preparatory refactors as zero-behaviour PRs ahead of feature work.

Strangler routing: Introduce a gateway or facade, shift the smallest valuable slice first, monitor error budgets, expand routes, and only then retire legacy binaries. Document decommission criteria up front.

Mikado discipline: Attempt the desired end state, record breakages, revert to green, build the dependency tree from leaves inward, never leave main red overnight.

Tooling habits: Lean on IDE refactorings (Rename, Move, Extract) so compiler feedback catches missed references. For cross-repository moves, script codemods (OpenRewrite, jscodeshift) and run them in a branch with full CI. Pair every catalog refactor with a test that exercises the behaviour path you touched.

Review etiquette: Mark refactor-only PRs in the title, avoid mixing formatting sweeps with behaviour edits, and time-box large strangler milestones so the proxy layer does not become permanent infrastructure.

Fowler’s catalog supplies the moves—Extract Method, Inline, Replace Conditional with Polymorphism—but Feathers’s characterization tests unlock legacy without fear. Find seams (injection points, config flags) and use branch by abstraction when two implementations must coexist. Programme sequencing, funding, and parallel expand-contract migrations belong in refactoring strategy so this article stays technique-focused.

Rename and move in small PRs with compiler green between steps—IDE refactors beat manual copy-paste for cross-module moves. Document which catalog refactors require pairing because they touch money or compliance paths.

Characterisation tests: When legacy lacks coverage, capture outputs for representative inputs (Feathers’ golden master pattern) before extract or move operations. Delete golden files only after behaviour is covered by intentional assertions.

Incremental extraction: For monolith slices, extract pure functions first, then modules, then deployable units—each step shippable behind the same strangler router with comparable error budgets.

Before Extract Class, ensure tests cover the behaviour slice you move—otherwise you ship structural change without a safety net. Refactor-only PR titles help reviewers scope risk quickly, skip feature QA paths, and land during quiet deploy windows when possible.

Common failure modes

  • Untested edits: “It compiles” is not proof behaviour survived.
  • Permanent proxy: Strangler facades become archaeology without sunset owners.
  • While-I’m-here sprawl: Opportunistic edits balloon diff size and review risk.
  • Mikado without revert: Fixing forward on a red tree multiplies breakage.
  • Behaviour creep: Sneaking fixes into “refactor-only” PRs hides regressions from reviewers.

Decision checklist

  • Is there test or characterisation coverage for the code under change?
  • Are structure-only commits isolated from feature commits?
  • For legacy replacement, is traffic routing in place before new code ships?
  • For large moves, is a Mikado graph agreed before coding resumes?
  • Are IDE refactors preferred over manual rename grep-fests?
  • Is proxy removal scheduled with measurable completion criteria?
  • Did characterisation tests land before the first structural edit on legacy code?
