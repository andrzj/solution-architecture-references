Test Pyramids

Mike Cohn’s pyramid: many fast unit tests, a sensible band of integration and contract tests, and only critical E2E journeys—optimize CI time and defect signal.

⏱ 10 min read

What it is

The test pyramid is a model for how many tests to write at each level of automation: a wide base of fast unit tests, a narrower band of integration tests that exercise real collaborators (databases, HTTP, messaging), and a thin cap of end-to-end tests through the full stack. Mike Cohn introduced the pyramid metaphor to make the cost curve explicit—UI tests are powerful but slow and brittle; unit tests are cheap and precise.

The pyramid is a portfolio guideline, not a rigid formula. Ham Vocke’s Practical Test Pyramid (on Martin Fowler’s site) and Thoughtworks testing guidance stress optimising for feedback time and defect signal, not counting tests for their own sake. Modern systems often add contract tests between services as part of the middle layer.

Why it exists

Inverted pyramids—“ice cream cones” with many slow UI tests and few units—produce hour-long CI runs, flaky reds developers ignore, and unclear failure diagnosis. Cohn’s shape encodes economics: push detection left and down to layers that run in seconds. Google’s testing blog popularised rough allocation targets (about 70% unit, 20% integration, 10% E2E) as a conversation starter; your numbers should follow measured CI time and escaped-defect data.

Architects use the pyramid when defining engineering standards, pipeline stages, and test types in inner-source libraries—so teams do not each reinvent incompatible definitions of “integration test.”

When to use

  • Setting org-wide testing strategy for microservices, modular monoliths, or large front-end codebases.
  • Diagnosing slow or flaky CI where nobody knows which layer is overloaded.
  • Onboarding teams to consistent test taxonomy and ownership.
  • Planning where to invest when escaping defects cluster in wiring or cross-service breaks.

When not to use

  • Deleting valuable E2E coverage before building faster lower-layer replacements.
  • Treating percentage targets as law when the product is mostly integration (thin domain, heavy I/O)—adjust shape consciously.
  • Using the pyramid to justify zero manual exploratory testing for UX and novel flows.

Typical architecture

Feedback flows upward from many isolated tests to fewer full-journey checks.

Pros and cons

Pros

  • Short default feedback loop for developers and PR CI.
  • Failures localize to small units instead of whole journeys.
  • Cheaper to run at scale than UI-heavy strategies.
  • Shared vocabulary for test placement decisions in design reviews.

Cons

  • Unit-heavy suites can miss configuration, schema, and protocol mismatches.
  • Middle layer needs investment (containers, brokers, contract tooling).
  • Literal 70/20/10 ratios may not fit every domain without tuning.
  • Pyramid talk does not replace observability and production verification.

Implementation notes

Define test types in your style guide. Document what counts as unit vs integration in your stack (e.g., in-process with Testcontainers Postgres vs hitting shared staging). Ambiguous labels cause double-counting or gaps.

Measure outcomes. Track median PR CI duration, flake rate per layer, and defects found in staging/production. Shift tests down when E2E dominates time without unique signal.

Contract layer. For microservices, prefer consumer-driven contracts over multiplying cross-team E2E environments.

Variants. The “testing trophy” (Kent C. Dodds) emphasises integration for SPAs; still keep expensive E2E rare. Fowler’s pyramid article discusses service tests as the middle tier in distributed systems.

Balance cost and signal: many fast unit tests, fewer integration tests with real wiring, rare end-to-end journeys. Mutation testing (PIT, Stryker) exposes weak assertions; line coverage alone is a weak gate. Track flake rate per layer and enforce a quarantine budget—flaky tests erode trust faster than gaps. The testing honeycomb and trophy adjust the middle layer for microservices and SPAs without eliminating the need for cheap unit feedback on domain rules.

Set CI timeouts per layer: fail builds when integration suites exceed agreed minutes unless labeled nightly. Record which defects each layer caught last quarter before deleting “redundant” tests.

Avoid duplicating the same assertion in unit and E2E unless the E2E checks wiring the unit cannot see. Favour fewer, sharper E2E journeys over wide shallow coverage.

Common failure modes

  • E2E gridlock: One shared environment serialises the suite—parallelise, containerise dependencies, or shrink journeys.
  • No middle layer: Green units but broken deploys—add API/database integration and contracts.
  • Ice cream cone: UI tests duplicate unit assertions—drive rules downward.
  • Metric chasing: Coverage percentage rises while escaped defects stay flat—review assertion quality.

Decision checklist

  • What is median PR CI time and which layer dominates it?
  • Are E2E tests limited to irreplaceable user journeys?
  • Is there a written definition of unit vs integration vs contract?
  • Do service boundaries have contract or integration coverage?
  • When a defect escapes, which layer should have caught it?

Example use cases

  • Illustrative scenario — A ten-service platform: thousands of unit tests, hundreds of Testcontainers integration tests, dozens of Pact contracts, twelve smoke E2E journeys; PR pipeline under ten minutes.
  • Case study — Mike Cohn’s test automation pyramid articles define the unit / service / UI layering teams still reference.

Related patterns

  • Test-Driven Development — grows the unit base of the pyramid.
  • Integration Testing — middle-layer practices with real dependencies.
  • Contract Testing — service-boundary tests without full stacks.
