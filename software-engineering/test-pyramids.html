Test Pyramids

Unit, integration, and end-to-end test proportions for reliable, fast test suites.

⏱ 10 min read

What it is

The test pyramid recommends many fast unit tests, fewer integration tests, and minimal end-to-end UI tests. The shape controls feedback speed, flake rate, and maintenance cost.

Modern variants include the testing trophy (more integration) for SPAs and contract tests between services as a middle layer.

Why it exists

Inverted pyramids (many slow UI tests, few units) yield 45-minute CI and ignored red builds.

Teams need a shared vocabulary for where to add the next test.

When to use

  • Defining CI strategy for microservices or modular monoliths.
  • Auditing why CI is slow or flaky.
  • Onboarding teams to consistent testing standards.

When not to use

  • Throwing away valuable e2e coverage before adding faster lower-layer tests.

Typical architecture

Pros and cons

Pros

  • Fast developer feedback.
  • Pinpoints failures to small units.
  • Cheaper to run at scale in CI.

Cons

  • Unit tests miss wiring and config errors.
  • Requires investment in test doubles and containers for integration.

Implementation notes

Target ratio guidelines per repo type but measure outcome: CI duration and defect escape rate.

Add contract tests at service boundaries before expanding e2e.

Common failure modes

  • E2E gridlock: Suite serialized through one environment — parallelize or shrink.
  • No integration layer: Unit green but deploy fails — add API contract and DB integration tests.

Decision checklist

  • What is p95 CI time for pull requests?
  • Are e2e tests limited to critical user journeys?
  • Is there a definition of unit vs integration in the style guide?

Example use cases

  • Microservice suite: 2k unit, 120 contract, 12 smoke e2e; PR CI under 8 minutes.
