Clean Architecture

Robert C. Martin’s concentric-ring layout—entities, use cases, adapters, frameworks—with the dependency rule pointing inward.

⏱ 10 min read

What it is

Clean Architecture is Robert C. Martin’s ring model that places enterprise rules and application-specific use cases at the center while UI, databases, and frameworks remain replaceable plugins on the outside, governed by the Dependency Rule: source code dependencies always point inward.

Inner rings know nothing about outer ones. Entities hold business-wide invariants; use-case interactors orchestrate workflows; interface adapters translate between the outside world and inner ports; frameworks and drivers supply concrete technology. Gateways (repository, payment, notification) are interfaces owned by inner layers, implemented by adapters that depend inward—not the reverse.

Why it exists

Martin’s 2012 essay and Clean Architecture book react to frameworks colonizing the center of diagrams. When Spring annotations or ActiveRecord callbacks own the domain, policy code splinters across controllers, and tests require containers. Clean Architecture recenters tests on plain objects and ports so you can swap PostgreSQL for DynamoDB or REST for gRPC by rewriting adapters, not interactors.

The goals mirror Hexagonal and Onion architectures—testable domain, UI independence, database independence, external agency independence—but Clean Architecture names the rings and boundary objects (Interactor, Presenter, Gateway) that teams reference in coding standards and ArchUnit rules. Naming those seams explicitly helps architects argue about *where* a feature belongs before debates devolve into package politics.

When to use

  • Rich domain logic must survive framework upgrades and cloud vendor moves.
  • Products outlive multiple presentation channels and need one use-case layer behind them.
  • Engineering culture prioritizes fast unit tests without Testcontainers for every branch.
  • Compliance asks for auditable rules separated from infrastructure configuration.
  • Multiple teams share core policy modules across web, mobile, and batch entry points.

When not to use

  • Thin CRUD services where interactors only forward to repositories add layers without rules to protect.
  • Throwaway prototypes where rewrite cost is cheaper than port/adapter ceremony.
  • Organizations without experience in dependency inversion—ring rules will erode within sprints.

Typical architecture

Four concentric rings enforce inward dependencies; adapters implement ports declared by use cases and entities.

Pros and cons

Pros

  • Policy tests run in milliseconds because interactors depend on interfaces, not Tomcat or EF Core.
  • Vendor or framework migrations touch adapter modules while use-case code stays stable.
  • Role names in package structures make onboarding expectations explicit.
  • One interactor can sit behind HTTP controllers, gRPC services, and CLI commands simultaneously.
  • Ring boundaries reinforce Martin’s Dependency Inversion and Single Responsibility guidance.

Cons

  • Each feature may need request/response models, ports, interactors, and presenters—file counts climb.
  • Simple lookup endpoints gain little from extra layers unless rules appear later.
  • Strict presenter flow feels foreign to teams used to returning DTOs directly from controllers.
  • Navigation overhead rises unless naming conventions and module diagrams stay current.

Implementation notes

Model each application capability as an interactor implementing an input port interface controllers invoke. Accept request models free of framework types, invoke entities for enterprise rules, call gateway interfaces for persistence or partners, and hand results to an output port (presenter) or return a response model when pragmatism wins. Declare gateways beside use cases; adapters in infrastructure implement them and map to SQL, HTTP, or message clients.

Wiring happens only in the composition root (main module, DI module, or Program.cs). Architecture tests—ArchUnit, NetArchTest, or custom linters—fail builds when entities import Spring or when interactors reference JDBC drivers. Many teams relax presenters for JSON APIs but keep request/response mapping to prevent MVC types leaking inward.

Uncle Bob’s original guidance stresses that outer rings may depend on inner rings but never the reverse: UI and database are plugins to the application, not the center of the model. That mindset keeps refactors localized when you swap PostgreSQL for a document store or add a gRPC port beside REST.

The dependency rule points inward: entities and use cases know nothing of Spring, Express, or SQL. Define ports (repository interfaces, notification gateways) in the application ring; adapters implement them in infrastructure. Frameworks live only in composition roots—wiring modules, main, or Nest providers. Resist five-package ceremonies on a two-endpoint service: a thin hexagonal slice with one domain module and one adapter package often suffices until multiple inbound channels force a split.

Test use cases without containers: instantiate interactors with in-memory fakes of ports so domain rules run in milliseconds. Let integration tests cover adapter mappings once per boundary.

When a framework upgrade breaks adapters, domain tests should still pass—only composition roots change. That split is the payoff for keeping frameworks at the edge.

Common failure modes

  • Framework DTOs in interactors: Accepting @RequestBody objects inside use cases tethers policy to web stacks.
  • Annotated entities: JPA or serialization attributes on enterprise objects break the dependency rule instantly.
  • Pass-through interactors: Layers that only delegate findById add meetings without protecting rules.
  • Repositories in the wrong ring: Concrete SQL classes living beside interactors invite upward imports.
  • No automated guardrails: Without CI architecture tests, outer layers creep inward within quarters.

Decision checklist

  • Can interactors run entirely with in-memory gateway fakes in unit tests?
  • Do entity modules compile with zero framework package imports?
  • Are request and response models plain data carriers devoid of transport metadata?
  • Do gateway interfaces live next to the use cases that define the need?
  • Does CI enforce dependency direction automatically, not only via code review?
  • Is exactly one composition root responsible for binding concrete adapters?
  • When infrastructure changes, do you update adapters without rewriting business rules in entities or use cases?

Example use cases

  • Illustrative scenario — Threadline Lending shares one loan approval interactor across REST, mobile GraphQL, and nightly batch files with separate controllers but identical policy tests.
  • Illustrative scenario — A clinical records product keeps patient safety rules in entities while Oracle and cloud adapters swap beneath gateway interfaces.
  • Illustrative scenario — A multi-tenant SaaS billing service isolates metering and entitlement interactors from Stripe or Adyen adapter packages.
  • Case study — Martin’s original Clean Architecture blog post diagrams the rings and dependency rule that teams still trace in architecture reviews.
  • Case study — The Clean Architecture book extends the model with screaming architecture and component principles for large systems.

Related patterns

  • Hexagonal Architecture — Alistair Cockburn’s ports-and-adapters view shares the same inversion center.
  • Onion Architecture — Palermo’s layers emphasize domain services at the core with similar dependency flow.
  • CQRS — Command and query interactors fit naturally in the use-case ring when read/write models diverge.
  • SOLID Principles — DIP and ISP explain why gateways stay narrow and inward-facing.
