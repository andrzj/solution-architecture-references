CQRS Pattern

Command Query Responsibility Segregation: separate write models (commands) from read models (queries) to independently optimize each for its workload.

⏱ 9 min read

What it is

CQRS (Command Query Responsibility Segregation) splits commands that change state from queries that return data, often with separate models and stores for each side.

Greg Young extended Bertrand Meyer’s Command Query Separation from methods to systems: the write model enforces invariants; the read model is shaped for how screens and APIs actually ask questions.

In a retail catalog, the merchandising API accepts PublishProduct and UpdatePrice commands against a normalized Postgres write model, while shoppers hit OpenSearch and a Redis-backed facet cache built by projectors — not the same tables the merchandiser edits.

Why it exists

Catalog search often joined six tables on every browse request. Merchandisers adding attributes slowed checkout-style admin writes, and tuning indexes for search polluted the write schema.

CQRS lets the catalog team keep a strict Product aggregate for commands while search owns denormalized documents with synonyms, facets, and ranking boosts. Each side scales and deploys on its own cadence.

When catalog pairs CQRS with event sourcing for orders (see Event Sourcing), the same domain events feed both search projections and fulfillment read models — one write path, many read shapes.

CQRS does not require two databases on day one. Many teams begin with segregated command and query handlers against one Postgres schema until search QPS or mapping churn forces a dedicated read store. The expensive part is operational: lag SLOs, projector idempotency, and rebuild runbooks—not the interface split itself.

When to use

  • Apply CQRS when read traffic dominates and query shapes differ from write invariants, as catalog browse versus merchandising edits.
  • Apply CQRS when the write model is a rich domain model that should not absorb report-friendly denormalization.
  • Apply CQRS when multiple UIs need different projections of the same catalog truth — mobile cards, B2B CSV export, and ops dashboards.
  • Apply CQRS alongside event sourcing when domain events naturally feed projectors (an order stream updating catalog “bought together” hints).
  • Apply CQRS when you need to scale OpenSearch or Redis read tiers without touching Postgres write primaries.

When not to use

  • Skip CQRS for internal admin CRUD with a handful of fields — a tax-code lookup does not warrant projectors.
  • Skip CQRS when the merchandising UI must show search-indexed fields in the same transaction as a command — async lag will confuse users unless you design optimistic UI.
  • Skip full physical CQRS until the team can own projection code, rebuild jobs, and drift alerts — logical CQRS inside one service is often enough first.

Typical architecture

A catalog command API mutates Postgres and emits ProductPublished events. Projectors update OpenSearch documents and Redis facet sets; the storefront query API reads only those stores.

Pros and cons

Pros

  • Teams change search ranking in OpenSearch without refactoring the Product aggregate in Postgres.
  • Read stores pick the right engine — OpenSearch for full text, Redis for hot facet counts.
  • Projectors can rebuild catalog search from ProductPublished history after a mapping bug.
  • Domain commands stay focused on invariants instead of join-heavy DTOs for the storefront.
  • Black Friday scales query nodes independently from merchandising write traffic.

Cons

  • A merchandiser may publish a SKU and see search lag seconds behind Postgres unless the UI optimistically updates.
  • You maintain command handlers, events, projectors, and query APIs — more moving parts than one CRUD service.
  • A projector defect corrupts OpenSearch until ops run a full replay job.
  • “Wrong price on search” tickets require tracing command → event → projector, not one SQL query.

Implementation notes

Start logical: Many teams begin with separate command and query services against one Postgres database before splitting OpenSearch off — most clarity comes from segregated handlers, not day-one polyglot storage.

Projection timing: Async projectors on a broker feed search; admin screens that need read-your-writes poll the write API or use synchronous projection to a small Redis cache for SKU detail.

Rebuild path: A RebuildCatalogSearch job replays ProductPublished and PriceChanged from the outbox into a fresh OpenSearch index, then aliases cutover.

Write concurrency: Product aggregates carry version numbers; conflicting UpdatePrice commands fail fast instead of silently overwriting.

Define projection lag as a product-facing SLO, not a hidden broker metric. Many catalog teams target one to five seconds from command commit to searchable documents; analytics may tolerate minutes. Admin UIs should show “last synced” timestamps or use optimistic updates so operators know when they are looking at stale denormalized data. When a screen must be read-your-writes, narrow synchronous projection to that view or route the query back through the write API instead of pretending the index is authoritative.

Projectors must be idempotent under at-least-once delivery: record event_id or (aggregate_id, sequence) in a processed table before mutating the read model. Publish changes through a transactional outbox—never dual-write Postgres and a search index in one handler. CQRS is frequently paired with event sourcing because domain events feed projections naturally, but logical CQRS (separate handlers, one database) is common and often the right first step. Full physical split is overkill when read and write shapes, security models, and scale profiles are identical—reserve the operational tax for places where search ranking, facets, or read replicas genuinely diverge from the write schema.

Common failure modes

  • CQRS everywhere: Full projection stacks on tiny lookup tables drown teams in boilerplate.
  • No rebuild: A bad projector deploys for a week; search prices drift with no replay lever.
  • Stale admin UX: Merchandisers refresh and still see old titles because search lag was never communicated.
  • Commands querying OpenSearch: PublishProduct checks the search index for duplicates — circular coupling breaks segregation.
  • ORM write model: The “aggregate” is every column on products — invariants live only in controllers.

Decision checklist

  • Is the read shape materially different from write invariants, not merely “we like Elasticsearch”?
  • Can storefront and admin UIs tolerate or mask projection lag after commands?
  • Is there an documented rebuild procedure for each read model?
  • Do command handlers load state only from the write model, not from search indexes?
  • Does the write side use optimistic concurrency on catalog aggregates?
  • Would logical CQRS inside one service deliver enough benefit before operating separate databases?

Related patterns
