Hexagonal Architecture (Ports & Adapters)

The application core is isolated from infrastructure through ports (interfaces) and adapters (implementations), making domain logic independently testable.

⏱ 8 min read

What it is

Hexagonal Architecture (ports and adapters) isolates the application core behind explicit interfaces. Ports are the contracts the core exposes or requires; adapters are the concrete REST clients, databases, and vendor SDKs that plug into those ports.

Northwind Payment uses hexagonal layout inside the Payment bounded context. The core owns PaymentIntent capture rules and refund invariants. Primary ports such as CapturePayment and RefundCapture are what Billing and dispatch call. Secondary ports such as CardProcessorPort, LedgerPort, and FraudScreeningPort describe what the core needs from the outside world. Adapters implement those ports — a card processor SDK wrapper, a Postgres ledger repository, and in-memory fakes for unit tests.

The domain never imports adapter code. Infrastructure depends on port interfaces declared alongside the core — a direct application of the Dependency Inversion Principle.

Why it exists

Layered architectures still let vendor SDKs and ORM types leak into “domain services” because nothing structurally forbids it. Northwind learned that when Billing imported the card processor’s Java client directly: capture retries, idempotency keys, and PCI boundaries mixed with HTTP controllers.

Hexagonal Architecture draws a hard line: the Payment hexagon compiles without the processor SDK. Tests exercise CapturePayment through primary ports with stubbed CardProcessorPort implementations, so CI validates capture rules without sandbox credentials or network calls.

Swapping processors or adding a backup acquirer becomes an adapter problem — the core’s vocabulary stays PaymentIntent, not provider-specific charge objects.

When to use

  • Use hexagonal layout when Northwind Payment rules are rich enough to justify isolation from processor SDKs and persistence frameworks.
  • Use it when fast unit tests of capture, refund, and idempotency logic are a priority for the Billing squad.
  • Use it when Northwind must support multiple processors or route traffic through primary and backup acquirer adapters.
  • Use it when Billing practices TDD and wants the Payment core drivable equally from tests, HTTP, and async invoice events.
  • Use it when PCI scope must stay in adapters while the core manipulates token references only.

When not to use

  • Skip ports and adapters for simple payment-status CRUD where no capture invariants exist.
  • Skip the pattern on short-lived experiments where adapter indirection slows validation.
  • Skip it until the team can tell primary (driving) ports from secondary (driven) ones, or every class becomes an “adapter.”

Pros and cons

Pros

  • Northwind validates capture and refund rules in memory with stub CardProcessorPort implementations before sandbox deploys.
  • Replacing the primary acquirer means shipping a new adapter, not rewriting PaymentIntent behavior.
  • Ports force explicit conversation about what Payment does versus how it talks to processors and ledgers.
  • The same core runs under Billing HTTP, invoice event consumers, and CLI replay tools without code forks.
  • The hexagon maps cleanly to Northwind’s Payment bounded context and its published capture API.

Cons

  • Every external system needs a port interface plus at least one adapter — noticeable boilerplate for thin flows.
  • More packages and indirection can feel heavy when the domain is mostly pass-through to the processor.
  • Interactors that only orchestrate without rich PaymentIntent behavior recreate an anemic core.
  • New contributors must learn which types belong inside the hexagon versus in adapter modules.

Implementation notes

Declare secondary ports in the core package: Northwind defines CardProcessorPort next to PaymentIntent, not under infrastructure.processor, so adapter modules depend inward.

Map at the adapter edge: The Stripe-style adapter translates provider charge IDs and failure codes into Northwind’s CaptureResult value objects. Processor DTOs never appear in the hexagon.

Ship in-memory adapters for CI: InMemoryCardProcessor records calls for assertions; production wires the real SDK adapter at the composition root.

Group by feature: Northwind keeps payment/capture ports, core, and adapters together so Billing engineers find capture logic in one vertical slice.

Common failure modes

  • SDK types in the core: Importing the processor’s client or webhook DTO into PaymentIntent collapses the hexagon.
  • Anemic core: All logic sits in a “service” class while entities are data bags — ports protect nothing.
  • Port explosion: One interface per repository method creates dozens of ports nobody reuses.
  • Integration tests only: CI hits the real sandbox adapter for every test, erasing the speed benefit.
  • Tests import adapters: Specs new up StripeCardProcessorAdapter instead of the port, so refactors break tests for the wrong reason.

Decision checklist

  • Are secondary port interfaces declared in Northwind Payment’s core package, not in infrastructure?
  • Can the capture and refund suite run without starting Postgres, the processor sandbox, or HTTP?
  • Does every secondary port have an in-memory adapter used in unit tests?
  • Do adapters translate provider types into domain types at the boundary?
  • Does a composition root wire adapters without DI annotations inside the hexagon?
  • Are domain types free of processor, ORM, and messaging imports?

Example use cases

Northwind Payment’s card processor integration follows one hexagonal map:

  • Primary ports: CapturePayment and RefundCapture are what Billing’s invoice service calls after dispatch confirms pickup.
  • Core: PaymentIntent enforces idempotency keys, partial capture limits, and settlement state without importing SDK classes.
  • Processor adapter: CardProcessorPort is implemented by a vendor adapter in production and InMemoryCardProcessor in CI.
  • Ledger adapter: LedgerPort posts double-entry rows through a Postgres adapter while tests use an in-memory ledger.
  • Swap path: Northwind pilots a backup acquirer by adding a second adapter and routing at the composition root — the hexagon unchanged.

Related patterns

  • Clean Architecture — Uncle Bob's concentric-ring formulation of similar dependency inversion principles.
  • Onion Architecture — Jeffrey Palermo's variant with explicit domain service and application service layers.
  • CQRS — Often applied within the hexagonal core, with separate command and query ports.
