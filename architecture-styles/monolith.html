Monolith Architecture

A single deployable unit where all application components run in one process, sharing memory and a common data store.

⏱ 7 min read

What it is

A monolith is one deployable application: every module runs in the same process and typically talks to one primary database through shared connection pools. A logistics dispatch portal, an internal admin console, or an early-stage SaaS product often ships this way — load assignments, user profiles, and reporting screens all live in a single artifact behind one URL.

Because calls stay in-process, engineers debug with one run configuration and keep multi-step updates inside ordinary database transactions instead of sagas across the network.

Why it exists

Monoliths are the default shape of most new products. You avoid service discovery, cross-service versioning, and partial-failure debugging until the business and team topology justify that cost.

Teams often choose a monolith first so they can rename domain concepts and reshape module seams without publishing breaking HTTP contracts to mobile clients on every iteration. Martin Fowler’s MonolithFirst argument matches that story: prove the domain in one unit, then extract only where autonomy or scale force it.

The failure mode is social as much as technical: without module APIs and architecture tests, every feature imports every repository and the deployable becomes one blast radius. Horizontal scaling then duplicates all code paths—including batch jobs nobody intended to multiply—while the database remains the choke point.

When to use

  • One team (or tightly coupled teams) can ship on a shared release cadence without waiting on separate service pipelines.
  • Domain rules are still moving — module boundaries inside the monolith are cheaper to move than network API versions.
  • Operations wants a single deployable to monitor, roll back, and certificate-manage during early rollouts.
  • The organization has not yet invested in Kubernetes, a service mesh, or organization-wide distributed tracing for this product.
  • Peak load grows roughly with total portal traffic rather than one hot subsystem that must scale on its own.
  • The product is still being validated with early customers before paying the tax of running many small services in production.

When not to use

  • Dispatch, mobile, and partner teams must deploy on independent schedules and cannot share one release train.
  • One capability (for example map tile preprocessing or batch rating) needs CPU or memory profiles that differ sharply from the interactive portal.
  • Different subsystems must run on different languages or runtimes and cannot share one binary.
  • Policy requires cardholder or safety-critical code in a separate trust zone with network isolation from the main portal process.

Pros and cons

Pros

  • Developers run the whole application locally with one command and one debugger session.
  • In-process calls avoid network latency and serialization on hot request paths.
  • One CI/CD pipeline and one production artifact simplify rollback when a deploy misbehaves.
  • Assigning work and recording completion can stay in one ACID transaction instead of a distributed commit.
  • Production triage uses logs and breakpoints in one codebase instead of stitching traces across services.
  • Renaming a domain concept is a refactor inside the repo, not a coordinated API version bump.

Cons

  • Every deploy restarts the whole application, so an unrelated change can still take critical flows offline.
  • An unhandled exception in one module can terminate the process and knock out all clients entirely.
  • Scaling out duplicates every module, even when only one subsystem (for example map rendering) is hot.
  • Without discipline, cross-module imports turn the codebase into a single tangled ball of mud.
  • The runtime and framework choice applies to every feature — you cannot run one slice on a different stack.

Implementation notes

Treat each feature area as a future service boundary: expose a small public API per module, ban direct SQL against another module’s tables, and prefer internal events for cross-module work. Run ArchUnit (Java), Dependency Cruiser (TypeScript), or similar checks in CI so modules cannot import each other’s internals. That modular monolith discipline keeps a single deployable while preserving a strangler fig path — peel off a module behind an HTTP facade only when release or scale pain proves it.

Horizontal scale duplicates every module in the deployable, not just the hot path—stateless tiers behind a load balancer help, but connection pools must be sized so replica count times pool size stays under roughly sixty to seventy percent of database max_connections. Read replicas offload reporting; bulkheads (separate thread pools for batch versus interactive) and ingress rate limits keep one misbehaving job from starving checkout. Post-deploy synthetics with automatic rollback thresholds catch regressions before traffic fully shifts. Split only when teams, scale shapes, or compliance zones force it—after modular discipline, not before.

Common failure modes

  • Big ball of mud: Handlers in one module reach into another module’s repositories directly; every change risks breaking unrelated screens.
  • Shared mutable tables: Two modules update the same row without a module API, so schema changes become organization-wide projects.
  • God service: All business rules pile into one orchestrator class that nobody dares touch before peak season.
  • Release train bottleneck: Mobile, operations, and billing teams queue on one pipeline and stop shipping mid-week fixes.
  • Process-wide resource leaks: A caching mistake in one module grows heap for every instance and pages on-call for “mystery” restarts.

Decision checklist

  • Can stakeholders accept a single coordinated release for the application they all depend on?
  • Are service boundaries still likely to move as domain rules mature?
  • Is the team ready to operate containers, meshes, and distributed traces if you split the monolith tomorrow?
  • Does load rise with overall portal traffic rather than one subsystem alone?
  • Do CI architecture tests block new cross-module imports?
  • Is there a written plan for which module would extract first if autonomy becomes mandatory?

Example use cases

  • Illustrative scenario — Northwind FieldOps: One deployable serves dispatch consoles and driver mobile clients until partner APIs or fleet scale force selective extraction.
  • Case study — Shopify monolith era: Years of commerce logic lived in a single Rails app before modules became services where independence paid off.
  • Illustrative scenario — Basecamp / Hey: Product teams returned to a monolith after distributed integration slowed feature work more than it helped isolation.

Related patterns

  • Modular Monolith — The disciplined evolution of a monolith with enforced internal boundaries.
  • Microservices — The distributed alternative, appropriate once team size and domain complexity justify the operational cost.
  • Event-Driven Architecture — Can be adopted inside a monolith to decouple modules before extraction.
