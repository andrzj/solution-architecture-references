Event-Driven Architecture

Components communicate through events, enabling temporal and spatial decoupling, asynchronous processing, and high scalability.

⏱ 10 min read

What it is

In event-driven architecture (EDA), a service publishes a domain event when something meaningful happens instead of calling the next service synchronously and waiting.

Events flow through a broker — at Northwind Logistics, that broker is Apache Kafka — that durably stores and fans out messages. Producers append to topics such as dispatch.load-assigned and shipment.delivered; consumers in billing, driver notification, and analytics read at their own pace.

EDA is a family of patterns, not one design. Martin Fowler distinguishes event notification (signal only), event-carried state transfer (payload carries enough data to act without a callback), and event sourcing (the event log is the system of record). Northwind’s dispatch pipeline uses notification and state transfer on Kafka; Order at Meridian Commerce (a separate bounded context) may source state from events — see Event Sourcing.

Why it exists

Northwind’s dispatch service used to call billing, routing, and the driver app over HTTP inside one request. When billing slowed during month-end, loads stalled in the yard and drivers saw timeouts.

EDA breaks that coupling: dispatch publishes LoadAssigned and moves on. Billing invoices from the topic when it is ready; analytics replays the same stream for SLA dashboards without peeking into dispatch’s database.

Fan-out is the other payoff. One ShipmentDelivered event can trigger invoice generation, customer SMS, and warehouse metrics — Northwind adds a consumer without redeploying dispatch.

When to use

  • Adopt EDA when Northwind-scale producers must not block on slow consumers, such as peak dispatch bursts while billing catches up overnight.
  • Adopt EDA when services have different availability and scaling profiles, as dispatch (always on) versus analytics (batch-tolerant).
  • Adopt EDA when one domain fact must fan out to several independent reactions, like LoadAssigned reaching routing, billing, and driver notify.
  • Adopt EDA when audit or replay requirements favor an immutable log — Northwind replays Kafka topics after schema fixes.
  • Adopt EDA when integrating heterogeneous stacks where a shared envelope (CloudEvents headers, Avro payloads in Schema Registry) beats point-to-point RPC.

When not to use

  • Skip EDA for paths that need an immediate synchronous answer in the same HTTP response, such as card authorization before Northwind commits a load — use RPC or a saga, not fire-and-forget alone.
  • Skip EDA for small CRUD tools where a broker’s operational cost outweighs two services talking over REST.
  • Skip EDA until the team can run Kafka (or an equivalent) with consumer lag alerts, DLQs, and on-call playbooks — unmanaged brokers become silent data loss.

Typical architecture

Northwind’s dispatch and shipment-tracking services publish to Kafka topics. Consumer groups parallelize billing and notification workers; retained segments let analytics replay last week’s ShipmentDispatched events after a bug fix.

Pros and cons

Pros

  • Northwind dispatch stays responsive when billing or analytics lag, because Kafka buffers between producers and consumers.
  • Consumer groups scale out by adding partitions and workers on the billing topic during month-end.
  • New reactions (for example a compliance export on ShipmentDelivered) ship as new consumers without changing dispatch code.
  • The retained topic is the operational audit trail for “which loads were assigned when.”
  • Peak Monday-morning dispatch spikes land in the broker instead of timing out downstream HTTP handlers.

Cons

  • Billing may invoice seconds after dispatch assigns a load — UIs and support tools must tolerate eventual consistency.
  • Tracing one load across five topics requires correlation IDs and OpenTelemetry, not grep in a monolith log.
  • Kafka’s default at-least-once delivery means Northwind’s billing consumer must dedupe on loadId.
  • Avro schema changes on LoadAssigned can break old consumers unless Schema Registry enforces compatibility.
  • Operating Kafka (partitions, rebalances, retention) is real platform work — Northwind funds a small streaming team.

Implementation notes

Envelope: Every Northwind event carries correlationId, loadId, and CloudEvents-style metadata so support can follow one shipment across dispatch, billing, and notify.

Idempotency: Billing stores processed eventId keys — at-least-once delivery must not double-invoice the same ShipmentDelivered.

Schema Registry: LoadAssigned and ShipmentDispatched use Avro with backward-compatible evolution; producers register schemas before deploy.

Choreography vs orchestration: Load-to-delivery is choreographed off Kafka events. Northwind reserves Step Functions–style orchestration for rare compensation flows (cancel after partial billing).

Dead letters: Poison messages on the billing consumer go to a DLQ topic with alerts — one bad payload must not stall the partition.

Common failure modes

  • Duplicate billing: Billing applies ShipmentDelivered twice because the consumer is not idempotent on loadId.
  • Unbounded lag: Analytics cannot keep up with dispatch publish rate; retention expires before the warehouse catches up.
  • Breaking schema deploy: Dispatch adds a required Avro field without compatibility mode; notify consumers crash-loop.
  • No DLQ: A malformed LoadAssigned blocks the billing partition until manual intervention.
  • Missing correlation IDs: Ops cannot tie driver SMS failures back to the originating dispatch command.

Decision checklist

  • Does every Northwind consumer dedupe or otherwise handle at-least-once delivery safely?
  • Does every published event include correlationId and domain identifiers such as loadId?
  • Are Avro schemas registered with backward-compatible evolution rules?
  • Do critical consumer groups have DLQs and paging when messages land there?
  • Are consumer lag and topic retention monitored against Northwind’s replay needs?
  • Is event retention documented so compliance knows how far back Kafka can be replayed?

Example use cases

Northwind’s dispatch-to-delivery story is one EDA thread:

  • Assignment: Dispatch commits a load and publishes LoadAssigned to Kafka; routing consumes it and publishes RoutePlanned without synchronous coupling.
  • In transit: Shipment tracking emits ShipmentDispatched and ShipmentDelivered with event-carried state (driver, timestamps, geo) so billing does not query dispatch’s database.
  • Fan-out: The same ShipmentDelivered triggers invoice creation, customer notification, and analytics ingestion through independent consumer groups.
  • Replay: After a projector bug, analytics replays the shipment.delivered topic from a known offset to rebuild SLA dashboards.

Related patterns

  • Event Sourcing — Uses events as the persistent source of truth, not just communication.
  • CQRS — Frequently combined with EDA; events update read-model projections asynchronously.
  • Microservices — EDA is the preferred async communication pattern between microservices.
