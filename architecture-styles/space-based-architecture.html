Architecture Styles Scalability

Space-Based Architecture

Achieve extreme scalability by removing the database from the hot path — processing units share state through in-memory data grids, eliminating the central database bottleneck entirely.

⏱ 9 min read

What it is

Space-Based Architecture (SBA) — also called tuple-space or cloud architecture — removes the central database from the synchronous request path. Application logic and hot state live in identical processing units (PUs) that share a virtual in-memory space instead of round-tripping to disk on every read and write.

A ride-hailing or ticketing platform can use SBA for surge-time matching. When a stadium lets out, a very large crowd taps “Match” at once. A messaging grid routes each request to an available PU; the processing grid is those PUs running match scoring and offer logic; the data grid holds replicated in-memory copies of open driver slots, active offers, and zone surge multipliers on every unit. Completed trips drain to the system-of-record database through an async data writer — not through the match hot path.

Scale out by adding PUs: each new unit adds CPU and a slice of the distributed memory fabric. The idea traces to tuple spaces (JavaSpaces, GigaSpaces), where collaborators read and write entries by key in shared space rather than by server hostname.

Why it exists

Horizontally scaled app tiers hide the real bottleneck: every surge request still contends for the same database connections, row locks, and disk I/O. Caching trims median latency but cache misses and inventory writes still collapse into the RDBMS during spikes — exactly when a match API must stay responsive under spike load.

SBA answers spiky, key-oriented workloads — flash matching, bidding, ticketing — where working set size fits cluster RAM and stakeholders accept write-behind persistence for analytics and settlement. The database remains authoritative for history; it is no longer the throttle on live matching.

When to use

  • Use SBA when database I/O or connection pools cap throughput during predictable spikes (concerts, holidays, playoff games).
  • Use it when match, bid, or reservation logic needs single-digit millisecond reads and writes against keys, not ad-hoc joins.
  • Use it when the hot working set fits in aggregate cluster memory with headroom for replication.
  • Use it when dispatch teams can document eventual lag between grid state and billing exports.

When not to use

  • Do not adopt SBA when cold data exceeds RAM — eviction turns every request into a database round trip and undoes the pattern.
  • Do not rely on it for cross-entity reporting SQL; grids excel at key lookup and entry processors, not warehouse-style queries.
  • Do not choose it when finance requires synchronous ACID across match and ledger in one transaction.
  • Do not pay grid operations cost for moderate traffic that a sized database tier and cache already sustain.

Pros and cons

Pros

  • Ops can add PUs before a known surge and gain both matchers and memory-backed slot inventory in one scaling action.
  • Match reads and offer writes hit local grid replicas instead of contending on shared database rows.
  • The messaging grid absorbs connection storms by spreading RPCs across healthy PUs without opening more DB pool slots.
  • Elastic shrink after the event returns cluster cost to baseline without redesigning the schema.

Cons

  • Open-driver and offer maps must fit in RAM — oversizing zones into the grid is expensive and brittle.
  • Finance dashboards trail live matching until the async data writer flushes trip facts to the RDBMS.
  • Cross-PU replication during a write storm can briefly expose stale slot counts unless entry processors are carefully scoped.
  • Grid topology, partition keys, and write-behind tuning demand senior ops attention beyond a typical CRUD stack.
  • A PU group that dies before write-behind drains can lose in-flight offers unless durability tiers are configured per object type.

Implementation notes

Three grids on one cluster: Run the messaging grid (request router or space-based executor), processing grid (stateless-ish PUs with embedded logic), and data grid (Hazelcast, Ignite, or commercial IMDG) as coordinated tiers. Key offers by geohash prefix so each PU co-locates scoring with the partition it owns.

Partition vs replicate: Replicate small, hot surge multipliers everywhere; partition large driver-location maps by zone so each PU holds only the shard it matches. Full replication on million-row maps will blow memory budgets.

Near-cache and compute-to-data: Keep per-zone surge counters in a near-cache on each PU to avoid cross-node chatter; use entry processors to decrement open slots atomically inside the partition.

Write-behind: Batch completed match events to Postgres for analytics and payouts. Keep in-flight offers on write-through or short TTL if re-deriving them from riders is costly.

In-memory data grids such as Hazelcast, Apache Ignite, and VMware Tanzu GemFire implement the data tier: partition large working sets by zone or geohash so each processing unit colocates scoring with the rows it owns, and replicate only small, hot reference data globally—replicating million-row maps blows memory and bandwidth. Near-cache and entry processors keep atomic decrements on the partition owner instead of cross-node chatter. Write-behind batches durable persistence asynchronously, which improves peak throughput but risks finance lag or lost in-flight offers if a unit dies before flush—use write-through for authoritative in-flight state. Size partitions with load tests (objects × bytes plus replication headroom); alert on rebalance duration, off-heap pressure, and failover time. Misrouted requests that hit the wrong partition cause cross-grid storms—integration tests should assert colocation rules. Sub-10 ms matching at extreme concurrency with expert grid operators is the sweet spot; modest CRUD latency targets stay on API, cache, and database.

Common failure modes

  • Eviction under memory pressure: Cold zone metadata evicts under pressure; the next match misses the grid and hammers Postgres — restoring the pattern requires capacity planning, not bigger connection pools.
  • Replication lag at kickoff: A stadium surge generates more driver ping updates than cross-PU bandwidth allows; matchers read neighboring PUs with stale “available” flags and double-book drivers.
  • Write-behind backlog: The async data writer cannot keep pace with completed trips; the queue grows until grid nodes OOM or finance reports are hours late.
  • Cold start after deploy: Every PU reloads zone inventory from the database before taking traffic — a full-cluster restart during peak blocks matching unless warm-up pipelines pre-fill the grid.
  • Split-brain: A network partition lets two PU islands accept conflicting reservations for the same driver; healing requires version vectors or last-writer-wins rules documented in advance.

Decision checklist

  • Does the surge-time working set fit planned cluster RAM with headroom above current peak open-offer volume?
  • Is matching keyed by zone, offer, or driver ID rather than arbitrary SQL?
  • Can billing and analytics tolerate minutes of lag behind live grid state?
  • Is there a warm-up runbook that hydrates the data grid before re-enabling the messaging grid?
  • Are write-behind lag alerts and durability levels defined per object (offer vs completed trip)?
  • Has the team compared grid operations cost against Redis-plus-DB for non-surge baseload?

Example use cases

  • Illustrative scenario — RideRelay stadium surge (messaging + processing + data grids): The messaging grid steers “Match” RPCs to PUs; each PU scores nearby drivers from its data-grid replica; accepted offers decrement slot counters via entry processors; the data writer persists trip starts for downstream billing.
  • Illustrative scenario — RideRelay airport queue flash: Holiday return traffic spikes concurrent matches; elastic PU count tracks queue depth while replicated surge multipliers stay consistent across units without a central Redis choke point.
  • Illustrative scenario — RideRelay post-surge reconcile: After load drops, write-behind drains to the warehouse; ops scale PUs down knowing the RDBMS never sat in the critical match path during the spike.

Related patterns

  • Event-Driven Architecture — The messaging grid in SBA is often event-driven; write-behind persistence can be event-triggered.
