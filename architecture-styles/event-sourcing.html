Event Sourcing

Instead of persisting current state, store every state change as an immutable domain event. Current state is derived by replaying the event stream.

⏱ 10 min read

What it is

In event sourcing, the system of record is an append-only log of domain events, not a row that gets overwritten in place.

Instead of updating orders.status to SHIPPED, Meridian Commerce appends OrderPlaced, PaymentConfirmed, and OrderShipped to an Order aggregate stream. Current order state is computed by replaying those events (often from a snapshot plus tail events).

Greg Young popularized the pattern alongside CQRS. Fulfillment dashboards and customer “where is my order?” views are projections built from the same stream — they are not authoritative copies of truth.

Why it exists

Meridian’s support team kept asking “who changed this order to cancelled?” UPDATE statements in Postgres erased the story; audit tables lagged production schema.

Event sourcing makes the history the product: every transition is an immutable fact. Compliance can replay PaymentConfirmed events; engineering can rebuild a new “delayed shipment” read model from five years of streams without retroactive ETL.

Temporal questions become mechanical — replay events until timestamp T to see what the customer was promised before a warehouse outage.

When to use

  • Use event sourcing when Meridian-style audit requires a tamper-evident narrative of order and payment transitions, not only current status.
  • Use event sourcing when the domain thinks in events first — checkout, capture, ship, return — not in silent column updates.
  • Use event sourcing when product needs “state as of time T” for disputes or SLA investigations.
  • Use event sourcing when future read models (fraud scoring, partner feeds) must be derived from history already collected.
  • Use event sourcing with CQRS so Order write streams feed catalog, fulfillment, and analytics projectors asynchronously.

When not to use

  • Skip event sourcing for Meridian’s static reference data where history adds no business value.
  • Skip event sourcing when a single aggregate would accumulate huge event rates without a snapshot strategy — replay cost dominates.
  • Skip event sourcing until the team can operate an event store, upcasters, and projection rebuilds — mistakes in append-only logs are painful to undo.
  • Skip event sourcing for PII-heavy streams unless Meridian implements field-level encryption and key-deletion erasure policies compatible with GDPR.

Typical architecture

Meridian’s Order aggregate loads from its stream in EventStoreDB (or an append-only Postgres table), applies commands, appends new events, and publishes to projectors that maintain SQL views, search indexes, and ops dashboards.

Pros and cons

Pros

  • Meridian’s event store is the audit log — support does not maintain a parallel order_audit table.
  • Replay to timestamp T answers “what did we promise the customer before the carrier scan failed?”
  • New partner integrations can consume historical OrderShipped events without backfilling warehouses.
  • Engineers reproduce production order timelines in staging by copying streams.
  • Order aggregates align with DDD — commands emit past-tense domain facts.

Cons

  • Meridian operates EventStoreDB (or equivalent), snapshot jobs, and full replay drills — not trivial platform work.
  • Immutable events demand upcasters when OrderPlaced schema evolves — you cannot ALTER old rows.
  • GDPR erasure needs encrypted PII and key deletion, not DELETE FROM events.
  • Long-lived orders without snapshots slow load times as streams grow.
  • Most hires have not shipped event-sourced systems before — ramp time is real.

Implementation notes

Store choice: Meridian uses EventStoreDB for Order streams with expected-version concurrency; Kafka remains the integration bus to fulfillment, not the authoritative per-order stream.

Snapshots: After every 200 events (or nightly for hot orders), Meridian persists aggregate state plus stream position so reload replays only the tail.

Schema evolution: OrderPlaced v2 adds optional fields; upcasters map v1→v2 during replay so projectors read one shape.

Privacy: Ship-to names encrypt with per-customer keys; erasure deletes keys while events remain for non-PII analytics.

Projectors: Fulfillment and customer-history projectors dedupe on (streamId, eventNumber) because at-least-once delivery happens on the bus.

Common failure modes

  • No snapshots: A marketplace return loop appends thousands of events; checkout latency suffers on every load.
  • Breaking renames: Meridian renames lineItems without an upcaster; nightly replays fail silently.
  • Command-shaped events: The log stores ShipOrder instead of OrderShipped, blurring what actually happened.
  • UI field churn: One event per form keystroke bloats streams without domain meaning.
  • Non-idempotent projectors: Redelivered PaymentConfirmed double-counts revenue in ops dashboards.

Decision checklist

  • Do Meridian events use past-tense domain facts rather than imperative command names?
  • Is snapshot frequency defined for long-running Order aggregates?
  • Are schema versions and upcasters tested in CI replay fixtures?
  • Is there a documented GDPR approach for personal data inside streams?
  • Do all projectors handle duplicate delivery safely?
  • Can ops trigger a full projection rebuild from the Order event store?

Example use cases

Meridian’s Order aggregate is the reference story:

  • Placement: PlaceOrder appends OrderPlaced with line items and pricing snapshot at commit time.
  • Payment: PaymentConfirmed records processor references; the aggregate rejects ship commands until this event exists.
  • Fulfillment: OrderShipped and OrderDelivered extend the same stream; customer tracking UI is a projector, not source of truth.
  • Disputes: Support replays the stream to Tuesday 3pm to show promised delivery before granting a credit.
