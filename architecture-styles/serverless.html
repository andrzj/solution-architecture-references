Serverless Architecture

Event-triggered managed compute where the cloud provider handles provisioning, scaling, and operations. You write functions; the platform runs them on demand.

⏱ 9 min read

What it is

Serverless architecture runs your code on managed, event-triggered compute instead of servers you size and patch yourself.

Function-as-a-Service (FaaS) — AWS Lambda, Google Cloud Functions, Azure Functions — is the usual unit: each invocation is isolated, stateless, and billed for duration and memory, not idle uptime. Backend-as-a-Service (BaaS) covers the data and auth around it (DynamoDB, S3, API Gateway).

A regional ride-hailing product often runs surge-pricing recalculation and partner webhooks on managed functions. Friday-night demand spikes spin up thousands of concurrent invocations; Sunday afternoon can scale toward zero without an ops engineer resizing a fleet.

Why it exists

Early surge engines often live on a small container cluster that runs 24/7 to survive Friday peaks. Most hours the cluster idles, yet the organization still pays for it.

Serverless bills only when a function runs. EventBridge schedules and Kinesis or SQS bursts invoke functions for surge math and payment webhook validation — no capacity planning when a concert lets out downtown.

The trade-off is control: typical FaaS timeouts, cold starts, and cloud-specific triggers are constraints teams accept on bursty, event-shaped work, not on always-hot matching APIs (those often stay on containers).

When to use

  • Use serverless when workloads are intermittent or spiky and idle servers would waste budget.
  • Use serverless for event-shaped pipelines, including Kinesis-driven surge recalculation, S3 receipt archives, and HTTPS webhook handlers behind API Gateway.
  • Use serverless for scheduled jobs such as EventBridge rules that recompute zone multipliers every minute during peak hours.
  • Use serverless for low-traffic admin APIs where per-invocation billing beats a minimum container footprint.
  • Use serverless when the team wants the cloud provider to own patching, scaling, and AZ failover for stateless handlers.

When not to use

  • Avoid serverless for jobs longer than the platform’s execution cap (for example AWS Lambda’s 15-minute limit), such as full-day pricing backtests — run those on batch or container clusters instead.
  • Avoid serverless on user-facing paths where cold starts break tight latency SLOs — keep real-time matching on long-lived containers instead of functions.
  • Avoid serverless for steady high QPS where reserved containers or VMs beat per-ms billing at scale.
  • Avoid serverless when handlers need shared in-process mutable state; store surge multipliers in a database, not static globals inside a function.

Pros and cons

Pros

  • The platform team does not patch OS images or resize autoscaling groups for bursty function workloads.
  • Idle nights cost near zero because functions scale to zero between ride events.
  • Friday peaks add concurrency automatically instead of pre-provisioned EC2 headroom.
  • Individual functions deploy in minutes, which suits rapid pricing experiments.
  • Multi-AZ availability is inherited from AWS rather than custom failover scripts.

Cons

  • Cold starts can delay webhook ACKs unless runtimes are right-sized or provisioned concurrency covers hot paths.
  • Lambda, EventBridge, and Step Functions APIs tie migration to another cloud to a rewrite, not a lift-and-shift.
  • The 15-minute ceiling blocks long batch pricing simulations inside FaaS.
  • Local dev and step-debugging lag behind container workflows unless the team invests in SAM, Serverless Framework, or similar tooling.
  • Sustained millions of invocations per hour can exceed Fargate cost — finance reviews monthly curves.

Implementation notes

Runtime choice: A surge worker might use Node 20 with minimal dependencies to keep cold starts short on bursty invocations; JVM functions can use SnapStart only where the team accepts AWS-specific tuning.

Idempotency: Stripe webhooks may redeliver; the handler keys idempotency on event.id in DynamoDB before updating payout state.

Orchestration: Payout flows use Step Functions instead of Lambda→Lambda chains so failures surface in one workflow history.

State externalization: Zone multipliers and webhook dedupe keys live in DynamoDB; nothing critical sits in /tmp or static fields.

Observability: Each function exports p99 duration, error rate, and cold-start metrics per alias — aggregate dashboards hide surge regressions.

Common failure modes

  • Cold-start herd on deploy: A new function version cold-starts across all zones at once — use weighted aliases to warm gradually.
  • Silent DLQ growth: Webhook Lambda failures enqueue to SQS DLQ without paging — finance discovers missing payouts days later.
  • Function chaining: Surge Lambda invokes payout Lambda invokes notify Lambda with no central state — Step Functions should own the saga.
  • Runaway concurrency: A mis-tuned Kinesis iterator or EventBridge rule retriggers surge math in a loop — account-level concurrency caps limit blast radius.
  • VPC latency: Functions in a VPC for legacy RDS access pay ENI setup cost — prefer public managed datastore access for webhook handlers where policy allows.

Decision checklist

  • Is the workload bursty or event-driven rather than continuously loaded at high QPS?
  • Are cold-start budgets acceptable, or is provisioned concurrency allocated for webhook ACK paths?
  • Are handlers stateless with dedupe keys for at-least-once event sources?
  • Do async triggers have DLQs with alerts before money-moving code runs?
  • Do multi-step flows use Step Functions (or equivalent) instead of opaque Lambda chains?
  • Has the team documented lock-in and a migration path if invocation rates outgrow FaaS economics?
