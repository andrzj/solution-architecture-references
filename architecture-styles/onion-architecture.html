Architecture Styles Domain-Centric

Onion Architecture

Jeffrey Palermo's domain-centric layering model where all dependencies point toward the Domain Model at the center, and infrastructure is the outermost ring.

⏱ 7 min read

What it is

Onion Architecture is Jeffrey Palermo’s domain-centric layering model: dependencies point inward toward the Domain Model at the center, with Domain Services, Application Services, and Infrastructure as outward rings.

Subscription billing systems are a common fit: the inner Domain Model holds aggregates such as Invoice, Subscription, and UsageRecord. Domain Services such as ProrationCalculator and TaxLineAllocator express cross-aggregate math with no I/O. Application Services such as IssueInvoiceService load aggregates, invoke domain services, start transactions, and call repository interfaces. Infrastructure implements repositories, payment gateways, and HTTP — never referenced from the domain model.

Unlike Hexagonal’s symmetric ports metaphor, Onion emphasizes where behavior lives: pure rules in the domain model and domain services, orchestration in application services, technical detail in infrastructure.

Why it exists

Database-first designs let EF Core or Hibernate entities become the “real” model. Teams often spread proration formulas across application services and UI pages because no layer owned “billing math” explicitly.

Onion Architecture makes the domain model immovable. Every change asks whether logic belongs in an entity, a domain service, or application orchestration before someone adds another if beside a repository call.

The explicit Domain Services ring matters when proration across multiple Subscription lines, tax jurisdiction splits, and credit-note pairing involve several aggregates but still must stay pure and fast to test — that is domain service territory, not HTTP orchestration.

When to use

  • Use Onion Architecture when cross-aggregate billing rules deserve a dedicated Domain Services layer separate from Application Services.
  • Use it when the team wants clearer placement than a two-tier core-versus-adapters split provides.
  • Use it for DDD-aligned billing where aggregates, repositories, and domain services are already part of the ubiquitous language.
  • Use it when invoice and dunning invariants must compile and test with zero infrastructure references.
  • Use it when .NET or Java module boundaries can enforce ring dependencies through project references or ArchUnit.

When not to use

  • Skip the extra layer when billing is mostly CRUD on invoice headers with no proration or tax rules to isolate.
  • Skip mixing Onion and Hexagonal metaphors in the same codebase without a written layering guide — choose one vocabulary.
  • Skip the pattern when the Domain Services versus Application Services distinction would not clarify any real workflow.

Pros and cons

Pros

  • ProrationCalculator and similar domain services have a named home instead of hiding in application classes.
  • The domain model runs unit tests with no mocks when behavior lives on entities and value objects.
  • Infrastructure such as SQL invoice stores or payment clients can be replaced without touching proration rules.
  • Layer names align with DDD vocabulary finance and engineering already share.
  • Clear rings reduce “where does this invoice rule go?” debates during code review.

Cons

  • Onion is close to Clean Architecture — teams must pick one narrative and stay consistent.
  • Domain Services versus Application Services boundaries blur without written team conventions.
  • Extra mapping between layer DTOs adds friction on simple invoice line CRUD.
  • Developers may over-create domain service classes when logic belongs on a single aggregate.

Implementation notes

Domain Services stay pure: ProrationCalculator accepts Subscription and UsageRecord instances passed in by IssueInvoiceService; it never calls IInvoiceRepository itself.

Application Services orchestrate: IssueInvoiceService opens a transaction, loads aggregates, calls domain services, persists through repository interfaces, and publishes InvoiceIssued — it does not embed tax formulas.

Repository interfaces live in the domain model ring: IInvoiceRepository sits with aggregates; EF Core or Dapper implementations live in Infrastructure.

Enforce with projects or ArchUnit: Separate class libraries with inward-only references, plus ArchUnit rules in CI, keep rings honest in Java or .NET solutions.

Common failure modes

  • Domain services that query: ProrationCalculator that loads subscriptions from SQL is really an application service in disguise.
  • Business rules in application services: Tax allocation if chains in IssueInvoiceService belong in TaxLineAllocator or entities.
  • ORM on entities: EF attributes on Invoice break the dependency-free domain model promise.
  • One DTO everywhere: Reusing API invoice JSON through all four rings couples Billing to external field names.
  • Unresolved layer disputes: Recurring “domain or application?” arguments signal missing ADRs or team guidelines.

Decision checklist

  • Is the domain model free of ORM, web, and messaging framework imports?
  • Do domain services operate only on objects passed as parameters, with no I/O?
  • Do application services handle transactions, events, and security while delegating rules inward?
  • Are repository interfaces defined beside aggregates, not in infrastructure projects?
  • Is there a short document stating when Billing logic belongs in Domain Services versus Application Services?
  • Do architecture tests enforce ring dependencies in CI?

Related patterns

  • Clean Architecture — Uncle Bob's closely related concentric ring model; choose one and apply it consistently.
  • Hexagonal Architecture — Ports-and-adapters formulation of the same principles; more flexible layer decomposition.
  • CQRS — Often applied within Application Services to separate command and query handling paths.
