Architecture Styles Clean Code

Clean Architecture

Concentric dependency layers organized so that the domain is at the core, use cases in the next ring, and frameworks and drivers on the outermost ring. Dependencies only point inward.

⏱ 9 min read

What it is

Clean Architecture organizes code as concentric rings so business rules sit at the center and every outer layer depends inward. The Dependency Rule is the constraint: source code dependencies may only point toward higher-level policy — never toward frameworks, UI, or databases.

A dispatch-scheduling service is a common fit. Inner Entities such as Shipment, PickupWindow, and CarrierCommitment encode carrier cutoffs and hazmat holds. Use Case Interactors such as SchedulePickupInteractor and RescheduleForWeatherInteractor orchestrate those entities through gateway interfaces. Interface Adapters translate mobile operations HTTP, routing Kafka events, and Postgres JDBC — but inner rings never import those types.

Nothing in an inner circle may know about an outer circle. That compile-time boundary keeps Spring controllers and JPA mappings from leaking into rules that must stay stable across framework upgrades.

Why it exists

Robert C. Martin observed that many codebases treat the framework as the architectural center — the Spring Boot application or the Rails app — when the framework is only a delivery mechanism. Business logic drifts into controllers, services bend to ORM constraints, and tests require spinning up the whole stack.

Teams hit that wall when scheduling rules had to run through a mobile ops REST API, a nightly CLI rebalancer, and async RouteReoptimized replays from a routing service. Carrier SLA logic duplicated across adapters until the dispatch team recentralized it in interactors and entities. Clean Architecture makes the business rules the center and treats frameworks as plugins.

The goals match Hexagonal Architecture — testable domain, swappable UI, swappable database, swappable externals — with explicit ring names: Entities, Use Cases, Gateways, and Presenters.

When to use

  • Apply Clean Architecture when scheduling invariants must survive framework and infrastructure churn without rewriting business rules.
  • Apply it when the same interactors must serve multiple delivery mechanisms, such as a mobile ops REST API, internal CLI tools, and Kafka-driven replays.
  • Apply it when the dispatch team practices TDD and needs interactors and entities runnable with in-memory gateways only.
  • Apply it when carrier commitments and hazmat rules must be auditable apart from Postgres schemas or Kafka topic layouts.
  • Apply it when ArchUnit or equivalent can enforce the Dependency Rule in CI for a long-lived service.

When not to use

  • Skip the pattern for CRUD-only endpoints where interactors would delegate straight to repositories with no scheduling rules to protect.
  • Skip it for throwaway pilots where ring ceremony slows learning more than it prevents real coupling.
  • Skip it until the team understands dependency inversion, because rings without enforcement become folder labels rather than boundaries.

Pros and cons

Pros

  • Carrier cutoff and hazmat rules live in Entities and interactors that run without Postgres, Kafka, or Spring on the classpath.
  • The dispatch team can swap ORM mappings or move from REST callbacks to gRPC without touching SchedulePickupInteractor.
  • Named roles — Interactor, Gateway, Presenter — give code review a shared vocabulary when mobile ops and routing both call scheduling.
  • One RescheduleForWeatherInteractor can serve storm dashboards, batch replan jobs, and integration tests with different outer adapters.
  • The layout reinforces SOLID, especially Dependency Inversion, when multiple squads touch the same service repository.

Cons

  • Each scheduling flow tends to need Input Port, Output Port, Interactor, and request/response models — ceremony that hurts thin CRUD paths.
  • Layer mapping between HTTP DTOs and domain objects adds work when no invariant sits between them.
  • The Presenter pattern feels awkward for synchronous REST unless the team standardizes on returning response models from interactors.
  • Many small classes remain hard to navigate without a package convention such as scheduling.usecases.* and architecture tests that guard imports.

Implementation notes

Model scheduling as use cases: Define SchedulePickupInputPort that HTTP controllers call. SchedulePickupInteractor accepts a plain SchedulePickupRequest, loads or creates a Shipment entity, enforces CarrierCommitment windows, and calls ShipmentRepository and CarrierCapacityGateway interfaces declared in the use case ring.

Keep entities framework-free: Shipment and PickupWindow have no JPA, Jackson, or Lombok infrastructure annotations. Persistence adapters in the outer ring map rows to entities at the repository boundary.

Wire at the composition root: A Spring @Configuration module binds Postgres ShipmentRepositoryImpl and in-memory fakes for CI. Inner packages never reference org.springframework.

Pragmatic presenters: Many teams let interactors return SchedulePickupResponse directly to controllers instead of pushing through an Output Port — slightly less pure, far easier for mobile and ops APIs.

Use-case transactions: One interactor equals one consistency boundary—open the unit of work at the use-case boundary, commit after persistence ports succeed, roll back before any outbound gateway call unless outbox is used. Never span a single HTTP request across two database transactions without explicit saga documentation.

Cross-cutting without framework leakage: Auth, metrics, and validation via decorators, middleware at the adapter layer, or pipeline behaviors that call only use-case interfaces—entities stay free of javax or spring imports.

Port versioning: DTOs crossing use-case boundaries version independently of OpenAPI—CLI and async drivers consume the same interactors; deprecate use-case inputs before REST fields.

Testing pyramid: Mutation or property tests on scheduling invariants in the entity ring; contract tests on adapters with Testcontainers for Postgres; acceptance tests through primary ports only.

When NOT to add rings: Scripts and internal cron with no alternate delivery channels do not need full port fan-out—apply Clean Architecture where multiple drivers (HTTP, Kafka, CLI) genuinely share core rules.

Common failure modes

  • HTTP DTOs in interactors: Passing SchedulePickupHttpRequest into the use case ring couples scheduling rules to the web framework.
  • JPA on Shipment: Hibernate annotations on entities break the Dependency Rule at the core and invite lazy-load surprises in domain code.
  • Anemic interactors: GetShipmentByIdInteractor that only calls the repository adds rings without protecting any scheduling invariant.
  • Repositories in the wrong ring: Concrete PostgresShipmentRepository living beside interactors lets infrastructure imports creep inward.
  • No architecture tests: Without ArchUnit, the domain package slowly accumulates Kafka and Spring imports until rings are fiction.

Decision checklist

  • Can you run every scheduling interactor test with in-memory gateways and no database?
  • Are Shipment, PickupWindow, and related entities free of framework imports?
  • Do request and response models contain only plain data, not HTTP framework or Kafka types?
  • Are gateway interfaces defined in the use case layer, not under infrastructure?
  • Does CI enforce the Dependency Rule with ArchUnit or an equivalent tool?
  • Is there one composition root that wires adapters without inner-ring @Autowired?

Example use cases

  • Illustrative scenario — At Northwind Logistics, the dispatch-scheduling service applies Clean Architecture to shipment scheduling. Shipment, PickupWindow, and CarrierCommitment entities enforce cutoffs, hazmat pairing, and freeze windows without knowing Postgres or Kafka.
  • Illustrative scenario — Northwind hit coupling when scheduling rules had to run through FieldOps REST, a nightly CLI rebalancer, and async RouteReoptimized replays from Routing — carrier SLA logic duplicated until the team recentralized it in interactors.
  • Illustrative scenario — SchedulePickupInteractor and RescheduleForWeatherInteractor orchestrate entities and call ShipmentRepository and WeatherAlertGateway interfaces declared in the use case ring.
  • Illustrative scenario — FieldOps REST controllers, Routing event consumers, and JDBC repositories sit in the outer ring; the same interactors power storm rebalancing CLI jobs and FieldOps mobile scheduling without duplicating carrier logic.

Related patterns

  • Hexagonal Architecture — The ports-and-adapters formulation of the same dependency inversion principle; less prescriptive ring decomposition.
  • Onion Architecture — Jeffrey Palermo's variant; similar concepts but with explicit Domain Services and Application Services layers.
  • CQRS — Frequently applied inside the Use Cases layer to separate command and query interactors.
